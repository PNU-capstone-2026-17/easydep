# 중립 앱 상태 VM 교체 실험 결과

## 결론

AWS·Azure·GCP에서 모두 다음 경로가 한 번씩 통과했다.

```text
동일 App VM과 동일 App 이미지
→ State VM A에 값 기록
→ State VM A 삭제
→ 같은 독립 데이터 디스크를 State VM B에 연결
→ 파일시스템 마운트 및 PostgreSQL 데이터 경로 연결
→ App 컨테이너에 State VM B의 사설 주소만 다시 주입
→ 교체 전에 기록한 값 조회
→ 실행 소유 리소스 잔여 0
```

따라서 현재 범위에서 다음 조건부 의존성을 개발 근거로 사용할 수 있다.

- PostgreSQL 실행에는 쓰기 가능한 파일시스템이 필요하지만 별도 데이터 디스크 자체는 필수가 아니다.
- VM 교체 뒤에도 데이터를 보존하려면 VM과 수명이 분리된 데이터 디스크가 필요하다.
- 별도 디스크를 선택하면 연결, 파일시스템 준비, 마운트, PostgreSQL 데이터 경로 연결이 모두 필요하다.
- State VM 교체로 endpoint가 바뀌면 App 런타임 연결 정보를 갱신해야 한다.
- 이 갱신은 App 코드나 이미지를 다시 만드는 작업이 아니라 배포 설정의 하위 수정으로 처리할 수 있다.

이 결과는 자동 장애조치나 고가용성을 뜻하지 않는다. State VM을 교체하는 동안 서비스는 중단됐고 App 컨테이너도 새 endpoint를 받기 위해 재시작했다.

## 실험 질문과 합격 기준

실험은 특정 업무 도메인 대신 일반 key/value API를 사용했다. App은 HTTP로 값을 쓰고 읽으며 State workload인 PostgreSQL은 독립 데이터 디스크를 사용했다.

합격 기준은 다음 다섯 조건을 모두 만족하는 것이다.

1. 교체 전에 App을 통한 값 쓰기와 읽기가 성공한다.
2. 최초 State VM을 삭제하고 동일한 데이터 디스크를 교체 State VM에 연결한다.
3. 기존 파일시스템을 다시 포맷하지 않고 마운트해 PostgreSQL을 시작한다.
4. App VM과 로컬 App 이미지 ID를 유지하고 새 State endpoint만 주입한다.
5. 교체 전에 쓴 값을 App을 통해 다시 읽고, 종료 뒤 해당 실행 ID 소유 리소스가 0개다.

## CSP별 관찰

### AWS

- EBS를 State A와 같은 가용 영역에 만들고 연결했다.
- State A 종료 완료까지 79.3초, EBS가 다시 연결 가능한 상태가 되는 데 3.9초가 걸렸다.
- State B의 도구 준비가 82.3초로 가장 긴 복구 구간이었다.
- 기존 EBS 마운트와 PostgreSQL 준비는 4.4초, App 재바인딩과 기존 값 조회는 6.9초였다.
- EC2 user-data는 16 KiB 한도가 있으므로 Docker 준비만 user-data에 두고 App 이미지 빌드는 관리 단계로 분리했다. 이는 앱별 축약이 아니라 공급자 전송 경계의 일반 제약 처리다.

### Azure

- Managed Disk는 State A 삭제 뒤 3.9초 만에 재연결 가능 상태가 됐다.
- State B 생성 47.4초, 디스크 연결 12.6초, PostgreSQL 준비 101.9초였다.
- App 재바인딩과 기존 값 조회는 71.3초였다.
- 전체 시간이 가장 긴 주된 이유는 Managed Run Command 호출마다 발생한 관리 채널 오버헤드와 Resource Group 정리 시간이다. App 연산 시간으로 해석하면 안 된다.

### GCP

- Persistent Disk는 State A 삭제 뒤 8.2초 만에 재사용할 수 있었다.
- State B 생성 20.3초, PostgreSQL 준비 98.9초였다.
- instance metadata로 새 State 주소를 전달한 뒤 동일 이미지 App 재바인딩과 기존 값 조회는 8.7초였다.
- 직렬 콘솔의 임의 마지막 표식 대신 PostgreSQL 연결 수락과 startup script 정상 종료를 함께 State 준비 기준으로 사용했다.

## 해석 범위

이 실험으로 확인한 것은 복구 가능성, 데이터 수명 분리, 디스크 실현 경로, 런타임 endpoint 재주입이다. 다음 항목은 확인하지 않았다.

- 자동 장애 감지와 자동 교체
- 무중단 전환, RTO 또는 RPO
- PostgreSQL 복제와 상태 계층 고가용성
- 다중 영역·다중 리전 장애
- hot detach
- 관리형 데이터베이스
- 수강신청의 정원·중복·동시성 규칙
- 성능과 적정 VM 사양

따라서 중립 앱 의존성 실험은 이 E3로 종료하고, 다음 평가는 수강신청 업무 기능·동시성 및 실제 부하에 따른 별도 검증으로 분리한다.
