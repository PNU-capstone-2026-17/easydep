# 클래스 설계 temperature 비교 결과 (2026-08-29)

## 목적

같은 요구사항으로 클래스 설계를 생성하면서 `temperature`만 `0.0`, `0.2`, `1.0`으로
바꿔 실행 시간, LLM 호출 수, token 사용량과 수리 횟수를 비교했다.

공통 조건은 다음과 같다.

- 입력: 고정 `e1-aws` 요구사항
- 모델: `openai/gpt-oss-120b`
- cache: 비어 있는 process-local cache
- SDK 재시도: 0회
- reasoning: inventory, operation, call plan 모두 `medium`
- 출력 한도: inventory 16,384, operation 8,192, call plan 8,192

여기서 `로컬 수리`는 클래스 생성 서비스 안에서 수행한 JSON 형식 수리와 설계 내용
수리를 뜻한다. `최초 투영 검사 발견`은 생성된 클래스 모델을 시퀀스 모델로 한 번 변환한
직후 발견한 흐름 순서 문제의 수다.

`0.2`는 `0.0`보다 전체 token을 9.9%, 시간을 23.9% 줄였다. 호출 수와 로컬 수리 횟수는
같았고 출력 한도에 도달한 응답도 없었다. `1.0`은 `0.2`보다 호출, 수리와 token 사용량이
모두 많았다.

## 해석할 때 주의할 점

이번 비교는 전체 제품 그래프를 실행한 실험이 아니다. 클래스 생성 서비스 내부의 JSON·설계
수리는 실행했지만, 최초 시퀀스 투영 검사에서 발견된 문제를 제품 그래프가 다시 LLM에 맡겨
고치는 자동 수리 루프는 실행하지 않았다.

따라서 `0.2`와 `1.0`에서 발견 사항이 남았다는 결과만으로 전체 파이프라인이 완주하지
못한다고 판단할 수 없다. 이 표는 수리 전 최초 결과의 품질과 생성 비용을 비교한 자료다.
완주율을 비교하려면 같은 입력을 프론트엔드가 사용하는 API 경로로 실행하고 자동 수리가
끝난 뒤의 최종 상태, 추가 호출 수, 추가 token과 전체 시간을 함께 측정해야 한다.

이번 비교만으로 기본 `temperature`는 변경하지 않았다. 실제 실행 기록은 Git에서 제외되는
다음 경로에 보관했다.
