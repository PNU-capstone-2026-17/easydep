# 수강신청 사례연구 요구사항

이 디렉터리는 기존 P1~P3과 분리한 수강신청 PoC 입력을 둔다. P1~P3은 범용
Docker-on-VM 회귀 사례이고, 이 입력은 순차 설계 산출물과 앱–클라우드 정합성을 확인할
사례연구 후보다. 아직 동결된 확인 실험 suite나 완료된 실험 결과는 아니다.

## 작성 원칙

요구사항의 문장 형태와 입도는 PURE의 공개 SRS 문서들을 참고했다.

> Ferrari, Spagnolo, Gnesi. “PURE: A Dataset of Public Requirements Documents.”
> RE'17, pp. 502–505. DOI 10.5281/zenodo.7118517.

PURE는 수강신청이나 클라우드 네이티브 요구사항의 근거가 아니다. 따라서 PURE 문장을
복사하거나 클라우드 구조의 대표성 근거로 사용하지 않고, 다음 형식만 참고했다.

- 한 문장에는 한 가지 사용자 기능 또는 품질 제약을 적는다.
- 기능 요구사항은 사용자와 시스템의 관찰 가능한 행동으로 적는다.
- 비기능 요구사항은 구현 제품이 아니라 보존해야 할 성질로 적는다.
- 설계·구현·시험이 결정할 내용은 사용자 요구사항에 미리 답으로 넣지 않는다.

이에 따라 API 경로, HTTP 상태코드, Java·Spring Boot, PostgreSQL 버전, 환경 변수 이름,
seed 데이터와 동시 시험 절차는 요구사항에서 제외했다. 이들은 요구사항 분석 이후 설계
계약이나 독립 평가 oracle에서 정한다.

## 기능 요구사항

| ID | 사람이 작성하는 요구사항 |
|---|---|
| `FR-01` | 학생은 개설된 강좌와 각 강좌의 남은 좌석 수를 조회할 수 있어야 한다. |
| `FR-02` | 학생은 강좌명, 담당 교원, 수업 시간, 정원과 남은 좌석을 포함한 강좌 상세 정보를 조회할 수 있어야 한다. |
| `FR-03` | 학생은 남은 좌석이 있는 강좌를 신청할 수 있어야 한다. |
| `FR-04` | 시스템은 신청 성공 여부를 학생에게 알려야 하며, 실패한 경우 그 이유를 알려야 한다. |
| `FR-05` | 시스템은 같은 학생을 같은 강좌에 두 번 이상 등록해서는 안 된다. |
| `FR-06` | 시스템은 강좌 정원을 초과하는 신청을 받아서는 안 된다. |
| `FR-07` | 학생은 자신이 신청한 강좌 목록을 조회할 수 있어야 한다. |
| `FR-08` | 학생은 수강신청 기간 안에 자신의 신청을 취소할 수 있어야 한다. |
| `FR-09` | 신청이 취소되면 해당 강좌의 남은 좌석이 다시 한 자리 늘어나야 한다. |

강좌 개설, 학생 정보 관리, 로그인과 권한 부여는 대학의 기존 학사 시스템이 담당한다고
가정하며 이 PoC의 기능 범위에서는 제외한다.

## 비기능 요구사항

| ID | 사람이 작성하는 요구사항 |
|---|---|
| `NFR-01` | 여러 학생이 마지막 한 자리를 동시에 신청하더라도 정원을 초과해서는 안 된다. |
| `NFR-02` | 한 학생이 같은 강좌를 동시에 여러 번 신청하더라도 최종 신청은 하나만 남아야 한다. |
| `NFR-03` | 강좌와 수강신청 정보는 애플리케이션이나 서버가 다시 시작되어도 유실되어서는 안 된다. |
| `NFR-04` | 애플리케이션은 Linux 가상머신에서 실행 가능한 컨테이너로 배포할 수 있어야 한다. |
| `NFR-05` | 애플리케이션 인스턴스가 교체되더라도 다른 인스턴스가 후속 요청을 처리할 수 있도록 권위 있는 업무 상태를 한 인스턴스의 로컬 저장소에만 두어서는 안 된다. |
| `NFR-06` | 수강신청 정보가 저장되는 시스템은 인터넷에서 직접 접근할 수 없어야 한다. |
| `NFR-07` | 배포 환경마다 달라지는 설정과 비밀정보는 애플리케이션 산출물에 포함하지 않고 실행 시점에 제공할 수 있어야 한다. |
| `NFR-08` | 운영 시스템은 애플리케이션이 요청을 처리할 준비가 되었는지 자동으로 확인할 수 있어야 한다. |
| `NFR-09` | 서비스 운영에 필요한 클라우드 환경은 버전 관리되는 인프라 정의로 동일하게 생성하고 제거할 수 있어야 한다. |
| `NFR-10-E1` | 초기 시험 운영에서는 애플리케이션 서버 장애로 인한 일시적인 서비스 중단을 허용한다. |
| `NFR-10-E2` | 수강신청 기간에는 애플리케이션 서버 한 대에 장애가 발생해도 학생이 조회·신청·취소 기능을 계속 사용할 수 있어야 한다. |

생산 부하를 뒷받침할 근거가 없으므로 RPS·p95 목표를 임의로 만들지 않는다. 복구 시간도
현재 측정 대상이 아니므로 수치 요구사항으로 두지 않는다.

`NFR-10-E1`과 `NFR-10-E2`는 동시에 쓰는 요구사항이 아니라 배포 조건별 대안이다. 가용성은
별도의 요구사항 종류가 아니라 비기능 요구사항으로 취급한다. E2의 가용성 범위는
애플리케이션 서버 장애까지이며 데이터 저장 서버 장애 복구는 이번 PoC에서 요구하지 않는다.
따라서 E2 결과도 종단 고가용성이라고 부르지 않는다.

## 클라우드 배포 제약의 경계

이 연구에서 말하는 클라우드 네이티브 제약은 범용 정의 전체가 아니라 Docker-on-VM 범위의
관찰 가능한 배포 성질이다.

- `NFR-04`: 컨테이너화와 Linux VM 실행 경계
- `NFR-05`: 교체 가능한 앱 인스턴스와 권위 상태 분리
- `NFR-06`: 데이터 계층의 비공개 배치
- `NFR-07`: 설정·비밀정보의 실행 시점 주입
- `NFR-08`: 자동 health 판단
- `NFR-09`: 인프라의 재현 가능한 생성·제거
- `NFR-10`: 앱 계층의 가용성 목표

HTTPS/TLS, 인증서 발급·갱신과 도메인 관리는 현재 연구 범위에서 제외한다. 실제 cloud 시험은
합성 데이터와 실행 후 제거하는 임시 HTTP endpoint만 사용한다. 따라서 결과를 운영 환경의
보안 적합성이나 프로덕션 배포 준비 완료의 근거로 사용하지 않는다. 사용자가 HTTPS를
명시적으로 요구하면 시스템은 HTTP로 낮추지 않고 지원 범위 밖으로 판정한다.

선택 CSP·Region과 예산, Docker-on-Linux-VM·Terraform 범위, 관리형 DB·Kubernetes·서버리스
제외는 `cloudConstraints`와 고정 실험 범위로 별도 전달한다. 반면 특정 ASG·VMSS·MIG,
VM 수, Zone 수, Load Balancer 제품명은 요구사항에 넣지 않는다. 이러한 리소스 선택은 위
비기능 목표와 CSP 제약으로부터 설계 단계가 도출해야 한다.

## 실행 입력과 평가 정보의 분리

- [`e1-course-registration-aws.json`](e1-course-registration-aws.json): E1 자연어 요구사항
- [`e2-course-registration-aws.json`](e2-course-registration-aws.json): E2 자연어 요구사항

두 JSON의 `requirements`는 위 내용을 영어 자연어로 옮긴 시스템 입력이다. `cloudConstraints`는
사용자가 별도로 제공하는 배포 위치·예산·운영 범위이며 기능 요구사항과 구분한다.

HTTP 계약, 초기 데이터, 동시 요청 barrier, 최종 row 수 확인과 오류 응답 판정은 시스템에
정답으로 주지 않고 후속 독립 평가 oracle에 둔다. 먼저 E1 로컬 종단이 성공한 뒤 같은
업무 요구를 유지한 채 Azure·GCP 좌표로 확장한다.

[`business-oracle.json`](business-oracle.json)은 설계 단계에서 확정된 OpenAPI와 합성 초기
데이터를 외부 black-box 판정으로 옮긴 파일이다. 순차 기능뿐 아니라 마지막 좌석과 중복 신청을
barrier 동시 요청으로 실행하고, 응답 상태 개수와 후속 조회 상태를 함께 확인한다. 같은 파일을
로컬 Docker endpoint와 실제 cloud endpoint에 사용하며, 애플리케이션 내부 단위시험을 성공
근거로 대신하지 않는다.
