# 에이전트의 클라우드 의존성 지식 활용 실험

## 목적

리소스 모델이 정확하더라도 에이전트가 이를 활용하지 못하면 최종 IaC는 좋아지지 않는다. 반대로 큰 지식 묶음을 프롬프트에 넣어 성능이 좋아져도, 그것이 정확한 검색 때문인지 단순 토큰 증가 때문인지 알기 어렵다. 따라서 다음 두 효과를 분리한다.

1. 동일한 근거 모델을 제공했을 때 지식 자체가 주는 효과
2. 직접 프롬프트, 함수 도구, MCP처럼 지식을 전달하는 방식이 주는 효과

## 공통 조회 경계

모든 지식 제공 실험군은 `app.core.cloudkb.depkb.knowledge_access.query_knowledge`만 사용한다. 이 함수는 공급자, 시작 리소스, capability ID를 받아 다음을 반환한다.

- 공식 문서로 확인된 의존관계와 필수성 판정 상태
- 선택한 capability의 공급자별 다대다 실현 구성
- 두 정본 파일의 동결 해시

동일 인자에는 항상 동일 결과가 나와야 한다. MCP가 별도 KB를 읽거나 함수 도구만 추가 설명을 받는 것을 금지한다.

## 비교 조건

| 조건 | 지식 접근 방식 | 해석 |
|---|---|---|
| no-knowledge-control | 접근 없음 | 지식 제공의 전체 효과 기준 |
| direct-context | 관련 묶음을 프롬프트 JSON에 직접 주입 | 현재 EasyDep 방식 |
| on-demand-tool | 모델이 함수 도구를 필요할 때 호출 | 검색 선택과 질의 형성 효과 |
| on-demand-mcp | 동일 조회를 MCP 도구로 호출 | 함수 도구 대비 전달 프로토콜 효과 |

함수 도구와 MCP는 이름만 비슷한 별도 기능이 아니라 입력·출력·오류·최대 호출 횟수까지 같아야 한다. 이 둘의 차이를 “MCP 지식이 더 우수하다”로 해석하지 않고, 발견 가능성·호출 비용·프로토콜 오버헤드의 차이로 해석한다.

## API 및 전송 경계

현재 EasyDep의 IaC 생성기는 Chat Completions에 텍스트 한 번을 보내는 경로다. 이 경로에서
호스트 프로그램이 모델 대신 조회 함수를 호출하고 결과를 프롬프트에 붙인 뒤 이를 `MCP`라고
부르는 것은 금지한다. 그런 구현은 `direct-context`의 다른 직렬화일 뿐 모델의 도구 발견·호출
선택이나 MCP 전송 비용을 측정하지 못한다.

OpenAI 공식 문서는 도구 호출과 Remote MCP를 Responses API의 도구로 제공하며, 모델별
지원 기능을 별도로 명시한다. 따라서 `on-demand-tool`과 `on-demand-mcp`를 확인 실험에
포함하려면 다음 조건을 모두 사전 점검한다.

1. 같은 동결 모델 식별자와 같은 API 엔드포인트가 Responses API를 지원한다.
2. 그 모델이 함수 호출과 MCP를 모두 지원한다.
3. 두 실험군이 같은 도구 이름, 설명, JSON 입력 스키마, 조회 결과, 오류 형식, 호출 상한을 쓴다.
4. MCP 서버는 읽기 전용이며 `query_knowledge` 외의 데이터 원천이나 도구를 노출하지 않는다.
5. API 요청·응답 기록에서 실제 함수 호출 또는 MCP 호출을 구별해 세고, 호출이 0회인 실행도
   그대로 결과에 포함한다.

하나라도 확인되지 않으면 프로토콜 상태를 `development`로 유지한다. 함수 도구만 가능한
엔드포인트에서는 `no-knowledge-control`, `direct-context`, `on-demand-tool`의 개발
실험은 할 수 있지만 이를 4군 확인 실험으로 보고하지 않는다. 다른 모델이나 엔드포인트로 MCP
실험군만 실행하는 것도 모델·실행 환경 교란 때문에 금지한다.

근거는 [OpenAI API 개발자 빠른 시작의 도구 확장 설명](https://platform.openai.com/docs/quickstart/make-your-first-api-request)과
[OpenAI 모델별 도구 지원 표](https://developers.openai.com/api/docs/models)를 동결 시점에 다시
확인하고, 사용한 모델 식별자와 API 기능 점검 결과를 실행 매니페스트에 보존한다.

## 공정성 통제

- 같은 사례, 모델, temperature, seed, 시간 제한과 최종 산출물 계약을 사용한다.
- 모든 조건에 같은 평가기를 적용한다.
- 도구 응답 토큰과 지연 시간도 전체 예산에 포함한다.
- 대조군은 숨은 검색이나 시스템 프롬프트의 지식 요약을 받지 않는다.
- 직접 주입군은 해당 사례에 필요한 행만 받으며 전체 KB를 덤프하지 않는다.
- 도구를 한 번도 호출하지 않은 실행과 실패 실행도 제외하지 않는다.
- holdout을 보기 전에 도구 설명, 인자, 호출 상한을 동결한다.

노트북 자원을 보호하기 위해 모든 실행은 직렬로 수행하고 백그라운드 작업자를 남기지 않는다. 실행 전 남은 디스크가 5 GiB 미만이면 새 작업을 시작하지 않으며, 실행별 임시 파일과 프로세스 트리는 성공·실패·시간 초과와 무관하게 정리한다. 연구 재현에 필요한 최종 산출물만 보존한다.

## 측정

주 지표는 공급자 구성요소 완전성, 공급자 스키마가 거부한 잘못된 클라우드 주장 수, 컨테이너 대표 기능 성공률이다. 다음 활용 지표를 함께 기록한다.

- 검색 재현율: oracle에 필요한 근거 중 실제 조회한 비율
- 지식 사용 정밀도: 최종 산출물에 반영한 근거 중 요구사항과 관련된 비율
- 미확정 필수성 승격 수: `candidate` 또는 `notAssessed`를 보편적 필수관계로 주장한 횟수
- 호출 횟수, 조회 바이트, 입력·출력 토큰, wall-clock 시간

검색 재현율이 높아도 기능이 실패할 수 있고, 호출 수가 적어도 필요한 근거만 정확히 찾았다면 우수할 수 있다. 따라서 단일 종합 점수로 합치지 않고 효과와 비용을 함께 보고한다.

## 실행 순서

먼저 개발 사례에서 도구 계약만 조정한다. 이후 계약과 지식 snapshot을 동결하고 기존 종단 실험과 별도의 구성요소 실험으로 실행한다. 현재 GCP 기능 개입이 끝나기 전에는 확정 결과를 만들지 않는다. 개입 완료 후에도 기존 3개 종단 비교군의 결과와 이 4개 접근 방식 결과를 한 표에서 같은 처치로 합치지 않는다.
