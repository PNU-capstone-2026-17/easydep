# VM 기반 졸업과제 연구·개발 계획

## 범위

`docs/research.md`의 목표를 AWS·Azure·GCP의 Docker-on-Linux-VM 범위에서 구현한다. EasyDep은 근거 기반 벤더 의존성 지식, 앱–클라우드 계약, 역할별 에이전트와 체크포인트를 사용해 누락과 불일치를 조기에 찾고 실패한 하위 작업부터 복구한다.

범용 클라우드 메타모델, 모든 합법 토폴로지 열거, 앱 부하에서 VM 사양을 자동 추정하는 연구, 멀티 에이전트 구조만의 인과적 우월성은 범위 밖이다. P1~P3은 모델의 근거가 아니라 종단 통합 벤치마크로만 사용한다.

## 주장–측정 연결

| 제한된 주장 | 구현 산출물 | 최소 측정 | 성공 근거 | 주장하지 않는 것 |
|---|---|---|---|---|
| DepKB가 세 배포 capability를 CSP 구성으로 실현한다 | 근거 claim, 배포 capability, CSP별 native realization | 동일 LLM 출력의 full/no-depkb 결과, provider validate | 입력 해시, 구성요소·관계·제약 상태, 검증 로그 | 전체 클라우드의 완결 모델, 앱 성공 |
| 앱 요구와 VM 환경의 불일치를 조기에 표시한다 | 앱–클라우드 계약과 validator | 발견 단계, 오탐, 수정 소유 작업, 최종 기능 | build/runtime 의존성·port·storage path·HA/local state의 고정 진단군 | 사례별 오류 문자열 지식의 일반화 |
| 단계별 에이전트가 실패 지점부터 복구한다 | 4단계 및 구현 하위 체크포인트 | 실패 소유 작업 식별, 상류 재실행 회피, 복구 시간 | run 상태·retry history·timing summary | 멀티 에이전트 구조 자체의 단독 인과효과 |
| 명시된 제약으로 VM 후보를 안내한다 | 고정 catalog 선택기 | 하한 유무, 예산 충족 여부, 경고, IaC 반영 | 가격 snapshot 시각·출처와 선택 근거 | 전체 비용, 실제 처리량, 최적 VM 보장 |

## 실행 순서와 중단 기준

1. 측정기 신뢰성을 먼저 고정한다. 앱별 mount 경로 하드코딩을 금지하고, relation reference와 cardinality/constraint 검증을 분리한다. 필수 정적 edge는 근거 모델에서 기계적으로 파생한다. “의존성 누락 감소” 효과는 생성 결과에 이 edge 평가를 적용한 뒤에만 산출한다.
2. PS/LB/TLS의 저장된 동일 LLM 출력으로 full/no-depkb 투영 절제를 완료한다. 3 CSP provider validate를 개발 실행으로 확인하되 같은 오류가 반복되면 사례별 패치를 추가하지 않고 provider schema/생성 프롬프트 경계를 수정한다.
3. 실제 cloud apply는 비용·정리 가능성을 확인한 최소 셀에서만 한다. 각 실행은 `apply → ready → 업무 기능 → 실패/재시작 기능 → destroy`를 별도 기록하고, timeout과 budget censorship을 구분한다. 반복 수는 파일럿 시간·비용·검열률을 본 뒤 정한다.
4. 앱 계약은 기존 네 진단군만 고정해 `full/no-consistency-validator`를 비교한다. 고정입력 validator 절제는 완료했으며, 동일 앱 snapshot의 downstream 실패·부분 복구·최종 기능 비교를 다음 게이트로 둔다. 특정 SQLite나 notes 앱에 맞춘 규칙은 추가하지 않는다.
5. provider/region 누락과 최소 용량 누락은 실제 질문–응답–부분 재개를 완료했다. HA와 로컬 상태 충돌도 실제 자연어 입력에서 탐지해 가용성 요구 완화, revision별 내부 checkpoint 격리, 같은 run의 build·HTTP·컨테이너 재시작까지 완료했다. 다만 최종 Terraform의 영속 저장 누락을 의미 평가가 검출했으므로 종단 성공은 아니다. capability 이름이 아닌 `applicationState.durability` 의미로 배선을 교정했으며, 새 확인 run보다 회귀시험과 최소 cloud 후보의 기능 gate를 우선한다.
6. VM 선택기의 결정론적 단위 사례와 3 CSP IaC 반영 gate를 완료했다. Azure Korea Central 가격 공백은 보류했다. provider validate와 실제 성능은 별도 증거가 필요하다.
7. P1~P3 및 CoT/MetaGPT는 전체 시스템의 실용 비교로만 수행한다. 한 번의 파일럿 후 감당 가능한 반복 수를 정하며, DepKB나 멀티 에이전트의 개별 효과로 해석하지 않는다.

## 단계 간 사용자 피드백 정책

사용자 피드백은 현재 단계가 소유한 계약 안에서만 바로 수정한다. 구현 피드백이 요구사항,
유스케이스, 클래스, 시퀀스, API 또는 ERD처럼 앞단계 산출물의 변경을 요구하면 구현 에이전트가
임의로 계약을 바꾸지 않는다. 현재 작업을 `NEEDS_INPUT`으로 중단하고 필요한 복귀 단계와 이유를
제시한 뒤, 그 단계로 돌아가 이후 단계를 다시 진행할지 사용자에게 묻는다.

현재 완료된 범위는 다음과 같다.

- 명시적으로 드러난 요구사항·설계 계약 변경을 구현 피드백 경계에서 차단한다.
- `requirements` 또는 `design` 중 필요한 복귀 단계와 확인 질문을 구조화해 반환한다.
- 사용자 확인 전에는 구현 수정 작업을 생성하거나 실행하지 않는다.

남은 작업은 다음과 같다.

- 사용자가 복귀에 동의했을 때 해당 단계의 기존 산출물을 입력으로 새 revision을 시작하는 경로를 연결한다.
- 거절하면 기존 산출물과 실행 상태를 그대로 보존하고 피드백 요청만 종료한다.
- 자연어에 산출물 이름이 직접 나오지 않아도 업무 의미가 바뀌는 피드백의 단계 판정 정확도를 평가한다.
- 복귀 후에는 선택한 단계부터 하위 산출물을 재생성·재검증하되, 앞선 산출물을 몰래 수정하거나 전체 실행을 무조건 처음부터 반복하지 않는다.

이 기능이 종단 검증되기 전에는 “사용자 변경 요청을 자동으로 전체 산출물에 반영한다”고 주장하지
않는다. 현재 주장은 “앞단계 변경 필요성을 감지한 경우 계약을 보호하고 사용자에게 복귀 여부를
묻는다”로 제한한다.

## 공통 기록 규칙

- 단계·하위 작업·LLM 시도·provider init/validate/apply·기능 probe·cleanup 시간을 run 내부 로그에 남긴다.
- 비정상 LLM 지연 때만 짧은 별도 호출로 429, TTFT, 전체 시간을 확인한다. 무제한 재시도는 금지한다.
- 동일 run을 유지하고 실패 소유 하위 작업부터 재개한다. 다른 attempt의 앱은 runId, appId, 완료 단계, 내용 digest가 맞을 때만 복원한다.
- 정적 생성 가능성, provider 검증, 실제 생성, 앱 기능, cleanup을 합산 점수로 숨기지 않는다.
- 사람이 읽는 결과와 한계는 한국어로 기록하며 `docs/research.md`는 수정하지 않는다.

## 코드베이스 정리 기준

실험 산출물은 run ID와 manifest가 있는 디렉터리에만 보존한다. `.terraform`, Gradle build, pytest 임시 디렉터리와 종료된 실험 workspace는 재현에 필요한 manifest·source snapshot을 보존한 뒤 제거한다. provider 캐시는 검증한 고정 버전만 공유하고, CSP provider 제한은 보편 의존성 규칙이 아니라 이 VM 실험의 재현성 정책으로 문서화한다.
