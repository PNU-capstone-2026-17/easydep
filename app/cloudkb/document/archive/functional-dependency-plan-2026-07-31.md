# 기능 의존 첫 실험 계획 — publicIp 도달성, 3사 (2026-07-31, 실행 전 기록)

## 왜 이것인가

존재 의존과 생명주기 결속은 컨트롤 플레인의 **거부 코드**가 오라클이었다.
그런데 EKS 라운드에서 경계가 하나 드러났다: 클러스터가 ACTIVE인 채로 IAM
역할 정책 분리가 **성공**했다 — 컨트롤 플레인이 참조 무결성을 지키지 않는
지대가 있고, 그 지대의 의존은 거부 코드로는 잴 수 없다. 이것이 셋째 질문
축, **기능 의존**이다: A가 B 없이 존재할 수는 있지만 B가 없으면 A가 제
기능을 못 한다.

## 오라클 정의 (이 라운드의 본체)

기능 의존의 관측은 두 반쪽으로 정의한다:

1. **참조 무결성**: 기능을 깨는 변이(분리·삭제)를 컨트롤 플레인이 막는가.
   — 막으면 그것은 이미 생명주기 결속(holds)이다. 기능 의존이 고유한 것은
   **막지 않는(무방비)** 지대다.
2. **기능 신호**: 변이 후 기능이 실제로 깨지는가 — 컨트롤 플레인 밖에서
   관측 가능한 동작이어야 한다.

**인과 사다리**: 기능 확인 → 변이(성공 관측 = 무방비) → 기능 상실 관측 →
**복원 → 기능 회복 관측**. 회복까지 봐야 상실이 변이 탓임이 선다(회복
없이는 우연한 네트워크 변화와 구별 불가).

## 첫 사례 선정 — publicIp

선정 기준: 기능 신호가 **값싸고 외부에서 관측 가능**할 것. 공인 IP의
기능은 "외부 도달성"이고, 신호는 우리 로컬에서의 TCP 접속(포트 22, SSH
리스너 — 이미지가 기본 제공)이다. VM 안에 들어갈 필요가 없다.

| CSP | 변이 | 간선 |
| --- | --- | --- |
| azure | NIC의 ipConfiguration에서 PIP 제거/재부착 | nic→publicIp (존재·생명주기 기판정 쌍에 셋째 질문 추가) |
| gcp | 인스턴스 accessConfig 삭제/재부여 (RUNNING 유지) | vm→publicIp (신규 쌍) |
| aws | EIP disassociate/associate (퍼블릭 IP 자동부여 없이 기동) | vm→publicIp (신규 쌍) |

EKS IAM 사례는 이번에 판정하지 않는다 — 깨지는 기능이 무엇인지(노드 등록?
업그레이드?) 신호 정의부터 별도 설계가 필요하다. 무방비 관측만 기존 기록에
있다(aws-eks 라운드).

## 판정 어휘 (우리 구성)

- 질문 신설: `question: "function"`. 판정은 `holds` 재사용 — "기능 결속
  실재"(B를 떼면 A의 기능이 깨지고, 컨트롤 플레인은 막지 않는다).
- 술어 부류 신설: `무방비:` — 변이를 컨트롤 플레인이 허용한다는 관측.
  기능 신호의 정의(무엇으로 깨짐을 쟀나)는 note에 명시한다.
- 소비: closure·infra_intent는 existence/lifecycle만 읽으므로 function
  행은 흘러가지 않는다(이번 라운드는 어휘·측정까지 — 소비 배선은 후속).
  뷰어에는 표시한다.

## 함정·위협

- **로컬 망 전제**: F1(기준 접속)이 실패하면 우리 사무망이 22를 막는
  것일 수 있다 — 그 경우 판정 불가로 중단하고 그대로 기록한다.
- **부팅 지연**: sshd가 뜰 때까지 재시도 폴링(총 ~3분).
- **aws 기본 SG는 인바운드 차단** — 22 허용 SG를 만들어야 한다(전제이지
  판정 대상 아님). gcp default 네트워크의 default-allow-ssh는 기본 제공.
- **T-단일실행** · 각 CSP 1회. 기능 신호는 TCP 도달성 하나 — 다른 기능
  (DNS·NAT 등)은 이 판정이 말하지 않는다.

비용: VM 3대 × 수 분(azure B2s_v2 · gcp e2-small · aws t3.micro).
리전 계승. 라운드 끝 3사 전수 점검(잔여 0).
