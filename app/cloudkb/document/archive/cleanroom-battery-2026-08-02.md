# 클린룸 배터리 — 재구성물 셋의 독립 재현과 개선점 (2026-08-02)

> 1차 클린룸(관심사 단건, `concern-cleanroom-replication-2026-08-02.md`)에 이어
> 사용자 지시("다른 것도 다 시켜보자, 개선점을 뽑아내자")로 셋을 병렬 실행했다:
> **계약 재도출** · **배포 후 점검법** · **관심사 2차 반복**. 설계는 1차와 동일
> (무컨텍스트 · claims 사본만 · 저장소 접근 금지).

## 1. 관심사 2차 반복 — 입도 분포와 규칙의 갈림 하나

3회 실행 입도: **본 도출 7 · 클린룸 1차 13 · 클린룸 2차 9.** 군집이 매번 갈리는
것은 안정적 현상이다(군집=우리 구성의 실증). 그 안에서 **안정적으로 재현되는 것**:

- **네트워크 격리** — 3/3, 좌표까지 거의 동일(7좌표).
- **주소 안정성** — 클린룸 **2/2 독립 재도출**, 본 도출만 놓침. gcp 새 주소 ↔
  aws 같은 주소 회복 실측이 근거. 채택 신호가 가장 강한 후보.
- 데이터 수명/잔존 · 신원/권한 · 저장 프로비저닝 · 노출 — 3/3 (경계는 다름).
- **본 도출의 platform-owned 우산이 가장 불안정** — 두 클린룸 다 이 덩어리를
  노출 기제·저장 프로비저닝·용량으로 해체했다. 묶음의 틀("합성 수용")이
  결정 하나가 아니라는 신호.

**규칙 갈림 하나 — 무방비(function) 축**: 본 도출·1차는 관심사로 채택
(runtime-binding-protection), **2차는 원칙을 들어 탈락**시켰다 — *"보호 공백은
'환경이 허용한다'이지 '대신 정한다'가 아니고, 요구사항 단계에서 확정할 결정이
없다 — 런타임 감시 층의 소재"*. 우리 시스템의 실제 배선도 기능 결속을 요구사항
질문이 아니라 operationalWarnings·deploy_checks로 흘린다 — 2차의 논리가 우리
배선과 더 정합하다. 존폐는 사용자 결정 대상.

2차의 순수 기여: **"지연 실패" 부류 명명** — 생성은 통과시키고 하위 결정 부재를
뒤 단계 실패로 미루는 관측(정책 0 클러스터 ACTIVE → join 실패 · 기본 SC 부재 →
PVC Pending 방치). 본 도출의 부류 5종에 없던 여섯째 후보.

## 2. 계약 재도출 — 수렴 4 · 갈림 3 · 맹점 재현 1

클린룸 산출: 5칸 (anchor: provider·region·**existingResources** / judgment:
budgetCeiling / candidate: minResources).

**수렴**: provider·region·예산·스펙 하한(소거 논증 — "변환 규칙을 지어내는 대신
하한을 아는 사용자에게 받거나 판정 닫힘을 명시"를 그대로 재도출) ·
**탄소·레지던시 배제 재현**("실물 0건 — 근거 없는 필드를 제조하지 않는다").

**갈림 = 개선 후보**:
- **existingResources를 필수(빈 목록 허용)로** — *"'없다'와 '말 안 했다'를
  구분 못 하면 삭제 안전 판정이 원리적으로 불가능"*. 현행은 맥락(선택)이라
  침묵=없음으로 뭉개진다. 이 저장소의 없다/안 봤다 규율과 같은 논리.
- **모양을 {종류, 식별자} 쌍으로** — azure LB 배타 삼지선다(OnlyOne) 실측 근거:
  무엇으로 쓸 자원인지에 따라 유효한 가지가 바뀐다. 현행은 타입 수준 목록이라
  실제 재사용(기존 VPC id 참조)에 못 미친다.
- **채널 소유권 논증** — 규모·부하 모양·다중화는 요구사항 산문이 소유하는
  값이니 별도 계약이 재차 받으면 이중 채널이라는 주장. 현행은 우선순위 규칙
  (답 > 제약 원문 > 산문)으로 충돌을 처리한다. 설계 긴장으로 기록.

**맹점 재현**: **workloads(위상축)를 못 봤다** — 본 도출도 증분에서는 못 봤고
사슬을 끝까지 돌려서야 찾은 축이다. 클린룸이 같은 맹점을 재현한 것은 위상축이
자명하지 않다는 방증이자, "사슬 실행"이 도출 도구로서 값을 낸다는 증거.

## 3. 배포 후 점검법 — 레시피 8종 전부 재현 + 함정·공백이 순수 기여

신호 8종 대응 1:1 재현. 현행 `_HOW`보다 **함정이 훨씬 두껍고 대부분 note 실측
인용이 붙어 있다**:

- inbound-tcp: 주소 재조회 강제(gcp 새 주소 실측 — 옛 주소로 찍으면 회복을 영영
  못 본다) · secure-by-default를 상실로 오판하는 함정 · 자원 식별자 검증(Z0
  결과 파일 경합 사례) · 기준선은 직전 회복 위에 · VM 생존 교차 확인(M1b) ·
  합성 신호라 실패 계층을 단독으로 못 가름.
- node-join: **기존 노드 무증상이라 카나리아 없이는 상실이 잠복**(O1) · 변이
  지속 실증(F1c) · 클러스터 역할≠노드 역할.
- imds-credentials: SDK가 캐시한 STS 자격증명이 상실을 가린다(일반 지식 표시) ·
  상위 증폭(EKS CSI) 전에 VM 층 격리.
- volume-write: 재마운트 필요 여부 미확정을 실측 정정 그대로 반영.

**gaps 절(순수 신규)**: 합성 신호는 실패 시 계층별 API 조회의 2차 진단 필요 ·
게스트 안 신호들은 **진입 경로가 판정 대상과 겹치면 점검 마비**(Z1 교훈의
일반화) · egress 방향 비대칭 미측 · 캐시가 통과 신뢰를 TTL만큼 깎음 ·
service-discovery는 워크로드 이전 단계에 대체 신호 없음.

## 5. 한계
