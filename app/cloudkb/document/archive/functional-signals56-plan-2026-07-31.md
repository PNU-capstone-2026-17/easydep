# 기능 신호 5·6 계획 — LB 서빙 · 서비스 디스커버리 (2026-07-31, 실행 전)

신호 4종 라운드에서 "앱이 정말 필요한 자리는 둘"로 좁혔다. 그 둘을 연다.
**설계를 다시 보니 하나는 앱이 필요 없다** — 그 사실 자체를 먼저 적는다.

## 신호 5 — LB 백엔드 서빙 (앱 **불요**로 정정)

백엔드가 응답해야 LB가 서빙한다. "응답하는 백엔드"에 앱이 필요하다고 봤는데,
`python3 -m http.server`가 **OS 기본 도구**다(Ubuntu·AL2023 모두 python3
기본 탑재). 앱을 들이지 않고도 최소 관측자가 선다 — 앞 라운드의 규율이
그대로 유지된다.

- 겨누는 간선: `loadBalancer→vm`(백엔드 결속). 존재 판정에는 없던 간선이다
  — LB는 백엔드 없이도 만들어지므로(기존 실측) 존재로는 안 보이고 **기능
  으로만 보인다**. 기능 축이 새 간선을 여는 첫 사례가 된다.
- 사다리: 백엔드 풀에 VM + http.server → LB 프론트엔드로 HTTP 200 →
  **백엔드 풀에서 VM 제거**(무방비) → 서빙 상실 → 재등록 → 회복.
- CSP: azure(Standard LB + 백엔드 풀). aws는 타깃 그룹 등록 해제로 같은
  꼴이나 이번 라운드에서는 azure 하나로 연다(비용·시간).

## 신호 6 — 서비스 디스커버리 (앱 **필요**)

클러스터 안에서 이름으로 서로 찾는 것. 이건 컨테이너가 응답해야 하므로
최소 이미지를 쓴다 — **이 라운드에서 유일하게 앱이 필요한 자리**다.

- 이미지: `registry.k8s.io/e2e-test-images/agnhost`(k8s 프로젝트 공식 테스트
  이미지, netexec 모드가 HTTP 응답). **애플리케이션이 아니라 관측자**임을
  판정 note에 명시한다.
- 겨누는 간선: `k8sService→k8sCluster`의 기능 면 — Service를 지우면 이름이
  안 풀리고 접속이 끊긴다. 클러스터 내부 DNS(CoreDNS)가 기능의 담지자다.
- 사다리: Pod(agnhost) + Service → 다른 Pod에서 `curl svc-name` 200 →
  **Service 삭제**(무방비) → 이름 해석·접속 상실 → 재생성 → 회복.
- CSP: gcp(GKE) 하나. k8s 층은 3사 동형이 이미 여러 번 확인됐고(합성
  라운드), 여기서 재는 것은 **k8s 자체의 기능**이라 CSP 차이가 예상되지
  않는다 — 그 예상도 판정에 넣지 않고 "한 CSP에서만 쟀다"로 적는다.

## 함정 (앞 라운드 여섯을 겪고 나서)

- **캐시**: 클러스터 DNS도 캐싱한다. 상실 관측은 연속 2회 + 짧은 간격.
- **파이프**: 종료 코드를 삼키지 않게 `curl -sf`의 rc를 직접 본다.
- **경합**: 셀을 **순차로만** 돌린다. 결과 파일을 공유하는 실행을 겹치지
  않는다(신호 4종에서 다른 VPC의 라우트를 지웠다).
- **LB 헬스 프로브 지연**: azure LB는 프로브 주기가 있어 상실·회복이 즉시가
  아니다 — 시한을 넉넉히.

비용: azure VM 1대 + Standard LB(분 단위) · GKE 클러스터 1개(~30분).
라운드 끝 3사 전수 점검.
