# 용량 측정 개선 계획 — 방법론 등급으로 (2026-08-02, 실행 전)

> 조사 `capacity-measurement-methodology-2026-08-02.md`가 우리 측정을 문헌에
> 대고 **거친 하한이지 right-sizing이 아니다**로 판정했다. 이 문서는 그 갭을
> 메우는 실행 계획이다 — **구현 전**, 완료는 커밋이 기록. 규율: 설계마다 조사의
> 어느 기둥이 근거인지 대고(①~④), 지어내지 않는다.

## 0. 무엇을 바꾸나 (현재 → 목표)

| 축 | 현재(measure_capacity·load_probe) | 목표 | 근거 |
|---|---|---|---|
| 통계 | 단일 실행 **피크** | 시계열 **백분위**(p50/p95/p99) | ②(VPA) |
| 워밍업 | 없음(시동 스파이크가 CPU 지배) | 워밍업 후 **정상상태**만 | ①(Kalibera·Barrett) |
| 부하 | **닫힌 루프**(N워커, 앞 요청 끝나야 다음) | **open 모델**(고정 도착률) | ③(coordinated omission) |
| 반복 | 1회 | 여러 프로세스 실행 + 신뢰구간 | ①(Kalibera&Jones) |
| 메모리 | 단일 RSS | **RSS 전량 p99 + 25~50% 헤드룸** | ④(AWS) |
| 시동/정상 | 뒤섞임 | **분리**(시동→readiness/limit, 정상→request) | ①④ |

## 1. 선행 조건 — 앱이 독립 부팅돼야 한다 (P0)

부하 프로브의 전제다. field-report는 H2+Flyway인데도 90초 내 미부팅
(`load_probe`가 "안 떴음"으로 정직히 멈춤). **P0: 부팅 오류 진단.** 부팅 로그를
잡아(현재 프로브는 stdout을 버린다 — 이걸 파일로) 원인(빈 배선·포트·마이그레이션)을
읽는다. 못 고치면 **부팅되는 참조 앱**(우리가 쓴 최소 Spring, 비교 대상 아님)으로
측정 방법론을 검증하고, field-report는 "미부팅"을 결과로 남긴다.

## 2. open 모델 부하 생성기 (P1) — 근거 ③

- **고정 도착률**로 요청을 스케줄한다(응답과 무관). 닫힌 루프 폐기.
- 도착률은 `scale`에서 **Little의 법칙**(L=λW)으로 환산 — 목표 동시성·응답시간을
  잇는다. field-report scale(동시 40)을 도착률로 옮기는 절차를 명시.
- **램프 + 포화 탐지**: 도착률을 올리며 응답시간·오류율이 무너지는 지점(포화)을
  찾는다 — 그 아래가 지속 가능한 서빙 용량.
- coordinated omission 회피: 요청 발사 시각을 예정대로 고정, SUT 지연에 생성기가
  안 끌려가게. (지연 통계를 낼 거면 예정-실제 시각차를 보정.)

## 3. 워밍업 + 정상상태 판정 (P2) — 근거 ①

- 부하를 걸고 **워밍업 구간**(시동·클래스로딩·JIT)을 지난 뒤부터 잰다.
- 정상상태 판정: 1차는 **고정 워밍업 + 안정성 검사**(이동 창의 변동계수 임계),
  가능하면 **변화점 탐지**(Barrett)로 자동화. **"정상상태에 도달 못 함"도 결과**
  (JIT가 안정 안 되면 그렇게 적는다 — ①의 실측).
- 시동 스파이크는 **버리지 않고 따로** 기록(readiness 프로브·CPU limit의 근거).

## 4. 백분위 집계 + 반복 (P3) — 근거 ②①

- 정상상태 구간에서 CPU·RSS를 촘촘히 표본, **p50/p95/p99** 산출.
- **여러 프로세스 실행**(예: 5회)으로 각 백분위의 **분산·신뢰구간**(Kalibera&Jones).
  MoE 아닌 결정적 앱이라 흔들림은 부하·GC·JIT에서 온다 — 그 흔들림을 보존.
- 산출 레코드: p95 CPU · p99 RSS · 시동 피크 · 포화 도착률 · 실행 수 · 신뢰구간.

## 5. 메모리 헤드룸 + sizing 배선 (P4) — 근거 ④

- 메모리 하한 = **RSS p99 + 25~50% 헤드룸**(네이티브·Metaspace 포함이 RSS라
  자동 반영). CPU request ≈ 정상 **p95**.
- `sizing_floor.Measurement` 확장: 단일 vcpu/mem_gib → **분포**(p50/p95/p99) +
  시동 피크 + 신뢰구간 + `saturation` 필드. `production_load=True`(open 부하라).
  measured 층의 `why`가 "p95 서빙 CPU"임을 밝히고 시동 피크는 별도 노트로.
- 하위 호환: 현재 measure_capacity(테스트-JVM)는 **시동/테스트 신호로 강등** 표시
  (서빙 하한이 아님을 이미 evidence에 적었으니 계승).

## 6. 범위 경계 (안 하는 것)

- **2~4주 프로덕션 창은 안 한다**(VPA 관행) — 우리는 **합성 부하 단발 캠페인**
  이다. 실서비스 분포가 아니라 "이 부하에서의 분포"임을 명시. 관행의 최적성
  검증도 안 한다(조사 §5의 자세 — 관행을 관찰 코퍼스로 읽는다).
- **APM·프로파일러 통합 안 함** — psutil 프로세스 표본으로 족하다(CPU·RSS).
- **자동 request/limit 설정 안 함** — 측정을 내고, 사이징 판단은 사람/계획.

## 7. 타당성 위협 (실행 전에 적는다)

- **T-단일 앱·단일 워크로드**: 한 앱의 측정은 그 앱까지만. 일반화 금지(반복은
  실행 반복이지 앱 반복이 아니다). 여러 표본 앱이 있어야 축이 선다.
- **T-부트 의존**: 앱이 독립 부팅돼야 하는데 field-report가 못 떴다(P0). 이
  전제가 안 서면 서빙 측정 자체가 불가 — 미부팅을 결과로 남긴다.
- **T-도착률 선정**: scale→도착률 환산에 응답시간 가정이 든다(Little). 그
  가정을 명시하고, 포화 램프로 단일 도착률의 임의성을 완화.
- **T-환경**: 측정 머신이 프로덕션 노드가 아니다(로컬 CPU·페이징). WinError 1455
  (페이징 부족)를 이미 봤다 — 측정 환경의 자원을 기록하고, 코어 수 정규화.
- **T-관행 vs 학술 등급 혼합**: ②③④는 산업 관행이라 통제 실험이 아니다
  (조사 §5). "관행이 이렇게 한다"까지만 주장.

## 8. 단계 요약

    P0  부트 오류 진단(로그 잡기) / 참조 앱 대안
    P1  open 모델 부하 생성기(고정 도착률·Little·포화 램프)
    P2  워밍업 + 정상상태 판정(변동계수/변화점, "미도달"도 결과)
    P3  백분위(p50/95/99) + 반복 실행 + 신뢰구간
    P4  메모리 헤드룸 + Measurement 분포 확장 + sizing 배선
    P5  기록·원고 반영
