# 요구사항 → 설계 → 배포 다이어그램, 무엇이 어디서 채워지는가 (2026-07-28)

> **이력이다. 참조하지 않는다.**
>
> 현재 진실은 [`docs/cloud-native-extension.md`](../../../../docs/cloud-native-extension.md). 이 문서는 작성 시점의
> 스냅샷이고 전제가 바뀐 자리가 있다. **여기 적힌 결정·계획을 근거로 새 작업을
> 시작하지 말 것.** 안의 **실측치는 유효하다** — 다시 재지 말고 인용한다.

**질문**: 클래스·시퀀스·ER 다이어그램과 API 명세서만으로는 배포 다이어그램을 만들 수
없다. 그럼 **무엇이 더 있어야 하고, 그건 어느 단계에서 정해져야 하는가.** 그리고
그것이 과제 목적과 맞는가.

추측하지 않았습니다. **코드가 실제로 무엇을 읽고 무엇을 짐작하는지**를 세어서 씁니다
(`nim_agent/design_tools.py`·`appkb/schema.json`·`appkb/request.json`·
`requirements/knowledge/concerns.py`, 예제는 `appkb/examples/order-demo.json`).

## 1. 한 장으로 — 사슬은 셋이 아니라 넷이다

```
 ① 요구사항 분석            ② 시스템 설계              ③ 배포 계획·다이어그램
 ─────────────────         ─────────────────         ─────────────────────
 기능 요구사항        →    클래스·시퀀스·ER·API   →   ??? 
 비기능 요구사항                                        └ 여기서 끊긴다
      │                                                      ↑
      └──────────────  ④ 클라우드 사실 ─────────────────────┘
                     (제약·의존·가격·성능·번들·리전)
```

**핵심**: ①→②→③은 **한 줄로 이어지지 않습니다.** ②의 산출물은 *"무엇을 만드는가"*를
말하고 ③은 *"어디에 어떻게 올리는가"*를 말하는데, 둘 사이에는 **설계도에 없는 정보**가
필요합니다. 그 정보의 출처가 둘입니다 — **①에서만 정할 수 있는 것**과 **④가 아는
것**. 이 문서는 그 둘을 가르는 것이 전부입니다.

## 2. 설계 산출물이 실제로 주는 신호 — 전수

`_collect_signals()`가 산출물에서 뽑는 것 전부입니다. **이게 ②가 ③에게 줄 수 있는
것의 상한**입니다.

| 산출물 | 읽는 필드 | 나오는 신호 | 배포 계획에서의 쓰임 |
|---|---|---|---|
| **API 명세**(OpenAPI) | `paths` 존재 | `has_api` | 이 컴포넌트는 **HTTP 서비스**다 → 컴퓨트 노드 |
| | `components.securitySchemes` | `needs_secret` | **시크릿 저장소**가 필요하다 |
| | `requestBody.content`가 `multipart/*`·`octet-stream` | `uploads` | **객체 스토리지** 후보 |
| **ER** | `entities[].ownerComponentId` | `owners` | 이 컴포넌트는 **영속 저장소**가 필요하다 |
| | `engineHint` | `engine_of` | 관리형 DB의 **엔진**(postgresql 등) |
| | `archetypeHint` | `archetype_hint_of` | 아키타입 직접 지정 |
| **시퀀스** | `messages[]`에서 `actor → component` | `exposed` | **공개 노출** → 앞에 로드밸런서 |
| | `messages[].async = true` | `async_targets` | **큐**가 필요하다 |
| | 모든 메시지 | `sync_calls` | 다이어그램의 **선** |
| **클래스** | — | **없음** | **읽지 않는다** |

### OpenAPI로 정말 되나 — 변형 9종 실측 ★

"API 명세가 OpenAPI 형식인데 그걸로 되는가"에 답하려면 **교과서적 예제 하나로는
부족합니다.** 실무 OpenAPI에서 흔한 형태 아홉 가지를 만들어 돌렸습니다.

| 변형 | HTTP 서비스 | 시크릿 | 업로드 |
|---|:--:|:--:|:--:|
| ① 교과서적 3.0 (인증·업로드 인라인) | O | **O** | **O** |
| ② 인증을 `$ref`로 분리 — **가장 흔한 실무 형태** | O | · | · |
| ③ `security`만 쓰고 schemes는 외부 문서 | O | · | · |
| ④ 업로드 `requestBody`를 `$ref`로 | O | · | · |
| ⑤ 바이너리 업로드지만 `image/png` | O | · | · |
| ⑥ OpenAPI **3.1 webhooks 전용**(paths 없음) | O | · | · |
| ⑦ `callbacks`(비동기 신호) | O | · | · |
| ⑧ `paths`가 비어 있음 | O | · | · |
| ⑨ `servers`에 도메인·경로 | O | · | · |

**①만 세 신호가 다 나옵니다.** 나머지 여덟은 시크릿·업로드를 **전부 놓칩니다.**

원인은 넷입니다.

1. **`$ref`를 해석하지 않는다.** OpenAPI는 문서를 쪼개는 것이 표준 관행인데
   (`#/components/...` 내부 참조조차) 그대로 읽어 키가 없다고 판단한다. ②④가 이것.
2. **선언만 보고 사용은 안 본다.** `components.securitySchemes`가 있는지만 보므로,
   루트 `security`로 쓰기만 하고 스킴이 외부에 있으면 못 잡는다(③).
3. **바이너리 판정이 content-type 문자열 두 개뿐이다**(`multipart/*`·
   `application/octet-stream`). `image/png`·`application/pdf`처럼 실제 파일 업로드인데
   놓친다(⑤). 스펙에는 `schema.format: binary`라는 **더 정확한 신호**가 있는데 안 쓴다.
4. **3.1의 `webhooks`와 `callbacks`를 안 읽는다**(⑥⑦). 이 둘은 **비동기 선언**이라
   곧 큐·이벤트 스트림 신호인데, 지금은 비동기를 시퀀스 다이어그램에서만 읽는다.

그리고 반대 방향 결함도 하나: **`has_api`는 openapi 산출물이 있으면 무조건
참**입니다 — `paths`를 보지 않아 빈 문서도 HTTP 서비스로 칩니다(⑧).

**가장 나쁜 것은 조용하다는 점입니다.** 같은 API를 ①처럼 쓰면 노드 7개, ②처럼
쓰면 5개가 나오는데 — **`secret-store`와 객체 스토리지가 사라지고, 사라졌다는 말이
어디에도 없습니다.**

```
① 인라인   → vnet · subnet · securitygroup · sshkey · svc · secret-store · svc-files
② $ref     → vnet · subnet · securitygroup · sshkey · svc
             (고지: 없음 — 조용히 빠짐)
```

이 저장소가 가장 경계해 온 실패 유형(**침묵이 "없음"으로 읽힌다**)이 **설계 입력
경로에서만 안 지켜지고 있습니다.** KB 축들은 "수집 범위 밖이라 모른다"를 문장으로
답하는데, 산출물 파서는 못 읽은 것을 세지도 않습니다.

**결론**: OpenAPI로 **됩니다.** 다만 지금 추출기는 **가장 단순한 형태만** 읽고,
표준 관행에서 바로 무너지며, 무너진 사실을 알리지 않습니다. 고칠 순서는 §8에 있습니다.

> **클래스 다이어그램은 신호를 하나도 내지 않습니다.** 계약은 받아 주지만
> `_collect_signals`가 `"class"`를 조회하지 않습니다. 배포 관점에서 클래스 구조는
> *"무엇이 어디에 배치되는가"*를 가르지 못하기 때문입니다 — 같은 클래스 구조가
> VM에도, 컨테이너에도, 함수에도 올라갑니다. **이건 결함이 아니라 경계**이고,
> 그렇게 적어 두지 않으면 "4종을 다 쓴다"로 읽힙니다.

## 3. 그래서 설계도만으로 얼마나 만들어지나 — 측정

예제(`order-demo.json`: 컴포넌트 2 + 외부 1 + 산출물 4종)를 넣고 나온 계획입니다.

| 계획 요소 | design(설계도가 말함) | inferred(우리 추론) | kb(클라우드 사실) |
|---|--:|--:|--:|
| **노드 12** | **2** | 6 | 4 |
| **엣지 6** | 2 | 4 | — |
| **노트 47** | 4 | 11 | **32** |

**노드 12개 중 설계도가 직접 준 것은 2개**(컴포넌트 두 개)뿐입니다. 나머지 10개 —
VPC·서브넷·보안그룹·SSH키·로드밸런서·RDS·SQS·시크릿저장소 — 는 **설계도에 없습니다.**

즉 **배포 다이어그램의 83%가 설계 산출물 바깥에서 옵니다.** 그 바깥이 어디인지가
이 과제의 내용입니다.

## 4. 부족한 정보는 세 종류다

### (가) 요구사항 단계에서만 정할 수 있는 것 — `RESOURCE_SPEC` 11칸

설계도를 아무리 자세히 그려도 **나오지 않는** 것들입니다. 설계자가 아니라 **요구자가
정해야** 합니다.

| 칸 | 없으면 무슨 일이 나나 | 필수 |
|---|---|:--:|
| `provider` | 비용·성능·번들·벤더 타입 대응이 **전부 닫힌다** | ● |
| `region` | 가격·지연·탄소·이미지 조인이 안 된다 | ● |
| `monthlyBudgetUSD` | **비용 부합 판정의 기준이 없다** | ● |
| `expectedConcurrentUsers` / `approxRequestsPerSecond` | 스펙 추천이 **전부 임의**가 된다 | ○ |
| `multiZone` | 서브넷 분산·k8s 최소 서브넷 수가 안 정해진다 | |
| `trafficPattern` | 버스트 상충 판정 불가(steady인데 버스트형이면 위험) | |
| `stateless` | 서버리스 적합 판정 불가 | |
| `dataResidency` | 리전이 요구 지역과 맞는지 **대조**할 수 없다 | |

> **필수의 기준이 목록이 아니라 판정식입니다**: *"그 칸이 없으면 뒤 단계 산출물의
> 요구사항 부합을 잴 수 없는 것만 필수."* 그래서 예산은 필수이고 `multiZone`은
> 아닙니다 — 없어도 계획은 나오고, 다만 그 축의 판정이 "해당 없음"이 됩니다.

### (나) 클라우드가 아는 것 — 지식베이스 축

설계도에도 요구사항에도 없고, **클라우드 회사만 아는** 사실입니다. 계획 노트 47개
중 **32개가 여기서** 왔습니다.

| 축 | 예제에서 채운 것 | 없으면 |
|---|--:|---|
| **bundlekb** | 8건 | VM 하나에 vNet·subnet·sshKey·SG가 딸려오는 걸 모른다 → **다이어그램에 상자 4개가 빠진다** |
| **costkb** | 7건 | 값이 안 붙는다 → **예산 판정 자체가 불가능** |
| **mapping/svcmap** | 8건 | `app::relationalDatabase`가 어느 회사 타입인지 모른다 → **노드에 타입을 못 적는다** |
| **graphkb** | 2건 | 무엇이 수평 확장 단위인지, 무엇을 먼저 만드는지 모른다 |
| **perfkb** | 2건 | "버스트형이라 크레딧 소진 시 하락" 경고가 없다 |
| **sizingkb** | 2건 | 서브넷에 몇 대가 들어가는지 모른다 |
| **envkb**(이미지) | 2건 | OS 이미지를 못 고른다 |

### (다) 우리가 추론하는 것 — 반드시 표시된다

위 둘로도 안 채워지는 자리는 **추론**하되 `<<inferred>>`로 표시합니다(노드 6·엣지
4·노트 11). 예: *"actor가 이 서비스를 직접 부르니 앞에 로드밸런서를 둔다 — **이건 우리
권고이지 설계가 지정한 것이 아니다**."*

## 5. 그럼 요구사항 단계에 무엇이 더 필요한가 ★

여기가 이 문서의 결론입니다.

`RESOURCE_SPEC`의 11칸은 **사용자가 요구사항으로 쓰지 않는 것들**입니다. "주문을
접수한다"는 쓰지만 "상태를 프로세스에 두지 않는다"는 안 씁니다. 그래서 **요구사항
단계에 그 칸을 묻는 축**이 따로 있어야 하고, 그게 클라우드 네이티브 관심사 축입니다
(`app/requirements/knowledge/concerns.py`, 29건).

관심사의 정의가 정확히 이겁니다:

> **요구사항 단계에서 확정할 수 있고, 확정하지 않으면 클라우드 실행 환경이 그 답을
> 대신 정해 버리는 결정.**

### 그런데 여기가 끊겨 있습니다

| | 건수 |
|---|--:|
| 관심사 축 전체 | **29** |
| 그중 `RESOURCE_SPEC`으로 흘러가는 것(`consumer` 지정) | **6** |
| **소비자가 없는 것** | **23** |

흘러가는 여섯은 이렇습니다.

```
cn.stateless-process   → RESOURCE_SPEC.stateless
cn.traffic-shape       → RESOURCE_SPEC.trafficPattern
cn.redundancy-target   → RESOURCE_SPEC.multiZone
cn.data-residency      → RESOURCE_SPEC.dataResidency
cn.expected-scale      → RESOURCE_SPEC.expectedConcurrentUsers | approxRequestsPerSecond
cn.cost-ceiling        → RESOURCE_SPEC.monthlyBudgetUSD
```

**나머지 23건은 사용자에게 묻기는 하는데, 답을 받아도 배포 계획에 닿지 않습니다.**
이게 ①→③ 사슬의 실제 끊긴 자리입니다. 두 가지로 읽을 수 있고, **둘을 갈라야
합니다.**

- **아직 소비자를 안 만든 것** — 만들면 이어진다. (구현 범위 문제)
- **애초에 배포 계획이 소비할 수 없는 것** — 예: 로깅 보존 기간, 장애 통보 대상.
  이건 배포 다이어그램의 관심사가 아니라 **운영·관측 단계**의 것이다. (경계 문제)

### 23건을 갈랐습니다 — 기준을 먼저 적고 적용

**기준**(적용 전에 고정):

> **배포 계획이 그 답을 받아 무언가를 다르게 만들 수 있는가.**
> 계획이 만드는 것은 여섯뿐이다 — 컴퓨트 노드·방식 / 관리형 서비스 노드 / 공유
> 인프라 / 진입점 / 값 / 판정. **그 여섯 중 하나가 달라지지 않으면 배포 관심사가
> 아니다.** "관련은 있다"는 기준이 아니다.

| 갈래 | 건수 | 뜻 |
|---|--:|---|
| **A. 계획의 구조를 바꾼다** | 8 | 노드·엣지가 실제로 달라진다. **먼저 이을 것** |
| **B. 판정·고지를 낳는다** | 7 | 구조는 같고 판정문이 붙는다 |
| **C. 배포 계획 밖** | 8 | 설계·구현·운영 단계의 것 — **안 잇는 것이 맞다** |

**A — 계획의 구조를 바꾼다 (8건, 우선순위 순)**

| 관심사 | 무엇이 달라지나 | 받을 자리 |
|---|---|---|
| `cn.network-exposure` | **공개 노출 범위** — 지금은 시퀀스의 `actor→component`로만 유추한다. 요구사항이 말하면 LB·보안그룹이 근거를 갖는다 | 새 칸 |
| `cn.managed-vs-self` | 관리형을 써도 되는가 — **노드 종류 자체**를 가른다(RDS냐 EC2 위 PostgreSQL이냐) | 새 칸 |
| `cn.scale-out` | **수평 확장 대수** — 계획이 지금 "정해지지 않았습니다"라고 답하는 바로 그 칸 | 새 칸 |
| `cn.backing-services` | 앱이 네트워크로 쓰는 백엔드 — **관리형 노드를 직접 낳는다** | 새 칸 |
| `cn.recovery-objective` | RPO/RTO — 다중화 범위. `multiZone`의 상위 개념 | `multiZone` 확장 |
| `cn.service-limits` | 플랫폼 한도에 닿는 볼륨 — **capacitykb 쿼터 542건이 이미 있는데 소비자가 없다** | 새 칸 |
| `cn.carbon-constraint` | 탄소 제약 — **envkb 탄소 161건이 이미 있는데 소비자가 없다** | 새 칸 |
| `cn.performance-target` | 응답시간·처리량 목표 — 버스트 상충 판정을 근거 있게 만든다 | `trafficPattern` 확장 |

> **뒤 둘이 특히 아까워 보였고, 하나만 맞았습니다.** 이어 보고 정정합니다.
>
> - **탄소는 맞았습니다.** `lowCarbonPreferred` 칸 하나로 이어졌습니다(2026-07-28
>   구현). 계획이 선택 리전의 탄소집약도와 **같은 프로바이더 안에서 더 낮은 리전 수**를
>   싣고, 판정은 하지 않습니다 — 옮길지는 지연·레지던시와의 상충이고 우리는 그걸
>   못 잽니다. 프로바이더 간 비교도 안 합니다(출처 등급·방법론이 달라 실측에서 같은
>   도시의 순서가 뒤집혔습니다).
> - **쿼터는 틀렸습니다.** 542건 중 **`type_id`가 있는 것이 12건(2%)**뿐이라
>   **계획 노드에 조인할 키가 없습니다.** "데이터가 있다"와 "이을 수 있다"는 다른
>   말이었고, 세어 보기 전에는 같아 보였습니다. 잇는 일은 칸 추가가 아니라 **쿼터
>   파서가 타입을 붙이는 일**부터입니다.
>
> 나머지 여섯도 같은 잣대로 다시 보면 **지금 이을 수 있는 것이 없습니다** — 각각
> 계획에 없는 능력을 전제합니다(대수·관리형 선택 축·노출 축). 그래서 A갈래의 실제
> 상태는 *"8건 중 1건 연결, 7건은 선행 작업 있음"*이고, 그 선행 작업이 무엇인지가
> §8의 목록입니다.

**B — 판정·고지를 낳는다 (7건)**

`cn.data-classification` · `cn.encryption-obligation` · `cn.regulatory-obligation` ·
`cn.tenancy-model` · `cn.usage-quota` · `cn.identity-access` · `cn.operational-signal`

구조는 그대로고 **판정문이 붙습니다.** 예: 암호화 의무가 있으면 계획의 저장소 노드에
"이 타입의 암호화 속성은 이것"이라는 고지가 붙습니다(capacitykb가 답합니다).
`cn.regulatory-obligation`은 `dataResidency`와 같은 계열이라 **"판정 불가"를 명시하는
소비자**가 됩니다 — 규제 준수는 우리가 판정하지 않습니다(§7의 5번 참조).

> `cn.operational-signal`(관측)과 `cn.identity-access`(권한)는 B에 두되 **주의**가
> 필요합니다. 둘 다 대응하는 `app::` 개념이 **없습니다**(모니터링·IAM 아키타입 부재 —
> 5장 참조). 노드를 낳으려면 svcmap을 먼저 넓혀야 하므로, 지금은 판정·고지까지만입니다.

**C — 배포 계획 밖 (8건, 안 잇는 것이 맞다)**

| 관심사 | 어느 단계의 것인가 |
|---|---|
| `cn.transient-fault` · `cn.cross-service-consistency` · `cn.degradation-policy` | **설계·구현** — 재시도·보상 트랜잭션·과부하 정책은 코드가 하는 일이다 |
| `cn.disposability` · `cn.config-externalised` | 이미 있는 칸과 **겹친다**(`stateless`·시크릿 저장소) — 새로 잇지 말고 기존 칸을 보강 |
| `cn.release-continuity` · `cn.critical-flow` | **운영** — 배포 전략·SLO는 계획이 아니라 운영의 것 |
| `cn.event-record` | 경계선. `app::eventStream`이 있으니 A로 옮길 수 있으나, "감사 추적"과 "이벤트 스트림"은 다른 것이라 **섞으면 안 된다** |

**이 분류가 무엇을 바꾸나**: "29건을 묻는데 6건만 쓴다"가 → **"29건 중 21건이
배포로 갈 길이 있고(A 8 + B 7 + 기존 6), 8건은 다른 단계의 것이라 안 잇는다"**가
됩니다. 뒤쪽은 **경계를 그은 것**이지 미완이 아닙니다. 심사에서 갈리는 지점이 정확히
이것입니다 — **"안 한 것"과 "안 하기로 한 것"을 구별할 수 있는가.**

## 5.5. 난점을 어떻게 넘는가 — 층이 셋이다

§2의 실측(OpenAPI 변형 9종 중 8종이 신호를 놓침)을 "파서를 더 정교하게"로 답하면
안 됩니다. 그 길은 끝이 없고, 이 저장소는 그 유혹을 이미 한 번 거절했습니다 —
*"목표는 완벽한 데이터셋이지 완벽한 파서가 아니다"*(4장 ③).

난점을 갈라 보면 **성격이 다른 셋**이고, 셋 다 **이 저장소가 다른 축에서 이미 푼
문제**입니다. 새 기법이 필요한 게 아니라 **같은 규율을 입력 경로로 옮기는** 일입니다.

### 층 1 — 표현이 여러 가지다 (`$ref`·3.0/3.1·content-type 변형)

**해법: 정규화를 계약 진입 앞에 둔다.**

이 저장소에 이미 같은 규율이 있습니다 — *"지명('서울')은 계약 진입 전에 리전 해석
도구로 코드(`ap-northeast-2`)로 바꿔 담는다. 그대로 오면 조인이 조용히 빈 답이
된다."* 산출물도 똑같습니다. **`$ref`가 섞인 OpenAPI는 '서울'이고, 펴진 OpenAPI가
`ap-northeast-2`입니다.**

- 정규화를 **파서 안에 넣지 않습니다.** 파서마다 되풀이되고 서로 어긋납니다.
  계약 앞 한 곳에서 폅니다(내부 `$ref` 해소 · 3.0/3.1 차이 흡수 · 바이너리 판정을
  `schema.format`으로 통일).
- **외부 파일 참조(`./security.yaml`)는 원리적으로 못 폅니다** — 우리가 그 파일을
  받지 못합니다. 그건 층 3으로 넘깁니다.

### 층 2 — 산출물이 애초에 말하지 않는다 (규모·예산·노출 범위)

**해법: 짐작으로 메우지 말고 물어야 할 것으로 만든다.** 이게 `RESOURCE_SPEC`이고,
§5의 관심사 축이 그 칸을 채우는 장치입니다. 층 1을 아무리 잘해도 **여기는 안
줄어듭니다** — 정규화의 문제가 아니라 **단계의 문제**이기 때문입니다.

### 층 3 — 못 읽은 것과 없는 것이 구별되지 않는다 ★ 여기가 본체

**이게 진짜 난점이고, 나머지 둘보다 값이 큽니다.**

지금 신호는 **2상태**입니다. `needs_secret: set[str]` — 컴포넌트가 집합에 있거나
없거나입니다. 그래서 **"읽었고 인증이 없었다"와 "참조라 못 읽었다"가 같은 값**이
됩니다. 그 결과가 §2의 조용한 누락입니다.

**이 저장소는 정확히 같은 결함을 두 번 고쳤습니다.**

| 어디서 | 무엇이 문제였나 | 어떻게 고쳤나 |
|---|---|---|
| perfkb(8장) | 네 경우가 전부 `None`을 반환해 **출력이 바이트 단위로 같았다** | 다섯 상태로 갈랐다(`warn`/`ok`/`no_record`/`untracked`/`not_built`) |
| capacitykb(6장) | 조건을 모를 때 한쪽으로 접었다 | **3상태**(성립/불성립/모름) |
| 질의 계층(13장) | "모른다"가 한 문장이었다 | 침묵 다섯 종류를 다섯 문장으로 |

**산출물 파서에만 이 처리가 없습니다.** 같은 모양으로 고칩니다.

```
지금            needs_secret: set[str]                 # 있다 / 없다
                                                        ↑ 못 읽음이 '없다'로 접힌다

바꿔서          needs_secret: Signal
                  present:  set[str]   확실히 있다 (읽었고 있었다)
                  absent:   set[str]   확실히 없다 (읽었고 없었다)
                  unknown:  set[str]   **못 읽었다** ($ref·외부 문서·모르는 구조)
```

이 한 칸이 생기면 아래가 **저절로** 따라옵니다.

1. **조용한 누락이 구조적으로 불가능해진다.** 모든 신호가 상태를 가지므로, 노드가
   빠지면 반드시 `unknown`이 남습니다. 계획 고지에 *"이 설계에서 신호 N건을 읽지
   못했습니다(참조 M건·모르는 구조 K건) — 그래서 빠진 노드가 있을 수 있습니다"*가
   실립니다.
2. **되묻기에 근거가 생긴다.** 지금 배치 경로에는 되묻기가 없는데, `unknown`이
   있으면 **무엇을 되물을지가 데이터로 정해집니다** — "인증 스킴이 외부 문서에
   있어 못 읽었습니다. 이 서비스는 자격증명 저장소가 필요합니까?"
3. **판정이 자기 한계를 말할 수 있다.** `verify`가 *"이 판정은 신호 K건이 미상인
   상태에서 낸 것"*이라고 밝힐 수 있습니다. 예산 판정의 비대칭(11장)과 같은 결입니다.
4. **파서를 정교하게 만들 이유가 줄어든다.** 못 읽는 것을 정직하게 말하면,
   `$ref` 해소를 완벽히 하지 않아도 **답이 거짓말이 되지 않습니다.**

> **순서가 중요합니다.** 층 1(정규화)을 먼저 하면 커버리지는 늘지만 **남은 구멍은
> 여전히 조용합니다.** 층 3을 먼저 하면 커버리지는 그대로여도 **거짓말이 멈춥니다.**
> 이 저장소의 제1원칙("확신에 찬 오답을 막는다")대로면 **층 3이 먼저**입니다.

### 하지 말아야 할 것

**못 읽은 자리를 LLM에게 메우게 하는 것.** 유혹이 크고(모델은 OpenAPI를 잘 읽습니다)
정확히 이 저장소가 결정론 층을 만든 이유와 충돌합니다. `unknown`은 **사용자에게 묻는
신호**이지 모델에게 채우게 하는 자리가 아닙니다 — 채우게 하면 환각이 검사 없는 곳으로
이사할 뿐이고, 그건 `deployHint`를 상류로 올릴 때 계약이 이미 내린 판단입니다.

### 검증은 어떻게 — 골든 케이스

§2의 변형 9종을 **테스트로 고정**합니다. 각 변형마다 기대는 "신호가 나온다"가 아니라
**"신호가 나오거나, 못 읽었다고 표시된다"**입니다. 그러면 파서를 개선할 때마다
`unknown`이 `present`로 옮겨 가는 것이 눈에 보이고, **조용히 `absent`로 접히는 회귀가
막힙니다.**

## 5.7. 배포 다이어그램은 결국 무엇을 어떻게 표현해야 하나

앞의 모든 이야기가 여기로 모입니다. **그림이 답해야 하는 질문이 넷**이고, 그중
셋은 UML 배포 다이어그램의 표준 관심사이며 **넷째가 이 과제의 고유 축**입니다.

| # | 그림이 답해야 할 것 | 표준에서의 이름 | 지금 상태 |
|---|---|---|---|
| 1 | 무엇이 **어디서** 도는가 | Artifact —«deploy»→ Node | ⚠ **둘이 한 상자로 접혀 있다** |
| 2 | 무엇이 무엇과 **어떻게** 통신하는가 | Communication path | ⚠ 선은 있으나 **프로토콜·포트가 없다** |
| 3 | **경계**는 어디인가 | Node 중첩 · 실행 환경 | ⚠ 중첩이 **하드코딩**이고 관리형이 밖에 있다 |
| 4 | **이 그림의 어디를 믿어도 되는가** | (표준에 없음) | ✅ **여기가 강하다** — origin·`<<inferred>>`·범례 |

**4번이 기여이고 1~3이 숙제입니다.** 순서를 뒤집으면 안 됩니다 — 예쁜 그림은 많고,
**"어디를 믿을지 말하는 그림"은 드뭅니다.**

### 규칙 1 — 노드와 아티팩트를 가른다

지금은 `_SHAPE["compute"] = "node"`이고 라벨이 컴포넌트 이름입니다. 즉
**`OrderService`가 곧 노드**입니다. UML에서는 컴포넌트가 노드가 아니라 **노드 위에
배포되는 아티팩트**인데, 둘이 접혀 있어서 **표현할 수 없는 것이 셋** 생깁니다.

- **한 VM에 두 컴포넌트를 같이 올리는 배치** — 지금 문법으로는 못 그린다.
- **수평 확장 대수** — 계획이 "대수는 정해지지 않았습니다"라고 **노트로만** 말한다.
  그림에는 상자가 하나뿐이라 **1대처럼 읽힌다.**
- **k8s·서버리스로 갔을 때의 층** — 노드풀 ≠ 파드 ≠ 컨테이너인데 1층으로 접힌다.

```
지금        node "OrderService"

바꿔서      node "VM · t3a.medium · ×?" {
              artifact "OrderService"
              artifact "OrderWorker"     ← 같이 올릴지 나눌지가 표현된다
            }
```

**`×?`가 핵심입니다.** 대수가 미정이라는 사실을 **그림에** 남깁니다 — 그림은 잘려
돌아다니고, 노트는 같이 안 갑니다(범례에 유보를 넣은 것과 같은 이유).

이건 미관 문제가 아니라 **목표 ②와 직결**됩니다. "VM 3대 vs k8s 노드 2개"를
비교하려면 **대수와 배치가 그림에 있어야** 합니다.

### 규칙 2 — 경계를 경계로 그린다 (그리고 KB에서 끌어온다)

지금 중첩은 이렇습니다.

```python
_CONTAINERS = ("vnet", "subnet")                     # 하드코딩
inside = {n.id for n in plan.nodes if n.role == "compute"}   # 컴퓨트만 안으로
```

결과가 둘입니다.

- **관리형 서비스가 VPC 밖에 그려집니다.** 예제에서 `order-api-db`·`message-queue`·
  `secret-store`가 전부 바깥입니다 — RDS는 실제로 서브넷에 삽니다.
- **보안그룹이 떠 있는 상자입니다.** 경계를 나타내는 요소인데 **아무것도 감싸지
  않습니다.**

**여기서 이 문서의 초판이 틀렸습니다 — 정정합니다.**

초판은 *"graphkb의 `contained_in`을 쓰면 된다"*고 적었습니다. 실측해 보니
**그 관계는 네트워크 배치가 아닙니다.**

| 층 | `contained_in`이 실제로 뜻하는 것 | 건수 |
|---|---|--:|
| core | `subnet ⊂ vNet` · `vm ⊂ mci` · `k8sNodeGroup ⊂ k8sCluster` | 3 |
| azure | **ARM 이름 계층** — `farmBeats/extensions ⊂ farmBeats` | 2,223 |
| gcp | **프로젝트·조직 소속** — `ServicePerimeter ⊂ Project` | 378 |
| **aws** | — | **0**(5장의 의도된 공백) |

**"RDS가 서브넷에 산다"를 아는 축은 어디에도 없습니다.** GCP 쪽은 서브넷을 가리키는
담김이 **0건**이고, Azure의 182건은 `virtualNetworks/subnets ⊂ virtualNetworks`처럼
이름 계층이지 배치가 아닙니다.

그래서 결론이 바뀝니다.

- **하드코딩된 `("vnet","subnet")`은 core 층의 사실과 일치합니다** — 틀린 값이
  아니라 **근거가 안 달린 값**입니다. 같은 값을 KB에서 끌어오면 근거가 붙습니다.
- **컴퓨트를 서브넷 안에 그리는 것은 KB 사실이 아닙니다.** core는 `vm
  **references** subnet`이라고 말하지 담김이라고 말하지 않습니다. 실무적으로 맞는
  배치이지만 그건 **우리 읽기**이고, 그렇게 표시해야 합니다.
- **관리형 서비스는 배치를 모릅니다.** 지금 VPC 밖에 그려지는 것이 "밖에 있다"는
  주장으로 읽히는데, 사실은 **"우리가 모른다"**입니다. 안 그리는 것보다 나쁜 것은
  모른다는 말 없이 밖에 그리는 것입니다.

> **이 정정 자체가 이 문서의 방법을 증명합니다.** "KB에 있으니 쓰면 된다"는 그럴듯한
> 문장이었고, **세어 보기 전까지는 맞아 보였습니다.** 16장의 "실측 전 착수 금지"가
> 문서 작성에도 적용됩니다.

### 규칙 3 — 확실성을 시각 언어로 (이미 강한 축을 끝까지)

`origin`은 넷(design·designer·kb·inferred)인데 **스테레오타입은 둘**뿐이고, **`unknown`
(못 읽음)은 그림에 아예 없습니다.** 층 3(§5.5)에서 `unknown`이 생기면 그림에도
자리를 줘야 합니다.

| 무엇 | 어떻게 |
|---|---|
| KB 사실 | 실선 · 스테레오타입 없음 |
| 우리 추론 | `<<inferred>>` (지금 그대로) |
| 설계자 지정 | `<<specified by the designer>>` (지금 그대로) |
| **후보가 여럿** | **하나를 고르지 않고 후보를 나열한 상자** — 임의 선택 금지의 시각화 |
| **못 읽음(`unknown`)** | **회색 물음표 노드** — *"여기 뭔가 있을 수 있는데 우리가 못 봤다"* |

마지막 줄의 기제는 **이미 있습니다** — `plan.unresolved`가 있고 범례에
*"N items we could not answer"*가 실립니다. 다만 **예제에서 값이 비어 있습니다**
(`unresolved == []`). OpenAPI 파서가 못 읽은 것을 여기 안 먹이기 때문입니다.
**층 3을 하면 이 칸이 저절로 채워집니다.**

### 규칙 4 — 무엇을 표현하지 **않을** 것인가

그림이 커지면 쓸모가 줍니다. 안 그릴 것을 정하는 것도 설계입니다.

| 안 그린다 | 왜 |
|---|---|
| 우리가 안 정한 것을 정한 것처럼 | 임의 선택은 이 저장소가 막아 온 실패다. 후보로 그리거나 안 그린다 |
| 짐작한 인스턴스 대수 | 근거 없는 사이징은 확신에 찬 오답의 왕도(9장) |
| 규제 준수 판정 | 법적 판단은 우리 몫이 아니다(11장) |
| 모니터링·로깅 파이프라인 | **운영의 그림**이다. `app::` 아키타입에 모니터링이 없는 것과 같은 경계 |

### 한 줄로

> **배포 다이어그램은 "무엇이 어디에 몇 개 놓이고 무엇과 통신하는가"를 그리되,
> 각 요소마다 그 배치가 어디서 나왔는지와 우리가 못 본 자리를 함께 그려야 한다.**

앞의 절반은 UML이 이미 답을 갖고 있고(우리가 아직 안 따라간 것), **뒤의 절반이 이
과제가 더하는 것**입니다.

## 6. 연구 목적과 맞는가 — 원문 대조

`docs/research.md`의 목표 셋과 이 사슬을 맞춰 봅니다.

| 과제 목표(원문 요지) | 사슬에서의 자리 | 상태 |
|---|---|---|
| **① 요구사항 기반 산출물 검증 + 피드백으로 에이전트 갱신** | `verify_against_requirements` — 계획을 `RESOURCE_SPEC`과 대조해 판정 4줄 | **작동**. 예산은 비대칭 판정(초과 확정 / 준수 판정 불가) |
| **② 클라우드 환경·리소스 특성(성능·비용·용량·의존성) 가이드라인** | 창립 4축이 **그 네 단어 그대로** — perfkb·costkb·capacitykb·graphkb | **작동**. 단 축마다 덮는 CSP가 다르다(kb-book 3장 격자) |
| **③ 에이전트 간 연계, 개발 단계별 산출물 생성** | 설계 에이전트 산출물(JSON 계약) → 배포 계획·다이어그램 | **작동**. 단 계약 협의가 회신 대기 |

그리고 **문제 정의**와의 대응이 더 정확합니다.

| 과제가 적은 문제 | 이 사슬의 대응 |
|---|---|
| "AI가 환각으로 요구사항에 부합하지 않는 리소스를 산출물에 포함" | `evidence`/`basis`/`origin` — 계획의 모든 요소에 근거가 붙고, 검증 안 된 것은 `<<inferred>>` |
| "리소스 간 의존 관계와 선택 제약이 존재" | graphkb(의존) · capacitykb(제약) |
| "특정 리소스를 선택하면 **연계되는 리소스 군을 획득**할 수 있어야" | **bundlekb** — 예제에서 상자 4개가 이걸로 생겼다 |
| "선택 가이드라인(비용·성능) 제공" | costkb · perfkb — 계획 노트에 값과 경고로 실린다 |
| "단계별 산출물이 요구사항에 부합하는지 **측정**" | `verify` 판정 4줄 |

**부합합니다.** 목표 ①의 **"사용자 피드백을 위한 에이전트 갱신 과정"**에 대해서는
초판이 *"사슬에 자리가 없다"*고 적었는데 **절반이 틀렸습니다 — 정정합니다.**

| 어디 | 피드백 고리 |
|---|---|
| **요구사항 에이전트** | **있습니다** — `agent/playbook.py`. 사용자 지적이 적용되고 동시에 플레이북에 남아 다음 실행이 읽습니다. 출처별로 문턱이 다릅니다(결정론 검출기는 낮게, LLM 판정은 높게, 사람 말은 그 사이) — LLM 판정이 78~90% 흔들리는 것을 측정해서 정한 값입니다 |
| **배포 계획** | **없습니다** — `verify`가 판정을 내지만 그 판정이 어디로도 돌아가지 않습니다 |

그래서 남은 것은 "고리가 없다"가 아니라 **"고리가 요구사항 쪽에만 있다"**입니다.
그리고 배포 쪽 고리의 가장 값싼 형태는 새 학습 장치가 아니라 **이미 있는 판정을
요구사항 질문으로 되돌리는 것**입니다 — `verify`가 *"규모를 판정할 수 없다"*고 할 때
그 판정을 닫는 데 필요한 칸은 이미 알고 있고(`RESOURCE_SPEC.expectedConcurrentUsers`),
그 칸을 묻는 관심사도 이미 있습니다(`cn.expected-scale`). **끊긴 것은 그 둘을 잇는
한 줄뿐입니다.**

### OpenAPI 추출기 보강 — 값싼 순서 (§2 실측에서 도출)

| 순 | 할 일 | 왜 이 순서인가 |
|---|---|---|
| 1 | **못 읽은 것을 세어서 밝힌다** | 고치기 전에 **드러내는 것**이 먼저다. `$ref`를 만나면 "참조라 못 읽음 N건"을 계획 고지에 싣는다. 이것만으로 조용한 누락이 사라진다 |
| 2 | **로컬 `$ref` 해석**(`#/...`) | 실무 관행의 대부분이 문서 내부 참조다. 외부 파일(`./x.yaml`)은 우리가 못 받으므로 1번의 고지로 남긴다 |
| 3 | **바이너리 판정을 `schema.format == "binary"`로** | content-type 목록은 늘려도 끝이 없다. 스펙이 주는 정확한 신호를 쓴다 |
| 4 | **`webhooks`·`callbacks` → 비동기 신호** | 지금은 비동기를 시퀀스에서만 읽는다. API 명세만 있는 컴포넌트의 큐 신호를 통째로 놓친다 |
| 5 | **`paths`가 비면 `has_api`를 참으로 하지 않는다** | 부재를 긍정으로 승격하지 않는다는 규율 그대로 |

**1번이 나머지 넷보다 값이 큽니다.** 2~5는 덮는 범위를 넓히는 일이고, 1번은
**틀린 답을 맞는 답처럼 보이게 하는 것을 멈추는 일**입니다.

| 2 | ~~노드와 아티팩트를 가른다~~ → **절반 완료** | **대수는 그렸다**(2026-07-28) — 컴퓨트 노드에 `×?`가 붙고 범례가 "몇 대인지 정해지지 않았다"고 말한다. 그림에 상자가 하나뿐이라 **1대처럼 읽히던 것**이 사라졌다. **남은 절반**은 `node{artifact}` 중첩(한 VM에 여러 컴포넌트·k8s 3층)이고, 되파싱 검증까지 같이 손봐야 해서 별도 과제다 |

**1번이 가장 값싸고 효과가 큽니다** — 코드 상수를 KB 조회로 바꾸는 일이고, 그 순간
그림이 프로바이더를 따라가고 "왜 여기 들어가나"에 근거가 붙습니다.

### 4번을 먼저 하는 것이 값이 크다

`consumer=None`이 지금 **두 가지 뜻**을 겸하고 있습니다 — "이을 건데 아직"과 "안
이을 것". 이 저장소가 반복해서 지켜 온 규율(**"모른다"와 "없다"를 다른 문장으로**,
**"구현 범위와 근거를 섞지 않는다"**)이 관심사 축에서만 안 지켜지고 있는 셈입니다.
칸 하나(`out_of_scope` 또는 `consumer="(deployment 밖: 운영)"`)면 해결되고, 그
순간 **"23건이 끊겼다"가 "8건은 경계, 15건은 예정"**으로 바뀝니다.
