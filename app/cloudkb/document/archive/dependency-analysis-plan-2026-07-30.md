## 0.1 범위 진술 (사용자, 2026-07-30)

**cloud-barista는 벤더 중립이라 분석 기준으로 고른 것이다 — 직접 사용할 계획은 없다.**
따라서:

- CB 소스(tumblebug·spider)는 **관측 코퍼스로 계속 읽는다** — 소스를 읽는 것은
  사용이 아니다. 경계(자원 21종)도 유지한다.
- `authority=tumblebug` 간선은 우리 시스템에 **구속력이 없다** — 우리는 그 도구로
  배포하지 않는다. 귀속(P1·P2)이 장부 정리가 아니라 강제 대상 선별이 되는 이유다.
- 실배포 검증(P5)의 경로에서 **CB가 빠진다.** 진실 문서 §6의 *"실제로 배포해 볼 수
  있는 유일한 검증 경로"*는 이 결정으로 무효 — 진실 문서에 정정을 적었다.

## 0.2 진실의 원천 서열 (사용자 정정, 2026-07-30)

**graphkb 산출물(`tumblebug_resources.json` · `core_vendor_map.json` · `reviewed/*`)도
우리 가공물이다 — 지식베이스는 진실의 원천이 아니다.** 서열:

1. **컨트롤 플레인** (동적 — P5a·P5b)
2. **원천 캐시** — CB 소스 원문 · 벤더 스키마 원문. 관측의 `file:line` 인용이
   가리켜야 하는 곳이다
3. **우리 가공물** — **피검사물이거나 중간 산물이다. 오라클로 쓰지 않는다**

따라서 P3의 오라클은 벤더 스키마 **원문(캐시)**이고, `core_vendor_map`을 경유한
투영은 가공물이라 드라이버 코드 재확인을 거친다 — T3이 개별 사례가 아니라 이 서열의
일반 규율이다. 이 계획 §0의 재검증도 같은 이유로 "우리 JSON과 문서의 일치"까지만
말하고 원천과의 일치는 P2~P5가 잰다.

## 0.3 계정 현황 (2026-07-30)

**CSP 계정은 azure 하나다.** 동적 검증의 CSP별 상한:

| CSP | 도달 가능한 최고 층 | 비고 |
|---|---|---|
| azure | **P5b** | 하필 preflight가 가장 강한 CSP다(ARM validate/What-If). 외부 대조에서 실제로 틀렸던 방향 역전이 azure였고, `cspConditional` 6건 전부에 azure 값이 갈려 들어가 있다(k8s subnet 수 2↔1 · vpn은 azure만 필수 · sqlDb는 aws만 요구) — **동적 검증이 가장 필요한 열이기도 하다** |
| aws · gcp | **P2 (정적 상한)** | 동적 미실행으로 표시한다. azure 결과를 일반화하지 않는다(T9) |

P5.0(LocalStack)은 AWS 에뮬레이터라 현 계정 구성에서는 **보류** — azure 하네스
셰이크아웃은 비용 0인 P5a 호출이 겸한다. AWS 계정이 생기면 되살린다.

## 1. 문제 진술 — 판정 셋이 필드 하나에 눌려 있다

`required: true/false` 하나가 세 질문을 겸한다: **존재 의존인가**(진실 문서 §7 질문 1) ·
**누구의 요구인가**(§6 — *"cb-tumblebug이 요구한다 ≠ 클라우드가 요구한다"*) ·
**어느 CSP에서인가**(`cspConditional`). 외부 대조에서 틀린 셋 전부가 이 압축에서 나왔다 —
sshKey(도구의 요구를 클라우드의 요구로 읽음) · spec/image(값을 간선으로 읽음) ·
azure 방향(§3.2의 층 혼합).

**정의 (진실 문서 §7을 유지하고 검증 절차만 붙인다).** 간선은 검증 가능한 주장이다:

- 존재 의존 — *B 없이 A 생성을 시도하면 실패한다.*
- 생명주기 의존 — *A가 있는 채 B 삭제를 시도하면 거부되거나 캐스케이드된다.*
- 기능 의존 — 유형을 새로 만들지 않는다. §7 결정대로 **명시적 공백으로 출력**한다.

이 반사실 정식화는 우리 발명이 아니라 계보 인용이다 — Parnas의 uses 관계
(*Designing Software for Ease of Extension and Contraction*, IEEE TSE 1979:
"A uses B iff correct functioning of A depends on a correct implementation of B")를
인프라 자원에 인스턴스화한 것. 새 분류 라벨은 만들지 않는다(문서 정책 5 · `D1~D9` 전례).

## 2. 단계

### P1 — 간선에 판정을 갈라 싣는다 (스키마 개정)

- **첫 작업: 소비자 전수 확인.** `tumblebug_resources.json`을 읽는 코드를 전부 찾고
  나서 필드를 움직인다. (이 계획 시점에 소비자 목록은 미확인 — 확인 전 개정 금지.)
- 간선에 두 필드: `question`(existence | lifecycle) · `authority`(cloud | tumblebug | spider).
  - `question`은 **관측 형태에서 기계적으로 도출**한다(요청 스키마 필드·생성 전 존재
    확인 → existence, 삭제 보호 코드 → lifecycle, 운영 스크립트 순서 → 보강 전용).
    **이 대응표 자체는 우리 구성이다 — 파일에 표시해 싣고 반례에 열어 둔다.**
  - `authority`의 근거는 §6의 구분과 sshKey 반례.
- 멈추는 조건: 관측 없는 유형 배정 0건 · 분류하는 것이 없는 값 0개 · 기존 12건 테스트
  통과 유지 + 유형-관측 정합 테스트 신설.

### P2 — 필연의 귀속 재판정 (`required` 28 전수)

- 각 필수 간선에 대해 *"클라우드의 요구인가, 도구의 요구인가"*를 공급자 스키마 투영
  (`core_vendor_map.json` 경유)과 **cb-spider 드라이버 코드**로 판정한다. 방법은
  `a490071`에서 이미 쓴 드라이버 재확인 절차(28/28)를 그대로 쓴다 — 사람 검수 매핑은
  근거가 못 되므로 코드가 최종.
- 산출: `required: true` → CSP·권위로 갈라진 판정. 판정 불가는 판정 불가로 적는다.
- **왜 중요한가 (§0.1)**: 우리는 CB로 배포하지 않으므로, 도구 귀속 간선은 우리
  산출물의 강제 대상이 아니라 참고가 된다. 귀속이 곧 범위 판정이다.
- 멈추는 조건: 28개 전수 · "이유 미확정" 0(외부 대조가 세운 기준을 유지).

### P3 — 벤더 스키마가 말하는데 우리에게 없는 간선 6 닫기 (미결 5)

- `k8sNodeGroup→subnet`(aws 필수) · `nlb→subnet` · `nlb→securityGroup` ·
  `k8sNodeGroup→vNet` · `subnet→securityGroup` · `customImage→dataDisk` —
  각각 드라이버/스키마 인용을 붙여 **채택 또는 사유 있는 기각**.
- 포화 기준: 벤더 투영 그래프와 우리 그래프의 대칭차가 전부 "사유 있는 미채택"이 될 때.

### P4 — 외부 어휘 재정박: `com.ubicity:2.5` (미결 2)

- 간선 전수를 ubicity 어휘(Network·Subnet·SecurityGroup·KeyPair·Port·VirtualCompute)와
  짝짓고, 대응 없는 간선은 대응 없음으로 기록한다.
- **모양 대조 전용이다.** TOSCA 2.0 사정(§3.1.2)으로 `required` 판정은 기대하지 않는다.

### P5 — 반사실 검증 = 모델 기반 테스트 생성 — **게이트 있음(P5b만)**

**프레임 (2026-07-30 개정).** 고전 MBT는 모델에서 테스트를 도출해 구현을 검사한다
(Utting & Legeard, *Practical Model-Based Testing*). 우리는 방향이 반대다 — 컨트롤
플레인이 진실이고 **모델(우리 간선)이 피검사물**이다(모델 학습의 역방향 —
Vaandrager, *Model Learning*, CACM 2017 계열). 기계는 같다: **유형 붙은 간선에서
테스트 템플릿을 기계적으로 도출한다.** P1(유형 분리)이 이 단계의 선행 조건인 이유다 —
유형 없이는 어느 실험이 그 간선을 검증하는지 도출할 수 없다.

| 간선 유형 | 음성 테스트 | 양성 대조군 |
|---|---|---|
| existence(필수) | B 없이 A 생성 → 실패해야 한다 | B 생성 후 A 생성 → 성공해야 한다 |
| lifecycle | A 있는 채 B 삭제 → 거부/캐스케이드를 관측 | A 삭제 후 B 삭제 → 성공해야 한다 |

쌍을 넘는 시퀀스는 연쇄 의존 계산 시작 리소스 7행(`dependency-model.md` §1.2)으로 한정한다 — 상태
폭발 없음. **CB 없이 한다(§0.1)** — 경로는 CSP API 직접 또는 terraform `apply`
(`plan`/`validate`는 서버 측 제약을 안 보므로 동적 증거는 `apply`부터다).

**3층 실행.**

| 층 | 무엇 | 비용 | 증거 지위 |
|---|---|---|---|
| **P5.0** | LocalStack — **하네스 디버깅 전용**(생성·삭제·정리 루프가 도는가, 실패 관측이 파싱되는가). **현 계정 구성(azure뿐)에서는 보류 — §0.3** | 0 | **증거 아님.** 에뮬레이터는 제3자 재구현, 즉 또 하나의 모델이라 모델 대 모델 대조다. 특히 "허용" 관측은 무증거 — 충실도 공백이 기본 설명이다. AWS 전용이라 멀티 CSP도 깨진다 |
| **P5a** | **서버 측 사전 검증(preflight)** — ARM `validate`/What-If · EC2 `DryRun` · GCP `validateOnly` | ~0 — **계정만 필요** | **실물 증거, 부분 커버리지.** 에뮬레이터와 달리 진짜 컨트롤 플레인의 답이다 |
| **P5b** | 실제 `apply` + teardown — 유형별 층화 표본. **현 계정으로는 azure 열만(§0.3)** | 소액 | 최상급. 유형별 혼동 행렬을 낸다 |

- **P5a 실행 전 확인 항목 — 기억 기반이라 미확인, API 문서로 검증하고 시작한다:**
  `DryRun`의 검증 범위(권한 외 파라미터·의존 검증이 어디까지인가) · GCP `validateOnly`의
  소재(서비스별로 다르다) · What-If가 우리 간선의 제약 종류를 실제로 잡는가.
- **게이트 재정의: P5a는 CSP 계정만 있으면 열린다. 비용·teardown 위험 결정은
  P5b에만 남는다.** 게이트가 안 열리면 P2의 드라이버 코드 판정이 주장의 상한이다
  (정적 판정까지만 주장하고, 실배포 검증은 미실행으로 표시).
- 실측 전 추정(주장 아님): 39간선의 자원 다수(vNet·subnet·securityGroup·sshKey)는
  무료이고 유료 자원도 분 단위 생성-삭제면 실험 전체가 몇 달러 규모로 예상된다 —
  실행 시 실측으로 대체한다.
- 1회 실행으로 A/B 하지 않는다(진실 문서 §10.1-4).

## 3. 측정과 논문 연결

- 오라클 층화: 벤더 스키마 **원문·캐시**(정적, P3 — 투영 가공물이 아니라 원문이
  오라클이다, §0.2) → 드라이버 코드(정적, P2) → 서버 측 사전 검증(실물·부분, P5a) →
  실배포(동적, P5b). 각 층에서 정밀도/재현율을 따로 보고하고 층을 섞어 말하지 않는다.
  **에뮬레이터(P5.0)는 오라클 층이 아니다** — 결과를 증거로 쓰지 않는다.
- **간선×CSP마다** 도달한 최고 오라클 층을 기록한다 — "검증됨"은 층 이름과 함께만
  쓴다. 현 계정 구성에서 동적 층은 azure 열만 닿는다(§0.3).
- 부합 판정 축(진실 문서 §10-3, 의도 오류 4종)은 이 그래프의 **소비자**다 — 이 계획이
  입력 품질을 정한다.

## 4. 타당성 위협

| | 위협 | 대응 |
|---|---|---|
| T1 | 관측 형태→질문 대응표는 우리 구성 | 표시하고 싣는다. 반례 나오면 표를 고친다 |
| T2 | 참조 앱 코퍼스 편향 — 선언형 갈래는 의존을 템플릿 안에 숨긴다(`dependency-model.md` §2.3: vpn·sqlDb) | **미관측 ≠ 부재.** 미관측은 갈래 사유와 함께만 보고 |
| T3 | `core_vendor_map`은 사람 검수 산출물 | 드라이버 코드 재확인을 유지(P2) |
| T4 | 판 고정(tumblebug v0.12.25 · spider v0.12.37) | 판 갱신 시 재추출 전제를 명시 |
| T5 | P5 표본이 층화가 아니면 existence만 검증되고 lifecycle이 빈다 | 유형별 층화 + 유형별 보고 |
| T6 | **어휘–실행 갭**: 분석 어휘는 CB 중립 자원 21종인데 실행은 CB 밖(k8s 매니페스트·CSP 자원)이다. 추상 계층의 간선이 실행 계층의 진실과 다를 수 있다 | 간선 주장마다 **어느 계층에서 성립하는가**를 명시. P5가 실행 계층 대조를 겸한다 |
| T7 | **preflight 커버리지 편향** — P5a가 잡는 제약 종류만 "검증됨"이 되면 P5b 없이 주장이 부푼다. 런타임에만 드러나는 오류는 preflight가 못 본다 | 간선마다 도달한 최고 오라클 층을 기록하고 층별로만 집계(§3). P5a 단독 결과로 재현율을 말하지 않는다 |

## 5. 진실 문서 §10과의 관계

이 계획은 §10을 대체하지 않는다 — §10의 2(설계 산출물)·3(부합 판정)·4(측정)에 근거를
대는 **의존성 갈래의 세부**다. §10-1(`RESOURCE_SPEC` 개편)과는 독립이라 순서 제약이
없다. P1·P2가 §10-2의 연쇄 의존 계산 시작 리소스 품질을 정하므로 그보다 먼저가 맞다.
