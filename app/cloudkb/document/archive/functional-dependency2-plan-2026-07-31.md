# 기능 의존 2라운드 계획 — firewall·라우팅 도달성, 3사 (2026-07-31, 실행 전 기록)

## 왜 이것인가

1라운드가 오라클(기능 신호 = 외부 TCP 도달성, 인과 사다리 = 확인→변이→
상실→복원→회복)을 세웠다. 같은 신호로 잴 수 있는 간선이 둘 더 있다:

- **nic/vm→firewall**: 1라운드 덤 관측(Standard PIP secure-by-default —
  NSG 부착 전 7회 실패, 부착 직후 성공)이 이미 이 결속의 반쪽이다. 정식
  사다리로 승격한다.
- **subnet→internetGateway(라우트)**: 어휘 밖 대기열의 internetGateway를
  기능 축으로 닫는다 — 존재 전제(aws IGW 교란)는 기실측이고, 남은 것은
  "라우트가 빠지면 도달성이 죽는가"다.

VM 1대/CSP로 두 셀을 연속으로 잰다(비용 절약 — 셀 간 독립성은 복원 후
F3 회복 확인이 지킨다).

## 셀

| CSP | firewall 변이 | 라우팅 변이 |
| --- | --- | --- |
| azure | 서브넷에서 NSG 분리 → 재부착 (Standard PIP secure-by-default와 합성된 효과임을 술어에 명시) | **대응 자원 부재** — 인터넷 경로가 시스템 라우트라 사용자 자원이 아니다. 측정 불가가 아니라 자원 부재의 기록 |
| aws | 인스턴스의 SG를 빈 인그레스 SG로 교체 → 원복 (관계 변이 — 규칙 변이보다 간선다움) | 전용 VPC의 0.0.0.0/0→IGW 라우트 삭제 → 재생성 |
| gcp | 전용 네트워크의 allow-22 방화벽 규칙 삭제 → 재생성 (gcp 방화벽은 자원 간 부착이 아니라 네트워크 스코프 규칙 — 관계 변이가 없어 규칙 변이가 유일한 경로임을 명시) | 전용 네트워크의 default-route(0.0.0.0/0 → default-internet-gateway) 삭제 → 재생성 |

aws·gcp는 전용 네트워크 사슬을 세운다(default VPC/네트워크의 공용 라우트를
건드리면 안 된다). azure는 1라운드와 같은 vnet 경로 + NSG.

## 함정·위협

- **연쇄 오염**: 셀1(방화벽) 복원 후 F3 회복을 확인하고 나서 셀2(라우트)로
  간다 — 회복 확인 없이 이어가면 상실의 원인이 섞인다.
- **전파 지연**: 방화벽/라우트 변이는 즉시~수십 초 전파. probe 재시도가
  흡수하되, 상실 관측(want False)은 연속 2회 확인으로 강화한다(순간 지연
  오판 방지).
- gcp 라우트 재생성 이름은 우리가 정한다(자동 생성명과 다름) — 기능 회복이
  기준이지 이름 동일성이 아니다.
- T-단일실행 · 신호는 TCP 22 하나(1라운드와 같은 지위).

비용: VM 3대 × 수 분. 리전 계승. 라운드 끝 3사 전수 점검.
