# VM 리소스 선택 기준

## 1. 목적

의존성 분석이 “함께 필요한 리소스”를 정한다면, VM 선택은 그중 어떤 VM 제품을 쓸지
정한다. 둘은 다른 문제이며 같은 점수로 합치지 않는다.

## 2. 입력과 출력

선택기를 실행하기 위한 입력은 CSP, 리전, 최소 vCPU, 최소 메모리다. 예산 상한, 아키텍처,
가속기 필요 여부와 상시 CPU 필요 여부는 선택 입력이다. 이는 사용자가 최초 요구사항에서
모두 답해야 한다는 뜻이 아니다. 현재는 사용자가 명시했거나 실험 입력으로 고정한 최소
용량만 사용하며, 검증된 부하 측정값이 없으면 가장 작은 VM이 충분하다고 추정하지 않고
추천을 보류한다.

출력은 조건을 만족하는 후보 목록과 다음 근거다.

- 제품명, vCPU, 메모리, 리전
- 가격 스냅샷과 기준 시점
- 버스트·구세대 등 확인 가능한 성능 경고
- 데이터가 없어서 판정하지 못한 항목

## 3. 선택 절차

1. CSP·리전·아키텍처가 맞지 않는 후보를 제외한다.
2. 최소 vCPU·메모리·가속기 조건을 충족하지 않는 후보를 제외한다.
3. 예산이 있으면 월 730시간 기준의 VM 목록 가격으로 상한을 검사한다.
4. 같은 CSP 안에서만 확인 가능한 성능 경고를 붙인다.
5. 남은 후보를 비용 등 명시된 기준으로 정렬하되, 결측값을 좋은 값으로 해석하지 않는다.

프로바이더마다 성능 지표가 달라 AWS·Azure·GCP VM의 절대 성능 순위를 만들지 않는다.
정규화된 동일 벤치마크가 생기기 전까지 CSP 간 비교는 용량 충족과 가격 비교로 제한한다.

## 4. 데이터 범위

`costkb`와 `perfkb`에는 AWS·Azure·GCP VM만 남긴다. 관리형 서비스, Kubernetes,
IBM 등 다른 CSP는 포함하지 않는다. 가격은 실제 청구액이 아니라 스냅샷 목록 가격이며
스토리지·송신·세금은 포함하지 않는다.

## 5. 현재 구현 상태

3사 VM 카탈로그는 65,032개 사양·가격 레코드와 같은 수의 성능 레코드를 포함한다.
구현 단계의 VM Terraform 생성 직전에 후보 필터를 실행하며, 결과와 추천 근거는
`vmSelection`으로 구현 산출물에 저장하고 같은 구조를 IaC 생성기에 제공한다.

최소 vCPU와 메모리 중 하나도 없으면 추천을 보류한다. 정확한 카탈로그 리전만 사용하며,
최소 VM 수와 월 730시간을 곱한 온디맨드 컴퓨트 목록 가격이 예산을 넘는 후보를 제외한다.
상시 부하는 성능 KB에서 경고 없음이 확인된 후보 중 최저가를 우선하고, 확인 가능한 후보가
없으면 최저가 후보와 경고를 함께 낸다. 이 판단은 스토리지·송신·LB·세금·할인을 포함하지
않으므로 전체 예산 충족 판정이 아니다.

실제 카탈로그 점검에서 AWS `ap-northeast-2`, Azure `koreasouth`, GCP
`asia-northeast3`의 2 vCPU·4 GiB 상시 부하 후보를 생성했다. 현재 Azure 가격 데이터에는
`koreacentral`이 없어 그 리전은 거짓 대체 없이 보류한다.

애플리케이션 부하를 최소 vCPU·메모리로 바꾸는 검증된 모델은 여전히 없다. 따라서 사용자가
최소 용량을 명시한 별도 여섯 개발 사례로 RQ3 구성요소 검사를 수행한다. 기존 P1~P3 종단
입력은 최소 용량이 없어 RQ3 표본으로 사용하지 않는다. 이 검사는 카탈로그 경로의 직접
효과만 보여 주며 LLM 대조군과의 종단 효과를 대신하지 않는다.

## 6. 평가 기준

- 최소 vCPU·메모리 미충족률
- 예산 상한 위반률
- 지원하지 않는 CSP·관리형 서비스 추천 수
- 가격 기준 시점과 성능 결측 고지율

추천 정확도는 의존 리소스·간선 F1과 별도로 보고한다.
