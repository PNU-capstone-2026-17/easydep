# 상류 산출물 샘플 — 무엇을 받아야 하고, 왜

배포 계획·다이어그램은 **요구사항 에이전트와 설계 에이전트가 낸 것**을 먹고 만들어
집니다. 그런데 이 저장소에는 그 실물이 한 벌도 없었습니다 — 지금까지의 시연은
`examples/order-demo.json`(**손으로 쓴 것**)과 테스트 픽스처로 돌렸습니다.

그러면 결과의 결함이 **어댑터 탓인지 입력 탓인지 가릴 수 없습니다.** 실제로
2026-07-28에 어댑터 경로로 돌려 보니 손으로 쓴 예제보다 결과가 나빴는데
(컴포넌트가 하나로 뭉치고, 시크릿 저장소가 빠지고, 큐가 선 없이 떠 있었다),
**입력이 픽스처라 원인을 못 가렸습니다.**

여기는 그 실물이 사는 곳입니다.

---

## 한 벌의 구성

```
samples/<이름>/
  PROVENANCE.md              ← **필수.** 누가·언제·무엇으로 만들었나
  requirements/
    resource_spec.json       ← RESOURCE_SPEC 계약 산출물
    cloud_concerns.json      ← (선택) 관심사 커버리지 — 진단용
  design/
    class_diagram.puml
    sequence_diagram.puml
    api_spec.json            ← OpenAPI 3.x
    erd.puml
```

`PROVENANCE.md`가 없는 샘플은 **손으로 쓴 것과 구별되지 않습니다.** 이 저장소가
소스마다 핀을 박는 것과 같은 이유입니다 — 어디서 나왔는지 모르는 입력으로 낸 결과는
재현도 반증도 안 됩니다. 최소한 이 셋을 적으십시오.

- **누가 만들었나** — 어느 에이전트/사람이, 어느 커밋에서
- **언제** — 날짜
- **무엇을 넣었나** — 원본 요구사항 문장(또는 그 출처)

---

## 각 산출물이 배포 단계에 무엇을 주는가

**측정한 것**입니다(`nim_agent/design_tools.py`의 `_collect_signals`가 실제로 읽는 것).
"있으면 좋다"가 아니라 **없으면 무엇이 안 나오는지**를 적습니다.

| 산출물 | 읽는 것 | 없으면 |
|---|---|---|
| **`api_spec.json`** | `paths` 존재 | 컴포넌트가 HTTP 서비스인지 모름 |
| | `components.securitySchemes` | **시크릿 저장소 노드가 안 생김** |
| | `requestBody`의 `multipart`·`octet-stream`·`format: binary` | **객체 스토리지 노드가 안 생김** |
| **`erd.puml`** | 엔티티의 소유 컴포넌트 | **DB 노드가 안 생김** |
| | `engineHint`(postgresql 등) | 엔진을 못 정해 후보로 남음 |
| **`sequence_diagram.puml`** | `actor → component` | **공개 노출을 몰라 로드밸런서가 안 생김** |
| | 비동기 메시지 | **큐가 안 생김** |
| | 전체 메시지 | 다이어그램의 **선이 없음** |
| **`class_diagram.puml`** | — | **아무것도 안 바뀜** (아래) |
| **`resource_spec.json`** | provider·region | **값·성능·번들 조인이 전부 닫힘** |
| | monthlyBudgetUSD | 예산 판정 없음 |
| | 규모·trafficPattern·stateless·multiZone | 해당 판정이 "요구사항이 없어 판정 안 함"으로 |

> **클래스 다이어그램은 지금 신호를 하나도 내지 않습니다.** 배포 관점에서 클래스 구조는
> "무엇이 어디에 배치되는가"를 가르지 못하기 때문입니다 — 같은 클래스 구조가 VM에도
> 컨테이너에도 함수에도 올라갑니다. **그래도 받아 두십시오**: 컴포넌트 경계를 뽑을
> 길이 여기밖에 없을 수 있고(아래 미해결), 안 받으면 그 가설을 시험할 수 없습니다.

## 이 샘플로 답하려는 질문

받는 것이 목적이 아니라 **아래 셋을 가리는 것**이 목적입니다.

1. **컴포넌트 경계** — 어댑터가 클래스 다이어그램에서 컴포넌트를 못 갈라 앱 하나로
   뭉쳤습니다. 실제 산출물에도 경계 정보가 없나, 아니면 픽스처가 얇았던 건가?
2. **비동기 신호** — 픽스처의 비동기가 `A ->> A`(자기 자신)라 큐가 선 없이 떴습니다.
   실제 시퀀스는 컴포넌트 사이로 그리나?
3. **`resource_spec`의 충족률** — 계약 필수 4칸을 요구사항 에이전트가 실제로 채우나?
   (배치 경로에는 되묻기가 없어 **구조적으로 0**일 수 있습니다.)

셋 다 **지금은 픽스처 탓인지 시스템 탓인지 못 가릅니다.**

## 받은 뒤에 할 것

```bash
python -m app.core.cloudkb.tools.intake_report app/core/cloudkb/appkb/samples/<이름>
```

무엇을 읽었고 무엇을 못 읽었는지, 그래서 계획에 무엇이 빠지는지를 냅니다.
**샘플을 눈으로 읽고 판단하지 마십시오** — 그게 지금까지 원인을 못 가린 이유입니다.
