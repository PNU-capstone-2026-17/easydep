# 리소스 의존성 분석 안내서

## 1. 무엇을 해결하는가

사용자가 “외부에서 HTTPS로 접근 가능한 애플리케이션”을 요청했다고 가정하자. VM 하나만
만든다고 서비스가 작동하지는 않는다. 네트워크, 서브넷, 방화벽, 외부 주소 또는 로드밸런서,
백엔드 연결과 상태 검사가 함께 맞아야 한다.

EasyDep은 다음 두 질문에 답한다.

1. 이 리소스를 만들기 위해 어떤 다른 리소스가 필요한가?
2. 생성된 뒤 요구한 인프라 기능을 제공하려면 어떤 관계가 유지되어야 하는가?

삭제 순서와 소유 리소스의 연쇄 삭제는 모델링하지 않는다. 새 배포 생성이라는 시스템 목적에
직접 쓰이지 않고, Terraform/OpenTofu가 실제 상태와 참조 그래프로 처리하기 때문이다.

## 2. 범위

- CSP: AWS, Azure, GCP
- 배포 방식: Docker-on-Linux-VM
- 핵심 리소스: VM, network, subnet, NIC, firewall, public IP, disk, load balancer,
  workload identity, default route
- 제외: Kubernetes, 서버리스, VPN, 범용 데이터베이스 서비스, 임의의 CSP 전체 API

## 3. 리소스와 구성 요소

모든 항목을 같은 수준의 리소스로 취급하지 않는다.

| 구분 | 예 | 설명 |
|---|---|---|
| 독립 리소스 | VM, VPC/VNet, subnet, disk | 독립 식별자와 제어 평면 연산을 갖는다. |
| 연결 리소스 | AWS ENI, Azure NIC | 독립 리소스일 수도 있고 VM 구성에 포함될 수도 있다. |
| 하위 구성 요소 | GCP `network_interface`, LB listener | 상위 리소스 속성이나 하위 블록으로 실현될 수 있다. |
| 논리 capability | 공개 진입, 영속 블록 저장소 | CSP마다 하나 또는 여러 native 리소스로 실현된다. |

벤더 API의 CRUD 연산은 이 경계를 판별하는 증거다. CRUD가 있다는 사실과 리소스 사이의
삭제 순서를 모델링하는 것은 별개의 문제다.

## 4. 관계를 읽는 방법

`A → B`는 관계군과 판정을 함께 읽어야 한다.

### 프로비저닝 관계

- `mandatoryForProvisioning`: B 없이는 A 생성이 거부된다.
- `conditionalForProvisioning`: 선택한 구성이나 범위에 따라 B가 필요하다.
- `notMandatoryForProvisioning`: 관측 조건에서는 B를 생략해도 A가 생성된다.

예를 들어 AWS `subnet → network`는 필수다. 반면 AWS VM의 별도 data disk는 선택이며,
부팅에 필요한 root volume은 이미지와 provider가 처리한다.

### 런타임 관계

생성 성공과 기능 성공을 구분한다. VM이 만들어져도 다음이 틀리면 서비스는 작동하지 않는다.

- 방화벽 인바운드 규칙
- 외부 주소 또는 로드밸런서 경로
- 기본 경로와 외부 통신
- 디스크 attach·format·mount
- workload identity 결합

각 claim은 `inbound-tcp`, `lb-serving`, `volume-write`처럼 관측할 신호를 명시한다.

## 5. 증거와 판정

각 claim에는 다음 정보가 있다.

- CSP와 관계 방향
- 관계군과 판정
- 적용 조건
- 공식 스키마 위치 또는 실험 좌표
- 예상 결과와 실제 결과
- 반복 상태

반복 상태는 다음처럼 해석한다.

| 상태 | 현재 수 | 의미 |
|---|---:|---|
| `replicated` | 38 | 동결한 기대 결과를 같은 절차에서 다시 관측했다. |
| `failed` | 5 | 반복에서 같은 결과를 얻지 못해 제품 추론에 사용하지 않는다. |
| `pending` | 2 | 아직 반복을 완료하지 않아 제품 추론에 사용하지 않는다. |
| 합계 | 45 | 프로비저닝 33개, 런타임 12개다. |

실패와 대기는 성공으로 간주하지 않는다. `closure()`는 확인되고 반복된 claim만 실제 계획에
반영하고, 나머지는 `unavailableFindings`에 남긴다.

## 6. 처리 흐름

```text
요구사항의 배포 capability
        ↓
DepKB의 CSP별 프로비저닝 관계 폐쇄
        ↓
필수·조건부·provider 생성 리소스 결정
        ↓
생성 순서와 CSP 제약 생성
        ↓
IaC 생성·validate·plan
        ↓
준비 상태와 애플리케이션 기능 검사
```

`createOrder`는 필수 프로비저닝 간선에서 계산한다. 삭제 순서 필드는 존재하지 않는다.

## 7. 현재 모델이 주장하지 않는 것

- 45개 claim이 모든 클라우드 애플리케이션을 대표한다는 주장
- CSP별 리소스가 항상 1:1로 대응한다는 주장
- 리소스 생성 성공이 애플리케이션 업무 기능 성공을 보장한다는 주장
- VM 사양만으로 처리량이나 비용 최적화를 보장한다는 주장
- 반복 실패 claim이 거짓이라고 확정하는 주장

이 모델은 제한된 범위의 배포 누락을 줄이기 위한 근거 기반 지식이며, 실제 앱 기능 검사를
대체하지 않는다.

## 8. 유지보수 원칙

1. 새 claim은 현재 Docker-on-VM 범위에 직접 필요한 경우만 추가한다.
2. 생성 가능성과 런타임 기능을 같은 판정으로 합치지 않는다.
3. CSP 기본 생성과 명시적 리소스를 구분한다.
4. 사람 문장을 실행 규칙으로 파싱하지 않는다.
5. 제품 모델에는 반복 확인된 관계만 사용한다.
6. 삭제·교체·마이그레이션 요구가 실제 제품 범위가 될 때만 별도 모델을 설계한다.
