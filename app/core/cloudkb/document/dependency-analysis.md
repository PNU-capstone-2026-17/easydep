# 클라우드 리소스 의존성 분석

> 적용 범위: AWS·Azure·GCP의 Docker-on-VM 배포

## 1. 쉬운 설명

VM 한 대만 선택해도 실제 배포에는 네트워크, 서브넷, 방화벽 규칙과 이미지 등이
필요하다. 클라우드 리소스 의존성 분석은 **선택한 리소스를 실제로 만들고 연결하기 위해
함께 필요해지는 리소스와 그 순서를 찾는 일**이다.

예를 들어 VM이 서브넷을 참조하고 서브넷이 네트워크 안에 있어야 한다면 다음과 같이
표현한다.

```text
VM → Subnet → Network
```

화살표는 "왼쪽을 배포하려면 오른쪽이 필요하다"는 뜻이다. 이 관계를 끝까지 따라가 얻은
이렇게 연쇄적으로 따라가 얻은 결과를 이 문서에서는 **연쇄 의존 자원 집합**이라고 한다.

## 2. 연구에서 사용하는 정의

배포 계획의 리소스 집합을 `V`, 의존관계를 `E ⊆ V × V`라고 하자. 조건 `c`에서
리소스 `a`가 리소스 `b`에 의존한다는 것은 다음 중 하나가 참이라는 뜻이다.

1. `a`의 생성 요청 또는 설정에 `b`의 식별자·속성·기능이 필요하다.
2. `b`가 준비되지 않으면 `a`를 유효하게 생성하거나 의도한 방식으로 운용할 수 없다.

이를 방향 간선 `a → b | c`로 기록한다. 무조건 성립하면 조건을 생략한다. 관계를 제품
지식으로 채택하려면 위 의미 조건과 별개로 CSP 공식 자료 또는 재현 가능한 대조 실험이
필요하다. 분석 결과는 시작 리소스에서 연쇄적으로 필요한 자원 집합, 조건, 필수성,
생성 순서와 근거를 포함한다.

이 정의는 TOSCA의 requirement–capability 관계 및 일반 `DependsOn`, Terraform의
참조 기반 암시적 의존성과 `depends_on`을 개념적 기준으로 삼는다. 하지만 특정 CSP에서
간선이 실제로 성립한다는 증거는 표준의 일반 개념이 아니라 해당 CSP 자료나 실험에서
얻는다.

### 이 정의의 출처

“클라우드 리소스 의존성 분석”에 대해 세 CSP가 공유하는 단일 판정 표준은 없다. 위 정의와
아래 판정표는 TOSCA의 요구–능력·관계 모델과 Terraform/OpenTofu의 참조 기반 생성 순서를
바탕으로 **본 연구가 정한 조작적 정의**다. 따라서 논문에는 기존 표준의 정의라고 쓰지 않고,
“관련 표준에 근거해 연구 범위에 맞게 정의했다”고 쓴다. 개별 간선의 참·거짓은 이 정의가
아니라 버전이 고정된 CSP 자료와 대조 실험으로 뒷받침한다.

## 3. 의존성으로 보지 않는 것

다음은 별도로 다룬다.

- 두 리소스가 예제에 함께 등장했다는 사실만 있는 경우
- VM 이미지나 인스턴스 유형처럼 기존 카탈로그에서 고르는 값
- 비용이 싸거나 성능이 좋다는 추천 관계
- 애플리케이션 서비스 사이의 API 호출
- 단순한 그룹·소유 표기이며 생성이나 유효성의 선행조건이 아닌 경우

따라서 동시 출현은 후보 간선을 찾는 단서일 수 있지만 확정 근거가 아니다. 용량·가격·성능
정보도 후보 선택에 사용하지만 의존 간선과 섞지 않는다.

## 4. 간선 판정 기준

각 후보 간선은 다음 질문으로 판정한다.

| 질문 | 기록 |
|---|---|
| CSP 공식 입력에서 상대 리소스 참조가 필수인가? | 필수 의존 |
| 특정 기능을 켤 때만 필요한가? | 조건부 의존과 조건 |
| 참조 없이도 만들 수 있으나 선택적으로 연결 가능한가? | 선택 가능한 연결; 선택되기 전에는 연쇄 의존 자원 집합에서 제외 |
| 서버가 자동 생성하여 사용자가 만들면 안 되는가? | 자동 생성, `doNotCreate` |
| 자료가 없거나 서로 충돌하는가? | `unknown`; 간선을 추측하지 않음 |
| 단순 동시 출현·추천·카탈로그 선택인가? | 의존에서 제외 |

`required=false`는 "불필요"가 아니라 현재 조건에서는 의무 간선이 아니라는 뜻이다.
선택 기능이 활성화되면 조건부 필수 간선이 될 수 있다. 조건을 모르면 필수와 선택 중 하나로
억지 판정하지 않고 미결 질문을 남긴다.

## 5. 근거 규칙

근거는 다음 순서로 우선한다. 이 순서는 외부 표준의 등급표가 아니라, 재현성·CSP 직접성·
대조 가능성을 기준으로 본 연구가 정한 증거 채택 규칙이다.

1. 버전이 고정된 CSP 공식 API·리소스 스키마
2. 최소 대조군을 둔 실제 생성·삭제 실험
3. 공식 IaC 공급자 스키마와 공식 예제
4. 검토된 오픈소스 구현
5. 문서 설명이나 관측된 동시 출현

하위 근거가 상위 근거보다 강한 주장을 만들 수 없다. 모든 간선은 CSP, 출처 위치 또는
실험 ID, 판정 조건과 관측일을 가져야 한다. "자료에서 찾지 못함"과 "의존하지 않음"을
구분한다.

TOSCA는 관계를 표현하는 이론적 정박점이고, Terraform은 참조가 생성 순서를 결정하는
실무적 정박점이다. 둘 다 AWS·Azure·GCP 간선의 정답 그 자체로 사용하지 않는다.

## 6. 분석 절차

1. 설계 산출물에서 VM, 영속 디스크, 외부 진입점 같은 시작 리소스를 정한다.
2. CSP별 지식베이스에서 직접 의존을 조회한다.
3. 조건을 평가하고 모르는 조건은 질문으로 남긴다.
4. 새로 발견된 리소스에 대해 반복하여 연쇄적으로 필요한 자원을 계산한다.
5. 순환, 미지원 간선, 사용자가 만들면 안 되는 리소스를 검사한다.
6. 설계에는 노드·간선·근거를, 구현에는 생성 순서와 검증 규칙을 전달한다.

자연어 요구사항의 해석은 LLM이 담당할 수 있지만, 연쇄 의존 자원 계산과 알려진 간선 검사는
결정론적 코드가 담당한다. LLM은 지식베이스에 없는 간선을 만들어서는 안 된다.

## 7. 타당성 위협

- CSP API와 공급자 스키마는 변경되므로 버전과 관측일을 고정해야 한다.
- 한 CSP의 관계를 이름이 비슷한 다른 CSP에 복사하면 안 된다.
- 성공한 생성 실험만으로 의존의 필수성을 입증할 수 없다. 의존 대상을 제거한 대조군이
  필요하다.
- 연구자가 만든 골드셋과 평가기가 같은 오류를 공유할 수 있으므로 원자료 링크와 판정
  근거를 공개하고 일부 표본은 독립 검토해야 한다.
- 본 결과는 Docker-on-VM 범위에만 일반화한다.

## 8. 현재 구현 상태

`depkb`는 CSP별 간선, 연쇄 의존 자원 집합, 설계 뷰, 프로비저닝 뷰와 계획 검사를 제공한다. 제품
`claims.json`은 VM 범위 주장 56개만 포함하며 AWS·Azure·GCP를 모두 포함한다. K8s·VPN
시작점은 공개 의존성 계산 함수가 거부한다. 과거 조사 코드는 소스 장부에 일부 남아 있지만 제품
산출물 생성 전에 제외되고, 인용되지 않는 실험은 제품 디렉터리에서 격리했다.

2026-08-06 산출물 감사 기준으로 56개 주장은 필수 10개, 선택 23개, 기능·수명주기 성립
23개다. 근거 항목은 스키마 61개, 실제 API 적용 실험 131개, 사전 검증 11개이며 참조한
실험 결과 파일의 누락은 0개다. 이 수치는 근거의 **존재와 연결**을 확인할 뿐, 판정 자체를
독립 검토했다는 뜻은 아니다.

세 CSP의 동결 골드로 KB 적용·제거 구성요소 검사는 완료했으며, 적용판 간선 F1 1.000,
제거판 0.000을 확인했다. 다만 골드와 KB가 같은 실측 주장을 공유하므로 이는 배선 검사지
독립 정확도 증명이 아니다. 독립 검토된 골드와 최종 구현물 종단 비교 전에는 전체 효과가
입증됐다고 주장하지 않는다.
