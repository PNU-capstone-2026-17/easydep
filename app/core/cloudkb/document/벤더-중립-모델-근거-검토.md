# 벤더 중립 모델의 추상화 근거와 EasyDep 적용 범위

## 결론

기존 모델들은 같은 의미의 “벤더 중립”을 제공하지 않는다. OCCI는 작은 IaaS 공통 자원
모델, TOSCA는 확장 가능한 토폴로지 언어, Cloud-Barista는 실제 멀티 CSP 운용 API,
CAMEL은 설계부터 런타임 적응까지의 애플리케이션 모델이다. Crossplane은 사용자가 정의하는
합성 API이며 Terraform은 실행 코어만 중립적이고 리소스 스키마는 공급자별이다.

따라서 EasyDep은 하나를 정답 온톨로지로 채택하지 않는다. 공통 개념은 비교 좌표로만 쓰고,
각 CSP의 독립 리소스·내장 구성·합성 실현을 별도 projection으로 보존한다.

## 모델별 판독

| 모델 | 추상화 수준 | 대응 방식 | 이 연구에서의 용도 | 핵심 한계 |
|---|---|---|---|---|
| Cloud-Barista | 운용 가능한 공통 IaaS API | 공통 객체를 CB-Spider 드라이버가 CSP API에 연결 | 리소스 후보와 성능 측정 용어 호환 | 공통 객체가 CSP 필수성이나 경계를 증명하지 않음 |
| TOSCA 2.0 | 애플리케이션·서비스 토폴로지 메타모델 | node type/profile과 requirement-capability 해소 | 관계·기능 계약·합성 표현 | 언어 자체에는 CSP 리소스 사전이 없음 |
| OCCI 1.2 | compute/network/storage/link 중심 최소 IaaS 모델 | kind·mixin·표준 속성에 구현체가 적합 | 최소 경계와 link/configuration 구분 | 현대 CSP의 VPC·IAM·LB 구조를 충분히 표현하지 못함 |
| CAMEL | 설계 및 models@runtime multi-DSL | 독립 모델을 공급자 모델·PaaSage 실행기로 구체화 | 앱 기능과 런타임 상태를 리소스 그래프에 연결 | control-plane 경계 판정 모델이 아님 |
| Crossplane | 조직 정의 상위 composite API | Composition이 하나 이상의 managed resource로 투영 | 다대다·합성 projection 설계 비교 | 보편 의미가 아니라 작성자별 플랫폼 API |
| Terraform | 중립 실행 코어와 provider별 자원 모델 | 보통 한 resource가 underlying API 객체 하나에 대응 | native 경계 보조 확인과 IaC 출력 | 리소스 종류는 벤더 중립이 아님 |

## 채택 규칙

1. 중립 모델에서 나온 개념은 조사 후보일 뿐이다.
2. CSP 경계는 공식 식별자와 create/read/delete 수명주기로 확정한다.
3. 대응은 `full` 또는 `partial`, 표현은 `independent`, `embedded`,
   `composite-member`로 기록한다.
4. 한 native 리소스가 여러 중립 개념을 포함하거나 한 중립 기능이 여러 native 리소스로
   실현되는 것을 허용한다.
5. 기능 실현의 완전성은 생성 성공이 아니라 앱 기동과 대표 업무 요청까지 검증한다.

세부 출처·버전·절 위치와 연구 내 사용 범위는
`evaluation/research_protocol/definitions/neutral-model-evidence.json`에 기계 판독 가능하게 고정한다.
런타임에서 사용하는 다대다 대응은
`app/core/cloudkb/depkb/provider-projections.json`을 단일 원본으로 삼는다.
