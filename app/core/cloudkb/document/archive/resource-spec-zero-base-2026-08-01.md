# RESOURCE_SPEC 제로베이스 재도출 (2026-08-01)

> **앞 문서를 정정한다.** `resource-spec-item-selection-2026-08-01.md`는 선정
> *절차*를 세웠지만, 실제로 한 일은 **증분**이었다 — 기존 15칸을 두고 `workloads`를
> 더한 뒤 몇 개를 빼거나 계층을 옮겼다. 사용자 지적: *"지금 계약이 제로베이스에서
> 다시 만들어진 건 맞아? 내가 제로베이스에서 하라고 했을 텐데?"* 맞는 지적이고,
> 이 문서가 실제 재도출이다.

## 1. 도출식

계약에 둘 이유는 하나뿐이다: **다른 어디서도 못 얻는 값인가.**

그래서 사슬이 소비하는 값을 전부 늘어놓고 값마다 물었다 — *누가 아는가.*
사용자 아닌 출처가 있으면 계약에 둘 이유가 없다(있으면 같은 답을 두 곳에서
받게 되고, 어긋날 때 어느 쪽이 진실인지 말할 수 없다).

출처는 넷이다:

    설계 산출물   컴포넌트·API·ERD·시퀀스
    실측 KB       depkb · costkb · perfkb · envkb
    계획 생성기   우리 추론
    CI·운영       렌더·배포 시점

**이 도출은 현행 계약을 보지 않고 했다.** 보고 나서 대조했다.

## 2. 결과 — 사용자만 아는 것 11

| 값 | 왜 사용자만 아나 |
|---|---|
| 어느 클라우드 | 조인 축이자 주장의 색인. 설계도 KB도 못 정한다 |
| 어느 리전 | 단가·용량·탄소가 코드로 색인. 설계 산출물에 없다 |
| 무엇 위에 올릴지 | 설계는 아키타입까지만 낸다 — k8s냐 VM이냐는 안 낸다. **과제 원문이 "사용자가 클라우드 리소스를 선택"이라 적는다** |
| 예산 | 요구사항 산문에 **0건**(코퍼스 실측). 제약 원문에서만 온다 |
| 스펙 하한 | 설계 산출물에 없다. 규모→스펙 변환은 소스가 없어 KB가 배제 |
| 부하 모양 | `cn.traffic-shape` |
| AZ 분산 요구 | `cn.redundancy-target` |
| 규모 | `cn.expected-scale` |
| 데이터 레지던시 | `cn.data-residency` |
| 탄소 제약 | `cn.carbon-constraint` |
| **이미 갖고 있는 자원** ★ | 실측 폐포는 *"무엇이 필요한가"*는 알아도 *"이미 있는가"*는 **원리적으로 모른다** |

사용자 아닌 것으로 갈린 것:

| 값 | 누가 | 
|---|---|
| 공개 노출 여부 · 영속 저장 필요 · 컨테이너 포트 · 프로브 경로 | **설계 산출물** |
| 이미지 태그 · 레지스트리 · 인그레스 컨트롤러 · TLS | **CI·운영** (→ 인계 항목) |
| 생성/삭제 순서 · 서버가 대신 만드는 것 · 완료 대기 | **실측 KB** |
| 스펙 선택 · 배포 방식 권고 | **계획 생성기** |

## 3. 현행과의 대조 — 10/11 일치, 하나 공백

도출한 11개 중 **열은 이미 계약에 있었다.** 증분으로 쌓은 것이 우연히 맞은
것은 아니고, 그동안의 정리(소비자 없는 칸 배제 · 계층 재판정 · 인계 분리)가
같은 판정식을 부분적으로 적용해 온 결과다.

**빠진 하나가 `existingResources`다.** 그리고 이것은 증분으로는 나올 수 없는
종류였다 — 기존 칸을 다듬는 방식으로는 "**없는 축**"이 안 보인다. 제로베이스가
실제로 값을 낸 자리가 여기다.

### 왜 이 칸이 필요한가

실측 폐포는 aws EKS에 `iamRole → network → subnet → k8sCluster`를 만들라고
한다. 사용자가 기존 VPC·서브넷에 얹는 경우에도 그렇게 말한다 — **폐포는
"사용자가 무엇을 갖고 있는지"를 알 방법이 없다.**

그러면 두 가지가 잘못된다:

- 있는 것을 **또 만든다**
- 정리할 때 **남의 자원을 지운다**(우리가 안 만든 것을 삭제 순서에 넣는다)

실측:

    기존 자원 없음            생성 [iamRole, network, subnet, k8sCluster]
                              삭제 [[k8s,network],[k8s,subnet],[subnet,network]]
    network·subnet 이미 있음  생성 [iamRole, k8sCluster]
                              삭제 []
                              재사용 [network, subnet]

**빠진 이유를 말한다**: 계획이 *"you already have them — they are still required;
we simply do not make them"*이라고 적는다. 순서에서 빠진 것이 *"필요 없다"*가
아니라 *"이미 있다"*임을 구별하려는 것이다.

## 4. 지금 계약 — 13칸

| 계층 | 칸 |
|---|---|
| 필수 4 | `provider` · `region` · `workloads` · `monthlyBudgetUSD` |
| 권고 4 | `minVCpu` · `minMemoryGiB` · `trafficPattern` · `multiZone` |
| 맥락 5 | **`existingResources`** · `expectedConcurrentUsers` · `approxRequestsPerSecond` · `dataResidency` · `lowCarbonPreferred` |
| 안 받음 3 | `schemaVersion` · `meta` · `regionAsWritten`(배관) |
| 인계 3 | 레지스트리 · 인그레스 컨트롤러 · TLS |
| 파생 | 결정 6건(앵커 확정 뒤) |

`workloads`가 **요구사항 문장에서 오지 않는다**는 점을 분명히 적어 둔다. 계약의
입력은 `resource_constraints_text`(사용자가 요구사항과 **따로** 쓰는 클라우드
제약 산문)이고, 코퍼스 실측이 provider·region·예산은 요구사항 산문에 0건이라고
말한다. 과제 원문도 *"사용자가 클라우드 리소스를 선택"*을 전제한다.

## 5. 타당성 위협

- **T-사후 정당화**: 도출을 하면서 현행 칸이 머릿속에 있었다. 10/11 일치가
  독립적 수렴인지 기억의 재생인지 이 절차로는 못 가른다. 완화가 안 된 위협이고,
  그렇게 적는다. 다만 **하나가 안 맞았다**는 사실이 완전한 재생은 아님을
  보여 준다.
- **T-출처 넷의 임의성**: 출처를 넷으로 가른 것은 우리 구성이다. 다섯째(예:
  조직 정책)를 두면 목록이 달라질 수 있다.
- **T-단일 판정자**: 값마다 "누가 아는가"를 나 혼자 판정했다. 관심사 축이
  겪은 것과 같은 위협이고, 거기서는 코퍼스 좌표로 완화했는데 여기는 그런
  외부 기준이 없다.
