## 1. 기준 체계 — 3등급

### 0. 공정성 필터 (사용자 지적, 2026-08-02) — 모든 채점 기준이 통과해야 한다

*"베이스라인들도 할 수는 있는 것을 기준으로 해야 공정하다."* 맞다. 채점하는
모든 기준은 **두 조건**을 만족해야 한다:

- **(가) 세 계열이 다 시도할 수 있다** — "우리 산출물 X가 있는가"를 묻지
  않는다. 우리를 위해 만든 산출물의 유무를 채점하면 "그 기능을 넣었나"를 재는
  것이지 "출력이 더 나은가"가 아니다.
- **(나) 판정은 결과에 대한 중립 잣대다** — 우리 어휘·우리 게이트가 아니라,
  실제로 도는가·통과하는가·요구를 구현했는가 같은 외부 관측.

이 필터가 실제로 **기준 하나를 걸러냈다**(C-CONF의 첫 판 — 아래). 걸러낸 것은
버리지 않고 **공정한 판본으로 다시 쓰거나, 채점이 아닌 "능력 차이 기술"로
분리**한다. 능력 차이(우리는 설계·적합성 보증을 구성상 낸다)는 사실이고 적을
가치가 있지만, **점수판에 올리지 않는다** — 정성 기술로만 남긴다.

### 1급: 중립 심판 · 높은 변별 · 직관적 (주 결과)

**C1 함정 결말** — 씨앗에 심은 실측 함정마다 세 계열의 결말을 관측한다.
**공정성: 통과.** "이 앱을 EKS에 배포하라"는 셋 다 시도하는 과제이고, SC 지정·
reclaim 정책·IRSA 배선은 우리 KB 없이도 누구나 할 수 있다(비밀 지식이 아니다 —
베이스라인이 피하면 잘 채점된다). 잣대는 "시간이 지나도 실제로 도는가"로 중립.
우리는 "침묵 함정은 안정적으로 못 피한다"를 **예측**할 뿐 채점을 조작하지 않는다.
심판은 컨트롤 플레인과 **시간**이다(지연 실패가 핵심 — apply는 초록인데
나중에 죽는 것):

| 함정 | 실측 근거 | 무단 결정 시 예상 결말 | 심판 |
|---|---|---|---|
| EKS 기본 SC 부재 | aws k8sPvc→disk (지연 실패) | PVC 무기한 Pending, 오류 없음 | 클러스터 상태 |
| 공유 볼륨 RWX (API가 쓴 사진을 워커가 읽음) | aws RWX 전제 부재 | RWX Pending 또는 RWO 공유로 둘째 파드 스케줄 실패 | 클러스터 |
| reclaim Delete vs 5년 보존(NFR 9) | 3사 동반 소멸 실측 | 재배포/PVC 삭제 시 데이터 소실 | 삭제 실험 |
| Ingress 컨트롤러 부재 | aws 무합성 실측 | 리소스는 생기고 주소는 영영 안 옴 | ADDRESS 칸 |
| 야간 백업 권한(문장 8) | iamRole 기능 축·IRSA 사슬 | 스냅샷 호출 AccessDenied — **밤에야 드러남** | Job 로그 |
| 주소 안정성(모바일) | publicIp 회복 3사 3색 | 재배포 시 주소 변경 → 앱 단절 | 재배포 실험 |

가장 직관적인 산출물은 **침묵 실패 연대기**다: t=0 셋 다 apply 초록 → t+10분
베이스라인 PVC Pending → t+1일 백업 실패 로그 → 재배포 후 데이터 소실.
행마다 claims 좌표가 붙는다.

**C2 NFR 수용 검증** — 비기능 충족도를 산문 평가가 아니라 **중립 수용 스위트**
로: NFR 9(보존) = 재배포 후 데이터 생존 · NFR 13(격리) = 워커를 죽여도 제출이
되는가 · NFR 12(3초) = 응답 프로브. **심판의 중립성이 핵심이다** — 각 시스템이
낸 자기 테스트로 자기를 채점하면 자기심판이다(§3-T). 그래서 스위트는 **내가
씨앗의 NFR에서 직접 작성**하고(어느 시스템의 출력도 보기 전에), 세 계열의
배포된 서비스에 대해 **블랙박스(HTTP)로** 똑같이 돈다. 엔드포인트는 각 시스템이
낸 API 문서(우리는 OpenAPI 네이티브)에서 발견한다 — **문서가 없어 못 구동하면
그 자체가 결과**(추적성 부재).

**C-BUILD 빌드·테스트가 실제로 서는가** — 각 계열의 생성 코드가 (a) 빌드/컴파일
되는가 (b) 테스트를 **내는가** (c) 그 테스트가 통과하는가. 우리 사슬은 셋 다
게이트다(Gradle `compileJava test`, 설계 기반 E2E). pass/fail은 언어 무관·중립.
자기심판 우려는 있으나(자기 테스트) **테스트를 아예 안 내는 것**과 **내는데
통과 못 하는 것**의 구별이 이미 정보다 — 보강으로 테스트-코드 비율·테스트가
요구를 실제로 건드리는지(C2와 교차)를 함께 본다.

**C3 비용 진술** — 예산 400 USD 대비: 비용을 말하는가, 근거(단가 출처)가
있는가, 공개 가격표 대비 오차. 심판은 AWS 가격표(공개·중립).

**C-COVER 요구→코드 구현 충실도 (C-CONF의 공정한 대체)** — 첫 판 C-CONF는
"우리 적합성 게이트가 있는가"를 물어 **공정성 필터 (가)에 걸렸다**(우리를 위해
만든 게이트의 유무를 채점). 공정한 판본으로 다시 쓴다 — 셋 다 시도하고 결과로
판정하는 잣대:

- **요구 커버리지**: 씨앗의 기능 요구 8개 각각을 코드가 실제로 구현하는가.
  중립 수용 스위트(C2)가 행동으로 확인하고, 정적으로도 요구↔코드 대응을 읽는다.
  누락(요구를 안 만듦)과 과잉(안 시킨 걸 지어냄) 둘 다 센다. **셋 다 코드를
  내므로 셋 다 채점 가능**하다.
- **설계↔코드 일관성**: 각 시스템이 **자기가 낸 설계**(우리 BCE·시퀀스 / MetaGPT
  system design·API design / 단순 LLM은 냈다면 그것)와 자기 코드가 맞는가.
  형식이 제각각이라 완전 자동은 어렵고, 판정 절차(무엇을 대조했는지)를 기록해
  반중립으로 표시한다. **우리 형식을 강요하지 않는다.**

**(정성 기술 — 채점 아님) 능력 차이: 설계·적합성 보증**. 우리 사슬은 기계
검증된 설계 계약과 소스-설계 적합성 게이트를 **구성상** 낸다(BCE 해시·시퀀스
호출 대조, `reports/source-design-conformance.json`). 베이스라인은 설계 산출물
자체를 안 낼 수도 있다. 이건 사실이고 사용자 직관("다이어그램→구조화")의 뿌리이지만,
**점수로 세지 않는다** — 세면 "우리 기능을 넣었나"를 재는 것이라 공정성 필터
(가) 위반이다. 대신 "세 계열이 각각 어느 단계 산출물을 냈는가"를 표로 기술하고,
그 산출물의 **품질**만 위 C-COVER·C6로 공정하게 잰다.

**C4 침묵 결정의 처리** — 관측점마다 {질문·인계로 드러냄 / 무단 결정(맞음) /
무단 결정(틀림 — C1이 판명) / 무시}. **공정성: 통과** — 결과를 재지 절차를
재지 않는다. 베이스라인도 되물을 수 있고 가정을 밝힐 수 있다("assuming X…");
안 하고 지어내면 그것이 결과다. "우리 관심사 체크리스트를 썼나"가 아니라
"그 침묵 지점을 어떻게 다뤘나"를 각자에게 묻는다. 관측점 목록이 우리 구성이라
반중립 표시, "틀림"은 컨트롤 플레인이 판정.

**C5 상호작용 부담** — 우리가 묻는 질문 수. **우리에게 불리한 축을 일부러
센다** — "전부 물어보면 당연히 낫지"라는 반론을 선제한다(계약이 필수 4로
제한하는 것이 답의 일부).

### 3급: 보조 (정직한 한계 표시)

**C6 코드 구조 지표(순환복잡도·결합도)** — 코드 생성 단계가 있으니 이제
직접 측정 가능하다(radon 등). 그러나 **언어 교란**이 있다: 우리는 Java/Spring
고정(BCE+OpenAPI Generator), MetaGPT는 대개 Python이라 절대 CC 수치의 비교는
사과-오렌지다. 그래서 이 축은 **수치 경쟁으로 쓰지 않고** 두 가지만 본다 —
(a) 함수당 CC의 **극단값**(200줄 god-function은 어느 언어든 나쁨) (b) 계층
일관성(BCE 4계층 vs 단일 모놀리식). 구조의 가치는 **C-COVER가 더 공정하게**
보이므로 CC는 보강 증거다. 언어 교란은 완화 불가 — 그렇게 적는다.

## 2. 정직한 예상 — 어디서 비기고 어디서 갈리나 (실행 전 기록)

- **비길 것**: Service→LB(3사 합성이 다 해줌) · 기본 매니페스트 · NFR 12
  (소부하에서 셋 다 3초 통과 예상).
- **변별 안 될 것 하나를 미리 적는다**: 부하 모양 — 이 앱은 spiky라 버스트

- **갈릴 것**: C1의 여섯 함정 — 전부 "생성은 통과하고 나중에 죽는" 부류라

## 3. P2가 바뀌었다 — 앱을 손으로 쓰지 않는다

첫 판 P2는 "앱을 최소 코드로 구현 + NFR 스위트 동봉"이었다. **코드 생성이
사슬에 있으므로 앱은 세 계열이 각자 씨앗에서 생성한다** — 손으로 쓸 참조 앱은
없다. 그래서 내가(내 영역에서) 작성하는 것은 앱이 아니라 **중립 심판 도구**다:

1. **중립 수용 스위트 (C2)** — 씨앗의 NFR에서 직접 작성한 블랙박스 HTTP 검증.
   어느 시스템의 배포된 서비스에도 똑같이 돈다. **어느 출력도 보기 전에**
   작성하고, 실행 후 고치면 사후 조정이므로 그 사실을 기록한다. 위치: 내
   영역(`app/core/cloudkb/`) — `app/implementation/`은 팀원 코드라 안 건드린다.
2. **베이스라인 하네스 + 채점기** — 세 계열의 산출물을 같은 절차로 배포·측정·
   채점한다. 계열별 프롬프트 포장은 실행 기록에 남긴다.
3. **T-수용 스위트 자기검증(선택)** — 스위트가 성립 가능한지 확인하려고 버리는
   참조 구현을 하나 둘 수 있다. **이것은 비교 대상이 아니다**(스위트의 테스트일
   뿐) — 쓰면 그렇게 명시한다.

**T-자기심판(C-BUILD·C2)**: 각 시스템의 자기 테스트로 자기를 채점하면 자기심판이다.
완화 — C2는 내가 쓴 중립 스위트가 판정하고, C-BUILD는 "테스트를 내는가/통과하는가"의
사실만 취하되 자기 테스트의 품질 주장은 안 한다(테스트-코드 비율·요구 커버리지로
보강).

함정은 여전히 **앱의 실제 필요에서** 나온다(요구 문장엔 함정 이야기 없음):
사진 공유 볼륨 · 클러스터 내 DB(보존이 걸리는 데이터) · 야간 스냅샷 백업 ·
모바일 고정 진입점. 어느 시스템이 생성하든 이 필요가 그 CSP의 실제 행동과
만나는 지점에서 함정이 선다.

## 4. 씨앗 정정 하나 — 범위 충돌 (실행 전 발견, 고침)

사진 저장의 관용적 답은 S3, DB는 RDS인데 **둘 다 우리 범위 밖**(관리형 상품
서비스 제외)이다. 이대로면 베이스라인이 S3를 써서 함정 지대를 자연스럽게
피하고 더 관용적인 설계를 내는, 우리에게 일방적으로 불리하면서 **비교 자체가
안 되는**(서로 다른 흙 위) 실험이 된다.

정정: 제약 산문에 **"모든 것을 클러스터 안에서 돌린다(관리형 데이터 서비스
불사용)"**를 추가한다 — 이식성·벤더 종속 회피를 이유로 실제 조직이 흔히 거는
제약이고, 세 계열에 **같은 규칙**으로 걸린다. 실행 전 정정이므로 사후 조정이
아니며, 이 문서와 커밋이 그 기록이다.

## 5. 위협 (계획 문서 5종에 추가)

- **T-함정 설계 편향**: 함정은 우리가 잰 지대에 심겼다. 방어: 함정은 발명이
  아니라 그 CSP의 실제 행동이고(전부 claims 좌표), 요구 문장은 평범한 필요만
  말한다. 그래도 주장은 "실측이 존재하는 지대에서 낫다"로 한정한다.
- **T-측정 어휘 선택**: 앱이 우리 측정 어휘 안에 산다 — 어휘 밖(S3·RDS·
  서버리스)에서는 이 실험이 아무 주장도 못 한다. §4의 제약은 이 한계를
  가리는 것이 아니라 명시하는 것이다.
- **T-생성 흔들림**: 계열마다 생성 3회(정적 채점으로 안정성 확인), 배포는
  계열당 1회(비용) — 배포 표본이 1이라는 한계를 적는다.
- **T-언어 교란(C6)**: 우리는 Java/Spring 고정, 베이스라인은 언어 자유. 절대
  CC 수치 비교 불가 — §1-C6대로 극단값·계층 일관성만 보고, 구조 주장은
  C-CONF(언어 무관)로 옮긴다. 완화 불가, 명시.
- **T-우리 스택 강제**: 우리 코드 생성이 Java/Spring·BCE로 고정된 것은 우리
  설계 선택이다. 배포·함정·NFR·비용은 언어 무관이라 영향 없고, 코드 지표만
  이 선택에 묶인다 — 그래서 코드 지표를 주 결과로 쓰지 않는다.
- **T-구현 에이전트 실행 부담**: 우리 사슬 완주는 OpenHands·NVIDIA NIM·JDK 21·
  Gradle을 요구한다(무겁다). 세 계열을 실제로 배포까지 돌리는 것과, 산출물만
  받아 정적 채점하는 것을 나눠 — 정적 채점(C-BUILD 일부·C-CONF·C4·C5·C6)이
  먼저 값을 내고, 실배포 심판(C1·C2)은 예산·환경이 서면 얹는다.
