# 비교실험 기준 설계 — 무엇으로 "더 낫다"를 보이나 (2026-08-02, 실행 전)

> `comparison-experiment-plan-2026-08-02.md`의 보강. 사용자 요구: *"기존 대비
> 어떤 기준에서 더 나은지 객관/직관적으로 보여줄 수 있어야 한다(예: 순환복잡도,
> 비기능 충족도)."* 기준마다 심판의 중립성·변별력·직관성을 따져 등급을 매기고,
> 씨앗의 공정성 결함 하나를 고친다.

## 1. 기준 체계 — 3등급

### 1급: 중립 심판 · 높은 변별 · 직관적 (주 결과)

**C1 함정 결말** — 씨앗에 심은 실측 함정마다 세 계열의 결말을 관측한다.
심판은 컨트롤 플레인과 **시간**이다(지연 실패가 핵심 — apply는 초록인데
나중에 죽는 것):

| 함정 | 실측 근거 | 무단 결정 시 예상 결말 | 심판 |
|---|---|---|---|
| EKS 기본 SC 부재 | aws k8sPvc→disk (지연 실패) | PVC 무기한 Pending, 오류 없음 | 클러스터 상태 |
| 공유 볼륨 RWX (API가 쓴 사진을 워커가 읽음) | aws RWX 전제 부재 | RWX Pending 또는 RWO 공유로 둘째 파드 스케줄 실패 | 클러스터 |
| reclaim Delete vs 5년 보존(NFR 9) | 3사 동반 소멸 실측 | 재배포/PVC 삭제 시 데이터 소실 | 삭제 실험 |
| Ingress 컨트롤러 부재 | aws 무합성 실측 | 리소스는 생기고 주소는 영영 안 옴 | ADDRESS 칸 |
| 야간 백업 권한(문장 8) | iamRole 기능 축·IRSA 사슬 | 스냅샷 호출 AccessDenied — **밤에야 드러남** | Job 로그 |
| 주소 안정성(모바일) | publicIp 회복 3사 3색 | 재배포 시 주소 변경 → 앱 단절 | 재배포 실험 |

가장 직관적인 산출물은 **침묵 실패 연대기**다: t=0 셋 다 apply 초록 → t+10분
베이스라인 PVC Pending → t+1일 백업 실패 로그 → 재배포 후 데이터 소실.
행마다 claims 좌표가 붙는다.

**C2 NFR 런타임 검증** — 비기능 충족도를 산문 평가가 아니라 **기계 판정
테스트**로: NFR 9(보존) = 재배포 후 데이터 생존 검사 · NFR 13(격리) = 워커를
죽여도 제출이 되는가 · NFR 12(3초) = 응답 프로브. 심판은 실행되는 시스템.
**앱은 이 검증 스위트와 함께 설계된다**(§3) — 어느 계열의 배포에든 같은
스위트를 돌린다.

**C3 비용 진술** — 예산 400 USD 대비: 비용을 말하는가, 근거(단가 출처)가
있는가, 공개 가격표 대비 오차. 심판은 AWS 가격표(공개·중립).

### 2급: 반중립 (목록은 우리 것, 판정은 기계 — 표시하고 센다)

**C4 침묵 결정의 처리** — 관측점마다 {질문·인계로 드러냄 / 무단 결정(맞음) /
무단 결정(틀림 — C1이 판명) / 무시}. 관측점 목록이 우리 구성이라 반중립이나,
"틀림"은 컨트롤 플레인이 판정한다.

**C5 상호작용 부담** — 우리가 묻는 질문 수. **우리에게 불리한 축을 일부러
센다** — "전부 물어보면 당연히 낫지"라는 반론을 선제한다(계약이 필수 4로
제한하는 것이 답의 일부).

### 3급: 보조 (정직한 한계 표시)

**C6 코드 구조 지표(순환복잡도·결합도)** — 측정 도구는 객관(radon 등)이나
이 실험에서 성립 조건이 까다롭다: **우리 사슬에는 앱 코드 생성 단계가 없다**
(구현 에이전트는 배포 의도를 내지 앱 코드를 내지 않는다). 성립하는 형태는
하나뿐 — **처치 실험**: 같은 코드 생성기에 우리 설계 산출물(클래스·시퀀스·
API 명세)을 준 경우 vs 안 준 경우의 코드를 비교한다("다이어그램이 코드
구조화를 돕는가"의 검증). 다만 소형 생성 앱에서 CC 변별력은 낮을 것으로
예상하고, 구조의 가치는 C2의 행동 검증(격리 테스트)이 더 강하게 보인다.
2차 실험으로 미룬다.

## 2. 정직한 예상 — 어디서 비기고 어디서 갈리나 (실행 전 기록)

- **비길 것**: Service→LB(3사 합성이 다 해줌) · 기본 매니페스트 · NFR 12
  (소부하에서 셋 다 3초 통과 예상).
- **변별 안 될 것 하나를 미리 적는다**: 부하 모양 — 이 앱은 spiky라 버스트
  인스턴스가 **적합**하다(우리 verify도 무충돌 판정). 버스트 함정은 이 앱에서
  베이스라인을 못 가른다. 명시 지점 대조군(판정문 존재 여부)으로만 쓴다.
- **갈릴 것**: C1의 여섯 함정 — 전부 "생성은 통과하고 나중에 죽는" 부류라
  단발 LLM·프레임워크가 사전에 다루기 어렵고, 우리는 실측이 직접 가리킨다.

## 3. 앱 설계 귀결 (P2 요건)

1. **NFR 검증 스위트 동봉** — 보존·격리·응답 프로브가 앱과 같이 산다. 어느
   배포에든 그대로 돈다(중립 심판의 실행체).
2. **배포 불가지 코드** — 설정은 환경변수로만: 세 계열의 배포 산출물이 같은
   컨테이너 이미지를 올릴 수 있어야 한다(1형 비교의 전제).
3. **함정이 앱의 실제 필요에서 나온다** — 사진 볼륨(공유 읽기) · 클러스터 내
   PostgreSQL(보존이 걸리는 데이터) · 야간 스냅샷 백업 · 모바일 고정 진입점.
   요구 문장에는 함정 이야기가 없다 — 평범한 필요가 그 CSP의 실제 행동과
   만나는 지점이 함정이다.

## 4. 씨앗 정정 하나 — 범위 충돌 (실행 전 발견, 고침)

사진 저장의 관용적 답은 S3, DB는 RDS인데 **둘 다 우리 범위 밖**(관리형 상품
서비스 제외)이다. 이대로면 베이스라인이 S3를 써서 함정 지대를 자연스럽게
피하고 더 관용적인 설계를 내는, 우리에게 일방적으로 불리하면서 **비교 자체가
안 되는**(서로 다른 흙 위) 실험이 된다.

정정: 제약 산문에 **"모든 것을 클러스터 안에서 돌린다(관리형 데이터 서비스
불사용)"**를 추가한다 — 이식성·벤더 종속 회피를 이유로 실제 조직이 흔히 거는
제약이고, 세 계열에 **같은 규칙**으로 걸린다. 실행 전 정정이므로 사후 조정이
아니며, 이 문서와 커밋이 그 기록이다.

## 5. 위협 (계획 문서 5종에 추가)

- **T-함정 설계 편향**: 함정은 우리가 잰 지대에 심겼다. 방어: 함정은 발명이
  아니라 그 CSP의 실제 행동이고(전부 claims 좌표), 요구 문장은 평범한 필요만
  말한다. 그래도 주장은 "실측이 존재하는 지대에서 낫다"로 한정한다.
- **T-측정 어휘 선택**: 앱이 우리 측정 어휘 안에 산다 — 어휘 밖(S3·RDS·
  서버리스)에서는 이 실험이 아무 주장도 못 한다. §4의 제약은 이 한계를
  가리는 것이 아니라 명시하는 것이다.
- **T-생성 흔들림**: 계열마다 생성 3회(정적 채점으로 안정성 확인), 배포는
  계열당 1회(비용) — 배포 표본이 1이라는 한계를 적는다.
