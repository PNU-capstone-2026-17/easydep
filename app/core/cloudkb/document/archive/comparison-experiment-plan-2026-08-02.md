# 비교실험 계획 — 시스템 산출 vs 베이스라인 (2026-08-02, 실행 전)

> 사용자 결정 셋: ① 계약은 신규 앱 개발 전제(existingResources 제거) ② 비교
> 대상은 **단순 LLM 및 MetaGPT류 프레임워크** ③ 비교 대상은 배포 구성만이
> 아니라 **전체 산출물**이다 — 우리 사슬은 요구사항 분석부터 설계·소스코드·
> 테스트·배포까지 낸다. 이 문서는 실행 전 계획이다(완료는 커밋이 기록).
> 기준·심판 상세는 자매 문서 `comparison-criteria-2026-08-02.md`.

## 1. 무엇을 비교하나 — 하나의 씨앗, 전 사슬 산출물

같은 입력(예시 CNA의 요구사항 산문 + 클라우드 제약 산문)을 세 계열에 주고,
**요구사항 분석 → 설계 → 소스코드·테스트 → 배포**의 **각 단계 산출물**을
비교한다. "누가 더 나은 k8s YAML을 쓰나"가 아니라 **"요구사항 씨앗 하나에서
누가 더 나은 CNA 개발 산출물 전체를 내나"**가 질문이다.

| 계열 | 사슬 |
|---|---|
| A 본 시스템 | 요구사항 에이전트(관심사·계약) → 설계(BCE 클래스·시퀀스·ERD·OpenAPI) → 구현(OpenHands Java/Spring + 테스트 + 소스-설계 적합성 게이트) → 배포(매니페스트 + 실측 사영·점검표) |
| B 단순 LLM | 같은 급 모델, 단발/소수 프롬프트로 같은 산출물 요청 |
| C 프레임워크 | MetaGPT 등 공개 멀티에이전트의 기본 파이프라인(PM→아키텍트→엔지니어) |

## 2. 단계별 산출물과 그것을 재는 기준

각 단계에서 무엇이 나오고 어느 기준이 거기 걸리는지. 기준 부호는 자매 문서.

| 단계 | 우리 산출물 | 우리 고유(차별점) | 심판·기준 |
|---|---|---|---|
| **요구사항** | classified·use case·**cloud_concerns(8)**·resource_spec(계약) | **침묵한 결정을 질문·인계로 드러냄** / 계약이 사용자만 아는 값만 받음 | C4(침묵 처리) · C5(질문 수, 불리하게 셈) · C3(비용 진술) |
| **설계** | BCE 클래스·시퀀스·ERD·OpenAPI | **기계 검증 가능한 설계 계약**(해시·호출 순서) | C-CONF의 상류 절반 |
| **구현** | Java/Spring 소스 + 단위·E2E 테스트 | **소스-설계 적합성 게이트**(시퀀스 호출이 소스에 존재) · 컴파일·테스트 게이트 | **C-BUILD**(빌드·테스트 서는가) · **C-CONF**(설계→코드 추적성) · C6(구조, 언어 교란 표시) |
| **배포** | 매니페스트 + 실측 사영(순서·대기·doNotCreate·경고) + 배포 후 점검표 | **depkb 실측 지식**(침묵 실패 지대) | **C1**(함정 결말·침묵 실패 연대기) · C2(NFR 수용) |
| **전 구간** | — | — | C2(재배포 생존·격리 등 행동 검증) |

**핵심 변별은 두 곳**이다: 상류의 **C-CONF**(설계→코드 추적성 — 사용자 직관
"다이어그램→구조화"의 강한 판본, 언어 무관)와 하류의 **C1**(배포 함정의 침묵
실패 — apply는 초록인데 나중에 죽는 지대, 우리 실측이 직접 가리킴). 나머지는
비기거나 부분 변별이며, 그 예측을 실행 전에 적어 둔다(criteria §2).

## 3. 심판 — 자기 KB로 채점하지 않는다 (T-자기 심판)

우리 depkb 검사기·우리 테스트로 B·C를 채점하면 자기 기준 채점이다. 심판은
중립층에 둔다:

1. **컨트롤 플레인** — 산출 매니페스트를 실제로 apply: 거부 수·거부 지점.
   그리고 **시간** — 침묵 실패(지연 결함)는 apply 직후가 아니라 나중에 드러난다.
2. **빌드·테스트 실행** — 생성 코드가 빌드되는가, 테스트를 내는가, 통과하는가.
   pass/fail은 언어 무관·중립(도구는 각 계열의 스택에 맞춰).
3. **중립 수용 스위트** — 씨앗의 NFR에서 내가 직접 작성한 블랙박스 HTTP 검증
   (어느 출력도 보기 전에). 각 시스템의 배포된 서비스에 똑같이 돈다.
4. **보조(비중립 명시)**: 설계→코드 추적성의 존부 · 침묵 결정 처리 · 질문 수 ·
   코드 구조 지표. 우리 가치 기준이라 **표시하고 따로 센다.**

## 4. 예시 CNA — 관심사 8건이 전부 걸리는 최소 구성

신규 개발 전제. 관심사 축의 결정들이 실제로 걸려야 비교가 의미를 갖는다.
씨앗은 `samples/field-report/`에 있다(현장 점검 보고 서비스):

- **외부 노출 API**(모바일 — 노출 경로·도달성·주소 안정성·부하 모양)
- **내부 처리 서비스**(썸네일·PDF — service-discovery)
- **영속 저장**(사진·보고서 — 저장 프로비저닝·데이터 운명·공유 볼륨 RWX)
- **야간 백업**(구현이 클라우드 API를 부를 자리 — 권한 축)

요구 문장엔 함정 이야기가 없다 — 평범한 필요가 그 CSP의 실제 행동과 만나는
지점이 함정이다. 관측점(무엇을 명시/침묵)은 `INPUT.md`에 실행 전 고정.

**경계(기존 결정 유지)**: 이 앱은 claims의 측정 기준이 아니다 — 의존 주장의
오라클은 컨트롤 플레인이고, 앱은 사슬 시연·비교의 재료다.

## 5. 단계 (P2가 바뀌었다 — 앱을 손으로 안 쓴다)

첫 판 P2는 "앱을 손으로 구현"이었다. 사슬이 소스코드를 생성·테스트하므로
(`app/implementation` — OpenHands, 팀원 코드·수정 금지) 앱은 세 계열이 각자
씨앗에서 생성한다. 내가 만드는 건 앱이 아니라 **중립 심판 도구**다(내 영역에만).

- **P1** 계획·기준 확정 + 예시 CNA 요구사항·제약 산문 작성 (**완료**)
- **P2** 중립 심판 도구 — 수용 스위트(씨앗 NFR에서, 출력 보기 전) + 계열별
  하네스·채점기(단계별 산출물을 같은 절차로 수집·측정). `app/core/cloudkb/`에만.
- **P3** 세 계열 산출 수집(전 단계 산출물) — A=우리 사슬 완주 · B=단순 LLM ·
  C=MetaGPT류. 같은 씨앗, 프롬프트 포장 기록.
- **P4-정적** 배포 전에 값을 내는 축: 요구사항(C4·C5) · 설계·코드(C-CONF·
  C-BUILD·C6) · 비용(C3). 실배포 없이 산출물만으로.
- **P4-동적** 실배포 심판: apply + C1 함정 결말 + C2 수용 스위트. 비용·환경
  확인 후 — 구현 에이전트 실행이 무거워(OpenHands·NIM·JDK·Gradle) 정적이 먼저.
- **P5** 기록·원고 반영

## 6. 위협 (실행 전에 적는다)

- **T-자기 심판**: §3으로 완화, 보조 축은 완화 불가 — 비중립 표시로만.
- **T-프롬프트 공정성**: B·C에게 각 단계 산출물을 얼마나 친절히 요청하느냐가
  결과를 좌우한다. 완화 — 동일 씨앗 전문 + 산출물 목록(요구사항 분석·설계·
  코드·테스트·배포)을 같게 요구하고, 프롬프트 원문을 기록. 강도별로 나눠 잰다.
- **T-단일 표본**: 앱 하나로는 일반화 불가 — "이 앱에서 이랬다"까지만.
- **T-언어/스택 교란**: 우리는 Java/Spring·BCE 고정. 배포·함정·NFR·추적성은
  언어 무관이나 코드 구조 지표(C6)는 교란 — 절대 수치 비교 안 함(criteria §5).
- **T-프레임워크 버전**: C는 버전·설정에 민감 — 핀 기록.
- **T-실행자 편향**: 세 계열 실행·채점을 우리가 한다. 프로토콜(입력·프롬프트·
  판정 기준)을 실행 전에 이 문서와 기준 문서로 고정하는 것이 완화.
- **T-구현 실행 부담**: 우리 사슬 완주는 무거운 환경을 요구한다. 정적 채점과
  실배포 심판을 나눠, 환경이 서기 전에도 정적 축이 값을 내게 한다.
