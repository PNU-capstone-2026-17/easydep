# 리소스 의존성 — 어떻게 알아냈고, 무엇이 나왔나

2026-07-30. 이 날 무엇을 보았는지의 기록이다(불변, 갱신하지 않는다).

읽는 순서: **1장 무엇을 알고 싶었나 → 2장 어떻게 알아냈나 → 3장 무엇이 나왔나 →
4장 얼마나 믿을 수 있나 → 5장 그래서 무엇이 문제인가.** 숫자와 목록은 6장 부록에 있다.

---

## 1. 알고 싶었던 것

사용자가 *"서버 하나에 이 앱을 올려 줘"*라고 말한다. 그런데 클라우드에서 서버 하나만
만들면 안 돈다. 네트워크가 있어야 하고, 그 안에 주소 대역이 있어야 하고, 방화벽
규칙이 있어야 하고, 접속 열쇠가 있어야 한다.

**그러면 정확히 무엇이 함께 만들어져야 하나?** 이게 알고 싶었던 것이다.

이게 왜 어려운가:

- **아무도 목록을 써 두지 않았다.** 클라우드 문서는 각 자원을 따로 설명하고, "이걸
  만들려면 저것들이 먼저 있어야 한다"를 한 장에 모아 놓지 않는다.
- **클라우드마다 다르다.** AWS에서 방화벽은 네트워크에 딸려 있는데 Azure에서는 아니다.
- **어떤 것은 자동으로 만들어진다.** 사용자가 몰라도 시스템이 대신 만든다. 그러면
  그건 "필요한 것"인가 "안 물어봐도 되는 것"인가.

---

## 2. 어떻게 알아냈나

두 갈래로 물었다. **한 갈래로는 답이 안 나오기 때문이다.**

### 2.1 첫째 갈래 — 우리가 실제로 부를 API를 읽는다

우리 시스템이 최종적으로 하는 일은 **cb-tumblebug이라는 도구에 배포 요청을 보내는
것**이다. 그러면 답은 단순하다: **tumblebug이 무엇을 요구하는지 읽으면 된다.**
tumblebug이 거절하는 요청은 우리 계획이 틀린 것이고, 받아 주는 요청은 맞는 것이다.

그래서 tumblebug과 그 하부 도구(cb-spider)의 소스 코드를 읽었다. **판본을 고정했다** —
특정 태그의 소스 뭉치를 내려받아 sha256 해시까지 기록했다. 나중에 같은 것을 다시
확인할 수 있어야 하기 때문이다.

**읽을 때 여덟 종류의 증거를 찾았다.** 각각이 다른 것을 말해 준다:

| 증거 | 이게 말해 주는 것 | 찾은 건수 |
|---|---|---:|
| 요청 양식의 필수 칸 | "이 칸을 비우면 요청을 거절한다" | 28 |
| 클라우드 공통 인터페이스 | "tumblebug 밖에서도 이 값이 필요하다" — 즉 tumblebug만의 요구가 아니다 | 28 |
| 주소 경로의 중첩 | `/vnet/{a}/subnet/{b}` 처럼 주소 자체가 소속을 말한다 | 7 |
| 삭제 보호 코드 | "쓰는 것이 남아 있으면 못 지운다"고 막는 코드 | 7 |
| 없으면 자동 생성 | 사용자가 안 줘도 대신 만들어 주는 코드 | 4 |
| 클라우드별 설정 데이터 | AWS는 2개, Azure는 1개처럼 값이 갈리는 자리 | 4 |
| 만들기 전 존재 확인 | 없으면 거부하는 코드 | 3 |
| 운영 스크립트의 순서 | 만드는 순서 (보강 용도로만) | 2 |

**규칙 둘을 세웠다.**

첫째, **한 종류만으로는 의존이라고 인정하지 않았다.** 여러 종류가 같은 것을 가리켜야
한다.

둘째, **순서는 근거가 아니다.** "A 다음에 B를 만든다"는 것이 "B가 A를 필요로 한다"를
뜻하지 않는다. 실제로 초안이 스크립트의 나열 순서에서 짝을 만들어 `이미지 → 네트워크`
같은 **거짓 의존 10개**를 냈고, 이 규칙으로 걷어냈다. 그래서 순서 증거가 83건 중
2건뿐이다.

**결과: 자원 21개, 의존 39개, 근거 83건.** 근거마다 어느 파일 몇 번째 줄인지 적었다.

### 2.2 둘째 갈래 — 남이 실제로 배포한 것과 대조한다

첫째 갈래만으로는 가릴 수 없는 게 하나 있다.

> tumblebug이 "이 칸은 필수"라고 한 것이, **클라우드가 그렇게 요구해서**인가
> **tumblebug이 그렇게 만들기로 정해서**인가?

이걸 가르려면 tumblebug 밖의 증거가 필요하다. 그래서 **다른 사람들이 실제로 클라우드에
배포한 코드**를 읽었다. 요즘은 인프라를 코드로 쓴다(Terraform, Bicep). 그 코드에는
"이 자원을 만들 때 저 자원을 참조한다"가 그대로 적혀 있다.

**어떤 것을 읽을지 고르는 과정:**

1. 공개된 클라우드 네이티브 참조 앱 후보를 **65건** 모았다(학계 벤치마크, 커뮤니티
   데모, AWS·Azure·Google 공식 샘플, 인프라 참조 구현).
2. 그중 **인프라까지 코드로 만드는 것**만 남겼다. 대부분은 "클러스터는 이미 있다"고
   가정하고 앱만 배포한다. 그러면 우리가 알고 싶은 게 안 적혀 있다.
3. 남은 것이 **6건**이었다.
4. 그런데 이 6건이 네트워크를 직접 만들지 않고 **공용 모듈을 불러 쓴다.** 그래서 그
   모듈 **23건**도 함께 읽었다.

**합쳐서 29개 소스, 자원 839개.** 여기도 커밋 번호를 다 고정했다.

셀 때는 **코드에 적힌 참조만** 셌다. 문서에 쓰인 설명이나 만드는 순서는 세지 않았다 —
첫째 갈래와 같은 규칙이다.

## 3. 무엇이 나왔나

### 3.1 한눈에

- 우리가 찾은 39개 의존 중 **외부에서 그대로 확인된 것은 6개**였다.
- 나머지 33개는 대부분 **"틀렸다"가 아니라 "다른 것을 재고 있었다"**였다.
- 그런데 **세 가지는 실제로 틀렸다.**
- 그리고 **우리가 아예 안 보고 있던 큰 영역**이 드러났다.

하나씩 본다.

### 3.2 왜 6개만 맞았나 — 세 가지 다른 질문을 한 그래프에 섞었다

의존이라는 말이 세 가지 다른 뜻으로 쓰인다. 비유로 말하면:

| | 비유 | 실제로는 |
|---|---|---|
| **① 신청서 층** | 전입신고서에 "이전 주소"를 반드시 써야 한다 | API 요청 양식의 필수 칸 |
| **② 실물 층** | 방은 건물 안에 있다 | 클라우드에서 자원이 실제로 무엇에 담기나 |
| **③ 살림 층** | 사람이 살려면 전기·수도·인터넷이 있어야 한다 | 서비스를 돌리려면 결국 무엇이 다 필요한가 |

**우리 39개는 거의 다 ① 신청서 층이었다.** 외부 인프라 코드에서 읽은 15개는 ② 실물
층이다. 서로 다른 것을 재고 있었으니 많이 안 겹치는 게 당연하다.

예를 들어 우리는 `서버 → 사양`을 의존이라고 적었다. ①에서는 맞다 — 신청서에 사양 ID를
써야 한다. 하지만 ②에서 사양은 자원이 아니라 **그냥 값**이다(`t3.medium` 같은 글자).
방을 빌릴 때 "평수"는 별도의 물건이 아닌 것과 같다.

**이건 우리 잘못이 맞다.** 신청서 칸과 실물 관계를 같은 목록에 섞어 놓았다.

### 3.3 실제로 틀린 것 셋

| 우리가 뭐라고 했나 | 실제로는 | 어떻게 알았나 |
|---|---|---|
| **서버는 접속 열쇠(SSH 키)를 반드시 요구한다** | tumblebug이 그렇게 정한 것이다. 클라우드의 요구가 아니다 | 외부 29개 소스 전체에서 **열쇠 자원이 0건**. 관리형 컨테이너 서비스는 SSH로 접속하지 않고, VM을 쓰는 참조 구현조차 열쇠를 별도 자원으로 만들지 않는다 |
| **사양·이미지는 자원이다** | 값이다 | 인프라 코드에서 `instance_type = "t3.medium"`처럼 값으로 쓴다. 그리고 **우리 계획 만드는 코드가 이미 그렇게 처리하고 있었다**(주석에 "이미지는 리소스가 아니라 값이다"라고 적혀 있다) |
| **방화벽은 네트워크에 딸린다** | Azure에서는 방향이 반대다 | 세 곳에서 독립적으로 확인했다 — tumblebug 소스 주석 · Azure 공식 참조 아키텍처 코드 · TOSCA 표준의 Azure 프로파일 |

세 번째는 우리 데이터가 이미 맞게 적어 두었던 것이다(`AWS는 그렇다 / Azure는 아니다 /
GCP는 그렇다`). 외부 확인으로 **근거가 세 겹**이 됐다.

### 3.4 안 보고 있던 것

외부 참조 구현이 만드는 자원 839개를 성격별로 갈라 보니, **우리가 이름을 가지고 있는
것은 13%뿐**이었다. 나머지는:

| 우리 밖에 있는 것 | 뭐냐 | 비중 |
|---|---|---:|
| 권한·계정 | "누가 무엇을 할 수 있나" — 역할, 권한, 서비스 계정 | 가장 많다 |
| 관측 | 로그·지표를 어디에 모으나 | 두 번째 |
| 통행 | 인터넷 게이트웨이, 경로표 | |
| 비밀 보관 | 암호·키를 어디에 두나 | |
| 정책·가드레일 | 조직 차원의 금지 규칙 | |

즉 **진짜 배포의 대부분은 "권한"과 "관측"이고, 우리는 그걸 아예 안 다루고 있다.**

이건 다른 조사와 맞아떨어진다. 우리 요구사항 단계가 뽑아내는 클라우드 관심사 29건 중
21건이 **"이 답을 적을 칸이 없다"**고 표시돼 있는데, 그중에 권한(`identity-access`)과
관측(`operational-signal`, `event-record`)이 들어 있다. 위에서 내려온 조사와 아래에서
올라온 조사가 같은 자리를 짚었다.

### 3.5 곁가지로 나온 사실 하나

논문에서 가장 많이 쓰이는 마이크로서비스 벤치마크 11개(DeathStarBench, TrainTicket,
TeaStore 등)를 조사했는데, **인프라를 만드는 코드가 하나도 없다.** 전부 "클러스터는
이미 있다"에서 시작한다.

우리 시스템의 배포 단계가 딱 그 지점에서 끊겨 있었는데, 그게 우리만의 문제가 아니라
**참조 코퍼스 전체의 성질**이라는 뜻이다.

## 4. 이 결과를 얼마나 믿을 수 있나

**믿을 만한 근거:**

- **인용을 다시 열어 봤다.** 표본 8개를 고정된 소스 뭉치에 대고 확인해서 7개가 원문
  그대로 맞았다. 하나는 줄 번호가 3줄 어긋났다(찾는 기호 자체는 맞았다).
- **소스 해시가 일치했다.** 기록된 sha256을 다시 계산해서 같았다.
- **한 결론은 세 곳에서 독립 확인됐다**(3.3의 Azure 방향).

**믿기 어려운 부분 — 정직하게:**

1. **판정한 사람이 나 하나다.** 여덟 종류 증거를 읽고 판단한 게 전부 한 사람(AI)이다.
   교차 검증이 없다.
2. **인용이 자동 검사되지 않는다.** 지금 테스트 12개는 "근거가 적혀 있나"만 보고
   "그 근거가 실제로 그 줄에 있나"는 안 본다. 위의 줄 번호 오차를 아무도 잡지 못한다.
3. **39개가 전부라는 증명이 없다.** 판정하지 못한 ID 필드 99개를 따로 세워 뒀는데, 그
   99개가 자원이 아니라는 확인이 재현 가능한 형태로 남아 있지 않다.
4. **외부 대조에서 놓친 게 있다.** 참조를 정규식으로 찾았기 때문에, 값이 문자열로
   조립돼 넘어가는 경우는 못 잡는다. 실제로 클러스터가 네트워크를 받는 자리가
   `"projects/${...}/global/networks/${var.network}"` 같은 문자열이어서 안 잡혔다. 즉
   **"안 보였다"와 "없다"는 다르다.**
5. **인프라 코드에는 "필수"라는 정보가 없다.** Terraform은 "이 자원이 저 자원을
   반드시 요구한다"를 적지 않는다. 어떤 배포에서 실제로 참조했다는 사실만 있다. 그래서
   **필수/선택 판정은 여전히 tumblebug 소스만이 근거다.**
6. **분류는 우리가 얹은 것이다.** 3.4의 "권한·관측·통행" 같은 갈래도, 외부 자원 이름을
   우리 이름에 짝지은 것도 우리 판단이고 틀릴 수 있다.

## 5. 그래서 지금 무엇이 문제인가

**지식이 부족한 게 아니다. 이미 아는 것을 안 쓰고 있는 게 문제다.**

배포 계획을 실제로 만들어 보고 확인한 것:

- 계획은 **끝까지 나온다.** 그리고 자기가 무엇을 모르는지 정확히 표시한다(사양 미정,
  대수 미정, 배치 미정).
- 그런데 **쿠버네티스로 배포하는 앱은 네트워크가 하나도 없는 계획을 받는다.**
  네트워크도 주소 대역도 방화벽도 없다.
- **우리 지식베이스는 그게 필요하다는 걸 이미 알고 있다.** AWS라면 주소 대역이 서로
  다른 구역에 2개 있어야 한다는 것까지 안다.

왜 이런가: 같은 질문("무엇이 함께 필요한가")에 **답이 두 군데** 있다. 하나는 계획
만드는 코드가 읽고, 다른 하나는 아무도 읽지 않는다. 그리고 읽히는 쪽이 네트워크를
모른다.

| | 계획이 읽는 쪽 | 아무도 안 읽는 쪽 |
|---|---|---|
| VM에 딸리는 것 | 방화벽·열쇠·주소대역·네트워크·이미지 | 같음 + **무엇이 자동 생성인지 구별** |
| 쿠버네티스에 딸리는 것 | 클러스터·노드그룹 — **네트워크 없음** | 방화벽·**주소대역 2개**·네트워크 |

**할 일은 배선이다.** 계획 만드는 코드가 두 곳을 다 읽고, 어긋나면 "모른다"고 표시하게
하는 것. 그러면 위 결함이 없어진다.

그리고 남은 질문들(사양을 값으로 내릴지, 대수를 어디서 받을지)은 **계획이 서는지 안
서는지로** 답이 나온다. 더 조사해서 답할 문제가 아니다.
