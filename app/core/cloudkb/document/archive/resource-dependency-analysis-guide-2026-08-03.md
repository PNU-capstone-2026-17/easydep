# 클라우드 리소스 의존성 분석, 처음부터 이해하기

> **불변 안내 스냅샷 (2026-08-03).** 현재 범위·코드·수치는 바뀔 수 있다. 현재
> 진실은 [`docs/cloud-native-extension.md`](../../../../../docs/cloud-native-extension.md)와 코드·테스트다.
> 이 글은 `depkb`가 왜 존재하며 무엇을 실제로 분석하는지, 비전공자도 검토할 수
> 있도록 설명한다. 새 분석의 근거는 이 문서가 아니라 원천·코드·실험 기록이어야 한다.

## 1. 먼저 답: 객관적 기준은 하나가 아니다

**"클라우드 리소스 의존성"을 판정해 주는 전 세계 단일 표준이나 단일 그래프는 없다.**
클라우드마다 API와 자동 생성 방식이 다르고, 같은 자원도 어떤 생성 경로를 택하느냐에
따라 필요한 것이 달라진다. 대신 다음 네 종류의 기준을 교차해 객관성을 확보할 수 있다.

| 기준 | 답하는 질문 | 강점 | 한계 |
|---|---|---|---|
| CSP 제어면(API) | 실제로 만들거나 지울 수 있는가? | 실제 서비스의 최종 답 | 계정·비용·실험 설계가 필요하다 |
| CSP 스키마·문서 | 어떤 필드가 참조·필수 후보인가? | 넓게 후보를 찾고 재현하기 좋다 | `required` 필드만으로 자원 간 필연을 확정할 수 없다 |
| 모델 표준(TOSCA) | 관계를 어떤 어휘로 표현할 것인가? | 관계·요구사항·수명주기를 공통 모델로 설명한다 | 개별 CSP API의 실제 동작을 보장하지 않는다 |
| IaC·Kubernetes 실행 규칙 | 생성 순서·소유·삭제가 어떻게 작동하는가? | 구현 산출물이 소비할 수 있다 | 도구가 아는 의존만 본다; 런타임 기능까지 자동으로 알지 못한다 |

TOSCA는 애플리케이션 구성요소와 그 관계를 서비스 토폴로지로 표현하고, 생성·변경의
수명주기 절차까지 모델링하기 위한 표준이다. 즉 **좋은 개념 언어**다. 하지만 AWS,
Azure, GCP의 특정 API가 지금 무엇을 거부·자동 생성하는지는 각 CSP 제어면으로 확인해야
한다. [OASIS TOSCA 2.0](https://docs.oasis-open.org/tosca/TOSCA/v2.0/TOSCA-v2.0.html)

Terraform도 리소스 간 의존성을 선언할 수 있지만, 그것은 Terraform이 계획 순서를
계산하기 위한 표현이다. 실제 클라우드의 모든 기능·운영 의존을 의미하지는 않는다.
[Terraform language overview](https://developer.hashicorp.com/terraform/language)

따라서 이 프로젝트에서 말할 수 있는 가장 정직한 기준은 다음과 같다.

> **한 의존성 주장은 CSP, 생성 경로, 시점, 조건을 명시하고, CSP 스키마로 후보를
> 찾은 뒤 가능한 경우 실제 제어면의 반사실 실험으로 확인하며, 근거와 미확인 상태를
> 함께 남겨야 한다.**

여기서 *반사실 실험*은 "B를 일부러 빼거나 잘못 가리킨 상태에서 A를 만들면 어떻게
되는가"를 보는 실험이다. 예를 들어 VM 생성에 subnet이 필요하다고 주장하려면,
subnet을 생략하거나 존재하지 않는 subnet을 가리켜 실제 API가 거부하는지 확인한다.

## 2. 의존성은 화살표 하나가 아니다

`A → B`를 단순히 "A와 B는 관계가 있다"로 읽으면 거의 쓸모가 없다. 다음 질문을
갈라야 한다.

| 질문 | 쉬운 말 | 예 | 결과를 어디에 쓰나 |
|---|---|---|---|
| **존재 의존** | A를 만들 때 B가 먼저 있어야 하나? | VM을 만들려면 NIC가 필요한가? | 생성 순서·필수 자원·사용자 질문 |
| **선택/조건 의존** | B들 중 하나를 고르거나, 특정 조건에서만 필요한가? | LB는 subnet 또는 public IP 중 하나가 필요한가? | 선택 UI·계획 검증 |
| **속성/배치 제약** | 둘의 값·개수·배치가 맞아야 하나? | 두 subnet이 서로 다른 AZ에 있어야 하나? | IaC 사전 검사 |
| **수명주기 의존** | 무엇을 먼저 지워야 하며, 무엇이 같이 지워지나? | 사용 중 subnet 삭제가 거절되는가? | 삭제 순서·정리 계획 |
| **기능 의존** | API는 성공해도 B가 없으면 서비스가 망가지나? | 방화벽이 없으면 외부 TCP 접속이 실패하는가? | 배포 후 점검·운영 경고 |
| **운영 의존** | 권한·쿼터·DNS·준비 상태가 갖춰져야 하나? | IAM 역할 없이 노드가 클러스터에 join할 수 있는가? | readiness·운영 점검 |

이 중 첫 넷은 인프라 제어면에서 비교적 관측하기 쉽다. 다섯째와 여섯째는 더 어렵다.
리소스 생성 API가 성공해도 애플리케이션 트래픽, DNS, 권한, 데이터 쓰기가 정상이라는
보장은 없기 때문이다.

Kubernetes도 이 차이를 보여 준다. `ownerReferences`와 finalizer는 객체 소유와 삭제
보호를 다루지만, 그것만으로 서비스 간 통신이 되는지는 보장하지 않는다. 실제로
Kubernetes는 의존 객체·foreground 삭제·finalizer를 별도 개념으로 다룬다.
[Kubernetes owners, dependents, and finalizers](https://kubernetes.io/docs/concepts/overview/working-with-objects/owners-dependents/)

## 3. 좋은 의존성 분석 결과의 최소 단위

이 프로젝트의 `depkb`가 채택한 단위는 **주장(claim)** 이다. 개념적으로는 다음 모양이다.

```text
(주체 A, 대상 B, 질문 종류, CSP, 조건/술어)
    + 판정(required / optional / holds / unknown)
    + 증거(원천 위치 또는 실험 단계와 관측 코드)
    + 검증 수준(schema / preflight / apply)
```

예를 들어 사람이 읽는 결과는 이런 식이어야 한다.

```text
Azure에서 VM을 만들 때 NIC는 필수다.
근거: NIC를 생략하거나 존재하지 않는 NIC를 가리킨 VM 생성이 실제 제어면에서 거절됐다.
단, public IP는 VM 생성 자체에는 선택이다. 다만 외부 접속이라는 기능에는 필요할 수 있다.
```

여기서 중요한 점은 **"필수"와 "기능상 필요"를 섞지 않는 것**이다. public IP가 없어도
VM은 정상 생성될 수 있다. 그렇다고 인터넷에서 접속할 수 있다는 뜻은 아니다.

### 3.1 판정 어휘

| 판정 | 뜻 | 시스템의 행동 |
|---|---|---|
| `required` | 이 생성 경로에서 B 없이는 A가 서지 않는다 | 계획에 넣고 생성 순서에 반영 |
| `optional` | B 없이 A가 설 수 있다 | 선택 사항으로 제시 |
| `holds` | 삭제·기능 관계가 실제로 관측됐다 | 삭제 제약 또는 운영 경고로 출력 |
| `unknown` | 스키마 후보는 있지만 동적 확인이 안 됐다 | 통과로 처리하지 않고 소비를 보류 |

`unknown`은 실패도 통과도 아니다. **"아직 모른다"는 결과**다. AI 기반 시스템에서
이 상태를 남기지 않으면, 모델이 그럴듯한 답을 채워 넣는 순간 사실처럼 굳어 버린다.

### 3.2 방향도 적어야 한다

이 문서에서는 `A → B`를 **"A가 B를 요구한다"**로 읽는다. 그러면 생성 순서는 보통
`B`가 먼저다. 반대로 삭제 순서는 항상 그 반대가 아니다. 서버가 B를 자동 생성했거나
A를 삭제할 때 B가 함께 정리되는 경우가 있기 때문이다.

따라서 다음 셋은 서로 다른 데이터여야 한다.

```text
생성 의존:     VM → NIC          (NIC가 먼저 있어야 VM 생성 가능)
삭제 제약:     VM을 먼저 삭제 → NIC 삭제 가능
동반 정리:     Cluster 삭제 → 서버가 만든 부속 자원을 함께 정리
```

## 4. Cloud-Barista를 기준으로 삼는 것은 적절한가

**적절하다. 단, Cloud-Barista를 진실의 원천이나 실행 대상이라고 과장하면 안 된다.**

Cloud-Barista의 CB-Tumblebug은 여러 CSP의 인프라를 공통 인터페이스로 프로비저닝·관리·
오케스트레이션하려는 프로젝트다. AWS·Azure·GCP 등을 단일 인터페이스로 관리한다는 점에서,
이 프로젝트가 멀티클라우드 공통 어휘를 정하는 출발점으로 쓰기 좋다.
[CB-Tumblebug 저장소](https://github.com/cloud-barista/cb-tumblebug)

### 4.1 차용해도 좋은 것

| Cloud-Barista에서 차용하는 것 | 왜 유용한가 |
|---|---|
| 공통 자원 이름·모델 | VPC/vNet, subnet, VM/node, security group/firewall처럼 CSP별 이름을 같은 질문으로 묶을 수 있다 |
| 요청 스키마와 생성 흐름 | "어떤 값이 다른 자원을 가리키는가"라는 후보를 체계적으로 찾을 수 있다 |
| 멀티클라우드 구현 차이 | 같은 공통 자원이라도 CSP별 자동 생성·미지원·대체 방식을 드러낸다 |
| 라이프사이클 코드 | 삭제 거부·자동 정리·생성 순서의 후보를 찾는 관측 코퍼스가 된다 |

### 4.2 차용하면 안 되는 결론

| 잘못된 결론 | 왜 틀렸나 |
|---|---|
| "CB-Tumblebug이 요구하니 클라우드도 반드시 요구한다" | 도구 API의 입력 요구와 CSP API의 실제 요구는 다를 수 있다 |
| "공통 모델에 없는 자원은 CSP에 없다" | 모델의 범위 밖이거나 속성으로 표현됐을 수 있다 |
| "CB-Tumblebug의 실행 결과가 CSP 일반 규칙이다" | 버전·드라이버·도구 정책에 영향을 받는다 |
| "Cloud-Barista를 바로 배포 경로로 써야 한다" | 이 프로젝트의 결정은 분석 기준으로 사용하고, 실제 배포는 CSP 직접 또는 IaC 경로로 한다는 것이다 |

정리하면 Cloud-Barista는 **사전과 관측 코퍼스**로는 매우 유용하다. 그러나 최종
판정의 오라클은 Cloud-Barista가 아니라 CSP 제어면이어야 한다.

## 5. `depkb`는 실제로 무엇을 하는가

`depkb`는 Cloud-Barista의 기존 그래프를 그대로 받아 적는 방식이 아니라, 현재는
독립된 주장 기반 파이프라인을 둔다. 전체 흐름은 아래와 같다.

```text
1. 분석 범위와 공통 자원 어휘 선정
        ↓
2. Azure / AWS / GCP 원천 스키마에서 "관계 후보" 추출
        ↓
3. 후보마다 CSP 제어면에 물을 반사실 실험 설계·실행
        ↓
4. 증거와 판정을 claim으로 통합
        ↓
5. 선택한 자원의 이행 폐포(함께 고려할 자원군) 계산
        ↓
6. 설계용 그림과 구현용 계획으로 각각 투영
        ↓
7. 구체적인 계획의 일부 제약을 사전 검사하고,
   기능 의존은 배포 후 점검/운영 경고로 전달
```

### 5.1 범위와 어휘

`depkb/vocabulary.py`는 `network`, `subnet`, `firewall`, `nic`, `publicIp`,
`loadBalancer`, `vm`, `disk`, `sshKey`를 핵심 독립 CRUD 자원으로 잡고, 이후
Kubernetes 관련 자원을 확장했다. 관리형 DB·큐·오브젝트 스토리지 같은 상품 서비스는
**"아직 안 했다"가 아니라 현재 분석 범위 밖**으로 표시한다.

이 선택은 완전한 클라우드 카탈로그를 만들려는 것이 아니라, 현재 시스템이 클라우드
계획에서 실제로 생성 여부·개수·순서를 정할 수 있는 자원부터 분석하려는 경계다.

### 5.2 스키마는 후보 생성기다

`fetch_vendors.py`와 `extract_vendors.py`는 원문을 버전·SHA-256으로 핀하고 다음을
찾는다.

- Azure: 강타입 `$ref`, 중첩 경로, 입력 참조
- AWS: CloudFormation 속성 이름과 `Required` 플래그
- GCP: discovery schema의 참조와 속성 쌍

하지만 여기서 나온 것은 **후보**다. 예를 들어 어떤 중첩 속성이 `Required`여도,
그 블록을 선택했을 때만 필요한 것일 수 있다. 그래서 코드도 스키마의 `Required`를
간선 필수성의 확정 증거로 쓰지 않는다.

### 5.3 실험이 판정을 만든다

`build_claims.py`의 `EXPERIMENT_JUDGMENTS`는 실험 결과 파일의 단계와 실제 오류 코드
또는 성공 결과를 대조한다. 인용한 관측과 결과 파일이 다르면 claims 빌드가 실패한다.

검증 수준의 강도는 다음 순서다.

```text
apply (실제 생성/삭제 API 결과)
  > preflight (제어면 사전검증 결과)
  > schema (문서·스키마에 보이는 후보)
```

스키마 통과나 사전검증의 침묵은 "문제가 없다"는 증거가 아니다. 실제 생성 경로에서
확인하지 못했다면 `unknown`으로 남기는 것이 원칙이다.

### 5.4 claims가 분석의 결과물이다

`claims.json`은 사람이 읽는 그래프 그림보다 중요한 결과물이다. 각 행이 어떤 CSP에서
어떤 관계를 어떤 질문으로 검증했고, 어느 증거에 기대는지 갖고 있기 때문이다.

2026-08-03 작업 트리에서 이 파일은 119개 주장을 담고 있으며, 존재 의존 72개,
수명주기 32개, 기능 의존 15개로 구성된다. 숫자는 다시 빌드하면 달라질 수 있으므로
**숫자 자체보다 claim 형식과 증거 연결이 핵심**이다.

### 5.5 폐포는 "하나를 고르면 무엇이 따라오나"의 답이다

`closure.py`는 선택한 앵커에서 출발해 필요한 자원을 이행적으로 계산한다. 결과는
다섯 묶음으로 나뉜다.

| 폐포 결과 | 뜻 |
|---|---|
| `required` | 없으면 앵커가 생성되지 않는 자원 |
| `attachable` | 붙일 수 있지만 없어도 생성되는 자원 |
| `decisions` | 사용자나 설계자가 선택해야 하는 조건·대안 |
| `createOrder` / `deleteBefore` | 생성·삭제에서 지켜야 할 순서 |
| `functionalDeps` | 생성은 되지만 떼면 서비스 기능이 깨질 수 있는 결속 |

예를 들어 단순화한 Azure VM 경로는 다음처럼 읽을 수 있다.

```text
VM
 └─ 반드시: NIC
     └─ 반드시: subnet
         └─ 반드시: network

public IP / firewall은 "VM 생성"만 놓고 보면 선택일 수 있다.
하지만 외부 접속·허용 포트라는 기능을 요구하면 별도의 기능 의존·운영 점검이 된다.
```

이것이 과제에서 말한 "특정 자원을 선택할 때 연계되는 자원군"의 정확한 구현 형태다.
단순히 후보를 많이 나열하는 것이 아니라, 필수·선택·자동·결정을 가른다.

### 5.6 분석 결과의 소비

`infra_intent.py`는 폐포를 `easydep-infra-intent/v1alpha1`로 바꾸며,
`views.py`는 이를 두 용도에 맞게 나눈다.

| 뷰 | 소비자 | 담는 것 |
|---|---|---|
| 설계 뷰 | 배포 다이어그램 | 노드, "A가 B를 요구"하는 화살표, 근거, 아직 결정할 것 |
| 구현 뷰 | IaC·매니페스트 생성 | 생성/삭제 순서, 자동 생성 경고, 사전 검사 규칙, 운영 경고 |

`check.py`는 배치 수·AZ 분산·zone 호환·이름 조건처럼 구조화된 일부 제약을 실제
계획에 대조한다. 구현되지 않은 종류는 성공으로 가장하지 않고 `unchecked`로 남긴다.

## 6. 이 분석이 잘했는지 판단하는 객관적 체크리스트

다음 질문에 모두 "예"라고 답할 수 있을수록 분석은 신뢰할 만하다.

1. **대상이 명확한가?** `vm`, `subnet` 같은 공통 이름이 실제 CSP 타입과 어떻게
   대응되는지 기록되어 있는가?
2. **방향과 질문이 명확한가?** `A → B`가 생성, 삭제, 기능 중 무엇인지 명시하는가?
3. **조건을 잃지 않았는가?** "두 개 이상", "서로 다른 AZ", "둘 중 하나만" 같은
   제약을 간선 옆에 보존하는가?
4. **후보와 결론을 구분하는가?** 스키마 참조는 후보, 동적 제어면 관측은 판정으로
   구분되는가?
5. **CSP 차이를 보존하는가?** AWS에서 필요한 것이 Azure에서 자동 생성되거나,
   GCP에서 속성으로 표현되는 차이를 평균 내 버리지 않는가?
6. **생성·삭제·기능을 섞지 않는가?** "생성 가능"을 "서비스 정상"으로 오독하지
   않는가?
7. **모름을 표현하는가?** 미검증 관계가 통과나 필수로 둔갑하지 않는가?
8. **소비자가 있는가?** 생성 순서는 IaC에, 기능 의존은 배포 후 점검에 실제로
   전달되는가?
9. **재현 가능한가?** 원천 버전, 해시, 실험 단계, 오류 코드가 남는가?
10. **범위를 고지하는가?** 관리형 서비스·권한·애플리케이션 런타임처럼 아직 다루지
    않은 곳을 빈칸이 아니라 범위로 보이는가?

`depkb`는 1~7, 9~10에 대해 비교적 좋은 구조를 갖고 있다. 특히 "스키마 후보를
실험 없이 사실로 승격하지 않는다", "미확인을 숨기지 않는다", "자동 생성과 직접
생성을 구분한다"는 점이 AI가 만든 단순 관계 그래프보다 강하다.

## 7. 현재 `depkb`의 정확한 평가

### 잘한 점

- **Cloud-Barista 종속 그래프를 그대로 신뢰하지 않았다.** 공통 어휘·관측 코퍼스로는
  쓰되, 독립적인 CSP 스키마와 제어면 실험을 도입했다.
- **CSP별 차이를 1급 데이터로 뒀다.** 공통 모델 하나로 AWS·Azure·GCP 차이를
  덮지 않는다.
- **시간을 분리했다.** 생성 필요성, 삭제 제약, 자동 정리, 대기 상태를 한 간선에
  압축하지 않는다.
- **기능 실패를 별도 축으로 열었다.** API가 통과해도 `node-join`, `inbound-tcp`,
  `dns-resolution`, `volume-write` 등이 실패할 수 있음을 신호로 기록한다.
- **산출물이 소비 가능한 모양이다.** 그림용·IaC용·계획 검사용 결과가 분리되어 있다.

### 아직 말하면 안 되는 것

- "모든 클라우드 리소스 의존성을 분석했다." — 아니다. 현재는 의도적으로 좁힌
  IaaS·일부 Kubernetes 자원 중심이다.
- "모든 기능 의존성을 검증한다." — 아니다. 기능 의존은 15개 주장으로 시작한
  상태이며, 많은 결과가 운영 경고로 남는다.
- "Cloud-Barista가 말한 의존성은 CSP의 객관적 사실이다." — 아니다. CB는
  공통 모델과 관측 재료다.
- "IaC가 apply되면 애플리케이션도 정상이다." — 아니다. 네트워크 도달, DNS,
  IAM, 서비스 readiness, 데이터 경로는 별도 확인이 필요하다.
- "모든 결과가 현재 제품 API 흐름에 자동으로 강제된다." — 아니다. 분석·계획
  모듈은 구현되어 있으나, 일반 FastAPI 설계·구현 흐름의 완전한 자동 배선은 별도
  통합 과제다.

## 8. 앞으로 분석을 넓힐 때의 올바른 순서

무작정 자원 종류를 늘리는 것은 좋은 다음 단계가 아니다. 아래 순서가 안전하다.

1. **소비자를 먼저 정한다.** 새 자원이 설계 그림, IaC, 배포 후 점검 중 어느
   판정을 가능하게 하는지 한 문장으로 쓴다.
2. **공통 어휘와 CSP 대응을 고정한다.** Cloud-Barista 모델을 출발점으로 삼되,
   각 CSP의 실제 타입·속성·대체 방식을 명시한다.
3. **스키마에서 후보를 뽑는다.** 후보는 결론이 아니라 실험 대기열이다.
4. **반사실 실험을 설계한다.** 생략, 잘못된 참조, 조건 반전, 정상 대조군을
   함께 준비한다.
5. **주장으로 기록한다.** 근거·CSP·시점·조건·`unknown`을 빠뜨리지 않는다.
6. **소비 경로를 붙인다.** 생성 제약은 IaC 사전 검사, 기능 결속은 배포 후
   probe로 연결한다.
7. **범위와 미검증을 발표한다.** 커버리지 수치와 미측정 영역을 같이 제시한다.

특히 다음 확장은 서로 다른 연구 과제다. 한 그래프에 섞으면 판단이 흐려진다.

| 다음 확장 | 새로 필요한 증거 |
|---|---|
| IAM·권한 의존 | 최소 권한, 토큰 획득, 실제 작업 성공 실험 |
| 네트워크 기능 의존 | 라우팅·DNS·TLS·보안 규칙을 포함한 end-to-end probe |
| 관리형 서비스 | 각 CSP 상품별 API·가격·운영 모델과 별도의 범위 결정 |
| 애플리케이션 의존 | API 호출, 데이터 계약, 실패 전파, SLO 관측 |
| 복구·장애 의존 | 장애 주입, failover, 백업·복구 시험 |

## 9. 한 문장 결론

`depkb`는 **"모든 클라우드 네이티브 의존성"을 완성한 시스템은 아니지만, 현재 범위에서
"선택한 인프라 자원을 실제 CSP에 만들고·지우고·작동시키기 위해 무엇을 함께 고려해야
하는가"를 증거와 불확실성까지 포함해 분석하는, 타당한 클라우드 리소스 의존성 분석
기반이다.

좋은 다음 목표는 더 많은 화살표를 만드는 것이 아니라, 이미 있는 각 주장이 설계,
IaC, 배포 후 검증에서 실제로 빠짐없이 소비되게 하는 것이다.
