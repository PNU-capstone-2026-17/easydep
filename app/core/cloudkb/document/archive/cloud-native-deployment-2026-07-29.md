## 1. 과제가 요구한 것 — research.md를 지식 요구로 번역

`research.md`가 정의한 개발 과정은 셋입니다.

```
클라우드 리소스 배포  →  리소스 연결 및 서비스 기능 탑재  →  서비스 실행
```

그리고 AI 에이전트가 이 과정에서 겪는 문제 셋 중 **둘**이 배포 단계에 직접 걸립니다.

| research.md의 문제 | 배포 단계에서 뜻하는 것 |
|---|---|
| **문제 ①** 환각으로 요구사항에 부합하지 않는 리소스·기능을 산출물에 포함 | 모델이 클라우드 사실(한도·가격·성능)을 **지어낸다.** 어제는 맞고 오늘은 틀린 값을 확신 있게 말한다 |
| **문제 ②** 리소스 간 의존 관계성과 선택 제약이 존재하며, 특정 리소스를 고르면 **연계되는 리소스 군**을 획득할 수 있어야 하고, **비용·성능 가이드라인**이 필요 | "이걸 만들려면 뭐가 먼저 있어야 하나" · "이걸 쓰면 뭐가 따라오나" · "얼마고 얼마나 빠른가"에 **근거를 대고** 답해야 한다 |
| 문제 ③ 단계별 산출물의 일관된 생성·측정 | (목표 3 — 설계도→배포 계획 층에서 일부 다룸. 5.6절) |

목표 2의 문장이 그대로 요구 명세입니다.

> *"클라우드 환경 특성(클라우드 인스턴스 성능, 비용 등), 클라우드 리소스의 특성
> (리소스 용량, 리소스 의존성 등)을 고려한 클라우드 네이티브 환경 가이드라인 제공"*

여기서 **네 가지 지식 요구**가 나옵니다. 괄호가 우리가 만든 축입니다.

```
리소스 의존성   "무엇이 무엇을 필요로 하나"          (graphkb)
리소스 용량     "무엇이 허용되나 · 한도 · 바꿀 수 있나"  (capacitykb)
비용            "무엇을 얼마에 살 수 있나"            (costkb)
인스턴스 성능   "얼마나 빠른가 · 함정은 없나"          (perfkb)
```

조사하면서 **요구 명세에 없던 것 다섯이 더 필요하다는 것**이 드러났고, 그것이 축이
아홉으로 자란 이유입니다(3절).

### 결정적 전제 하나 — 우리는 배포기가 아니라 가이드라인이다

research.md는 "가이드라인 제공"이라고 적고 있습니다. 이 한 단어가 전체 설계를
가릅니다.

```
배포기        만들어 준다.  "됐습니다"가 답이다
가이드라인    답을 준다.    "왜 그렇게 아는지"가 답의 일부다
```

그래서 **모든 사실 한 줄에 출처와 근거의 성격이 붙습니다.** 이게 문제 ①(환각)에 대한
구조적 대응이고, 배포기였다면 필요 없었을 장치입니다.

## 2. 어떻게 조사했나

### 2.1 선정 절차 — 체계적 문헌고찰의 포함/배제 기준에 대응

소스 47종이 **편의표본이 아님**을 보이려면 절차가 기록돼야 합니다.

| 기준 | 내용 |
|---|---|
| **포함** | ① 무인증 공개 ② 기계 판독 ③ 버전을 못 박을 수 있음 ④ 회사의 배포 시스템이 실제로 쓰는 것 |
| **배제** | 산문 스크래핑 · 자격증명 필요 · 핀 불가 · 재배포 명시 금지(산출물 커밋 불가) |
| **예외 3** | 표만 파싱(`azure-limits-doc`·`azure-compute-docs`) · 자문 전용 렌더링 HTML(`gcp-architecture-framework`) · 공식 배포 PDF(`aws-well-architected`) |
| **흐름 기록** | 기각한 후보와 기각 사유를 남김 — `cloud-foundation-fabric`(무조건 리소스 0개), Magic Modules YAML(태그 0개·빈 목록 증발), `instances.json`(209MB, 커밋 안 됨·재배포 불가) |

**"기계에 주라고 만든 설명서"를 씁니다** — 틀리면 그 회사가 먼저 아프기 때문입니다.
사람이 읽는 문서를 긁는 것은 원칙적으로 안 합니다.

### 2.2 규율 여섯 — 조사 중에 굳은 것

1. **못 박고 시작한다.** 소스마다 태그·커밋·지문을 고정하고(`태그 23 · 커밋 18 ·
   지문 5 · 동봉 1`), 받은 바이트의 sha256을 함께 남깁니다. 안 그러면 "고쳤다"를
   증명할 수 없습니다 — 감사 중 캐시된 AWS zip(2,783,390 B)이 같은 URL의
   라이브(2,794,161 B)와 이미 달라진 것을 이 기록이 잡았습니다.
2. **새 소스를 찾기 전에 이미 받아 둔 소스의 안 쓰는 부분부터 본다.**
   `tumblebug-cloudinfo`(리전 188개)·`botocore-endpoints`(엔드포인트 9,039쌍)가
   그렇게 나왔습니다. *이 규율을 어긴 사례가 하나 실측됐고 그 개선 계획이
   `perfkb-field-axis-plan-2026-07-29.md`입니다.*
3. **두 소스가 같은 말을 할 때만 담는다.** AWS 디스크 한도는 Price List × botocore가
   10쌍 전부 일치한 **20건만** 담았습니다. `gp2`의 IOPS는 한쪽에만 있어 **없는 제약을
   만들 뻔한 것을 안 담아서** 막았습니다.
4. **단정 전에 센다.** "NHN은 공개 프로바이더가 없다"·"botocore shape에는 min/max가
   없다"가 둘 다 실측으로 뒤집혔고, 그 정정을 소스 등록부에 남겼습니다.
5. **버린 것을 세어 밝힌다.** Azure 가격 279,234행을 이유별로, IBM의 버린 칸 이름을,
   못 붙인 서비스 이름을 개수까지 산출물에 적습니다.
6. **포화는 커버리지 격자로 판정한다.** "12개 클라우드 지원"이 축마다 다른 말이라는
   것을 표로 드러냅니다(3절). 선언이 아니라 전수로 센 값입니다.

## 3. 지식을 어떻게 나눴나 — 축 아홉

한 덩어리로 만들면 **"무엇을 모르는지"를 말할 수 없습니다.** 축을 나누면 각 축이 자기
수집 범위를 스스로 말합니다.

| 축 | 답하는 질문 | 요구 출처 |
|---|---|---|
| **graphkb** | 무엇이 무엇을 필요로 하나 · 회사 간 대응 | research.md **리소스 의존성** |
| **capacitykb** | 무엇이 허용되나 · 한도 · 바꿀 수 있나 | research.md **리소스 용량** |
| **costkb** | 무엇을 얼마에 살 수 있나 | research.md **비용** |
| **perfkb** | 얼마나 빠른가 · 함정은 없나 | research.md **인스턴스 성능** |
| bundlekb | 이것을 쓰면 무엇이 따라오나 | ← 조사 중 발견: **"연계되는 리소스 군"**은 의존성과 다른 축 |
| sizingkb | 도구·플랫폼이 요구하는 최소 규모 | ← "만들 수 있다"와 "실제로 쓸 수 있다"의 간극 |
| envkb | 리전·지연·탄소·수명주기 | ← 리소스가 아니라 **환경**의 사실 |
| patternkb | 설계 지침 산문 (**자문 전용**) | ← 수치로 환원되지 않는 지식 |
| appkb | 설계 JSON 계약·검증·다이어그램 | 목표 3의 진입점 |

**bundlekb가 요구 명세를 가장 직접 읽은 축입니다.** research.md의 *"특정 리소스를
선택하는 경우 연계되는 다양한 리소스 군을 획득할 수 있어야 하며"*는 "A가 B를
참조한다"(graphkb)와 다른 질문입니다 — "VM 하나를 만들면 실제로 무엇이 함께
생기나"이고, 그 답은 스키마가 아니라 **실제 배포 사례**에 있습니다.

### 커버리지 격자 — "12개 클라우드"는 축마다 다른 말이다

**의존성(엣지)은 사실상 3개 클라우드뿐입니다.** 나머지는 Terraform provider에서 타입은

가장 오해하기 쉬운 칸은 **oracle**입니다 — 제약이 14,614건(3위)인데 가격·성능·관계가
전부 0입니다.

## 4. 에이전트에 어떻게 녹였나

지식이 맞아도 **말하는 방식이 틀리면** 사용자는 틀린 답을 받습니다. 반영은 네 층입니다.

```
① 데이터 층    레코드마다 evidence + basis        (무엇을 근거로 아는가)
② 도구 층      로컬 도구 31개 + tumblebug MCP     (축 조인은 여기서만)
③ 답변 규율    침묵 4구분 · 조건부 3상태 · 구조적 금지
④ 검증 층      claim_check · 라이브 프로브
```

### 4.1 근거 두 꼬리표 — 문제 ①에 대한 구조적 대응

사실 한 줄마다 **어디서 왔나**(`evidence`)와 **어떻게 아나**(`basis`)가 붙습니다.

```
stated    원본이 그렇게 적어 놓았다. 우리는 옮겼을 뿐이다        37개 라벨
inferred  이름·문장·구조를 보고 우리가 짐작했다. 틀릴 수 있다     15개 라벨
observed  실제 사례 뭉치에서 센 것. 규칙이 아니라 관찰이다         2개 라벨
```

숫자 신뢰도(0.5~1.0)를 쓰다가 **전부 버렸습니다** — 척도의 정의가 어디에도 없었고,
실제로 쓰이는 임계값 하나(`>= 0.8`)가 가른 것은 158건 중 115건이 정확히 0.8이라
상수를 0.81로만 바꿔도 결과가 뒤집히는 상태였습니다.

이 셋에서 두 판정이 갈라집니다.

```
is_fact      이 근거로 값을 거부해도 되는가   ← 검수되면 면제된다. observed는 절대 아니다
needs_hedge  답에 유보를 붙여야 하는가        ← 검수도 면제가 아니다
```

**한 방향만 말하는 칸을 양방향으로 읽지 않습니다.** AWS의
`BurstablePerformanceSupported=false`는 "버스트가 아니다"가 아니라 "그 칸에서 빠졌다"
입니다. 실제로 `t1.micro`가 `false`인데 T2 크레딧 모델보다 앞선 세대라서일 뿐입니다.
그대로 옮겼다면 "t1은 성능이 보장된다"는 정반대 답이 나갔을 것이고, 이 규율 하나로
29,395건이 `stated`에서 `inferred`로 내려갔습니다.

### 4.2 침묵을 넷으로 가른다

옛날에는 이 넷이 **전부 같은 출력**이었습니다 — 함수가 넷 다 `None`을 반환해서
화면 글자가 **바이트 단위로 똑같았습니다.**

| 상황 | 답변 |
|---|---|
| 수집 범위 안, 제약 없음 | "알려진 제약이 없습니다 (**수집 범위 안이므로 '없음'이 답**)" |
| 수집 범위 밖 | "**수집 범위 밖**이라 모릅니다 — 없다는 뜻이 아닙니다" |
| 정규식을 못 읽음 | "제약은 있으나 그 정규식을 읽을 수 없습니다" + 원문 |
| 조건에 안 걸림 | "조건부 제약 N건이 있지만 **주신 조합에 걸리는 것이 없습니다**" |

밖에서 부르는 이름이 있습니다 — **국소 폐쇄세계 가정**(local closed-world assumption).
"수집 범위 안이라 없음이 답"과 "범위 밖이라 모름"의 구분이 정확히 그것입니다.

### 4.3 조건을 모르면 한쪽으로 찍지 않는다 — 3상태

```
질문) AWS 디스크에 30,000 GiB (VolumeType=gp2)   → 안 됩니다. 최대 16,384 GiB
질문) 같은 질문, VolumeType=gp3                   → 됩니다
질문) VolumeType을 안 알려줌                      → 조건에 따라 갈립니다
                                                    (14가지 중 9개 허용 · 5개 불허)
```

"아마 되겠죠"는 gp2 디스크를 망가뜨리고, "안 됩니다"는 gp3로 하면 되는 길을 막습니다.
이것도 이름이 있습니다 — **Kleene 강 3치 논리**(SQL의 NULL 의미론과 같은 것).

### 4.4 막다른 길을 답으로 바꾼다

실측에서 가장 큰 수확이었습니다. 에이전트가 `p5.48xlarge`(**값**)를 타입 이름으로
검색했을 때 "없습니다"만 줬더니, 웹검색 13회·14분을 쓰고 "지식베이스에 없습니다"라고
답했습니다 — 그때 우리는 그 값의 리전별 데이터 39건을 쥐고 있었습니다.

값 역인덱스(고유 값 7,095개)를 넣은 뒤: **838초 → 6.6초, 웹검색 0회, 정답.**

> 배운 것: 모델은 매번 다른 문으로 들어옵니다 — **모든 문이 답을 알아야 합니다.**

### 4.5 구조적으로 막은 것 — 프롬프트에 맡기지 않는다

문제 ①에 대한 대응 중 **가장 강한 것**입니다. 하면 안 되는 일을 설명하는 대신 **할 수
없게** 만듭니다.

| 막은 것 | 방법 | 왜 |
|---|---|---|
| 프로바이더 간 성능 비교 | `perf_compare`가 **단일 프로바이더만 받는다** | ACU는 Azure에만, 클럭은 AWS에만 — 공통 기준이 없다 |
| 총비용 합계 | 어느 도구도 합계를 만들지 않는다 | 일부만 아는데 합계를 내면 **그럴듯한 거짓 총액**이 된다 |
| 데이터 주권 준수 판정 | 리전 사실과 **대조만** 하고 "판정 불가"를 명시 | 법적 판단이라 우리 몫이 아니다 |
| 컴퓨트 방식 임의 선택 | **상충 없는 후보가 정확히 하나일 때만** 권고 | 여럿이면 안 고른다 |
| 가격 데이터 재배포 | `pack`이 파일 이름을 보고 거절 + 테스트가 `data/` 존재를 막는다 | AWS 약관이 **명시적으로 금지** |
| 도구 이름 누출 | 도구 출력에 다른 도구 이름을 넣지 않는다 | 모델이 그 문자열을 답변에 그대로 복사한다(실측 3/3) |

### 4.6 설계도 → 배포 계획 (목표 3과의 접점)

외부 설계 에이전트의 산출물을 JSON 계약으로 받아 배포 계획을 냅니다.

- **계약 위반이면 무엇이 왜 위반인지 목록으로 답하고 처리하지 않습니다.** 라이브
  검증에서 모델이 이 위반 목록을 **지어내지 않고 그대로 전달**함을 확인했습니다.
- 계획의 각 노드·엣지·노트에 **origin**이 붙습니다 — 설계 원문 / 설계자 지정 /
  KB 사실 / 우리 추론. 추론에는 유보(⚠)가 붙습니다.
- **값은 하한이고 그 하한의 전제를 밝힙니다** — "월 $X (하한, 컴퓨트 각 1대 기준.
  수평 확장 대수는 정해지지 않았습니다)".
- **예산 판정이 비대칭입니다.** 하한이 예산을 넘으면 "초과 **확정**", 하한이 예산
  안이면 "지킬 수 있을지 **판정 불가**". 같은 데이터에서 한쪽은 확정, 한쪽은 불가 —
  이 비대칭이 정직함입니다.
- 렌더한 PlantUML을 **되파싱해 계획과 대조**합니다. 그리기 코드가 노드를 빠뜨리면
  테스트가 죽습니다.

### 4.7 출처 세탁 방지 — 측정이 계속 가리킨 곳

> **모델이 자기 기억을 우리 지식베이스의 이름으로 내보낸다.**

가장 위험한 실패입니다. 근거를 대는 KB를 만들어도, 모델이 KB에 없는 값을 "지식베이스에서
조회한 결과"라고 말하면 **KB가 오히려 신뢰를 빌려주는 장치**가 됩니다. 실측 사례:
"ap-northeast-2에서 쓸 수 있는 GPU 인스턴스"에 모델이 GPU 개수·vCPU·메모리 표를 통째로
지어내고 `g5g`를 AMD라고 했습니다(NVIDIA입니다) — 그리고 그것을 **우리 KB 조회
결과라고 명시**했습니다.

대응은 둘입니다. ① **빈칸을 메운다**(그 사건이 `ec2-hardware` 소스를 넣은 이유입니다 —
빈칸이 지어내기를 부릅니다). ② **주장 대조기**(`claim_check`)가 답변의 주장을 산출물과
대조합니다. 밖에서의 이름은 **귀속성 평가**(attribution)·그라운드니스 검증입니다.

## 6. 아직 안 녹인 것 — 그리고 녹여낼 것

정직하게 미결로 둡니다. **이게 이 문서에서 가장 값이 큰 절입니다.**

| # | 공백 | 성격 | 계획 |
|---|---|---|---|
| 1 | **의존성이 3개 클라우드뿐** (나머지 7곳 엣지 0) | 비어 있는 축 | Terraform provider에서 관계를 뽑는 경로가 없음. 스키마에 참조 메타데이터가 없어서이지 누락이 아님 |
| 2 | **정확성을 잰 적이 없다** | 구조적 | 정답지(gold set)가 없습니다. 교차 검증(두 소스가 같은 말)은 **대용이지 정확성 측정이 아닙니다.** ISO/IEC 25012의 *accuracy* 칸이 비어 있습니다 |
| 3 | **완전성은 선언이지 측정이 아니다** | 구조적 | "수집 범위"는 우리가 밝히는 것이지 잰 것이 아닙니다 |
| 4 | 소스 신선도 주기 없음 | 운영 | 핀 47종이 언제 낡는지 지켜보는 주기가 없습니다. 지문 소스 5종은 재빌드 때만 드리프트가 드러납니다 |
| 5 | 라이선스 미확인 4종 | 법적 | `cfn-schema`는 저장소가 없어 **원리적으로 어렵습니다** |
| 6 | **누가 검수했는지가 없다** | 구조적 | `reviewed`가 참/거짓 하나입니다. PROV의 `Agent`·`wasAttributedTo`에 해당하는 칸이 없어, 코더가 여럿이 돼도 지금 자료구조로는 구별할 수 없습니다 |
| 7 | TOSCA Requirements/Capabilities 모델 없음 | 설계 | "A가 B를 참조한다"만 말하고 "A가 요구하는 능력을 B가 제공한다"가 없습니다. **대체 후보를 고르는 일**이 이 모델의 몫인데 svcmap의 이름 대응으로 대신하고 있습니다 |
| 8 | perfkb 필드 선정 절차 없음 | 진행 중 | 미러 `details` 키의 전수 분류가 없어 aws `maxNics` 0건 같은 공백이 조용히 남았습니다 → `perfkb-field-axis-plan-2026-07-29.md` |
| 9 | 실사용 질의 분포 | 운영 후 | 프로브는 우리가 지어낸 질문입니다 |
| 10 | 국내 클라우드가 전 축에서 1% 미만 | 자료 한계 | 공개된 기계 판독 자료가 그만큼뿐입니다. **이 KB로 "국내 클라우드 가이드라인"을 주장하면 안 됩니다** |

2·3·6·7이 **연구적으로 가장 아픈 자리**입니다. 넷 다 "출처를 밝히는 일은 잘하고,
맞는지 재는 일은 하지 않았다"는 한 문장으로 묶입니다.

## 7. 외부 표준에 대고 보면

우리 말로만 쓰면 규율끼리는 정합적인데 **자기참조**가 됩니다. 매핑은 **양방향**이어야
합니다 — 표준에 있는데 우리에게 없는 칸을 함께 내지 않으면 유리한 쪽만 고른 것입니다.

| 우리 규율 | 밖에서의 이름 |
|---|---|
| "범위 안이라 없음" vs "범위 밖이라 모름" | 국소 폐쇄세계 가정 |
| 성립/불성립/**모름** 3상태 | Kleene 강 3치 논리 |
| `evidence`+`basis`+`reviewed` | W3C PROV |
| 핀·sha256·`_source` | ISO/IEC 25012 *currentness · traceability · credibility* |
| `references`·`contained_in`·`equivalent_to` | OASIS TOSCA 관계 타입 |
| `claim_check` | 귀속성 평가 · 그라운드니스 검증 |
| 소스 선정 절차 | 체계적 문헌고찰의 포함/배제 기준 |

**반대 방향**(표준에 있는데 우리에게 없는 것)은 6절의 2·3·6·7이 그대로입니다.

요구사항 쪽 관심사 축은 이미 ISO/IEC 25010에 양방향 매핑돼 있습니다
(`cloud-native-requirements.md`). 배포 쪽 매핑이 뒤늦은 것이 감사에서 지적된
불균형이었습니다.
