# 인프라 의도 — 배선 계획 (2026-07-31)

> **불변 기록·실행 전 계획.** 완료·정정은 커밋이 기록한다. 근거 없는 결정은
> **우리 결정**으로 표시했다.

## 0. 왜 지금인가

의존성 분석은 58주장·23라운드로 섰고 소비자(`closure`·`app/core/dependency`)도
있는데 **부르는 코드가 없다.** 지식이 계획에 닿지 않으면 "클라우드 네이티브
개발 지원"이라는 과제 문장이 참이 되지 않는다.

## 1. 실물 확인 (2026-07-31, 코드에서)

| 층 | 지금 있는 것 | 비어 있는 것 |
|---|---|---|
| 요구사항 | `RESOURCE_SPEC` — provider·region·monthlyBudgetUSD 필수 | 자원 종류를 안 정한다 |
| 설계 | 클래스·시퀀스 다이어그램(소프트웨어 설계) | **배포/인프라 다이어그램 없음** |
| 구현 | `easydep-deployment-intent/v1alpha1` — Deployment·Service·Ingress·HPA·PDB·NetworkPolicy·PVC | **전부 k8s 층. 클라우드 자원 0** |

즉 사슬이 요구사항 → 설계 → 배포 의도(k8s) → manifest이고 **클라우드 자원 층이
통째로 없다** — "클러스터는 이미 있다"가 암묵 전제다. 우리 58주장이 정확히 그
없는 층의 지식이다.

## 2. 결정 (사용자, 2026-07-31)

- **D1. 프로비저닝 포함.** 클러스터·네트워크를 우리가 만드는 것으로 본다.
  기존 클러스터 참조 모드는 이번 범위 밖(뒤집힐 조건: 하류가 참조 모드를
  요구하면).
- **D2. 산출물을 먼저 만들고 에이전트를 맞춘다.** 기존 계약에 맞추는 것이
  아니라 필요한 형태를 정의한다 — "클라우드 네이티브 요소를 첨가"하는 일이므로
  기존에 없는 것이 있는 게 정상이다.
- **D3. 두 뷰로 나눈다** — 소비자가 둘이고 필요가 다르다(§4).

## 3. 앵커는 발명하지 않는다 — 하류가 이미 말한다

`kind: Deployment`라고 적는 순간 앵커는 `k8sCluster`다. 워크로드 형태 매핑을
새로 만들 필요가 없다. **번역 규칙은 우리 구성이되 하류 신호의 해석이다**:

| 하류 신호 | 클라우드 함의 | 근거 |
|---|---|---|
| `workloads[].kind` | `k8sCluster` 앵커 | k8s 오브젝트는 클러스터 없이 못 산다 |
| `capabilities.ingress` | `loadBalancer` + 노출 스킴 | 외부 노출의 유일한 신호 |
| PVC 필요 | `disk`(+ 존 쌍 호환 검사) | gcp 존 일치 실측 |
| `replicas.max` | **안 쓴다** — 스펙·대수는 우리 축이 아니다 | 범위 밖 명시 |
| `capabilities.networkPolicy` | **클라우드 firewall이 아니다** | k8s 층 오브젝트 — 혼동 금지 |

**미해결로 남긴다**: k8s Service(type LoadBalancer)가 클라우드 LB를 자동 생성하는
경로. 우리가 한 번도 재지 않았고, 우리 IaC가 LB를 또 만들면 **이중 생성**이
된다. 측정 전까지 추측으로 메우지 않는다.

## 4. 산출물 — 인프라 의도 하나, 뷰 둘

`easydep-infra-intent/v1alpha1`(이름은 하류 관례를 따른 우리 구성):

```
{ schemaVersion, csp, region,
  anchors: [...],                     # 무엇을 고른 결과인가
  resources: [{id, role, because[]}], # 연쇄 의존 자원 집합 — role: required|attachable
  createOrder: [...], deleteBefore: [[a,b]],
  autoFilled: [{id, what}],           # 서버가 채우는 것 + 고지 문장
  decisions: [{about, kind, question}],  # 사람이 정할 것 + 질문 문장
  constraints: [{kind, subject, object, rule}],  # 쌍 호환·배치·이름 조건
  provenance: {claims, oracleLayer}   # 근거
}
```

**뷰 둘** — 같은 의도의 사영이다.

| 뷰 | 소비자 | 담는 것 |
|---|---|---|
| `design_view` | 설계(배포 다이어그램) | 노드·간선·필연성·**근거**·사람이 정할 빈칸. 순서는 거의 불필요 |
| `provision_view` | 구현(IaC) | 생성 순서·삭제 순서·참조 위치·**제약 검사 규칙**. 근거는 주석 수준 |

## 5. 단계

| 단계 | 무엇 | 멈추는 조건 |
|---|---|---|
| **P1** | 인프라 의도 스키마 + 빌더(`closure` 소비) | 3사 × 앵커 조합에서 스키마 검증 통과, unknown 만나면 죽는다 |
| **P2** | 하류 신호 번역(§3 표) — deployment-intent → 앵커·노출·스토리지 | 규칙마다 근거 1줄. 애매하면 값이 아니라 `decisions` |
| **P3** | 뷰 둘 + 사람이 읽는 문장화(질문·고지) | 질문은 **술어 원문이 아니라 문장**. 고지 없는 autoFilled 금지 |
| **P4** | 제약 검사기 — 쌍 호환·배치·이름 조건을 계획에 적용 | 위반을 잡는 음성 테스트가 있을 것 |
| **P5** | 에이전트 배선 — 설계·구현이 실제로 호출 | 산출물이 run 아티팩트로 남는다 |

**P1이 먼저인 이유**: P2~P5의 입력이고, 새 조사 없이 기존 claims만으로 만들 수
있다. **P5가 마지막인 이유**: 앞 넷이 서기 전에 배선하면 에이전트가 반쪽 산출물에
의존하게 된다.

## 6. 이 계획이 열어 주는 것

IaC가 산출되면 **그 IaC의 apply가 곧 claims의 회귀 검사**가 된다. 계획이 만든
IaC가 `SubnetIsRequired`나 `InUseSubnetCannotBeDeleted`로 깨지면 주장이 틀렸거나
소비가 잘못된 것이다 — 지식과 산출물이 서로를 검증하는 고리가 여기서 닫힌다.

## 7. 타당성 위협

| | 위협 | 대응 |
|---|---|---|
| I1 | 번역 규칙(§3)이 우리 구성 | 규칙마다 근거를 달고, 애매하면 질문으로. 반례에 열어 둔다 |
| I2 | **층 경계 미측정** — k8s Service ↔ 클라우드 LB 이중 생성 | 명시적 미해결. P5 이후 실측 대상 |
| I3 | 하류가 k8s를 전제 — VM만 쓰는 앱은 앵커가 없다 | 이번 범위는 k8s 경로. VM 경로는 신호가 생기면 |
| I4 | 산출물이 소비되지 않으면 검증 불가 | P5까지 가야 계획이 닫힌다. 중간 정지는 미완으로 표시 |
| I5 | 우리 축이 아닌 것(스펙·대수·비용)을 요구받을 수 있다 | §3에서 명시적으로 뺐다. 요구되면 별도 결정 |
