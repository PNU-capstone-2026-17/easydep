# customImage 라운드 계획 — 3사 존재·생명주기 (2026-07-31, 실행 전 기록)

## 왜 이것인가

어휘 밖 대기열. graphkb에 `node→customImage` 생명주기 간선이 **관측만**
돼 있고(P1 분포에서 lifecycle만 1건인 유일 사례) 컨트롤 플레인 실측이
없다. 배포 파이프라인에서 "골든 이미지"는 CNA의 실제 관행이기도 하다.

## 셀

`image`(플랫폼/마켓플레이스)와 달리 `customImage`는 **우리가 만드는 것**이라
질문이 둘이다.

| 질문 | 셀 |
| --- | --- |
| 존재: customImage→disk | 원본 없이 이미지를 만들 수 있는가(허상 원본 거부) · 원본 디스크로 생성 성공(양성) |
| 생명주기: customImage→disk | 이미지가 원본 디스크를 붙잡는가 — 이미지 존재 중 원본 삭제 시도 |
| 존재: vm→customImage | 그 이미지로 VM이 서는가(사슬 완결, 실제 부팅까지) |

3사 공통 사다리:
1. 원본 준비 — 플랫폼 이미지로 디스크 생성(azure는 VM의 OS 디스크,
   gcp/aws는 이미지에서 디스크/인스턴스).
2. **허상 원본으로 이미지 생성 → 거부 코드** (존재 판정의 음성)
3. 실제 원본으로 이미지 생성 → 성공 (양성 대조)
4. **이미지 존재 중 원본 디스크 삭제 시도** → 거부/허용 관측 (생명주기)
5. 정리 — 이미지 삭제 후 원본 삭제(4가 거부였다면 양성 대조가 된다)

aws는 EBS 스냅샷 기반이라 이미지(AMI) 생성이 인스턴스/볼륨에서 나온다 —
`create-image`(인스턴스에서) 경로를 쓰고, "원본"은 인스턴스의 루트 볼륨이
된다. 그 차이(원본이 디스크가 아니라 인스턴스)는 판정에 적는다.

## 예상과 위협

가설: 이미지는 스냅샷 복사본을 갖게 되므로 원본 삭제가 **허용**될 것이다
(생명주기 결속 없음). 하지만 azure는 관리 이미지가 원본 디스크를 참조로
붙잡을 수 있다 — graphkb 관측이 그 방향이었다. 가설은 실측으로만 판정에
들어간다. 결속이 없으면 그것도 판정이다(`optional`이 아니라 lifecycle
행 자체를 안 만든다 — 없는 결속을 적지 않는다).

- **T-비동기**: 이미지 생성은 수 분. 완료 폴링 필수.
- **T-vm 부팅 확인 범위**: VM이 서는지(provisioning 성공)까지만 본다 —
  게스트 안 확인은 이 라운드 밖.
- aws AMI 삭제는 등록 해제(deregister) + 스냅샷 삭제 둘이다 — 잔여 0
  점검에 스냅샷을 포함한다(놓치면 조용히 남는다).

비용: azure VM 1대 + 이미지 · gcp 디스크+이미지 · aws t3.micro+AMI.
전부 수 분. 리전 계승. 라운드 끝 3사 전수 점검(스냅샷 포함).
