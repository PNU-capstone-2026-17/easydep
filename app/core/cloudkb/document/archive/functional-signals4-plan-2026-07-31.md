# 기능 신호 4종 계획 — 앱 없이 (2026-07-31, 실행 전 기록)

## 왜 앱을 안 쓰나 (설계 결정)

기능 축의 신호가 외부 TCP 도달성 하나뿐이라는 것이 위협 ④다. 신호를 늘리는
방법으로 **샘플 애플리케이션**을 도입할 수 있지만 쓰지 않는다:

- 앱을 기준으로 삼으면 주장이 *"B를 떼면 A의 기능이 깨진다"*에서 *"이 앱의
  이 동작이 깨진다"*로 좁아지고, 앱의 언어·프레임워크·설정이 전부 교란
  변수가 된다. 지금 112주장이 앱 독립이라 3사 비교가 성립한다.
- **한 번에 한 축만 흔든다**(§2 규율)와 정면으로 부딪힌다.

대신 **기능 종류(capability)**를 축으로 잡고 각각에 **최소 관측자**를 정한다.
앱은 최소 관측자를 만들 수 없을 때만 도입한다(이번 넷은 전부 불필요).

## 공통 투자 — SSH 게스트 실행 하네스

넷 다 게스트 안에서 봐야 한다(DNS 질의·파일 쓰기·아웃바운드·IMDS). 그래서
이 라운드의 실제 비용은 신호가 아니라 **하네스**다:

| CSP | 키 주입 | 접속 |
| --- | --- | --- |
| azure | `az vm create --generate-ssh-keys`(기존 경로) | `ssh -i ~/.ssh/id_rsa` |
| aws | `create-key-pair` → pem 파일(gitignore) | `ssh -i <pem>` |
| gcp | 인스턴스 메타데이터 `ssh-keys` | `ssh -i <key>` |

**게스트 명령은 OS 기본 도구만 쓴다** — `getent hosts`·`dd`·`curl`·`mount`.
설치가 필요하면 그건 앱이고, 이 라운드의 전제가 깨진다.

원격 실행 자체가 실패할 수 있으므로 **기준선(F1)에서 명령이 도는 것을 먼저
확인**한다. F1이 실패하면 판정 불가로 중단하고 그대로 기록한다.

## 셀 — 신호 × 겨누는 간선

| 신호 | 최소 관측자 | 겨누는 간선 | CSP |
| --- | --- | --- | --- |
| **DNS 해석** | `getent hosts <사설이름>` | `globalDns→network`(영역-네트워크 연결) | azure(vnet link) · gcp(privateVisibility) · aws(VPC association) |
| **볼륨 I/O** | 마운트 후 `dd`로 쓰기·읽기 | `vm→disk` | azure · gcp (aws는 EBS detach) |
| **아웃바운드** | `curl -s -o /dev/null -w %{http_code}` | `subnet→internetGateway`(aws) · `network→라우트`(gcp) | aws · gcp |
| **메타데이터** | `curl 169.254.169.254`로 토큰 획득 | `vm→iamRole` | aws(인스턴스 프로필) · gcp(SA) |

각 셀은 기존 인과 사다리를 그대로 쓴다: 기능 확인 → 변이 성공(무방비) →
상실 → 복원 → 회복.

## 예상되는 함정

- **캐시**: DNS는 게스트가 캐싱할 수 있다 — `getent`는 nscd가 없으면 매번
  질의하지만, 상실 관측은 연속 2회로 강화한다.
- **detach 중 게스트 상태**: 디스크를 떼면 파일시스템이 오류 상태가 된다.
  재부착 후 회복 관측은 **재마운트를 포함**해야 한다(운영 절차이지 판정
  대상이 아님을 명시).
- **IMDS 전파**: 인스턴스 프로필 분리는 즉시 반영되지 않을 수 있다 —
  EKS IAM 라운드에서 비동기 때문에 판정을 놓쳤다(§4-2). 상실 관측 시한을
  넉넉히 두고, 시한 내 미상실이면 **미판정**으로 적는다.
- **azure defaultOutboundAccess**: 신규 서브넷은 기본 아웃바운드가 꺼져
  있다(func2에서 관측) — azure 아웃바운드 셀은 그 자체가 교란이라 뺀다.

비용: VM 3대 × 각 10~20분. 리전 계승. 라운드 끝 3사 전수 점검.
