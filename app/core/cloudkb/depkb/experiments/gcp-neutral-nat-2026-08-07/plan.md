# GCP 중립 NAT 제어 평면 실험(사전 등록)

## 질문

VM이 없는 경우에도 GCP는 중립 개념인 `private outbound NAT`를 커스텀 VPC 네트워크, 리전 서브네트워크, Cloud Router, 예약된 리전 외부 주소, Cloud NAT 구성으로 이루어진 수명 주기 의존적 조합으로 구현하는가?

이 실험은 제어 평면의 요청 수용 여부와 의존성 동작만 측정한다. 데이터 평면의 외부 통신은 시험하지 않으며 VM도 생성하지 않는다. P1-P3 및 그 밖의 이전 평가 산출물은 입력으로 사용하지 않는다.

## 고정 절차

- `--project`/`GOOGLE_CLOUD_PROJECT`로 지정한 프로젝트를 사용하고, 지정하지 않으면 활성 `gcloud` 프로젝트를 사용한다. 기본 리전은 `asia-northeast3`이며 변경할 수 있다.
- 고유한 `ed-nat-<UTC timestamp>-<random>` 접두사를 생성한다. 커스텀 모드 네트워크, `/28` 리전 서브넷 하나, 리전 Cloud Router 하나, 예약된 리전 외부 주소 하나를 차례로 생성한 뒤 해당 라우터에 연결된 Cloud NAT 하나를 생성한다.
- 실험 서브넷에만 NAT를 구성하고 예약 주소(`MANUAL_ONLY`)를 사용한다. 엔드포인트 독립 매핑이나 로깅을 명시적으로 활성화하지 않고, `describe` 결과에 달리 나타나지 않는 한 서비스 기본값을 유지한다.
- 생성 후 네트워크, 서브넷, 라우터, 주소, NAT를 조회한다. 비식별화하고 길이를 제한한 JSON 일부만 보존한다.
- 반사실 조건: NAT 구성이 존재하는 동안 라우터 삭제를 요청한다. 예상 결과는 0이 아닌 의존성/구성 거부 응답이며 라우터/NAT는 계속 조회할 수 있어야 한다. 예상과 달리 성공하면 이를 기록하고 정리 절차를 조정하며, 증거를 만들기 위한 재시도는 하지 않는다.
- 의존성의 역순인 NAT 구성, 주소, 라우터, 서브넷, 네트워크 순으로 정리한다. 그 후 다섯 리소스 종류를 모두 조회하고 정확히 같은 이름의 잔존 리소스를 보고한다.

## 실행 전 등록한 해석 기준

- VM 없이 NAT 생성과 조회에 성공하면 Cloud NAT가 VM에 연결되는 리소스가 아니라 제어 평면의 조합이라는 주장을 뒷받침한다.
- NAT가 존재할 때 라우터 삭제가 거부되면 라우터와 NAT 사이의 수명 주기 의존성을 뒷받침한다. 삭제가 수용되면 해당 의존성 예상은 반증되지만, 그것만으로 조합 구조까지 부정되지는 않는다.
- 예약 주소가 수동 NAT 풀로 수용되면 이 조합에 명시적인 공인 주소 연결 관계가 있음을 뒷받침한다.
- 인증, 권한 부여, 할당량, 비활성화된 API, 조직 정책 또는 리전 가용성 때문에 생성에 실패한 경우 결론을 내리지 않는다. 오류 코드/범주는 보존한다.
- 정리 실패로부터 의미론적 결론을 도출하지 않는다. 잔존 리소스는 즉시 수동 정리가 필요한 운영상 발견 사항이다.

## 안전 및 기록

실행기는 `--execute`를 필수로 요구하고 `gcloud` 인증/프로젝트 상태를 확인하며, 정확히 생성된 이름만 사용하고 `finally`에서 최선 노력 방식으로 정리한다. 자격 증명 자료는 읽거나 쓰지 않는다. `results.json`에는 UTC 타임스탬프, 명령 종료 코드, 분류된 오류, 비식별화한 일부 결과를 기록하며 프로젝트 ID, 계정 이름, 액세스 토큰, 외부 IP, 생성된 접미사는 가린다. Cloud Router, Cloud NAT 및 예약 주소에는 비용이 발생할 수 있으므로 리소스는 이 짧은 실행 동안만 존재하도록 한다.
