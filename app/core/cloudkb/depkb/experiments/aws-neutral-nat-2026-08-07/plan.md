# AWS 퍼블릭 NAT 게이트웨이 제어면 실험

상태: 사전 등록됨. 이 문서를 결과로 간주하지 않는다.

## 질문

VM 없이 퍼블릭 NAT 게이트웨이를 구성할 때 어떤 AWS 리소스와 수명 주기 제약을 관찰할 수 있는가?

이 실험은 VPC, 퍼블릭 서브넷, 연결된 인터넷 게이트웨이, 명시적인 라우팅 테이블 연결과 기본 경로, Elastic IP 할당, 퍼블릭 NAT 게이트웨이를 생성한다. 공급자가 반환한 식별자와 상태 및 정확한 AWS 오류 코드를 관찰한다. P1-P3을 사용하지 않으며 중립 모델 매핑이 옳다고 가정하지 않는다.

## 절차

1. 실행마다 고유한 `depkb-nat-<UTC timestamp>-<random>` 접두사를 생성하고 태그를 지원하는 모든 리소스에 이 값을 태그로 지정한다.
2. 선택한 리전에서 사용 가능한 첫 번째 가용 영역에 `10.97.0.0/16` VPC와 `10.97.1.0/24` 서브넷을 생성한다.
3. 인터넷 게이트웨이를 생성하고 연결한다.
4. 라우팅 테이블을 생성하여 서브넷에 연결하고 인터넷 게이트웨이를 통한 `0.0.0.0/0` 경로를 추가한다.
5. VPC 도메인의 Elastic IP를 할당하고 이를 사용하는 퍼블릭 NAT 게이트웨이를 생성한다.
6. NAT 게이트웨이가 `available` 상태가 되거나 종료/시간 초과 조건에 이를 때까지 폴링한다.
7. 사용 가능한 상태가 되면 실패할 것으로 예상되는 두 가지 반사실 연산, 즉 연결된 Elastic IP 해제와 NAT를 포함하는 서브넷 삭제를 시도한다. 정확한 응답을 기록하며, 예상 밖의 성공을 가설의 확인으로 해석하지 않는다.
8. `finally`에서 NAT 게이트웨이를 삭제하고 삭제 완료를 기다린 다음, 의존성의 역순으로 정리한다. 존재하지 않거나 일부만 생성된 리소스도 허용한다.
9. 태그가 지정된 리소스와 알려진 ID를 조회하고 잔존 리소스를 기록한다.

## 사전 등록된 해석

- NAT 생성에 성공하고 `available` 상태에 도달하면, 이번 실행의 AWS 제어면이 조합된 리소스를 수용했다는 증거다.
- 반사실 연산에서 발생한 서버 측 오류 코드는 관찰한 상태에서 해당 연산이 거부되었다는 증거일 뿐이다. 클라이언트 측 검증, 권한 부여 실패, 스로틀링, 시간 초과 또는 할당량 오류로는 수명 주기 제약을 판단할 수 없다.
- 정리 결과와 잔존 리소스 조회는 운영상의 증거이지, 모든 곳에 리소스가 없다는 증명은 아니다. 잔존 ID가 있으면 즉시 조사하여 제거해야 한다.
- 실패했거나 일부만 완료된 실행도 원시 응답과 정리 결과를 보존하면 유용하다. 같은 실행인 것처럼 조용히 재시도해서는 안 된다.

## 안전, 비용 및 실행 방법

NAT 게이트웨이와 퍼블릭 IPv4 할당에는 비용이 발생할 수 있다. 권한이 있는 일회용 계정에서만 실행하고 정리 과정을 모니터링한다. VM이나 트래픽 워크로드는 생성하지 않는다. 자격 증명은 설치된 AWS CLI 설정을 통해서만 읽는다. 실험 디렉터리에는 자격 증명을 기록하지 않는다.

기본 리전은 `ap-northeast-2`이며 `--region` 또는 `AWS_REGION`으로 재정의할 수 있다. 스크립트는 같은 디렉터리에 `results.json`을 기록하며, `--output`으로 다른 위치를 지정하지 않으면 기존 결과를 덮어쓰지 않는다.

```powershell
python run.py --execute --region ap-northeast-2
```
