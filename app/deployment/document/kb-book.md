# 클라우드 지식베이스 만들기 — 처음부터 끝까지

이 문서 하나만 읽고도 **같은 것을 처음부터 다시 만들 수 있게** 쓴 글입니다.
클라우드를 잘 몰라도 읽을 수 있게 용어를 그때그때 풀어 씁니다.

> **읽는 순서 안내**
> 0장은 용어표입니다. 1부(1~3장)는 "왜 이런 게 필요한가"입니다. 급하면
> 3장(전체 지도)부터 읽어도 됩니다 — 그 안의 **커버리지 격자**가 "어느 클라우드의
> 무엇까지 답할 수 있나"의 지도입니다. 각 축의 속사정은 3부(5~11장), 믿을 수 있게
> 만드는 장치는 4부(12~17장)에 있습니다. 실제로 만들려면 18장(재현 절차)으로
> 가세요. 19장(함정 모음)은 **직접 겪은 실패**만 모은 곳이라, 만들 사람에게
> 가장 값이 클 겁니다.
>
> **이 작업을 심사·평가하는 사람**이라면 순서가 다릅니다: 16장 머리(**왜 이
> 소스들인가** — 선정 절차와 포화 기준) → 22장(**타당성 위협**) → 23장(**외부
> 표준 매핑**, 표준에 있는데 우리에게 없는 칸 포함). 이 셋이 "돌아간다"가 아니라
> "근거가 선다"를 묻는 자리입니다.
>
> 본문은 원리를 말하고 예시를 아낍니다. **실제 출력이 어떻게 생겼는지**가
> 필요하면 **부록 A(실물 예시)**로 가세요 — 본문의 규율 하나하나가 실제로 어떤
> 문장이 되어 나오는지를, 코드를 돌려 받은 답 그대로 실었습니다.
>
> 이 문서의 수치는 별도 표기가 없으면 **2026-07-24에 코드와 데이터에서 다시 뽑은
> 실측값**입니다. 수치는 데이터와 함께 늙으므로, 현재값이 필요하면 문서가 아니라
> 코드를 돌리세요(18장). 이건 이 저장소의 문서 정책이기도 합니다 — **변하는
> 숫자의 집은 코드이고, 문서에는 이야기와 원리를 둔다.**

## 0. 먼저 알아야 할 말 몇 개

이 문서는 되도록 평범한 말로 씁니다. 다만 **코드에 실제로 그 이름으로 들어 있는
것**은 바꿔 쓸 수 없어서 그대로 둡니다.

| 말 | 뜻 | 예 |
|---|---|---|
| **리소스** | 클라우드에서 만드는 것 하나 | 가상 서버, 네트워크, 디스크 |
| **타입** | 리소스의 종류 | `AWS::EC2::Instance`(아마존 가상 서버) |
| **속성** | 리소스에 채워 넣는 칸 | 디스크의 `Size`, 서버의 `InstanceType` |
| **스키마** | 회사가 공개한 설명서 파일. "이 타입에는 이런 속성이 있고, 이 속성은 숫자이며 최댓값은 얼마"가 적혀 있다 | |
| **레코드** | 우리가 저장하는 **사실 한 줄** | "gp2 디스크의 최대 크기는 16,384 GiB다" |
| **제약** | 값에 걸린 조건 한 줄 (레코드의 한 종류) | 최소·최대·허용 목록·못 바꿈 |
| **`evidence`** | 그 레코드가 **어느 소스의 무엇**에서 나왔는지 적는 칸 | `cfn-schema` |
| **`basis`** | 원본이 **그렇게 말한 것**(`stated`)인지, 우리가 **짐작한 것**(`inferred`)인지, 코퍼스에서 **세어 본 것**(`observed`)인지 | |
| **관리형 서비스** | 서버를 직접 안 띄우고 회사가 대신 운영해 주는 것 | 관리형 데이터베이스(RDS), 관리형 캐시(Redis) |
| **아키타입** | 관리형 서비스의 회사 무관 분류 | `relationalDatabase`, `cache`, `queue` |
| **미러** | 다른 오픈소스가 배포하는 데이터를 **그대로 베낀 사본** | CB-Tumblebug의 스펙·가격 데이터 |
| **advisory(자문)** | 사실이 아니라 **지침**으로만 쓰는 지식. 답변에 항상 "지침이지 사실 아님" 딱지가 붙는다 | 설계 패턴 문서 |

그리고 자주 나오는 표현 셋을 미리 풀어 둡니다.

- **원본 / 상류** — 우리가 가져다 쓰는 클라우드 회사의 공개 파일. 우리가 만든 게
  아니라 저쪽이 만든 것.
- **결과 파일(산출물)** — 우리 프로그램이 만들어 저장하는 JSON 파일.
- **직접 재 봤다(실측)** — 추측이 아니라 실제로 프로그램을 돌려 숫자를 세어 봤다는 뜻.

# 1부 — 왜와 원칙

## 1. 무엇을 만들려는 건가

클라우드에 서비스를 올리려면 여러 **리소스**를 순서대로 만들어야 합니다. 문제는
이것들이 서로 얽혀 있다는 점입니다.

- 가상 서버를 만들려면 먼저 네트워크가 있어야 합니다.
- 디스크는 크기에 상한이 있는데, **디스크 종류마다 상한이 다릅니다.**
- 어떤 설정값은 한 번 정하면 **영영 못 바꿉니다.** 바꾸려면 리소스를 지우고 새로
  만들어야 하고, 그러면 그 안의 데이터가 사라질 수 있습니다.

사람이 이걸 다 외울 수 없어서 AI 에이전트에게 맡깁니다. 그런데 **AI는 그럴듯한
거짓말을 합니다.** "EBS 디스크는 최대 16TB입니다" 같은 말을 자신 있게 하는데,
그게 어제까지는 맞았고 오늘은 틀릴 수 있습니다.

그래서 **에이전트가 참고할 사실 창고**를 따로 만듭니다. 그게 이 지식베이스(KB)입니다.

### 하는 일이 셋으로 자랐습니다

처음에는 "리소스에 대한 질문에 답하기" 하나였는데, 지금은 셋입니다.

1. **리소스 자문** — "이 디스크 최대 몇 GiB야?", "이 인스턴스 GPU 뭐 달렸어?",
   "이 둘 중 뭐가 싸?" 같은 질문에 **검증된 데이터**로 답한다.
2. **가이드라인** — 배포 설계가 알려진 요구·제약·지침과 부합하는지 **판정**한다.
   여기엔 사실 판정(예산 하한 초과)과 자문 인용(설계 패턴)이 구분돼 들어간다.
3. **설계도 → 배포 계획** — 앱 설계 JSON을 받아 배포 다이어그램과 리소스 명세를
   **근거를 달아** 만들어 낸다. 외부 팀(easydep)의 설계 에이전트가 만든 산출물이
   여기 꽂힌다.

### 이 프로젝트가 막으려는 단 하나

> **확신에 찬 오답.**

틀린 답보다 나쁜 것은 **틀린 답에 우리 보증이 찍혀 나가는 것**입니다. 사용자가
"이건 검증된 데이터겠지" 하고 믿는데 사실은 AI가 지어낸 것이라면, 지식베이스가
없느니만 못합니다.

아래 모든 설계 결정이 이 한 문장에서 나옵니다.

## 2. 기본 원칙 — 둘, 그리고 거기서 자란 규율들

### 원칙 1 — 확실하지 않으면 막지 마라

확실하지 않으면 **막지 않습니다.** 우리가 모른다고 해서 사용자가 못 하게 하면
안 됩니다.

단, 여기 함정이 있습니다.

> **침묵이 "문제 없음"으로 읽히면 안 됩니다.**

"제약이 없습니다"와 "우리가 안 봤습니다"는 **전혀 다른 말**인데, 아무 말도 안 하면
둘이 똑같아 보입니다. 실제로 우리 KB가 구글 리소스 527종 전부에 "제약 없음"이라고
답한 적이 있습니다 — 사실은 구글 데이터를 **읽지도 않은** 상태였습니다.

이 원칙은 "짐작으로 막지 마라"이지 **"짐작을 숨겨라"가 아닙니다.**
(영어 문헌에서는 이런 태도를 *fail-open*이라고 부릅니다.)

### 원칙 2 — 데이터가 먼저

목표는 **완벽한 데이터셋**이지 완벽한 파서(추출 프로그램)가 아닙니다.

근거가 있습니다. dbt라는 회사가 통제 실험을 공개했는데, AI에게 데이터베이스 질문을
시켰을 때 정답률이 이렇게 나왔습니다.

| 조건 | 정답률 |
|---|---|
| 원시 스키마 그대로 | 64.5% |
| **데이터를 잘 정리한 뒤** | **90.0%** |
| 그 위에 질의 계층까지 얹은 뒤 | 98.2% |

**64.5 → 90이 데이터 정리의 몫**이고, 인터페이스를 아무리 다듬어도 마지막 8점입니다.
그래서 우리는 도구를 예쁘게 만드는 것보다 데이터를 늘리고 고치는 데 시간을 씁니다.

### 두 원칙에서 자란 작업 규율

만들면서 반복해서 확인된 것들이라, 이제는 규율로 지킵니다. 각각의 사연은
해당 장에 있습니다.

| 규율 | 한 줄 요약 | 어디서 |
|---|---|---|
| **모르면 모른다** | 부재를 안전·최신·허용으로 승격하지 않는다 | 5·8장 |
| **합계를 내지 않는다** | 부분만 아는 값들의 합은 거짓 총액이다 | 7·11장 |
| **비대칭을 대칭으로 옮기지 않는다** | 원본 필드가 한 방향만 말하면 반대 방향은 우리 추론이다 | 12장 |
| **실측 전 착수 금지** | 소스가 그 값을 정말 주는지 세어 보기 전엔 파서를 안 짠다 | 16장 |
| **이미 받은 소스의 안 쓰는 부분부터** | 새 소스 추가보다 기존 핀 안의 미사용 파일이 싸고 안전하다 | 16장 |
| **기대를 먼저 의심하라** | 검사가 실패하면 시스템보다 검사 기대부터 본다 | 15장 |
| **규약은 검사로** | 지키고 싶은 규약은 문서가 아니라 테스트로 만든다 | 15장 |
| **재조사 금지 기록** | 기각한 후보는 이유와 함께 남겨 같은 조사를 반복하지 않는다 | 20장 |

## 3. 지식의 축 — 전체 지도

한 덩어리로 만들면 "무엇을 모르는지"를 알 수 없습니다. 축을 나누면 각 축이 자기
**무엇까지 훑었는지(수집 범위)**를 스스로 말할 수 있습니다.

창립 축은 넷이었고, 이후 같은 규율(소스 핀 → 파서 → 산출물 → 불변식 → 검사)로
축이 자랐습니다. 현재 패키지 지도입니다.

| 패키지 | 답하는 질문 | 비유 | 규모(2026-07-24 실측) |
|---|---|---|---|
| **graphkb** | 무엇이 무엇을 필요로 하나 + 회사 간 대응 | 부품 조립 순서도 | 노드 10,157(10개 CSP) · 엣지 6,548(**3개 CSP만** — 아래 격자) |
| **capacitykb** | 무엇이 허용되나 · 한도 · 바꿀 수 있나 | 부품 규격서 | 제약 141,377건 (**10개** 클라우드) |
| **costkb** | 무엇을 살 수 있고 얼마인가 | 가격표 | 스펙 73,083 + 할인 32,073 + 스팟/약정 11,193 + 관리형 24,294 |
| **perfkb** | 얼마나 빠른가 · 함정은 없나 | 성능 시험 성적서 | 신호 65,032 + IBM 2,002 |

**엣지가 aws·azure·gcp에만 있습니다.** 나머지 일곱은 Terraform provider 스키마에서
타입은 뽑았지만 **관계를 뽑는 경로가 아직 없습니다.** 이건 결함이 아니라 **비어

가장 오해하기 쉬운 칸은 **oracle**입니다 — 제약이 14,614건(전체 3위)인데 가격도
성능도 관계도 0입니다. "지원 클라우드 목록에 이름이 있다"와 "그 클라우드 질문에
답할 수 있다"는 다른 말입니다.

> 이 격자를 3장에 두는 이유: **"무엇을 모르는지 말할 수 있게" 축을 나눴다면, 그
> 말을 표로도 해야 합니다.** 축별 수집 범위 고지가 답변마다 붙지만(13장), 문서를
> 읽는 사람은 답변을 보기 전에 이 지도를 봅니다.

**중요한 규약이 하나 있습니다.**

```
에이전트 → KB   (한 방향으로만)
KB ↛ KB         (지식베이스끼리는 서로 부르지 않는다)
KB → kbcommon   (공용 규율만 아래로)
```

축끼리 직접 부르면 순환이 생기고, 한 축의 결함이 다른 축으로 번집니다. 축을 합쳐야
하는 일(예: 추천 목록에 성능 경고 붙이기, 설계도에 가격 달기)은 **도구 계층**
(`nim_agent/`)에서 합니다. 이 규약은 문서가 아니라 **테스트가 지킵니다** —
`tests/test_architecture.py`가 전 소스 파일의 import를 검사해서, KB 패키지가
kbcommon 밖을 부르면 빌드가 빨갛게 됩니다.

### 축이 자란 순서 (왜 이 모양이 됐나)

1. **창립 4축** (graph·capacity·cost·perf) — "리소스 질문에 답하기".
2. **bundlekb·sizingkb** — 실측에서 "만들 수 있다"와 "실제로 쓸 수 있다"의 간극이
   드러남. 리소스 하나가 아니라 **동반 리소스와 최소 규모**까지 알아야 했다.
3. **envkb** — 리전·탄소·지연은 리소스가 아니라 **환경**의 사실이라 축이 다르다.
4. **12개 클라우드 확장** — 미러가 다루는 CSP 전부로 그래프·제약을 넓힘.
   소스가 없는 곳은 Terraform provider가 유일한 경로였다(16장).
5. **appkb + svcmap** — "설계도를 받아 배포 계획을 내라"는 요구(목표 3). 설계
   개념(`app::queue`)과 회사 타입을 잇는 svcmap 층이 graphkb에 생겼다.
6. **patternkb** — 수치로 환원되지 않는 설계 지침을 **자문 전용**으로 수록.
7. **관리형 과금 축** — "관리형 데이터베이스는 얼마?"가 인스턴스 가격과 전혀
   다른 구조임이 조사로 드러나 costkb가 확장됐다(7장).

# 2부 — 데이터가 지나는 길

## 4. 파이프라인 — 소스에서 도구까지 8단계

```
 ① 소스            ② 핀            ③ 파서           ④ 쓰기 전 검사  ⑤ 결과 파일
공개 스키마  →  버전 고정  →  레코드로 변환  →  쓰기 관문  →  JSON (+gz 커밋)
                                                                      │
                                       ⑧ 도구  ←  ⑦ 표시  ←  ⑥ 질의 ─┘
```

### ① 소스 — 어디서 가져오나

**사람이 읽는 문서를 긁지 않습니다.** 클라우드 회사들이 **기계가 읽으라고 공개한
스키마**를 씁니다. 문서는 사람이 쓰고 사람이 고치므로 표현이 제각각이고 자주
틀립니다. 스키마는 회사의 배포 시스템이 실제로 쓰는 것이라 **틀리면 그 회사가
먼저 아픕니다.**

이 원칙에 예외가 정확히 세 부류 있고, 전부 이유가 기록돼 있습니다.

- **표만 뽑는 문서** — Azure VM 크기 문서(8장), Azure 한도 문서. 산문이 아니라
  **표의 칸**만 읽고, 산문 추출의 함정(19장)을 규칙으로 막는다.
- **자문 전용 산문** — patternkb의 지침 문서(10장). 애초에 사실 축으로 안 쓴다.
- **렌더링된 HTML 1건** — GCP Architecture Framework(10장). 저장소가 없어서
  웹페이지를 받되, **자문 전용이므로** 허용했다. 사실 축에 이 소스를 쓰면 안 된다.

### ② 핀 — 버전을 못 박는다

**이게 없으면 나머지가 전부 흔들립니다.**

소스는 계속 바뀝니다. 오늘 "제약 47,070건"을 뽑았는데 내일 다시 돌려서 47,109건이
나오면, **우리가 고친 건지 원본이 바뀐 건지 알 수 없습니다.** 사람이 손으로 검수한
결과가 다음 빌드에서도 유효한지도 말할 수 없습니다.

그래서 소스마다 "정확히 이 버전"을 박아 둡니다. 네 가지 방식이 있습니다.

| 방식 | 뜻 | 예 |
|---|---|---|
| `tag` | 저장소가 붙인 버전 태그 | cb-tumblebug `v0.12.25` |
| `commit` | 태그가 쓸모없을 때 커밋 고유번호 | bicep-types-az `ef7421bb…` |
| `digest` | **버전 개념이 아예 없는 소스** — 받은 파일의 지문(sha256)만 기록 | AWS CloudFormation zip, Azure 소매가 API |
| `bundled` | 우리 저장소 안의 파일 (사람 검수표) | 매핑표 |

`digest`가 정직한 항복입니다. AWS는 스키마 zip 파일 **하나를 계속 덮어씁니다.**
고정할 URL이 없습니다. 그래서 받은 파일의 지문을 기록해 두고, 다음에 달라지면
**알립니다.** 재현은 못 해도 **바뀐 사실은 놓치지 않습니다.**

> 효과가 실측으로 확인됐습니다. 재빌드했을 때 고정된 소스는 결과가 **완전히
> 동일**했고, **고정 불가능한 AWS만** 46,810 → 47,109로 변했습니다. 핀이 실제로
> 작동한다는 증거이자, AWS는 원리적으로 재현이 안 된다는 증거이기도 합니다.

현재 핀 46종의 전체 목록과 각각의 사연은 16장에 있습니다.

### ③ 파서 — 스키마를 레코드로

파서는 스키마 파일을 읽어 **레코드 한 줄씩** 만듭니다. 레코드는 "사실 하나"이고,
반드시 `evidence`(어디서)와 `basis`(원본이 말한 건가)를 달고 나옵니다.

파서에 관한 태도 하나가 중요합니다. **핀을 박았으므로 예외는 손 검수로 처리해도
됩니다.** 소스가 고정돼 있으면 "이 파일의 이 줄만 이상하다"가 재현 가능한
사실이 되므로, 파서를 무한히 정교하게 만드는 대신 예외 목록을 사람이 확인하고
기록하는 쪽이 쌉니다. 목표는 완벽한 데이터셋이지 완벽한 파서가 아니기 때문입니다.

### ④ 쓰기 전 검사 — 저장하기 직전의 관문

레코드 하나하나는 멀쩡한데 **여러 줄이 모이면 모순**인 경우가 있습니다.

```
기본값 = 0        ← 한 줄
최솟값 = 10       ← 다른 줄
```

각각은 문법에 맞지만 함께 보면 말이 안 됩니다. 스키마 검사는 **한 줄의 모양만**
보므로 이걸 못 잡습니다. 그래서 파일을 쓰기 **직전에** 레코드 사이의 관계를
검사하는 층(불변식)을 뒀습니다.

심각도가 둘입니다.

- **`error`** — 우리 잘못이고 고칠 수 있다 → **파일을 아예 쓰지 않는다**
- **`report`** — 우리 권한 밖(상류가 그렇다) → 쓰되 **건수를 반드시 말한다**

전부 `error`로 만들지 않은 이유: 그러면 **원본을 그대로 베낀 사본을 만들 수
없습니다.** costkb가 하는 일이 바로 그것인데, 원본이 모순이라고 우리가 값을 고치면
그 순간 사본이 아니게 됩니다.

대표 검사 규칙 (전체는 `kbcommon/invariants.py`가 진실):

| 이름 | 무엇을 막나 |
|---|---|
| `default-within-bounds` | 기본값이 자기 최소/최대를 위반 |
| `read-only-not-required` | 읽기 전용인데 "네가 채워라"라고 표시 |
| `one-basis-per-evidence` | 근거 라벨 하나가 두 성격(사실/짐작)을 겸함 |
| `no-casing-duplicate-ids` | 대소문자만 다른 같은 타입이 둘로 존재 |
| `edges-point-at-real-nodes` | 관계가 없는 리소스를 가리킴 |
| `region-invariant-signals` | "리전 불변"이라는 **가정을 매번 검사** |
| `accelerator-fields-agree` | GPU가 있다는데 개수가 0 |
| `disk-size-zero-is-ambiguous` | (report) 0이 사실인지 미기입인지 못 가림 |

### ⑤ 결과 파일 — 그리고 커밋된 사본

산출물은 `output/`의 JSON 파일입니다. 파일마다 `_source` 블록이 들어가서 **어느
소스 어느 버전에서 나왔는지가 파일 안에 남습니다.**

```json
{"source": "cfn-lint", "pin_kind": "tag", "pin": "1.53.1",
 "sha256": "0df021a3…", "bytes": 5083662, "fetched_at": "2026-07-21T13:50:23+00:00"}
```

그리고 산출물을 gzip해 저장소에 커밋합니다(`data/*.gz`, 56개 파일 · 약 9MB).
클론 직후 **빌드 없이 동작**하는 이유입니다. 읽기 우선순위는

```
output/  (새로 빌드한 것)  →  data/*.gz  (커밋된 것)
```

포장은 `python -m kbcommon pack <파일>`이 합니다. 이 명령에는 **거부 목록**이
있습니다 — AWS 관리형 가격 산출물은 재배포가 금지라(17장) pack이 이름을 보고
거절합니다. "커밋하지 마세요"라는 주석 대신 **커밋이 안 되는 구조**를 만든 것입니다.

### ⑥~⑧ 질의 → 표시 → 도구

질의 계층이 산출물을 읽어 **사람이 읽을 한국어 문장**을 만들고(현재 한국어 —
영어 전환이 예정돼 있습니다, 21장), 도구 계층이 에이전트에게 노출합니다.
자세한 것은 13장에서 다룹니다.

# 3부 — 축 하나씩

## 5. graphkb — 무엇이 무엇을 필요로 하나

**3계층 구조**입니다.

```
공통 층   (회사 무관)     vm, vNet, subnet …  13종  +  app:: 설계 개념 13종
   ↕ 매핑 레이어 (동치 관계)
회사별 층  aws 1,638종 · azure 3,382종 · gcp 527종 · 그 외 9개 클라우드
```

공통 층은 CB-Tumblebug이라는 오픈소스의 모델에서 가져옵니다. 다루는 범위는 좁지만
**정확하고 특정 회사에 매이지 않아** "AWS의 이것이 Azure에선 무엇인가"를 잇는
기준점이 됩니다.

**레코드 예시** (실제 데이터):

```json
{
  "from": "aws::AWS::ACMPCA::Certificate",
  "to":   "aws::AWS::ACMPCA::CertificateAuthority",
  "type": "references",
  "via_property": "CertificateAuthorityArn",
  "required": true,
  "cardinality": "one",
  "evidence": "cdk-oob",
  "basis": "stated",
  "reviewed": true
}
```

읽는 법: "인증서는 인증기관을 **참조한다**. `CertificateAuthorityArn`이라는 칸을
통해서다. **필수**이고 하나만 가리킨다. 근거는 AWS CDK가 배포하는 관계표이고,
원본이 그렇게 **말한 것**이며, 사람이 검수까지 했다."

관계 종류는 셋입니다.

- `references` — 참조한다 (A가 B의 id를 자기 칸에 적는다)
- `contained_in` — 담겨 있다 (B 안에 A가 산다)
- `equivalent_to` — 같은 것이다 (클라우드 회사가 달라도 같은 개념)

### 필수성은 조상과의 논리곱이다 ★

여기가 **가장 틀리기 쉬운 곳**입니다. 실제로 우리가 틀렸었습니다.

스키마에서 "이 칸은 필수"라는 표시는 **그 칸이 속한 부모 객체 안에서만** 필수라는
뜻입니다. 부모 자체가 선택이면 전체적으로는 선택입니다.

```
properties
└ storageProfile
  └ osDisk
    └ encryptionSettings          ← 선택 (디스크 암호화를 안 쓸 수 있다)
      └ diskEncryptionKey
        └ sourceVault  ← "필수"    ← 암호화를 쓴다면 필수라는 뜻
```

이걸 그대로 리소스 필수로 끌어올렸더니 이런 답이 나왔습니다.

> "Azure 가상머신을 만들려면 **KeyVault**가 먼저 있어야 합니다."
> (네트워크 인터페이스는 **선택**으로 표시)

**정확히 거꾸로**입니다. 올바른 규칙: **경로상 모든 조상이 필수일 때만 리소스에
필수.** 고친 뒤 오염된 타입이 59종 → 25종이 됐습니다.

### 필수 표시가 없다고 "바로 만들어도 된다"고 하지 마라 ★

위를 고쳤더니 이번엔 **반대 방향 거짓말**이 나왔습니다.

> "반드시 먼저 만들어야 하는 선행 리소스가 없습니다. **바로 생성할 수 있습니다.**"

Azure 가상머신은 네트워크 인터페이스 없이 못 만듭니다. 스키마가 그걸 필수로 표시하지
않을 뿐입니다. **스키마의 필수 표시와 실제 배포 요건은 다릅니다.** 말하지 않는 것을
허가로 바꾸면, 막지 않는 게 아니라 그냥 틀린 말이 됩니다. 지금은 이렇게 답합니다.

> "스키마가 **필수로 표시한** 선행 리소스가 없다는 뜻이며, 실제로 아무것도 필요
> 없다는 뜻이 아닙니다."

### AWS의 "담김" 축은 일부러 비워 뒀다 ★

GCP는 `projectRef` 같은 참조로 "이 리소스는 어느 프로젝트에 속한다"를 말하고,
그게 유일한 계층 신호라 378건을 담았습니다. AWS는 **만들지 않았습니다** —
CloudFormation 스키마에 담김을 뜻하는 어휘가 아예 없기 때문입니다(전수 확인).
"필수 참조를 담김으로 치자"는 짐작인데, 맞는 것과 애매한 것이 섞여 있어 뭉뚱그리면
정확히 우리가 막으려는 확신에 찬 오답이 됩니다. **빈 축을 비워 두고 이유를 코드에
적는 것**도 결정입니다.

### svcmap 층 — 설계 개념과 회사 타입을 잇다

목표 3(설계도→배포 계획)이 생기면서 새 질문이 왔습니다: 설계자가 "큐가 필요해"라고
하면 그게 AWS에선 SQS이고 Azure에선 Service Bus라는 걸 **근거를 달고** 알아야
합니다. 그래서 공통 층에 `app::` 접두사의 설계 개념 13종을 두고, 회사 타입으로 가는
엣지를 만들었습니다(2026-07-28 실측 — 산출물이 진실입니다).

```
apiGateway · cdn · containerService · dnsZone · eventStream · keyValueCache ·
messageQueue · nosqlDatabase · objectStorage · relationalDatabase · searchIndex ·
secretStore · serverlessFunction
```

> **여기 없는 둘을 밝혀 둡니다.** 로드밸런서는 `app::` 개념이 아니라 배포 계획의
> **역할**(`ingress`)로만 있고, **모니터링은 아예 없습니다** — 관측 축을 아직 안
> 열었기 때문입니다. 이 문서가 한동안 그 둘을 목록에 적어 두고 있었는데 데이터에는
> 없었습니다. 목록이 늘어날 때 문서가 따라가지 못한 자리입니다.

- **1차 근거**: Microsoft가 공개한 AWS↔Azure·GCP↔Azure **서비스 비교표**
  (`ms-learn-comparison`, CC-BY-4.0). 단 이건 산문 표라 `inferred`입니다.
- **독립 교차 소스**: mingrammer/diagrams의 서비스 분류(`mingrammer-taxonomy`).
  두 소스가 같은 대응을 말하면 `svcmap-cross-checked`로 승급합니다.
- **사람 검수**: 최종적으로 사람이 훑은 것은 `svcmap-reviewed`.

여기서 지키는 것: **바인딩 검증**. svcmap 엣지가 가리키는 회사 타입이 그래프에
실재하는지를 빌드가 검사합니다. 비교표가 낡아서 없는 타입을 가리키게 되면 빌드가
죽습니다 — 조용히 낡는 것보다 시끄럽게 죽는 쪽을 택했습니다.

그리고 정직한 공백: **kafka류는 일부러 미매핑**입니다. "관리형 Kafka로 갈지,
이벤트 스트림 서비스로 갈지"는 아키텍처 결정이라 우리가 대신 정하면 안 됩니다.
설계자가 `engineHint`로 말하면 그때 잇습니다(11장).

## 6. capacitykb — 무엇이 허용되나

가장 큰 축입니다. **제약 141,377건**(2026-07-24 실측, 12개 클라우드: aws 51,197 ·
azure 44,336 · oracle 14,614 · tencent 11,222 · alibaba 9,167 · gcp 6,923 ·
ibm 1,987 · nhn 779 · openstack 725 · ncp 427)과 **쿼터 542건**.

### 레코드 형식

```json
{
  "type_id": "aws::AWS::RDS::DBInstance",
  "property": "DBInstanceClass",
  "kind": "enum",
  "value": ["db.m5.12xlarge", "db.m5.16xlarge", "…"],
  "evidence": "cfn-lint-conditional",
  "basis": "stated",
  "conditions": [
    {"property": "Engine",        "op": "eq",      "value": "aurora-mysql"},
    {"property": "EngineVersion", "op": "matches", "value": "^(10\\.11\\..+|10\\.11)$"}
  ]
}
```

`kind`는 15종입니다 — mutability(바꿀 수 있나) · required · 길이/개수 한도 ·
pattern · enum(허용 목록) · min/max · default · 교차 조건(`at_least_one_of` 등).

### "제약 1건"이 무엇인지 — 세는 단위 ★

141,377이라는 수는 **세는 단위를 밝히지 않으면 남이 다시 셀 수 없습니다.** 다른
연구나 다른 KB와 비교할 때 단위가 다르면 비교 자체가 무의미해집니다. 그래서
정의를 못 박습니다.

> **1건 = `(타입, 속성, 제약 종류, 조건 집합)` 하나.**
> 조건이 다르면 **다른 건**으로 셉니다.

같은 데이터를 다른 단위로 세면 이렇게 됩니다(2026-07-28 실측).

| 세는 단위 | 수 |
|---|---:|
| 레코드 (우리가 쓰는 단위) | **141,377** |
| `(타입, 속성, 종류)` 고유 — 조건을 무시하면 | 139,697 |
| `(타입, 속성)` 고유 — "몇 개 칸에 뭔가 알려져 있나" | 100,787 |

**차이가 작아 보이는 데 이유가 있습니다.** 조건이 붙은 레코드는 1,371건(전체의
**1.0%**)뿐입니다. 조건부 제약은 **드물지만 없으면 답이 거짓이 되는** 종류라
(아래 "뭉뚱그린 범위"), 수가 적다고 중요도가 낮은 게 아닙니다. 쏠림도 극단적입니다
— `AWS::RDS::DBInstance.DBInstanceClass` **하나**가 조건별로 938건입니다. 이
칸에서 조건을 접으면 938건이 1건이 되고, 그 1건은 **어떤 실제 엔진 조합에도 맞지
않는** 허용 목록이 됩니다.

**한 가지 더 밝힐 것**: 완전히 같은 `(타입, 속성, 종류, 조건)` 키가 두 번 나오는
경우가 **328건(레코드 656개)** 있습니다. 결함이 아니라 **서로 다른 소스가 같은
사실을 말한 것**입니다 — 324건이 `cfn-schema` × `tpaws-schema` 쌍입니다. 근거가
다르므로 레코드를 합치지 않지만, **총계는 그만큼 같은 사실을 두 번 셉니다.**
교차 확인된 사실을 하나로 치면 141,049건입니다.

### 뭉뚱그린 범위 — 이 축이 존재하는 핵심 이유 ★

디스크 크기 한도는 **디스크 종류마다 다릅니다.**

| 종류 | 최소 | 최대 |
|---|---:|---:|
| gp2 | 1 | 16,384 |
| gp3 | 1 | 65,536 |
| io1 | 4 | 16,384 |
| standard | 1 | 1,024 |

이걸 최소·최대 한 쌍으로 뭉개면 **1 ~ 65,536**이 됩니다. 그런데 이 범위는 **어떤
실제 설정에도 해당하지 않습니다.** `standard` 디스크에 5,000을 넣으면 실제로는
불가능한데 이 뭉뚱그린 범위는 통과시킵니다. 조건을 담는 칸(`conditions`)이 필요한
이유가 이것입니다.

쓰기 전 검사로 재발을 막습니다 — 같은 `(타입, 속성, 종류)`에 조건 있는 레코드와
없는 레코드가 **공존하면 쓰기를 거부**합니다. **중복 판정 키에도 조건을 넣어야
합니다.** 안 넣으면 종류별 레코드가 하나로 접혀, 조건을 담으려던 것이 도로
뭉뚱그린 범위가 됩니다.

### 판정은 3상태다 ★

조건이 성립하는지 볼 때 답이 셋입니다: **성립 / 불성립 / 모름**(문맥에 그 속성이
없음). **모름을 어느 쪽으로든 접으면 거짓이 됩니다.** 성립으로 치면 gp2 디스크에
gp3 한도를 적용하고, 불성립으로 치면 아는 제약을 통째로 버립니다.

조건이 여럿일 때 순서: **하나라도 확실히 안 맞으면 불성립. 안 맞는 게 없고 모르는
게 있으면 모름. 셋 다 아니면 성립.** 엔진은 알고 버전은 모르는 경우가 흔한데,
그때 엔진이 다르면 그 블록은 확실히 해당 없음이기 때문입니다. 실측에서 엔진만 줘도
후보가 67개로 좁혀지고 "67가지 전부 불가"라는 확정 답이 나왔습니다.

### 주요 소스와 결정들

| 소스 | 무엇을 주나 |
|---|---|
| CloudFormation 레지스트리 스키마 | AWS 속성 제약 (digest — 고정 불가) |
| bicep-types-az | Azure 필수·읽기전용·길이·범위 |
| azure-rest-api-specs | **Azure 불변성** (bicep 변환기가 떨어뜨리는 것) |
| terraform-provider-google/aws | GCP 최신 값 · AWS 교차 필드 |
| KCC (스키마·설명문·CEL) | GCP 제약·불변성 |
| cfn-lint | 엔진×버전 조건부 · 리전별 인스턴스 종류 |
| swagger(Azure 운영·시크릿) | 조회로 채워지는 칸 · 비밀 취급 칸 |
| Terraform provider 8종 | alibaba·tencent·oracle·ibm·nhn·ncp·openstack 확장 |

**Azure 불변성을 따로 받는 이유.** bicep-types에는 이 정보가 **0건**입니다. 원본에
없어서가 아니라 **변환기가 떨어뜨립니다.** 그 결과 (당시) Azure 타입 전부가 "변경
불가로 알려진 속성이 없습니다"라고 답하고 있었습니다. 원본 명세에서 그 필드 하나만
캐서 채웠습니다.

**AWS 디스크 한도는 두 소스가 같은 말을 한 것만.** 가격표 API와 SDK 문서를 교차
검증해 10쌍 전부 일치한 20건만 담았습니다. `gp2`의 IOPS는 한쪽에만 있어서 담지
않았습니다 — 한쪽만 보고 담았으면 **없는 제약을 만들 뻔했습니다.**

**GCP는 소스가 사실 셋이다.** KCC는 하나처럼 보이지만 내부적으로 세 파이프라인이
섞여 있고, 그중 하나(`tf2crd`, GCP 제약의 55%)는 **2023년 9월** 버전의 복사본입니다.
그래서 `backend` 칸에 어느 파이프라인에서 왔는지를 적습니다. 이건 **등급이 아니라
사실**입니다 — 위아래를 이름에 박으면 나중에 판단이 바뀔 때 이름이 거짓이 됩니다.

## 7. costkb — 무엇을 얼마에 살 수 있나

네 덩어리로 자랐습니다.

### (가) 미러 — 스펙·정가 73,083건

CB-Tumblebug이 배포하는 스펙·가격 데이터를 **그대로 베낀 사본**입니다.
에이전트에는 실시간 조회 경로도 있는데, 두 경로가 다른 답을 하면 사용자가
혼란스럽습니다. 그래서 값을 **고쳐 쓰지 않습니다.**

한 가지 예외에도 근거가 있습니다. 상류에 메모리 단위 변환 버그가 있어 일부 값이
2.4% 낮습니다. 우리는 두 값을 다 싣습니다 — `memGiB`(상류 그대로)와
`memGiBActual`(보정값). 보정을 회사 이름으로 하드코딩하지 않고 빌드 때 데이터
지문("MiB가 1000의 배수인 비율")을 재서 적용합니다. 원본이 버그를 고치는 순간
하드코딩된 보정은 **오류 방향을 조용히 뒤집기** 때문입니다.

### (나) 할인 — 스팟·예약·약정

미러엔 온디맨드 정가뿐이라 "예약하면 얼마"에 답할 수 없었습니다. Azure 소매가
API(스팟·예약·저축 플랜 32,073건)와 Cyclenerd의 GCP 카탈로그(스팟·약정
11,193건)로 채웠습니다. AWS 할인가는 **수록하지 않았고 이유를 답에 밝힙니다**
(Price List의 예약 조건 조합이 커서 좁힌 질문에만 실시간 경로가 낫습니다).

### (다) 관리형 서비스 과금 축 — "얼마"가 한 종류가 아니다 ★

"관리형 Redis는 얼마?"에 시간당 단가 하나로 답하면 거짓입니다. 조사(재편 계획
6-B)에서 관리형 가격이 **세 종류 축**으로 갈린다는 게 확인됐습니다.

| 축 | 뜻 | 예 |
|---|---|---|
| `instanceHour` | 인스턴스 크기 × 시간 | RDS db.m5.large $/h |
| `capacityRate` | 용량 단위 × 시간 | DTU, RCU, 처리 유닛 |
| `usage` | 호출·전송량 과금 | 요청 100만 건당, GB당 |

그래서 관리형 가격 레코드에는 반드시 `axis`가 붙고, 도구는 **축별로 나눠 보여 주되
합계를 내지 않습니다.** 부분만 아는 축들의 합은 그럴듯한 거짓 총액이 되기
때문입니다. "값 없음"도 축 목록으로 답합니다 — "이 서비스는 이런 축으로 과금되는데
그중 우리가 수록한 것은 이것"이라고.

수록 상태(2026-07-24): azure 23,563건(12개 아키타입) · gcp 731건 · **aws는 로컬
빌드 전용**(재배포 금지 — 17장). aws가 미빌드인 환경에서는 그 사실과 빌드 명령을
답에 밝힙니다. "미빌드"와 "수록 없음"은 다른 문장으로 답합니다.

여기서 밟은 함정들이 19장에 있습니다 — 단위 문자열로 축을 정하는 규칙(vCore·
Throughput Unit은 `capacityRate`), serviceName의 경계('Azure Cognitive Search'),
로드밸런서 가격의 리전이 "Global"인 것, AWS 중복 행의 판별자들.

### (라) 이그레스 — 나가는 트래픽

"이그레스는 GB당 얼마"도 한 값이 아닙니다 — **경로·목적지·구간**(같은 리전/
대륙 간/인터넷, 첫 10TB/다음 40TB…)마다 다릅니다. 그래서 축 개수와 구조를 답하고
합계를 거절합니다. 배포 계획(11장)에도 "이그레스 비용은 경로·목적지·구간별 축
N개"라는 고지가 실립니다.

## 8. perfkb — 얼마나 빠른가, 함정은 없나

미러에서 뽑은 성능 신호 65,032건에, 세 개의 **보강 소스**(enricher)를 조인해
현재 **34개 필드**를 다룹니다. 필드 예: 버스트 여부·상시 CPU 보장·세대·클럭·
EBS 대역폭·ACU·네트워크 대역폭·NIC 수·GPU 모델/개수·로컬 SSD·CPU 플랫폼.

### 침묵은 정보를 담아야 한다 ★

성능 경고 기능에 심각한 결함이 있었습니다. 함수가 네 경우(정상 / 조인 키 없음 /
레코드 없음 / **그 회사를 아예 추적 안 함**)에 전부 `None`을 반환해 출력이
**바이트 단위로 똑같았습니다.** 검증된 안전한 인스턴스와 우리가 아무것도 모르는
인스턴스가 구별되지 않았습니다. 지금은 다섯 상태(`warn`/`ok`/`no_record`/
`untracked`/`not_built`)를 구분하고, 블록 끝 꼬리말이 침묵의 의미를 한 번 밝힙니다.

### 판단 불가는 `False`가 아니다 ★

"네트워크가 버스트인가"를 `"Up to"로 시작하는가`로 판정하다가 실제 값 **72종**
(`High`, `Moderate`, `Low to Moderate`…)을 만났습니다. `startswith`가 실패했을 때
`False`(=문제 없음)를 반환한 것이 잘못입니다. **모르면 `None`이어야 합니다.**
Azure에서도 같은 문제로 96%에 "CPU 보장됨"을 붙일 뻔했습니다 — **부정은 이름
근거가 있지만 긍정은 근거의 부재**였습니다.

### 보강 소스 셋 — 미러가 못 주는 것

**(1) ec2-hardware** — AWS 인스턴스의 클럭·EBS baseline 등 하드웨어 실측치.

**(2) Azure 크기 문서 표** (`azure-sizes-doc`, stated) — 미러의 Azure 스펙에는
NIC 수·네트워크 대역폭이 없었습니다. Azure VM 크기 문서의 **표**(산문 아님)에서
뽑아 NIC 25,385건·대역폭 24,108건을 채웠습니다. 여기에 **구세대 판정**도
실었습니다: 생애주기 문서(previous-gen·retired 목록)의 시리즈 라벨 37종을 크기
정규식 손 표로 만들되, **문서 라벨과 손 표가 어긋나면 빌드가 죽는 상호 대조**를
내장했습니다. 구세대 146종에 `currentGeneration=False`를 붙이되 **목록에 없다고
`True`를 주지 않습니다** — 부재를 최신 주장으로 승격하는 것이 침묵 오독입니다.

**(3) GCP 시리즈 카탈로그** (`cyclenerd-gcp-catalog`, inferred) — GCP 스펙의
CPU 플랫폼·대역폭·GPU·로컬 SSD가 비어 있었습니다. Cyclenerd 저장소의 시리즈별
SQL(UPDATE 문)을 파싱해 98%를 채웠습니다. 큐레이션된 서드파티라 `inferred`이고,
모르는 GPU 키는 **승격하지 않고 셉니다.**

구세대 경고는 이제 aws(공식 필드)·azure(손 표) 두 회사에서 동작합니다. gcp는
공식 신호가 없어 비워 뒀습니다 — 이유가 코드에 적혀 있습니다.

### IBM — 일곱 회사 중 소스가 실재하는 유일한 곳

성능 축을 12개 클라우드로 넓히려 조사했더니, aws·azure·gcp 밖 아홉 중 **공개
성능 소스가 실재하는 곳은 IBM뿐**이었습니다(2,002건 수록). 나머지는 "부재
확정"으로 기록하고 재조사 금지 목록에 올렸습니다(20장).

## 9. 곁 축들 — bundlekb · sizingkb · envkb

### bundlekb — 이것을 쓰면 무엇이 따라오나

"가상머신 하나 만들래"가 실제로는 네트워크·서브넷·보안그룹·IP까지 딸려 오는
일입니다. 세 부류의 소스로 **동반 리소스**를 담습니다.

- **이름 붙은 번들** (tumblebug 템플릿·KCC 샘플·AVM 모듈) — 사람이 묶어 둔 것.
- **동시 출현** (`aqt-corpus`·`awscfn-corpus`, basis=**observed**) — 실제 배포
  템플릿 코퍼스에서 "A가 있는 템플릿의 몇 %에 B가 있는가"를 **센 것**. 관측이지
  주장이 아니므로 별도 basis를 만들었습니다. **동시출현 100%가 판별자**입니다 —
  100% 미만은 "자주 함께"일 뿐이라 담지 않습니다.
- **교차 확인** — 독립된 두 소스가 같은 쌍을 말하면 `bundle-cross-checked`.

여기서 AVM의 함정을 밟았습니다. Azure Verified Modules의 모듈 구조가 **3층**인데
판별자를 두 번 잘못 짚어 두 번 틀렸습니다 — 지금 규칙은 코드에, 실패 기록은
아카이브 문서에 있습니다.

### sizingkb — 일부러 좁게

"규모 산정"은 유혹이 큰 축입니다 — "동접 1만이면 서버 몇 대?"에 답하고
싶어집니다. **안 합니다.** 그 답의 근거가 될 공개 소스가 없고(조사로 확정),
근거 없는 사이징은 확신에 찬 오답의 왕도입니다.

대신 **원본이 명시한 최소 요건만** 담습니다(규칙 65건): 서브넷의 예약 IP 수
(AWS 5개·Azure 5개·GCP 4개 — 회사마다 다르고 문서에 적혀 있습니다), k8s 노드
최소 사양(우리 런타임 도구의 요구), 프로바이더별 필수 서브넷 수, 컨테이너 규모
프리셋(bitnami — 원본이 스스로 밝힌 값). 전부 "누가 그 숫자를 말했는가"를
답할 수 있는 것들입니다.

## 10. patternkb — 산문 지식, 자문 전용

수치로 환원되지 않는 지식이 있습니다 — "재시도는 지수 백오프로", "비용을 아끼면
신뢰성에서 무엇을 잃는가" 같은 **설계 지침**입니다. 이걸 사실 축에 넣으면 지침이
사실 행세를 하게 되므로, 별도 축을 만들고 **자문 전용**이라는 원칙을 박았습니다.

> **advisory 원칙**: 이 축의 답에는 항상 "설계 지침이지 검증된 사실이 아니다"라는
> 고지가 붙고, 근거 라벨은 `pattern-advisory`(inferred) 하나뿐입니다. 가격·한도
> 같은 사실 질문은 다른 축으로 가라고 답 자체가 안내합니다.

### 코퍼스 — 5소스 523편 (2026-07-25)

| 소스 | 내용 | 라이선스 |
|---|---|---|
| Azure Architecture Center | 클라우드 설계 패턴 (Retry, Circuit Breaker …) | CC-BY-4.0 |

AWS Well-Architected는 사연이 하나 더 깁니다. HTML 문서는 사이트 약관이 자동

1,334개**(계층·쪽 번호)로 자릅니다 — 1,002쪽짜리 문서가 목차 구조를 기계로
주는데 정규식으로 자르는 것은 함정을 자초하는 일입니다.

### 검색 — 벡터가 아니라 FTS5

검색은 SQLite FTS5(어휘 일치)로 합니다. **2패스**입니다: 먼저 모든 단어 AND로
정밀 검색, 결과가 모자라면 OR로 채웁니다(제목 가중치 5배). 임베딩(벡터) 검색은
**두 번 검토하고 두 번 기각**했습니다.

- 1차: 창립기 무편향 조사에서 검색 실패가 0건 — 없는 문제였습니다.
- 2차: 코퍼스가 자란 뒤 재현율을 실측(hit@3 엄격 75% · 주제 적합 ~90%)했는데,
  자문 용도(인용+고지)에 충분했고, 시스템 타겟이 영어라 다국어 필요도 없으며,
  임베딩은 의존성·결정론·오프라인 테스트 중 하나를 깨는 비용이 있습니다.
- 재상정 조건이 기록돼 있습니다: **라이브에서 자문 오답이 실제 문제로 실측되면.**

라이브 검증에서 모델이 pattern_search를 부르고, 인용(패턴 이름)과 advisory 고지가
최종 답변까지 살아남는 것을 확인했습니다(15장).

## 11. appkb와 설계도→배포 — 목표 3의 층

외부 설계 에이전트(easydep 팀)가 만든 앱 설계를 받아 배포 계획을 내는 층입니다.

### 진입 계약 — appkb

설계는 JSON 계약으로 받습니다. 핵심 결정들:

- **필수 4칸**: 스키마 버전·컴포넌트·아티팩트(OpenAPI 등 실물)·요구사항.
  계약 위반이면 **무엇이 왜 위반인지 목록으로 답하고 처리하지 않습니다** —
  라이브 검증에서 모델이 이 위반 목록을 지어내지 않고 그대로 전달함을 확인했습니다.
- **설계자의 결정 칸**: `deployHint`(컴퓨트 방식)·`engineHint`(큐=kafka 같은 엔진
  지정)·`archetypeHint`(아키타입 직접 지정). 설계자가 정하면 그 결정이 이기고,
  답에는 "설계자 지정"이라고 표시됩니다.
- **`dataResidency`** — "데이터는 한국에"라는 요구는 우리가 **판정할 수 없습니다**
  (법적 판단). 대신 리전 사실과 **대조**해 "선택 리전은 한국이 맞다/아니다 +
  판정은 못 한다"를 답합니다. 판정 불가를 명시하는 소비자가 계약에 있습니다.

### compose — 배포 계획 구성 6단계

설계를 받아 계획을 만드는 순서가 코드에 단계 함수로 박혀 있습니다: 신호 수집 →
컴퓨트 배치 → 관리형 서비스(svcmap) → 공유 인프라 → 진입점(LB) 배선 → 값
붙이기 → 전역 고지. 각 노드·엣지·노트에는 **origin**(설계 원문 / 설계자 지정 /
KB 사실 / 우리 추론)이 붙고, 추론에는 유보(⚠)가 붙습니다.

몇 가지 정직성 장치:

- **값은 하한이고, 그 하한의 전제를 밝힙니다** — "월 $X (하한, 컴퓨트 각 1대 기준.
  수평 확장 대수는 정해지지 않았습니다)". 스케일아웃 대수를 짐작하지 않습니다.
- **로드밸런서 삽입은 우리 권고**로 표시됩니다(공개 노출 VM 앞) — 근거와 함께.
- **컴퓨트 방식 비교 판정** — deployHint가 없으면 VM/k8s/서버리스 각각에 우리가
  잴 수 있는 판정(비용 하한·버스트 상충·stateless 적합·도구 최소사양·대응 존재)을
  나란히 놓습니다. **권고는 상충 없는 방식이 정확히 하나일 때만** 내고, 그때도
  "우리 권고이지 검증된 사실이 아니며 잰 축 밖의 입력(팀 역량·지연 요건)은 이
  판정에 없다"를 답니다. 여럿 남으면 고르지 않습니다 — 임의 선택이 이 저장소가
  막아 온 실패입니다.

### 다이어그램 — 그리고 왕복 검증

계획은 PlantUML 배포 다이어그램으로 렌더됩니다(easydep 쪽 최종본이 PlantUML이라
어댑터를 뒀습니다). 다이어그램에는 근거 주석이 실립니다. 그리고 **렌더한 것을
되파싱해 계획과 대조**하는 검증이 있습니다 — 그리기 코드가 노드를 빠뜨리면
테스트가 죽습니다.

### verify — 요구 부합 판정

계획을 요구사항과 대조합니다. 판정문의 규율:

- **예산 판정은 비대칭입니다.** 하한이 예산을 넘으면 "초과 **확정**"(하한이
  넘으니 실제는 더 넘습니다), 하한이 예산 안이면 "지킬 수 있을지 **판정
  불가**"(하한만 알기 때문). 같은 데이터에서 한쪽은 확정, 한쪽은 불가 — 이
  비대칭이 정직함입니다.
- **트래픽×버스트, 상태성×서버리스** 같은 조인 판정은 "상충 확정"과 "상충
  가능성(우리 추론)"을 구분합니다.

## 12. 근거 체계 — 숫자를 버리고 세 단어로

처음에는 신뢰도를 **0.5~1.0 숫자**로 매겼습니다. 전부 버렸습니다. 척도의 정의가
어디에도 없었고(0.9와 0.95의 차이를 아무도 못 말함), 라벨이 신뢰도의 함수가
아니었으며(같은 라벨에 0.6/0.7/0.8), 실제로 쓰이는 임계선 하나(0.8)에 하필 값이
몰려 있어 상수를 0.81로만 바꿔도 결과가 뒤집혔습니다.

지금은 **세 값**만 씁니다.

```
basis = "stated"    원본이 그렇게 적어 놓았다
      | "inferred"  우리가 이름·산문·구조에서 짐작했다
      | "observed"  코퍼스에서 세어 봤다 (동시 출현 — 관측이지 주장이 아님)

사실로 취급(is_fact) = stated 이거나, 사람이 검수했다(reviewed)
유보 필요(needs_hedge) = 짐작이고 검수 안 됨 — 답에 ⚠ 표시
```

`is_fact`와 `needs_hedge`는 **다른 질문**입니다 — "사실로 인용해도 되나"와 "유보를
달아야 하나". 검수된 짐작은 사실로 취급하되, 검수가 짐작을 stated로 바꾸지는
않습니다.

### 라벨 하나에 성격 하나 ★

> **근거 라벨 하나에 basis 하나.** 위반하면 라벨을 쪼갠다.

이건 실패에서 나왔습니다. 검수 파일에 `{"evidence": "kcc-ref"}` 한 줄로 승인했는데,
그 라벨이 **사실(대응표)과 짐작(설명문 정규식)을 겸하고** 있어서 짐작 322건까지
같이 승인됐습니다. 지금은 `one-basis-per-evidence` 불변식이 error 등급으로 막고,
전 라벨 54종의 성격이 `kbcommon/basis.py` 카탈로그 한 곳에 적혀 있습니다.

라벨은 쪼개질 때 이야기를 담습니다. 예를 들어 `aws-burstable-field`(stated)와
`aws-non-burstable-inferred`(inferred)가 **한 필드에서 나온 두 라벨**입니다 —
아래 사연 때문입니다.

### 비대칭을 대칭으로 옮기지 마라 ★

AWS API에 `BurstablePerformanceSupported`라는 칸이 있습니다. `true`면 버스트,
`false`면 아니라는 뜻처럼 보입니다. 그대로 옮겼더니 `t1.micro`가 "상시 성능 보장"
이라고 단언하게 됐습니다. t1은 실제로 버스트 계열입니다 — AWS가 `false`를 주는
이유는 t1이 크레딧 모델보다 **앞선 세대**라 그 필드에서 제외된 것이지, 성능이
보장돼서가 아닙니다.

**원본에 충실했는데 결과 명제가 사실과 반대**였습니다. 이 필드는 한 방향만 직접
말합니다: `true`→버스트다(stated), `false`→버스트가 아니다(inferred, 우리 추론).
29,395건이 inferred로 바뀌었습니다. **이름으로 예외 처리하지 않았습니다** —
"t1만 특별 취급"으로 고쳤으면 다음 세대에서 같은 모양으로 재발합니다.

### 다리를 건너면 등급이 떨어진다

두 사실을 이어서 새 명제를 만들면, 새 명제의 등급은 **가장 약한 고리**를 따릅니다.
전이 동치(A=B, B=C ⇒ A=C)가 그 예입니다. 조인으로 만든 판정("상시 부하인데 최저가
스펙이 버스트형")도 구성 사실은 stated지만 판정 자체는 우리 추론으로 표시됩니다.

## 13. 질의·도구 계층 — 데이터를 답으로

데이터가 맞아도 **말하는 방식이 틀리면** 사용자는 틀린 답을 받습니다.

### 없다 / 안 봤다 / 못 읽었다 / 조합이 없다 — 넷을 구분한다 ★

| 상황 | 답변 |
|---|---|
| 수집 범위 안, 제약 없음 | "알려진 제약이 없습니다 (수집 범위 안이므로 '없음'이 답입니다)" |
| 수집 범위 밖 | "**수집 범위 밖**이라 모릅니다 — 제약이 없다는 뜻이 아닙니다" |
| 정규식을 못 읽음 | "제약은 있으나 그 정규식을 읽을 수 없습니다" + 원문 |
| 조건에 안 걸림 | "조건부 제약 938건이 있지만 **주신 조합에 걸리는 것이 없습니다**" |

"우리가 모른다"와 "당신이 준 조합을 우리가 모른다"는 전혀 다른 신호입니다 —
뒤쪽은 오타나 미지원 버전을 의심하라는 뜻입니다.

### 한도가 어느 조건에서의 것인지 밝힌다 ★

"30,000 GiB는 최대 16,384 GiB를 벗어남 **(VolumeType='gp2'일 때)**" — 조건이
없으면 16,384가 보편 상한처럼 읽힙니다. 정작 필요한 사실은 gp3로 바꾸면 65,536까지
된다는 것입니다. **한도를 어겼다는 말보다 어느 조건에서의 한도인지가 해결책을
가리킵니다.**

### 막다른 길을 답으로 바꾼다 ★★

실측에서 가장 큰 수확이었습니다. 에이전트가 `p5.48xlarge`(값)를 타입 이름으로
검색했을 때 "없습니다"만 줬더니, 웹검색 13회·14분을 쓰고 "지식베이스에
없습니다"라고 답했습니다 — 그때 우리는 그 값의 리전별 데이터 39건을 쥐고
있었습니다. 지금은 값 역인덱스(고유 값 7,095개)가 "그건 타입이 아니라 값이고,
이 값이 나오는 곳은 여기"라고 답합니다. **838초 → 6.6초, 웹검색 0회, 정답.**
살짝 틀린 속성 이름(RDS에 `InstanceType`)도 아는 이름(`DBInstanceClass`)을
가리키고, 각 축의 응답 끝에는 다른 축을 가리키는 줄이 붙습니다.

> 배운 것: 모델은 매번 다른 문으로 들어옵니다 — **모든 문이 답을 알아야 합니다.**

### 도구 — 늘리지 말고 통합하고, 규율은 설명에 싣는다

현재 41개(2026-07-24)입니다. 새 도구는 "자주 쓰이고 복잡하다"를 만족할 때만
만듭니다(관리형 과금 축도 새 도구 없이 기존 도구·계획 노트에 실었습니다).

지키는 규칙들:

- **도구 출력에 다른 도구 이름을 넣지 않는다.** 모델이 그 문자열을 답변에 그대로
  복사합니다(실측 누출 3/3). 행위 서술로 바꿉니다("월 비용은 다음 단계에서 계산").
  결정론적으로 고칠 수 있는 누출은 프롬프트에 맡기지 않습니다.
- **라우팅 규율은 도구 설명(docstring)에 싣는다.** 시스템 프롬프트는 길어질수록
  흐려지지만 도구 설명은 그 도구를 고를 때 읽힙니다. 새 필드를 추가하면 라우팅
  신호도 함께 갱신해야 합니다 — "로컬 SSD **용량**"이라는 질문이 '용량'이라는
  단어 때문에 용량 축으로 흘러갔다가 웹검색으로 누출된 실측 사례가 있습니다.
  도구 설명에 "인스턴스 장착 하드웨어는 이쪽"을 명시해 고쳤습니다.
- **프로바이더 간 성능 비교는 구조적으로 막는다.** perf_compare가 단일 프로바이더만
  받습니다 — ACU는 Azure에만, 클럭은 AWS에만 있어 공통 기준이 없기 때문입니다.

### 긴 목록을 통째로 찍지 않는다

한 도구 응답이 **377,439자**였던 적이 있습니다. 요약으로 5,153자로 줄였더니,
이번엔 39줄이 전부 똑같아 보이는 문제가 드러났습니다 — 어느 리전의 값인지가 그
줄의 뜻 전부인데 그게 빠져 있었습니다. 내부 식별자(`aws::` 접두사, 라벨 원문)는
API가 아예 만들지 않습니다 — 근거를 없애는 게 아니라 사람 말로 적습니다.

## 14. 출처 세탁 — 가장 위험한 실패

측정이 계속 같은 곳을 가리켰습니다.

> **모델이 자기 기억을 우리 지식베이스의 이름으로 내보낸다.**

실제 사례: "※ cap_allowed_values 지식베이스에서 조회한 뒤 GPU가 장착된 패밀리만
추려낸 결과" — 그런데 GPU 개수·vCPU·메모리는 그 지식베이스에 **없는 데이터**이고,
그 도구를 부르지도 않았으며, 값도 틀렸습니다(g5g는 NVIDIA인데 AMD라고 함).
**지어낸 값에 우리 보증이 찍혔습니다.** 도구가 "840가지 가능"이라 했는데 "지원되지
않음"으로 **뒤집어 놓고 우리 이름으로 출처 표기**를 한 사례도 있습니다.

프롬프트로는 못 고칩니다 — 이 프로젝트는 프롬프트 준수가 안 통한다고 이미
쟀습니다(26질의 × 3회에서 16개만 3/3 완벽).

### 대신 만든 것 — 주장 대조기 (claim_check)

**설득하지 않고 대조합니다.** 답변에 나온 숫자·식별자가 그 턴의 **도구 출력에
실재하는지**만 기계적으로 봅니다. 24건 실측에서 지어냄 3건(최악은 표 하나에
16개), 기억 답변 1건, 헛짚음 1건을 갈라냈습니다.

이걸 검사 장치에 **신호로만** 얹었습니다 — 통과/실패에는 넣지 않습니다. 헛짚음을
실패로 만들면 멀쩡한 답변이 빨갛게 뜨고 진짜 실패가 노이즈에 묻힙니다.

> 대조기는 "틀렸다"고 말하지 않습니다. **"이건 확인하지 않고 한 말이다"**라고
> 말합니다. 모델 기억은 낡습니다 — gp3 최대 IOPS를 모델이 16,000으로 기억하는데
> AWS가 80,000으로 올린 사례를 직접 겪었습니다. 그때도 답변은 자신 있어 보였습니다.

한계도 분명합니다: 숫자·이름이 아니라 **문장의 뜻**이 뒤집힌 것은 못 잡습니다.
우리 도구가 만드는 정형 줄(`가능:`/`불가:`)의 뒤집기만 형식으로 잡습니다.

## 15. 검증 — 만든 게 맞는지 어떻게 아나

다섯 층으로 봅니다.

### (가) 단위·불변식 테스트

빠르고 네트워크가 필요 없습니다(개수는 pytest가 진실 — 2026-07-24 기준 1,332건).
하지만 이것만으로는 부족합니다 — `cap_check_value`가 문맥을 못 받아 조건부 판정이
통째로 안 쓰이던 결함 때, 단위 테스트는 전부 통과하고 있었습니다.

### (나) 규약을 지키는 구조 테스트

지키고 싶은 규약은 문서가 아니라 **테스트**로 만듭니다.

- `test_architecture.py` — import 방향(KB↛KB, KB→kbcommon만).
- `test_source_pinning.py` — 모든 소스에 핀. 핀 불가 소스는 이유와 함께 명시
  등록해야 통과.
- `test_docs_structure.py` — 문서 정책(살아있는 문서 2개, 날짜 박힌 문서는
  아카이브에 불변, 죽은 참조 금지).
- 커밋 금지 산출물(aws 관리형)이 data/에 없는지, pack이 거부하는지.

### (다) KB 사이 검증

`python -m kbcommon verify`. 단방향 규약 때문에 어느 빌드에도 넣을 수 없어서,
산출물 JSON을 **데이터로 읽어서** 축 사이 정합(제약이 가리키는 타입이 그래프에
실재하나 등)을 봅니다.

### (라) 황금 출력 대조

큰 리팩터링(compose 단계 분리 등)은 **재편 전후 산출물이 바이트 단위로 같은지**로
검증했습니다. "같은 일을 한다"는 주장을 diff가 증명합니다.

### (마) 라이브 프로브 — 모델을 끼우고 잰다

실제 모델을 태우는 프로브(2026-07-24 기준 21건)가 옵트인 테스트로 있습니다.
단위 테스트가 못 보는 층 — 도구 라우팅, 응답이 답변까지 살아남는가, 누출 —
을 여기서만 잡을 수 있습니다.

프로브 해석에 규율이 있습니다. 전부 실패에서 나왔습니다.

- **한 실행의 실패는 신호이지 판정이 아니다.** 같은 날 두 실행에서 3건이 갈린
  실측이 있습니다. 일관 실패만 회귀로 취급합니다.
- **일관 실패면 프로브 기대부터 의심하라.** 기대가 틀려 있던 전례가 넷입니다 —
  리전 코드가 두 회사에서 같은 줄 모르고 "명시 없이도 한 회사로 답하라"고 기대한
  것(`ap-northeast-2`는 aws와 alibaba가 같이 씁니다 — 모델의 되묻기가 지시
  준수였습니다), 데이터가 없다고 전제했는데 그 사이 생긴 것 등.
- **자동 판정은 도구 호출로만, 답의 옳고 그름은 사람이 읽는다.** 한국어 부분
  문자열 판정은 양방향으로 틀립니다("사용할 수 있습니다"가 "확인할 수 없습니다"에
  들어 있습니다). 유사 문자(U+2011 하이픈, U+202F 공백)는 정규화합니다.
- **기대값은 산출물 실측에서 가져온다.** 기대를 기억으로 쓰면 검사가 데이터보다
  먼저 늙습니다.

### 무편향 조사 — 아는 것만 검사하지 않기 위해

기대 문구를 쓰다 보면 내가 아는 데이터만 검사하게 됩니다. 그래서 24개 질문을
**데이터를 확인하지 않고 먼저 쓰고**, 정답지를 답변 읽기 전에 만들고, 답변은
사람이 읽어 분류한 조사를 했습니다. 결과가 설계 판단을 바꿨습니다 — 실패 원인
1위가 "출처 혼합"(4건)이었고 "관련 있는 걸 못 찾음"은 **0건**이라, RAG(벡터
검색)를 넣지 않는 결정의 근거가 됐습니다.

**① 탐색은 축의 공백에서 시작합니다.** 소스를 먼저 모으고 쓸 곳을 찾은 게 아니라,

**③ 실측 전 착수 금지.** 소스가 그 값을 정말 주는지 **받아서 세어 보기 전에는

- "botocore shape에 min/max가 없다"고 적어 뒀다가 세어 보니 **있었습니다**
  (EC2만 봐도 min 183·max 175·enum 457).
- "NHN은 공개 프로바이더가 없다"고 적어 뒀다가 받아 보니 **110종이 있었습니다.**

두 번 다 **우리 기대가 틀렸고 데이터가 맞았습니다.** 그래서 기대로 배제하지
않습니다.

**④ 배제 기준과 그 기록.** 기각한 후보는 이유와 함께 남깁니다 — 20장이 그
목록입니다. 배제 사유는 세 종류로 갈라 적습니다: **근거가 없어서**(사이징
소스) / **표현할 자리가 없어서**(Terraform 스키마 JSON) / **권리가 막아서**(AWS
Price List 재배포). 이 셋을 뭉뚱그리면 리뷰어가 "안 한 것"과 "못 하는 것"을
구별할 수 없습니다.

**⑤ 값싼 순서로 훑습니다.** 새 소스를 찾기 전에 **이미 핀 박은 저장소의 안 쓰는
파일**을 먼저 봅니다. 받는 비용도 검증 비용도 0에 가깝고 태그가 이미 맞기
때문입니다 — `botocore-endpoints`·`tumblebug-cloudinfo`·`tumblebug-src`가 그렇게
들어왔습니다.

**⑥ 언제 멈추나 (포화).** 레코드 수는 포화 지표가 아닙니다 — 같은 종류의 사실이
늘어난 것일 수 있습니다. 축이 포화했다고 보는 기준은 이것입니다.

> **소스를 하나 더 넣어도 그 축이 답할 수 있는 질문의 종류가 늘지 않으면 포화.**

이 기준으로 현재를 읽으면 축마다 다릅니다. **capacity는 포화에 가깝고**(12개
CSP 중 소스가 있는 곳을 다 넣었습니다), **graph는 전혀 아닙니다**(7개 CSP의
관계 축이 비어 있습니다 — 3장 격자). **perf는 조사로 포화가 확정된 경우**입니다:
aws·azure·gcp 밖 아홉을 전수 조사해 **소스가 실재하는 곳은 IBM뿐**임을 확인하고
나머지를 재조사 금지 목록에 올렸습니다(20장).

> **한계도 적습니다.** 이 절은 **사후에 구성한 것**입니다(2026-07-28). 기준을
> 먼저 문서로 정하고 그에 따라 고른 게 아니라, 실제로 쓰인 규칙을 나중에 말로
> 옮겼습니다. 그래서 "사후 정당화가 아닌가"라는 의심은 정당하고, 반박 근거는
> 위 표의 **조사 기록이 채택 이전 날짜로 남아 있다**는 것뿐입니다.

### 소스가 서로 독립인가 — 47종이 47개의 독립 근거가 아니다 ★

**"두 소스가 같은 말을 하면 승급"**은 이 저장소의 핵심 장치입니다(5·9장의 교차
확인). 그런데 그 두 소스가 사실 **같은 물건**이면 승급이 아니라 **같은 말을 두 번
센 것**입니다. 그래서 독립성을 표의 칸으로 다룹니다.

| 표시 | 뜻 | 교차 확인에 쓸 수 있나 |
|---|---|---|
| **독립** | 발행 주체도 생성 경로도 다름 | 쓸 수 있다 |
| **같은 발행자** | 조직은 같고 산출 경로가 다름 | 약하게. "둘 다 틀릴" 상관이 남는다 |
| **같은 상류의 다른 파일** | 같은 저장소·같은 ref | **못 쓴다** |
| **복제** | 한쪽이 다른 쪽의 코드·데이터 사본 | **절대 못 쓴다** |

아래가 **독립이 아닌 것 전부**입니다. 나머지는 독립으로 봅니다.

| 묶음 | 표시 | 실측 |
|---|---|---|
| tumblebug-dump · src · latency · cloudinfo · swagger | **같은 상류의 다른 파일** | 5종이 한 저장소. 여기서 정가 73,083 · 성능 65,032 · 리전 188 · 지연 10,890 · 번들 23 · 공통층 13이 나옵니다 |
| cb-spider · cb-spider-map | **같은 발행자**(cloud-barista) | 매핑표는 cb-spider를 근거로 만든 손 검수표입니다 |
| botocore · botocore-endpoints | **같은 상류의 다른 파일** | 같은 태그 1.43.52 |
| **tp-nhn ← tp-openstack** | **복제** | 구현 파일 111개 중 90개가 `resource_openstack_*.go` 그대로. 이름이 84/110 겹치는 것은 **교차 검증이 아니라 같은 코드** |
| **kcc-crd(tf2crd) ↔ tpg-provider** | **복제(버전 차)** | KCC의 `tf2crd` 파이프라인은 terraform-provider-google **4.84.0(2023-09)을 벤더링한 것**이고, tpg-provider는 같은 생성기의 최신 산출물입니다 |
| gcloud-machine-types · cyclenerd-gcp-pricing | **같은 발행자**(같은 저자의 다른 저장소) | 둘 다 커뮤니티 큐레이션이라 `inferred` |
| azure-compute-docs · azure-limits-doc · azure-well-architected · ms-architecture-center | **같은 발행자**(MicrosoftDocs) | 저장소는 다르지만 편집 주체가 같습니다 |
| cfn-schema · cdk-oob · botocore · aws-price-list · aws-cfn-templates · aws-solutions-constructs | **같은 발행자**(AWS) | AWS 디스크 한도의 "두 소스 교차 검증"(6장)은 **같은 회사의 두 산출물**입니다 |

**가장 값이 큰 줄은 GCP입니다.** 실측하면(2026-07-28) GCP 제약 6,923건의 출처가
이렇습니다.

```
tpg-schema        3,383   terraform-provider-google v7.40.0  (Magic Modules 산출물)
kcc  tf2crd       1,572   같은 생성기의 4.84.0 벤더링본       ← 위와 같은 뿌리
kcc  dcl2crd      1,098   다른 파이프라인
kcc  direct         870   다른 파이프라인
kcc  기타(불변성) 3,540 중 위 셋으로 나뉨
```

즉 **GCP 제약의 71.6%(4,955건)가 결국 같은 생성기에서 나옵니다** — 버전만 3개
메이저 떨어져 있습니다. "KCC와 Terraform provider 둘 다 그렇게 말한다"를 교차
확인으로 읽으면 안 되는 이유입니다. `backend` 칸을 등급이 아니라 **사실**로 적어
둔 결정(6장)이 여기서 값을 합니다 — 그 칸이 없었으면 이 계산 자체가 불가능합니다.

> **독립으로 남은 교차 확인**은 그래서 더 값이 있습니다: `ms-architecture-center`
> (마이크로소프트) × `mingrammer-diagrams`(제3자 오픈소스)의 svcmap 교차 확인,
> `azure-quickstart-templates`(마이크로소프트) × `aws-cfn-templates`·
> `widdix-cf-templates`(AWS·제3자)의 동시 출현 방법 재현이 그렇습니다.

## 17. 라이선스와 재배포 — 법적 경계도 데이터다

소스마다 "가져다 쓸 수 있는가"와 별개로 **"재배포할 수 있는가"**가 갈립니다.
이 구분을 어기면 기술이 아니라 권리를 어기는 것이라, 코드로 강제합니다.

| 등급 | 뜻 | 우리 처리 |
|---|---|---|
| 허용 (MIT·Apache·MPL·MIT-0) | 재배포 가능 | `data/`에 커밋, NOTICE에 표기 |
| **CC-BY-4.0** | 재배포 가능하되 **저작자 표시 의무** | NOTICE + 문서별 attribution 칸 |
| **명시 없음** (azure-retail-prices·ibm-global-catalog) | 공개 API지만 재배포 허락이 적혀 있지 않음 | 수록하되 NOTICE에 그 사실을 공시 |
| **공정이용** (aws-well-architected) | 라이선스 부여 없음(All rights reserved) — **교육 목적 공정이용 판단으로 수록** | NOTICE·`_note`·attribution 3곳에 판단 명시, 요청 시 제거 |
| **거부** (AWS Price List 약관) | 가격 데이터 재배포 금지 | **커밋 자체가 불가능한 구조** |

거부 줄이 AWS 관리형 가격입니다. 데이터는 공개 API로 받을 수 있지만 약관이
재배포를 금지하므로: 빌드는 **로컬 전용**(`python -m costkb build-aws-managed`,
사용자 환경에서), `data/`에 그 파일이 존재하면 테스트가 실패하고, `kbcommon pack`은
파일 이름을 보고 포장을 거부합니다.

공정이용 줄은 이 넷 중 유일하게 **라이선스가 아니라 판단**입니다 — 허가가 있는
것처럼 굴지 않는 것이 핵심이라, "허가를 받았다는 뜻이 아니며 요청 시 제거한다"는
문장까지 테스트가 강제합니다. 사실 데이터(가격·스펙 — 저작권 보호가 얇음)와 산문
저작물(저작권의 본체)의 차이를 인지한 상태에서, 비영리 졸업과제라는 용도에 기대
내린 결정입니다.

### 위 표는 **분류가 끝난 목록이 아니다** ★

여기가 이 문서가 **코드보다 자신 있게 말하던 유일한 자리**였습니다(감사
2026-07-28). 위 5등급 표는 47종 전부가 분류된 것처럼 읽히지만, 실제로 등급이
붙어 있던 소스는 **넷**뿐이었습니다 — 거부 1(`aws-price-list`) · 문구 없음
2(`azure-retail-prices`·`ibm-global-catalog`) · 공정이용 1(`aws-well-architected`).
나머지 43종은 `redistribution` 칸이 비어 있었고, 그 빈 칸의 뜻은 코드가 정확히
적어 두고 있었습니다 — **"괜찮다"가 아니라 "따로 판단하지 않았다."**

지금은 라이선스도 **등록부의 칸**입니다(`kbcommon/sources.py`의 `license`).
현재 상태입니다.

| 라이선스 | 소스 수 |
|---|---:|
| Apache-2.0 | 17 |
| MPL-2.0 (Terraform provider 계열) | 9 |
| MIT | 7 |
| CC-BY-4.0 (**저작자 표시 의무**) | 5 |
| MIT-0 | 1 |
| `not-stated` (공개돼 있으나 부여 문구 없음) | 2 |
| `all-rights-reserved` (공정이용 판단으로 수록) | 1 |
| `bundled-own` (우리 파일) | 1 |
| **빈 칸 — 아직 확인 안 함** | **4** |

**빈 칸 넷을 감추지 않습니다.** `cfn-schema` · `cdk-oob` · `aws-price-list` ·
`azure-rest-api-specs`이고, `unlicensed()`가 모으며 테스트가 이 목록을 못 박습니다
(`test_unlicensed_sources_are_declared_as_such` — 목록이 자라면 빌드가 죽습니다).

넷 중 셋은 **아직 안 본 것**이라 확인하면 채워집니다. `cfn-schema` 하나만
**원리적으로 어렵습니다** — 저장소가 없고 AWS가 서빙하는 zip뿐이라 LICENSE 파일
자체가 존재하지 않습니다. 하필 그 소스가 이 저장소 **최대 근거(46,911건)**입니다.

> 규율은 `unpinnable()`과 같습니다: **모르는 것을 세어서 드러내면 다음 사람이
> 착각하지 않습니다.** 라이선스 표기도 자유 서술이 아니라 정해진 어휘여야 하고
> (`test_license_values_are_from_the_known_vocabulary`), 부여가 없는 소스는
> **왜 수록했는지**가 반드시 적혀 있어야 합니다.

**칸을 만들자마자 위반이 하나 나왔습니다.** CC-BY는 "넣어도 되나"가 아니라
**"표시했나"**가 조건이라, 새 검사가 CC-BY 소스 전부에 대해 NOTICE에 이름이
있는지를 봅니다. `azure-compute-docs`가 걸렸습니다 — 이 소스에서 나온 필드가
`data/tumblebug-perf.json.gz`에 **26,823건** 들어 있는데 NOTICE에는 이름이
없었습니다. **저작자 표시 의무를 지키지 않고 있던 것**이고, 사람이 표를 읽어서는
못 찾았을 종류입니다(같은 파일의 주 소스인 cb-tumblebug만 표기돼 있었고, 보강
소스 셋은 필드 단위로 들어가 있어 눈에 안 띕니다). 지금은 셋 다 NOTICE에 있습니다.

> 이게 "규약은 문서가 아니라 검사로"의 값입니다. 라이선스 칸을 문서 표로만
> 만들었다면 **표는 예뻐지고 위반은 남았을** 겁니다.

# 5부 — 실무

## 18. 처음부터 다시 만드는 절차

```bash
uv sync                 # 의존성
```

산출물이 `data/*.gz`로 커밋돼 있어 **클론 직후에는 빌드 없이 동작합니다.**
재빌드는 소스 핀을 올릴 때만 필요합니다. 각 축은 독립이라 순서가 자유롭습니다.

```bash
# 창립 4축
python -m graphkb build --source tumblebug   # core 13종 (+cfn/azure/gcp/mapping/svcmap …)
python -m capacitykb build --source cfn      # (+azure/gcp/aws-tf/aws-conditional …)
python -m costkb build                       # 미러 사본 (+build-azure-managed 등)
python -m perfkb build                       # 성능 신호 + 보강 소스 3종

# 자란 축
python -m bundlekb build … ; python -m sizingkb build … ; python -m envkb build …
python -m patternkb build … ; # 소스별 하위 명령은 각 패키지 --help가 진실

# 축 사이 검증과 포장
python -m kbcommon verify
python -m kbcommon pack <산출물.json>        # data/*.gz 갱신 (금지 목록 내장)
```

정확한 하위 명령 목록은 **각 패키지의 `--help`가 진실**입니다. 이 문서에 다
적으면 문서가 코드보다 먼저 늙습니다.

### 빌드가 실패하면

**그게 정상 동작입니다.** error 등급 불변식에 걸리면 파일을 쓰지 않습니다. 실제로
Azure 확장 중 `read-only-not-required` 위반 6건으로 빌드가 멈췄는데, 원인은 한
파일 안에서 API 버전이 섞인 것이었습니다. 그대로 나갔으면 사용자에게 채울 수 없는
칸을 채우라고 했을 것입니다. 구세대 손 표도 같습니다 — 문서 라벨과 어긋나면
빌드가 죽습니다. **조용히 낡는 것보다 시끄럽게 죽는 것.**

### 성능 이야기

세션 첫 호출이 느리다면 스키마 검증이 범인입니다(실측 94~96%). 읽기 검증을
컴파일형 검증기로 바꿔 78초 → 10.6초가 됐습니다 — 단, **판정이 전부 일치함을
먼저 확인하고** 바꿨고, 쓰기 경로는 오류 메시지가 유일한 단서라 느린 채 뒀습니다.
검증 캐시는 일부러 안 만들었습니다 — 낡은 결과를 조용히 내주는 실패를 새로
들이는 것이기 때문입니다.

## 19. 함정 모음 — 직접 밟은 것들

만들 사람에게 가장 값이 클 부분입니다. 전부 **실제로 겪은** 것입니다.

### 데이터 만들 때

**빈 목록을 "아무것도 안 됨"으로 읽지 마라.** cfn-lint의 `"all"` 키 값이 빈
목록이었습니다. 리전인 줄 알고 담았으면 모든 인스턴스 종류가 거부됩니다.

**속성 이름을 짐작하지 마라.** 파일명에서 이름을 만들되 스키마에 실재하는지
확인하고, 없으면 담지 않고 셉니다. 없는 이름의 제약은 영원히 아무것에도 안 걸립니다.

**URL을 위치로 파싱하라.** ARM 경로는 `타입/이름/타입/이름` 교대입니다. "중괄호가
없으면 타입"으로 읽었더니 이름을 타입으로 읽었습니다(21종). `/providers/`가 두 번
나오면 뒤쪽이 진짜입니다.

**한 파일 안에서 버전을 섞지 마라.** 옛 버전의 "필수"와 새 버전의 "읽기 전용"이
섞입니다.

**상류가 모순이면 경계만 싣고 값은 버려라.** `default: 0, minimum: 10`이 30건 —
의도를 지어낼 수 없으므로 경계만 담습니다. 반대로 우리가 오독한 것은 우리를
고칩니다.

**필드명을 바꿀 때 낡은 산출물을 조용히 읽지 마라.** 로더가 모르는 옛 키를
무시했더니 조건이 사라지고 레코드가 접혔습니다 — 막으려던 뭉뚱그린 범위가 칸
이름을 바꾸다가 재현됐습니다. 지금은 거부합니다.

### 산문·문서에서 뽑을 때

**블록의 첫 단위 토큰을 믿지 마라.** 초를 시간으로 읽어 3,600배 어긋난 값이
있었습니다. 이름에서 먼저 찾고, `in X` 선언을 보고, 환산 괄호는 떼고, 그래도
갈리면 단위를 붙이지 않습니다.

**시리즈 라벨은 산문이다.** Azure 생애주기 문서의 "Dv2 and Dsv2-series" 같은
라벨은 크기 이름이 아닙니다. 손 표로 정규식을 만들되, **문서와 손 표의 상호
대조를 빌드에 내장**해 어느 쪽이 낡아도 시끄럽게 죽게 합니다.

**HTML에서 조각 링크를 버리지 마라.** `href="...#section"`을 거르는 정규식이
조각 붙은 링크 전체를 버렸습니다 — 자기 단위 테스트가 잡았습니다.

### 가격 데이터에서

**단위 문자열이 축을 정한다.** "vCore", "Throughput Unit", "RCU-Hrs"는 인스턴스
시간이 아니라 용량 단가입니다. 단위 규칙표 없이 담으면 축이 뒤섞입니다.

**serviceName의 경계를 확인하라.** 'Azure Cognitive Search'처럼 이름이 곧
경계인 경우와, meter 이름으로 걸러야 하는 경우가 섞여 있습니다.

**리전이 "Global"인 상품이 있다.** Azure 로드밸런서 가격은 리전 칸이 Global입니다.
리전 필터를 그대로 걸면 0건이 되고, 그건 "가격 없음"이 아닙니다.

**중복 행은 판별자를 찾을 때까지 의심하라.** AWS 관리형 가격에서 같은 키의 행이
443건 나왔습니다 — engine·deployment·license·edition 등 판별자를 더하니 195건이
됐고, 그래도 남은 'NA' 행 194건은 **버리되 셌습니다.**

**리전 코드는 회사를 특정하지 않는다.** `ap-northeast-2`는 AWS와 Alibaba가 같이
씁니다. "리전만 주면 회사를 알겠지"는 우리 기대가 틀린 것이었습니다.

### 정규식

**번역하지 말고 그 문법을 아는 엔진으로 읽어라.** 파이썬 `re`가 못 읽는 205건 중
194건은 원본이 틀린 게 아니라 .NET/PCRE 문법입니다. 근사 번역은 막지 말아야 할
것을 막는 쪽으로 틀립니다.

**앵커를 마음대로 붙이지 마라.** JSON Schema의 `pattern`은 규약상 부분 일치입니다.
앵커 없는 1,430건은 결함이 아닙니다. 반대로 우리가 손 표를 만들 땐 앵커를 꼭
칩니다 — 현행 세대를 구조적으로 배제하기 위해서입니다.

**어느 엔진에서도 안 도는 것은 고치지 말고 밝혀라.** 조용히 건너뛰면 "제약이
없다"로 읽힙니다.

### 한국어·환경 처리

**파이썬 `\b`·`\w`는 한글을 단어 문자로 봅니다.** 경계가 안 잡히거나 조사까지
이름에 붙습니다. 답을 아는 사례에 먼저 걸어 보지 않았으면 틀린 검사기로 24건을
돌리고 결과를 믿었을 것입니다.

**콘솔·셸 인코딩.** Windows에서 UTF-8을 모든 진입점에 명시해야 합니다. 그리고
**PowerShell로 한국어 파일을 정규식 치환하지 마세요** — 인코딩이 깨져 파일이
통째로 오염된 사고가 있습니다. 한국어 파일 편집은 전용 편집 도구로만 합니다.

### 검증할 때

**잘못 잡은 것을 그럴듯하게 만드는 수정은, 잘못 잡은 채 두는 것보다 나쁘다.**
대소문자 무시 매칭이 잘못 잡은 것을 실재하는 관계로 이어 옳은 것과 구분이 안
되게 했습니다.

**금지어 목록을 손으로 만들지 마라.** 취향이 아니라 규칙("KCC 부품 이름은 예외
없이 PascalCase")만이 다음 버전에서도 통합니다.

**"문제 없음이 확인된 영역"을 기록하라.** 재조사 낭비를 막습니다.

**대체 경로는 조용히 고장 납니다.** 커밋된 gz를 읽는 폴백이 `.gz`를 못 읽어 두
축만 0건이 된 적이 있습니다 — `output/`을 실제로 치워 보지 않았으면 못 봤을
것입니다. 테스트가 "미빌드 상태"를 검사할 때는 커밋 데이터가 끼어들지 않도록
기본 위치에서만 폴백합니다.

**검사 문자열이 다른 검사와 충돌하는지 보라.** 새 고지문에 쓴 표현이 기존 테스트의
금지 문자열과 충돌해 빌드가 죽은 적이 있습니다. 문구도 이름공간입니다.

cb-tumblebug ─┬─ 스펙·정가 73,083   (costkb의 (가) 전부)

- 제약의 **67.7%**가 aws+azure(95,533 / 141,377).
- 성능의 **79.9%**가 azure+aws. 관리형 가격의 **78.4%**가 azure 하나.
- 국내 CSP(ncp 427 · nhn 779 · kt 220스펙)는 **전 축에서 1% 미만**입니다.

원인은 명확하고 **우리 잘못이 아닙니다** — 공개 기계가독 소스가 그렇게
분포합니다. 그러나 결론에는 영향이 있습니다: **"이 가이드라인이 국내 클라우드에도
통하는가"에 지금 데이터로는 답할 수 없습니다.** 3장 격자가 이 사실의 지도입니다.

### (다) 검수가 1인 코더다 — 일치도 수치가 없다

`reviewed=true`는 사실 승격의 두 경로 중 하나인데(12장), 검수 절차 자체는
문서화돼 있지 않습니다. 두 번째 코더가 없고, 일치도를 잰 적이 없으며,
"가장 가깝다"의 기준이 재현 가능하게 적혀 있지 않습니다.

부록 A.4가 이 위험을 그대로 보여 줍니다 — Azure VM의 관계 46건이 **94% 이름 추론 +
사람 검수**입니다. 그 답의 신뢰도는 거의 전적으로 **한 사람의 판단**에 걸려
있습니다. 답변에 그 비율을 실어 방어하고 있지만(**방어와 검증은 다릅니다**).

**그래서 한 번 재봤습니다 (2026-07-28).** svcmap 엣지 69건 전부를 2차 코더가
독립 재판정했습니다. 기준은 판정 **전에** 못 박고 전 건에 같게 적용했습니다.

> "이 타입 **하나를 배포하면** 그 `app::` 개념의 기능을 얻는가?"
> ① 같은 서비스 범주인가 ② 부모가 따로 필요한 하위 리소스가 아닌가

| | |
|---|---:|
| 재판정 대상 (1차가 전부 `reviewed=True`로 승인) | 69건 |
| 동의 | 66 |
| 이견 | 1 |
| 유보(타입 이름만으로 못 가름) | 2 |
| **단순 일치율** | **95.7%** |
| 유보 제외 시 | 98.5% |

**결과보다 중요한 것은 어디서 갈렸나입니다.** 갈린 셋이 **전부 같은 라벨**에
몰렸습니다.

| 근거 라벨 | 건수 | 동의율 |
|---|---:|---:|
| `svcmap-cross-checked` (**두 소스가 같은 말 → 승급**) | 31 | **90.3%** |
| `mingrammer-taxonomy` | 17 | 100% |
| `svcmap-reviewed` (사람 검수만) | 16 | 100% |
| `ms-learn-comparison` | 5 | 100% |

**가장 강해야 할 라벨이 가장 약했습니다.** 이유가 설명됩니다 — 교차 확인은
**서비스 이름 수준**('Amazon RDS ↔ Azure SQL')에서 두 소스가 일치하는지를 보는데,
우리가 붙이는 것은 **타입 id 수준**입니다. 이름이 맞아도 입도가 어긋날 수
있고, 갈린 셋이 정확히 그 자리입니다.

- **이견 1건** — `app::relationalDatabase → azure::Microsoft.Sql/servers/databases`.
  이건 **하위 리소스**라 부모 서버 없이는 존재할 수 없습니다. 같은 개념의 다른
  Azure 엣지 둘(`flexibleServers`)은 최상위라 기준을 만족합니다. *두 판정 다
  변호 가능합니다* — 1차는 "개념의 대응"으로, 2차는 "배포 단위"로 봤습니다.
  그래서 **고치지 않고 남깁니다.** 불일치를 지우면 일치도를 잰 뜻이 없어집니다.
- **유보 2건** — `serverlessFunction → Microsoft.Web/sites`(Azure에 함수 전용
  타입이 없어 **다른 답이 없는데**, 그냥 배포하면 웹앱이 나옵니다) ·
  `eventStream → gcp::PubSubTopic`(**`messageQueue`에도 같은 타입**이라 GCP에서는
  두 설계 개념이 구별되지 않습니다). 둘 다 틀린 대응이 아니라 **타입 축만으로는
  표현이 안 되는 자리**입니다.

**이 수치의 한계를 분명히 적습니다.** 이건 **한쪽 방향만 본 검사**입니다 —
1차 코더가 **기각한 후보는 데이터에 남지 않으므로**, 우리가 잡을 수 있는 것은
"잘못 넣은 것"뿐이고 **"넣었어야 하는데 빠뜨린 것"은 못 잡습니다.** 같은 이유로
카파(κ) 같은 일치도 계수는 **계산할 수 없습니다** — 1차 판정에 범주가 하나뿐이라
우연 일치를 정의할 수 없습니다. 제대로 재려면 **기각 기록까지 남겨야** 합니다.

빠뜨린 쪽을 대신 본 것이 커버리지 표입니다. 주요 3사에서 빈 칸은 둘뿐이고
(`cdn → gcp` · `searchIndex → gcp`), 둘 다 **매핑 가능한지부터 확인이 필요한**
자리입니다(GCP CDN은 로드밸런서 백엔드 설정이라 독립 타입이 아닐 수 있습니다).

### (라) 측정 도구를 우리가 만들었다

- 프로브 질문은 **우리가 지어낸 것**입니다(21장). 실사용 질의 분포가 아닙니다.
- **영어 질의 프로브가 한 벌도 없습니다.** 도구 출력이 영어로 넘어갔는데
  영어로 물어본 측정이 없습니다. 라우팅이 질의 언어에 민감하다는 것은 우리가
  직접 쟀습니다(13장의 "로컬 SSD 용량" 누출) — 즉 **한국어에서 잰 결과가 영어에서
  성립한다는 증거가 없습니다.**
- 완화 장치는 있습니다: 무편향 조사는 **질문을 데이터 보기 전에 쓰고 정답지를
  답변 읽기 전에 만드는** 방식이라, 아는 것만 검사하는 편향을 막습니다(15장).
  이건 강점이므로 위협 목록에 함께 적어 둡니다.

### (마) 관측 코퍼스의 표본 편향

`observed` 값은 **"이 코퍼스에서 그렇게 나왔다"**이지 **"클라우드가 그렇게
강제한다"가 아닙니다.** Azure Quickstart는 데모 쪽으로 기울어 있어 VM과 스토리지
계정이 53.6%로 같이 나오는데, 그건 **옛 부트 진단 관행의 흔적**입니다. AWS 쪽은
코퍼스가 얇아(362개) RDS·EKS 앵커가 임계에 못 미칩니다 — **채운 척하지 않습니다.**

### (바) 재현 불가능한 소스가 5종, 그중 하나가 최대 근거다

`digest` 핀 5종은 원리적으로 재현이 안 됩니다. 규모를 밝히면:
**`cfn-schema` 하나가 전체 근거 라벨 중 최대인 46,911건**입니다. 즉 **이 저장소의
최대 근거가 재현 불가능한 소스**입니다. 보관해 둔 zip을 `--source-file`로 넘기면
그때 그 파일로 다시 만들 수 있지만, 그건 **우리 손에 있는 사본에 기댄 재현**이지
독립적인 재현이 아닙니다.

### (사) 스냅샷 하나뿐 — 신선도 정책이 없다

핀 47종이 전부 2026년 7월 시점입니다. **언제 낡는지 지켜보는 주기가 없습니다**
(21장). `digest` 소스는 재빌드할 때만 드리프트가 드러납니다. 부록 A.9가 나흘
만에 생긴 드리프트를 보여 주는데, 그건 **수치가 얼마나 빨리 늙는지**의 증거이지
갱신 절차가 아닙니다.

### 이 장을 어떻게 쓸 것인가

위 일곱 중 **(다)·(라)는 고쳐서 없앨 수 있고**(일치도 측정, 영어 프로브),
**(가)·(나)·(마)·(바)는 구조적**이라 밝히는 것이 최선입니다. **(사)는 정책의
문제**입니다. 무엇이 어느 쪽인지 갈라 적는 것이 이 장의 목적입니다 — 리뷰어가
"안 한 것"과 "못 하는 것"을 구별할 수 있어야 합니다.

## 23. 밖에서는 뭐라고 부르나 — 외부 표준·문헌 매핑

이 문서는 지금까지 **우리 말로만** 썼습니다. 그러면 규율끼리는 정합적인데
**자기참조**가 됩니다 — "왜 이 설계가 옳은가"의 답이 이 문서 안에만 있습니다.
그래서 여기서 밖에 댑니다.

**중요한 전제 둘.** ① 우리가 발명했다고 생각한 것 상당수는 **이미 이름이 있습니다.**
이름을 붙이면 방어가 쉬워집니다. ② 매핑은 **양방향**이어야 합니다 — 표준에 있는데
우리에게 없는 칸을 함께 내지 않으면 유리한 쪽만 고른 것입니다.

### (가) 우리가 만든 것 ↔ 이미 있는 이름

| 이 문서의 규율 | 밖에서의 이름 | 얻는 것 |
|---|---|---|
| "수집 범위 안이라 '없음'이 답" vs "범위 밖이라 모름"(13장) | **국소 폐쇄세계 가정**(local closed-world assumption) — 지식그래프 완전성 문헌의 표준 장치 | 임기응변이 아니라 **알려진 해법의 구현**이 된다 |
| 성립 / 불성립 / **모름** 3상태(6장) | **Kleene 강 3치 논리** — SQL의 NULL 의미론이 같은 것 | 조건 평가 순서 규칙("확실히 안 맞으면 불성립, 모르는 게 있으면 모름")이 **논리 규칙으로 정당화**된다 |
| `evidence` + `basis` + `reviewed`(12장) | **W3C PROV** 계열 프로버넌스 모델 (Entity / Activity / Agent, `wasDerivedFrom`, `wasAttributedTo`) | 산출물이 **표준 어휘로 교환 가능**해진다 |
| 핀 · sha256 · `_source`(4장 ②⑤) | **ISO/IEC 25012** 데이터 품질 특성의 *currentness · traceability · credibility* | 품질 주장이 **정의된 축**을 갖는다 |
| `references` · `contained_in` · `equivalent_to`(5장) | **OASIS TOSCA**의 관계 타입 (`DependsOn` · `HostedOn` · `ConnectsTo`)과 Requirements/Capabilities | 그래프가 **표준 토폴로지 모델**에 얹힌다 |
| `claim_check` 주장 대조기(14장) | **귀속성 평가**(생성문이 제시된 출처에 귀속되는가) · 그라운드니스 검증 | "프롬프트로는 못 고친다"에 **선행 연구의 자리**가 생긴다 |
| 무편향 조사 — 질문 먼저, 정답지 먼저(15장) | **사전등록**(pre-registration) · 맹검 평가 | 이미 하고 있는 강점인데 **이름이 없어 강점으로 안 읽혔다** |
| 라이선스 표기 어휘(17장) | **SPDX** 식별자 | 표기가 갈리지 않고 도구가 읽는다 |
| 소스 선정 절차(16장) | 체계적 문헌고찰의 **포함/배제 기준 + 흐름 기록** | "편의표본"이라는 지적에 답할 수 있다 |
| 22장 | 실험 소프트웨어공학의 **타당성 위협** 절 | 리뷰어가 찾는 자리가 생긴다 |

> 요구사항 쪽 관심사 축은 이미 **ISO/IEC 25010**에 양방향 매핑돼 있습니다
> (`docs/cloud-native-requirements.md`). 같은 저장소인데 **큰 축인 이쪽만 매핑이
> 없던 것**이 감사에서 지적된 불균형이었습니다.

### (나) 표준에 있는데 우리에게 없는 칸 ★

이쪽이 더 값이 큽니다. 유리한 매핑만 적으면 매핑을 안 한 것과 같습니다.

**TOSCA에 대고 보면**

| TOSCA의 개념 | 우리 상태 |
|---|---|
| `HostedOn` (호스팅 관계) | **AWS는 통째로 비어 있음** — 스키마에 담김 어휘가 없어 일부러 비웠습니다(5장). 표준에 대고 말하면 이 공백이 **결정**으로 읽히고, 안 대고 말하면 **누락**으로 읽힙니다 |
| Requirements / Capabilities 매칭 | **없음.** 우리는 "A가 B를 참조한다"만 말하고, "A가 요구하는 능력을 B가 제공한다"는 모델이 없습니다. 대체 후보를 고르는 일이 이 모델의 몫인데, 우리는 svcmap의 이름 대응으로 대신하고 있습니다 |
| 생애주기 인터페이스 (create·configure·start·stop·delete) | **부분.** 생성 순서와 삭제 영향은 답하지만 **연산 단위 모델은 없습니다** |
| Topology Template (실제 배치 인스턴스) | appkb의 배포 계획이 가장 가깝지만 **TOSCA 타입 체계가 아닙니다** |

> **"왜 TOSCA를 안 썼나"에 대한 답**도 여기 적어 둡니다: TOSCA는 **토폴로지를
> 기술하는 언어**이지 벤더 타입별 사실(한도·가격·성능)을 담는 창고가 아닙니다.
> 우리가 필요한 것은 "이 값이 허용되나"에 근거를 달아 답하는 것이고, 그 자리는
> TOSCA에 없습니다. 다만 **그래프 축의 관계 어휘는 TOSCA에 맞출 수 있고**,
> 그러면 위 표가 곧 로드맵이 됩니다.

**PROV에 대고 보면**

| PROV의 개념 | 우리 상태 |
|---|---|
| `Entity` (산출물) · `wasDerivedFrom` | **있음** — 레코드와 `evidence`가 그것입니다 |
| `Agent` (누가 했나) · `wasAttributedTo` | **없음.** `reviewed`가 **참/거짓 하나**라서 **누가 검수했는지가 어디에도 없습니다.** 22장 (다)의 "1인 코더" 위협이 여기서 구조로 드러납니다 — 코더가 여럿이 돼도 지금 자료구조로는 구별할 수 없습니다 |
| `Activity` (언제 무엇이 돌았나) | **부분** — 소스를 받은 시각은 있으나 **파서 실행이 활동으로 기록되지 않습니다** |
| `wasRevisionOf` (이전 판) | **없음.** 레코드가 바뀌었을 때 이전 값과의 관계를 남기지 않습니다 |

**ISO/IEC 25012에 대고 보면**

| 품질 특성 | 우리 상태 |
|---|---|
| *traceability* (추적성) | **강함** — 이 저장소의 중심 |
| *credibility* (신뢰성) | **강함** — `basis`가 정확히 이것 |
| *currentness* (최신성) | **절반** — "언제 것"은 알지만 **언제 낡는지 보는 주기가 없습니다**(22장 (사)) |
| *consistency* (일관성) | **있음** — 쓰기 전 불변식(4장 ④) |
| *completeness* (완전성) | **선언만 있고 측정이 없습니다.** "수집 범위"는 우리가 밝히는 것이지 잰 것이 아닙니다 |
| *accuracy* (정확성) | **측정하지 않습니다.** 정답지(gold set)가 없어 "이 값이 실제와 맞는가"를 잰 적이 없습니다. 교차 검증(두 소스가 같은 말)이 대용이지만 **정확성 측정이 아닙니다** |

마지막 두 줄이 이 표에서 가장 정직한 부분입니다. **우리는 "출처를 밝히는 일"은
아주 잘하고, "맞는지 재는 일"은 하지 않았습니다.** 두 축이 다르고, 지금까지
이 문서는 앞의 축만 이야기했습니다.

## 24. 한 장 요약

만들 사람이 기억할 것을 줄이면 이것입니다.

1. **소스를 못 박아라.** 안 그러면 "고쳤다"를 증명할 수 없다.
2. **기계가 읽으라고 만든 것을 써라.** 산문은 표·자문·예외 기록으로만.
3. **레코드마다 어디서 왔는지(evidence)와 어떻게 아는지(basis)를 적어라.**
   라벨 하나에 성격 하나.
4. **여러 줄이 모여 생기는 모순을 쓰기 직전에 검사하라.** 시끄럽게 죽는 쪽이 낫다.
5. **조건을 담아라.** 안 그러면 어떤 실제 설정에도 맞지 않는 범위가 된다.
6. **모름을 3상태로 유지하라.** 어느 쪽으로 접어도 거짓이 된다. 부재는 안전도
   최신도 허용도 아니다.
7. **"없다"와 "안 봤다"를 다른 문장으로 답하라.** 합계는 부분만 알면서 내지 마라.
8. **막다른 길을 답으로 바꿔라.** 모델은 매번 다른 문으로 들어온다.
9. **판정은 사실로, 선택은 근거 달린 권고로, 단정은 하지 마라.** 권고는 상충
   없는 선택지가 하나일 때만.
10. **모델을 끼우고 재라.** 그리고 검사가 실패하면 **검사 기대부터 의심하라** —
    우리 기대가 틀려 있던 적이 시스템이 틀린 적보다 많았다.

그리고 마지막으로, 이 프로젝트에서 가장 자주 재확인한 것:

> **재지 않고 판단하면 확신에 찬 오답이 나옵니다.** 만드는 사람도 예외가 아닙니다.
> 이 문서의 수치는 전부 코드와 데이터에서 다시 뽑은 것이고, 그 과정에서 제 기억이
> 여러 번 틀렸습니다.

## A.1 조건이 답을 가른다 — 그리고 조건을 모르면 3상태 (6·13장)

## A.5 짐작한 자리를 짐작이라고 말한다 (12장)

같은 함수, 두 인스턴스. **단정과 유보가 갈립니다.**

```python
perf.instance_profile("aws", "t3.micro")
```
```
  Sustained CPU performance: not guaranteed
    ⚠ Burstable instance — performance drops to baseline once the CPU credits run out.
  generation: current generation
```

```python
perf.instance_profile("aws", "m5.large")
```
```
  Sustained CPU performance: guaranteed (a guess from the naming convention)
    ⚠ A type AWS does not classify as burstable — sustained performance is inferred
      from that.
  generation: previous generation
  network: Up to 10 Gigabit
    ⚠ Network bandwidth is burst ('Up to'), not a sustained value.
```

`t3.micro`의 "not guaranteed"는 AWS가 **직접 말한 것**이고, `m5.large`의 "guaranteed"는
**필드가 말하지 않은 것에서 우리가 뒤집어 얻은 것**입니다. 그래서 뒤에만 괄호가 붙습니다.
이게 12장의 `aws-burstable-field`(stated) / `aws-non-burstable-inferred`(inferred) 두 라벨이

```python
perf.compare("aws", ["t3.large", "m5.large"])

  EBS max bandwidth (burst): t3.large=2780 Mbps / m5.large=4750 Mbps
  ⚠ t3.large: Burstable instance — performance drops to baseline …
  ⚠ m5.large: This is a previous-generation instance …
※ 'Faster' depends on the workload (CPU-bound vs IO-bound), so no winner is declared.
  Cross-provider comparison is impossible because the axes differ.
```

상시 대역폭은 t3가 높고 버스트 최대는 m5가 높습니다 — **한 줄로 접으면 어느 쪽으로 접든
거짓**이라 접지 않습니다.

**컴퓨트 방식은 고르지 않았습니다** — 상충 없는 후보가 셋이라서입니다(11장).

```
Compute method comparison — 2 components with no deployHint (currently assumed VM):
  VM:         cheapest t3a.medium $0.0468/h (one instance)
  k8s:        node minimum memoryGiB 4.0GiB · node minimum vCPU 2 · 2 subnets required
              · the value is per node group, not per component
  Serverless: no hourly rate (billed per invocation and usage) · ? stateless unconfirmed
              — fit verdict held

No recommendation — methods with no conflict: VM, k8s, serverless. The measured axes
alone give no ground for picking one, so we do not pick (an arbitrary pick is the
failure this repository guards against). The deciding inputs (team skills, latency
requirements, and the like) are outside this verdict — specify one with deployHint
and we follow it.
```

## A.8 계약 위반은 지어내지 않고 목록으로 (11장)

```python
contract.validate_design({"schemaVersion": "1", "components": [{"id": "x", "name": "X"}]})
```
```
[schema] (top level): 'name' is a required property
[schema] (top level): 'artifacts' is a required property
```

`RESOURCE_SPEC` 쪽은 **왜 그 칸이 필수인지까지** 답합니다 — 필수의 기준이 목록이 아니라
판정식이기 때문입니다("그 칸이 없으면 뒤 단계 산출물의 요구사항 부합을 잴 수 없는 것만 필수").

```python
contract.validate_request({"schemaVersion": "1", "provider": "aws", "region": "서울"})
```
```
[required] monthlyBudgetUSD missing — it is the yardstick for judging whether cost fits
  the requirement (USD)
[required] no scale signal (expectedConcurrentUsers or approxRequestsPerSecond) — it is
  the basis for the sizing verdict; without it every spec recommendation is arbitrary
```

> `region`에 `"서울"`이 그대로 들어간 것은 **잡히지 않습니다.** 지명은 계약 진입 전에
> 리전 해석 도구로 코드(`ap-northeast-2`)로 바꿔 담아야 하고, 그대로 오면 조인이
> **조용히 빈 답**이 됩니다(실측). 계약이 못 잡는 것이 있다는 것도 실물로 봐 둘 값이 있습니다.
