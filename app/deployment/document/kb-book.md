# 클라우드 지식베이스 만들기 — 처음부터 끝까지

이 문서 하나만 읽고도 **같은 것을 처음부터 다시 만들 수 있게** 쓴 글입니다.
클라우드를 잘 몰라도 읽을 수 있게 용어를 그때그때 풀어 씁니다.

> **읽는 순서 안내**
> 0장은 용어표입니다. 1~3장은 "왜 이런 게 필요한가"이고, 급하면 4장(전체 그림)부터 읽어도 됩니다.
> 실제로 만들려면 9장(재현 절차)으로 가세요. 12장(함정 모음)은 **직접 겪은
> 실패**만 모은 곳이라, 만들 사람에게 가장 값이 클 겁니다.

---

## 0. 먼저 알아야 할 말 몇 개

이 문서는 되도록 평범한 말로 씁니다. 다만 **코드에 실제로 그 이름으로 들어 있는
것**은 바꿔 쓸 수 없어서 그대로 둡니다. 여덟 개뿐입니다.

| 말 | 뜻 | 예 |
|---|---|---|
| **리소스** | 클라우드에서 만드는 것 하나 | 가상 서버, 네트워크, 디스크 |
| **타입** | 리소스의 종류 | `AWS::EC2::Instance`(아마존 가상 서버) |
| **속성** | 리소스에 채워 넣는 칸 | 디스크의 `Size`, 서버의 `InstanceType` |
| **스키마** | 회사가 공개한 설명서 파일. "이 타입에는 이런 속성이 있고, 이 속성은 숫자이며 최댓값은 얼마"가 적혀 있다 | |
| **레코드** | 우리가 저장하는 **사실 한 줄** | "gp2 디스크의 최대 크기는 16,384 GiB다" |
| **제약** | 값에 걸린 조건 한 줄 (레코드의 한 종류) | 최소·최대·허용 목록·못 바꿈 |
| **`evidence`** | 그 레코드가 **어느 소스의 무엇**에서 나왔는지 적는 칸 | `cfn-schema` |
| **`basis`** | 원본이 **그렇게 말한 것**(`stated`)인지, 우리가 **짐작한 것**(`inferred`)인지 | |

그리고 자주 나오는 표현 셋을 미리 풀어 둡니다.

- **원본 / 상류** — 우리가 가져다 쓰는 클라우드 회사의 공개 파일. 우리가 만든 게
  아니라 저쪽이 만든 것.
- **결과 파일(산출물)** — 우리 프로그램이 만들어 저장하는 JSON 파일.
- **직접 재 봤다(실측)** — 추측이 아니라 실제로 프로그램을 돌려 숫자를 세어 봤다는 뜻.
  이 문서의 숫자는 전부 그렇게 얻은 것입니다.

## 1. 무엇을 만들려는 건가

클라우드에 서비스를 올리려면 여러 **리소스**를 순서대로 만들어야 합니다. 리소스란
가상 서버, 네트워크, 디스크, 데이터베이스 같은 것들입니다. 문제는 이것들이 서로
얽혀 있다는 점입니다.

- 가상 서버를 만들려면 먼저 네트워크가 있어야 합니다.
- 디스크는 크기에 상한이 있는데, **디스크 종류마다 상한이 다릅니다.**
- 어떤 설정값은 한 번 정하면 **영영 못 바꿉니다.** 바꾸려면 리소스를 지우고 새로
  만들어야 하고, 그러면 그 안의 데이터가 사라질 수 있습니다.

사람이 이걸 다 외울 수 없어서 AI 에이전트에게 맡깁니다. 그런데 **AI는 그럴듯한
거짓말을 합니다.** "EBS 디스크는 최대 16TB입니다" 같은 말을 자신 있게 하는데,
그게 어제까지는 맞았고 오늘은 틀릴 수 있습니다.

그래서 **에이전트가 참고할 사실 창고**를 따로 만듭니다. 그게 이 지식베이스(KB)입니다.

### 이 프로젝트가 막으려는 단 하나

> **확신에 찬 오답.**

틀린 답보다 나쁜 것은 **틀린 답에 우리 보증이 찍혀 나가는 것**입니다. 사용자가
"이건 검증된 데이터겠지" 하고 믿는데 사실은 AI가 지어낸 것이라면, 지식베이스가
없느니만 못합니다.

아래 모든 설계 결정이 이 한 문장에서 나옵니다.

## 2. 두 가지 기본 원칙

### 원칙 1 — 확실하지 않으면 막지 마라

확실하지 않으면 **막지 않습니다.** 우리가 모른다고 해서 사용자가 못 하게 하면
안 됩니다.

단, 여기 함정이 있습니다.

> **침묵이 "문제 없음"으로 읽히면 안 됩니다.**

"제약이 없습니다"와 "우리가 안 봤습니다"는 **전혀 다른 말**인데, 아무 말도 안 하면
둘이 똑같아 보입니다. 실제로 우리 KB가 구글 리소스 527종 전부에 "제약 없음"이라고
답한 적이 있습니다 — 사실은 구글 데이터를 **읽지도 않은** 상태였습니다.

이 원칙은 "짐작으로 막지 마라"이지 **"짐작을 숨겨라"가 아닙니다.**
(영어 문헌에서는 이런 태도를 *fail-open*이라고 부릅니다.)

### 원칙 2 — 데이터가 먼저

목표는 **완벽한 데이터셋**이지 완벽한 파서(추출 프로그램)가 아닙니다.

근거가 있습니다. dbt라는 회사가 통제 실험을 공개했는데, AI에게 데이터베이스 질문을
시켰을 때 정답률이 이렇게 나왔습니다.

| 조건 | 정답률 |
|---|---|
| 원시 스키마 그대로 | 64.5% |
| **데이터를 잘 정리한 뒤** | **90.0%** |
| 그 위에 질의 계층까지 얹은 뒤 | 98.2% |

**64.5 → 90이 데이터 정리의 몫**이고, 인터페이스를 아무리 다듬어도 마지막 8점입니다.
그래서 우리는 도구를 예쁘게 만드는 것보다 데이터를 늘리고 고치는 데 시간을 씁니다.

## 3. 왜 지식을 넷으로 나눴나

한 덩어리로 만들면 "무엇을 모르는지"를 알 수 없습니다. 축을 나누면 각 축이 자기
**무엇까지 훑었는지(수집 범위)**를 스스로 말할 수 있습니다.

| 축 | 답하는 질문 | 비유 |
|---|---|---|
| **graphkb** | 무엇이 무엇을 필요로 하나 | 부품 조립 순서도 |
| **capacitykb** | 무엇이 허용되나 · 한도 · 바꿀 수 있나 | 부품 규격서 |
| **costkb** | 무엇을 살 수 있고 얼마인가 | 가격표 |
| **perfkb** | 얼마나 빠른가 · 함정은 없나 | 성능 시험 성적서 |

**중요한 규약이 하나 있습니다.**

```
에이전트 → KB   (한 방향으로만)
KB ↛ KB         (지식베이스끼리는 서로 부르지 않는다)
```

축끼리 직접 부르면 순환이 생기고, 한 축의 결함이 다른 축으로 번집니다. 축을 합쳐야
하는 일(예: 추천 목록에 성능 경고 붙이기)은 **도구 계층**(`nim_agent/`)에서 합니다.
현재 KB 패키지들이 에이전트를 import하는 곳은 **0건**입니다.

## 4. 전체 그림 — 데이터가 지나는 길

```
 ① 소스            ② 핀            ③ 파서           ④ 쓰기 전 검사  ⑤ 결과 파일
공개 스키마  →  버전 고정  →  레코드로 변환  →  쓰기 관문  →  JSON 파일
                                                                      │
                                       ⑧ 도구  ←  ⑦ 표시  ←  ⑥ 질의 ─┘
```

각 단계를 순서대로 설명합니다.

### ① 소스 — 어디서 가져오나

**사람이 읽는 문서를 긁지 않습니다.** 클라우드 회사들이 **기계가 읽으라고 공개한
스키마**를 씁니다. 스키마란 "이 리소스에는 이런 속성이 있고, 이 속성은 숫자이며,
최댓값은 얼마"를 적어 둔 파일입니다.

왜 문서 대신 스키마인가: 문서는 사람이 쓰고 사람이 고치므로 표현이 제각각이고
자주 틀립니다. 스키마는 회사의 배포 시스템이 실제로 쓰는 것이라 **틀리면 그 회사가
먼저 아픕니다.**

### ② 핀 — 버전을 못 박는다

**이게 없으면 나머지가 전부 흔들립니다.**

소스는 계속 바뀝니다. 오늘 "제약 47,070건"을 뽑았는데 내일 다시 돌려서 47,109건이
나오면, **우리가 고친 건지 원본이 바뀐 건지 알 수 없습니다.** 사람이 손으로 검수한
결과가 다음 빌드에서도 유효한지도 말할 수 없습니다.

그래서 소스마다 "정확히 이 버전"을 박아 둡니다. 네 가지 방식이 있습니다.

| 방식 | 뜻 | 예 |
|---|---|---|
| `tag` | 저장소가 붙인 버전 태그 | cb-tumblebug `v0.12.25` |
| `commit` | 태그가 쓸모없을 때 커밋 고유번호 | bicep-types-az `ef7421bb…` |
| `digest` | **버전 개념이 아예 없는 소스** | AWS CloudFormation zip |
| `bundled` | 우리 저장소 안의 파일 (사람 검수표) | 매핑표 |

`digest`가 정직한 항복입니다. AWS는 스키마 zip 파일 **하나를 계속 덮어씁니다.**
고정할 URL이 없습니다. 그래서 받은 파일의 지문(sha256)을 기록해 두고, 다음에
달라지면 **알립니다.** 재현은 못 해도 **바뀐 사실은 놓치지 않습니다.**

> 효과가 실측으로 확인됐습니다. 재빌드했을 때 고정된 소스는 결과가 **완전히
> 동일**했고(Azure 그래프 3,382노드/2,306엣지, 비용 73,083건 등 전부 불변),
> **고정 불가능한 AWS만** 46,810 → 47,109로 변했습니다. 핀이 실제로 작동한다는
> 증거이자, AWS는 원리적으로 재현이 안 된다는 증거이기도 합니다.

### ③ 파서 — 스키마를 레코드로

파서는 스키마 파일을 읽어 **레코드 한 줄씩** 만듭니다. 레코드는 "사실 하나"입니다.

### ④ 쓰기 전 검사 — 저장하기 직전의 관문

레코드 하나하나는 멀쩡한데 **여러 줄이 모이면 모순**인 경우가 있습니다. 예를 들어

```
기본값 = 0        ← 한 줄
최솟값 = 10       ← 다른 줄
```

각각은 문법에 맞지만 함께 보면 말이 안 됩니다(기본값이 최솟값보다 작다). 스키마
검사는 **한 줄의 모양만** 보므로 이걸 못 잡습니다. 그래서 파일을 쓰기 **직전에**
레코드 사이의 관계를 검사하는 층을 뒀습니다.

심각도가 둘입니다.

- **`error`** — 우리 잘못이고 고칠 수 있다 → **파일을 아예 쓰지 않는다**
- **`report`** — 우리 권한 밖(상류가 그렇다) → 쓰되 **건수를 반드시 말한다**

전부 `error`로 만들지 않은 이유: 그러면 **원본을 그대로 베낀 사본을 만들 수
없습니다.** costkb가 하는 일이 바로 그것인데, 원본이 모순이라고 우리가 값을 고치면
그 순간 사본이 아니게 됩니다.

현재 쓰이는 검사 규칙(9개가 `error`, 2개가 `report`):

| 이름 | 무엇을 막나 |
|---|---|
| `default-within-bounds` | 기본값이 자기 최소/최대를 위반 |
| `read-only-not-required` | 읽기 전용인데 "네가 채워라"라고 표시 |
| `one-basis-per-evidence` | 근거 라벨 하나가 두 성격을 겸함 |
| `no-casing-duplicate-ids` | 대소문자만 다른 같은 타입이 둘로 존재 |
| `edges-point-at-real-nodes` | 관계가 없는 리소스를 가리킴 |
| `region-invariant-signals` | "리전 불변"이라는 **가정을 매번 검사** |
| `no-negative-measurements` | 음수 크기 |
| `accelerator-fields-agree` | GPU가 있다는데 개수가 0 |
| `disk-size-zero-is-ambiguous` | (report) 0이 사실인지 미기입인지 못 가림 |

### ⑤~⑧ 산출물부터 도구까지

산출물은 JSON 파일입니다. 질의 계층이 그걸 읽어 **사람이 읽을 한국어 문장**을 만들고,
도구 계층이 에이전트에게 노출합니다. 자세한 건 7~8장에서 다룹니다.

## 5. 네 축을 하나씩

### 5-1. graphkb — 무엇이 무엇을 필요로 하나

**3계층 구조**입니다.

```
공통 층   (회사 무관)     vm, vNet, subnet …          13종
   ↕ 매핑 레이어 (동치 관계)
회사별 층  aws 1,638종 · azure 3,382종 · gcp 527종
```

공통 층은 CB-Tumblebug이라는 오픈소스의 모델에서 가져옵니다. 다루는 범위는
좁지만 **정확하고 특정 회사에 매이지 않아** "AWS의 이것이 Azure에선 무엇인가"를 잇는 기준점이
됩니다.

**레코드 예시** (실제 데이터):

```json
{
  "from": "aws::AWS::ACMPCA::Certificate",
  "to":   "aws::AWS::ACMPCA::CertificateAuthority",
  "type": "references",
  "via_property": "CertificateAuthorityArn",
  "required": true,
  "cardinality": "one",
  "evidence": "cdk-oob",
  "basis": "stated",
  "reviewed": true
}
```

읽는 법: "인증서는 인증기관을 **참조한다**. `CertificateAuthorityArn`이라는 칸을
통해서다. **필수**이고 하나만 가리킨다. 근거는 AWS CDK가 배포하는 관계표이고,
원본이 그렇게 **말한 것**이며, 사람이 검수까지 했다."

관계 종류는 셋입니다.

- `references` — 참조한다 (A가 B의 id를 자기 칸에 적는다)
- `contained_in` — 담겨 있다 (B 안에 A가 산다)
- `equivalent_to` — 같은 것이다 (클라우드 회사가 달라도 같은 개념)

#### 필수성은 조상과의 논리곱이다 ★

여기가 **가장 틀리기 쉬운 곳**입니다. 실제로 우리가 틀렸었습니다.

스키마에서 "이 칸은 필수"라는 표시는 **그 칸이 속한 부모 객체 안에서만** 필수라는
뜻입니다. 부모 자체가 선택이면 전체적으로는 선택입니다.

```
properties
└ storageProfile
  └ osDisk
    └ encryptionSettings          ← 선택 (디스크 암호화를 안 쓸 수 있다)
      └ diskEncryptionKey
        └ sourceVault  ← "필수"    ← 암호화를 쓴다면 필수라는 뜻
```

이걸 그대로 리소스 필수로 끌어올렸더니 이런 답이 나왔습니다.

> "Azure 가상머신을 만들려면 **KeyVault**가 먼저 있어야 합니다."
> (네트워크 인터페이스는 **선택**으로 표시)

**정확히 거꾸로**입니다. 디스크 암호화는 선택이고, 네트워크 인터페이스는 없으면
가상머신을 못 만듭니다.

올바른 규칙: **경로상 모든 조상이 필수일 때만 리소스에 필수.**
고친 뒤 오염된 타입이 59종 → 25종이 됐습니다(Azure 15→1, GCP 25→5).

#### 필수 표시가 없다고 "바로 만들어도 된다"고 하지 마라 ★

위를 고쳤더니 이번엔 **반대 방향 거짓말**이 나왔습니다.

> "반드시 먼저 만들어야 하는 선행 리소스가 없습니다. **바로 생성할 수 있습니다.**"

Azure 가상머신은 네트워크 인터페이스 없이 못 만듭니다. 스키마가 그걸 필수로 표시하지
않을 뿐입니다. **스키마의 필수 표시와 실제 배포 요건은 다릅니다.**

말하지 않는 것을 허가로 바꾸면, 막지 않는 게 아니라 그냥 틀린 말이 됩니다. 지금은 이렇게 답합니다.

> "스키마가 **필수로 표시한** 선행 리소스가 없다는 뜻이며, 실제로 아무것도 필요
> 없다는 뜻이 아닙니다. …아래 '함께 쓸 수 있는 것'을 함께 보세요."

#### AWS의 "담김" 축은 일부러 비워 뒀다 ★

GCP는 `projectRef` 같은 참조로 "이 리소스는 어느 프로젝트에 속한다"를 말합니다.
설명문에도 *"The project that this resource belongs to"*라고 적혀 있습니다(296개 중
273개). GCP는 타입 이름이 평평해서 **이 참조가 유일한 계층 신호**라 378건을 담았습니다.

AWS는 **만들지 않았습니다.** CloudFormation 스키마에 담김을 뜻하는 어휘가 아예
없기 때문입니다(전수 확인). "필수 참조를 담김으로 치자"는 짐작인데, 맞는 것
(`Certificate → CertificateAuthority`)과 애매한 것(`Instance → Subnet`)이 섞여 있어
뭉뚱그리면 정확히 우리가 막으려는 확신에 찬 오답이 됩니다.

**빈 축을 비워 두고 이유를 코드에 적는 것**도 결정입니다.

### 5-2. capacitykb — 무엇이 허용되나

가장 큰 축입니다. 현재 **제약 101,944건**(aws 51,197 · azure 43,824 · gcp 6,923)과
**쿼터 542건**.

#### 레코드 형식

```json
{
  "type_id": "aws::AWS::RDS::DBInstance",
  "property": "DBInstanceClass",
  "kind": "enum",
  "value": ["db.m5.12xlarge", "db.m5.16xlarge", "…"],
  "unit": null,
  "note": null,
  "evidence": "cfn-lint-conditional",
  "basis": "stated",
  "backend": null,
  "conditions": [
    {"property": "Engine",        "op": "eq",      "value": "aurora-mysql"},
    {"property": "EngineVersion", "op": "matches", "value": "^(10\\.11\\..+|10\\.11)$"}
  ]
}
```

칸별로 봅니다.

| 칸 | 뜻 |
|---|---|
| `type_id` | 어느 리소스 타입인가 (`회사::타입이름`) |
| `property` | 어느 속성인가. 중첩은 `a.b.c` 또는 `a/b/c` |
| `kind` | 제약 종류 (아래 표) |
| `value` | 제약 값 |
| `unit` | 단위 (`GiB`, `IOPS` 등) |
| `evidence` | **어느 소스의 무엇에서 나왔나** |
| `basis` | `stated`(원본이 말함) / `inferred`(우리가 짐작) |
| `backend` | 상류 파이프라인 (GCP 전용, 뒤에 설명) |
| `conditions` | **언제 적용되는가** (핵심, 뒤에 설명) |

현재 쓰이는 `kind` 15종:

```
mutability 38,260  required 26,155  max_length 8,149  min_length 7,204
pattern     6,813  max_items 4,477  enum      3,814  min_items  2,098
min         2,046  max       1,514  default   1,030
at_least_one_of 222  conflicts_with 82  exactly_one_of 69  required_with 11
```

#### 뭉뚱그린 범위 — 이 축이 존재하는 핵심 이유 ★

디스크 크기 한도는 **디스크 종류마다 다릅니다.**

| 종류 | 최소 | 최대 |
|---|---:|---:|
| gp2 | 1 | 16,384 |
| gp3 | 1 | 65,536 |
| io1 | 4 | 16,384 |
| st1·sc1 | 125 | 16,384 |
| standard | 1 | 1,024 |

이걸 최소·최대 한 쌍으로 뭉개면 **1 ~ 65,536**이 됩니다. 그런데 이 범위는
**어떤 실제 설정에도 해당하지 않습니다.** `standard` 디스크에 5,000을 넣으면
실제로는 불가능한데 이 뭉뚱그린 범위는 통과시킵니다.

이렇게 서로 다른 조건의 값을 하나로 뭉개서 **아무에게도 맞지 않는 범위**가 되는
것을, 이 문서에서는 **뭉뚱그린 범위**라고 부릅니다. 조건을 담는 칸이 필요한 이유가 이것입니다.

쓰기 전 검사로 재발을 막습니다 — 같은 `(타입, 속성, 종류)`에 조건 있는 레코드와 없는
레코드가 **공존하면 쓰기를 거부**합니다. 둘이 섞이면 어느 쪽이 이기는지 아무도
모르기 때문입니다.

> **중복 판정 키에도 조건을 넣어야 합니다.** 안 넣으면 종류별 6개 레코드가 "같은
> 제약"으로 판정돼 하나로 접히고, **조건을 담으려던 것이 도로 뭉뚱그린 범위가 됩니다.**

#### 조건은 목록이고, 연산자가 둘이다

처음에는 조건 **하나**만 담았습니다. 실제 필요 사례가 4건뿐이었기 때문이고,
그 판단은 **그때는 옳았습니다.**

나중에 데이터베이스 인스턴스 종류에서 **조건이 둘인 경우**를 만났습니다.

```
Engine = "aurora-mysql"  그리고  EngineVersion 이 "16.9" 꼴
   → 쓸 수 있는 인스턴스 종류 목록
```

버전은 등호로 못 씁니다(16.9, 16.9.1, 16.9.2가 다 해당). 그래서 `op`를 둘로 넓혔습니다.

- `eq` — 그 값일 때
- `matches` — 그 **패턴**에 걸릴 때 (정규식. `16.9`, `16.9.1`처럼 한 묶음을
  한 줄로 적는 표기법)

#### 판정은 3상태다 ★

조건이 성립하는지 볼 때 답이 셋입니다.

| 상태 | 뜻 |
|---|---|
| 성립 | 문맥이 조건과 맞다 |
| 불성립 | 문맥이 조건과 다르다 → 이 제약은 해당 없음 |
| **모름** | 문맥에 그 속성이 없다 |

**모름을 어느 쪽으로든 접으면 거짓이 됩니다.** 성립으로 치면 gp2 디스크에 gp3 한도를
적용하고, 불성립으로 치면 아는 제약을 통째로 버립니다.

조건이 여럿일 때 **순서가 중요합니다.**

> **하나라도 확실히 안 맞으면 안 맞는다**(불성립). 안 맞는 게 없고 모르는 게 있으면
> 모름. 셋 다 아니면 성립.

왜 이 순서인가: 엔진은 알고 버전은 모르는 경우가 흔합니다. 그때 엔진이 다르면 그
블록은 **확실히** 해당 없음입니다. 이걸 모름으로 접으면 938개 블록이 전부 미결로
남아 **아무것도 못 답합니다.** 실측에서 엔진만 줘도 후보가 67개로 좁혀지고
"67가지 전부 불가"라는 확정 답이 나왔습니다.

#### capacitykb의 소스들

| 소스 | 무엇을 주나 | 수확 |
|---|---|---:|
| CloudFormation 레지스트리 스키마 | AWS 속성 제약 | 46,911 |

없어서가 아니라 **변환기가 떨어뜨립니다** — Bicep 타입에는 "불변" 플래그가 없어서

그 결과 (당시) Azure 타입 3,371종 **전부**가 "변경 불가로 알려진 속성이
없습니다"라고 답하고 있었습니다. 원본 명세에서 그 필드 하나만 캐서 993건을 채웠습니다.

**AWS 디스크 한도는 두 소스가 같은 말을 한 것만.** 가격표 API와 SDK 문서를 교차
검증해 10쌍 전부 일치한 20건만 담았습니다. `gp2`의 IOPS는 한쪽에만 있어서
**담지 않았습니다** — gp2는 원래 IOPS를 지정하는 종류가 아닌데, 한쪽만 보고 담았으면

거짓이 됩니다.

### 5-3. costkb — 무엇을 얼마에 살 수 있나

CB-Tumblebug이라는 오픈소스가 배포하는 스펙·가격 데이터 파일을 **그대로 베낀
사본**입니다. 73,083건.

**"그대로 베낀다"가 중요합니다.** 에이전트에는 실시간 조회 경로도 있는데, 두 경로가 다른
답을 하면 사용자가 혼란스럽습니다. 그래서 우리는 값을 **고쳐 쓰지 않습니다.**

한 가지 예외가 있고, 그 예외에도 근거가 있습니다. 상류 소프트웨어에 메모리 단위
변환 버그가 있어서 GCP·Azure 값이 실제보다 2.4% 낮습니다. 우리는 **두 값을 다**
싣습니다.

- `memGiB` = 62.5 (상류 값 그대로 — 실시간 경로와 답이 같아야 하니까)
- `memGiBActual` = 64 (보정값)

보정을 **회사 이름으로 코드에 박아 두지 않습니다.** 빌드할 때 데이터 지문을 잽니다
— "결과 MiB가 1000의 배수인 비율"이 임계치 아래면 크게 실패시킵니다. 왜냐하면
원본 쪽이 버그를 고친 파일을 내놓는 순간, 하드코딩된 보정은 **오류 방향을 조용히
뒤집기** 때문입니다.

### 5-4. perfkb — 얼마나 빠른가, 함정은 없나

같은 데이터 파일에서 뽑은 성능 신호입니다. 65,032건.

핵심은 **버스트 인스턴스 경고**입니다. 버스트란 "평소엔 느리다가 잠깐 빨라지는" 저가
인스턴스인데, 크레딧이 떨어지면 성능이 급락합니다. 가격만 보고 고르면 가장 싸서
1순위로 올라옵니다.

#### 침묵은 정보를 담아야 한다 ★

성능 경고 기능에 심각한 결함이 있었습니다. 함수가 네 경우에 **전부 `None`**을
반환했습니다.

1. 성능 정상
2. 두 데이터를 이어 붙일 키가 없음
3. 레코드가 없음
4. **그 클라우드 회사를 아예 추적하지 않음** (7,051건 / 9.6%)

넷의 출력이 **바이트 단위로 똑같았습니다.** 검증된 안전한 인스턴스와, 우리가 아무것도
모르는 인스턴스가 구별되지 않았습니다. **침묵을 안전 신호로 오독하게 만드는 구조라
자동 경고 기능 전체의 신뢰도가 무효**였습니다.

지금은 다섯 상태를 구분합니다: `warn` / `ok` / `no_record` / `untracked` / `not_built`.
경고는 `⚠`, 정보 없음은 `·`, 정상은 무표시로 두되 **블록 끝 꼬리말이 침묵의 의미를
한 번 밝힙니다.**

#### 판단 불가는 `False`가 아니다 ★

"네트워크가 버스트인가"를 `"Up to"로 시작하는가`로 판정하고 있었습니다. 그런데 실제
값이 **72종**이었습니다 — `High`, `Moderate`, `Low to Moderate`(t2 전 계열) 등.
그래서 t2 인스턴스에 버스트 경고가 안 붙었습니다.

`startswith`가 실패했을 때 `False`(=문제 없음)를 반환한 것이 잘못입니다.
**모르면 `None`이어야 합니다.**

같은 문제가 Azure에도 있었습니다. "CPU 성능이 보장되는가"를 "패밀리 이름이 `standardB`로
시작하지 않음"으로 판정해 **33,456건(Azure의 96%)**에 "보장됨"을 붙였습니다.
**부정은 이름 근거가 있지만 긍정은 근거의 부재**입니다.

## 6. 근거와 신뢰 — 숫자를 버린 이야기

처음에는 신뢰도를 **0.5~1.0 숫자**로 매겼습니다. 이걸 전부 버렸습니다.

이유가 셋입니다.

**(가) 척도의 정의가 어디에도 없었습니다.** 0.9와 0.95의 차이가 무엇인지, 두 근거를
합치면 어떻게 되는지 아무도 정의하지 않았습니다.

**(나) 라벨이 신뢰도의 함수가 아니었습니다.** 같은 근거 라벨에 여러 값이 붙어
있었습니다(`cfn-description`에 0.6/0.7/0.8). 0.85는 전 데이터셋에 **단 1건**이었습니다.

**(다) 실제로 쓰이는 건 임계선 하나뿐인데, 하필 가장 붐비는 값에 있었습니다.**
`0.8` 기준선이 실제로 가르는 건 158건이었고 그중 **115건이 정확히 0.8**이었습니다.
상수를 0.81로만 바꿔도 결과가 뒤집히는 상태였습니다.

지금은 **두 값**만 씁니다.

```
basis = "stated"    원본이 그렇게 적어 놓았다
      | "inferred"  우리가 이름·산문·구조에서 짐작했다

사실로 취급 = stated 이거나, 사람이 검수했다(reviewed)
```

그리고 규칙이 하나 있습니다.

> **근거 라벨 하나에 성격 하나.** 위반하면 라벨을 쪼갠다.

이건 실패에서 나왔습니다. 검수 파일에 `{"evidence": "kcc-ref"}` 한 줄로 승인했는데,
그 라벨이 **사실(대응표)과 짐작(설명문 정규식)을 겸하고** 있어서 짐작 322건까지
같이 승인됐습니다. 지금은 `one-basis-per-evidence`가 **error 등급**으로 막습니다.

### 비대칭을 대칭으로 옮기지 마라 ★

AWS API에 `BurstablePerformanceSupported`라는 칸이 있습니다. `true`면 버스트,
`false`면 아니라는 뜻처럼 보입니다. 그대로 옮겼더니 `t1.micro`가 **"상시 성능 보장"**
이라고 신뢰도 1.0으로 단언하게 됐습니다.

t1은 실제로 버스트 계열입니다. AWS가 `false`를 주는 이유는 t1이 크레딧 모델보다
**앞선 세대**라 그 필드에서 제외된 것이지, 성능이 보장돼서가 아닙니다.

**원본에 충실했는데 결과 명제가 사실과 반대**였습니다. 이 필드는 **한 방향만 직접
말합니다.**

```
true  → 버스트다        (stated)
false → 버스트가 아니다  (inferred — 우리 추론)
```

29,395건이 `inferred`로 바뀌었습니다. 중요한 건 **경고 경로는 영향이 없다**는
점입니다 — 경고는 `true`일 때 나가고 그건 여전히 `stated`입니다.

> **이름으로 예외 처리하지 않았습니다.** "t1만 특별 취급"으로 고쳤으면 다음 세대에서
> 같은 모양으로 재발합니다. 뿌리는 t1이 아니라 **비대칭을 못 본 것**입니다.

## 7. 질의 계층 — 데이터를 답으로

데이터가 맞아도 **말하는 방식이 틀리면** 사용자는 틀린 답을 받습니다. 이 층에서
겪은 것들입니다.

### 없다 / 안 봤다 / 못 읽었다 / 조합이 없다 — 넷을 구분한다 ★

전부 "모릅니다"로 답하면 안 됩니다.

| 상황 | 답변 |
|---|---|
| 수집 범위 안, 제약 없음 | "알려진 제약이 없습니다 (수집 범위 안이므로 '없음'이 답입니다)" |
| 수집 범위 밖 | "**수집 범위 밖**이라 모릅니다 — 제약이 없다는 뜻이 아닙니다" + 현재 범위 |
| 정규식을 못 읽음 | "제약은 있으나 그 정규식을 읽을 수 없습니다" + 원문 |
| 조건에 안 걸림 | "조건부 제약 938건이 있지만 **주신 조합에 걸리는 것이 없습니다**" |

마지막 것이 특히 중요합니다. "우리가 모른다"와 "당신이 준 조합을 우리가 모른다"는
**전혀 다른 신호**입니다 — 뒤쪽은 오타나 미지원 버전을 의심하라는 뜻입니다.

### 한도가 어느 조건에서의 것인지 밝힌다 ★

```
전: "30,000 GiB는 최대 16,384 GiB를 벗어남"
후: "30,000 GiB는 최대 16,384 GiB를 벗어남 (VolumeType='gp2' 일 때, …)"
```

앞 문장은 16,384가 보편 상한처럼 읽힙니다. 정작 사용자에게 필요한 사실은 **gp2에서의**
한도라는 것 — gp3로 바꾸면 65,536까지 됩니다.

> **한도를 어겼다는 말보다 어느 조건에서의 한도인지가 해결책을 가리킵니다.**

### 막다른 길을 답으로 바꾼다 ★★

이게 실측에서 가장 큰 수확이었습니다. 세 가지가 같은 부류입니다.

**(1) 값을 타입 이름으로 물었을 때.** 에이전트가 `p5.48xlarge`(인스턴스 종류)를
타입 이름으로 검색했습니다. 사람도 그렇게 묻습니다. 우리는 "노드를 찾을 수 없습니다"만
줬고, 에이전트는 **웹검색 13회에 14분**을 쓰고 "지식베이스에 없습니다"라고 답했습니다.
그때 우리는 그 값에 대한 리전별 데이터 39건을 쥐고 있었습니다.

지금은 **값에서 거꾸로 찾는 표**를 둡니다(값이 등장하는 자리는 240,673곳이지만 **고유 값은
7,095개**뿐이라 쌉니다).

```
'p5.48xlarge' 은(는) 타입이 아니라 값입니다. 이 값이 나오는 곳:
  - AWS::EC2::Instance.InstanceType — 조건 38가지 중 14가지에서 허용
```

고친 뒤: **838초 → 6.6초**, 웹검색 0회, 정답.

**(2) 살짝 틀린 속성 이름.** 에이전트가 RDS에 `InstanceType`을 물었습니다. EC2가 그
이름을 쓰니 자연스러운 시도인데 RDS는 `DBInstanceClass`입니다. 지금은 아는 이름을
가리킵니다.

**(3) 축이 서로를 모름.** "이 리소스에 대해 알려줘"의 자연스러운 입구가 그래프
조회인데, 그 응답이 **제약을 한 글자도 말하지 않았습니다.** 지금은 다른 축을
가리키는 줄이 붙습니다.

> 여기서 배운 것: **고칠 곳을 실측 한 번으로 정하면 안 됩니다.** 처음에 "타입 상세"
> 경로만 고쳤다가 두 회차를 버렸습니다. 모델은 매번 다른 문으로 들어옵니다 —
> **모든 문이 답을 알아야 합니다.**

### 긴 목록을 통째로 찍지 않는다

한 도구 응답이 **377,439자**였던 적이 있습니다(리전 38개 × 인스턴스 종류 ~500개).
모델 컨텍스트를 통째로 먹어서 실측이 멈췄습니다. 요약을 넣어 5,153자로 줄였습니다.

줄이고 나니 **39줄이 전부 똑같아 보이는** 두 번째 문제가 드러났습니다 — 어느
리전에서의 값인지가 그 줄의 뜻 전부인데 그게 빠져 있었습니다.

### 내부 식별자는 API가 아예 안 만든다

`aws::` 같은 접두사와 `cfn-schema` 같은 라벨이 사용자에게 새어 나갔습니다.
프롬프트로 "지우라"고 시키는 것보다 **API가 안 만드는 편**이 확실합니다.
근거를 없애는 게 아니라 **사람 말로 적습니다**("CloudFormation 스키마").

## 8. 도구 계층 — 에이전트에게 어떻게 주나

### 도구는 늘리지 말고 통합한다

새 도구는 "자주 쓰이고 복잡하다"를 만족할 때만 만듭니다. 근거가 여럿 있습니다.

- Neo4j(그래프DB 회사)가 **자사 이익에 반해** 자연어→질의 변환을 "탐색용·최후 수단"으로
  권고하고 자기 벤치마크 일치율을 약 30%로 공개했습니다.
- Anthropic은 도구 30~50개를 넘으면 선택 능력이 떨어진다고 하고, 처방은 열거가
  아니라 **통합**입니다.
- Meta 연구는 보편 최적 개수가 없음을 보였습니다(어떤 벤치마크에서 7.4개가 50개와
  같은 범위를 덮었다).

현재 **20개**로 여유가 있습니다.

### 도구 출력에 다른 도구 이름을 넣지 않는다

모델이 그 문자열을 답변에 **그대로 복사**합니다(누출 3/3). 행위 서술로 바꿉니다
("월 비용은 다음 단계에서 계산").

**결정론적으로 고칠 수 있는 누출은 프롬프트에 맡기지 않습니다.**

## 9. 처음부터 다시 만드는 절차

### 9-0. 준비

```bash
uv sync                 # 의존성
```

### 9-1. 순서

각 축은 독립이라 순서가 자유롭지만, 검증까지 하려면 이 순서가 편합니다.

```bash
# ① 그래프 (무엇이 무엇을 필요로 하나)
python -m graphkb build --source tumblebug     # 코어 13종
python -m graphkb build --source cfn           # AWS 1,638종
python -m graphkb build --source azure         # Azure 3,382종
python -m graphkb build --source gcp           # GCP 527종
python -m graphkb build --source mapping       # 동치 관계

# ② 용량·제약
python -m capacitykb build --source cfn                # AWS 46,911
python -m capacitykb build --source azure              # Azure 42,831
python -m capacitykb build --source azure-quota        # 쿼터 542
python -m capacitykb build --source gcp                # GCP 6,923
python -m capacitykb build --source aws-limits         # 교차검증 20
python -m capacitykb build --source aws-tf             # 2,756
python -m capacitykb build --source aws-regions        # 리전별 385
python -m capacitykb build --source aws-conditional    # 조건부 966
python -m capacitykb build --source azure-mutability   # 불변성 993

# ③ 비용·성능 (같은 데이터 파일에서)
python -m costkb build
python -m perfkb build

# ④ KB 사이 검증 (빌드 안에서는 못 하는 것)
python -m kbcommon verify
```

### 9-2. 빌드가 실패하면

**그게 정상 동작입니다.** `error` 등급 검사에 걸리면 결과 파일을 **쓰지 않습니다.** 실제로
Azure 확장 중에 `read-only-not-required` 위반 6건으로 빌드가 멈춘 적이 있는데,
원인은 한 파일 안에서 **API 버전이 섞인 것**이었습니다. 그대로 나갔으면 사용자에게
**채울 수 없는 칸을 채우라고** 했을 것입니다.

### 9-3. 빌드 없이 쓰기

산출물을 gzip해서 저장소에 커밋해 뒀습니다(`data/`, 약 4MB). 클론 직후 빌드 없이
동작합니다.

```
읽기 우선순위:  output/  (새로 빌드한 것)  →  data/*.gz  (커밋된 것)
```

**대체 경로는 기본 위치에서만** 씁니다. 호출자가 다른 디렉터리를 명시하면 그 말을 그대로
지킵니다 — 테스트가 빈 디렉터리를 묶어 "미빌드 상태"를 검사하는데, 거기 커밋된
데이터가 끼어들면 그 테스트가 검사하려던 상황 자체가 사라집니다.

커밋된 파일에는 `_source` 블록이 그대로 들어 있습니다.

```json
{"source": "cfn-lint", "pin_kind": "tag", "pin": "1.53.1",
 "sha256": "0df021a3…", "bytes": 5083662, "fetched_at": "2026-07-21T13:50:23+00:00"}
```

**어느 소스 어느 버전에서 나왔는지가 파일 안에 남습니다.** 핀 규약이 약해지는 게
아니라 검증 가능해지는 쪽입니다.

### 9-4. 첫 호출이 느리면 어디를 보나

도구 하나하나는 빠릅니다(40~260ms). 느린 것은 **세션의 첫 호출**인데, 그때 결과
파일 전체를 읽기 때문입니다. 처음 쟀을 때 이랬습니다.

```
capacitykb  5.4초    graphkb  0.3초
costkb     29.0초    perfkb  43.6초      합계 약 78초
```

쪼개 보니 원인이 예상 밖이었습니다. **스키마 검증이 94~96%**였습니다.

```
costkb:  읽기 0.2초 + 파싱 1.6초 + 검증 28.8초
perfkb:  읽기 0.1초 + 파싱 1.7초 + 검증 48.6초
```

두 가지를 바꿔 **78초 → 10.6초**가 됐습니다.

| 바꾼 것 | 효과 | 왜 안전한가 |
|---|---|---|
| 읽기 검증을 컴파일형 검증기로 | 28.8초 → 2.3초 | 망가뜨린 입력 10가지에서 **판정이 전부 일치**함을 먼저 확인 |
| 파싱을 빠른 파서로 | 1.9초 → 0.58초 | 같은 JSON을 같은 값으로 읽을 뿐 |

**쓰기 경로는 안 바꿨습니다.** 거기 오류 메시지가 "어디가 틀렸는지" 경로를
알려주는데, 빌드가 막혔을 때 그게 유일한 단서입니다. 빌드당 한 번뿐이라 느려도
됩니다.

> **먼저 재고 고쳤습니다.** "도구가 느리다"는 말만 듣고 도구를 손봤으면 엉뚱한
> 곳을 고쳤을 것입니다 — 도구는 이미 빨랐습니다.

**안 하기로 한 것**: 검증 결과를 파일 해시로 캐시하기(2초 더 절약). 절약에 비해
**캐시가 낡은 결과를 조용히 내주는** 실패를 새로 들이는 것이라 하지 않았습니다.

## 10. 검증 — 만든 게 맞는지 어떻게 아나

세 층으로 봅니다.

### (가) 단위 테스트 — 640건

빠르고 네트워크가 필요 없습니다. 하지만 **이것만으로는 부족합니다.** 실제로
`cap_check_value`가 문맥을 못 받아 조건부 판정이 통째로 안 쓰이던 결함이 있었는데,
그때 단위 테스트 592개가 **전부 통과하고 있었습니다.**

### (나) KB 사이 검증

`python -m kbcommon verify`. 단방향 규약 때문에 어느 빌드에도 넣을 수 없어서,
산출물 JSON을 **데이터로 읽어서** 봅니다.

```
✓ capacity-joins-graph: 5,494건 전부 통과   ← 제약이 가리키는 타입이 그래프에 실재하나
✓ bundle-matches-mirror: 36건 전부 통과
```

### (다) 에이전트 실측 — 모델을 끼우고 본다

**KB가 준 문장이 나쁜 건지 모델이 못 읽은 건지 구별하려면** 두 가지를 다 해야 합니다.

- **KB만**: 에이전트 API를 직접 호출해 사용자가 볼 문장 그대로를 읽는다
- **모델까지**: 실제 질문을 태워 답변을 읽는다

실측이 없었으면 못 찾았을 결함들입니다.

| 결함 | 단위 테스트가 잡았나 |
|---|---|
| 조건부 판정이 통째로 안 쓰임 | ✗ (592개 전부 통과 중) |
| 낡음 고지가 답변에서 사라짐 | ✗ |
| 도구 응답 377,439자 | ✗ |
| 축이 서로를 모름 | ✗ |

#### 자동 검사 장치의 함정 ★

여기서 **일곱 번** 오판할 뻔했습니다. 전부 판정 방식 때문입니다.

**(1) 유사 문자.** 모델이 `ap-northeast-2`를 `ap‑northeast‑2`(U+2011 하이픈)로 씁니다.
`16,384`를 `16 384`로 쓰는데 그 공백이 U+202F입니다. 정답을 실패로 읽습니다.
→ 대시 7종·공백 12종을 ASCII로 정규화.

**(2) 한국어 부분 문자열.** 예/아니오 질문에서 이게 **원리적으로 안 됩니다.**

```
정답: "…사용할 수 있습니다"
거절: "…사용할 수 있는지 확인할 수 없습니다"
```

같은 조각을 담습니다. 반대로 내부 이름(`DBInstanceClass`)을 기대로 쓰면 모델이
"인스턴스 클래스"라고 자연스럽게 쓰기 때문에 **정답을 실패로** 읽습니다.

> 결론: **예/아니오 질문은 도구 호출로만 자동 판정하고, 답의 옳고 그름은 사람이
> 읽습니다.** 자동 검사에 못 시킬 일을 시키려다 양방향으로 다 틀렸습니다.

**(3) 낡은 기대.** 검사 질문의 전제가 "이 데이터는 없다"였는데 나중에 생겼습니다. 모델이
정확히 찾아냈는데 실패로 찍혔습니다. **기대도 데이터와 함께 늙습니다.**

#### 무편향 조사 — 아는 것만 검사하지 않기 위해

기대 문구를 쓰다 보면 **내가 아는 데이터만** 검사하게 됩니다. 실제로 우리가 갖고
있지도 않은 데이터를 묻는 검사 질문을 만든 적이 있습니다.

그래서 24개 질문을 **데이터를 확인하지 않고 먼저 쓰고**, 정답지를 **답변 읽기 전에**
만들고, 답변은 사람이 읽어 분류했습니다.

결과가 설계 판단을 바꿨습니다.

| 실패 원인 | 건수 |
|---|---:|
| 수집 범위 — 데이터가 아예 없음(정직히 밝힘) | 4 |
| **출처 혼합 — KB 사실과 모델 기억이 안 갈림** | **4** |
| KB 데이터 결함 | 1 |
| 경로 — 데이터에 못 닿음 | 1 |
| 표시 — 근거 등급이 사라짐 | 2 |
| **적합도 — 관련 있는 걸 못 찾음** | **0** |

**검색으로 풀 문제가 0건**이었습니다. 이 숫자가 "RAG(검색 증강)를 넣을 것인가"라는
질문에 답했습니다 — 넣을 이유가 없었습니다. 우리가 못 했던 건 "관련 있는 걸 찾는
것"이 아니라 **"어디를 봐야 하는지 아는 것"**이었습니다.

실제 사례입니다.

> "※ **cap_allowed_values 지식베이스에서 조회한 뒤** GPU가 장착된 패밀리만
> 추려낸 결과이며 …"
>
> | G5g | g5g.xlarge – 1 × **AMD Radeon Instinct MI250X** | 4 | 16 |

GPU 개수·vCPU·메모리는 그 지식베이스에 **없는 데이터**입니다. 그 도구를 부르지도
않았습니다. `g5g`는 NVIDIA이지 AMD가 아닙니다. **지어낸 값에 우리 보증이 찍혔습니다.**

또 하나. 도구가 정확히 이렇게 말했는데:

```
조건 938가지 중 840가지에서 가능, 98가지에서 불가입니다.
```

모델의 답변은:

> "16.4에서는 **사용할 수 없습니다.** ※ cap 지식베이스에서 … **지원되지 않음으로
> 표시되었습니다.**"

우리 KB는 16.4를 언급한 적이 없습니다. **뒤집어 놓고 우리 이름으로 출처 표기**를
했습니다.

### 왜 프롬프트로 못 고치나

"도구가 말하지 않은 걸 도구의 말로 옮기지 마라"는 지시문입니다. 이 프로젝트는
프롬프트 준수가 **안 통한다고 이미 쟀습니다** — 26질의 × 3회에서 16개만 3/3
완벽했고 나머지 10개는 회차마다 갈렸습니다.

### 대신 만든 것 — 답변에 나온 숫자·이름을 도구 출력과 대조하기

**설득하지 않고 대조합니다.** 답변에 나온 숫자·식별자가 그 턴의 **도구 출력에
실재하는지**만 기계적으로 봅니다.

24건에 걸어 잰 결과:

| | 판정 | 표시된 개수 |
|---|---|---:|
| GPU 사양표 | **지어냄 (확실)** | 16 |
| 스토리지 이름 규칙 | **기억으로 답함 (확실)** | 1 |
| Azure VM 선행 | **없는 식별자 추가 (확실)** | 1 |
| 인스턴스 추천 | 모델 산술 (약한 참) | 4 |
| Lambda 타임아웃 | **헛짚음** (900초=15분 단위 환산) | 1 |
| 나머지 19건 | 깨끗 | 0 |

**헛짚은 것이 1건**이고, 최악 사례가 **16 대 1**로 갈립니다. 개수가 심각도 신호가 됩니다.

이걸 자동 검사 장치에 **신호로만** 얹었습니다 — 통과/실패에는 **넣지 않습니다.**
헛짚은 것을 실패로 만들면 멀쩡한 답변이 빨갛게 뜨고, 그러면 **진짜 실패가 노이즈에
묻힙니다.**

가장 좋은 예가 이겁니다. 답변 자체는 훌륭합니다.

> gp2는 **최대 16,384 GiB**까지입니다. 30,000 GiB는 초과합니다(**※ cap_check_value
> 결과에 의함**). 대안으로 **gp3**를 쓸 수 있습니다. gp3는 **최대 65,536 GiB**까지
> 지원하므로 …

앞 문장은 도구를 인용까지 했습니다. 뒤 문장의 65,536은 **우리 KB에 있는 값인데
찾아보지 않고 기억으로 말한 것**입니다. 이번엔 맞았습니다.

왜 이게 신호인가: **모델 기억은 낡습니다.** 이 프로젝트에서 실제로 겪었습니다 —
gp3 최대 IOPS를 16,000으로 알고 있었는데 AWS가 2025년 9월에 **80,000**으로 올렸고,
우리 데이터가 맞고 기억이 틀렸습니다. 그때도 답변은 **지금처럼 자신 있게** 보였을
것입니다.

> 대조기는 "틀렸다"고 말하지 않습니다. **"이건 확인하지 않고 한 말이다"**라고
> 말합니다.

**한계도 분명합니다.** 위의 "뒤집기"는 숫자나 이름이 아니라 **문장의 뜻**이라
못 잡습니다.
지어내기에는 정면으로 맞고, 뒤집기에는 우연히 걸립니다.

## 12. 함정 모음 — 직접 밟은 것들

만들 사람에게 가장 값이 클 부분입니다. 전부 **실제로 겪은** 것입니다.

### 데이터 만들 때

**빈 목록을 "아무것도 안 됨"으로 읽지 마라.** cfn-lint 파일에 `"all"`이라는 키가
있고 그 값이 **빈 목록**이었습니다. 리전인 줄 알고 담았으면 "허용값 0개" 제약이
생기고 **모든 인스턴스 종류가 거부**됩니다. 하필 값이 가장 많은 파일(24,183개)에서
그랬습니다.

**속성 이름을 짐작하지 마라.** 파일명에서 이름을 만들되 **스키마에 실재하는지
확인**하고, 없으면 담지 않고 셉니다. 없는 이름을 지어내면 그 제약은 **영원히
아무것에도 안 걸립니다.**

**URL을 위치로 파싱하라.** ARM 경로는 `타입/이름/타입/이름` 교대입니다.
"중괄호가 없으면 타입"으로 읽었더니 `/virtualMachineInstances/default`의 `default`
(이름)를 타입으로 읽었습니다(21종). 또 `/providers/`가 두 번 나오면 **뒤쪽**이
진짜 타입입니다(10종).

**한 파일 안에서 버전을 섞지 마라.** 파일은 최신 버전으로 골랐는데 **파일 안에서**
모든 API 버전을 훑고 있었습니다. 옛 버전의 "필수"와 새 버전의 "읽기 전용"이 섞였습니다.

**상류가 모순이면 경계만 싣고 값은 버려라.** AWS가 `default: 0, minimum: 10`이라고
적어 놓은 곳이 30건 있습니다. **의도를 지어낼 수 없으므로** 경계만 담고 기본값은
버립니다. 반대로 우리가 오독한 것(`required`의 의미)은 **우리를 고칩니다.**

**필드명을 바꿀 때 낡은 산출물을 조용히 읽지 마라.** `condition`(단수)을
`conditions`(목록)로 넓혔을 때, 로더가 모르는 옛 키를 **무시**했습니다. 그러자
리전별 38개 레코드의 조건이 전부 사라지고 중복 키가 같아져 **하나로 접혔습니다** —
우리가 막으려던 뭉뚱그린 범위가 칸 이름을 바꾸다가 재현됐습니다. 지금은 **거부합니다.**

### 정규식

**번역하지 말고 그 문법을 아는 엔진으로 읽어라.** 파이썬 `re`가 못 읽는 패턴이
205건인데 그중 **194건은 원본이 틀린 게 아니라 .NET/PCRE 문법**입니다(`\p{L}` 계열).
`\p{L}`을 `[^\W\d_]`로 옮기는 건 **근사치**라, 검증이 조금이라도 엄격해지면
**막지 말아야 할 것을 막는 쪽**이 됩니다.

**앵커를 마음대로 붙이지 마라.** 앵커 없는 패턴이 1,430건이지만 **결함이 아닙니다.**
JSON Schema의 `pattern`은 규약상 부분 일치입니다. 앵커를 붙이면 우리가 원본에 없는
엄격함을 지어내는 것입니다.

**어느 엔진에서도 안 도는 11건은 고치지 말고 밝혀라.** `*{1,1000}` 같은 상류
오류입니다. 예전에는 조용히 건너뛰어서 **"제약이 없다"로 읽혔습니다.**

### 한국어 처리

**파이썬 `\b`·`\w`는 한글을 단어 문자로 봅니다.**

```
64개            → 경계가 안 잡혀 검사 자체가 안 됨
db.t3.medium을   → 조사(을)까지 이름에 붙어 들어옴
```

검사기를 만들자마자 **양방향으로 틀렸습니다.** 답을 아는 사례에 먼저 걸어 보지
않았으면 이 상태로 24건을 돌리고 결과를 믿었을 것입니다.

**콘솔 인코딩.** Windows에서 한국어 출력이 깨집니다. 모든 진입점에서 UTF-8을
명시해야 합니다. 한 번은 검사가 **전부 통과한 뒤 `✓`를 찍다가** 죽었습니다.

### 검증할 때

**잘못 잡은 것을 그럴듯하게 만드는 수정은, 잘못 잡은 채 두는 것보다 나쁘다.** 대소문자 무시
매칭을 넣었더니 소문자 `service`가 진짜 `Service`로 이어져 **잘못 잡은 것이 사라지는 대신
더 그럴듯해졌습니다** — 실재하는 관계로 가니 옳은 것과 구분이 안 됩니다.

**금지어 목록을 손으로 만들지 마라.** 30단어 금지 목록으로 잘못 잡히는 것을 막으려다 맞는
관계까지 막았습니다. "KCC 부품 이름은 예외 없이 PascalCase"는 취향이 아니라 **규칙**이라
다음 버전에서도 통합니다.

**"문제 없음이 확인된 영역"을 기록하라.** 억지 결함이 아님을 보이고, 무엇보다
**재조사 낭비를 막습니다.**

**대체 경로는 조용히 고장 납니다.** 저장소에 넣어 둔 결과 파일을 쓰는 대체
경로를 만들었는데 읽기 함수가
`.gz`를 못 읽어서 두 축만 0건이 됐습니다. **"빌드 안 됨"과 구분이 안 되는 실패**라,
`output/`을 실제로 치워 보지 않았으면 못 봤을 것입니다.

문서에 이유까지 적었습니다("이런 명령형 구성은 혼란스럽고 검증 도구들이 널리
지원하지 않는다").

> 즉 **우리 KB의 표현은 어느 클라우드 회사의 스키마보다도 풍부해야 하며, 이건 우리 잘못으로
> 생긴 숙제가 아닙니다.**

## 15. 한 장 요약

만들 사람이 기억할 것을 줄이면 이것입니다.

1. **소스를 못 박아라.** 안 그러면 "고쳤다"를 증명할 수 없다.
2. **기계가 읽으라고 만든 스키마를 써라.** 사람 문서를 긁지 마라.
3. **레코드마다 어디서 왔는지(evidence)와 원본이 말한 건지(basis)를 적어라.**
4. **한 줄이 아니라 여러 줄이 모여 생기는 모순을 쓰기 직전에 검사하라.**
5. **조건을 담아라.** 안 그러면 어떤 실제 설정에도 맞지 않는 범위가 된다.
6. **모름을 3상태로 유지하라.** 어느 쪽으로 접어도 거짓이 된다.
7. **"없다"와 "안 봤다"를 다른 문장으로 답하라.**
8. **막다른 길을 답으로 바꿔라.** 살짝 틀린 키에도 아는 것을 가리켜라.
9. **모델을 끼우고 재라.** 단위 테스트는 이 층의 결함을 못 본다.
10. **판정 도구 자체를 의심하라.** 우리는 일곱 번 오판할 뻔했고, 전부 판정 방식
    때문이었다.
