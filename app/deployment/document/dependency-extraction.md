# 리소스 사이의 "먼저 만들어야 하는 순서"를 어떻게 알아냈나

(2026-07-20 기준. 숫자는 전부 실제로 세어본 값이다.)

## 이 문서가 답하는 것

클라우드에서 서버 하나를 만들려면 그 전에 네트워크가 있어야 하고, 네트워크 안에는
구역이 나뉘어 있어야 하고, 접근 권한도 미리 만들어져 있어야 한다. 이런 **"A를 만들려면
B가 먼저 있어야 한다"** 를 우리 프로그램이 어떻게 알아냈는지 적는다.

서버·네트워크 같은 것을 앞으로 **부품**이라고 부르겠다.

---

## 1. 우리가 읽는 것

아마존·마이크로소프트·구글은 자기 서비스를 **기계가 읽을 수 있는 설명서**로 공개한다.
"이 부품을 만들려면 어떤 칸을 채워야 하는가"가 적힌 문서다. 사람이 읽는 매뉴얼이 아니라
프로그램이 읽으라고 만든 것이다. 아마존은 부품이 1,635가지, 마이크로소프트는 3,382가지다.

## 2. 문제: 설명서가 순서를 안 알려준다

구역(서브넷)은 네트워크(VPC) 안에 만들어야 한다. 아마존의 구역 설명서에서 `VpcId` 칸을
열어보면 전부가 이것이다.

```json
"VpcId": {
  "type": "string",
  "description": "The ID of the VPC the subnet is in."
}
```

"VpcId: 글자를 넣는 칸. 설명 — 이 구역이 속한 네트워크의 ID."

**"네트워크라는 부품을 가리킨다"는 말이 기계가 알아볼 형태로는 없다.** 타입은 그냥
"글자"고, 네트워크 이야기는 사람 읽으라고 쓴 설명문에만 있다.

---

## 3. 관계 하나에 무엇을 적는가 — 그리고 왜 그것들인가

관계를 찾았다고 치자. "구역은 네트워크가 필요하다"만 적어두면 될까? **안 된다.**
실제로 뭔가를 만들려면 세 가지를 더 알아야 한다.

### (1) 어느 칸에 적나 — `via_property`

```
Batch::ComputeEnvironment → EC2::Subnet
   칸: ComputeResources/Subnets
```

"계산 환경을 만들 때 `ComputeResources` 안의 `Subnets` 칸에 구역을 넣어라"는 뜻이다.

이게 없으면 "구역이 필요하다"는 건 알아도 **어디에 적어야 할지 모른다.** 설명서 하나에
칸이 수십 개씩 있고 상자 안에 상자가 들어 있어서, 위치를 모르면 찾을 수가 없다.

### (2) 안 적어도 되나 — `required`

칸이 있다고 다 채워야 하는 건 아니다.

```
S3::BucketPolicy → S3::Bucket    필수 O   (정책은 대상 저장소 없이 존재 불가)
S3::Bucket → S3::AccessPoint     필수 X   (저장소는 접근점 없이도 만들어진다)
```

**이 값이 순서를 푸는 열쇠다.** 7절에서 자세히 다룬다.

전체의 29.7%만 필수다. 나머지 70%는 "쓸 수도 있는 칸"이고, 순서를 강제하지 않는다.

### (3) 하나인가 여러 개인가 — `cardinality`

```
Subnet → VPC            하나   (구역은 네트워크 하나에 속한다)
Instance → SecurityGroup 여럿   (서버에 방화벽을 여러 개 붙일 수 있다)
```

"방화벽이 필요하다"만으로는 하나를 만들지 열 개를 만들지 모른다.

### 이 세 개로 충분한가 — **아니다**

세 개는 각각 **어디에(where) / 꼭 해야 하나(whether) / 몇 개(how many)** 에 답한다.
그런데 실제로 조립하려면 하나가 더 필요하다.

**(4) 그 칸에 무슨 값을 적나 — 2026-07-21 추가했다.**

부품을 만들면 여러 값이 나온다. 방화벽을 만들면 방화벽 번호, 이름, 소속 네트워크가
생긴다. 다른 부품이 방화벽을 가리킬 때 그중 **어느 값을 복사해 넣는지**가 정해져 있다.

아마존은 이걸 `propertyPath`라는 이름으로 알려준다. 그런데 우리 프로그램은 "어느
부품인지"만 저장하고 이 값을 버린다. 그래서 이런 일이 생긴다.

```
우리가 아는 것:  VPC엔드포인트 → 네트워크를 가리킴
버린 정보:       실제로 복사해 넣는 값은 네트워크 번호가 아니라
                 "그 네트워크의 기본 방화벽" (/properties/DefaultSecurityGroup)
```

**방향도 대상도 맞는데 무엇을 적을지를 모른다.** 원본과 대조해도 "네트워크를 가리킨다"는
맞으니까 잘 드러나지 않는 종류의 누락이었다.

지금은 `target_property`로 저장한다. 소스마다 이름이 다르다 — 아마존은 `propertyPath`,
구글은 servicemapping의 `targetField`, 마이크로소프트는 ARM 관례상 항상 `id`다.
관계 5,524개 중 **1,704개**가 이 값을 갖는다(아마존 1,278 / 구글 373 / 마이크로소프트 53).
나머지는 소스가 알려주지 않은 것이고, 빈 값은 "결합 지점이 없다"가 아니라 **"우리가 모른다"**　는 뜻이다.

**(5) 나중에 채워도 되나 — 이것도 없다.**

"만들 때 반드시 넣어야 하는가, 아니면 만든 다음에 이어붙여도 되는가"는 순서 판단에
결정적인데 우리는 기록하지 않는다. 지금은 `required`가 아니면 나중에 붙일 수 있다고
**간접적으로 짐작**하고 있을 뿐이다.

정리하면 이렇다.

| 정보 | 답하는 질문 | 있나 |
|---|---|---|
| `via_property` | 어느 칸에 적나 | ✅ |
| `required` | 꼭 적어야 하나 | ✅ |
| `cardinality` | 하나인가 여럿인가 | ✅ |
| `target_property` | 대상의 어느 값을 복사하나 | ✅ (5,524 중 1,704) |
| 언제 적나 | 만들 때? 만든 다음? | ❌ 없음 |

## 4. 아마존 — 관계를 찾는 세 가지 방법

### 방법 1. 회사가 직접 적어둔 것 (87개)

일부 설명서에는 아마존이 관계를 명시해 뒀다.

```json
"SecurityGroups": {
  "relationshipRef": {
    "typeName": "AWS::EC2::SecurityGroup",
    "propertyPath": "/properties/GroupId"
  }
}
```

"이 칸은 방화벽을 가리키고, 그 방화벽의 `GroupId` 값을 가져다 쓴다." 짐작할 게 없다.
다만 1,635가지 부품 중 87곳에만 있다. (여기 나오는 `propertyPath`가 3절 (4)번에서
말한 버리고 있는 정보다.)

### 방법 2. 다른 사람들이 정리해둔 목록 (1,205개)

아마존의 개발 도구를 만드는 팀(CDK)이 "설명서에는 없지만 실제로 있는 관계"를 손으로
모아 공개해 뒀다. 그대로 옮기면 된다. 아마존 공식 문서가 아니라 다른 팀이 정리한
것이라 방법 1보다는 한 단계 약하게 보지만, 사람이 검토한 목록이라 짐작보다는 낫다.

### 방법 3. 이름을 보고 짐작하기 (1,203개)

나머지는 짐작이다.

```
1. 칸 이름이 "~Id"나 "~Arn"으로 끝나는가?     VpcId → 앞부분 "Vpc"
2. "Vpc"라는 이름의 부품이 있는가?            있다 → AWS::EC2::VPC
3. 그런 부품이 딱 하나일 때만 연결한다.       둘 이상이면 포기
```

**"딱 하나일 때만"이 유일한 안전장치**다. 이름이 구체적이면 잘 맞고, 흔한 단어면
무너진다(6절).

## 5. 규칙 하나 — 내가 채우는 칸만 본다

설명서의 칸에는 두 종류가 있다.

- **내가 채우는 칸**: 구역을 만들 때 "어느 네트워크에?"를 내가 지정한다.
- **만들고 나서 아마존이 채워주는 칸**: 고유번호, 생성 시각, 현재 상태 같은 것.

두 번째는 만들기 **전에** 채우는 게 아니므로 순서와 무관하다. 그래서 건너뛴다.
안 건너뛰면 "만들고 나서 생기는 값"을 "만들기 전에 필요한 것"으로 착각한다.

### 어느 칸이 어느 쪽인지 어떻게 아나

**우리가 판단하지 않는다. 아마존이 목록으로 선언한다.** 설명서 안에
`readOnlyProperties`라는 항목이 있고, 거기 적힌 칸이 "아마존이 채워주는 칸"이다.

```json
"readOnlyProperties": [
  "/properties/ComputeEnvironmentArn",
  "/properties/ComputeResources/Ec2Configuration/*/BatchImageStatus"
]
```

첫 줄은 "계산 환경의 고유번호". 둘째 줄은 "`ComputeResources` 안의 `Ec2Configuration`
목록의 각 항목 안에 있는 `BatchImageStatus`"라는 뜻이다. `*`는 목록의 모든 항목을
가리킨다.

> **왜 그게 읽기 전용인지 우리는 모른다.** 아마존이 그렇다고 선언했을 뿐이고, 그 칸에는
> 설명문조차 붙어 있지 않다. 이름을 보면 "이미지 상태"라 만들고 나서 보고되는 값으로
> 보이지만 **그건 추측이고, 우리 프로그램은 그런 추측을 하지 않는다.** 선언을 그대로 믿는다.

### 여기서 사고가 있었다

우리 프로그램은 저 목록에서 **맨 앞 칸 이름만** 떼어 썼다. 그러니까 둘째 줄에서
`ComputeResources`를 읽고 "이 칸은 읽기 전용이구나" 하고 **상자 전체를 건너뛰었다.**

실제로 읽기 전용인 건 그 상자 깊숙한 곳의 `BatchImageStatus` 하나뿐인데, 바깥 상자를
통째로 버린 것이다. 그 안에 있던 서버 템플릿·구역·방화벽 관계가 전부 사라졌다.

지금은 `/properties/이름` **딱 그 깊이일 때만** 통째로 건너뛴다. 더 깊은 경로면 그 안의
특정 항목만 읽기 전용이라는 뜻이므로 상자는 계속 들여다본다.

## 6. 규칙 둘 — 너무 흔한 단어는 짐작하지 않는다

방법 3의 "딱 하나일 때만"은 이름이 구체적일 때만 안전하다. 흔한 단어가 마침 어느 한
서비스에만 부품 이름으로 있으면 우연히 "딱 하나"가 되어버린다.

| 칸 이름 | 실제 의미 | 우리가 연결했던 곳 |
|---|---|---|
| `FieldId` | 차트 안의 항목 번호 | 고객센터 서비스의 `Field` 부품 |
| `VersionId` | 설정 파일의 버전 번호 | 람다 서비스의 `Version` 부품 |
| `TypeId` | 인증서 서식 종류 | 카산드라 데이터베이스의 `Type` 부품 |

전부 관계가 아닌 것을 관계로 만든 것이다. `FieldId`는 대시보드 설명서 안에서 **421곳**에
나오는 바람에 한 번에 421개의 잘못된 연결이 생겼다.

그래서 `field`, `version`, `type`, `name`, `key`, `policy` 같은 흔한 단어 30개는
**이름만으로는 연결하지 않는다.** 방법 1이나 2가 "이건 진짜 관계다"라고 하면 그건
그대로 인정한다. **짐작을 막는 것이지 사실을 막는 게 아니다.**

## 7. 순환 — 서로가 서로를 가리킬 때

### 왜 이런 게 생기나

권한(Role)과 정책(ManagedPolicy)을 보자. 둘을 연결하는 방법이 **두 가지**다.

```
권한 쪽에서:  Role의 "ManagedPolicyArns" 칸에 정책을 적는다
정책 쪽에서:  ManagedPolicy의 "Roles" 칸에 권한을 적는다
```

같은 연결인데 어느 쪽에서든 걸 수 있다. 그래서 설명서상으로는 **권한이 정책을 가리키고,
정책도 권한을 가리킨다.** 이런 쌍이 아마존에 18개 있다.

여기서 중요한 건, 이게 **부품 종류끼리의 관계**라는 점이다. 실제로 만들 때는 "이 권한"과
"저 정책"이라는 구체적인 물건 두 개를 만드는 것이고, 그 둘 사이에 진짜 순환이 생기지는
않는다. 설명서가 "이런 연결도 가능하다"를 양쪽에 다 적어놨을 뿐이다.

### 그러면 뭐가 먼저인가

**필수인 쪽이 나중이다.** 저장소(Bucket)와 정책(BucketPolicy)이 좋은 예다.

```
BucketPolicy → Bucket    필수 O    정책은 대상 저장소가 없으면 만들 수 없다
Bucket → BucketPolicy    필수 X    저장소는 정책 없이도 잘 만들어진다
```

그러니 **저장소가 먼저, 정책이 나중**이다. 순환처럼 보이지만 실제로는 순서가 있다.

18쌍을 전부 확인했더니 **양쪽 다 필수인 경우는 0건**이었다. 즉 **모든 순환은 풀 수 있다.**
한쪽만 필수면 그쪽이 나중이고, 양쪽 다 선택이면(15쌍) 아무거나 먼저 만들고 나중에
이어붙이면 된다.

### 실제로 해보면

우리 프로그램에는 "필수 관계만 따라가기" 모드가 있다. 정책을 만들려면 뭐가 필요한지
물어보면 이렇게 갈린다.

```
[전부 따라갈 때]        15단계, 그중 3개 그룹이 "순서를 정할 수 없음"
   1. [네트워크, 네트워크암호화제어]  ← 순서 못 정함
   ...
   15. [람다, 레이어, 로그그룹, 접근점, 저장소, 알림, 정책]  ← 순서 못 정함

[필수 관계만 따라갈 때]  2단계, 순환 없음
   1. S3::Bucket
   2. S3::BucketPolicy
```

**필수만 보면 답이 깨끗하게 나온다.** 선택적인 연결까지 다 따라가니까 관계없는 부품
수십 개가 딸려 들어오면서 뒤엉킨 것이다.

지금 기본값은 "전부 따라가기"다. 필수만 보는 게 더 쓸모 있어 보이는데, 아직 바꾸지 않았다
(10절).

### 그래도 못 푸는 게 남으면

프로그램은 순환을 하나의 덩어리로 묶어 **"이 안에서는 순서를 정할 수 없다"** 고 표시한다.
없는 순서를 지어내지 않는다. 그리고 이런 경우 실제 해법은 "하나를 먼저 만들고, 만든
다음에 서로를 이어붙이는 것"인데, 그게 가능한지 여부가 바로 3절 (5)번에서 없다고 한
정보다.

## 8. 마이크로소프트와 구글은 왜 다른가

### 마이크로소프트 — 이름이 곧 주소

애저는 부품 이름 자체가 주소다.

```
Microsoft.Compute/virtualMachines/extensions
```

슬래시로 자르면 "확장 프로그램은 가상머신 안에 있다"가 바로 나온다. **설명서를 읽을
필요도 없이 이름만 자르면 된다.** 애저 관계 2,306개 중 **2,223개(96.4%)가 이 방식**이고,
규칙을 어기는 경우가 0건이었다.

나머지 83개만 짐작인데, 그중 65개가 "칸의 타입 이름이 부품 이름과 같으면 그 부품을
가리킨다고 본다"는 방식이다. **여기가 애저에서 유일하게 문제 있는 부분이다.**

```
VPN 연결의 "routingConfiguration"(라우팅 설정) 칸
  → 우리는 "routingConfigurations"라는 부품을 가리킨다고 판단했다

그 칸의 실제 내용: [연결된 경로표, 들어오는 규칙, 나가는 규칙, …]
  = 별도 부품이 아니라 그 자리에 직접 적어 넣는 설정값 뭉치
```

구별법이 있다. **애저에서 진짜로 다른 부품을 가리키는 것은 반드시 `id`라는 항목을
갖는다.** 이 검사를 넣으면 잘못된 연결 9개가 걸러진다. 아직 안 넣었다.

이름으로 짐작한 나머지 18개는 **전수 확인 결과 전부 맞았다.** 애저는 부품 이름이 길고
구체적이라(`diskEncryptionSets`) 6절에서 본 "흔한 단어" 사고가 잘 안 난다.

### 구글 — 회사가 대응표를 준다

구글은 두 가지를 준다.

**첫째, 대응표를 직접 준다.** "이 부품의 이 칸은 저 부품을 가리킨다"를 표로 만들어
공개한다. 143개가 여기서 나온다. 짐작이 0이다.

**둘째, 설명문에 대상 이름을 정확히 적어준다.**

```
"Allowed value: The `selfLink` field of a `ComputeInstanceTemplate` resource."
 (허용값: ComputeInstanceTemplate 부품의 selfLink 항목)
```

아마존은 "the VPC"라고 두루뭉술하게 적지만 구글은 **부품 이름을 그대로** 적는다.
51개가 여기서 나오고, 확인해보니 **50개가 설명문과 일치**했다(1개는 설명문이 비어 대조
불가). 이름으로 짐작한 9개도 **전부 맞았다.**

다만 두 가지를 놓치고 있다.

**설명문의 다른 표현을 모른다 — 20개 놓침.** 우리가 아는 문구는 위의 한 가지인데
`"The Google Cloud resource name of a 'ComputeFirewallPolicy' resource"` 같은 변형이 더
있다. 답이 설명문에 그대로 있는데 표현이 달라 못 읽는다. 그래서 방화벽 정책 **연결**
부품이 관계 0개로 나온다 — 이름부터 "연결"인데 말이다.

**두 서비스만 읽고 있다.** 구글이 공개한 부품 설명서는 510개(서비스 136종)인데 우리는
컴퓨팅·컨테이너 두 종류 95개만 읽는다. 프로그램 설정 한 줄 문제다.

## 9. 요약

| | 짐작이 아닌 것 | 이름으로 짐작한 것 | 짐작한 것의 문제 |
|---|---|---|---|
| **아마존** | 1,292개 (52%) | **1,203개 (48%)** | 흔한 단어 사고 |
| **마이크로소프트** | 2,223개 (96%) | 83개 (4%) | 65개 중 9개가 잘못된 연결 |
| **구글** | 194개 (96%) | 9개 (4%) | 전부 정확 |

**짐작 비율이 아마존만 유독 높다.** 마이크로소프트는 이름이 곧 주소라서, 구글은 회사가
대응표를 줘서 짐작할 일이 적다. 아마존은 설명서에 관계가 거의 안 적혀 있어서 짐작에
기댈 수밖에 없고, 부품 이름이 짧고 흔해서 짐작이 잘 틀린다.

아마존에는 짐작으로도 못 보는 영역이 있다. CDK 목록이 아는 관계 중 **54%가 `~Id`나
`~Arn`으로 끝나지 않는 이름**이다(`S3BucketName`, `IAMServiceRole`, `AlarmActions` 등).
우리 방식은 이름 끝을 보기 때문에 **원리적으로 볼 수 없다.** 고칠 수 있는 버그가 아니라
방식의 한계다.

## 10. 아직 안 고친 것

**(2) "나중에 채워도 되나"를 기록하지 않는다.** 3절 (5)번. 순환을 제대로 푸는 데
필요한 정보다.

**(3) 순환이 있을 때 기본값이 "전부 따라가기"다.** 7절. 필수만 따라가면 답이 깨끗한데
기본이 아니라서, 물어보면 뒤엉킨 15단계가 나온다.

**(4) 애저의 `id` 검사가 없다.** 8절. 잘못된 연결 9개가 그대로 있다.

**(5) 구글 설명문의 다른 표현 20가지를 모른다.** 8절.

**(6) 구글을 두 서비스만 읽는다.** 8절.

**(7) 같은 관계가 여러 번 기록된다.** 사물인터넷 규칙이 권한을 가리키는 관계가 40개
있다. 40가지 동작(경보 보내기, 로그 쓰기, 데이터 저장하기…)마다 권한 칸이 하나씩 있어서다.
칸마다 별개로 세니 40개가 된다. 각각 실재하는 칸이라 데이터로는 맞는데, "뭐가 필요해?"에
같은 답이 40번 나온다. 저장할 때 합칠지 보여줄 때 합칠지 정하지 않았다.

**(8) "반드시 필요한가?"에 답이 하나가 아니다.** 위와 같은 이유로, 같은 두 부품 사이인데
어떤 칸에서는 필수고 어떤 칸에서는 선택인 경우가 19건 있다. 둘 다 사실이라 모순은
아니지만 단일한 답이 없다.

**(9) 아마존에는 "안에 들어 있다" 관계가 하나도 없다.** 애저는 2,223개가 포함 관계인데
아마존은 전부 "가리킨다"다. 아마존 설명서가 포함 관계를 이름으로 표현하지 않기
때문인데, 다른 단서로 알아낼 수 있는지 아직 조사하지 않았다.

**(10) 이름부터 "연결"인 부품들이 관계 0개다.** 아마존의 `ConfigurationAssociation`,
구글의 `FirewallPolicyAssociation` 같은 것. 정의상 최소 둘을 잇는 부품인데 관계가 없다.
구글 쪽은 (5)번이 원인으로 확인됐고 아마존 쪽은 아직 모른다.

## 부록: 확신의 정도 대신 사실 여부

이 프로젝트에는 관계마다 0.5부터 1.0까지 숫자가 붙어 있다. 확신의 정도를 나타내려던
것인데 **그 숫자가 무슨 뜻인지 정의된 적이 없다.** 0.9와 0.95를 가르는 기준도, 두 근거가
겹칠 때 어떻게 계산하는지도 없다.

그래서 이 문서는 숫자로 줄을 세우지 않고 **"회사가 알려준 것"인지 "우리가 이름 보고
짐작한 것"인지**로만 나눴다. 중요한 질문은 "얼마나 확신하는가"가 아니라 **"이게 사실인가"**
이기 때문이다. 짐작한 것은 짐작이라고 말하면 되고, 틀렸으면 고치면 된다. 0.6이라는
숫자는 그 둘 중 어느 것도 해주지 못한다.
