# 조사 1 — 각 축의 데이터를 어떻게 연결하나

## 결론

**새 소스도 새 손표도 필요 없습니다. 다리는 이미 데이터 안에 있습니다.**
이 프로젝트에서 네 번 반복된 그 교훈이 다섯 번째로 나왔습니다 — *이미 받아 둔 것의
안 쓰는 부분부터.*

```
번들 멤버   aws::AWS::EC2::Instance
   ↓  mapping-graph   equivalent_to (역방향)          근거 cb-spider-driver
core::vm
   ↓  core-graph      references via specId (required) 근거 swagger-field
core::spec
   ↓  =  costkb 스펙 카탈로그의 바로 그것              aws+us-east-1+m5.large
hourlyUSD   +   perfkb 성능 경고
```

## 실측 — 어디는 이미 붙어 있고 어디가 갈라져 있나

**타입 층 안에서는 거의 완전히 붙어 있습니다.**

```
번들 멤버 787종
   graphkb 노드에 있음      783   99.5%
   capacitykb 제약이 있음   767   97.5%
```

즉 "이 번들의 멤버가 무엇을 참조하고 어떤 제약을 갖나"는 **지금도 답할 수
있습니다.** 안 하고 있을 뿐입니다.

**사이징 ↔ 비용은 이미 조인됩니다.**

```
sizingkb reference_point 18건은 metric=specId, 값이 costkb id 그대로다
   workload:llm-bench  →  aws+us-west-2+g6e.2xlarge
   costkb id와 정확 일치  18 / 18  (100%)
```

**갈라진 곳은 하나뿐입니다 — 타입 층(번들·그래프·제약)과 스펙 층(비용·성능).**

```
번들 멤버 787종 중 mapping-graph에 걸리는 것   19종
```

19종밖에 안 되는 건 결함이 아니라 **mapping-graph가 core 개념 13종만 다루기
때문**입니다(vNet·subnet·vm·spec·nlb·k8sCluster 등 × 벤더 9곳 = 엣지 82).
그리고 **다리에 필요한 건 그 13종뿐입니다** — 나머지 768종은 애초에 시간당 단가가
붙는 물건이 아닙니다.

## 막는 것은 조인 키가 아니라 **가격의 부재**입니다

다리가 이어 주는 것은 **VM 하나**입니다. 번들의 나머지 멤버 — NIC·서브넷·라우트
테이블·로드밸런서·디스크 — 는 **가격 데이터가 아예 없습니다**(항목 5의 "스토리지·
관리형 서비스 0건"과 같은 구멍입니다).

그래서 **"번들 총비용"은 지금 데이터로 낼 수 없습니다.** 낼 수 있는 것은
*"VM 단가 + 값을 매길 수 없는 멤버 N종"*입니다.

이걸 총액처럼 내면 이 프로젝트가 가장 경계하는 실패입니다 — **모르는 것을 0으로
채우는 것.** 서브넷 예약 IP를 몰라서 256으로 답하던 것과 같은 모양이고, 그때보다
나쁩니다(예산은 사람이 그 숫자로 결정하니까).

## 설계 판단 — 합계가 아니라 **가격표**

번들 비용 질의는 하나의 숫자가 아니라 **줄 목록**을 돌려줍니다.

```
core::vm 을 고르면 함께 만들어지는 것:

  값을 매길 수 있음
    core::vm      aws+ap-northeast-2+t3.medium   $0.0416/h
                  ⚠ 버스트 인스턴스 — 크레딧이 소진되면 baseline으로 떨어짐

  값을 매길 수 없음 (이 데이터셋에 가격 축이 없음)
    core::vNet · core::subnet · core::securityGroup · core::sshKey
    core::image (값을 반드시 줘야 함)

※ 합계를 내지 않습니다 — 위 4종의 단가를 모르는 채로 더하면 실제보다 낮은
  숫자가 나옵니다.
```

`cost_recommend_specs`가 성능 경고를 다는 방식(`_perf_annotate`)과 같은 모양입니다 —
**침묵을 안전 신호로 오독하지 않도록 "왜 비어 있는지"를 블록 끝에서 한 번 밝힙니다.**

## 조사 중 나온 데이터 결함

`tumblebug` 번들 23건 중 **13건이 같은 멤버를 여러 번** 담습니다(위 항목 3).
축을 연결하려고 멤버를 훑다가 나왔습니다 — 연결이 없었으면 안 보였을 결함입니다.

## 근거 등급은 다리를 건너며 떨어진다

다리의 두 링크는 등급이 다릅니다. 이걸 뭉개면 안 됩니다.

| 링크 | 근거 | basis |
|---|---|---|
| `core::vm → core::spec` | `swagger-field` | 원본 명시 |
| `core::vm ↔ aws::AWS::EC2::Instance` | `cb-spider-driver` | **짐작(검수됨)** |

즉 **벤더 타입에서 출발한 비용 답은 짐작 한 단계를 거칩니다.** `core::vm`에서
출발하면 안 거칩니다. `needs_hedge`가 이미 이 구분을 알고 있으므로, 답에 그대로
실으면 됩니다 — 새 규칙이 필요 없습니다.

# 3번 완료 — 번들 멤버 id 정합성

축을 연결하려고 멤버를 훑다가 나온 결함 셋입니다. **연결을 안 했으면 안 보였을
것들**입니다.

| | 무엇이 틀렸나 | 고친 뒤 |
|---|---|---|
| 1 | infra 템플릿이 노드 그룹마다 줄을 만들어 `core::vm`이 28줄. 게다가 `nodeGroupSize`를 안 봐서 **대수가 틀렸다**(17×2=34대를 17로) | `Member.count`로 한 줄. `infra-across-global`은 실측 **36대** |
| 2 | k8s 템플릿이 `core::cluster`라고 적었는데 **그런 노드가 없다**. 앵커도 같아서 `bundle_for_resource('core::k8sCluster')`가 아무것도 못 찾았다 | `core::k8sCluster` + 노드 그룹까지 담음 |
| 3 | vNet 템플릿이 서브넷을 적는 방식이 둘인데 `vNetPolicy`만 봤다 | `vNetReq.subnetInfoList`로 적은 AWS 템플릿이 **0개 → 3개** |

`Bundle.__post_init__`이 중복 타입에 **예외를 던집니다.** 조용히 합치지 않는 이유는
note를 어떻게 할지가 파서가 원본을 보고 내릴 판단이기 때문입니다. `count`는 1이면
산출물에 적지 않습니다 — 거의 다 1이라 다 적으면 1이 아닌 곳이 안 보입니다.

avm 207 · kcc 296 · aws-patterns 52는 중복 0건이라 **이 파서만의 문제**였습니다.
재빌드 후 중복 0건, 매달린 타입 id 0건.

> **곁다리로 확인한 것**: AVM이 말하는 `Microsoft.Insights/diagnosticSettings`와 우리
> 그래프의 `microsoft.insights/diagnosticSettings`는 **대소문자만 다릅니다**(ARM은
> 대소문자를 안 가립니다). `bundlekb`의 조회는 이미 소문자로 정규화하므로 영향이

Azure Retail과 같이 **재배포 허가를 확인하지 못해 커밋하지 않습니다.**

## 담을 것을 채움률이 아니라 **변별력**으로 정했다

`default_config`에 칸이 30개 가까이 있는데, **값이 하나뿐인 칸은 담지 않았습니다.**

```
freqency          310건 100%  값 1가지(2000)      ← 안 담음. 원본 철자 그대로다
status            287건  93%  값 1가지(current)
vcpu_architecture / os_architecture / reservation_terms / iothreads … 전부 1가지
```

**`freqency`를 담았으면 모든 IBM 스펙이 "2.0 GHz"로 나왔을 것**이고, 실제 클럭은
세대마다 다른데 우리는 그걸 모릅니다. 채움률 100%짜리를 버리는 게 이 축에서 옳은
판단이었습니다.

담은 것은 실제로 갈리는 것들입니다 — 대역폭(18가지)·포트 속도(3)·최대 NIC(5)·
NUMA(2)·CPU 제조사(Intel/AMD)·CPU 계열(Sapphirerapids 등 3)·점유 방식(3)·
프로비저닝 타임아웃(7)·GPU.

## `sustainedCpu`를 만들어 내지 않았다 — 그래서 상태를 하나 더 뒀다

IBM엔 버스트 여부도 세대 표시도 없습니다. `vcpu_tenancy`가 `dedicated`인 걸 보고
"상시 CPU 보장"이라 적고 싶어지지만 **그건 우리 추론이지 원본이 한 말이 아닙니다.**

그런데 그냥 두면 새 구멍이 생깁니다. `recommend_note`가 경고할 게 없다고 `ok`를
돌려주고, 비용 도구 꼬리말이 *"경고가 없는 후보는 성능 확인됨(상시 CPU 보장·최신
세대)"*라고 말합니다 — **확인한 적 없는 것을 확인했다고 말하는 셈**입니다. 결함 C4에서
침묵을 안전 신호로 오독하게 만든 것과 같은 모양입니다.

`NOTE_PARTIAL`을 더했습니다.

```
ibm     bx2-16x64     partial    버스트·세대 판정 불가 — ibm는 원본에 그 신호가 없습니다
aws     t3.medium     warn       버스트 인스턴스 …
aws     m5.large      warn       구세대 인스턴스입니다 …
alibaba ecs.g6.large  untracked  alibaba는 성능 신호를 추적하지 않습니다
```

## 곁다리 — `cpuVendor`가 한 번도 화면에 나온 적이 없었다

IBM을 붙이며 드러났습니다. `cpuVendor`는 aws 61.9%·ibm 82.9%로 채워져 있는데
**어느 표시 목록에도 없었습니다.** 필드 목록이 세 벌로 갈라졌던 그 문제의 잔재입니다.

# 7번 완료 — 없는 축을 웹으로 보충

도구가 "이 데이터셋에 없습니다"라고 하면 거기서 멈추고 *"직접 찾아보세요"*로 끝나고
있었습니다. 이제 **web_search로 공식 자료를 찾아 보충**합니다.

**다만 섞으면 안 됩니다** — 값을 핀 박고 근거 등급을 매기는 이유가 통째로 사라집니다.
네 규칙을 지시문에 박았습니다: 절을 나눌 것 · 출처를 적을 것 · "검증한 값이 아니다"를
밝힐 것 · **두 출처의 값을 더해 하나의 숫자로 만들지 말 것**(월 비용 합계에 웹 단가를
넣으면 그 합계는 어느 기준도 아닌 것이 됩니다).

그리고 **지식베이스가 답할 수 있는데 웹으로 가는 것은 여전히 금지**입니다 — 보충은
없다고 확인된 뒤의 일입니다. 프로브 둘이 짝으로 그걸 지킵니다.

| | 무엇을 지키나 | 결과 |
|---|---|---|
| P4 | 없는 축(AWS 스팟)을 웹으로 보충하고 출처를 밝히는가 | ✓ |
| P5 | 있는 축(Azure 예약)에서 웹으로 새지 않는가 | ✓ |

실측에서 P4가 낸 답입니다:

```
1️⃣ 지식베이스 … 조회·제공할 수 없습니다
2️⃣ 웹 검색으로 찾아본 최신 Spot 가격(보조 정보)
   | 리전 | Spot 가격 | 출처 |
   | us-east-1 | $0.0354/hr | https://www.doit.com/… |
```

절이 갈렸고 출처가 붙었고 "보조 정보"라고 표시됐습니다.

> **기계로 강제한 것은 아닙니다.** `claim_check`가 지어낸 값과 출처 세탁은 잡지만,
> "웹 값을 검증된 값처럼 적었는가"는 문장의 뜻을 봐야 하는 일이라 잡지 못합니다.
> 프로브 둘로 재기만 합니다.

## 남은 것

- **불안정한 프로브 셋** — 전수 46건에서 `1-2a`·`H1`·`BU1`이 재시도로 통과했다.
- **`priced_as_free`가 매 회차 잡는 것** — 도구가 "값을 매길 수 없다"고 한 칸에
  모델이 자기 기억으로 "무료"를 덧붙인다. 회차마다 0~4건으로 **개수가 흔들린다** —
  한 번 재고 "1건 남았다"고 적었다가 정정했다.
- **번들 총비용은 여전히 못 낸다.** 5번이 늘린 것은 **VM 가격의 종류**(스팟·예약·
  저축 플랜)이지 vNet·서브넷·보안그룹의 가격이 아니다. Azure Retail API에
  `Networking` 서비스 패밀리가 있긴 하지만, 그건 스펙 이름이 아니라 **미터 단위**라
  `core::vNet`에 붙일 조인 키가 없다 — 별도 작업이다.
- **성능 축은 여전히 프로바이더 넷.** 6번으로 IBM이 붙어 셋에서 넷이 됐지만
  alibaba·tencent·ncp·kt·nhn·openstack **여섯은 소스 부재가 확정**이다. 그리고 IBM은
  버스트·세대 신호가 없어 다른 셋과 **같은 질문에 답하지 못한다** — 넷이 됐다고
  프로바이더 간 비교가 가능해진 것은 아니다.
- **웹 보충은 기계로 강제되지 않는다.** 절을 나눴는지·검증 여부를 밝혔는지는
  문장의 뜻을 봐야 해서 프로브로만 잰다.
