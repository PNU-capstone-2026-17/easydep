# 클라우드 지식베이스 해설서 — AI 에이전트에게 무엇을, 왜, 어떻게 가르쳤나

> 이 문서는 클라우드를 잘 모르는 분도 이해할 수 있도록, 이 프로젝트가 만든 **세 개의
> 지식베이스**가 무엇을·왜·어떻게 만들어졌는지 설명합니다.
> 전문 용어는 처음 등장할 때마다 뜻을 풀어서 적었습니다.

**세 지식베이스는 각각 다른 질문에 답합니다.** 이 문서도 그 순서로 읽으면 됩니다.

| 축 | 패키지 | 답하는 질문 | 이 문서에서 |
|---|---|---|---|
| **의존성** | `graphkb` | 무엇이 무엇을 필요로 하나 (조립 순서) | 1~12장 |
| **용량·제약** | `capacitykb` | 무엇이 허용되나 / 한도 / 바꿀 수 있나 | 13장 |
| **스펙·가격** | `costkb` | 무엇을 살 수 있고 얼마인가 | 14장 |
| **성능** | `perfkb` | 그게 실제로 얼마나 빠른가 | 15장 |

처음 읽는다면 1~4장(배경과 용어)을 먼저 보시고, 특정 축이 궁금하면 위 표에서 바로
해당 장으로 건너뛰어도 됩니다. 전체 요약만 원하면 마지막 17장을 보세요.

> 직접 돌려보고 싶다면 [`kb-test-queries.md`](kb-test-queries.md)에 축별 질의와 **함정
> 질의**(에이전트가 "모른다"고 말해야 하는 경우)가 기대 결과와 함께 정리돼 있습니다.

## 1. 무엇을 만들었나? — 한 문장 요약

먼저 첫 번째 축(`graphkb`, 의존성)부터 봅니다. 나머지 둘은 13·14장에 있습니다.

**"클라우드에서 리소스 X를 만들려면 그 전에 무엇부터 만들어야 하는가?"**
라는 질문에 컴퓨터(AI 에이전트)가 즉시 답할 수 있도록,
클라우드 리소스들 사이의 **선후 관계 지도(의존성 그래프)** 를 자동으로 만들어주는
파이썬 프로그램을 만들었습니다.

### 비유: 이케아 가구 조립 설명서

이케아 책장을 조립한다고 생각해 보세요. 설명서에는 이런 순서가 있습니다.

> 바닥판을 먼저 놓고 → 옆판을 세우고 → 선반을 끼우고 → 마지막에 뒷판을 붙인다

순서를 어기면 조립이 안 됩니다. 클라우드도 똑같습니다.
"가상 서버 한 대"를 만들려면 그 전에 "가상 네트워크"가 있어야 하고,
그 안에 "구역(서브넷)"이 있어야 하고, "방화벽 규칙"과 "출입 열쇠"도 준비돼 있어야 합니다.

문제는 이 조립 순서가 **문서 어디에도 지도 한 장으로 정리돼 있지 않다**는 것입니다.
사람은 경험으로 알지만, AI 에이전트는 모릅니다. 그래서 우리가
공개된 기술 문서들을 자동으로 읽어서 **조립 설명서(그래프)를 기계가 읽을 수 있는
형태로 뽑아내는 도구**를 만든 것입니다.

## 2. 배경 용어 사전 — 클라우드란 무엇인가

먼저 이 프로젝트에 계속 나오는 개념들을 정리합니다.

| 용어 | 뜻 | 비유 |
|---|---|---|
| **클라우드(Cloud)** | 아마존(AWS), 마이크로소프트(Azure), 구글(GCP) 같은 회사가 자기네 데이터센터의 컴퓨터를 인터넷으로 빌려주는 서비스 | 발전기를 직접 사는 대신 전기를 사서 쓰는 것 |
| **CSP** | Cloud Service Provider. 위의 클라우드 제공 회사들을 부르는 말 | 전력 회사 (한전, 민간 발전사…) |
| **리소스(Resource)** | 클라우드에서 빌려 쓰는 부품 하나하나. 가상 서버, 네트워크, 저장소 등 | 가구 조립 부품 (판자, 나사, 선반) |
| **리소스 타입(Type)** | 리소스의 "종류". 이 프로젝트가 다루는 건 개별 부품이 아니라 부품의 **종류** 간 관계 | "M6 나사"라는 규격 자체 (내 책상에 박힌 나사 1개가 아니라) |

### 이 프로젝트에 등장하는 대표 리소스 타입들

- **VM (Virtual Machine, 가상 머신)** — 클라우드에서 빌리는 컴퓨터 한 대.
  실제 기계가 아니라 소프트웨어로 흉내 낸 컴퓨터라서 "가상"입니다.
  *비유: 원룸 건물에서 방 하나를 빌리는 것. 건물(물리 서버) 하나를 여러 명이 나눠 씁니다.*
- **vNet / VPC (가상 네트워크)** — 내 리소스들만 모여 사는 **사설 구역**.
  AWS에서는 VPC(Virtual Private Cloud), 중립 용어로는 vNet이라 부릅니다.
  *비유: 아파트 단지. 이 단지 안에 내 건물들을 짓습니다.*
- **서브넷(Subnet)** — 가상 네트워크를 더 잘게 나눈 **구역**.
  *비유: 아파트 단지 안의 101동, 102동.*
- **시큐리티 그룹(Security Group)** — 리소스에 붙이는 **방화벽 규칙 묶음**.
  "80번 문으로 오는 손님만 받아라" 같은 출입 규칙입니다.
  *비유: 건물 경비실의 출입 허용 명단.*
- **SSH 키(sshKey)** — 서버에 원격 접속할 때 쓰는 **디지털 열쇠**.
- **스펙(spec)** — 빌릴 컴퓨터의 사양(CPU 몇 개, 메모리 몇 GB). *비유: 방 평수와 옵션.*
- **이미지(image)** — 서버에 처음 깔려 나오는 소프트웨어 묶음(운영체제 등).
  *비유: 입주 시 기본 설치된 가전/가구 패키지.*
- **NLB (Network Load Balancer, 부하 분산기)** — 손님(접속)을 여러 서버에 골고루
  나눠주는 장치. *비유: 은행 창구 번호표 기계.*
- **K8s (쿠버네티스, Kubernetes)** — 수많은 서버 위에서 프로그램들을 자동으로
  배치·관리해 주는 시스템. 글자 수가 길어 K8s(K + 8글자 + s)로 줄여 씁니다.
  *비유: 대형 물류센터의 자동 배차 관제 시스템.*

### "의존성"이란?

**A가 B에 의존한다 = A를 만들려면 B가 먼저 있어야 한다**는 뜻입니다.

예를 들어 "서브넷은 VPC에 의존한다"는 말은, 101동(서브넷)을 지으려면
먼저 아파트 단지(VPC)가 조성돼 있어야 한다는 뜻입니다.

### "그래프"란? (수학 시간의 그 그래프가 아닙니다)

여기서 그래프는 꺾은선 그래프가 아니라, **점과 화살표로 관계를 그린 지도**를 말합니다.

- **노드(node, 점)** = 리소스 타입 하나 (예: "서브넷"이라는 종류)
- **엣지(edge, 화살표)** = 두 타입 사이의 의존 관계 (예: 서브넷 → VPC)

```
   VM ──→ 서브넷 ──→ VPC
   │                  ↑
   └──→ 시큐리티그룹 ─┘
```

이런 지도가 있으면 컴퓨터가 화살표를 따라가기만 해도
"VM을 만들려면 VPC → 서브넷/시큐리티그룹 → VM 순서로 만들어야 한다"를 계산할 수 있고,
반대로 화살표를 거슬러 올라가면 "VPC를 지우면 서브넷·VM이 모두 영향받는다"도 알 수 있습니다.

## 3. 왜 만들었나? — AI 에이전트의 지식베이스

이 저장소(agent-sdk)에는 클라우드 관련 작업을 도와주는 AI 에이전트(`nim_agent/`)가 있습니다.
AI에게 "서버 한 대 배포해줘"라고 시키려면, AI가 **배포 순서**를 알아야 합니다.

AI가 매번 인터넷을 검색해서 순서를 추측하게 하면 느리고 부정확합니다. 대신
**미리 만들어 둔 정확한 지도(지식베이스)** 를 주면, AI는 그걸 조회만 하면 됩니다.
`graphkb`(graph knowledge base, 그래프 지식베이스)가 바로 그 지도 생성기입니다.

중요한 특징: 이 지도는 **"지금 떠 있는 서버 목록"이 아니라 "종류 간의 규칙"** 을 담습니다.
전화번호부(현재 상태)가 아니라 문법책(규칙)에 가깝습니다. 그래서 한 번 만들면
클라우드 계정이나 비밀번호 없이도 계속 쓸 수 있습니다.

## 4. 지도의 재료 — 어디서 정보를 얻었나

지도를 그리려면 "누가 누구를 필요로 하는지" 적힌 원본 자료가 필요합니다.
다행히 클라우드 업계에는 **기계가 읽을 수 있는 공식 명세서**들이 공개돼 있습니다.

### 용어: API, 스키마, JSON

- **API** (Application Programming Interface) — 프로그램끼리 대화하는 창구.
  "서버 만들어줘"라는 요청을 정해진 형식으로 보내는 접수 창구라고 생각하면 됩니다.
- **JSON** — 컴퓨터끼리 데이터를 주고받을 때 쓰는 표준 문서 형식.
  `{ "이름": "값" }` 꼴의 중괄호 텍스트입니다. 이 프로젝트의 입력도 출력도 대부분 JSON입니다.
- **스키마(schema)** — 문서의 **양식/서식**. "서버 생성 신청서에는 이름 칸(필수),
  네트워크 ID 칸(필수), 설명 칸(선택)이 있다"처럼, 어떤 항목이 있고 무엇이 필수인지
  정의한 규격입니다. *비유: 주민센터 민원 신청서 양식.*

핵심 아이디어는 이것입니다:

> **"서버 생성 신청서 양식에 '네트워크 ID를 적으시오'라는 칸이 있다면,
> 그건 곧 '서버는 네트워크에 의존한다'는 뜻이다."**

신청서 양식(스키마)만 읽어도 의존 관계를 알 수 있으니,
실제로 서버를 만들어보지 않고도 지도를 그릴 수 있습니다.

### 재료 1: CB-Tumblebug의 API 명세서 (중립 지도용)

- **Cloud-Barista / CB-Tumblebug** — 여러 클라우드(AWS·Azure·GCP 등)를
  **하나의 공통 언어로** 다루게 해주는 국내 주도 오픈소스 프로젝트입니다.
  *비유: 나라마다 콘센트 모양이 달라도 다 꽂히는 만능 여행용 어댑터.*
- Tumblebug은 자기 API의 신청서 양식들을 **Swagger(OpenAPI)** 라는 표준 형식의
  파일로 공개합니다. Swagger는 "API 신청서 양식 모음집의 표준 포맷"이라고 보면 됩니다.
- 여기서 뽑은 지도는 특정 회사에 얽매이지 않은 **중립(코어) 지도**가 됩니다.

### 재료 2: AWS CloudFormation 리소스 스키마 (AWS 상세 지도용)

- **CloudFormation** — AWS의 "설계도 기반 자동 건축" 서비스입니다. 설계도(템플릿)를
  내면 AWS가 그대로 리소스를 지어 줍니다. AWS는 이 서비스를 위해
  **1,630종의 리소스 타입 각각에 대한 신청서 양식(JSON 스키마)** 을 zip 파일로 공개합니다.
- 일부 양식에는 `relationshipRef`라는 **친절한 각주**가 붙어 있습니다.
  "이 칸에 적는 값은 AWS::EC2::VPC의 ID입니다"라고 관계를 명시해 주는 것이죠.

### 재료 3: CDK 팀의 관계 데이터 (AWS 지도의 보강재)

구현하면서 중요한 사실을 발견했습니다. 위의 친절한 각주(`relationshipRef`)가
**1,630개 양식 중 겨우 26개에만** 붙어 있었습니다. 심지어 가장 기본적인
"서브넷 → VPC" 관계조차 각주가 없었습니다.

다행히 AWS의 다른 팀(CDK 팀)이 **별도 파일로 관계 목록(약 350개 타입, 968건)** 을
관리하고 있어서 이를 함께 가져왔습니다. *비유: 교과서(공식 스키마)에 각주가 부실해서,
유명 참고서(CDK 데이터)를 함께 보는 것.*

## 5. 만든 프로그램의 구조 — 공장 라인처럼

`graphkb/` 폴더 안의 파일들은 각자 역할이 나뉜 공장 라인입니다.

```
graphkb/
├── fetch.py        ← [자재 입고] 인터넷에서 명세서 다운로드 + 창고(캐시)에 보관
├── parsers/        ← [가공] 명세서를 읽어 의존 관계를 뽑아내는 기계
│   ├── tumblebug.py   ← Tumblebug 명세서 담당 (중립 지도)
│   └── cfn.py         ← AWS CloudFormation 담당 (AWS 지도)
├── model/          ← [규격 검사] 지도의 표준 양식 정의 + 불량품 검사
│   ├── graph.py       ← 노드/엣지/그래프 자료형
│   └── schema.json    ← "올바른 지도 파일"의 규격서
├── query.py        ← [활용] 완성된 지도에서 "조립 순서" 계산
├── export/         ← [포장] 사람이 눈으로 볼 수 있는 그림 형식으로 변환
│   ├── graphml.py     ← GraphML 형식 (그래프 전용 프로그램용)
│   └── dot.py         ← DOT 형식 (Graphviz라는 그림 도구용)
└── cli.py          ← [조작반] 터미널에서 명령어로 전체 라인을 조작
```

몇 가지 용어:

- **캐시(cache)** — 한 번 다운로드한 파일을 로컬(`.cache/graphkb/`)에 보관해 두고
  다음부터는 다시 안 받는 것. *비유: 장 봐온 재료를 냉장고에 넣어두는 것.*
- **파서(parser)** — 문서를 읽고 필요한 정보만 뽑아내는 프로그램.
  *비유: 신청서 더미에서 "네트워크 ID 칸"만 골라 형광펜 치는 사무원.*
- **CLI** (Command Line Interface) — 마우스 클릭 대신 **글자 명령어**로 프로그램을
  조작하는 방식. 검은 터미널 창에 `python -m graphkb build ...`처럼 칩니다.

## 6. 지도 데이터는 실제로 어떻게 생겼나

모든 지도는 아래처럼 생긴 JSON 파일로 저장됩니다 (`output/` 폴더).

```json
{
  "nodes": [
    {
      "id": "aws::AWS::EC2::Subnet",        ← 점(리소스 타입)의 고유 이름
      "layer": "vendor",                     ← 벤더(회사별) 지도인지 중립 지도인지
      "provider": "aws",                     ← 어느 회사 것인지 (중립이면 "common")
      "kind": "resource_type",
      "display_name": "AWS::EC2::Subnet",
      "source": "cloudformation-registry"    ← 이 정보의 출처
    }
  ],
  "edges": [
    {
      "from": "aws::AWS::EC2::Subnet",       ← 화살표 시작 (의존하는 쪽)
      "to": "aws::AWS::EC2::VPC",            ← 화살표 끝 (먼저 있어야 하는 쪽)
      "type": "references",                  ← 관계 종류 (아래 설명)
      "via_property": "VpcId",               ← 신청서의 어느 칸에서 발견했는지
      "required": true,                      ← 그 칸이 필수 기입란이었는지
      "cardinality": "one",                  ← 하나를 가리키나(one) 여러 개인가(many)
      "evidence": "cdk-oob",                 ← 근거가 무엇이었는지 (아래 설명)
      "confidence": 0.9                      ← 이 관계를 얼마나 확신하는지 (0~1)
    }
  ]
}
```

### 관계의 세 종류 (`type`)

| 종류 | 뜻 | 예 |
|---|---|---|
| `references` (참조) | A 신청서에 B의 ID를 적는 칸이 있음 → B가 먼저 필요 | VM 신청서의 "서브넷 ID" 칸 |
| `contained_in` (포함) | A는 B **안에** 들어가는 존재 | 서브넷은 VPC 안에 포함됨 (101동은 단지 안에) |
| `equivalent_to` (동치) | 서로 다른 회사 용어지만 같은 것 (Phase 2 예정) | 중립 vNet = AWS VPC |

### 근거와 신뢰도 (`evidence`, `confidence`) — 이 지도의 정직함 장치

모든 화살표에는 **"내가 왜 이렇게 판단했는지"** 와 **"얼마나 자신 있는지"** 를 남깁니다.

| evidence | 무슨 근거? | confidence |
|---|---|---|
| `relationshipRef` | AWS 공식 각주에 명시됨 | 1.0 (확실) |
| `swagger-field` | Tumblebug 신청서의 알려진 칸 이름 | 1.0 (확실) |
| `cdk-oob` | AWS CDK 팀이 관리하는 별도 관계 목록 | 0.9 (거의 확실) |
| `heuristic` | 칸 이름을 보고 추측 (아래 7절) | 0.5~0.6 (추측) |

*비유: 지도에 "실측한 길"은 실선으로, "주민 증언으로 추정한 길"은 점선으로
그려두는 것. 나중에 지도를 쓰는 쪽(AI)이 점선을 믿을지 말지 선택할 수 있습니다.*

## 7. 파서들이 일하는 방식

### 7-1. Tumblebug 파서 — 중립 지도 만들기

1. Tumblebug의 Swagger 명세서 파일을 내려받습니다.
   (버전을 v0.11.8로 **고정**했습니다. 최신 버전에서 용어가 대거 바뀌어서,
   결과가 매번 달라지지 않도록 검증된 버전에 못 박은 것입니다.)
2. 그 안에서 **"생성 신청서" 양식들만** 골라냅니다 (예: `TbSecurityGroupReq` =
   시큐리티 그룹 생성 요청 양식). 응답 양식은 서버가 채워주는 값이 많아 잡음이 되므로
   쓰지 않습니다.
3. 양식의 칸 이름을 봅니다. `vNetId` 칸이 있으면 "→ vNet" 화살표를,
   `sshKeyId` 칸이 있으면 "→ sshKey" 화살표를 긋습니다.
   이때 그 칸이 필수(required)였는지도 함께 기록합니다.
4. 어떤 양식이 다른 양식을 통째로 품고 있으면(예: vNet 신청서 안에 서브넷 목록이
   들어감) `contained_in`(포함) 관계로 기록합니다.

**결과: 13개 타입, 19개 관계.** 브리프가 요구한
"vNet → 서브넷 → 시큐리티그룹 → VM" 조립 사슬이 그대로 재현됩니다.

### 7-2. CloudFormation 파서 — AWS 상세 지도 만들기

AWS 쪽은 양식이 1,630개나 되고, 공식 각주가 부실해서 **세 가지 방법을 병행**합니다.

1. **공식 각주 읽기** (`relationshipRef`, 신뢰도 1.0)
   — 있으면 가장 확실하지만 26개 양식에만 존재.
2. **참고서 대조** (`cdk-oob`, 신뢰도 0.9)
   — CDK 팀의 관계 목록 968건을 가져옴. "서브넷 → VPC" 같은 핵심 관계가 여기서 나옴.
3. **이름 보고 추측하기** (`heuristic`, 신뢰도 0.5~0.6)
   — **휴리스틱(heuristic)** 이란 "완벽한 규칙은 아니지만 대체로 잘 맞는 어림짐작"
   이라는 뜻입니다. 칸 이름이 `VpcId`라면 "아마 VPC를 가리키겠지"라고 추측하는 식이죠.
   *비유: 택배 상자에 "김치"라고 적혀 있으면 열어보지 않아도 내용물을 짐작하는 것.*

   추측이므로 오답 방지 장치를 달았습니다:
   - 이름과 일치하는 타입이 **정확히 하나일 때만** 화살표를 긋습니다 (애매하면 포기).
   - 신뢰도를 낮게(0.5~0.6) 적어, 확실한 정보와 섞이지 않게 합니다.
   - 같은 관계가 여러 방법으로 발견되면 **신뢰도 높은 근거 하나만** 남깁니다.

   또 하나의 함정 방지: 양식에는 "내가 만들어지고 나서 발급받는 값"(읽기 전용,
   readOnly) 칸도 있는데, 이건 조립 순서와 무관하므로 전부 제외했습니다.
   이걸 안 걸렀다면 화살표 방향이 뒤집힌 오류 데이터가 섞일 뻔했습니다.

**결과: 1,631개 타입, 2,373개 관계** (참고서 1,220 / 추측 1,094 / 공식 각주 59).

## 8. 완성된 지도 사용법 — 명령어 몇 가지

터미널에서 아래처럼 씁니다. (`python -m graphkb`는 "graphkb 프로그램을 실행하라"는 뜻)

```bash
# 1) 지도 만들기 (인터넷에서 명세서를 받아와 output/ 폴더에 저장)
python -m graphkb build --source tumblebug   # → output/core-graph.json (중립 지도)
python -m graphkb build --source cfn         # → output/aws-graph.json  (AWS 지도)

# 2) 조립 순서 물어보기
python -m graphkb query --deps vm
```

실제 출력 예 — "VM을 만들려면 뭐부터?":

```
core::vm 생성에 필요한 선행 체인 (위상순):
  1. core::image        ← 이런 것들을 먼저 만들고
  2. core::spec
  3. core::sshKey
  4. core::vNet
  5. core::securityGroup
  6. core::subnet
  7. core::vm (self)    ← 마지막에 VM 자신
```

여기서 **위상순(위상 정렬, topological sort)** 이란, "선행 조건이 항상 먼저 오도록
줄 세우는 것"을 말합니다. *비유: 대학 수강 계획 — 전공기초를 먼저 듣고 전공심화를
듣도록 학기 순서를 짜는 것.*

```bash
# 3) 삭제 영향 물어보기 — "VPC를 지우면 뭐가 무너지나?"
python -m graphkb query --dependents AWS::EC2::VPC

# 4) 사람 눈으로 볼 그림 파일로 변환
python -m graphkb export --format dot --graph output/core-graph.json
```

## 9. 품질은 어떻게 보장했나 — 테스트

**테스트(test)** 란 "프로그램이 약속대로 동작하는지 자동으로 검사하는 코드"입니다.
*비유: 출고 전 자동차 검사 라인.* 이 프로젝트에는 51개의 검사 항목이 있고 전부 통과합니다.

특징적인 부분:

- **골든 케이스(golden case)** — "이 관계만큼은 반드시 나와야 한다"고 정해둔
  대표 정답들. 예: "서브넷 → VPC", "시큐리티그룹 → vNet". 파서를 아무리 고쳐도
  이 정답이 깨지면 검사가 실패하도록 해뒀습니다.
- **픽스처(fixture)** — 검사용으로 미리 잘라 둔 **진짜 명세서의 축소판**.
  실제 파일에서 발췌했기 때문에 현실과 같고, 파일로 저장돼 있어서
  **인터넷 없이도** 검사가 돌아갑니다.
- 지도 파일을 저장할 때마다 규격서(`model/schema.json`)와 대조해
  형식이 어긋난 데이터는 아예 저장되지 않게 했습니다. *비유: 규격 미달 제품은
  포장 단계에서 자동으로 걸러지는 검수기.*

## 10. 설계 과정에서 내린 주요 결정들

| 결정 | 이유 |
|---|---|
| Tumblebug 명세서를 v0.11.8 버전에 고정 | 최신 개발 버전은 용어가 대거 바뀌는 중이라, 오늘 만든 지도와 내일 만든 지도가 달라질 수 있음. 검증된 버전에 고정해 재현성 확보 |
| 추측(휴리스틱)을 기본으로 켬 | AWS 공식 각주가 1,630개 중 26개에만 있어서, 추측 없이는 지도가 거의 백지가 됨. 대신 신뢰도 표기로 구분 |
| 그래프 전문 라이브러리(networkx) 안 씀 | 노드 수천 개 수준에서는 기본 파이썬만으로 충분. 외부 의존성을 줄여 유지보수 부담 감소 |
| 다운로드 캐시 사용 | 매번 수 MB를 다시 받지 않도록. `--refresh` 옵션으로 강제 갱신 가능 |

## 11. Phase 2 — Azure·GCP 지도와 "번역 사전" (완료)

Phase 1이 중립 지도와 AWS 지도였다면, Phase 2에서는 나머지 두 대형 클라우드의
지도와, 지도들 사이를 잇는 번역 사전을 만들었습니다.

### 11-1. Azure 지도 — 타입 색인에서 뽑아내기

Azure의 설계도 언어는 **ARM/Bicep**이라고 부릅니다(AWS의 CloudFormation에 해당).
마이크로소프트는 모든 리소스 타입의 목록과 상세 규격을
`bicep-types-az`라는 저장소에 기계가 읽기 좋은 형태로 공개합니다.

Azure에는 재미있는 공짜 정보가 하나 있습니다. 타입 이름 자체가 **주소 체계**라서,
`Microsoft.Network/virtualNetworks/subnets`라는 이름만 봐도
"subnets는 virtualNetworks 안에 포함된다"는 사실을 알 수 있습니다.
*비유: "서울시/강남구/역삼동"이라는 주소만 봐도 역삼동이 강남구 소속임을 아는 것.*
색인 파일 하나(약 6MB)로 **3,382개 타입 전체의 노드와 포함 관계**를 얻었습니다.

반면 참조 관계는 아쉽게도 Azure가 명시 각주를 지워버려서(변환 과정에서 소실),
"이 칸의 데이터 모양이 서브넷의 모양과 같다"는 **구조적 단서**로 찾아냈고
(신뢰도 0.8), 이름 추측(0.6)으로 보강했습니다.

### 11-2. GCP 지도 — 쿠버네티스 문서에서 뽑아내기

구글은 **Config Connector(KCC)** 라는 도구를 통해 GCP 리소스들의 규격서를
공개합니다. 이 규격서에는 참조 필드가 `networkRef`처럼 **"~Ref"로 끝나는 칸**으로
아주 규칙적으로 표시돼 있어 찾기는 쉽습니다. 문제는 "이 Ref가 **어떤 종류**를
가리키는지"가 본문 설명 문장 속에 숨어 있다는 것. 그래서 3단계로 해석합니다:

1. 구글이 별도로 관리하는 **매핑 메타데이터 파일**에서 찾기 (확실, 신뢰도 1.0)
2. 설명 문장의 정형 패턴("ComputeNetwork 리소스의 selfLink 값")을
   정규식으로 읽기 (신뢰도 0.9)
3. 필드 이름으로 추측 (networkRef → ComputeNetwork, 신뢰도 0.6)

결과: compute·container 서비스 기준 **95개 타입, 203개 관계**.

### 11-3. 매핑 레이어 — 3개 지도를 잇는 번역 사전

"중립 지도의 vNet = AWS의 VPC = Azure의 virtualNetworks = GCP의 ComputeNetwork"
처럼 **회사별 용어를 잇는 번역 사전**입니다. 관계 종류는 `equivalent_to`(동치).

근거는 **CB-Spider**(Cloud-Barista의 멀티클라우드 드라이버)의 소스 코드입니다.
CB-Spider는 "중립 명령 → 각 회사 API 호출"로 번역하는 프로그램이므로,
그 코드가 곧 살아있는 번역 사전인 셈입니다. 코드를 분석해 **28건의 매핑**을
사람이 검수한 표로 만들어 두었고, 흥미로운 발견들도 기록했습니다:

- GCP에는 "시큐리티 그룹"이라는 단일 개념이 없어서, 규칙 하나마다 방화벽
  리소스를 여러 개 만드는 방식으로 흉내냅니다 (1:N 매핑, 신뢰도 0.7로 하향)
- GCP에는 "SSH 키"라는 독립 리소스가 아예 없습니다 (매핑 항목 없음)
- AWS CloudFormation에는 커스텀 이미지(AMI)를 만드는 타입이 없습니다

**반자동 검수 파이프라인**도 있습니다: `suggest-mapping` 명령이 이름 유사도로
새 후보를 뽑아 검수 파일을 만들면, 사람이 확인 표시(status: confirmed)를 하고
다시 넣는 구조입니다. 실제로 이 후보 목록 덕분에 "GCP에 ComputeMachineImage
타입이 존재한다"는 사실(조사 단계의 결론을 뒤집는 발견)을 찾아
customImage 매핑을 하나 더 확정했습니다.

### 11-4. 새 명령어

```bash
python -m graphkb build --source azure     # → output/azure-graph.json
python -m graphkb build --source gcp       # → output/gcp-graph.json
python -m graphkb build --source mapping   # → output/mapping-graph.json (번역 사전)
python -m graphkb suggest-mapping          # 매핑 후보 생성 (사람 검수용)
```

## 12. Phase 3 — 지도를 AI 에이전트의 손에 쥐여주기 (완료)

지도를 만들었으니, 이제 실제로 **쓰는** 단계입니다.

### 12-1. 에이전트 질의 도구 — AI가 지도를 직접 펼쳐본다

이 저장소의 AI 에이전트(`nim_agent`)에 5개의 도구를 새로 등록했습니다.
에이전트가 대화 중 필요하면 알아서 호출합니다:

| 도구 | 답하는 질문 | 비유 |
|---|---|---|
| `kb_creation_order` | "X를 만들려면 뭐부터?" | 조립 설명서의 순서 페이지 |
| `kb_deletion_impact` | "X를 지우면 뭐가 무너지나?" | 젠가에서 이 블록 빼도 되나 |
| `kb_equivalent_types` | "AWS의 VPC가 Azure에선 뭐지?" | 번역 사전 찾아보기 |
| `kb_describe_type` | "X는 정확히 뭘 참조하지?" | 부품 상세 스펙 카드 |
| `kb_search_types` | "서브넷 관련 타입 다 보여줘" | 지도 색인에서 검색 |
| `kb_rank_types` | "**전체 중** 의존성이 가장 큰 타입은?" | 지도 전체를 놓고 보는 통계 |

**`kb_rank_types`를 왜 따로 뒀나** — 앞의 5개는 전부 **타입 하나씩** 물어보는 도구입니다.
"AWS 전체에서 의존성이 가장 큰 타입은?" 같은 질문을 이 도구들로 풀려면 1,631개를 하나씩
조회해야 해서 **영원히 끝나지 않습니다**(실제로 에이전트가 시도하다 턴 한도에 걸렸습니다).
전체를 훑는 질문에는 전체를 한 번에 세는 도구가 따로 있어야 합니다.

실제로 물어보면:

```
AWS에서 의존받는(= 삭제 시 영향 주는) 타입 상위 3개
  1. AWS::IAM::Role   — 198개
  2. AWS::EC2::Subnet — 116개
  3. AWS::EC2::VPC    —  64개
```

*IAM Role과 서브넷이 최상위라는 건 클라우드를 아는 사람의 직관과 정확히 일치합니다 —
지도가 현실을 제대로 반영하고 있다는 방증이기도 합니다.*

설계 결정 하나: 브리프는 "text-to-Cypher(AI가 데이터베이스 질의문을 직접 작성)
또는 사전 정의 질의 API" 중 선택하라고 했는데, **사전 정의 질의**를 택했습니다.
AI가 임의로 질의문을 지어내면 틀린 질의를 검증하기 어렵고 데이터베이스 없이는
동작하지 않는 반면, 사전 정의 함수는 안전하고 JSON 파일만으로 돌아갑니다.

실제 동작 예 — "AWS VPC가 다른 클라우드에선 뭐야?":

```
aws::AWS::EC2::VPC 와 같은 것을 가리키는 타입:
- core::vNet (common)
- azure::Microsoft.Network/virtualNetworks (azure)
- gcp::ComputeNetwork (gcp)
```

### 12-2. Neo4j 적재 — 그래프 전용 서랍장에 넣기

**Neo4j**는 그래프(점·화살표) 저장에 특화된 데이터베이스입니다.
*비유: 지금까지의 JSON 파일이 "지도를 접어 넣은 서류봉투"라면, Neo4j는
"벽에 펼쳐 붙인 상황판" — 복잡한 관계 탐색을 훨씬 빠르고 유연하게 할 수 있습니다.*

두 가지 경로를 만들었습니다:

```bash
# 경로 1: Neo4j 서버에 직접 적재 (드라이버 필요: uv sync --extra neo4j)
python -m graphkb load-neo4j --password <비밀번호>

# 경로 2: 서버 없이 적재 스크립트 파일만 생성 (나중에 붙여넣기)
python -m graphkb export --format cypher --graph output/core-graph.json
```

Neo4j 안에서는 노드가 `(:ResourceType {id, layer, provider, ...})`,
관계가 `REFERENCES / CONTAINED_IN / EQUIVALENT_TO`로 저장됩니다.

### 12-3. CB-Tumblebug MCP와의 역할 분담 (연계 검토)

**MCP**(Model Context Protocol)는 AI가 외부 시스템의 도구를 빌려 쓰는 표준
연결 방식입니다. 이 저장소는 CB-Tumblebug의 MCP 서버에 연결할 수 있는데
(`nim_agent/tumblebug_mcp.py`, `main.py --tumblebug`으로 켭니다 — 기본은 꺼져 있고
이유는 14-7절), graphkb와 역할이 겹치지 않도록 분담을 정리했습니다:

| 질문 종류 | 담당 | 예 |
|---|---|---|
| **정적 지식** (타입 간 규칙) | graphkb 도구 | "VM을 만들려면 뭐가 먼저 필요해?" |
| **동적 상태** (지금 떠 있는 것들) | Tumblebug MCP | "지금 내 VM 목록과 상태 보여줘" |

*비유: graphkb는 "요리책"(레시피·순서), MCP는 "냉장고 안 확인"(지금 뭐가 있나).*
에이전트의 자연스러운 작업 흐름은 둘을 조합합니다:
① 요리책에서 순서 확인(kb_creation_order) → ② 냉장고 확인(MCP로 기존 vNet
존재 여부 조회) → ③ 없는 것만 순서대로 생성 요청.

> ⚠️ **이 "정적 지식 vs 동적 상태" 구도는 graphkb에만 맞습니다.** 나중에 추가한
> costkb(스펙·가격)에는 깨집니다 — MCP의 `recommend_vm_spec`이 costkb와 **같은 질문**에
> 답하기 때문입니다. 자세한 건 14-4절 참고.

## 13. 두 번째 지식 차원 — capacitykb (리소스 용량·제약)

지금까지가 **"무엇이 무엇을 필요로 하나"**(의존성)였다면, 다음 차원은
**"무엇이 허용되나 / 한도는 얼마나 / 나중에 바꿀 수 있나"**입니다.

### 13-1. 왜 별도 패키지인가

지식 차원이 늘어날 때 한 폴더에 다 넣으면 유지보수가 무너집니다. 그래서 축마다
패키지를 나누고, **겹치는 것(다운로드 캐시)만** 공유합니다.

| 패키지 | 답하는 질문 | 비유 |
|---|---|---|
| `graphkb/` | 무엇이 무엇을 필요로 하나 | 조립 **순서** |
| `capacitykb/` | 무엇이 허용되나 / 한도 / 변경 가능성 | 부품 **규격표** |
| `costkb/` | 무엇을 살 수 있고 얼마인가 | **가격표** |
| `kbcommon/` | (공유) 다운로드 캐시 | 공용 창고 |

지식베이스들은 코드가 완전히 분리돼 있지만 **같은 이름표 규약**
(`aws::AWS::EC2::Subnet`)을 써서, 필요할 때 서로 이어 붙일 수 있습니다.

### 13-2. 세 가지 제약

1. **값 제약** — "디스크는 1~65,536 GiB", "이 칸엔 gp2/gp3만"
2. **변경 제약** — "이 값을 바꾸면 리소스가 **삭제되고 새로 만들어진다**"
   *비유: 조립 후엔 바닥판을 바꿀 수 없고, 바꾸려면 다 분해해야 하는 것.*
   실측해 보니 AWS 스키마의 **86.5%**가 이 정보를 명시하고 있었습니다 —
   이 소스에서 가장 풍부하고, 배포 사고를 막는 데 가장 유용한 데이터입니다.
3. **서비스 쿼터** — "구독당 vNet 1,000개", "vNet당 서브넷 3,000개"
   → 세 클라우드 중 **Azure만** 기계가 읽을 수 있는 공개 문서를 제공해서
   Azure부터 넣었습니다 (AWS는 공개 데이터셋이 없고, GCP는 문서 저장소 자체가 비공개).

### 13-3. 가장 어려웠던 부분 — 숫자가 "설명문 속"에 숨어 있다

기대와 달리, 정작 중요한 용량 숫자가 스키마의 정식 칸이 아니라 **사람이 읽는
설명문**에만 있었습니다:

> `"gp2: 1 - 16,384 GiB / gp3: 1 - 65,536 GiB / io1: 4 - 16,384 GiB …"`

그래서 설명문에서 숫자를 뽑아내는 **9개 규칙**을 만들었는데, 여기엔 함정이 있었습니다.

**함정 1 — 범위처럼 생긴 비율**: RDS의 `Iops` 설명에 `"Must be a multiple
between 1 and 50 of the storage amount"`가 있는데, 이건 범위가 아니라 **비율**입니다.
순진하게 읽으면 "최대 50"이 되어, 실제로 유효한 `Iops: 3000` 설정을 **거부**하게 됩니다.
*→ 방어: "비율/증분/예시" 같은 단어가 있는 줄은 무시(veto) + 같은 설명 안에서
하한이 상한을 넘으면(1000 > 50) 통째로 버리는 **이중 그물**.*

**함정 2 — 목록을 놓치면 정상 배포를 막는다**: 볼륨 타입을 불릿에서 긁어모으면
`[gp2, gp3, io1, io2]`가 나오는데 진실은 `+[st1, sc1, standard]`입니다. 3개를 놓치면
멀쩡한 값을 "잘못된 값"이라고 우기게 됩니다.
*→ 방어: 허용값 목록은 문서가 `Valid Values:` 라고 **명시한 한 줄**에서만 뽑음.*

**함정 3 — 범위 밖의 특수값**: SQS는 `"integer from 1 to 20"`이라면서 `"0을 지정하면
짧은 폴링"`이라고 덧붙입니다. `-1 = 무제한` 같은 것도 있죠. 하한을 그대로 믿으면
유효한 `0`을 거부합니다.
*→ 방어: 특수값 신호가 보이면 **하한을 아예 기록하지 않음**.*

관통하는 원칙은 하나입니다: **틀리더라도 느슨한 쪽으로만 틀려라(fail-open).**
잘못 막는 것이 모르는 것보다 나쁩니다.

### 13-4. 검증 — 정답지가 있는 시험

산문 추출이 맞는지 어떻게 아느냐? 두 가지로 확인했습니다.

1. **교차검증**: 스키마에 숫자가 **이미 있는** 곳에도 설명문 추출을 돌려 비교했습니다.
   정답이 있는 시험지인 셈이죠. → **겹침 24건, 불일치 0건.**
2. **전수 검토**: 설명문에서만 얻은 항목이 **31개뿐**이라 샘플링 없이 전부 사람이
   눈으로 확인하고, 그 목록을 파일로 고정했습니다. 나중에 정규식을 고쳐 결과가
   달라지면 테스트가 실패해 재검토를 강제합니다.

*수확량이 적다는 사실이 오히려 완전 검증을 가능하게 만든 셈입니다.*

### 13-5. 신뢰도로 답의 강도를 조절한다

같은 프로퍼티라도 근거가 다르면 신뢰도가 다릅니다. Lambda의 `Timeout`은
최솟값 1은 **스키마 필드**(신뢰도 1.0)인데 최댓값 900은 **설명문 추출**(0.8)입니다.
그래서 제약을 "프로퍼티당 한 줄"이 아니라 **"제약 하나당 한 줄"**로 저장합니다.

값을 판정할 때는 신뢰도 0.8 이상만 씁니다. 결과는 셋 중 하나입니다:

| 결과 | 뜻 |
|---|---|
| **불가** | 확실한 제약을 위반 |
| **판정 보류** | 확실한 제약은 없지만 참고 정보상 벗어남 → 문서 확인 권함 |
| **가능** | 확실한 제약을 실제로 검사했고 통과 |

"판정 보류"가 왜 필요하냐면 — EBS 100TB를 물었을 때 확정 제약이 없다고 **"가능"**이라
답하면 거짓말이 되기 때문입니다. 모르는 건 모른다고 해야 합니다.

### 13-6. 새 명령어와 도구

```bash
python -m capacitykb build --source cfn          # → output/aws-capacity.json (제약 46,810개)
python -m capacitykb build --source azure        # → output/azure-capacity.json (6,608개)
python -m capacitykb build --source azure-quota  # → output/azure-quota.json (쿼터 52개)
python -m capacitykb audit                       # 산문 추출 교차검증

python -m capacitykb query --check "AWS::EC2::Volume" --property Size --value 100000
python -m capacitykb query --immutable "AWS::EC2::Subnet"
python -m capacitykb query --quota subnet
```

에이전트에는 `cap_check_value`, `cap_property_limits`, `cap_immutable_properties`,
`cap_allowed_values`, `cap_service_quota` 5개 도구가 추가됐습니다. 실제로 물어보면:

> **"EBS 볼륨을 100TB로 만들 수 있어? 서브넷의 VpcId를 나중에 바꿔도 돼?"**
> → 에이전트가 스스로 두 도구를 호출해:
> "100 TB(≈102,400 GiB)는 불가능합니다. 최대 65,536 GiB(≈64 TiB)입니다."
> "VpcId는 생성 후 수정 불가 — 바꾸면 서브넷이 재생성됩니다."

## 14. 세 번째 지식 차원 — costkb (인스턴스 스펙·가격)

마지막 축은 **"무엇을 살 수 있고 얼마인가"** 입니다. 이 데이터는 원래 에이전트 폴더
안(`nim_agent/cloud/`)에 얹혀 있었는데, 지식이 에이전트에 섞여 있던 **유일한 축**이라
`costkb/`로 분리했습니다.

### 14-1. 다른 두 KB와 성격이 다르다

| | graphkb · capacitykb | costkb |
|---|---|---|
| 정체 | 공개 스키마에서 뽑은 **규칙** | **카탈로그** (가격표) |
| 근거 표시 | 레코드마다 evidence·confidence | 파일 단위 고지(`_note`) 하나 |
| 만드는 법 | `build`가 있어야 동작 | 번들 36건으로 **빌드 없이도** 동작<br>(`build`하면 73,083건으로 넓어짐) |

**왜 costkb엔 신뢰도를 안 넣었나**: capacitykb에서 신뢰도는 "스키마 필드(1.0)냐 설명문
추출(0.6)이냐"를 구분하려고 있었고, 실제로 그 값으로 판정을 걸렀습니다. costkb는 한 파일이
통째로 같은 출처·같은 방식이라 **모든 레코드가 같은 값**이 됩니다 — 쓰지도 않을 필드를
넣는 건 장식일 뿐입니다.

*단, 이것 때문에 에이전트 지침에 있던 "각 지식베이스는 근거와 신뢰도를 담고 있습니다"가
거짓말이 될 뻔해서, 그 문장을 `kb_*`/`cap_*` 한정으로 좁혔습니다.*

### 14-2. 옮기면서 메운 구멍

이 코드는 **직접 테스트가 하나도 없었습니다.** 손으로 편집하는 JSON인데 검증도 없어서,
오타(`memGib`) 하나면 로드가 아니라 한참 뒤 필터 안에서 터졌습니다. 옮기는 김에
스키마 검증(로드 시 1회)과 테스트 21개를 넣었습니다.

### 14-3. 통째로 옮기면 안 됐던 이유

`nim_agent/cloud/`를 그대로 `costkb/`로 옮기면 **화살표가 거꾸로 됩니다.** 그 안의
도구 파일이 에이전트 쪽(`session.py`의 계획 게이트)을 참조하고 있었거든요. 다른 KB들은
에이전트를 한 줄도 참조하지 않는데 costkb만 그러면 규약이 깨집니다.

*비유: 지식(백과사전)이 그걸 읽는 사람(에이전트)을 참조하면 안 됩니다.*

그래서 **가로가 아니라 세로로 잘랐습니다**:
- `costkb/` ← 데이터와 순수 로직만 (에이전트를 모름)
- `nim_agent/cost_tools.py` ← 도구 껍데기와 계획 게이트 (에이전트에 남음)

capacitykb가 이미 쓰던 구조와 똑같습니다.

### 14-4. cb-tumblebug MCP와 겹치는 유일한 축

12-3절에서 "정적 지식 = graphkb / 동적 상태 = MCP"라고 정리했는데, **costkb에는 그 구도가
깨집니다.** MCP의 `recommend_vm_spec`이 costkb와 **똑같은 질문**("이 요구사항에 맞는
인스턴스 뭐가 있고 얼마야?")에 답하기 때문입니다.

| | costkb | MCP `recommend_vm_spec` |
|---|---|---|
| 전제 | **없음** — 항상 동작 | 서버 구동 + 클라우드 자격증명 |
| 스펙 데이터 | 같은 표(미러) | 같은 표(원본) |
| 가격 | 스냅샷 — 시간이 지나면 낡음 | **라이브** |
| 역할 | **기본 경로** | 라이브 가격이 필요할 때 옵트인 |

즉 **다른 축이 아니라 같은 축의 두 소스**입니다. 왜 하필 costkb만 겹치냐면, 구조적인
이유가 있습니다:

- graphkb·capacitykb = **규칙** ("X는 Y가 필요하다", "최대 65,536 GiB") → Tumblebug에 대응물 없음
- costkb = **카탈로그** ("무엇이 있고 얼마인가") → Tumblebug도 카탈로그를 가짐 → 겹침 불가피

*비유: 요리책(규칙)은 마트에 없지만, 가격표(카탈로그)는 마트에도 있습니다.*

### 14-5. 36건의 벽 — 그리고 소스 선택이 뒤집힌 이야기

손으로 고른 36건은 데모엔 충분했지만 **경계가 너무 좁았습니다**. vCPU가 8을 넘거나
리전이 4개 밖이면 "조건을 만족하는 스펙이 없습니다"로 끝났습니다. 실소스로 넓혀야 했는데,
**여기서 처음 판단이 뒤집혔습니다.**

**처음 계획**: AWS Price List / Azure Retail Prices 같은 **1차 소스**에서 직접 가져오자.
당연해 보입니다 — 원산지에서 직접 받는 게 제일 정확할 테니까요.

**뒤집힌 이유**: 사용자가 이렇게 지적했습니다 — *"cb-tumblebug이 커버 못 하는 걸 우리도
커버 못 한다면, 그걸 소스로 쓰는 게 좋겠는데."* 확인해보니 맞았고, **직접 소스가 오히려
틀린 답을 만든다**는 게 코드로 증명됐습니다.

#### 용어: "미러(mirror)"

**미러** = 거울. 다른 곳의 데이터를 그대로 복사해 두고 오프라인에서 쓰는 사본입니다.
중요한 건 **"그대로"** — 원본에 흠이 있어도 그 흠까지 복사합니다.

#### 왜 흠까지 복사해야 하나 — 메모리 2.4% 사건

우리 에이전트가 실제로 클라우드에 물어보는 경로는 cb-tumblebug MCP의 `recommend_vm_spec`
도구입니다. 그 코드를 끝까지 따라가 보니, 결국 `spec_infos`라는 **표 하나를 읽어서 그대로
돌려줄 뿐**이었습니다:

```
recommend_vm_spec → /recommendSpec → FilterSpecsByRange → spec_infos 표
```

그런데 그 표의 메모리 값이 **GCP·Azure만 실제보다 2.4% 낮습니다.** 상위 프로젝트
(CB-Spider)의 단위 변환 함수에 버그가 있어서입니다:

```go
mib := int(mb * 1000 / 1024)   // 1024로 두 번 나눠야 하는데 한 번만 나눔
```

그래서 GCP `n2-highmem-8`은 **실제 64 GiB인데 표에는 62.5 GiB**로 적혀 있습니다.

여기가 함정입니다. AWS Price List에서 직접 가져오면 우리는 "64 GiB"라는 **맞는 값**을
갖게 됩니다. 그런데 **라이브 MCP는 여전히 62.5로 필터링합니다.** 사용자가 "메모리 64 GiB
이상"으로 물으면:

| | 우리(직접 소스) | 라이브 MCP |
|---|---|---|
| n2-highmem-8을 | 64 → **포함** | 62.5 → **제외** |

**같은 질문에 두 경로가 다른 답을 냅니다.** 더 정확한 데이터가 오히려 불일치를 만든 겁니다.

*비유: 마트 재고 시스템의 무게가 2.4% 적게 찍힌다고 합시다. 내가 정확한 저울을 들고 가서
"이건 사실 1kg야"라고 주장해도, **계산대는 여전히 976g으로 계산합니다.** 내 저울이 맞아도
계산대와 다투게 될 뿐입니다.*

그래서 costkb는 cb-tumblebug이 그 표를 통째로 커밋해 둔 백업 파일
(`assets.dump.gz`, 34 MB)에서 빌드합니다 — **라이브 MCP와 문자 그대로 같은 표**입니다.

```
recommend_vm_spec →  spec_infos  (라이브)
costkb build      →  spec_infos  (같은 표의 백업)
```

#### 그래도 사람은 진실을 봐야 한다 — 두 값 병기

버그를 복사하되 **숨기지는 않습니다.** 레코드마다 두 값을 나란히 둡니다:

- `memGiB` = **62.5** — 미러값. **필터·판정에 쓴다** (MCP와 항상 같은 답)
- `memGiBActual` = **64** — 보정값. **사람에게 보여준다**

에이전트 답변에는 `64 GiB (지식베이스 기준값 62.5)`처럼 나옵니다.

보정은 **버그를 실제로 확인한 GCP·Azure에만** 겁니다. 나머지 8개 프로바이더는 변환 경로를
추적하지 못했으므로 **건드리지 않습니다** — 모르면서 고치면 새 오류를 만듭니다. 대신
빌드할 때마다 프로바이더별로 "×1.024 하면 딱 정수가 되는 비율"(= 버그 지문)을 실측해
보여줍니다:

```
azure      n=34,846  정수 35.0%  bug 64.2% ← 보정 적용
aws        n=18,564  정수 97.9%  bug  0.0%
gcp        n=11,622  정수 19.5%  bug 77.6% ← 보정 적용
tencent    n= 2,865  정수 100.0%  bug  0.0%
alibaba    n= 2,494  정수 99.2%  bug  0.0%
...
```

추측이 아니라 **데이터가 스스로 증언합니다** — GCP·Azure만 버그 지문이 뚜렷하고
나머지는 0%입니다. 코드 추적으로 세운 가설이 실측으로 확인된 겁니다.

#### 미러 충실도의 나머지 두 조건

데이터가 같아도 **동작이 갈리면** 미러가 아닙니다. 두 개를 더 맞췄습니다:

1. **가격 `0`은 "무료"가 아니라 "모름"** — Tumblebug의 정렬 SQL이 `cost_per_hour > 0`인
   것만 가격으로 칩니다. 0을 무료로 읽으면 우리 추천 1위가 전부 "공짜 인스턴스"가 됩니다.
   실제로 0인 행이 6건, 음수(-1)가 4,372건 있었고 **4,378건 전부 "가격 미상"**으로 갑니다.
2. **`x86_64` 기본값** — MCP는 호출자가 CPU 아키텍처를 안 주면 몰래 `x86_64`를 끼워넣습니다.
   이걸 안 따라 하면 MCP에는 안 보이는 ARM 스펙이 우리에게만 보입니다.

#### 결과

```
행 73,083 → 레코드 73,083 (무효 0)
costkb: 73,083건 (가격 있음 68,705 / 94.0%) → output/tumblebug-cost.json
```

| | 전 (번들) | 후 (미러) |
|---|---|---|
| 레코드 | 36 | **73,083** |
| 프로바이더 | 3 | **10** |
| 리전 | 4 | **163** |
| vCPU 최대 | 8 | **896** |
| 메모리 최대 | 32 GiB | **32,000 GiB** |

예전엔 빈손이던 질의가 이제 답을 냅니다 — `vCPU≥64, 메모리≥256 GiB, AWS` →
`m6a.16xlarge (ap-south-1) $1.78/h`.

**번들 36건은 지웠냐고요? 아뇨.** `build`를 안 돌린 사람도, 인터넷이 없어도 즉시 동작해야
하니까 폴백으로 남겨둡니다. `output/tumblebug-cost.json`이 있으면 그쪽을, 없으면 번들을 씁니다.

*(빌드 결과물은 `output/`에 만들고 git에 올리지 않습니다 — 우리가 가격 데이터를
재배포하는 게 아니라, 각자 원본에서 받아 만드는 구조입니다.)*

### 14-6. 새 명령어

```bash
python -m costkb coverage    # 데이터셋이 어디까지 커버하는지 (빌드 불필요)
python -m costkb query --vcpu-min 4 --provider aws --region us-east-1

uv sync --extra costkb       # 미러 빌드용 덤프 파서(pgdumplib) 설치
python -m costkb build       # 34 MB 다운로드 → output/tumblebug-cost.json
```

`coverage`가 특히 쓸모 있습니다 — "조건을 만족하는 스펙이 없습니다"가 나올 때
경계를 바로 확인할 수 있습니다:

```
데이터셋 커버리지 — cb-tumblebug 미러, 총 73,083건:
  azure   34,846건  리전 39개  가격있음 94.5%  vCPU~832   메모리~14843.8 GiB
  aws     18,564건  리전 28개  가격있음 97.7%  vCPU~896   메모리~24576 GiB
  gcp     11,622건  리전 43개  가격있음 91.4%  vCPU~1920  메모리~32000 GiB
  ...
```

`build`는 **선택적 의존성**(`--extra costkb`)입니다. Neo4j 적재(12-2절)와 같은 방식으로,
안 쓰는 사람에게 34 MB짜리 덤프 파서를 강요하지 않습니다.

### 14-7. 그래서 라이브 MCP는 언제 쓰나 — 기본을 끄기로 한 이유

미러를 만들고 나니 자연스러운 질문이 남았습니다. *"그럼 비용 계산은 MCP가 아니라 costkb로
하는 건가?"* 코드를 다시 보니 **정하지 않은 채로 두고 있었습니다.**

두 도구를 **둘 다** 에이전트 손에 쥐여주고는, 무엇을 부를지는 프롬프트로 부탁만 하고
있었던 겁니다 — *"MCP가 연결돼 있으면 그것을 우선 사용하고…"*.

이 프로젝트는 그게 안 통한다는 걸 이미 비싸게 배웠습니다. 계획을 먼저 세우라는 지시를
프롬프트로 넣었을 때 **모델 3종이 전부 무시**했고, NIM은 `tool_choice`마저 무시해서 결국
도구가 **코드로 거부**하게 만들어야 했습니다(계획 게이트). 그런데 같은 종류의 지시를
여기서 또 프롬프트로 하고 있었고, 이번엔 **실측조차 안 해봤습니다.**

*비유: 냉장고에 우유 두 팩이 있는데 "오래된 것부터 드세요"라고 쪽지만 붙여놓은 셈입니다.
쪽지를 안 읽는다는 걸 이미 두 번 확인했으면서.*

그래서 **기본은 끄기로** 했습니다(`main.py --tumblebug`으로만 켬). 판단의 근거는:

- **잃는 게 거의 없다** — 미러라서 스펙 집합은 어차피 같습니다. 갈리는 건 **가격뿐**이고,
  최악의 경우가 "틀린 스펙"이 아니라 "조금 오래된 가격"입니다.
- **얻는 게 크다** — 기본 실행 경로가 costkb 하나로 확정돼서, 답이 어디서 왔는지 항상
  분명합니다. 서버·자격증명·Docker도 필요 없습니다.
- **없앤 게 아니다** — 라이브 가격이나 **실제 배포·상태 조회**(4번 축, costkb에 대응물이
  없음)가 필요하면 플래그 하나로 켭니다.

같이 정리한 게 하나 더 있습니다. **파일시스템 MCP는 아예 삭제**했습니다 — SDK 튜토리얼에서
따라온 데모 잔재로, 클라우드 지식 에이전트라는 이 프로젝트의 논지와 아무 상관이 없으면서
Node.js/npx 의존성만 끌고 있었습니다.

> **아직 안 한 것**: MCP를 켠 상태에서 에이전트가 실제로 어느 쪽을 부르는지는 **여전히
> 측정하지 않았습니다.** 지금은 그 불확실성을 기본 경로에서 치웠을 뿐입니다. 라이브 축을
> 상시로 쓰려면 그때 실측하고, 필요하면 계획 게이트처럼 코드로 강제해야 합니다.

## 15. 네 번째 지식 차원 — perfkb (인스턴스 성능)

연구 목표(research.md)가 콕 집어 요구한 항목은 넷이었습니다 — "인스턴스 **성능**, **비용**,
리소스 **용량**, **의존성**". 앞의 셋은 costkb·capacitykb·graphkb가 맡았는데, **성능만
비어 있었습니다.**

### 15-1. 왜 가격만으로는 부족한가 — 실제로 겪은 함정

costkb에 "웹서버급(vCPU 2, 메모리 4GiB) 최저가, AWS"를 물으면 이런 답이 나왔습니다:

```
t3a.medium  $0.0246/h  ← 1순위
t3.medium   $0.0416/h
t2.medium   $0.0464/h
```

**전부 "버스트(burst) 인스턴스"입니다.**

> **용어: 버스트 인스턴스** — 평소엔 성능의 일부(t3는 vCPU당 20%)만 쓰고, 남는 몫을
> "크레딧"으로 저축합니다. 잠깐 튀는 부하는 크레딧을 써서 넘기지만, **크레딧이 바닥나면
> 저축분(baseline)으로 떨어집니다.** 가끔 바쁜 서버엔 싸고 좋지만, 24시간 꾸준히 바쁜
> API 서버에 쓰면 어느 순간 느려집니다.

*비유: 평소 시속 40km로만 달리되 가끔 100km로 "부스트"할 수 있는 차입니다. 부스트 게이지가
차 있을 때만요. 고속도로를 계속 달려야 하는데 이걸 사면, 게이지가 비는 순간 40km로 기어갑니다.*

가격표만 보면 이걸 알 수 없습니다. "가장 싼 거 주세요"가 "상시 서버에 부적합한 걸 주세요"가
되는 겁니다. research.md가 성능과 비용을 나란히 쓴 이유입니다.

### 15-2. 소스가 이미 손에 있었다 — 버렸던 컬럼

costkb 미러를 만들 때(14장) cb-tumblebug의 `spec_infos` 표에서 **가격·vCPU·메모리 컬럼만
쓰고 `details` 컬럼을 버렸습니다.** 그 안에 CSP 원본 응답이 통째로 들어 있었습니다 — AWS의
경우 `describe-instance-types` 명령의 출력 그 자체이고, **73,083행 전부 채워져** 있습니다.

거기서 성능 신호를 꺼냅니다: 버스트 여부, 세대(`CurrentGeneration`), 클럭, EBS 디스크
대역폭(지속/최대), Azure의 ACU 등. 새 소스를 찾을 필요가 없었던 셈입니다.

### 15-3. 정직한 한계 — 프로바이더 간 비교는 못 한다

여기가 가장 조심한 부분입니다. **AWS와 Azure의 성능을 직접 비교할 수 없습니다.**

- Azure에는 **ACU**(Azure Compute Units)라는 성능 점수가 있지만 AWS엔 없습니다.
- AWS에는 **클럭(GHz)**이 있지만 Azure엔 없습니다.

기준이 아예 다릅니다. 그래서 "AWS m5.large vs Azure D2s_v3 중 뭐가 빨라?"는 **답할 수 없다고
말하는 게 정답**입니다. 없는 비교를 지어내는 것보다 "기준이 달라 비교 불가"가 정직합니다.
비교 도구(`perf_compare`)가 **한 번에 한 프로바이더만** 받도록 만들어, 이 한계를 코드로
강제했습니다.

*비유: 김연아의 피겨 점수와 손흥민의 골 수를 놓고 "누가 더 잘해?"라 묻는 것과 같습니다.
각자 훌륭하지만 같은 자로 잴 수 없습니다.*

또한 Azure ACU는 **약 38%만** 채워져 있습니다. 없는 건 "느리다"가 아니라 "**모른다**"로
둡니다 — capacitykb의 "판정 보류"와 같은 정신입니다.

### 15-4. 버스트를 한 단어로 뭉개지 않기

세 클라우드의 "상시 성능 안 보장" 사정이 **서로 다른 개념**입니다:

| | 왜 상시 보장 안 되나 | 어떻게 알아냈나 |
|---|---|---|
| AWS t계열 | CPU 크레딧 소진 | 명시 필드 (확실) |
| GCP 공유코어 | vCPU를 남과 나눠 씀 | 명시 필드 (확실) |
| Azure B계열 | 크레딧 모델 | **이름이 B로 시작**(추론, 덜 확실) |

그래서 레코드마다 "상시 보장?"이라는 결론과 함께 **왜 그렇게 판단했는지·얼마나 확실한지**를
같이 담습니다(graphkb·capacitykb의 근거·신뢰도와 같은 방식). Azure 판정은 이름 추론이라
신뢰도를 낮춰 두고, 사람에게 보여줄 때 "이름 규칙 추론"임을 밝힙니다.

### 15-5. 성능이 추천에 자동으로 끼어든다

가장 쓸모 있는 부분입니다. 성능을 **따로 물어봐야 나오는** 게 아니라, `cost_recommend_specs`가
후보를 줄 때 성능 경고가 **자동으로 붙습니다**:

```
- AWS t3a.medium (us-east-1): 2 vCPU / 4 GiB, $0.0376/h
    ⚠ 버스트 인스턴스 — CPU 크레딧이 소진되면 baseline 성능으로 떨어집니다.
- ALIBABA ecs.t5-lc1m2.large (us-east-1): 2 vCPU / 4 GiB, $0.0307/h
    · 성능 정보 없음 — alibaba는 성능 신호를 추적하지 않습니다(aws/azure/gcp만 수록).

※ 주석이 없는 후보는 성능 확인됨(상시 CPU 보장·최신 세대).
```

**둘째 줄과 꼬리말이 나중에 추가된 이유**가 이 기능의 핵심입니다. 처음에는 경고할 게 없을
때 아무 줄도 안 붙였는데, 그러면 (a)확인했고 괜찮음 (b)성능 데이터에 없음 (c)미추적
프로바이더 (d)perfkb 미빌드가 **전부 같은 출력**이 됩니다. `ecs.t5-lc1m2.large`는 Alibaba의
버스트 계열인데 검증된 비버스트 스펙과 글자 하나 다르지 않게 나왔습니다 — 침묵을 안전
신호로 읽게 만드는 구조라, 경고 기능 자체의 신뢰도를 무효화합니다(결함 C4).

지금은 **모르는 것은 모른다고 적고**, 침묵의 의미는 꼬리말이 한 번만 밝힙니다. 후보마다
"확인됨"을 적지 않는 건 5줄이 매번 붙으면 노이즈가 되기 때문입니다.

실제로 에이전트에게 "상시 부하 웹서버 최저가"를 물으면, 이제 최저가 t3a.medium을 주면서도
"이건 버스트라 상시 부하엔 부적합하니, 고정 성능이 필요하면 c6a.large를 고려하라"고
스스로 답합니다. 경고를 **모델이 안 물어봐도** 나오게 한 이유는, 이 프로젝트에서 "필요하면
도구를 부르라"는 프롬프트 지시가 안 통한다는 걸 여러 번 확인했기 때문입니다(계획 게이트와
같은 교훈).

경고로 삼는 건 **구매 결정을 바꾸는 것**만입니다 — 버스트와 구세대. "네트워크 대역폭이
버스트"라는 신호는 AWS의 절반에 해당해서, 경고로 쓰면 노이즈가 되므로 상세 프로파일에서만
보여줍니다.

### 15-6. 새 도구

성능은 aws/azure/gcp만 수록합니다(나머지 7개 프로바이더는 `details` 구조 미추적). 빌드 전제:
`python -m perfkb build`.

```bash
python -m perfkb build              # spec_infos.details → output/tumblebug-perf.json
python -m perfkb show --provider aws --spec m5.large
python -m perfkb coverage           # 무엇을 알고 무엇을 모르는지
```

에이전트 도구 3개(`perf_*`): 스펙 프로파일, 같은-프로바이더 비교, EBS 지속 대역폭 필터.

*(costkb의 덤프 리더는 원래 costkb 안에 있었는데, perfkb가 같은 표를 읽게 되면서 공용
인프라인 `kbcommon`으로 옮겼습니다 — 두 KB가 서로를 참조하지 않도록.)*

### 18-2. 가공 경로 — 원본 한 줄이 레코드 한 줄이 되기까지

여기서는 **실제 원본 파일을 열어** 어느 부분을 어떻게 읽었는지 보인다. 아래 인용은 전부
캐시(`.cache/cloudkb/`)에 있는 실물에서 그대로 뜬 것이다.

읽는 법: 클라우드 업체들은 자기 서비스를 **기계가 읽을 수 있는 명세서**로 공개한다.
"EC2 인스턴스를 만들려면 어떤 항목을 채워야 하고, 각 항목은 어떤 값이 허용되는가"가
적힌 설명서다. 우리는 그 설명서를 읽어 지식베이스를 만든다. 문제는 **설명서가 우리가
원하는 걸 직접 말해주지 않는다**는 것이고, 이 절은 그 간극을 어떻게 메웠는지에 대한 기록이다.

---

#### S1. AWS CloudFormation 리소스 스키마 → graphkb + capacitykb

**원본이 무엇인가**: AWS가 공개하는 zip 파일 하나에, 리소스 타입마다 JSON 파일이 하나씩
들어 있다(총 1,600여 개). 서브넷이면 `aws-ec2-subnet.json`이다.

파일을 열면 최상위 키가 이렇게 생겼다:

```
typeName, description, properties, definitions, required,
createOnlyProperties, conditionalCreateOnlyProperties,
primaryIdentifier, readOnlyProperties, writeOnlyProperties, handlers
```

##### (가) 의존성은 어디서 읽는가 — 대부분 **명시돼 있지 않다**

서브넷은 VPC 안에 만들어야 한다. 그 사실이 파일 어디에 적혀 있을까? `properties.VpcId`를
열어보면:

```json
"VpcId": {
  "type": "string",
  "description": "The ID of the VPC the subnet is in.\n If you update this property, you must also update the ``CidrBlock`` property."
}
```

**"AWS::EC2::VPC를 가리킨다"는 말이 없다.** 타입은 그냥 문자열이고, 사람이 읽는 설명문에만
"the VPC"라고 적혀 있을 뿐이다. 기계 입장에서 이건 아무 문자열이나 넣어도 되는 칸이다.

그래서 우리는 **속성 이름의 모양**으로 추론한다(`graphkb/parsers/cfn.py`):

1. 속성 이름이 `~Id` / `~Ids` / `~Arn` / `~Arns`로 끝나는가? → `VpcId`는 `Vpc` + `Id`
2. 앞부분(`Vpc`)과 이름이 맞는 리소스 타입이 존재하는가? → `AWS::EC2::VPC` 있음
3. 있으면 "서브넷 → VPC" 화살표를 긋는다

이게 `evidence: heuristic` 엣지이고 신뢰도가 낮은(0.5~0.6) 이유다. **추측이기 때문이다.**
같은 서비스 안에서 맞으면 0.6, 다른 서비스면 0.5를 준다 — `EC2::Subnet`이 `EC2::VPC`를
가리키는 건 그럴듯하지만, 엉뚱한 서비스의 비슷한 이름에 걸리면 오탐이기 때문이다.

##### (나) 가끔은 명시돼 있다 — `relationshipRef`

일부 최신 스키마에는 AWS가 참조 관계를 직접 적어뒀다.
`aws-autoscaling-launchconfiguration.json`의 `SecurityGroups`:

```json
"SecurityGroups": {
  "type": "array",
  "items": { "anyOf": [
      { "relationshipRef": {
          "typeName": "AWS::EC2::SecurityGroup",
          "propertyPath": "/properties/GroupId" } },
      ...
```

이건 추측이 아니라 **AWS가 선언한 사실**이라 신뢰도 1.0(`evidence: relationshipRef`)이다.
다만 전체 1,600여 타입 중 59건뿐이라 이것만으로는 그래프가 성기다.

> ⚠️ 여기서 우리가 **버리는 정보가 있다.** `propertyPath: "/properties/GroupId"`는
> "보안그룹의 GroupId 값을 가져다 쓴다"는 뜻인데, 현재 파서는 `typeName`만 읽고
> 이 경로를 버린다. 그래서 "VPCEndpoint가 VPC를 참조한다"로만 기록되고, 실제로는
> VPC의 `DefaultSecurityGroup` 출력을 쓴다는 사실이 사라진다
> (감사 결함 G3 — `kb-data-audit-2026-07-20.md`).

##### (다) 용량·제약은 같은 파일의 다른 부분에서 읽는다 (capacitykb)

`aws-ec2-subnet.json`의 나머지 키들이 그대로 제약 레코드가 된다:

```
required:              ["VpcId"]
                        → "VpcId는 반드시 채워야 함"
createOnlyProperties:  ["/properties/VpcId", "/properties/AvailabilityZone",
                        "/properties/CidrBlock", ...]
                        → "만들 때만 정할 수 있음. 나중에 바꾸려면 다시 만들어야 함"
readOnlyProperties:    ["/properties/SubnetId", "/properties/Ipv6CidrBlocks", ...]
                        → "AWS가 채워주는 값. 사용자가 못 씀"
primaryIdentifier:     ["/properties/SubnetId"]
```

이건 스키마가 **직접 말해주는 것**이라 신뢰도 1.0(`evidence: cfn-schema`)이다.
"서브넷을 만든 뒤 VPC를 바꿀 수 있나?" 같은 질문에 이 데이터로 답한다.

##### (라) 그런데 숫자 한도는 설명문 안에 숨어 있다 — 산문 추출의 이유

EBS 볼륨(`aws-ec2-volume.json`)에서 가장 자주 묻는 값들을 보면:

```
Size:       type=integer  minimum=None  maximum=None
Iops:       type=integer  minimum=None  maximum=None
Throughput: type=integer  minimum=None  maximum=None
```

**셋 다 스키마상 한도가 없다.** 그런데 같은 속성의 `description`을 읽으면:

```
Throughput: "The throughput to provision for a volume, with a maximum of 2,000 MiB/s.
             This parameter is valid only for ``gp3`` volumes. The default value is 125.
             Valid Range: Minimum value of 125. Maximum value of 2000. ..."

Iops:       "... Valid ranges: + gp3: ``3,000``(*default*)``- 80,000`` IOPS
             + io1: ``100`` - ``64,000`` IOPS ..."
```

숫자가 **사람이 읽는 문장 안에만** 있다. "gp3 볼륨의 최대 IOPS는?" 같은 실무 질문에
답하려면 이 문장에서 숫자를 꺼내야 하고, 그래서 정규식으로 산문을 긁는 경로
(`capacitykb/prose.py`, `evidence: cfn-description`)를 따로 만들었다.

당연히 이건 **깨지기 쉽다.** 그래서 두 겹으로 막았다:
- 신뢰도를 낮게(0.6~0.8) 주고, 판정에 쓸지를 임계선으로 거른다
- 틀리더라도 **느슨한 쪽으로만** 틀리게 한다(fail-open) — 잘못 막는 것보다 침묵이 낫다

실측상 이 경로로 나온 건 전체 46,810건 중 **158건(0.34%)** 뿐이다. 적지만, 하필 사람들이
가장 많이 묻는 값들이라 빼기 어렵다.

> ⚠️ 산문 추출은 실제로 사고를 냈다. `Iops`의 "operations per **second** (IOPS)"에서
> 단위를 `second`로 잘못 뽑는 등 3건이 확인됐다(감사 결함 (라)).

#### S3. Azure Bicep 타입 정의 → graphkb + capacitykb

**원본이 무엇인가**: Azure는 리소스 명세를 **타입 배열 하나**로 준다. AWS처럼 리소스마다
파일이 있는 게 아니라, 파일 하나에 온갖 타입이 평평하게 나열되고 서로를 **배열 인덱스로**
참조한다. `microsoft.compute` 2026-03-01 버전 파일을 열면 원소가 1,018개다:

```
$type 분포: StringLiteralType 534 · ObjectType 247 · UnionType 113 · ArrayType 94
            ResourceType 22 · IntegerType 4 · StringType 2 · BooleanType 1 · AnyType 1
```

`ResourceType`이 실제 리소스다:

```json
{ "$type": "ResourceType",
  "name": "Microsoft.Compute/availabilitySets@2026-03-01",
  "body": { "$ref": "#/3" },        ← 3번 원소(ObjectType)가 본문
  "readableScopes": 8, "writableScopes": 8 }
```

`#/3`은 "이 배열의 3번째 원소"라는 뜻이다. 그래서 파서는 **인덱스를 따라가며** 속성을
펼쳐야 한다(`graphkb/parsers/azure.py`, `capacitykb/parsers/azure.py`).

##### (가) 계층은 이름에 들어 있다 — `contained_in`

Azure 타입 이름은 `Microsoft.Compute/virtualMachines/extensions`처럼 **경로**다.
슬래시로 자르면 부모가 그대로 나온다:

```
Microsoft.Compute/virtualMachines/extensions
  → 부모: Microsoft.Compute/virtualMachines
```

이건 추론이 아니라 **ARM의 구조적 사실**이라 신뢰도 1.0(`evidence: arm-hierarchy`)이고,
Azure 그래프 엣지 2,306건 중 2,223건이 이것이다. AWS와 정반대다 — **AWS 그래프에는
`contained_in`이 0건**이고 전부 `references`다. 같은 지식베이스인데 프로바이더마다
표현 가능한 관계 종류가 다르다(감사 결함 G6).

##### (나) 참조는 이름 맞추기다 — `bicep-ref`

속성의 타입 이름이 리소스 타입 이름과 맞으면 참조로 본다(신뢰도 0.8).

> ⚠️ **이게 감사에서 오탐 12/59로 드러났다.** 예를 들어 가상머신의
> `properties.osProfile.linuxConfiguration.ssh.publicKeys`는 타입 이름이
> `sshPublicKeys`라 `Microsoft.Compute/sshPublicKeys` 리소스로 연결됐는데, 실제 그 객체의
> 속성은 `['keyData', 'path']`뿐이다 — **인라인으로 적어 넣는 공개키 자체**이지
> 별도 리소스에 대한 참조가 아니다.
>
> 판별법도 확인됐다: ARM에서 진짜 리소스 참조는 대상 객체에 반드시 `id` 속성이 있다.
> 그리고 이름 휴리스틱인데도 신뢰도가 0.8로, 같은 파서의 명시적 `heuristic`(0.6)보다
> 높다 — 근거 등급이 실제 추론 강도와 반대로 붙어 있다(감사 결함 G1).

##### (다) 제약은 비트 플래그에서 읽는다 (capacitykb)

각 속성에 `flags` 정수가 붙어 있고, 비트로 의미가 정해진다:

```
AvailabilitySetProperties 의 속성:
   statuses: flags=2 → 읽기 전용
   virtualMachineScaleSetMigrationInfo: flags=2 → 읽기 전용
```

```
flags & 1 → required        (반드시 채워야 함)
flags & 2 → read_only       (Azure가 채워주는 값)
flags & 8 → DeployTimeConstant  ← 불변성이 아니다. name/type/apiVersion에만 붙는다
```

8번 비트를 불변성으로 오해하면 안 된다는 것이 파서 주석에 박혀 있다.

> **Azure에는 "만들 때만 정할 수 있음"(create_only)에 해당하는 플래그가 아예 없다.**
> 그래서 Azure 제약 6,608건 중 `mutability`는 전부 `read_only`(4,704건)이고 `create_only`는
> **0건**이다. AKS의 `location`처럼 실제로는 바꾸면 재생성되는 속성이 있는데도
> "변경 불가로 알려진 속성이 없습니다"라고 답하게 되는 이유가 이것이다 — 데이터 부재가
> 사실 부재로 읽히는 문제(감사 결함 (나)-4).

#### S6. cb-tumblebug Swagger → graphkb (코어 레이어)

여기서는 프로바이더 중립 타입 13개를 만든다 — "AWS든 Azure든 상관없이 가상 네트워크라는

"model.TbVNetReq": {

#### S7. cb-tumblebug 자산 덤프 → costkb + perfkb

**원본이 무엇인가**: cb-tumblebug이 자기 데이터베이스를 통째로 백업해 저장소에 커밋해 둔
파일(`assets.dump.gz`, 34MB, PostgreSQL 백업 형식). 태그 `v0.12.25`로 고정.

그 안의 `spec_infos` 테이블에 인스턴스 스펙 73,083행이 있다. 한 행을 꺼내 보면 컬럼이 42개:

```
id             = 'aws+ap-east-1+t3.medium'
provider_name  = 'aws'
region_name    = 'ap-east-1'
csp_spec_name  = 't3.medium'
v_cpu          = '2'
memory_gi_b    = '4'
cost_per_hour  = '0.058400001376867294'
architecture   = 'x86_64'
infra_type     = 'node'
namespace      = 'system'
```

##### (가) costkb는 이 컬럼들을 그대로 투영한다

`id`·`vCPU`·`memGiB`·`hourlyUSD`… 계산이 거의 없다. **일부러 그렇게 했다** — 우리 에이전트의
라이브 경로인 cb-tumblebug MCP가 **같은 테이블을 읽기** 때문에, 우리가 "더 정확하게" 고치면
같은 질문에 두 경로가 다른 답을 낸다. 그래서 상위의 메모리 버그(GCP·Azure가 실제보다 2.4%
낮음)까지 그대로 복사하고, 보정값은 `memGiBActual`로 **따로** 병기한다(14절 참조).

예외는 센티널 처리다. `cost_per_hour`가 `0`이나 `-1`이면 "무료"가 아니라 **"가격 미상"**이라
`null`로 바꾼다 — Tumblebug의 정렬 SQL이 `CASE WHEN cost_per_hour > 0 ... ELSE 999999`로
뒤로 미는 것과 같은 취지다.

##### (나) perfkb는 costkb가 버린 `details` 컬럼을 읽는다

같은 행의 `details` 컬럼에 CSP 원본 응답이 들어 있다(1,670자):

```
[{"key":"AutoRecoverySupported","value":"true"},
 {"key":"BareMetal","value":"false"},
 {"key":"BurstablePerformanceSupported","value":"true"},
 {"key":"CurrentGeneration","value":"true"},
 {"key":"EbsInfo","value":"{EbsOptimizedInfo:{BaselineBandwidthInMbps:347,BaselineIops:2000,
                            BaselineThroughputInMBps:43.375,MaximumBandwidthInMbps:2085,
                            MaximumIops:11800,...}}"}, ...]
```

**바깥은 JSON인데 `value` 안쪽은 JSON이 아니다.** Go 언어의 `%v` 출력이라 따옴표가 없고,
값에 공백이 들어가고(`NetworkPerformance:Up to 5 Gigabit`), 중첩과 배열이 섞인다.
표준 JSON 파서로는 못 읽고, 범용 파서를 쓰면 `Up to 5 Gigabit`의 공백에서 깨진다.

그래서 **전체를 파싱하지 않는다.** 필요한 키만 정규식으로 뽑고 못 뽑으면 `None`을 준다
(`perfkb/parsers/details.py`). 뽑는 키를 7개로 유지하는 것 자체가 안전장치다.

정규식에는 **구분자 가드**가 필수였다. 키 앞에 `{`·`,`·`[` 중 하나를 요구하지 않으면
접미사가 같은 다른 키에 걸린다:

```
`Iops`를 찾으면          → MaximumIops:11800 에 걸림
`ThreadsPerCore`를 찾으면 → DefaultThreadsPerCore 에 걸림
```

여기서 뽑은 값이 성능 판정이 된다:
- `BurstablePerformanceSupported: true` → "상시 CPU 성능 **미보장**"(버스트 인스턴스)
  `evidence: aws-burstable-field`, 신뢰도 1.0 — AWS가 명시한 필드라서
- `CurrentGeneration: false` → "구세대"
- `EbsInfo` 안의 `BaselineBandwidthInMbps` → 지속 대역폭

> ⚠️ Azure는 이런 필드가 없어서 **스펙 이름이 `standardB`로 시작하는지**로 판정한다
> (`evidence: azure-family-name`, 신뢰도 0.8). 이름 추론이라 신뢰도를 낮춘 것인데,
> 34,846건에 붙는 이 하나의 상수가 판정 임계선(0.8)에 정확히 걸쳐 있다(§18-5).

#### S8. CB-Spider 드라이버 소스 → graphkb (매핑 레이어)

**원본이 무엇인가**: "AWS의 VPC와 Azure의 Virtual Network는 같은 것"이라는 번역 사전.
자동 추출이 아니라 **CB-Spider 드라이버 코드를 사람이 읽고 검수해** 만든 JSON이며,
저장소에 번들돼 있다(`graphkb/parsers/core_vendor_map.json`, 28건).

```json
{"core": "vNet", "provider": "aws", "target": "AWS::EC2::VPC", "confidence": 0.95,
 "note": "aws VPCHandler.go: ec2.CreateVpc (IGW/RouteTable 번들 생성 포함)",
 "status": "confirmed"}
```

`note`에 **근거가 되는 드라이버 파일과 함수**가 적혀 있다. 신뢰도가 낮은 항목은 그 이유도
함께 적혀 있다:

```json
{"core": "securityGroup", "provider": "gcp", "target": "ComputeFirewall", "confidence": 0.7,
 "note": "gcp SecurityHandler.go: Firewalls.Insert — 규칙별 방화벽 1:N 생성 +
          TargetTag 네트워크 태그 관례. 단일 리소스 동치가 아님"}

{"core": "nlb", "provider": "gcp", "target": "ComputeForwardingRule", "confidence": 0.7,
 "note": "gcp NLBHandler.go: ForwardingRules.Insert + TargetPools/HttpHealthChecks 번들
          (legacy target-pool 방식)"}
```

즉 GCP 방화벽은 AWS 보안그룹과 **엄밀히 같지 않다**(하나는 네트워크 단위 규칙, 하나는
인스턴스에 붙는 것). 그 사실이 신뢰도 0.7과 note로 기록돼 있다.

파이프라인은 반자동이다 — `suggest()`가 이름 유사도로 후보(`status: candidate`)를 만들면
사람이 검수해 `confirmed`로 바꾸고, 확정된 것만 그래프에 들어간다.

> **신뢰도 수치에 대한 정확한 진단**: 이 파일의 값들은 *이유가 없는* 게 아니다 — note에
> 근거가 적혀 있다. 문제는 **척도가 없다는 것**이다. 왜 0.7이고 0.65나 0.75가 아닌지,
> 0.95와 0.9를 가르는 규칙이 무엇인지가 어디에도 없다. 28개 엣지에 다섯 개 값
> (0.7/0.8/0.85/0.9/0.95)이 쓰이고 **0.85는 전 데이터셋에서 단 1건**이다. §18-5 참조.

| graphkb | `graphkb/model/schema.json` | `{nodes, edges}` | node: `id, layer, provider, kind, display_name, source`<br>edge: `from, to, type, via_property, required, cardinality, evidence, confidence` |
| capacitykb | `capacitykb/model/schema.json` | `{constraints, quotas}` | constraint: `type_id, property, kind, value, value_type, unit, conditional, note, evidence, confidence`<br>quota: `provider, name, scope, default, maximum, unit, type_id, source_doc, note, evidence, confidence` |
| costkb | `costkb/schema.json` | `{_note, specs}` | `id, provider, region, specName, vCPU, memGiB, memGiBActual, hourlyUSD, architecture, infraType, diskSizeGB, accelerator*` |
| perfkb | `perfkb/schema.json` | `{_note, specs}` | `id, provider, specName, sustainedCpu{value,note,evidence,confidence}, currentGeneration, clockGHz, networkPerformance, networkIsBurst, ebs*, acu, diskIops, maxPersistentDisk*` |

`id` 규약 — graphkb·capacitykb는 `{provider}::{타입명}`(예: `aws::AWS::EC2::Volume`),
costkb·perfkb는 Tumblebug 키 `{provider}+{region}+{spec}`. 앞의 둘이 조인 키를 공유하는 것이
두 KB를 코드 분리한 채로 엮는 방법이다.

### 18-5. 왜 신뢰도를 재설계하는가 (실측)

전 산출물에서 8개 값이 쓰인다: `0.5 / 0.6 / 0.7 / 0.8 / 0.85 / 0.9 / 0.95 / 1.0`.
**척도의 정의가 어디에도 없다.** 0.9와 0.95의 차이가 무엇인지, 두 근거를 결합하면
어떻게 되는지, 0.8이 "80% 확률"인지 "꽤 믿는다"인지가 기록돼 있지 않다.

한 가지는 분명히 해두자 — **개별 값에 이유가 없는 게 아니다.** S8에서 봤듯 매핑 신뢰도에는
`note`로 근거가 붙어 있고 내용도 타당하다. 문제는 그 산문 근거에서 **숫자가 유도되지
않는다**는 것이다. 그래서 재설계의 과제는 "근거를 만들어라"가 아니라 **"근거에서 등급이
함수적으로 나오게 하라"** 다.

실측으로 확인된 문제 셋:

1. **같은 evidence에 여러 confidence** — 라벨이 신뢰도의 함수가 아니다.
   `cfn-description`(0.6/0.7/0.8), `heuristic`(0.5/0.6), `kcc-ref`(0.9/1.0),
   `cb-spider-driver`(0.7/0.8/0.85/0.9/0.95 — 28개 엣지에 다섯 값, **0.85는 전체에서 1건**).
2. **작동하는 임계선은 하나뿐이고 하필 가장 붐비는 값에 놓였다.**
   `capacitykb/query.py`의 `CHECK_MIN_CONFIDENCE = 0.8`이 실제로 가르는 것은
   `cfn-description` 158건뿐이고, 그중 **115건이 정확히 0.8**이다. 상수를 0.81로 바꾸면
   115건이 판정에서 빠진다. perfkb의 `azure-family-name 0.8`은 **34,846건**에 붙는데
   역시 임계값에 정확히 걸쳐 있다.
3. **필요한 건 연속 척도가 아닐 가능성이 높다.** 코드가 이 값을 쓰는 곳은 최댓값 우선
   dedup과 단일 임계선 두 군데뿐이다.

**재설계 방향(초안)**: 연속값을 버리고 근거 종류에서 **함수적으로 유도되는 등급**으로 간다.
예: `declared`(상위가 명시) / `derived`(구조에서 유도) / `inferred`(이름·산문 추론).
등급이 evidence에서 결정되면 1번이 구조적으로 불가능해지고, 판정 여부를 등급으로 정하면
2번의 임계선 민감도가 사라진다. **등급 수·이름·판정 규칙은 재설계 시 근거와 함께 확정한다.**
