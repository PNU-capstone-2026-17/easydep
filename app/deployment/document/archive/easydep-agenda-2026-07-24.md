# easydep 팀 합의 안건 (2026-07-24)

agent-sdk 쪽에서 단독으로 결정할 수 없는 것만 모았습니다. 각 안건은
**배경(사실) → 선택지 → 우리 제안 → 누가 코드를 바꾸나** 순서입니다.
이 문서는 제안 시점의 스냅샷이며, 합의 결과는 각 저장소의 커밋이 기록합니다.

현재 상태 한 줄: easydep 삽입 자체는 완료되어 있습니다 — `RESOURCE_SPEC` 스키마
(`appkb/request.json`), 최종 PlantUML→계약 JSON 어댑터(`appkb/easydep.py`),
배포 다이어그램 노드 교체(`deployment_puml_from_easydep`), clarify 게이트 연동까지.
아래는 그 이후에 쌓인 것들입니다.

---

## 안건 1 — RESOURCE_SPEC 구조화가 신설 칸 3종을 알아야 한다

**배경.** 삽입 이후 agent-sdk 계약에 칸이 셋 늘었습니다. 전부 소비자(판정·대조)가
이미 구현되어 있어, easydep의 제약 구조화(resource_constraints_text → RESOURCE_SPEC)가
채워 주기만 하면 즉시 동작합니다.

| 칸 | 소비자 (agent-sdk에 구현됨) |
|---|---|
| `trafficPattern` (steady·spiky) | 버스트 인스턴스 상충 판정 — steady인데 버스트 스펙이면 "상충" |
| `stateless` (boolean, 주장으로 기록) | 서버리스 적합 판정 — false + 서버리스면 "상충 가능성" |
| `dataResidency` (사용자 표현 그대로) | 리전 원본 표시 이름 대조 + **판정 불가 명시** (국가 기계 판정은 안 함 — 소스 없음) |

**선택지.** (a) 구조화 프롬프트/파서에 3칸 추가 (b) 미채움 유지 — 계약상 전부
선택 칸이라 깨지진 않고, 그 판정들이 답에 안 실릴 뿐.

**제안.** (a). 특히 trafficPattern은 clarify 게이트 질문 하나로 얻을 수 있고
비용 판정의 질을 실제로 바꿉니다(데모 최저가 스펙이 버스트형이라 steady 앱에서
상충이 실제로 발생).

**변경 위치.** easydep 요구사항 분석(구조화 + clarify 질문 목록). agent-sdk는 변경 없음.

## 안건 2 — 모호 엔진의 해소 경로: archetypeHint를 누가 생산하나

**배경.** ER의 `engineHint`가 kafka류(큐·스트림·저장 중 어느 축인지 설계 의도에
달린 엔진)면 agent-sdk는 **일부러 분류하지 않고** 미결 + 패턴 자문으로 남깁니다.
해소 경로로 설계 계약에 `archetypeHint`(erArtifact, 설계자 지정 — hedge됨)를
열어 두었는데, easydep의 ERD 최종본(PlantUML)에는 이 정보를 실을 자리가 없어
**어댑터 경로에서는 항상 빕니다.**

**선택지.** (a) ERD PUML에 주석 규약(예: `' archetype: eventStream`)을 정하고
설계 에이전트가 생산, 어댑터가 파싱 (b) 별도 산출물/메타에 싣기 (c) 안 채움 —
모호 엔진은 미결로 남고 사용자가 직접 설계 JSON을 만질 때만 해소 가능.

**제안.** (a) — 최종본이 PlantUML이라는 현 구조(안건 4의 단기 방침)와 맞고,
주석이라 렌더링에 영향이 없습니다. 규약 문자열만 합의되면 어댑터 쪽 파싱은
agent-sdk가 구현합니다.

**변경 위치.** easydep 설계 에이전트(ERD 생성 시 주석) + agent-sdk 어댑터(파싱).

---

## 안건 3 — agent-sdk 의존 방식과 데이터 동반 배포

**배경.** 통합은 in-process import입니다(`deployment_puml_from_easydep`는 LLM 없는
결정론 함수). agent-sdk는 커밋된 산출물 `data/*.gz` 56개를 동반해야 클론 직후
동작합니다.

**결정할 것.**
- 의존 형태: 경로 의존(모노레포식) vs pip 패키지(버전 태깅 필요).
- **AWS 관리형 가격은 예외 사항**: 재배포가 명시적으로 금지된 소스라 저장소에
  없고(로컬 빌드 전용, `python -m costkb build-aws-managed`), easydep 운영 환경에서
  aws 관리형 과금 축을 원하면 **그쪽 배포 파이프라인에서 빌드를 실행**해야 합니다.
  실행하지 않으면 배포 답변이 그 사실과 빌드 명령을 안내합니다(기본 상태로 정상).

**제안.** 단기는 경로 의존(지금 방식), 릴리스 시점에 pip 전환. aws 빌드는 운영
정책 결정이라 easydep 쪽 판단에 맡깁니다.

**변경 위치.** easydep 배포 구성. agent-sdk는 변경 없음.

## 안건 4 — (기존 안건 재상정) 설계 산출물의 원본을 JSON으로

**배경.** 삽입 조사 때 상정된 안건 그대로입니다. easydep 최종본은 PlantUML이고
피드백이 PUML을 직접 수정하므로, 단기로 소비 시점 어댑터(A)를 택했고 그것이
지금 돌아갑니다. 장기 (B)는 설계 노드가 JSON을 원본으로 갖고 PlantUML을
렌더링으로 두는 것 — 어댑터의 componentId 합성 휴리스틱이 사라지고 안건 2도
자연 해소되지만, **설계 에이전트의 생성·피드백 루프를 바꾸는 일**입니다.

**제안.** 유지(단기 A) — 다만 안건 2를 (a)로 합의하면 (B)의 필요가 더 줄어드므로,
(B)는 어댑터 휴리스틱이 실측으로 문제를 일으킬 때 재상정.

**변경 위치.** (B)를 택할 경우 easydep 설계 에이전트 전반.

## 참고 (합의 불요 — 출력 변화 알림)

배포 다이어그램 노드의 출력이 삽입 시점보다 넓어졌습니다. PUML 주석의 근거·판정
블록에 다음이 추가로 실립니다: 진입점(로드밸런서, 노출 VM 앞)·수평 확장 단위
노트(대수는 미정 명시)·관리형 서비스 과금 축(azure 11종+LB·gcp 스토리지/이그레스,
합계 없음)·예산 판정의 "컴퓨트 각 1대 기준" 명시·레지던시 대조문. 형식(단일 PUML
문서, 주석은 렌더링에 안 나옴)은 그대로입니다.
