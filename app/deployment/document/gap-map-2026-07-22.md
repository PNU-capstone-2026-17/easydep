## 새 소스를 고를 때의 판정 기준

이 프로젝트가 소스를 받아들이는 조건입니다. 하나라도 못 지키면 안 씁니다.

1. **버전을 고정할 수 있는가** — 태그 · 커밋 SHA · (최후로) 받은 바이트의 sha256
2. **재배포 허가가 있는가** — 산출물을 저장소에 커밋하므로 라이선스가 실질 조건
3. **자격증명이 필요 없는가** — 필요하면 재현이 사람에 묶인다
4. **기계 판독인가** — 사람이 읽는 문서를 긁지 않는다
5. **조인 키가 있는가** — 인스턴스 타입명·리전명·리소스 타입 id로 우리 데이터에 붙는가
6. **우리가 이미 가진 것과 겹치지 않는가** — 겹치면 늘어나는 건 건수뿐이다
7. **답할 질문이 있는가** — 이게 마지막이자 가장 자주 놓치는 조건이다

**`azure-compute-docs`는 "SKU 단위"가 절반만 맞습니다.**


# 1번 채택 완료 — botocore `endpoints.json`

붙이면서 **설계가 조사와 달라진 곳이 셋**입니다. 전부 실측이 조사를 뒤집었습니다.

## (1) "리전별 서비스 가용성"을 담지 못했습니다 — **소재**만 담았습니다

조사는 이 소스가 가용성 축을 메운다고 했고 저도 그렇게 적었는데, 담으려고 보니
**"엔드포인트가 없다"에서 "그 리전에서 못 쓴다"를 끌어낼 수 없습니다.**

```
cloudfront   엔드포인트 1개 (us-east-1)
budgets      엔드포인트 1개 (us-east-1)
```

CloudFront가 us-east-1에서만 되는 게 아니라 **글로벌 서비스**라 하나인 겁니다.
판별자가 데이터에 있긴 한데(`isRegionalized`), 실측하니 **서비스 307개 중 22개에만**
있습니다. 위험군(엔드포인트 2개 이하) 34개 중 17개는 판별자가 없어
글로벌인지 진짜 리전 제한인지 **구분이 안 됩니다**(`cur`, `cost-optimization-hub` 등).

그래서 **있음만 담고 없음은 담지 않습니다.** 질의도 세 상태로 답합니다 —
있음 / 글로벌(원본이 밝힌 경우만) / 모름. "없음"이라는 답은 만들지 않습니다.

## (2) 서비스 이름을 짐작으로 붙이지 않습니다 (65%만 붙습니다)

CFN 네임스페이스 281개 중 그대로 148개, 하이픈을 지우면 34개 더해서 **182개(65%)**가
붙습니다(`acmpca` → `acm-pca`). 이 정규화는 **충돌이 0건**이라 안전합니다.

남는 99개는 철자가 아니라 **이름 자체가 다릅니다** — `cloudwatch`는 원본에서
`monitoring`, `cognito`는 `cognito-idp`, `certificatemanager`는 `acm`입니다. 규칙으로
못 맞힙니다. 손표를 만들 수도 있지만 틀리면 **엉뚱한 서비스의 리전을 자신 있게**
답하게 되므로, 못 붙는 건 못 붙는다고 답하고 비슷한 이름만 제안합니다.

## (3) 리전 판정을 제 정규식에 맡겼다가 진짜 리전을 버렸습니다

처음엔 `us-east-1` 꼴 정규식(`^[a-z]{2}(?:-[a-z]+)+-\d$`)으로 걸렀는데, 앞이 두
글자라고 짐작한 탓에 **`eusc-de-east-1`(유럽 주권 클라우드)을 버리고 있었습니다.**
반대로 원본의 `regions` 선언에는 `aws-global`·`fips-*` 같은 가짜 리전이 **한 건도**
섞여 있지 않았습니다(실측). **원본이 스스로 밝히는 목록이 제 규칙보다 정확했습니다.**

## 진짜 고친 것 — `서울`

실측에서 못 답했던 건 데이터가 없어서가 아니었습니다. `output/aws-regions.json`에
`ap-northeast-2`의 EC2 인스턴스 타입 **780개**가 그대로 있었고, 질문의 `서울`을
그 키로 바꾸는 길만 없었습니다. 이 프로젝트에서 반복해서 나온 실패 모양입니다 —
**데이터는 있는데 에이전트가 못 닿는다.**

한국어 별칭은 **리전 코드가 아니라 영어 낱말에 붙였습니다.**

```
"서울" → "Seoul" → (원본에서 찾기) → ap-northeast-2
```

`"서울": "ap-northeast-2"`가 짧지만 그러면 **리전 코드가 우리 표에 박혀** AWS가
리전을 늘릴 때 조용히 거짓이 됩니다. 낱말에 붙이면 코드는 늘 원본에서 오고
우리가 더하는 건 번역뿐입니다. `matched_by`로 원본이 말한 것(`code`·`name`)과
우리 번역(`alias`)을 구분해 돌려줍니다.

## 실측이 잡아낸, 제가 만든 결함

프로브 R1("서울 리전에서 쓸 수 있는 GPU 인스턴스")을 3번 돌려 1번만 끝까지 갔습니다.

# 2번 채택 완료 — azure-rest-api-specs 미사용 축 (secret)

조사는 이 소스가 **세 축**(secret · long-running · identifiers)을 준다고 했습니다.
붙이기 전에 각 축을 실측해 **판정 기준 6·7번**(겹침·답할 질문)으로 걸렀더니,
셋을 다 담는 게 아니라 **하나만** 담는 게 맞았습니다.

## 축별 판정 — 무비판적으로 다 담지 않았습니다

| 축 | 실측 | 판정 |
|---|---|---|
| **x-ms-secret** | PUT 본문·조인되는 것 288건/106종. 우리 kind에 secret **없음**(겹침 0) | **담음** |
| x-ms-long-running-operation | PUT의 58%가 LRO. 변별력은 있으나 **속성이 아니라 작업 단위** | 보류 |
| x-ms-identifiers | 빈 배열 2,343건, 대부분 `name`. 배열 병합 키라 앱 개발과 거리 멂 | **안 담음** |

- **secret**은 답할 질문이 명확합니다 — "이 값 나중에 확인 가능?" → 비밀값이라
  못 읽음. `password`·`adminPassword`·`connectionString`·`clientSecret`이 상위입니다.
- **LRO**는 58:42로 변별력이 있어 버리기 아깝지만, `Constraint`(속성 단위) 모델에
  안 맞습니다("이 **작업**이 오래 걸린다"). 별도 모델이 필요하니 다음 라운드입니다.
- **identifiers**는 대부분 빈 배열이거나 `name`이라, 배열을 어떻게 병합하는지에 관한
  것이지 리소스 특성이 아닙니다. 앱 개발 가이드라인에 쓸 질문이 없어 뺐습니다.

## secret은 mutability와 **직교**합니다 — 그래서 겹침이 아닙니다

같은 tarball의 `x-ms-mutability`는 이미 쓰고 있었지만 축이 다릅니다.

```
Microsoft.App/.../certificates.properties.password:
  - 생성 후 변경 불가 (x-ms-mutability = create_only)   ← 바꾸면 재생성되나
  - 비밀값 (x-ms-secret = true)                          ← 읽을 수 있나
```

`administratorLoginPassword`는 비밀이면서 보통 **변경 가능**입니다. 두 축이 직교하므로
같은 속성에 둘 다 붙어도 중복이 아니라 **서로 보완**합니다. 실측에서 확인했습니다.

## "없음"의 뜻을 프로바이더별로 좁힙니다

이 표시는 **Azure만** 줍니다. AWS·GCP 타입에 대고 "비밀값 없음"이라고 하면
없는 걸 확인해 준 것처럼 읽힙니다. 그래서 `cap_secret_properties`는 세 가지를
구분합니다 — 있음 / (Azure인데) 없음 / (다른 프로바이더라) **추적 안 함**.

## 실측

```

→ 비밀 속성 230건 (106종 · stable 최신 1,422개 중 141개 파일에서)

   Azure REST 스키마에서 비밀값으로 정의됨. Key Vault에 보관 권장" (통과)
```

근거를 우리 KB에 정확히 귀속시켰습니다("Azure REST 스키마에서 정의돼 있기 때문").

## (나) 4번 — 탄소, 완전히 새로운 축

`gap-map`의 "아예 없는 축"에서 **0건**이던 것이 채워졌습니다.

| 소스 | 무엇 | 라이선스 | 조인 |
|---|---|---|---|

CCF는 **파일 셋을 함께** 읽어야 합니다 — 계수 표가 NERC 상수를 참조하기 때문입니다

### 핵심 — 두 방법론을 섞으면 안 됩니다

```
서울   aws 477.4 · gcp 356.6 · azure 415.6    ← gcp가 최저
도쿄   aws 439.8 · gcp 452.9 · azure 465.8    ← aws가 최저
```

**같은 도시·같은 전력망인데 값이 다르고 순서까지 뒤집힙니다.** 실제 차이가 아니라
GCP는 자체 발표, CCF는 공개 그리드 추정이기 때문입니다. 그래서 이 축은
**프로바이더 안에서만 비교**합니다 — perfkb가 "프로바이더 간 성능 비교 불가"라고
답하는 것과 같은 이유이고, 같은 원칙을 일관되게 적용했습니다.

실측에서 이게 지켜지는지 확인했습니다(프로브 C2, "AWS 서울 vs GCP 서울"):

> 두 값은 각각 다른 방법론으로 산출되었습니다. AWS·Azure는 공개 그리드 데이터
> 기반 **추정치**이며, GCP는 Google이 직접 발표한 값입니다. 따라서 직접적인
> "어느 쪽이 더 적다"는 비교는 권장되지 않습니다.

값을 감추지 않고 둘 다 보여주면서 비교만 막는 것이 맞는 답입니다.

# 7번 채택 완료 — alicloud·tencent (새 프로바이더를 열다)

앞의 여섯 소스는 **있는 축에 데이터를 더했지만** 이건 대상 자체가 없었습니다.

```
빌드 전  graphkb 노드: aws 1,647 · azure 3,567 · gcp 536 · alibaba 0 · tencent 0

tencent : 제약 11,222건 · 타입 1,302종 (등록 1,334종 중 97.6% 파싱)
```

costkb·perfkb엔 두 CSP의 **스펙과 가격이** 있었는데(alibaba 2,494 · tencent 2,865)
리소스 제약은 0건이었습니다. 그 비대칭이 해소됐습니다.

## 타입 이름이 Terraform 것이라는 사실을 id에 남깁니다

    alibaba::alicloud_instance      tencent::tencentcloud_instance

다른 프로바이더는 벤더 공식 이름을 씁니다(`AWS::EC2::Subnet`). 이 둘은 쓸 수 있는
공개 스키마가 없어 Terraform 이름을 씁니다. **id에 `alicloud_`가 보이는 것이
의도입니다** — 나중에 공식 스키마가 생겼을 때 무엇을 바꿔야 하는지 드러나야 합니다.

## 함정 셋 (전부 실측으로 겪음)

**(1) 두 저장소의 등록 표기가 다릅니다.**

```
alicloud  "alicloud_vpc":    resourceAliCloudVpc()          ← 함수 그대로
tencent   "tencentcloud_vpc": vpc.ResourceTencentCloudVpc()  ← 패키지 접두사
```

점을 허용 안 하면 **tencent가 0건**이 됩니다. 실제로 그 상태로 한 번 빌드했습니다.

**(2) 데이터소스를 걸러야 합니다.** 안 거르면 등록이 1,875종으로 부풀고 조회 전용
스키마가 제약으로 들어갑니다. 거르니 1,134종으로 정확해졌습니다.

**(3) 파일 × 함수로 돌면 10분을 넘깁니다.** 1,879 파일 × 1,161 함수 = 218만 번
정규식 검색입니다. 파일에서 리소스 함수를 먼저 뽑고 등록표와 교집합을 취해
파일 수만큼만 돌게 고쳤습니다.

## 대조할 짝이 없는 단일 소스입니다

`tpaws`는 CFN이, `tpg`는 KCC가 독립 소스로 있어 어긋남을 셀 수 있었습니다.
**여기는 없습니다.** `ForceNew`·`validation.*`은 프로바이더 작성자의 주장이고

## graphkb 노드를 이 파서가 함께 만듭니다

`kbcommon verify`의 capacity-joins-graph는 모든 제약이 graphkb 노드로 이어지길
요구합니다. aws·azure·gcp는 그래프 파서가 따로 있지만 이 둘은 **타입 목록의 출처가
이 파서뿐**이라, 함께 만들지 않으면 조인이 깨집니다(처음 빌드에서 1,590건 전부 실패).
**엣지는 만들지 않습니다** — 참조 관계를 짐작으로 이으면 없는 의존성이 생깁니다.

번들 테스트도 결함을 하나 잡았습니다: 커밋되는 산출물은 출처를 담아야 하는데
graph 노드 파일에 빠뜨렸고, `test_bundled_artifacts.py`가 잡았습니다.

```
/providers/Microsoft.Compute/virtualMachines/{vm}/start
                                                  ^^^^^ 액션이지 타입이 아니다
```

안 떼면 타입/이름 교대 규칙상 액션이 타입 자리에 들어가
`Microsoft.Compute/locations/virtualMachinesBulkCancel` 같은 **없는 타입**이 나옵니다.
실제로 그 상태를 먼저 만들었고, 고친 뒤 `virtualMachines`의 `deallocate`·`generalize`가
제자리를 찾았습니다.

**(2) 모순은 담지 않습니다.** 같은 타입·메서드를 파일마다 다르게 말하는 것이 15건
있습니다. `aws_limits`의 "두 소스가 어긋나면 담지 않고 보고" 원칙을 그대로 적용했습니다.

**"원본이 말 안 함"과 "즉시"를 구분합니다.** 섞으면 타임아웃을 짧게 잡게 됩니다.

# cb-spider 흡수 — 12개 CSP로

**왜 중요한가.** 우리 실행 경로는 cb-tumblebug이고 그 하부가 cb-spider입니다.
그래서 **cb-spider 드라이버에 없는 것은 실제로 만들 수 없습니다.** "KT Cloud에서
쿠버네티스 클러스터 만들어줘"에 "됩니다"라고 답하면 데이터가 아니라 **실행이 실패**합니다.

지금까지 우리는 CSP를 다섯만 알았습니다. cb-spider는 **열둘**을 다룹니다.

```
python -m kbcommon build-cbspider
→ CSP 12곳 · 지원 111 · 핸들러 없음 9 · 스텁 0

VPC·Security·KeyPair·VM·Disk·MyImage   12/12  전부
NLB                                    11/12  oracle 없음
Cluster(k8s)                            8/12  kt·ktclassic·openstack·oracle 없음
```

## 함정 셋 — 전부 실측·테스트가 잡았습니다

**(1) 메서드 이름이 핸들러마다 다릅니다.** cb-spider는 VM 생성을 `StartVM`,
이미지를 `SnapshotVM`이라 부릅니다. `Create`로만 찾으면 **그 둘이 전부 미구현으로**
잡힙니다 — 처음에 그 상태를 만들었고, 인터페이스 정의를 직접 읽어 고쳤습니다.

**(2) "파일이 있다"와 "구현됐다"는 다릅니다.** 처음엔 본문 길이(<600자)로 스텁을
갈랐는데 **테스트가 그 취약함을 잡았습니다** — 짧지만 실제 구현된 본문을 스텁으로
판정했습니다. 길이는 우연이고, 스텁의 정의는 **"조건 없이 바로 미지원을 돌려주는
것"**입니다. 그렇게 고치니 정확해졌습니다.

**(3) 과잉 판정도 오답입니다.** 긴 본문 속 "not supported"는 일부 기능 제한일 수
있습니다(NLB가 UDP 헬스체크만 거부하는 식). 그걸 스텁으로 보면 **되는 것을 안 된다고**
답하게 됩니다. 첫 실행문 판정이 이것도 함께 해결했습니다.

곁가지로 `_method_body`가 시그니처 잔여물부터 자르던 버그도 테스트가 잡았습니다.

## "CSP에 기능이 없다"와 "드라이버가 없다"를 구분합니다

이게 이 축의 핵심 계약입니다. 실측(프로브 K1)에서 에이전트가 그대로 전달합니다:

> KT Cloud에서는 쿠버네티스 클러스터를 생성할 수 있는 **드라이버가 제공되지
> 않습니다.** 이는 해당 기능이 **CSP 자체에 없다는 것이 아니라**, 우리 시스템에서
> 이를 지원하는 cb-spider 드라이버가 아직 구현되지 않았기 때문입니다.

## 남은 것 — 일곱 CSP의 타입 이름

`core::vNet` ↔ 벤더 타입 매핑은 여전히 다섯 CSP뿐입니다. 나머지 일곱
(ibm·kt·ktclassic·ncp·nhn·openstack·oracle)은 **"만들 수 있다"까지는 알지만
"그게 무슨 타입인가"는 모릅니다.** 타입 이름의 출처가 필요한데:

- TF provider가 있는 것: ibm(`terraform-provider-ibm`) · ncp(`ncloud`) ·
  openstack · oracle(`oci`) → alibaba·tencent와 같은 방식으로 열 수 있습니다
- kt·ktclassic·nhn → 공개 provider를 아직 못 찾았습니다

지금 열린 것은 **"어느 CSP가 무엇을 만들 수 있나"**까지이고, 그것만으로도
"KT에서 k8s 되나"에는 정확히 답합니다.

```
core::vm                  반드시 먼저 있어야 하는 것 **7개**
```

## 원인 — 둘 다 사실이고 근거가 다릅니다

| | 근거 | 무엇을 말하나 |
|---|---|---|
| `core::vm` | **cb-tumblebug REST 스키마**(`swagger-field`) | `vNetId`·`subnetId`·`securityGroupIds`가 **required 필드** |
| `AWS::EC2::Instance` | **CFN/CDK**(`cdk-oob`) | `SubnetId`는 **선택** (기본 VPC를 쓸 수 있으니까) |

CloudFormation으로 만들면 서브넷 없이도 됩니다. **하지만 우리가 실제로 배포하는
길은 cb-tumblebug**이고, 그 요청은 저 값들을 채워야 성립합니다. 벤더 스키마만 보고

```
subnet                1        5/8

```

## 해결 — 감추지 않고 나란히 놓습니다

어느 한쪽을 고르면 그건 **우리가 정한 것**이 되고, 실제로는 무엇으로 만드느냐에
달렸습니다. 그래서 벤더 타입을 물으면 대응 코어 타입의 요구사항을 함께 밝힙니다:

```
※ **실행 경로에서는 더 필요합니다.** 위 목록은 이 CSP의 IaC 스키마
  (CloudFormation·ARM 등) 기준입니다. 우리가 실제로 배포하는 길인 cb-tumblebug은
  같은 리소스를 만들 때 **7가지를 필수로 요구**합니다:
  image, mci, securityGroup, spec, sshKey, subnet, vNet.
  둘 다 사실이며 근거가 다릅니다 — 스키마는 '없어도 API가 받는다',
  실행 경로는 '이 값을 채워야 요청이 성립한다'입니다.
```

대응 코어 타입이 없는 벤더 타입(`S3::BucketPolicy` 등)에는 아무것도 덧붙이지
않습니다 — 없는 요구사항을 만들어내지 않습니다.

# 관점 정정 — 우리는 배포기가 아니라 가이드라인 KB다

> "우리는 배포기를 만드는 게 아니라 가이드라인의 kb를 만드는 게 목적이다.
> 그런 관점과 충돌하는 부분은 고치고, 훑어보자."

바로 앞의 두 작업(cb-spider 흡수, core↔벤더 불일치)에 **배포기 관점**이 섞여
있었습니다. 훑어서 고쳤습니다.

## (1) core 필수 목록을 그대로 옮기면 **거짓말이 됩니다**

불일치를 고치면서 "cb-tumblebug이 7가지를 필수로 요구합니다"라고 적었는데,
그 7가지에는 **성격이 다른 셋**이 섞여 있었습니다:

```
만드는 리소스    vNet · subnet · securityGroup · sshKey
고르는 카탈로그   spec · image      ← 만드는 게 아니라 선택하는 값
도구 고유 개념    mci               ← cb-tumblebug의 묶음 단위
```

**"EC2를 만들려면 mci가 필요하다"는 가이드라인으로서 거짓입니다** — AWS에 그런
것은 없습니다. 특정 도구의 요구사항을 클라우드의 사실인 양 말한 것입니다.

다행히 판정 근거가 이미 데이터에 있었습니다. `core_vendor_map`이 **spec·image·mci는
등가물이 없다**고 명시하므로, **벤더 대응물이 있는 코어 타입만** 옮기면 셋이 자동으로
걸러집니다. 손으로 목록을 또 만들 필요가 없었습니다.

```
전 ※ 우리가 실제로 배포하는 길인 cb-tumblebug은 7가지를 필수로 요구합니다:
     image, mci, securityGroup, spec, sshKey, subnet, vNet
후 ※ 스키마는 선택으로 두지만 실무에서는 보통 필요합니다:
     securityGroup, sshKey, subnet, vNet
```

## (2) cb-spider는 **도구의 커버리지**이지 클라우드의 사실이 아닙니다

"KT Cloud에서 k8s 클러스터 만들 수 있어?"에 **"만들 수 없습니다"**라고 답하고
있었습니다. 이건 배포기의 답입니다. 가이드라인 KB로서 정확한 답은
**"KT Cloud에 그 서비스가 있는지는 이 데이터가 답하지 않는다. 다만 이 멀티클라우드
도구로는 다루지 못한다"**입니다.

실측에서 답이 바뀐 것이 분명합니다:

```
전 KT Cloud에서는 쿠버네티스 클러스터를 생성할 수 있는 드라이버가 제공되지
   않습니다. … 현재 상태로는 KT Cloud에서 직접 쿠버네티스 클러스터를 만들 수
   없습니다.

후 네, KT Cloud에서도 쿠버네티스 클러스터를 만들 수 있습니다. 다만 현재 제가
   접근할 수 있는 멀티클라우드 도구(cb-spider)에서는 KT Cloud의 쿠버네티스
   클러스터 리소스를 직접 다루는 지원이 구현되어 있지 않다는 점을 알려드립니다.
```

## 이 축의 값어치는 그대로입니다

도구 커버리지도 가이드라인에 쓸모 있는 지식입니다 — **"멀티클라우드로 한 방식으로
관리하려면 어디까지 되나"**는 실제 설계 결정에 들어갑니다. 바꾼 것은 그것을
**클라우드의 사실로 옮겨 말하지 않는 것**뿐입니다.

# 훑기 2 — costkb의 미러 원칙

## 가장 큰 충돌: 버그값으로 필터링하고 있었습니다

미러(cb-tumblebug 덤프)에는 상위 CB-Spider 버그가 실려 있어 GCP·Azure 메모리가
실제보다 2.4% 낮습니다. 우리는 그 값을 **표시할 때는 보정**했지만
**필터링할 때는 버그값을 썼습니다.**

```
스펙 73,083건 중 보정값이 다른 것  46,468건 (64% — azure 34,846 + gcp 11,622)

"메모리 N GiB 이상" 필터에서 실제로는 만족하는데 빠지던 스펙:
   4 GiB → 1,037건    16 GiB → 3,765건    64 GiB → 4,611건
```

근거는 *"라이브 MCP가 같은 컬럼으로 필터링하므로 두 경로의 답이 갈리면 안 된다"*
였습니다. **배포기의 이유입니다.** 가이드라인 KB로서 사용자가 "16GiB 이상"이라고
하면 실제로 16GiB인 것이 나와야 합니다 — Azure `Standard_M832is_16_v3`가 실제
15,200 GiB인데 미러엔 14,843으로 적혀 있다고 빼는 건 그냥 틀린 답입니다.

**원본을 고치지 않습니다.** `memGiB`에 상류가 뭐라고 적었는지 그대로 남습니다.
바뀐 것은 **무엇을 근거로 판단하느냐**입니다(`dataset.actual_memory`).

## 근거 문구도 고쳤습니다

`costkb/invariants.py`가 "미러라서 전부 `report`"라고 적고 있었습니다. 동작은
맞지만 이유가 배포기 관점입니다. **원본을 고쳐 쓰면 무엇이 원본이었는지 잃기
때문**으로 바꿨고, "원본 보존"이 "그 값으로 판단"과 같은 말이 아님을 명시했습니다.

## perfkb는 문제가 없었습니다

오히려 더 엄격합니다 — *"성능 KB에서는 과대 진술이 과소 진술보다 해롭다"*는
원칙으로 가속기 모순을 `error`(쓰기 거부)로 둡니다. 가이드라인 관점과 일치합니다.

## 남은 관점 충돌 없음

`DEFAULT_ARCHITECTURE = "x86_64"`도 MCP를 따른 것이지만, 이건 **기본값 선택**이라
사용자가 `architecture=None`으로 전체를 볼 수 있고 문서에도 밝혀져 있습니다.
답을 조용히 틀리게 만들지 않으므로 그대로 둡니다.

# 값을 고쳐서 담는다 — `memGiBActual` 제거

> "memGiB를 맞게 고치고, memGiBActual은 없애자. 그냥 메타데이터로 고쳐진거라고
> 적어만 둬."

앞 단계에서 **판단만** 보정값으로 바꿨는데, 값이 여전히 두 칸에 나뉘어 있었습니다.
사용자 결정대로 **값 자체를 고치고 칸을 하나로** 만들었습니다.

```
전  memGiB = 62.5(원본, 버그)   memGiBActual = 64.0(보정)
후  memGiB = 64.0(실제 값)      _corrections = [보정 규칙]
```

**왜 이게 더 낫나.** 칸이 둘이면 **표시·필터·정렬이 서로 다른 칸을 볼 수 있습니다** —
실제로 그렇게 갈려서 "16 GiB 이상"에서 3,765건이 조용히 빠졌습니다. 칸이 하나면
그런 어긋남 자체가 생길 수 없습니다.

## 보정 사실은 메타데이터에 규칙으로

값마다 칸을 늘리는 대신 **무엇을 어떻게 고쳤는지 한 곳에** 적습니다:

```json
"_corrections": [{
  "field": "memGiB", "providers": ["azure", "gcp"], "operation": "×1.024",
  "reason": "상위 CB-Spider의 ConvertMBToMiBInt64가 … 원본으로 되돌리려면
             이 값을 1.024로 나눈다."
}]
```

**이 식이 곧 원본 복원식입니다** — 원본이 필요한 사람은 되돌릴 수 있습니다.

## 실측 결과

```
gcp  n2-highmem-8      62.5      → 64.0
azure M832is_16_v3   14,843.75  → 15,200.0
memGiBActual이 남은 레코드: 0건
```

## 함정 하나를 스스로 만들고 잡았습니다

감사 통계(상위 버그 지문 감시)를 원본값으로 계산하도록 옮기면서 컬럼명을
`memory_gi_b` 대신 `mem_gib`로 잘못 적었습니다. 그러자 전부 0이 되어
**"정수 100% · bug 0%"라는 무해해 보이는 거짓 통계**가 나왔습니다.

감사가 조용히 죽으면 **새 프로바이더가 버그 영향권에 들어와도 못 잡습니다.**
고친 뒤 azure 64.2% · gcp 77.6%로 원래 수치가 돌아왔습니다.

## 스키마가 낡은 산출물을 막습니다

`memGiBActual`은 스키마에서 빠졌으므로 옛 산출물은 검증에 걸립니다 — 실제로
perfkb 테스트 픽스처가 그 필드를 갖고 있다가 번들로 폴백해 실패했고, 그게
스키마가 제 일을 한다는 증거였습니다. 그 동작을 테스트로 고정했습니다.

# 확인된 데이터 결함 수정 — 산문에서 뽑은 단위

`decisions.md` §7과 `kb-book.md` §14에 함께 열려 있던 항목입니다. **데이터가 실제로
틀린 답을 내고 있었습니다.**

```
BacktrackWindow  259200  → hours    실제 seconds   ← 3,600배
Iops               1000  → second   실제 IOPS
MaximumLength  20971520  → MB       실제 characters
```

첫 번째는 값 자체로도 말이 안 됩니다 — **259,200시간은 29.6년**입니다.
`cap_check_value`는 `"500 second는 최소 1000 second를 벗어남"`이라 답하고 있었습니다.

## 원인

`_unit_of(block)`이 매칭된 **좁은 블록의 첫 단위 토큰**을 그냥 돌려줬습니다.

```
원문   "The target backtrack window, in seconds. … from 0 to 259,200 (72 hours)."
블록                                              "from 0 to 259,200 (72 hours)"
                                                                      ^^^^^ 첫 단위
```

전체 원문의 `in seconds`가 정답인데, **괄호 안 환산 표기**를 집었습니다.

## 해결 — 순서를 세우고, 확신 없으면 담지 않는다

1. **속성 이름** — `TimeoutInMillis`·`IntervalSeconds`·`Iops`. 산문은 한 문단에
   단위를 여럿 섞지만 **이름은 하나뿐**이라 가장 강한 근거입니다.
2. **`in X` 선언** — 원문이 "in seconds"라고 못 박은 것. 괄호 환산 표기는 지웁니다.
3. **블록의 단위** — 위 둘이 없을 때만. 서로 다른 단위가 섞여 있으면 **비웁니다.**

`characters`처럼 우리 단위 목록에 없는 것은 **단위 없이** 담습니다 —
`20971520 MB`는 확신에 찬 오답이지만 빈 칸은 "모른다"입니다.

## 결과

```
전  단위 레코드 34건 (3건 틀림)
후  단위 레코드 32건 (전수 확인, 틀린 것 없음)
```

`MaximumLength` 2건이 단위 없이 담기며 줄었습니다. 사용자에게 보이는 답:

```
전  500 second는 최소 1000 second을(를) 벗어남 · 최대 259200 hours
후  500 IOPS는 최소 1000 IOPS을(를) 벗어남   · 최대 259200 seconds
```

## 고치다 만든 함정 — 보이지 않는 백스페이스

정규식을 셸 heredoc으로 쓰다가 `\b`(단어 경계)가 **리터럴 백스페이스
`\x08`**로 들어갔습니다. 화면·`grep`·에디터 어디에도 안 보이는데 정규식만 조용히
안 맞았습니다. `repr()`로 패턴을 찍고서야 드러났습니다.

**교훈**: 정규식이 든 코드는 셸 heredoc으로 쓰지 말 것. 파일로 저장해 실행하면
셸 이스케이프를 거치지 않습니다.

# 두 번째 오류 — 그래프 축이 근거를 안 내보냈다

용량 축은 5개 도구 전부 근거를 내는데 그래프 축은 **6개 중 3개가 버리고**
있었습니다(`equivalent_types`·`creation_order`·`deletion_impact`).

실측에서 드러난 형태입니다 — "AWS ALB는 GCP에서 뭐야?"에 모델이
`ComputeForwardingRule`을 **단언**했습니다. 데이터의 `basis`는 `짐작(검수됨)`인데
**출력에 안 실려서 모델이 알 방법이 없었습니다.**

## 동치는 코어를 거쳐 이어진다 — 근거는 가장 약한 고리

```
aws VPC → core vNet → gcp ComputeNetwork
```

두 벤더 타입 사이에는 **직접 엣지가 없습니다.** 경로의 근거가 곧 그 쌍의 근거이고,
**여러 고리 중 하나라도 짐작이면 결과도 짐작**입니다 — 사슬은 약한 곳에서 끊어집니다.

## 개수에 따라 표시 방식을 나눴습니다

| 도구 | 방식 | 왜 |
|---|---|---|
| `equivalent_types` | **줄마다** 근거 | 9건 안팎이라 다 보여도 된다 |
| `deletion_impact` | **블록당 한 번** 집계 | 466건에 줄마다 붙이면 노이즈가 되고, 노이즈가 되면 진짜 경고가 안 보인다 |
| `creation_order` | 블록당 한 번 | 같은 이유 |

## "검수됨"이 "명시"는 아닙니다

경고 조건을 `is_fact`로 뒀더니 **경고가 아예 안 붙었습니다.** 이름 추론 엣지
1,113건이 전부 `reviewed=True`이기 때문입니다(검수 파일이 `{"evidence":"heuristic"}`
한 줄로 근거 단위 확인을 적어 둠).

그 검수는 정직합니다 — 방법을 셋으로 나눠 적고 **"※ (3)은 표본 판단이므로 전수
개별 확인은 아니다"**까지 밝혀 뒀습니다. 하지만 **검수됐어도 짐작은 짐작**입니다.
특히 클라우드 간 동치는 사람이 "가장 가깝다"고 판단한 것이지 원본이 선언한 관계가
아닙니다. 그래서 경고 조건을 `basis != "stated"`로 바꿨습니다.

> 제가 중간에 "`reviewed`가 의미를 잃었다"고 판단했는데 **틀렸습니다.** 검수
> 근거와 표본 한계가 파일에 문서화돼 있습니다. 바꾼 것은 플래그의 뜻이 아니라
> **경고를 언제 띄우느냐**입니다.

## 실측

```
전  GCP 대응 서비스는 ComputeForwardingRule입니다.        (단언)
후  ALB에 가장 가까운 GCP 리소스는 Compute Forwarding Rule입니다.  (2/2)
```

`deletion_impact`도 이제 밝힙니다:

```
※ 이 관계들의 근거: AWS CDK 참조 정의 709건(원본에 명시됨),
   이름 규칙 추정 352건(짐작(검수됨)), 스키마의 관계 선언 53건(원본에 명시됨)
※ 그중 352건(32%)이 이름 추론에서 나온 것입니다. 사람이 확인했지만 원본이
   관계를 선언한 것은 아니므로, 삭제 계획에 쓸 때는 실제 참조를 함께 확인하세요.
```

# `cost_describe_spec` — 데이터는 있었고 표면이 없었다

`decisions.md` §7의 미결이었습니다. **"n2-highmem-8 메모리 몇 GiB?"에 답할 도구가
없어** 실측에서 **0/3 실패**하고 web_search로 3/3 샜습니다(도구 호출 11회까지).

`cost_recommend_specs`는 **조건 필터**이지 이름 조회가 아니고,
`perf_instance_profile`은 성능만 줍니다. 카탈로그 73,083건을 쥐고도
**이름으로 하나 꺼내는 길**이 없었습니다.

## 설계에서 정한 것 셋

**(1) 가격은 범위로 준다.** 리전마다 단가가 달라서 하나만 고르면 그게 대표값인 양
읽힙니다 — `n2-highmem-8`은 40개 리전에서 **$0.5241 ~ $0.8385**입니다.

**(2) 이름이 겹치면 둘 다 보여준다.** 실측상 5,248종 중 겹치는 것은 `m1.*` 4종
(aws·openstack)뿐입니다. 메모리가 1.7 vs 2.0 GiB로 **다르다는 것 자체가 정보**라
하나를 고르지 않습니다.

**(3) 없으면 비슷한 이름을 제안한다.** "그런 스펙이 없다"가 아니라 **"이 데이터셋에
없다"**로 답하고 후보를 댑니다 — 오타를 막다른 길로 만들지 않습니다.

## 성능 축으로 이어 붙였습니다

카탈로그 답만 주면 "이게 버스트인가", "구세대인가"를 모른 채 고르게 됩니다.
도구 계층에서 조인합니다(KB끼리 import하지 않는 규약):

```
t3.medium      → ⚠ 버스트 인스턴스 — CPU 크레딧이 소진되면 baseline으로 떨어집니다.
n2-highmem-8   → ※ 성능 특성은 perf_instance_profile('gcp','n2-highmem-8') 로 보세요.
```

## 실측

```
전  0/3 실패 · web_search 3/3 · 도구 호출 11회
후  ✓ 도구 1회 (6.4초)
    "GCP 인스턴스 n2-highmem-8의 메모리 용량은 64 GiB입니다."
```

> 곁가지: `decisions.md`는 이 항목의 값어치를 "**설계의 핵심인 62.5/64 미러 이야기가
> 한 번도 노출되지 않았다**"로 적었는데, 그 이야기는 이제 없습니다 — 앞 단계에서
> `memGiB`를 실제 값으로 고쳤기 때문입니다. 답은 그냥 **64 GiB**입니다.

# 필드 목록이 세 벌이었다 — `perfkb/fields.py`

`decisions.md` §7의 "`_COMPARE_AXES` 선정 기준과 도구 간 상충"입니다. 실측하니

```
perf_compare(aws, [m5.large, c6a.large])   세대 이야기 한 줄도 없음
recommend_note(aws, m5.large)              "구세대 인스턴스입니다"
```

## 더 큰 손실 (기록에 없던 것)

기록은 "GCP 프로파일 질의가 빈 답"이라 적었는데, 재현해 보니 빈 답은 아니고 **한 줄**

빠져 있었습니다.

| | 고치기 전 | 후 | 빠져 있던 100% 칸 |
|---|---|---|---|
| aws m5.large | 12줄 | 16줄 | 코어당 스레드, 베어메탈, EBS IOPS 2종 |
| azure Standard_D2s_v5 | 3줄 | 8줄 | 캐시 디스크 IOPS, 가속 네트워킹, 프리미엄 IO, 계열 |
| gcp n2-highmem-8 | 3줄 | 6줄 | 최대 영구 디스크 수·용량, 벤더 설명 |

그리고 **사람이 보는 것과 에이전트가 보는 것이 달랐습니다** — CLI는 `vendorDescription`을
출력하는데 에이전트용 `_describe`는 안 했습니다.

## 원인은 하나

같은 목록이 **세 군데**에 있었습니다: `agent_api._describe` · `agent_api._COMPARE_AXES` ·
`cli._describe`. 셋이 따로 자랐습니다. 그래서 개별 패치가 아니라 **선언을 한 곳으로**
모았습니다 — `perfkb/fields.py`. 축은 프로바이더별 dict가 아니라 **레코드에 있는 칸만
나오는** 방식이라, "ACU는 Azure에만"이라는 성질은 그대로 유지됩니다.

판정 문구도 공유합니다. 비교 표 밑에 `_warning_for`의 결과를 그대로 붙이므로,
`perf_compare`와 `cost_recommend_specs`가 이제 **글자 단위로 같은 말**을 합니다.

## 곁다리로 고쳐진 표시 결함

```
최신 세대: False        →  세대: 구세대
최대 영구 디스크 수: 128.0  →  최대 영구 디스크 수: 128
EBS 최대 대역폭          →  EBS 최대 대역폭(버스트)
```

`False`는 파이썬을 읽는 사람에게만 뜻이 통하고, 개수에 소수점이 붙으면 값 자체가
의심스러워 보입니다. 버스트 축은 숨기면 데이터를 버리는 것이고 그냥 "최대"면 지속
성능으로 읽히므로 **라벨에서 갈랐습니다.**

# 저신뢰 경고 기준의 승계 — 숫자가 아니라 질문을 갈랐다

`decisions.md` §7의 미결입니다. 옛 계획(P2a)은 **"신뢰도 < 0.7이면 경고"**였는데
(a) `check`가 쓰던 0.8과 어긋났고 (b) **신뢰도 자체를 버리면서 전제가 사라졌습니다.**

승계는 0.7을 다른 숫자로 바꾸는 일이 아니었습니다. 코드를 훑어보니 그 자리에는 이미
두 개의 **서로 다른 규칙**이 살고 있었는데, 이름이 붙은 쪽은 하나뿐이었습니다.

```
is_fact(basis, reviewed)     kbcommon에 정의됨.   검수가 면제된다.
basis != "stated"            이름 없음. graphkb·perfkb에 리터럴로 각각.
```

## 왜 둘이어야 하나

검수의 뜻이 **두 방향에서 다르기** 때문입니다.

- 사람이 확인한 제약으로 값을 **거부**하는 것은 정당합니다 — 확인했으니까요.
- 사람이 "가장 가깝다"고 고른 클라우드 간 동치를 **단언**하는 것은 정당하지 않습니다.
  확인한 것은 *우리 판단이 그렇다*는 사실이지 *원본이 그렇게 선언했다*는 사실이
  아닙니다.

실측이 이 칸을 정확히 짚었습니다. "AWS ALB는 GCP에서 뭐야?"에 모델이
`ComputeForwardingRule`을 **단언**했는데, 그 엣지는 **검수된 짐작**입니다 —
`is_fact`로는 사실이고 유보 기준으로는 대상입니다. **두 기준이 갈리지 않으면 이 답을
막을 수 없습니다.** 하나로 합치면 "쓰지도 말라" 아니면 "마음껏 단언하라" 둘 중
하나가 됩니다.

## 한 일

`kbcommon/basis.py`에 `needs_hedge(basis, reviewed)`를 두고 두 KB의 리터럴을 걷어냈습니다.

```
is_fact      값을 거부해도 되는가      검수가 면제된다
needs_hedge  유보를 붙여야 하는가      검수는 면제가 아니다
```

`reviewed` 인자를 받고도 **쓰지 않는 것**이 핵심입니다 — 호출부가 "인자를 빼먹었나"
하고 되묻지 않도록 시그니처를 맞춰 두고, 안 쓴다는 사실을 한 곳에만 적습니다.

`test_no_kb_reinlines_the_rule`이 여섯 패키지를 훑어 `basis == "stated"` 같은 리터럴
비교를 막습니다. **같은 규칙이 두 벌이면 갈라집니다** — 바로 앞 항목에서 필드 목록
세 벌이 실제로 갈라진 것과 같은 모양입니다.

> 가드 자신도 검사합니다(`test_the_guard_actually_bites`). **아무것도 안 무는 정규식은
> 조용히 통과합니다** — 이 저장소에서 셸 heredoc으로 정규식을 쓰다 `\b`가 진짜
> 백스페이스 문자가 된 적이 있고, 화면·grep·편집기 어디에도 안 보였습니다.

# 리전 부분 일치 — 트레이드오프인 줄 알았는데 아니었다

`decisions.md` §7의 "costkb의 미러 이탈 두 곳"입니다. 기록은 **"부분 일치 편의와 미러
불변식 중 하나를 포기해야 한다"**로 적혀 있었습니다. 실측해 보니 **포기할 필요가
없었습니다.**

## 재현

실존 리전 154개 중 **15쌍이 서로의 부분문자열**입니다.

```
region='centralus'   1,234건이어야 하는데 4,120건  (+2,886)  north/south/westcentralus
region='us-east'       190건이어야 하는데 4,349건  (+4,159)  us-east-1/2, us-east1/4/5
region='eastus'      1,301건이어야 하는데 2,504건  (+1,203)  eastus2
region='westus'      1,224건이어야 하는데 2,339건  (+1,115)  westus3
```

## 기록에 없던 사실이 답을 줬습니다

**`us-east`는 그 자체로 실존 리전(190건, IBM)이면서 다섯 리전의 접두사입니다.**
그래서 "부분 일치를 없앤다"도 "유지한다"도 답이 아니었습니다 — 둘 다 이 한 이름에서
틀립니다.

**정확 일치를 우선하면 둘 다 삽니다.**

```
centralus     → exact    centralus만              (미러와 같은 답)
us-east       → exact    us-east만                (미러와 같은 답)
ap-northeast  → partial  -1/-2/-3을 묶음 + 고지    (미러엔 없는 편의)
nowhere-9     → none     리전 이름이 범인이라고 말함
```

부분 일치로 넓혔을 때만 밝힙니다 — 정확 일치는 사용자가 물은 그대로라 덧붙일 말이
없고, 넓혔을 때 **여러 리전 단가를 하나로 읽으면 틀린 비교**가 되기 때문입니다.

## 곁다리로 드러난 것

빈 결과에 `require_accelerator`는 이유를 말하는데 **리전은 말하지 않았습니다.**
`region='nowhere-9'`이면 "조건을 조정하세요" + 커버리지 표만 나와서, 사용자는
vCPU·메모리만 낮추다 끝납니다. 리전 이름이 범인이면 그걸 먼저 말하게 했습니다.

## `_note`가 한 문단 안에서 모순이었습니다

```
… 두 경로의 답이 일치합니다. memGiB는 **보정된 실제 값**입니다 — …
```

앞 문장은 일치를 단언하고 뒷 문장은 일부러 다르게 했다고 말합니다. **일부러 다르게
하는 곳 셋**을 이름으로 적었습니다: memGiB 보정 · 가격 미상 제외(건수는 답에 적음) ·
리전 정확 일치 우선. 재빌드 후 `data/tumblebug-cost.json.gz`를 다시 포장했고,
레코드 73,083건은 **한 건도 달라지지 않았음을 대조로 확인**했습니다(`_note`만 변경).

> conftest가 리전 4개짜리 번들만 보므로 이 충돌은 구조적으로 안 잡혔습니다.
> `test_costkb_region.py`는 **실제로 겹치는 이름들**로 픽스처를 만듭니다 — 지어낸
> 리전으로는 이 결함이 재현되지 않습니다.
