# 에이전트 실측 — 데이터가 실제 답변으로 이어지는가 (2026-07-21)

이번 세션에 데이터가 크게 바뀌었습니다(제약 53,657 → 96,844, 커버율 세 프로바이더 모두
90%+). **모델이 그걸 실제로 쓰는지는 안 봤습니다.** 그래서 질의 12개를 실제 에이전트에
태우고 **도구 호출까지 기록**했습니다.

재현:

```bash
python tools/agent_probe.py                       # 전부 돌리고 결과를 본다
python tools/agent_probe.py --only 3-9            # 하나만
python tools/agent_probe.py --strict              # 실패가 있으면 종료코드 1

RUN_AGENT_TESTS=1 uv run pytest tests/test_agent_regression.py -v   # 회귀로
```

**회귀 테스트는 옵트인입니다.** 기본 `pytest`에서는 건너뜁니다 — 실제 API를 호출하고
(9건에 1~2분), 네트워크가 필요하며, **비결정성이 있어** 기본 스위트에 넣으면 실패가
일상이 되고 그러면 진짜 실패가 안 보입니다.

> 답만 읽으면 **도구를 쓴 답**과 **모델이 지어낸 답**이 구별되지 않습니다.
> 이 프로젝트가 반복적으로 겪은 실패 양상이라, 하네스가 도구 호출 순서를 함께 찍습니다.

## 데이터 작업이 답변까지 이어진 것

**3-9가 이번 세션 전체의 결론입니다.** 모델이 `cap_check_value`를
`context=VolumeType=gp2`로 부르고, 이렇게 답했습니다:

> 아니요. gp2 볼륨의 크기는 **1 GiB ~ 16 384 GiB**로 제한됩니다.
> 30 000 GiB는 이 한도를 초과합니다. gp3는 최대 65 536 GiB까지 지원합니다.

세션 시작 때 같은 질문의 답은 *"알려진 제약이 없어 판정할 수 없습니다"*였습니다.

**3-11도 통과했습니다.** 도구가 붙인 낡음 고지가 답변까지 살아남았고, 정밀도까지 지켰습니다:

> **참고**: 위 16개 항목 중 **1개**는 2023‑09‑26 기준 Terraform Google Provider
> 스키마에서 가져온 값으로, 최신 상황과 차이가 있을 수 있습니다.

## 고친 것

### 1. `cap_check_value`가 `context`를 못 받고 있었다 — D3이 절반만 연결돼 있었다

`agent_api.check()`에는 `context`를 넣었는데 **도구에는 안 넣었습니다.** 그래서 모델이
조건부 판정을 쓰고 싶어도 부를 방법이 없었고, `cap_property_limits`로 표를 받아 스스로
비교했습니다. 그 비교는 지식베이스가 보증하지 않습니다.

도구에 `context: 'VolumeType=gp2'` 형식을 추가하니 **바로 3-9가 통과**했습니다.

### 2. 낡음 고지를 꼬리말에서 **머리줄로** 옮겼다

꼬리말로 뒀을 때는 답변에 안 옮겨졌습니다(프롬프트로 "⚠는 반드시 옮기라"고 지시해도).
개수는 모델이 반드시 옮기는 정보이므로 **거기에 붙였습니다** — 그러면 경고만 따로
떼어내기 어렵습니다.

> 다만 정직하게: 처음 판정이 **화면 잘림 때문에 틀렸을 가능성**이 있어, 머리줄 이동이
> 원인이라고 단정하지는 않습니다. 아래 참고.

### 3. Azure limits 문서 13개를 놓치고 있었다

`-limits.md`로 **끝나는** 것만 읽어서 `azure-storage-account-limits-standard.md`,
`azure-virtual-machines-limits-azure-resource-manager.md` 같은 것들이 빠졌습니다.
`-limits`를 부분 문자열로 보게 고쳐 **쿼터 494 → 542건**.

## 오판할 뻔한 것 — 실측에서 가장 값진 부분

**세 번 다 "모델이 틀렸다"고 기록할 뻔했고, 세 번 다 우리 쪽 문제였습니다.**

1. **3-11 "모델이 낡음 경고를 뺐다"** → 처음 검사 대상이 `ComputeSubnetwork`였는데,
   **D6이 그 타입의 불변 레코드를 전부 최신 프로바이더 값으로 갈아끼워** 낡음 고지가
   애초에 안 붙었습니다. 뺄 경고가 없었습니다. `tf2crd`가 남아 있는 타입(109종)으로
   바꾸니 정상이었습니다.
2. **"경고가 여전히 안 옮겨진다"** → 하네스가 답변을 700자에서 잘라 보여줬는데
   **경고는 그 뒤에 있었습니다.** 전체를 검사하도록 고쳤습니다.
3. **3-9 "16,384가 답변에 없다"** → 모델이 `16 384`로 썼는데 그 공백이 **U+202F**
   (좁은 줄바꿈 없는 공백)라 문자열 비교가 실패했습니다. 맞는 답을 틀렸다고 기록할
   뻔했습니다. 숫자 안 구분자를 지우고 비교하도록 고쳤습니다.

> **교훈**: 실측 하네스 자체가 틀릴 수 있고, 그 오류는 **"모델 탓"으로 보인다.**
> 판정을 자동화할수록 판정기를 의심해야 합니다.

## 회귀로 승격하면서 정한 것

**자동 판정은 셋만 합니다** — 어떤 도구를 불렀나 / 부르지 말아야 할 걸 불렀나 /
답을 지탱하는 말이 답변에 들어 있나. **답변이 잘 쓰였는지는 판정하지 않습니다.**
그걸 코드로 굳히면 "문구가 바뀌었다"와 "동작이 틀렸다"가 구별되지 않습니다.

**지킬 생각 없는 기대는 뺐습니다.** 3-2·3-10에서 모델이 `cap_check_value` 대신
표를 받아 종류별로 정리해 답하는데, 그 답이 실용적으로 더 낫다고 판단했으므로
기대에서 제거했습니다. 남겨 두면 실패가 일상이 되고 진짜 실패가 묻힙니다.

**비결정성은 숨기지 않고 셉니다.** 실패하면 한 번 재시도하고, 재시도에서 통과하면
실패가 아니라 **불안정(flaky)**으로 기록합니다(pytest에서는 `xfail`).
두 번 돌린 실측:

| 실행 | 통과 | 불안정 |
|---|---:|---|
| 1차 | 7/9 | 2건 |
| 2차 | 8/9 | 1건 (`1-2a`) |

**불안정한 항목이 실행마다 바뀝니다.** 특정 질의가 약한 게 아니라 전반적으로
1~2건이 흔들린다는 뜻이고, 조용히 재시도만 했으면 이 사실이 사라졌을 겁니다.

여기서 지키는 것들은 전부 **한 번 깨진 적이 있는 것**입니다 — `cap_check_value`가
`context`를 못 받아 조건부 판정이 통째로 안 쓰이던 것, 낡음 고지가 답변에서
사라지던 것. **둘 다 실측으로만 발견됐고 단위 테스트 592개는 전부 통과하고 있었습니다.**

## 남은 것 (고치지 않음)

**3-2 · 3-10: 값 판정 질문에 `cap_property_limits`로 답한다.** 프롬프트에 "표만 보여주지
말고 판정하라"고 넣었는데도 그렇습니다. 다만 3-10의 답변은 **종류별로 가능/불가를 모두
정리해 줘서 실용적으로는 더 낫습니다.** "되물어야 한다"는 제 기대가 옳은지부터
다시 볼 문제라, 프롬프트를 더 조이지 않고 남겨 둡니다.

**3-3: 계획 게이트에 3번 부딪힌 뒤 계획을 세웠다.** 게이트는 제대로 막았지만
(`[스펙추천] 계획 없음 → 거부` ×3) 46.8초가 걸렸습니다. 첫 실행 때는 한 번에
`record_plan → cost_*`였으므로 **모델의 비결정성**입니다. 거부 메시지가 다음 행동을
충분히 안내하는지 볼 여지가 있습니다.

**D4: Azure Key Vault 쿼터가 1건뿐.** azure-docs `includes/`에 키 볼트 한도 문서가
**아예 없습니다**(우리 누락이 아님). 모델은 이걸 정확히 답했습니다 — *"이 지식베이스에
포함되어 있지 않으니 포털에서 확인하라."* **없는 걸 지어내지 않은 것이 정답입니다.**

회귀 9건은 통과 상태였으므로, **아직 회귀 항목이 없는 새 데이터**만 골라 4건을

| | 지키는 것 | 결과 | 실제 |
|---|---|---|---|
| N1 | 리전×인스턴스 타입 판정 | ✗ | **KB가 답을 쥐고도 모른다고 답함** |
| N2 | 리전 목록 | ✓(가짜) | 같은 실패. 부분 문자열이 거절을 통과시킴 |
| N3 | DynamoDB 불변 속성 | ✓ | 진짜 통과. 도구 1번, 68.9초 |
| N4 | S3 교차 필드 | — | **무효 프로브** (해당 데이터가 없음) |

## 프로브를 돌리려다 도구가 멈췄다 — 결함 2건

실측이 출력 없이 멎었습니다. 원인은 모델이 아니라 우리 도구였습니다.

`property_limits('AWS::EC2::Instance','InstanceType')`가 **377,439자**를 반환했습니다.
리전 38개 × 인스턴스 타입 ~500개를 통째로 찍어서, 도구 응답 하나가 모델 컨텍스트를
전부 먹었습니다. 요약(`brief`)을 `check` 경로에만 넣고 `property_limits` 경로에
안 넣은 것이 원인입니다. → 5,153자.

줄이고 나니 **39줄이 전부 똑같아 보이는** 두 번째 결함이 드러났습니다. 조건을
표시하지 않아서입니다. 같은 결함이 `check`의 위반 문구에도 있었습니다:

```
전: Size: 30000 GiB는 최대 16384 GiB을(를) 벗어남
후: Size: 30000 GiB는 최대 16384 GiB을(를) 벗어남 (VolumeType='gp2' 일 때, …)
```

앞 문장은 16,384이 EBS의 보편 상한처럼 읽힙니다. 정작 사용자에게 필요한 사실은
**gp2에서의** 한도라는 것 — gp3로 바꾸면 65,536까지 됩니다. **한도를 어겼다는 말보다
어느 조건에서의 한도인지가 해결책을 가리킵니다.**

두 결함 모두 데이터가 아니라 **데이터를 내보내는 방식**의 문제였고, 단위 테스트
609건은 전부 통과하고 있었습니다.

## N1/N2 — 축을 늘렸는데 축끼리 서로를 모른다

```
질문: af-south-1 리전에서 p5.48xlarge 인스턴스를 쓸 수 있어?
답변: "지식베이스에서는 확인할 방법이 없습니다. AWS 콘솔에서 확인하세요."

데이터: p5.48xlarge — 되는 리전 14 / 안 되는 리전 24 (af-south-1은 불가)
```

N2는 **838초(14분) 동안 웹검색 13회**를 돌고 같은 결론을 냈습니다. 우리 KB가
밀리초 안에 답하는 질문입니다.

**원인은 데이터가 아니라 도달 경로입니다.** 에이전트가 밟은 길:

```
kb_search_types('p5.48xlarge')          → 값이지 타입이 아니니 안 나옴
kb_describe_type('AWS::EC2::Instance')  → 1,484자, 전부 그래프 엣지
                                          'InstanceType' 언급 0회
→ 근거 없음으로 판단 → 웹검색 13회
```

`describe_type`은 "이 리소스에 대해 알려줘"의 자연스러운 입구인데 **제약을 한 글자도
말하지 않습니다.** 그래서 에이전트는 capacitykb에 이 타입 관련 데이터가 있다는 걸
알 방법이 없었습니다. 바로 옆에 `cap_allowed_values('AWS::EC2::Instance','InstanceType')`가
정답을 들고 있었는데도 그렇습니다.

이번 세션에 (리전, 값) 79,809쌍을 넣었지만 에이전트는 거기 닿지 못합니다.
**데이터를 늘리는 것과 데이터에 닿게 하는 것은 다른 일입니다.**

## 하네스가 또 오판을 만들 뻔했다

N2는 ✓로 찍혔습니다. `want_any=("us-east-1", "가능")`으로 썼는데 거절 답변의
**"실제 사용 가능 여부는"** 안에 "가능"이 들어 있었습니다. **거절을 성공으로 읽었습니다.**

1차 실측에서도 판정 아티팩트가 세 번 오판을 만들 뻔했습니다(낡은 레코드를 고른
질의, 700자 절단, `16 384`의 U+202F). 이번이 네 번째입니다.

> 한국어 짧은 부분 문자열은 기대 문구로 쓰지 않습니다. "가능"·"없음"처럼 흔한
> 조각은 **정반대 뜻의 문장에도 들어 있습니다.**

## N4는 제가 잘못 설계한 프로브다

S3 버킷의 교차 필드 조건을 물었는데 **`AWS::S3::Bucket` 교차 필드 데이터가 없습니다**
(총 162건, 대부분 `gcp::ContainerCluster` 16 · `gcp::CloudBuildTrigger` 11 ·
`aws::AWS::DLM::LifecyclePolicy` 9). 답변은 맞았지만 전부 웹검색에서 나왔으므로
**새 축이 작동한다는 증거가 아닙니다.** 유효한 프로브였다면 `ContainerCluster`를
물어야 했습니다.

## 조치

`kb_describe_type`이 다른 축을 가리키게 합니다. "이 타입에 제약 N건(InstanceType,
Size …), 불변 속성 M건이 있다"는 한 줄이면 N1/N2가 첫 도구 호출에서 풀립니다.

단방향 규약(에이전트 → KB, KB끼리 import 금지) 때문에 이 교차 참조는 `graphkb`
안이 아니라 **`nim_agent/graph_tools.py`**에 들어갑니다. 거기가 양쪽을 다 볼 수 있는
유일한 층입니다. 새 도구를 만드는 게 아니라 **기존 도구를 완성하는 것**입니다.

### 3차 — 고친 곳에 에이전트가 오지 않았다

`kb_describe_type`에 용량 축 안내를 붙였는데 결과가 그대로였습니다. 이유:

```
kb_search_types('p5.48xlarge')  → "타입이 없습니다"  ← 여기서 포기
                                   describe_type까지 오지 않음
```

1차 실측에서는 `describe_type`을 불렀기에 거기를 고쳤는데, **모델의 경로는
매번 다릅니다.** N1은 이 회차에 도구를 아예 하나도 부르지 않았습니다(7초).

또 하나: 에이전트는 `p5.48xlarge`를 **타입 이름으로** 물었습니다. 사람도 그렇게
묻습니다. 우리는 "노드를 찾을 수 없습니다"만 내놨습니다. **값에서 속성으로 가는
길이 KB에 없었습니다** — 지금까지 "타입을 주면 제약을 준다"만 할 수 있었습니다.
에이전트는 올바른 질문을 하고 막다른 길을 만났습니다.

역인덱스는 쌉니다: 등장 78,482회지만 **고유 값은 6,197개**뿐입니다.

### 4차 — 제가 새로 만든 모순

`search_types`에 값 안내를 **무조건** 붙였더니:

```
'subnet' 검색 결과 12개 중 12개:
- aws::AWS::DAX::SubnetGroup …
'subnet' 은(는) 타입이 아니라 **값**입니다.   ← 찾아 놓고 아니라고 한다
```

막다른 길일 때만 다른 길을 가리켜야 합니다. 판정을 위해 `graphkb.count_types()`를
새로 뒀습니다 — 반환 문자열에서 "타입이 없습니다"를 문자열 매칭하면 문구를
다듬는 순간 조용히 깨집니다.

### 도구가 "무엇을 할 수 있는지" 말하지 않았다

3차의 N1은 도구를 하나도 안 부르고 이렇게 답했습니다:

> "`cost_recommend_specs`·`perf_instance_profile` 등은 가격·성능·사양 정보를
> 제공하지만, **리전별 제공 여부**는 별도로 조회되지 않습니다."

`cap_*`는 후보로도 떠올리지 않았습니다. 확인해 보니 `cap_check_value` 설명에는
리전이라는 말이 한 번도 없었습니다. **안 된다는 말은 없었지만 된다는 말도
없었습니다.** 도구 설명에 이 사례를 명시했습니다 — 프롬프트를 조이는 것과
도구가 자기 적용 범위를 밝히는 것은 다릅니다.

### 결과

| | 전 | 후 |
|---|---|---|
| N1 | 웹검색, 도구 0개, 오답 | **6.6초 · `cap_check_value` 1회 · 정답** |
| N2 | 838초 · 웹검색 13회 · 오답 | **10.4초 · 도구 2회 · 리전 14곳 정확** |

모델이 낸 14개 리전 목록이 데이터 정답지와 정확히 일치합니다.
둘 다 회귀 하네스에 등록했습니다(`N1`·`N2`).

### 남는 교훈

**고칠 곳을 실측 한 번으로 정하면 안 됩니다.** 1차에서 본 경로(`describe_type`)만
믿고 고쳤다가 두 회차를 버렸습니다. 모델은 매번 다른 문으로 들어옵니다 —
**모든 문이 답을 알아야 합니다.**

# 3차 — 질문 24개 무편향 조사 (2026-07-21)

RAG가 필요한지 감으로 결정하지 않기 위해 실패 **원인**을 분류했습니다.

**설계를 바꿨습니다.** 지금까지는 데이터를 알고 기대 문구를 썼습니다. 그러면 내가
아는 것만 검사합니다 — N4를 우리가 갖고 있지도 않은 S3 교차 필드로 잘못 설계한
것이 그 증거입니다. 이번엔 **질문을 먼저 쓰고**, 도구 호출만 기록하고, 정답지를
답변 읽기 **전에** 만들고, 답변은 사람이 읽어 분류했습니다.

## 라우팅은 해결됐다

24건 중 **23건이 첫 시도에 맞는 KB 도구**로 갔습니다. 웹으로 샌 것은 1건(S19,
AKS 노드 풀 쿼터 — 우리가 실제로 안 가진 데이터)뿐입니다. 2차에서 838초·웹검색
13회가 걸리던 부류가 2~10초에 끝납니다.

## 적합도 실패는 여전히 0

| 원인 | 건수 |
|---|---:|
| 커버리지 — 데이터가 없음(정직히 밝힘) | 4 |
| **출처 혼합 — KB 사실과 모델 기억이 안 갈림** | **4** |
| KB 데이터 결함 | 1 |
| 경로 — 데이터에 못 닿음 | 1 |
| 표시 — 근거 등급이 답변에서 사라짐 | 2 |
| **적합도 — 관련 있는 걸 못 찾음** | **0** |

**RAG로 풀 문제는 조사 24건에서 한 건도 안 나왔습니다.** 대신 이름이 붙지 않았던
축이 하나 드러났습니다.

## 가장 위험한 것: 출처 세탁 (S21)

> "ap-northeast-2에서 쓸 수 있는 GPU 인스턴스 알려줘"
>
> "※ **cap_allowed_values 지식베이스에서 해당 리전의 전체 인스턴스 타입을 조회한
> 뒤** GPU가 장착된 패밀리만 추려낸 결과이며 …"
>
> | G5g | g5g.xlarge – 1 × **AMD Radeon Instinct MI250X** | 4 | 16 |

GPU 개수·vCPU·메모리는 capacitykb에 **없는 데이터**입니다(그 도구도 안 불렀습니다).
`g5g`는 NVIDIA T4G이지 AMD가 아닙니다 — **지어낸 값입니다.** 그런데 답변은 그것을
**우리 지식베이스에서 조회한 결과라고 명시**합니다.

모델이 자기 기억을 **우리 KB의 이름으로 세탁**했습니다. 이 프로젝트가 쌓아 온
`basis`·소스 핀·교차 확인이 통째로 무의미해지는 유일한 방식입니다. 틀린 답보다
나쁩니다 — 틀린 답에 우리 보증이 찍혀 나갑니다.

같은 부류가 3건 더 있습니다:

- **S03** S3 버킷 대문자 — "소문자만 가능"은 맞지만 우리 데이터에 없습니다(우리는
  `BucketName` 불변만 압니다). 둘을 한 **근거** 목록에 섞어 냈습니다.
- **S15** ALB 동치 — 우리 데이터의 `basis`는 `짐작(검수됨)`인데 답변은 단언합니다.
  확인해 보니 `equivalent_types` **출력 자체가 근거 등급을 안 싣습니다.**
- **S11** DynamoDB KeySchema — 데이터는 `조건부 변경 불가`인데 답변은 `변경 불가`로
  단정합니다. 조건이 사라졌습니다.

## KB 데이터 결함 (S05)

"Azure VM 만들 때 필요한 선행 리소스" → **KeyVault만 필수**, VNet·NIC는 선택.
정확히 거꾸로입니다. 원인은 중첩 필수성을 리소스 수준으로 끌어올린 것:

```
필수: properties.storageProfile.osDisk.encryptionSettings.diskEncryptionKey.sourceVault
```

`sourceVault`는 `encryptionSettings` **안에서만** 필수인데 그 부모가 선택입니다.

범위: 필수 엣지 3,540건 중 **139건(3.9%)**이 중첩 2단 이상
(gcp 13.8% · aws 5.8% · azure 1.0%), 필수 체인이 오염된 타입 **59종**.
사람이 물을 법한 타입 6개 중 2개가 걸립니다(Azure VM · GCP ContainerCluster).

규칙은 단순합니다 — **경로상 모든 조상이 필수일 때만 리소스에 필수**. 다만 파서
3종(Bicep·KCC·CFN)이 조상 필수성을 다시 읽어야 하고, 지금 그래프 산출물에는 그
정보가 없습니다.

## 잘 된 것도 기록한다

- **S13** VPC당 서브넷 — "우리 쿼터 데이터는 Azure만 있다"고 **먼저 밝히고**
  일반값은 출처를 구분해 덧붙였습니다.
- **S20** Lambda 환경변수 — KB에 없다고 명시하고 답했습니다. 정작 우리 KB 문구는
  *"수집 범위 안이므로 '없음'이 답입니다"*라고 **없는 한도를 단언**했는데(실제
  4KB 제한이 있습니다) 모델이 그걸 안 따라갔습니다.
- **S22** EC2 보안 그룹 개수 — 모른다고 답했습니다.

## 결론

**RAG는 지금 필요 없습니다.** 검색 문제가 24건 중 0건입니다.

다음에 손댈 것은 **출처 경계**입니다 — 답변에서 "KB가 보증하는 것"과 "모델이 아는

# 4차 실측 (2026-07-22) — 오늘 바꾼 데이터가 닿는가

capacitykb를 크게 바꾼 뒤 다시 쟀습니다(조건 목록·Azure 불변성 993건·정규식 엔진 교체).

**회귀 11건은 통과 10 · 불안정 1**로 살아 있습니다. 실패로 찍힌 `D4`는 **프로브가
낡은 것**이었습니다 — 전제가 "키 볼트 한도 문서는 원본에 아예 없다"였는데, *전용*
문서가 없을 뿐 `private-link-limits.md`에 "키 볼트당 프라이빗 엔드포인트 64개"가
있습니다. 모델은 그걸 찾아내고 나머지는 없다고 밝혔습니다. 기대를 우리 데이터에만
있는 숫자(`64`)로 바꿨습니다.

## 새 데이터는 닿는다

- **A1** Azure 불변성 — `administratorLogin` 등 12건이 답변에 그대로 나왔습니다.
- **A3** 없는 조합 — "938건이 있지만 이 조합에 걸리는 것이 없습니다"가 전달됐습니다.

## 판정의 구조적 한계를 확인했다

**예/아니오 질문은 한국어 부분 문자열로 판정할 수 없습니다.**

```
정답:  "…사용할 수 있습니다"
거절:  "…사용할 수 있는지 확인할 수 없습니다"
```

`want_any=("사용할 수 있",)`은 둘 다 통과시킵니다. 이걸로 A2에서 **실패를 통과로**
읽었습니다 — N2에서 똑같이 겪고 문서에 적어 두고도 반복했습니다(오판 7회째).

그렇다고 내부 이름(`DBInstanceClass`)을 기대로 쓰면 **정답을 실패로** 읽습니다.
모델은 자연스러운 한국어로 "인스턴스 클래스"라고 씁니다.

> 결론: 예/아니오 질문은 **도구 호출로만 자동 판정**하고 답변의 옳고 그름은 사람이
> 읽습니다. 하네스에 못 시키는 일을 시키려다 두 방향으로 다 틀렸습니다.

## 출처 세탁이 다시 잡혔다 — 이번엔 확정적 오답

`A3`의 한 회차에서 모델이 `context` 없이 도구를 불렀습니다. 도구는 정확했습니다:

```
조건 938가지 중 840가지에서 가능, 98가지에서 불가입니다.
```

모델의 답변:

> "Aurora PostgreSQL 16.4에서는 db.t3.medium을 **사용할 수 없습니다**.
> ※ **cap 지식베이스에서** … Aurora PostgreSQL 16.x에서는 해당 인스턴스 타입이
> **지원되지 않음으로 표시되었습니다.**"

우리 KB는 16.4를 언급한 적이 **없습니다**(원본에 그 버전이 없습니다). 840/938이
가능인데 "지원되지 않음"으로 뒤집고, 그것을 **우리 이름으로 출처 표기**했습니다.

24건 조사에서 1순위로 꼽은 문제가 재현된 것이고, 이번 것은 **확정적 부정**이라
사용자가 쓸 수 있는 구성을 못 쓰게 만듭니다.

## 실측이 찾아낸 KB 결함 둘

**(1) "모른다"와 "이 조합에 걸리는 게 없다"를 구분하지 않았다.**
`aurora-postgresql 16.4`에 938건을 쥐고도 *"알려진 제약이 없어 판정할 수 없습니다"*
라고 답했습니다. 앞은 데이터가 없다는 뜻이고 뒤는 조합 쪽을 다시 보라는 신호라
전혀 다른 말입니다. `CheckResult.excluded`로 갈랐습니다.

**(2) 살짝 틀린 속성 이름에 막다른 길을 줬다.**
모델이 RDS에 `InstanceType`을 물었습니다(EC2가 그 이름을 쓰니 자연스러운 시도인데
RDS는 `DBInstanceClass`). 우리는 938건을 쥐고도 "알려진 제약이 없다"고 답했습니다 —
`p5.48xlarge`를 타입 이름으로 물었을 때와 같은 실패입니다. 이제 아는 이름을
가리킵니다.
