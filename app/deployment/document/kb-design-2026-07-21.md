# 지식베이스 설계 — 데이터 먼저 (2026-07-21)

**질문 셋에 답하는 문서입니다.**
1. 우리 데이터셋은 충분한가?
2. 이런 상황을 바깥에서는 어떻게 푸는가?
3. 그래서 무엇을 어떤 순서로 할 것인가?

**결론 먼저**: 충분하지 않습니다. 그리고 **부족한 곳이 우리가 짐작하던 곳이 아닙니다.**
직전까지 본론으로 잡았던 "조건부 제약 칸"은 **4건짜리 각주**였고, 진짜 구멍은
**커버리지와 실제 한도값**입니다. 아래는 그 근거와, 바깥의 해법, 그리고 실행 순서입니다.

전제: 이 문서의 숫자는 전부 실측입니다. 재현 스크립트는 `tools/kb_audit/`.

## 1. 진단 — 무엇이 부족한가

### 1-1. "용량 KB"의 92%는 용량이 아니다

`capacitykb` 레코드 53,657건을 성격별로 갈라보면:

| 성격 | 건수 | 비율 |
|---|---:|---:|
| **스키마 모양** (필수 여부, 변경 가능성, 길이, 패턴, 개수) | 49,233 | **91.8%** |
| **실제 한도·값** (min, max, 허용값, 기본값) | 4,424 | **8.2%** |

`min`/`max`를 하나라도 가진 타입은 **346종 / 5,575종 = 6.2%**입니다.
쿼터("몇 개까지 만들 수 있나")는 **전체 52건**, 그것도 Azure만.

즉 **"이 필드가 필수인가", "나중에 못 바꾸는가"는 잘 답하지만, 사용자가 용량 KB에
기대하는 "얼마까지 되나 / 몇 개까지 되나"는 거의 못 답합니다.** 이름이 내용을
과장하고 있습니다.

### 1-2. 커버리지가 프로바이더마다 딴판이다

| 프로바이더 | 타입 | 제약 있음 | 커버율 |
|---|---:|---:|---:|
| aws | 1,647 | 1,644 | **99.8%** |
| azure | 3,392 | 288 | **8.5%** |
| gcp | 536 | 0 → **497** | 0% → **92.7%** (D1 완료) |

`capacitykb`는 Azure를 네임스페이스 3개(`compute`/`containerservice`/`network`)만 읽고,
**GCP는 아예 안 읽습니다.** 그래프(graphkb)는 GCP 536종을 아는데 용량은 0건이라,
"GCP 리소스의 제약"은 질문 자체가 성립하지 않습니다.

의존성 그래프 쪽도 축 하나가 통째로 비어 있습니다:

| | 참조 관계 | 담김 관계 |
|---|---:|---:|
| azure | 291 | **2,223** |
| aws | 2,391 | **0** |
| gcp | 803 | **0** |

**"이 리소스는 무엇 안에 담기나"는 azure만 답합니다.** 고립 타입(관계 0건)은
aws 545/1,647(33%), gcp 112/536(21%), azure 699/3,392(21%).

### 1-3. `basis`가 capacitykb에서는 정보를 거의 안 나른다

`stated` 53,498 vs `inferred` **159(0.3%)**, `reviewed` 0건. graphkb에서는 잘 작동하는
사실/짐작 구분이(3,888 vs 1,867 = 32% 짐작) 여기서는 거의 상수입니다.
**신뢰도를 표현하는 장치가 있는데 표현할 다양성이 없는 상태**입니다.

### 1-4. 조건부 제약은 진짜 문제이지만 작다

"볼륨 종류마다 크기 한도가 다르다" 같은 규칙 — 실제로 우리 데이터에서 **4건**입니다
(`Volume.Size` min/max, `Volume.Iops` min/max). 원본 산문을 유형별로 세어봐도
설명문 있는 속성 6,339개 중 규칙을 말하는 건 198개(3.1%)이고, 그중 조건부 성격은
"다른 속성에 의존" 130 + "변종별로 다름" 6 = **136건**이 상한입니다.

**4건을 위해 정교한 표현 체계를 설계하는 것이야말로 오버피팅입니다.**

## 2. 바깥은 어떻게 푸는가

조사 세 갈래를 돌렸습니다. 우리에게 쓸모 있는 것만 추립니다.
(출처 URL은 각 항목에 달았습니다. 벤더 마케팅과 측정된 결과를 구분해 적었습니다.)

### 2-1. 가장 중요한 발견 — 안 쓰고 있던 기계 판독 소스가 있다

**AWS Price List 벌크 API**가 볼륨 종류별 한도를 **구조화된 속성으로** 팝니다.
인증 없이 받을 수 있습니다:

```
https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonEC2/current/<region>/index.json
```

`productFamily: "Storage"` 항목에서:

| volumeApiName | maxVolumeSize | maxIopsvolume | maxThroughputvolume |
|---|---|---|---|
| gp2 | 16 TiB | 16000 | 250 MiB/s |
| gp3 | 64 TiB | 80000 | 2000 MiB/s |
| io1 | 16 TiB | 64000 | 1000 MiB/s |
| io2 | 64 TiB | 256000 | 4000 MiB/s |
| st1 | 16 TiB | `500 - based on 1 MiB I/O size` | 500 MiB/s |
| standard | 1 TiB | `40 - 200` | `40 - 90 MB/sec` |

조사자가 실제로 당겨 확인했고 **현재 AWS 문서와 값이 일치**합니다. 속성 이름은
`describe-services`가 공식 `AttributeNames`로 확인해 줍니다.

**정직한 한계 — 이걸로 EBS 사실의 6할쯤 됩니다:**
- **최댓값만** 있습니다. 최솟값(gp2 1 / io1 4 / st1·sc1 125 GiB)은 없습니다.
- 값이 **반쯤 산문**입니다. `"64 TiB"`는 단위 변환이 필요하고, st1/sc1/standard는
  숫자로 안 파싱됩니다.
- **비율 규칙이 없습니다.** gp3의 IOPS:용량 500:1 상한 같은 건 안 나옵니다.
- **과금 분류지 능력 분류가 아닙니다.** 값이 계속 정확하리란 계약상 보장이 없습니다 —
  오늘 정확한 건 경험적 사실입니다. **핀을 박고 재확인해야지 구조적으로 믿으면 안 됩니다.**
- 파일이 큽니다(작은 리전도 43MB). 볼륨 종류 속성은 리전 불변이라 **작은 리전에서
  받으면 됩니다**(`ap-east-2`·`mx-central-1`에서 동일 확인).

**최솟값은 botocore가 갖고 있습니다.** `EbsBlockDevice.VolumeSize`의 `documentation`이
규칙적인 HTML 목록입니다 — `gp2: 1 - 16,384 GiB / gp3: 1 - 65,536 / io1: 4 - 16,384 / ...`.
**가장 좋은 산문 파싱 대상이고, Price List가 빠뜨린 최솟값을 담고 있습니다.**

> **그래서 핵심 수는 "교차 검증"입니다.** 두 AWS 공식 소스가 같은 사실을 말하니,
> **불일치를 손 검수로 올리면 됩니다.** 어느 한쪽 파서를 완벽하게 만드는 것보다
> 강한 수입니다 — 감사에서 나온 "확신에 찬 오답"이 정확히 **단일 미검증 소스**에서
> 나오기 때문입니다.

### 2-2. 산문은 피할 수 없다 — 우리 잘못이 아니다

`AWS::EC2::Volume`을 **여섯 가지 기계 판독 표현**으로 추적했더니(CloudFormation 레지스트리,
botocore, Terraform 프로바이더 스키마, Crossplane/Upjet CRD, Pulumi 스키마, KCC)
**여섯 곳 전부에서 조건부 규칙이 `description` 문자열 안의 영어 산문**이었습니다.

CFN 스키마 1,635개 전수 조사(제가 직접 셌습니다):

| 키워드 | 사용 스키마 수 |
|---|---:|
| `if` / `then` / `else` | **0** |
| `dependentSchemas` / `dependentRequired` | **0** |
| `oneOf` | 171 |
| `enum` | 815 |

**0은 우연이 아니라 금지입니다.** AWS 메타스키마가 허용 키워드 목록에서 빼놨고,
문서에 이유까지 적어놨습니다 — "이런 명령형 구성은 작성자에게도 사용자에게도
혼란을 주고, 검증 도구들이 널리 지원하지 않는다."

그리고 `oneOf` 171건은 **값 조건이 아니라 "이것 아니면 저것이 있어야 한다"는 존재 조건**입니다.
전 코퍼스에서 값 판별자와 수치 한도를 같이 쓴 분기는 **단 1건**이었습니다.

**결론: 우리 KB의 표현은 어느 벤더의 스키마보다도 풍부해야 합니다.**
이건 우리가 뭘 잘못해서 생긴 숙제가 아닙니다.

> 유일한 예외는 쿠버네티스 CEL(`x-kubernetes-validations`, 1.29 GA)인데,
> **GCP Config Connector는 586개 CRD 중 74개(12.6%)만 쓰고 그마저 거의 전부
> 불변성(`self == oldSelf`) 표현입니다. 값 범위를 표현한 CEL 규칙은 0건.**
> `maximum:`은 586개 파일 중 **1개**에만 나옵니다.

### 2-3. 형식은 "평평한 reified 레코드"로 수렴한다

여섯 후보를 비교했고, 서로 다른 방향에서 **같은 답**에 도달했습니다.

| | 표현력 | 평가 없이 조회 | 작성 비용 | 출처 기록 | 데이터/코드 |
|---|---|---|---|---|---|
| **평평한 reified JSON** | 무제한 | **최상** | 낮음 | **최상**(제약 1건마다) | 데이터 |
| CUE 논리합 | 좋음 | 가능(검증됨) | 낮음 | 좋음 | 데이터 |
| SHACL Core | 보통 | 나쁨 | **높음** | 좋음 | 데이터 |
| Wikidata 한정어 | **나쁨** | 보통 | 높음 | 최상 | 데이터 |
| Rego | 좋음 | **불가** | 보통 | 규칙 단위만 | 코드 |
| OWL | 모달리티가 틀림 | 나쁨 | 보통 | 나쁨 | 데이터 |
| Cedar | **범위 표현 자체가 불가** | 불가 | 높음 | 없음 | 코드 |

탈락 이유 중 우리에게 특히 중요한 것:

- **Wikidata 한정어**는 부적합합니다. Wikidata 자신의 규칙이 *"한정어를 떼도 문장이
  쓸모 있어야 한다"*인데, `(EBS볼륨, 최대크기, 65536)`은 한정어를 떼면 **6종 중 5종에서
  거짓**입니다. 조건이 정황이 아니라 **정의**라서 그렇습니다. 게다가 한정어는
  **선택 사항**이라, 빠뜨리면 조용히 무조건 65536이 됩니다 — **지금 우리의 실패 모드
  그대로**입니다.
- **CUE**는 introspect가 되지만 `if` 가드에 **fail-open 함정**이 실측으로 확인됐습니다.
  판별자가 아직 구체값이 아니면 comprehension이 **조용히 보류**되어 제약이 아예
  적용되지 않습니다(`Size: 999999`가 통과). 논리합으로 쓰면 이 구멍이 없습니다.
- **Cedar**는 스키마가 타입만 담고 범위를 못 담습니다. **형식 검증까지 된 언어조차
  값 도메인을 스키마에 안 넣었다**는 사실 자체가 우리 질문에 대한 답의 일부입니다.

### 2-4. 도구를 그때그때 늘리지 말라는 건 벤더 문서가 하는 말이다

- **Neo4j가 자사 이익에 반해서** 권고합니다: Text2Cypher는 *"탐색용이나 폴백"*이고,
  복잡하고 자주 쓰는 질의는 *"전용 도구를 둬야 하며, 미리 작성한 파라미터 질의가
  더 안전하고 결정론적"*이라고. 자기네 벤치마크에서 GPT-4o도 파인튜닝 모델도
  일치율 "약 30%"라고 공개합니다.
  → **쓸 만한 규칙: 자주 쓰고 복잡하면 전용 도구, 드물고 단순하면 자유 생성.**
    "언제 도구를 하나 늘릴 자격이 있는가"에 대한 원칙입니다.
- **Anthropic**: 도구 30~50개를 넘으면 선택 능력이 떨어진다. 처방은 **열거가 아니라
  통합** — `list_users`+`list_events`+`create_event`를 `schedule_event` 하나로.
  **CRUD형이 아니라 작업형으로.**
- **OpenAI**: 한 턴에 20개 미만 권장.
- Meta의 chance-corrected 연구는 **보편적 최적 개수는 없다**고 결론냅니다
  (BFCL에서 K=7.4로 K=50과 같은 커버리지).

우리는 지금 도구 16개입니다. **여유가 있지만, 늘리는 기본값을 "통합"으로 잡아야 합니다.**

### 2-5. 그리고 가장 중요한 숫자

dbt가 교란변수를 분리한 **통제 실험**(하네스 공개):

| 조건 | Sonnet 4.6 |
|---|---:|
| 원시 스키마 text-to-SQL | 64.5% |
| **잘 모델링된 테이블** | **90.0%** |
| 시맨틱 레이어 | 98.2% |

**64.5 → 90은 데이터 모델링이고, 90 → 98이 인터페이스 계층의 실제 기여분입니다.**
이 분야 대부분의 주장은 이 격차 전체를 인터페이스 공으로 돌립니다.

> 우리 상황과 정확히 맞물립니다. 우리 KB의 92%가 스키마 모양이고 GCP는 0%인데,
> **질의 계층을 다듬어 얻을 수 있는 건 마지막 8점입니다.**

그리고 **AbstentionBench**(프런티어 모델 20종, 데이터셋 20종):
*"기권은 미해결 문제이며, 모델을 키우는 것은 별 도움이 안 된다."*
→ **불완전한 KB는 "모른다"를 모델에게 위임할 수 없습니다. KB가 신호해야 합니다.**
우리가 침묵을 4종으로 가른 설계(⚠/·/무표시/미빌드)가 옳았다는 독립 근거입니다.

### 2-6. 미리 알아둘 제약

**Anthropic Citations API는 structured outputs와 같이 못 씁니다**(400 에러).
"JSON 스키마에 `citation` 필드를 필수로 걸어 출처를 강제한다"는 흔한 설계가
그쪽에선 **불가능**합니다. 대신 Citations API 자체가 더 강한 보장을 줍니다 —
인용문을 **모델이 생성하는 게 아니라 원문에서 오프셋으로 잘라옵니다.** 표류가 불가능하고,
`cited_text`는 입력·출력 토큰 어느 쪽에도 안 잡힙니다.

## 3. 설계 원칙

조사에서 우리에게 적용할 것을 원칙으로 굳힙니다.

1. **데이터를 저장하고 실행형은 생성한다.** 제약은 평평한 레코드로 두고, 필요하면
   거기서 CUE·SHACL을 굽는다. 로직을 데이터에 섞지 않는다. (기존 `데이터셋 > 파서`의 연장)
2. **없음을 타입으로 표현한다.** Wikibase가 `NoValue`(없다고 단언)와
   `SomeValue`(있는데 모른다)를 **센티널이 아니라 타입**으로 구분합니다. 우리
   센티널 정규화 문제(디스크 0 GiB가 사실인지 결측인지)의 정답이 이것입니다.
3. **"모른다"는 KB가 신호한다.** 모델에게 맡기지 않는다. 이미 하고 있고, 계속한다.
4. **한 사실에 두 소스를 대고, 불일치를 사람에게 올린다.** 파서를 완벽하게 만드는
   대신 교차 검증한다.
5. **도구는 늘리지 말고 통합한다.** 새 도구는 "자주 쓰이고 복잡하다"를 만족할 때만.
6. **출처는 문장 단위로 남긴다.** 어느 원본의 어느 문장에서 왔는지. 그래야 자연어라도
   지어낸 말과 구분된다.

## 4. 레코드 형식

제약 하나를 이렇게 적습니다. **지금 형식에서 바뀌는 건 `condition`과 `provenance`
두 칸뿐입니다** — 나머지는 그대로라 기존 53,657건이 그대로 유효합니다.

```json
{
  "type_id": "aws::AWS::EC2::Volume",
  "property": "Size",
  "kind": "max",
  "value": 16384,
  "unit": "GiB",

  "condition": { "property": "VolumeType", "op": "eq", "value": "gp2" },

  "basis": "stated",
  "reviewed": false,
  "provenance": {
    "source": "aws-price-list",
    "sentence": "maxVolumeSize: 16 TiB",
    "url": "https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonEC2/current/ap-east-2/index.json",
    "retrieved": "2026-07-21",
    "agrees_with": ["botocore-doc"]
  }
}
```

**설계 판단 몇 가지:**

- `backend`: 이 레코드를 만들어낸 상류 파이프라인(`direct`·`tf2crd`·`dcl2crd`).
  값은 소스가 쓰는 말 그대로다. `tier`가 아닌 이유는 위아래를 이름에 박으면
  나중에 판단이 바뀔 때 이름이 거짓이 되기 때문이다 — 이건 등급이 아니라 사실이다.

- `condition`이 **없으면 무조건**입니다. 기존 레코드는 손댈 필요가 없습니다.
- `condition`은 **하나의 평평한 조건**만 담습니다. 중첩·AND/OR를 지금 넣지 않습니다 —
  필요한 사례가 136건 상한이고 그중 다차원은 손에 꼽습니다. 필요해지면 그때
  `conditions: []`로 넓힙니다. (지금 넓히면 그게 오버피팅입니다.)
- **봉투 붕괴를 불변식으로 막습니다.** 같은 `(type_id, property, kind)`에 `condition`이
  있는 레코드와 없는 레코드가 **동시에 존재하면 error**로 막습니다. 지금
  `Volume.Size max=65536`(무조건)과 종류별 값이 공존하면 어느 쪽이 이기는지가
  불명확해지기 때문입니다.
- `provenance.agrees_with`가 **교차 검증 결과**입니다. 두 소스가 같은 값을 말하면
  여기 쌓이고, 다르면 레코드를 만들지 않고 **미결로 보고**합니다.
- **담을 수 없는 규칙은 레코드를 만들지 않습니다.** `provenance.sentence`만 있고
  `value`가 없는 "산문 전용" 레코드를 허용해, 기계 판정에는 안 쓰되 사람·에이전트가
  읽을 수 있게 둡니다. 이게 "칸이냐 자연어냐"의 답입니다 — **같은 레코드가 둘 다
  담되, 칸이 비면 판정에 안 쓴다.**

## 5. 실행 순서 — 데이터 먼저

효과가 큰 순서입니다. 위 두 개가 이번 라운드입니다.

### D1. GCP 용량 수집 — ✅ 완료 (커버율 0% → 92.7%)

`capacitykb/parsers/gcp.py`. graphkb와 **같은 소스·같은 핀·같은 캐시**(`kcc-crd`
v1.153.0)를 씁니다. 결과:

| | 건수 |
|---|---:|
| `required` | 2,394 |
| `mutability`(불변) | 2,003 |
| `enum` / `pattern` / `default` / `max_length` | 13 / 6 / 4 / 1 |
| **`min` · `max`** | **0** |
| **합계** | **4,421건 / 497종** |

**수치 한도는 0건입니다.** 정찰에서 CRD 510개의 `spec` 서브트리를 전수로 세어
확인했습니다(조사자는 "1개 파일"이라 했는데 그건 파일 전체 기준이었고, `spec`
안에는 하나도 없습니다). 그래서 "GCP 한도를 모른다"는 **안 뽑아서가 아니라 원본에
없어서**이고, 그 사실을 파서 docstring과 테스트에 박아 뒀습니다.

**불변성은 두 소스를 다 읽습니다.** KCC는 `Immutable.` 설명문 접두사와 CEL
`self == oldSelf` 두 가지로 표시하는데 실측상 일치하지 않습니다 — 둘 다 55,
**CEL만 19**(접두사가 놓침), 접두사만 2,132. 반대 방향 모순(접두사가 있는데 CEL이
변경 허용)은 **0건**이라 접두사는 누락만 하고 과다 보고는 안 합니다. 그래서
합집합으로 담고 `basis=stated`로 둡니다 — 산문에 있지만 **표기 규약**이지 우리
짐작이 아닙니다.

> **D1이 드러낸 결함 2건도 함께 고쳤습니다.**
> - **제약 0건인 타입이 "타입을 찾을 수 없습니다"로 답했습니다.** 실재하고 우리가
>   읽기까지 한 39종이 그랬습니다. 에이전트가 그대로 옮기면 거짓말입니다.
>   `_coverage`에 `type_ids`를 남기고 이름 해석이 그것도 보게 했습니다.
> - **부모가 이미 불변인데 자식까지 다 나열했습니다.** KCC가 부모·자식 모두에
>   표기해서 2,003건 중 **913건(45.6%)**이 중복이었고, `DataprocWorkflowTemplate`은
>   185줄 중 179줄이 그랬습니다. 표시 단계에서 접고 몇 개를 접었는지 밝힙니다
>   (레코드는 원본 그대로 — 리전 접기와 같은 방식).

### D2. Azure 커버리지 확대 (8.5% → )
지금 네임스페이스 3개만 읽습니다. `bicep-types-az`는 `IntegerType{minValue, maxValue}`로
**진짜 수치 제약을 담을 수 있는** 몇 안 되는 원본입니다. 범위를 넓히는 건 파서 변경이
아니라 목록 변경이라 비용이 낮습니다. `_coverage` 기록도 함께 갱신합니다.

### D3. AWS 실제 한도 — Price List × botocore 교차 검증
새 파서 두 개를 붙이고 **일치할 때만** 레코드를 만듭니다.
- Price List → 최댓값 (구조화, 단위 변환 필요)
- botocore `documentation` → 최솟값·범위 (규칙적 HTML 목록)
- **불일치는 `reviewed` 대기열로.** 조용히 한쪽을 고르지 않습니다.
- 소스 핀: Price List는 계약상 보장이 없으므로 **받은 날짜와 sha256을 박습니다.**

> 여기서 조건부 레코드가 **자연스럽게** 생깁니다. 별도 과제가 아니라 D3의 산물입니다.
> 4건을 위해 설계하는 게 아니라, **소스가 조건부로 주니까 조건부로 받는 것**입니다.

### D4. 쿼터 확대 (52건 → )
AWS Service Quotas API가 기계 판독됩니다. **단, 함정이 있습니다** —
`Storage for gp3 volumes, in TiB = 50`은 **볼륨당 한도처럼 보이지만 계정 총량**입니다.
이걸 볼륨 크기 한도로 잘못 읽으면 정확히 우리가 막으려는 "확신에 찬 오답"이 됩니다.
스코프(계정/리전/리소스당)를 반드시 레코드에 적습니다.

### D5. graphkb의 빈 축 — aws·gcp `contained_in`
관계 종류 하나가 통째로 비어 있습니다(각 0건). 이건 별도 라운드로 둡니다.

### 미루는 것
- **조건부 표현의 일반화**(중첩 조건, 다차원). D3에서 실제로 필요한 모양이
  드러난 뒤에 합니다.
- **CUE/SHACL 생성.** 지금은 소비자가 우리 파이썬 질의뿐이라 얻을 게 없습니다.
  외부에 검증기를 내보낼 일이 생기면 그때.
- **질의 계층 개선.** dbt 숫자대로 마지막 8점입니다. 데이터가 먼저입니다.
- **불변 속성 위험도 정렬**(직전 테스트의 ③). 유효하지만 데이터 확장보다 뒤.

## 6. 이 설계로 무엇이 달라지나

`gp2 볼륨 30,000 GiB` 질문을 예로:

| | 지금 | D3 이후 |
|---|---|---|
| 판정 | 확정 판정 불가 | **불가** (gp2 상한 16,384 위반) |
| 근거 | 설명문(짐작) | Price List × botocore **두 소스 일치**(사실) |
| 조건 | 없음(봉투 1–65,536) | `VolumeType = gp2` |

**지금은 "모르겠으니 문서 보세요"이고, 이후는 "안 됩니다, 상한이 16,384이고 근거는
이것입니다"입니다.** 이게 데이터를 늘려서 얻는 것이지, 프롬프트나 도구로는 못 얻습니다.
