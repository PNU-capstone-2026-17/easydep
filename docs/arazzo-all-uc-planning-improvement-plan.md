# Arazzo 전 UC 계획 생성 개선안 (실험 기준)

## 목표와 현재 증거

> 2026-09-29 추가 확인: UC5는 동결 OpenAPI로도 고정 강좌 ID 재사용, 등록 목록의 동일 항목 선택, 수강 취소까지 Arazzo 구조 컴파일이 가능하다. 이는 HTTP 성공을 뜻하지 않으며, 생성 작업과 선택 기준을 모델이 자동으로 고르는 경로는 아직 미완성이다.

2026-09-29 UC5 소형 실호출 추가 결과: OSS는 등록 항목을 만드는 작업으로 registerForCourse를 골랐고, creator 근거를 먼저 제공하자 기존의 unsupported 대신 목록 조회의 registrationId를 생산자로 선택했다. 그러나 동일한 anchor 선택 함수는 한 호출에서 offering.offeringId를, 다른 호출에서 잘못된 offering.course.courseId를 선택했다. 후보는 두 고정 입력과 16개 목록 매칭 필드의 조합 32개였으며, 잘못된 courseId가 첫 후보였다. 따라서 한 번의 성공은 안정성 증거가 아니다. 생산 경로 연결과 호출되지 않는 실험 함수는 모두 되돌렸다. 동결 클래스 모델에는 각 필드의 고유 참조가 있지만 관리 요청 필드, 등록 입력, 조회 응답 필드의 참조값은 서로 다르다. 필드 고유 참조를 OpenAPI에 보존하는 작은 수정만으로 작업 간 동일 값 관계를 증명할 수 없으므로, 다음 단계는 설계 종료 시 생성 결과의 등록 ID 반환 계약과 실제 값 출처를 함께 확정하는 쪽이다. HTTP 실행은 하지 않았다.

이후 작업은 목록 필드명 비교나 옵션 순서 조정이 아니다. 요구사항의 여러 UC에서 소비하는 자원 ID를 어떤 생성 UC가 공급해야 하는지 OSS가 근거와 함께 제안하고, 설계 생성기는 그 관계를 받아 성공 반환 DTO의 ID 필드와 저장된 Entity ID의 값 출처를 만든다. 설계 종료 검사는 해당 반환 필드·출처가 모두 존재하는지만 결정론적으로 확인한다. 먼저 UC2→UC3·UC5 한 관계를 동결 근거로 소형 실호출 검증한 뒤, 다른 도메인의 생성→조회·수정 관계에도 같은 규칙이 통하는지 확인한다. 그 후 새 시스템 생성 경로의 클래스·API를 만들고 UC3·UC5 계획을 다시 시험한다. 기존 산출물을 직접 수정하지 않는다.

후속 소형 검증에서는 클래스 연산 생성기에 다른 UC의 식별자 입력 목록을 제공했다. 예전 보고서 스냅샷에는 해당 필수값 계약이 없었으므로 첫 UC2 호출은 판단 근거가 되지 않는다. 계약이 들어 있는 동결 체크포인트로 다시 호출했을 때도 OSS는 registrationResult 문자열만 반환했다. 이어 현재 inventory 생성기를 실제 OSS로 한 번 실행하니 Registration Entity를 UC2에 연결했고, 그 inventory에서 UC2 연산을 다시 생성해도 공개 반환은 registrationResult 문자열뿐이었다. 즉 Entity 후보 누락만 고쳐서는 해결되지 않으며, 교차 UC 수요를 단순 참고자료로 붙이는 방식도 효과가 없었다. 이 실험용 프롬프트·payload 코드는 되돌렸다. 다음 수리 지점은 클래스 생성기가 아니라 전 UC 요구사항 계약을 확정하는 시점의 공급·소비 관계 검토다.

교차 UC 계약 검토의 OSS 소형 실호출도 진행했다. UC2·UC3·UC5의 전체 명세와 정확한 단계 ID를 함께 주면 UC2의 새 등록 ID 반환을 제안하고 실제 `UC2:main:3`·`RR3`을 인용했다. UC7·UC8에서는 기존 반환 ID가 있으므로 수정 제안이 없었다. 그러나 11개 UC 전체를 한 번에 상세 검토시키면 UC2 누락을 놓치고 기존 UC7 출력을 중복 제안하거나 수정이 없다고 답했다. 따라서 전역 단일 검토는 채택하지 않는다. 11개 UC의 짧은 목표와 7개 소비 식별자만 준 후보 검색은 UC3·UC5의 등록 ID 후보 생산자로 UC2를 찾았다. 그 후보를 명시한 두 UC 쌍의 상세 검토에서는 UC2→UC3과 UC2→UC5 모두 ID 반환 누락을 찾았고, UC11→UC2는 생성 작업의 호출자 입력으로 강좌 ID가 이미 주어져 추가 결과가 불필요하다고 판단했다. 이는 `openai/gpt-oss-120b`의 요구사항 계약 제안 실험일 뿐이며, 요구사항 생성기에 연결되거나 새 설계·구현·Arazzo HTTP 테스트가 통과한 것은 아니다. 모델의 제안은 실제 UC·단계·필수값·요구사항 참조와 기존 출력에 대해 검증해야 한다.

이후 `check_specs`에 후보 검색→후보쌍 상세 검토를 연결하고 동결 명세를 입력으로 실제 OSS를 호출했다. 첫 시도는 모델이 새 `value_ref`를 임의 작성하는 응답 칸 때문에 제안이 거부됐다. 참조 생성은 모델이 아니라 코드에 맡기도록 그 칸을 제거한 뒤 다시 호출하니 UC2에 `registration_id` 식별자 결과가 정확히 하나 추가됐다. UC5 검토는 이미 추가된 결과 참조를 사용했고 UC7·UC11에는 새 결과를 추가하지 않았다. 별도 합성 고객지원 도메인의 티켓 생성→종료에서도 생성 UC에 `ticket_id` 결과 하나를 제안했다. 이는 요구사항 단계의 소형 실호출과 집중 테스트 결과이며, 이후 클래스/시퀀스/API 생성기가 새 계약을 실제 반환 타입과 값 출처로 옮기는지는 아직 검증하지 않았다. 기존 동결 산출물과 DB는 수정하지 않았다.

뒤이어 같은 동결 근거로 클래스 단계까지 이어 본 추가 표본은 반대 결과였다. 후보 검색이 UC2→UC3·UC5 쌍을 아예 제안하지 않아 상세 검토가 0회 실행됐고, UC2 요구사항 계약에는 식별자 결과가 추가되지 않았다. Inventory는 한 차례 수리 뒤 Registration Entity를 UC2 범위에 포함했지만, UC2 연산의 실제 OSS 제안은 `RegistrationResult { result: String }`만 반환했다. 즉 이 표본의 반환 ID 누락은 클래스 단계가 새 계약을 무시했다는 증거가 아니라, 앞선 후보 검색의 false negative가 그대로 전달된 결과다. 후보 검색은 최종 판정이 아닌 재현율 높은 검색으로 취급하고, 쌍별 상세 검토에서만 추가 여부를 판단하도록 조정한 뒤 재검증한다. 첫 클래스 probe는 모듈 순환 import로 모델 호출 전에 막혔으며, `design.contracts`의 배포 export를 lazy loading으로 바꿔 import와 inventory 집중 테스트 1건이 통과한 후 재개했다.

목표는 16개 요구사항 수강신청 앱의 11개 UC 각각에 대해, 동결된 설계 근거에서 실행 가능한 Arazzo 계획을 만들고 검증하는 것이다. 구조 검증 통과와 실제 HTTP 테스트 통과는 별개로 기록한다. 생성 앱·DB·동결 산출물을 직접 고치거나, 불가능한 연결을 데모 성공으로 처리하지 않는다.

- 2026-09-29 계획 전용 실모델 1회 순회: 11개 후보, `openai/gpt-oss-120b`, 57.015초. 출력이 보존된 것 중 UC1·UC6·UC7·UC9·UC10·UC11은 **구조 검증만** 통과했고, UC2·UC3·UC8은 실패했다. UC4·UC5 결과는 콘솔 출력 잘림으로 보존되지 않았다. 상세 근거는 `arazzo-fixed-plan-checkpoint-20260929.md`에 있다.
- 대상 UC의 공개 값 계약과 배열 표시를 기존 그래프 프롬프트에 더하는 실험은 UC2·UC8의 실패를 바꾸지 못했다. 이 패치는 되돌렸다. 근거 문구를 더 쌓는 것만으로 해결된다고 주장하지 않는다.
- UC5 등록 성공 응답을 메모리에서만 `{registrationId: string(uuid)}`로 바꾼 단일 전체 계획 호출은 다른 준비 입력 문제에서 먼저 실패했다. 다만 작업 순서를 고정한 작은 OSS 호출에서는 모델이 새 `registrationId` 출력을 선택했고, 타입 호환성도 확인됐다. 이는 **해당 연결 한 곳의 결과**이며 전체 UC5 성공 증거가 아니다.
- 현재 동결 UC2의 결과는 클래스·API 단계부터 단순 `String`이고, 실제 구현은 설명 문장을 반환한다. UC3·UC5의 등록 ID를 이 응답에서 UUID로 안전하게 추출할 계약은 없다. 목록 `[0]`도 항목 존재와 생성 대상의 신원을 보장하지 않는다. 반면 UC7의 대기열 등록 201 응답은 `uuid`이므로 UC8에는 직접 ID 출력 후보가 있다.
- 목표 입력별 후보만 준 동일한 생산자 선택 실호출 3건에서 OSS는 UC2의 강좌 ID에 `manageCourseOffering.offeringId`, UC8의 대기열 항목 ID에 `joinWaitlist` 201 응답을 선택했고, 동결 UC3의 등록 ID는 `unsupported`로 분류했다. 이 결과는 후보 선택 단계의 증거일 뿐, 전체 그래프/리터럴/HTTP 성공이 아니다. 특히 UC2의 `offeringId`는 현 OpenAPI에서 선택 필드이므로 응답 경로의 존재와 값의 존재 보장을 혼동하지 않는다.
- 선택된 준비 작업만 남긴 계획 전용 실호출에서 UC2는 `manageCourseOffering(create) → registerForCourse`로 Arazzo/OpenAPI 구조 검증까지 통과했다. UC8은 `joinWaitlist`를 제공해도 모델이 다시 `viewWaitlistEntries[0]`을 취소 ID로 골라 실패했다. 즉 후보 축소만으로는 충분하지 않고, 모델이 먼저 고른 출처를 다음 그래프 단계에 강제·검증해야 한다. 두 결과 모두 앱 HTTP 결과는 아니다.
- UC8에서 앞서 선택된 두 출처를 잠근 임시 그래프(`manageCourseOffering → joinWaitlist → viewWaitlistEntries → cancelWaitlistEntry`)는 한 번의 OSS 리터럴 호출 뒤 Arazzo/OpenAPI 구조 검증을 통과했다. 그러나 선택된 정원 30명만으로는 “만석 강좌의 대기열” 선행조건이 성립하지 않고, 강좌 ID 출력도 여전히 선택 필드다. 이는 그래프 컴파일 경로의 가능성을 보인 것뿐이며 **실행 가능한 UC8 성공 계획의 증거는 아니다**.
- 생성 앱 원문 조사에서는 더 근본적인 불일치가 확인됐다. UC7 요구는 만석·대기열 활성화·등록 거절 이후 가입이지만, 생성된 `addToWaitlist`는 강좌 존재만 검사하며 `waitlistEnabled` 상태 자체가 없다. 따라서 현재 공개 API의 생성→대기열 가입→취소는 HTTP로 실행할 수 있어도 UC7의 요구 의미를 검증하지 못한다. 이 문제는 테스팅 계획기에서 임의 fixture나 성공 판정으로 메울 수 없고 설계·구현 계약의 별도 결함으로 다룬다.
- 동결 OpenAPI를 수정하지 않고 **메모리 사본에서만** 등록 201 응답을 필수 `{registrationId: string(uuid)}`로 바꿔, 앞서 모델이 선택한 생산자를 잠근 UC3·UC5 그래프를 컴파일했다. UC5·UC3 모두 실제 OSS 리터럴 호출 한 번씩 뒤 Arazzo/OpenAPI 구조 검증을 통과했다. UC3에서는 두 강좌 생성의 `operationType=create`와 서로 다른 강좌 ID도 확인했다. 이는 계약+출처 고정 방식의 국소 가능성 증거이지, 현 설계·자동 계획·실제 구현의 통과 증거가 아니다.
- 첫 순회에서 출력이 보존되지 않았던 UC4를 같은 생산 계획 경로로 한 번 더 호출했다. `viewRegistrationsAndSchedule` 한 단계 계획이 Arazzo/OpenAPI 구조 검증을 통과했다(OSS 1회, 전체 5.186초). UC5는 앞선 별도 생산 경로 실호출에서 보장되지 않은 `registrationList[0]` 연결 때문에 실패한 것이 확인돼 있다.

### 11개 UC별 현재 경계

| UC | 현 동결 계약의 관찰 결과 | 다음에 필요한 확인 또는 보완 |
|---|---|---|
| UC1 | 구조 통과 | 실제 검색 응답·시나리오 의미 확인 |
| UC2 | 기본 계획 실패; 생산자 후보 축소 시 구조 통과 | `offeringId`의 create 분기 값 존재 보장과 출처 선택의 생산 경로 통합 |
| UC3 | 기본 계획 실패; 등록 ID 출처 계약 없음 | 등록 ID 계약 보완 후 반복 강좌 두 인스턴스·차이 관계를 자동 그래프에 고정 |
| UC4 | 구조 통과 | 조회 응답·시나리오 의미 확인 |
| UC5 | 기본 계획에서 보장되지 않은 목록 `[0]` 연결로 실패 | 등록 ID 계약 보완, 직접 반환 ID를 삭제 입력에 연결 |
| UC6 | 구조 통과 | 실제 실행 의미 확인 |
| UC7 | 구조 통과 | 만석·대기열 활성화·등록 거절 조건이 설계와 구현에서 실제로 성립하도록 보완 |
| UC8 | 기본 계획 실패; 출처 고정 임시 그래프는 구조 통과 | `joinWaitlist` 반환 ID를 취소 입력에 고정하고 UC7 선행 상태 문제 해결 |
| UC9 | 구조 통과 | 실제 실행 의미 확인 |
| UC10 | 구조 통과 | 실제 실행 의미 확인 |
| UC11 | 구조 통과 | create/update/publish/cancel 분기와 반환값 보장 확인 |

여기서 “구조 통과”는 계획 문서의 Arazzo/OpenAPI 검증 결과일 뿐이다. 어느 행도 HTTP 성공이나 요구사항 충족으로 간주하지 않는다. UC5 결과는 첫 11개 순회 출력이 잘려서 그보다 앞선 동일 생산 경로의 별도 호출에 근거한다.

## 개선 경계

1. **설계 종료 전 식별자 획득 경로를 명확히 한다.** 뒤따르는 UC가 리소스 ID를 필요로 하면, 설계 생성기는 관련 UC·RTM·클래스/API 근거로 생성 결과의 식별자 반환 또는 유일하게 선택할 수 있는 조회 계약을 결정한다. 결과 계약에는 리소스 종류, 생성 작업, 응답 경로, 타입, 성공 분기에서의 존재 보장을 남긴다. 제품 의미에 실제 선택이 남을 때에만 EasyDep가 근거 있는 사용자 질문을 만든다. UC 이름에 따른 고정 규칙이나 EasyDep 관리 DB 스키마 변경은 하지 않는다.
   UC7처럼 선행 상태 자체가 필요한 경우에는 그 상태를 만드는 공개 작업 또는 명시적 테스트 환경 fixture와, 구현의 가드가 동일한 근거를 따르는지도 설계 종료 전에 확인한다. 현재 생성 앱의 누락을 Arazzo 계획만 수정해 숨기지 않는다.
2. **계획기는 값 출처를 먼저 정한 뒤 그래프를 닫는다.** 각 목표 입력에 대해 타입이 맞는 상태 변경 작업의 출력만 작은 후보군으로 제시하고, LLM이 유스케이스 의미를 근거로 출처 또는 `unsupported`를 고르게 한다. 선택된 작업의 필수 입력을 재귀적으로 해소해 순서와 반복 인스턴스를 고정한 뒤 Arazzo로 컴파일한다. 결정론적 코드는 원본 operation/출력 참조, 타입, 순서, 스키마 보장만 검사한다. 같은 형식의 UUID라는 이유만으로 리소스 신원을 같다고 보지 않는다.
3. **실행 중 임의 값 보충은 하지 않는다.** 리터럴은 계획 생성 시 확정하고, 기존 리소스의 ID는 앞선 응답 또는 명시적 fixture에서만 얻는다. 목록의 첫 항목은 생성된 대상이라는 근거가 아니며, 사용할 경우 계약이 보장하는 선택 조건과 런타임 확인이 필요하다. 근거가 없으면 해당 계획을 TEST_DEFECT로 남기고 다른 UC의 유효한 계획은 계속 처리한다.

## 실험·수용 순서

1. 동결 UC2·UC8의 목표 ID와 동결 UC3의 등록 ID를 같은 작은 생산자 선택 형식으로 OSS에 각각 한 번 묻는다. 선택한 operation/출력이 원본 카탈로그에 있고 타입과 의미가 맞는지 검사한다. 이 단계의 한 차례 실험은 위와 같이 끝났으며, UC2 출력 존재 보장과 UC3 계약 빈틈은 남아 있다.
2. 성공한 생산자 선택에 한하여 UC2·UC8의 선택 작업을 고정한 작은 실제 모델 그래프 호출을 한다. 관련 UC 외의 전역 11개 재실행은 하지 않는다. UC3·UC5는 응답 계약이 빈틈없이 만들어지는지 별도 소규모 설계 실호출로 먼저 검증한다.
3. 설계 생성기 보완이 실호출과 집중 검증을 통과하면 새 설계/API/구현 산출물을 **시스템 경로로** 다시 만든다. 이전 체크포인트의 파일을 수동 편집하지 않는다. 계획 전용 11개 순회를 출력 파일에 완전히 보존하고, 각 UC의 구조 통과와 리소스 신원·분기 의미를 따로 검토한다.
4. 11개 계획이 실제로 유효해진 뒤에만 Workspace API의 Testing-only 실행으로 HTTP 결과를 확인한다. 계획 통과를 Testing 통과라고 보고하지 않는다.

한 실험에서 실패 위치만 이동하면 국소 가드나 프롬프트 문구를 연속 추가하지 않는다. 원인과 결과를 기록하고 계약 보완, 후보 축소, 또는 `unsupported`로 방향을 바꾼다.

## 2026-09-29 추가 검토: 11개 완료 전 중단 지점

- Astra 독립 검토에서 계획기의 전역 `guaranteed` 우선 필터가 의미상 맞는 선택적 출력을 후보에서 제거할 수 있음을 확인했다. 실험에서는 필터를 제거하고, 선택적 출력에 `success == true` 및 응답 값의 non-null 실행 조건을 붙였다. 집중 실행기 검사에서는 false·null·필드 누락 시 후속 HTTP 호출이 차단됐다. 하지만 이 실험은 계획 생성 개선을 입증하지 못해 생산 코드는 되돌린다.
- 동결 UC8의 `joinWaitlist.path:offeringId` 후보에 `manageCourseOffering.bodyOfferingId`가 남는 것은 결정론적으로 확인했다. 그러나 변경 후 정상 계획 경로의 단일 OSS 호출은 첫 입력인 `cancelWaitlistEntry.path:waitlistEntryId`에서 `unsupported`를 반환했다. 그래프·리터럴 생성은 시작되지 않았다. 이어진 UC2 회귀 실호출은 잘못된 `joinWaitlist.bodyValue`를 강좌 ID 생산자로 선택한 뒤 다음 입력에서 `unsupported`로 실패했다. 결과는 각각 `tmp/uc8_guarded_plan_probe_20260929.json`, `tmp/uc2_guarded_plan_regression_20260929.json`에 보존했다.

- 그 계약을 클래스 조각 생성에 시험했지만, 생성된 Boundary/Control 성공 반환과 저장된 Entity ID 사이의 값 출처가 증명되지 않았고 기존 검사는 Boundary에 노출된 server-context 학생 ID를 거부했다. 한 번의 수리도 같은 오류를 반복했다. 시험용 클래스 계약 코드는 되돌렸다. 따라서 UC3·UC5를 현재 동결 설계로 안전하게 통과시키려는 계획기 수정은 중단한다.
