# EasyDep 중간 개발 보고서

> 기준일: 2026년 8월 10일
>
> 범위: AWS·Azure·GCP의 Docker-on-Linux-VM 배포
> 이 문서는 현재까지 구현하고 측정한 결과를 요약한다. `research.md`는 변경하지 않는다.

## 1. 과제의 큰 그림

EasyDep은 요구사항을 분석하고 설계·코드·테스트를 만드는 기존 개발 지원 시스템에 클라우드 배포
지원을 더하고 있다. 목표는 Terraform 파일을 만드는 데서 끝나지 않는다.

```text
사용자 요구
  → 앱 설계와 구현
  → 필요한 클라우드 기능 결정
  → CSP별 리소스군과 연결 관계 생성
  → 앱과 배포 환경의 불일치 검사
  → 앱 사용량에 맞는 VM 후보 선택
  → 실제 배포와 업무 기능 확인
```

현재 연구 범위는 Linux VM에서 Docker 앱을 실행하는 경우다. Kubernetes, Serverless, 관리형 DB
등 모든 클라우드 서비스를 포괄하는 모델은 목표가 아니다.

## 2. 현재 시스템 상태

### 구현된 부분

- 요구사항 분석, 설계, 앱 골격, 테스트, 업무 로직 생성
- AWS·Azure·GCP VM 리소스 관계 지식의 저장과 조회
- 앱 요구를 영속 저장소·부하분산·HTTPS 같은 배포 기능과 연결
- 배포 기능을 CSP별 Terraform 리소스군으로 변환
- Terraform 구성요소와 명시적 참조 검사
- 앱의 빌드 의존성·포트·저장 경로와 배포 설정 비교
- 실패를 소유한 하위 작업부터 다시 실행하는 체크포인트 복구
- 앱 CPU·메모리 측정과 VM 카탈로그 기반 후보 선택
- 하위 작업, LLM 호출, 빌드와 검증 시간 기록
- 실제 cloud 실험 뒤 삭제와 잔여 리소스 확인 절차

구현 단계는 `scaffold → acceptance_tests → logic → vm_selection → vm_delivery`로 나뉜다. 입력과
시스템 로직이 바뀌지 않았다면 요구사항부터 다시 실행하지 않고, 마지막 성공 체크포인트에서 실패한
작업만 다시 실행한다.

### 클라우드 네이티브 애플리케이션은 어떤 순서로 개발하는가

여기서 말하는 개발 순서는 모든 클라우드 네이티브 개발 방법론의 보편적인 표준이 아니라, 현재
EasyDep이 Docker-on-Linux-VM 애플리케이션을 만드는 실제 실행 순서다. 상위 단계는 요구사항,
설계, 구현, 내부 테스트의 네 단계이며, 실제 클라우드 배포·업무 기능 확인은 생성 시스템과 분리된
공통 외부 평가에서 수행한다.

```text
사용자 요구사항
  → 1. 요구사항 분석
  → 2. 애플리케이션·클라우드 설계
  → 3. 애플리케이션·배포 구현
  → 4. 생성 애플리케이션 내부 테스트
  → 5. 실제 클라우드 종단 검증
  → 실패 원인을 소유한 하위 작업만 수정·재실행
```

| 순서 | 단계와 하위 작업 | 주요 내용 | 다음 단계에 전달하는 결과 |
|---:|---|---|---|
| 1 | `requirements.analysis` | 자연어 요구를 기능·비기능 요구, 사용자·사용 사례, 배포 요구, CSP·리전·예산·최소 용량 조건으로 정리한다. 정보가 부족하거나 충돌하면 추측하지 않고 질문·보류한다. | 정제 요구사항, 사용 사례, `resource_spec`, 배포 capability 후보 |
| 2-1 | `design.architecture` | 애플리케이션의 클래스, 호출 순서, API, 데이터 구조를 설계한다. | 클래스·시퀀스·OpenAPI·ERD 산출물 |
| 2-2 | `design.cloud_enrichment` | 승인된 capability를 DepKB의 CSP별 리소스군과 의존관계로 투영한다. 앱 요구와 클라우드 계약도 이 경계에서 구성한다. | 배포 다이어그램, 중립 의도, CSP별 의존성 계획, 모델링되지 않은 요구 목록 |
| 3-1 | `implementation.scaffold` | 멤버 구현 시스템이 설계 계약으로 프로젝트 골격과 애플리케이션 구성요소를 생성하고 빌드 가능한지 확인한다. | 소스·설정·빌드 파일과 멤버 workflow 상태 |
| 3-2 | `implementation.acceptance_tests` | 멤버 구현에 아직 없는 경우에만 요구사항과 API 계약에 따른 수용 테스트를 만든다. 이후 업무 로직 작업은 이 테스트를 수정할 수 없다. | 고정된 수용 테스트 파일 목록 |
| 3-3 | `implementation.logic` | 멤버 구현이 남긴 업무 로직 공백을 보완한다. 앱·클라우드 계약 검사에서 발견된 빌드 의존성, 포트, 저장 경로 등의 앱 측 불일치도 이 작업 또는 해당 소유 작업으로 돌린다. | 완성된 업무 코드와 앱 런타임 계약 |
| 3-4 | `implementation.vm_selection` | 측정값 또는 사용자가 명시한 최소 vCPU·메모리·아키텍처·예산으로 CSP·리전의 VM 후보를 결정론적으로 고른다. 근거가 없으면 성능을 추측하지 않고 보류한다. | 선택 VM과 선택·경고 근거 |
| 3-5 | `implementation.vm_delivery` | 선택 VM과 의존성 계획으로 Docker 실행 설정, cloud-init과 CSP별 Terraform을 생성한다. provider 초기화·검증과 앱 포트·mount 등 배포 계약 일치 여부를 확인한다. | Docker/VM 배포 파일, Terraform, 정적 검증 결과 |
| 4 | `testing.application` | 생성 저장소의 Java/Kotlin 테스트를 고정 Linux 실행환경에서 수행한다. 컴파일 실패와 테스트 실패의 파일·소유 작업을 식별한다. | 내부 테스트 결과와 구조화된 수리 진단 |
| 5 | 공통 외부 종단 검증 | 생성 시스템이 수정할 수 없는 평가기가 `validate/plan → apply → ready → 업무 API → 재시작·장애 시험 → destroy → 잔여 리소스 0`을 확인한다. | 실제 생성 가능성, 앱 기능 성공, 시간·비용·정리 결과 |

`implementation.scaffold` 안의 작업은 애플리케이션 설계에 따라 달라진다. 현재 구현 시스템은 필요한
경우 다음과 같이 더 작은 작업으로 나누고, 각 작업 산출물을 컴파일·테스트한 뒤 합친다.

```text
Control 구현
  → 영속 계층(Entity → Repository → Mapper → Schema)
  → API adapter와 Boundary adapter
  → Spring application wiring
  → Frontend
  → End-to-end 업무 흐름
```

영속성이 없는 앱에는 영속 계층 작업이 없어도 되고, 화면이 없는 API에는 Frontend 작업이 없어도
된다. 즉 이 목록은 특정 P1 사례를 모든 앱에 강제하는 고정 템플릿이 아니라, 설계 산출물에서 필요한
작업만 만드는 조건부 작업 그래프다.

단계별 분리는 실패했을 때 처음부터 다시 만드는 비용을 줄이기 위한 것이다. 예를 들어 Terraform
참조가 잘못되면 `vm_delivery`부터, 업무 코드가 수용 테스트를 만족하지 못하면 `logic`부터,
멤버가 만든 프로덕션 코드와 내부 테스트의 계약이 서로 달라지면 `scaffold` 경계부터 다시 실행한다.
완료된 요구사항·설계와 무관한 구현 작업은 체크포인트에 남긴다. 다만 현재 멤버 구현 내부의 세부
체크포인트 재사용은 충분하지 않아 `scaffold` 수리 시 내부 작업을 넓게 재생성하는 경우가 있으며,
이는 현재 확인된 효율 개선 대상이다.

### 아직 부족한 부분

- 새로 생성한 앱을 세 CSP에서 모두 실제 배포하고 외부 업무 API까지 확인한 종단 성공
- `apply → ready → 업무 API → 재시작 또는 장애 시험 → destroy`의 반복 결과
- DepKB가 실제 cloud 앱 기능 성공률을 높인다는 비교 결과
- 앱–클라우드 검사기의 충분한 반복 비교
- 로컬 용량 측정을 실제 CSP VM에서 다시 확인하는 과정
- 디스크·네트워크·로드밸런서를 포함한 전체 비용 계산

따라서 현재 시스템은 핵심 구성과 개발 실험은 갖췄지만, 세 CSP의 안정적인 종단 배포가 완료된
상태는 아니다.

## 3. 클라우드 리소스 의존성 분석

### 3.1 어떻게 조사했는가

공식 문서와 API schema에서 관계 후보를 찾은 뒤 세 CSP에서 직접 생성·삭제·기능 변경을 실행했다.

| 실험 | 확인한 질문 |
|---|---|
| 생성 | 대상을 생략하거나 잘못 지정해도 리소스를 만들 수 있는가 |
| 삭제 | 사용 중인 대상을 삭제할 때 CSP가 막는가 |
| 기능 | 관계를 제거하면 외부 접속·저장·신원·부하분산 기능이 실패하는가 |

총 56개의 관계를 관측했다.

| CSP | 생성 | 삭제·수명주기 | 기능 | 합계 |
|---|---:|---:|---:|---:|
| AWS | 12 | 3 | 5 | 20 |
| Azure | 12 | 5 | 4 | 21 |
| GCP | 9 | 3 | 3 | 15 |
| 합계 | 33 | 11 | 12 | 56 |

49개는 반복 실행에서 다시 확인됐고, 2개는 확인 대기, 5개는 같은 결과를 다시 얻지 못했다. 반복
실패 5개는 전파 지연과 상태 확인 시점에 민감한 실행 중 기능 실험이었다. 이 항목들은 확정 규칙에
넣지 않았다.

### 3.2 무엇을 알게 됐는가

- 리소스 생성 성공과 앱 기능 성공은 다르다.
- CSP 기본값 때문에 생략 가능한 리소스도 명시적 배포에서는 필요할 수 있다.
- 같은 역할도 CSP마다 연결 위치가 다르다.
- public/private 구성에 따라 합법적인 리소스군이 여러 개일 수 있다.
- 생성 순서뿐 아니라 안전한 삭제 순서도 의존관계에 포함된다.

예를 들어 방화벽은 AWS에서는 Security Group을 VM 또는 NIC에 연결하고, Azure에서는 NSG를 NIC나
subnet에 연결하며, GCP에서는 network 범위의 Firewall Rule로 적용한다. 공통 이름 하나로 이 차이를
없애면 실제 배포 관계를 잘못 표현하게 된다.

56개 관측은 EasyDep의 성능 평가가 아니라 모델을 만들기 위한 기초 자료다. 이 가운데 공식 근거와
반복 상태가 충분한 일부 관계만 설계 입력으로 사용한다.

## 4. 벤더 중립 배포 기능은 왜 필요한가

사용자는 보통 `aws_ebs_volume`이나 `google_compute_backend_service` 같은 리소스 이름이 아니라
“재시작 후에도 데이터가 남아야 한다” 또는 “여러 서버로 요청을 분산해야 한다”처럼 원하는 결과를
말한다. 요구를 곧바로 벤더 리소스에 연결하면 사용자 의도와 구현 방법이 섞인다.

EasyDep은 그 사이에 배포 기능을 둔다.

```text
“재시작 뒤에도 데이터가 남아야 한다”
          ↓
영속 블록 저장소
          ↓
AWS: EBS + 연결 + mount
Azure: Managed Disk + 연결 + mount
GCP: Persistent Disk + 연결 + mount
          ↓
쓰기 → 재시작 → 같은 데이터 조회
```

이 배포 기능은 모든 CSP를 같은 리소스 모양으로 만드는 공통 schema가 아니다. 사용자 요구를
CSP별로 서로 다른 리소스군과 연결하기 위한 중간 기준이다.

### 4.1 현재 배포 기능은 어떻게 정했는가

현재 세 기능은 56개 관계를 묶어 자동으로 발견한 것이 아니다. 다음 조건을 확인해 개발 대상으로
선정했다.

1. 사용자에게 보이는 결과를 분명한 문장으로 설명할 수 있는가
2. 성공과 실패를 앱 기능 시험으로 구분할 수 있는가
3. AWS·Azure·GCP에서 실제 구성 방법을 공식 문서로 확인할 수 있는가
4. CSP마다 구현 구조가 달라 중간 연결 계층이 필요한가
5. Cloud-Barista·OCCI 같은 기존 중립 모델에서 관련 개념을 찾을 수 있는가

| 배포 기능 | 사용자에게 보이는 결과 | CSP별 차이 |
|---|---|---|
| 영속 블록 저장소 | 재시작 뒤에도 데이터가 남음 | 디스크와 VM 연결 방식이 다름 |
| HTTP 부하분산 | 여러 backend로 요청을 전달함 | LB 구성요소와 리소스 경계가 다름 |
| HTTPS 종료 | 암호화된 진입점으로 업무 API를 제공함 | listener·proxy·인증서 연결이 다름 |

Cloud-Barista와 OCCI에서는 compute, storage, storage attachment, network, load balancer, listener,
backend group, health check 개념을 참고했다. TOSCA에서는 요구와 제공 기능을 분리하는 표현 방식을
참고했다. 기존 모델을 그대로 복사하거나 EasyDep이 TOSCA 호환이라고 주장하지는 않는다.

### 4.2 LLM의 역할

LLM은 새로운 배포 기능을 즉석에서 발명하지 않는다.

1. 요구문에서 근거가 되는 문장을 찾는다.
2. 근거가 확인된 기존 배포 기능 후보와 연결한다.
3. 후보가 여러 개이거나 정보가 부족하면 질문한다.
4. CSP별 구성은 DepKB에서 조회한다.

새 배포 기능을 추가하려면 사용자에게 보이는 결과, 독립 기능 시험, 공식 문서, CSP별 변환을 먼저
정의해야 한다. 현재는 기능 목록을 계속 늘리기보다 세 기능을 실제 종단 배포까지 연결하는 것이
우선이다.

## 5. 의존성 지식의 효과는 어떻게 측정했는가

### 정적 누락 검사

고정 공급자 시험 자료의 구조 참조 31개를 모두 읽었고, 각 참조를 하나씩 제거한 시험에서도 제거한
참조 31/31을 찾아냈다. 제거하지 않은 참조의 상태 변화는 없었다.

이 결과는 평가기가 정해진 시험 자료의 누락을 찾는다는 뜻이다. 실제 생성이나 앱 기능 성공을
보장하지는 않는다.

### 같은 입력에서 DepKB만 제거한 비교

같은 앱과 요구분석 결과를 사용하고 DepKB만 제공하거나 제거했다. `no-depkb`는 개선 대상이 아니라
비교를 위한 대조 조건이다.

- 기능: 영속 저장소, 다중 VM 부하분산, HTTPS 종료
- CSP: AWS, Azure, GCP
- 반복: 3회
- 총 54셀
- 요구사항·설계·앱 생성 LLM 호출: 0회
- 실제 cloud 생성: 수행하지 않음

| 지표 | DepKB 사용 | DepKB 제거 | 차이 |
|---|---:|---:|---:|
| 배포 파일 생성 완료 | 20/27 | 15/27 | +5셀 |
| 필요한 참조까지 완성 | 14/27 | 8/27 | +6셀 |
| 필요한 참조를 찾은 평균 비율 | 0.677 | 0.503 | +0.173 |

영속 저장소에서는 차이가 없었고 다중 VM 부하분산에서 가장 큰 차이가 나타났다. 세 번째 반복에서는
평균 차이가 반대로 나타났다. 제한된 개발 사례의 평균 결과는 좋아졌지만, 모든 CSP와 기능에서
안정적인 효과가 있다고 말할 수는 없다.

### 실제 cloud 확인

GCP의 `backend service → backend group` 관계를 제거하고 복원하는 실험을 세 번 수행했다. 정상
구성에서는 업무 기능이 성공했고, 참조를 제거하면 실패했으며, 복원하면 다시 성공했다. 삭제 뒤
잔여 리소스는 0이었다. 이는 해당 GCP 구성의 한 관계에 대한 직접 증거이며 다른 관계나 CSP로
확대하지 않는다.

54셀 결과에서 고른 AWS 후보는 `plan`을 통과했지만 실제 생성에서 실패했다. ALB에 subnet과 AZ가
하나만 전달됐고, 지정한 AMI가 선택한 리전에 없었다. 앱 기능에는 도달하지 못했다. 실패 뒤 삭제는
13.5초에 끝났고 잔여 리소스는 0이었다.

이 결과는 정적 참조가 맞아도 리소스 개수, 배치, 리전별 값, 실제 앱 기능을 따로 확인해야 한다는
점을 보여준다.

## 6. 앱과 클라우드 환경의 불일치

앱과 Terraform이 각각 정상처럼 보여도 함께 실행하면 실패할 수 있다.

| 불일치 | 예시 |
|---|---|
| 빌드·실행 의존성 | 코드가 사용하는 라이브러리가 build 파일에 없음 |
| 포트 | 앱, container, 방화벽, LB backend 포트가 다름 |
| 저장 경로 | disk는 있지만 앱 경로가 container mount 밖에 있음 |
| 상태와 가용성 | 로컬 상태를 쓰면서 여러 active VM을 요구함 |
| 상태 확인 | 앱 health 경로와 LB 확인 경로가 다름 |
| HTTPS | TLS 종료 위치와 앱의 HTTP/HTTPS 기대가 다름 |

EasyDep은 앱이 요구하는 사실, cloud가 제공해야 할 기능, 두 값을 연결한 배포 설정을 따로 기록하고
비교한다. 불일치를 찾으면 문제를 소유한 하위 작업만 다시 실행한다.

고정된 네 종류의 불일치 시험에서는 불일치 4/4를 조기에 찾았고, 정상 입력 오탐은 0/4, 수정할
하위 작업 선택은 4/4였다. 최신 수정 실행에서는 빌드 의존성과 포트 사례가 앱 테스트까지 통과했고,
저장 경로 사례는 한 번 수정한 뒤에도 실패했다. 특정 경로 예외를 추가하지 않고 현재 한계로 남겼다.

정보가 부족하거나 충돌하면 임의로 채우지 않고 질문하거나 보류한다.

## 7. 앱이 요구하는 클라우드 환경 조건

다음 값이 리소스군과 배포 결과를 바꾼다.

| 구분 | 확인할 내용 |
|---|---|
| 실행 | CPU 아키텍처, 최소 vCPU·메모리, 런타임, 환경변수, listen port |
| 저장 | 영속성 여부, 앱 경로, container 경로, guest mount, 크기와 보존 기간 |
| 네트워크 | 외부 공개 여부, 직접 공인 IP 또는 LB, 허용 port·CIDR |
| HTTPS | TLS 종료 위치, 인증서 소유와 연결 방식 |
| 가용성 | 최소 VM 수, 여러 zone 필요 여부, 수평 확장 가능성, 상태 공유 방식 |
| 위치·비용 | CSP, 정확한 리전, 월 예산, 가격 범위와 할인 포함 여부 |

특히 다음 경우에는 질문 또는 보류가 필요하다.

- CSP나 리전이 없음
- 성능 목표는 있지만 앱 측정값이나 최소 용량이 없음
- 고가용성을 요구하지만 앱이 로컬 상태에 의존함
- 영속성을 요구하지만 저장 경로 또는 보존 기간이 없음
- 예산과 최소 사양이 함께 만족될 수 없음

## 8. 성능·비용 기준 리소스 추천

자연어 요구만 보고 VM 사양을 추측하지 않는다.

1. 앱 이미지, 데이터, 요청 형태를 고정한다.
2. 처리량, 지연, 오류율, CPU, 메모리를 측정한다.
3. 목표 성능을 만족한 측정점에서 VM당 처리량과 자원 하한을 계산한다.
4. 영속 앱은 데이터 증가량과 보존 기간으로 disk 하한을 계산한다.
5. CSP·리전·아키텍처·사양으로 VM 카탈로그를 거른다.
6. compute 목록가격과 예산 조건을 적용한다.
7. 실제 CSP 후보에서 같은 부하를 다시 측정한다.

개발용 Spring Boot 앱에 동시성 4로 15초 부하를 준 결과는 다음과 같다.

| 지표 | 측정값 |
|---|---:|
| 성공 요청 | 3,735/3,735 |
| 처리량 | 229.204 RPS |
| p95 / p99 지연 | 34.132 / 64.316 ms |
| p95 CPU | 5.094 core |
| p99 메모리 | 약 325MB |

200 RPS와 정한 여유분을 적용한 개발 하한은 `8 vCPU, 0.5 GiB, 1대`였다. 고정 카탈로그
65,032개에서 찾은 후보는 다음과 같다.

| CSP·리전 | VM 후보 | 월 compute 목록가격 |
|---|---|---:|
| AWS `ap-northeast-2` | `c5a.2xlarge` | $251.12 |
| Azure `eastus` | `Standard_D8als_v6` | $235.06 |
| GCP `asia-northeast3` | `e2-highcpu-8` | $185.51 |

짧은 로컬 측정이므로 최종 권장이 아니라 실제 CSP 시험 후보다. 디스크·네트워크·LB·세금·할인은
포함하지 않았다. 데이터 증가량이 없는 영속 앱의 disk 추천은 보류했다.

## 9. 실행 과정에서 확인한 병목

멤버 OpenHands 구현 과정은 오케스트레이터에 연결됐다. 그러나 Windows와 Linux Docker의 경로·권한
차이, Gradle 이미지와 빌드 의존성, 작은 작업마다 반복되는 전체 검증이 병목이었다.

- 최초 Gradle 준비: 약 140초
- 한 실행의 `compileJava`·`bootJar`: 약 272초
- 한 wiring 작업 155.4초 중 Gradle 검증: 123.6초

LLM의 짧은 독립 호출은 정상적이었으므로 모든 장기 지연을 endpoint 속도 제한으로 볼 수 없었다.
일부는 응답이 끝나지 않았거나 내부 수정·검증 반복이 오래 걸린 경우였다. 현재는 호출과 하위 작업의
시작·종료·출력 길이·종료 이유를 따로 기록한다.

검증을 없애지 않고 범위를 나눠 개선한다.

- 하위 작업: compile과 영향을 받은 테스트
- 작업군 완료: 해당 기능의 통합 테스트
- 구현 완료: 전체 test·bootJar·앱 계약 검증
- 실패 복구: 실패 테스트와 소유 하위 작업부터 재개

### P1-AWS 생성 경로 복구 결과

2026년 8월 10일에는 기존 P1-AWS 체크포인트를 이용해 실패 소유 작업만 순서대로 복구했다. 멤버
구현 저장소는 수정하지 않았다. 오케스트레이터가 최종 조합에서 발생한 멤버 내부 테스트 불일치를
`implementation.scaffold`, 업무 구현 오류를 `implementation.logic`, 배포 토폴로지 오류를
`implementation.vm_delivery`에 각각 돌려보냈다. 요구사항과 설계 단계는 다시 실행하지 않았다.

마지막 산출물은 생성 시스템이 수정할 수 없는 고정 오라클로 다시 평가했다.

- Docker 이미지 빌드와 컨테이너 기동: 통과
- `GET /health`: HTTP 200
- 길이 변환 `1 meter → 100 centimeter`: 통과
- 온도 변환 `0 celsius → 32 fahrenheit`: 통과
- OpenTofu/Terraform provider 검증: 통과
- AWS 토폴로지: VM 1개, public HTTPS, 앱 포트 8080, 영속 디스크 없음, 로드밸런서 없음
- 오라클 점수: 10/10, `experimentEligible=true`
- 평가 컨테이너와 이미지 정리: 통과, 최종 잔여 항목 없음

근거 원본은
`artifacts/confirmatory/p1-aws-fixed-oracle-20260810-r3.json`이다. 이 결과는 로컬 Docker 업무 기능과
AWS IaC의 정적·provider 검증 성공을 뜻한다. AWS에 실제 리소스를 생성한 결과는 아니므로 cloud
배포 성공으로 확대 해석하지 않는다.

## 10. 다음 진행 계획

### 1단계: 앱 생성 경로 안정화

P1-AWS 체크포인트에서 실패 작업만 재실행해 compile, 전체 테스트, 독립 업무 API와 IaC 오라클을
통과했다. 다음 사례에서도 같은 소유권 분류와 부분 재개가 유지되는지는 후속 종단 실행에서 관찰한다.

### 2단계: 최소 cloud 종단 성공

P1-AWS 한 건에서 다음 흐름을 끝까지 확인한다.

```text
plan → apply → ready → 외부 업무 API → destroy → 잔여 리소스 0
```

성공하면 같은 앱을 유지하고 Azure·GCP의 배포 부분만 바꿔 확인한다.

### 3단계: 클라우드 기능 확인

- 영속 저장소: 데이터 쓰기 → 재시작 → 같은 데이터 조회
- 부하분산: backend 준비 상태와 업무 API
- HTTPS: HTTP LB가 성공한 뒤 인증서와 TLS 종료 추가

### 4단계: 효과 비교

- DepKB 사용 여부에 따른 관계 누락과 실제 기능 비교
- 앱–클라우드 검사기 사용 여부에 따른 발견 시점·복구시간·최종 기능 비교
- 전체 재실행과 체크포인트 부분 재개의 시간 비교
- EasyDep, 일반 LLM CoT, MetaGPT의 종단 결과 비교

정적 검사, provider 검증, 실제 생성, 앱 기능, 정리를 하나의 점수로 합치지 않는다. 소수 셀이
안정적으로 성공한 뒤 반복 수를 정하고, 실패 상태에서 대규모 cloud 실행을 시작하지 않는다.

### 5단계: 추천 결과 확인

로컬 부하를 더 긴 시간과 여러 동시성으로 반복하고 실제 CSP VM에서 다시 측정한다. 영속 앱은
데이터 증가량을 추가로 측정하고, 이후 disk·network·LB 비용을 별도로 더한다.

## 11. 현재 결론

현재 EasyDep은 일반 개발 지원 시스템에 다음 경로를 추가했다.

```text
앱 요구
  → 근거 있는 배포 기능
  → CSP별 리소스군과 관계
  → 앱–클라우드 불일치 검사
  → 실패 작업만 수정
  → 측정값 기반 VM 후보
```

리소스 관계 조사, 정적 누락 검사, DepKB 비교, 앱–클라우드 불일치 시험, 로컬 용량 측정에서는
의미 있는 개발 결과를 얻었다. 그러나 세 CSP의 실제 종단 성공과 반복 기능 비교는 아직 완료되지
않았다. 현재 주장할 수 있는 범위는 Docker-on-VM에서 근거 기반 의존성 표현과 앱·배포 연결 검사,
부분 복구, 측정 기반 VM 후보 추천 경로를 구현하고 개발 사례로 확인했다는 것까지다.
