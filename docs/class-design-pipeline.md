# 클래스·시퀀스 설계 생성 로직

클래스와 시퀀스 설계는 서로 다른 생성기가 독립적으로 추측하지 않는다. 클래스 단계에서
구조, 메서드 계약, 호출 트리와 값 출처를 함께 확정하고, 시퀀스 단계는 승인된 호출 트리를
결정론적으로 투영한다.

코드 위치, 실제 LLM payload·응답 예제와 finding 전달 방식은
[`class_diagram/README.md`](../app/design/services/class_diagram/README.md), 시퀀스 모델과
피드백 재투영은 [`sequence_diagram/README.md`](../app/design/services/sequence_diagram/README.md),
검사 실행 계약은 [`validation/README.md`](../app/design/services/class_diagram/validation/README.md)에
설명한다. 이 문서는 두 산출물의 도메인 흐름과 운영 원칙을 기준으로 유지한다.

```text
동결 요구사항·유스케이스 명세·관계
→ 시나리오 인덱스와 실행 슬라이스
→ 전역 BCE 구조
→ 슬라이스별 메서드 계약
→ 슬라이스별 호출 트리와 값 바인딩
→ 최종 계약 검사
→ 클래스·시퀀스 PlantUML
```

## 입력과 실행 단위

입력은 요구사항 문장, 유스케이스 요약·명세, `include`·`extend` 관계다. 시나리오
인덱스는 명세의 단계 ID를 보존하고, 주 액터가 새 요청을 시작하는 지점을 기준으로 한
유스케이스를 하나 이상의 실행 슬라이스로 나눈다. 내부 `include` 유스케이스는 호출한
슬라이스의 추적 범위에 합쳐지고, `extend`는 명세의 확장 지점에 대응하는 분기로 유지된다.

이 분할은 산출물을 늘리기 위한 것이 아니라 LLM의 선택 범위를 줄이기 위한 내부 작업
단위다. LLM에는 전체 프로젝트 대신 현재 슬라이스의 단계, 허용된 단계 ID, 해당 범위의
고정 클래스·타입, 이미 사용된 메서드·타입 이름만 전달한다.

## 클래스 계약 생성

1. **전역 인벤토리**는 Boundary·Control·Entity, Entity의 지속 필드와 구조 관계를 정한다.
   Entity 필드가 참조하는 구조 타입만 전역 DataType에 포함한다. 단계 커버리지, 이름·참조
   무결성, BCE 역할과 지속 식별자는 결정론적으로 검사하며 실패 시 전역 인벤토리 전체를
   최대 한 번만 교체한다.
2. **메서드 조각**은 실행 슬라이스별로 생성한다. 고정된 클래스에 어떤 메서드가 필요한지,
   매개변수·반환 타입과 근거 단계가 무엇인지만 결정한다. 요청·응답 DTO와 enum은 이 단계의
   지역 타입이며 실제 메서드 시그니처에서 도달 가능한 타입만 최종 모델에 남는다. 조각은
   최대 두 개씩 wave로 실행하고, 완료된 wave의 메서드·타입 카탈로그를 다음 wave의 예약
   목록으로 넘긴다.
3. 조각을 합칠 때 동일한 정의는 병합하고, 같은 이름의 서로 다른 메서드나 타입은 현재
   조각만 한 번 다시 생성한다. 다른 유스케이스의 성공한 조각은 바꾸지 않는다.
4. **호출 계획**은 새 메서드를 만들 수 없다. 현재 슬라이스와 `include` 범위에서 이미
   승인된 메서드 ID만 선택해 Boundary → Control → Entity 호출 트리를 만든다. 응답
   스키마의 `receiverOperationId` 자체가 실제 메서드 ID의 enum이므로 시그니처 생략이나
   목록 밖 호출은 구조적으로 불가능하다. LLM은 메서드와 부모 인덱스만 선택하고,
   `stepRefs`는 선택된 메서드 계약에서 코드가 투영한다.
5. 각 매개변수는 액터 입력, 선행조건, 상위 호출의 매개변수와 그 필드, 앞선 호출의
   반환값과 그 필드, 또는 지원 시간 타입의 런타임 시계 중 타입이 맞는 출처에 바인딩된다.
   상류 값이 있으면 런타임 시계보다 우선한다. 후보가 하나면 코드가 선택하고, 여러 개일
   때만 LLM이 고른다. 이때 각 응답 필드가 해당 매개변수의 실제 후보 enum이므로 후보
   문자열을 재작성하거나 목록 밖 값을 반환할 수 없다.

액터가 요청을 시작한 단계는 Boundary만 소유한다. Control·Entity가 같은 actor entry를
근거 단계라고 반환하면 코드가 그 참조를 제거하고, 남은 근거가 없는 위임 메서드는 최종
조각에서 제외한다. 이미 확정된 소유권 규칙을 다시 LLM 선택으로 돌리지 않기 위함이다.

대상 DTO의 필드가 상류 객체 필드·앞선 반환값·런타임 시계로 모두 채워질 수 있으면
`derived#Type(...)` 바인딩을 결정론적으로 기록한다. 이는 타입이 다른 요청 객체를 같은
타입이라고 간주하는 것이 아니라, 구현 단계가 수행할 명시적인 값 변환 근거다. 선택 필드는
원천이 없으면 기본값을 사용할 수 있지만 필수 필드 하나라도 채울 수 없으면 호출을 차단한다.

검사는 클래스·타입·단계 참조 무결성, 역할별 호출 방향, 호출 순서, 매개변수 타입과 값
출처, 지속 상태 작업의 Entity 참여를 다룬다. 호출 계획은 실패한 슬라이스에서만 최대 한
번 교체한다. 필요한 메서드가 빠져 호출을 만들 수 없는 경우에도 같은 슬라이스의 메서드
조각만 보완한 뒤 다시 계획한다. 최종 검사 실패는 또 다른 전역 수정 루프를 시작하지 않는다.

최종 `BCEModel`에는 다음이 함께 저장된다.

- `Classes`: BCE 클래스, 필드, 메서드와 근거 단계
- `DataTypes`: 구조 타입과 실제 시그니처에서 쓰는 지역 타입
- `Relationships`: 정적 클래스 관계
- `Collaborations`: 실행 슬라이스별 호출 트리, 매개변수 바인딩과 반환 계약

클래스 간 표시용 의존선은 별도 의미 사전에서 만들지 않고 저장된 호출 트리에서 파생한다.

## 시퀀스 투영

시퀀스 단계는 LLM을 호출하거나 클래스 모델을 수리하지 않는다. `Collaborations`의 호출
트리를 유스케이스·단계 순서로 배열하고, 모든 호출 직후 대응하는 반환 메시지를 만든다.
`include` 협업은 호출 위치에 삽입하고 `extend` 협업은 확장 지점의 조건부 fragment로
투영한다. 클래스·메서드·타입·값 출처가 클래스 계약에 없으면 시퀀스를 추측해서 만들지
않고 단계 검사를 실패시킨다.

PlantUML 레이블은 가독성을 위해 매개변수 이름만 표시하고 여러 인자를 줄바꿈하지만,
구조화 모델에는 정확한 타입과 바인딩을 그대로 보존한다. 따라서 화면 표현을 단순화해도
API·ERD 및 구현 단계가 사용하는 계약은 손실되지 않는다.

## 재개, 피드백과 진행 표시

중간 클래스 모델과 완료된 협업은 체크포인트에 저장한다. 재실행 시 시나리오와 체크포인트가
일치하면 누락되거나 실패한 실행 슬라이스만 재개한다. 사용자 피드백도 먼저 전역 구조,
특정 유스케이스의 메서드, 특정 협업 중 가장 작은 소유 단위로 라우팅하고 그 단위만 교체한다.
지역 타입 이름이 명시되면 해당 타입을 소유한 유스케이스로 바로 라우팅한다.

전역 구조, 메서드 조각, 협업이 승인될 때마다 현재 클래스 PlantUML 스냅샷을 진행 이벤트로
발행한다. UI는 같은 화이트보드를 갱신할 수 있고, CLI 체크포인트 실행기는 단계별 PUML과
렌더링 결과를 저장한다.

## 동시성과 선택 공간

요구사항 명세 생성·의미 검토는 과거 NIM 실측값을 복원해 `spec_concurrency=8`을 사용한다.
클래스 메서드와 협업 생성은 `design_class_behavior_parallelism=2`를 유지한다. 시퀀스
투영 자체는 결정론적이지만 관련 생성 병렬도의 기본값도 2로 제한한다.

품질은 더 많은 병렬 호출이나 큰 프롬프트보다 다음의 유한 선택 공간으로 관리한다.

- 실행 슬라이스의 허용 단계 ID
- 전역에서 고정된 클래스와 구조 타입
- 실제 enum으로 제한된 현재 범위의 메서드 ID
- 응답 필드별 enum으로 제한된 타입 호환 값 출처
- 메서드 계약에서 자동 투영되는 단계 참조
- 실패한 소유 단위 한 곳만 바꾸는 제한된 수리

전역 인벤토리 입력도 원문 명세 전체가 아니라 역할·목표·단계와 관계만 담은 압축 payload를
사용한다. 출력 토큰 상한을 임의로 낮춰 구조화 응답을 잘라내지 않고, 입력과 출력 스키마에서
선택지를 줄인다.

## 하류 연결과 평가

API 단계는 Boundary·Control의 메서드 계약과 시퀀스 흐름을 사용하고, ERD 단계는 Entity와
구조 필드를 사용한다. 이후 배포 설계는 클래스 개수로 워크로드를 나누지 않고 이 산출물을
생성 애플리케이션의 동작 근거로만 사용한다.

`python -m evaluation.class_design_evaluation`은 저장된 클래스·시퀀스 모델을 비교하며
상류 체크포인트 digest, 참조 무결성, 값 출처, 호출·반환 계약을 기계적으로 검사한다.
클래스 이름·개수·산출물 해시는 정답 조건이 아니다. 사람 검토는 요구사항 충실성, 책임
응집도, 거대·중복 클래스, 자연스러운 타입과 반환값, 호출·반환 가독성을 정성적으로 본다.
