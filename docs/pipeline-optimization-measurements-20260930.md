# End-to-end pipeline optimization: measurements and next checks

작성일: 2026-09-30. 목적은 요구사항부터 테스팅까지의 전체 완료 시간을 줄이면서 단계 실패와 불필요한 재실행을 줄이는 것이다. 아래 수치는 서로 다른 앱·체크포인트·실행 조건에서 얻은 값이므로 합산하거나 개선율로 비교하지 않는다. 같은 입력을 사용한 전후 비교가 아닌 값은 현황 표본으로만 취급한다.

## 확인된 병목과 미확인 사항

- 구현 작업 시도 시간의 합과 전체 구현 job 경과시간 사이에 차이가 크지만, 현재 이벤트만으로 차이의 원인을 분류할 수 없다. 같은 attempt ID를 기준으로 queue/dispatch, 모델 호출, 작업공간 반영, 검사, 결과 저장의 시작·종료 시각을 연결해야 한다.
- 과거 Testing 표본에서는 앱 기동/readiness와 Arazzo 계획이 각각 수분을 차지했다. 최근 같은 snapshot의 Linux volume 제품 경로에서는 45.075초 readiness로 준비됐지만, Arazzo와 전체 Testing 경로의 비용은 별도로 측정해야 한다.
- 최근 course Testing 실패는 최종 완료를 막았다. 계획 생성과 복구의 호출 수·시간, 각 workflow의 실행 시간, 자동 수리와 전체 재검증 비용이 같은 명령 trace에 아직 모이지 않아, 어느 하나를 우선 최적화할지 단정하지 않는다.
- 요구사항·설계의 일부 긴 과거 구간도 현재 재현되지 않았다. SQL 로그 수나 체크포인트 크기만으로 그 지연을 설명할 근거는 없다.

## 검증된 개선과 아직 검증되지 않은 개선

- 체크포인트 saver의 동일 함수 단위 A/B에서는 `put`이 SELECT 50회에서 2회로 줄고 wall time이 151.687ms에서 32.479ms로 줄었다. 이는 해당 saver 함수의 1회 측정이며 전체 생성 파이프라인 시간 감소를 입증하지 않는다.
- 설계 단계에는 서브그래프·저장·게이트를 나누는 타이머가 추가됐다. 이는 관측성 개선이며 그 자체로 실행을 빠르게 하지는 않는다.
- 구현 coordinator는 각 작업 시도에 `dispatchedAt`, `executorReturnedAt`, `executorDurationMs`를 기존 workflow 상태로 저장하도록 보완했다. fake executor 집중 테스트 1개가 통과했지만, 다음 실제 구현 실행의 분해 측정은 아직 없다. 이 변경 자체는 속도 개선이 아니다.
- Testing의 Linux volume 기동은 진단 helper에 이어 수정된 제품 `running_application` 경로에서도 같은 snapshot으로 성공했다. 제품 측정은 `/healthz`까지 45.075초이고 실행별 Docker 리소스가 모두 제거됐다. 표본이 작고 전체 Testing 명령이 아니므로 기동 경계 밖의 효과를 주장하지 않는다.
- Testing/Arazzo의 작은 OSS 호출에서 producer 후보 선택 또는 부분 graph 비용이 개선된 사례가 있으나, workflow 완성 및 HTTP 실행은 실패했다. 계획 성공률이나 전체 Testing 속도 향상으로 해석하지 않는다.

## 다음의 제한된 검증 순서

1. 같은 Testing checkpoint 또는 동등한 고정 입력에서 계획 생성, 앱 준비, 각 workflow 실행, 결과 검증, 자동 수리/재검증 경계를 기록한다. 성공·실패를 모두 보존하고, 실패가 나면 그 실패 단계만 재현한다.
2. 구현 coordinator의 다음 단일 attempt에서 새 dispatch/return 필드를 확인하고, 큰 차이가 재현될 때에만 GLM 요청, 파일 반영, focused 검사, 최종 result 저장의 추가 경계를 같은 attempt ID로 좁힌다. 전체 126분 run을 계측 확인만 위해 반복하지 않는다.
3. 소규모 경계 검증이 통과하면 소형 앱의 단계 실행으로 합성 효과를 확인하고, 마지막에 no-demo-bypass 수강신청 앱 요구사항 16개 전체 Workspace 실행으로 완료 여부와 총 wall time을 기록한다.

현재까지 전체 파이프라인의 전후 성능 개선은 입증되지 않았다. 다음 실행의 우선 목적은 실패를 포함한 전체 단계별 시간을 하나의 명령·attempt 식별자로 연결하는 것이다. 그 자료와 실제 성공률을 기준으로 최적화 우선순위를 정한다.
