## 확인된 병목과 미확인 사항

- 구현 작업 시도 시간의 합과 전체 구현 job 경과시간 사이에 차이가 컸다. 계산기 2회 실행에서 시도 사이 합계 339.6초와 263.0초가 재현됐고, 두 번째 실행의 상태 저장·해시 합은 각 0.1초 안팎이었다. 코드와 실행 관찰상 dependency 묶음마다 동일 workflow run에서 새 runner/lease가 생성됐다. 한 runner에서 의존 작업을 연속 실행한 뒤 4개 경계 합이 10.1초로 줄어, 반복 runner 수명주기가 큰 요인이었음을 뒷받침한다. 기존 공백 내 종료·정리/재큐잉/새 컨테이너 준비의 정확한 개별 배분은 그 실행에서 기록되지 않았다.
- 과거 Testing 표본에서는 앱 기동/readiness와 Arazzo 계획이 각각 수분을 차지했다. 최근 같은 snapshot의 Linux volume 제품 경로에서는 45.075초 readiness로 준비됐고 Workspace 재실행도 PASS했다. 새 계산기 실행은 Trivy와 package 총량·내부 경계를 기록했다. 이 표본에서는 package 69.64초 중 OpenTofu init 35.09초가 가장 긴 개별 명령이었다. 과거 미계측 package 창의 48.5초 잔여는 이번 실행으로 소급 분류하지 않는다.
- 최근 course Testing 재실행은 static·deployment까지 PASS했지만 동적 워크플로 계획 오류와 생성 앱의 응답 계약 불일치가 함께 발견되고 자동 수리 2회 미해결로 `AWAITING_INPUT`에 멈췄다. 이는 사용자 선택 문제가 아니며, `wait_reason=repair`인데 선택 가능한 조치도 없는 불완전한 상태다. 계획 결함은 OSS 계획 경계에서, 응답 계약 불일치는 구현/설계 계약 경계에서 각각 확인해야 한다. 계획 생성/복구 호출 수·시간과 반복 검사의 세부 비용은 별도 분해가 필요하다.
- 요구사항·설계의 일부 긴 과거 구간도 현재 재현되지 않았다. SQL 로그 수나 체크포인트 크기만으로 그 지연을 설명할 근거는 없다.

## 검증된 개선과 아직 검증되지 않은 개선

- 체크포인트 saver의 동일 함수 단위 A/B에서는 `put`이 SELECT 50회에서 2회로 줄고 wall time이 151.687ms에서 32.479ms로 줄었다. 이는 해당 saver 함수의 1회 측정이며 전체 생성 파이프라인 시간 감소를 입증하지 않는다.
- 설계 단계에는 서브그래프·저장·게이트를 나누는 타이머가 추가됐다. 이는 관측성 개선이며 그 자체로 실행을 빠르게 하지는 않는다.
- 구현 coordinator는 각 작업 시도에 `dispatchedAt`, `executorReturnedAt`, `executorDurationMs`와 dispatch 상태 저장·결과 해시·완료 상태 저장의 시간을 기존 workflow 상태로 남긴다. 집중 테스트와 계산기 실제 실행에서 값이 저장됨을 확인했다. 두 번째 실행에서 각 시도 파일 I/O는 0.072~0.156초로 측정되어 반복되는 약 50초 공백의 원인에서 제외됐다. 계측 자체는 속도 개선이 아니다.
- 구현 coordinator가 성공한 작업을 재조정한 뒤 다음 의존 작업을 같은 `run-workflow` 호출에서 실행하도록 변경했다. backend 선행→후속→frontend 실행과 인터럽트 경계의 집중 테스트가 통과했고, 실제 계산기 5개 작업이 검증 우회 없이 완료됐다. 작업 간 4개 경계 합은 339.6초에서 10.1초로 줄었다. 총 wall time 차이는 단일 실행 쌍과 캐시·모델 변동이라는 한계를 유지한다.
- Testing 자동 기술 재시도는 최신 체크포인트를 DB에 저장한 뒤 낡은 메모리 command 객체로 재실행하던 경계를 고쳤다. 최신 command를 다시 읽어 전달하는 집중 테스트와 부분 Arazzo 계획의 유효 peer 재사용 테스트가 통과했다. 과거 수강신청 최종 ID/order 오류의 정확한 목록은 저장되지 않아, 이 수정만으로 그 실패가 해결됐다고 주장하지 않는다.
- Testing의 Linux volume 기동은 진단 helper와 수정된 제품 `running_application` 경로의 동일 snapshot에서 성공했다. 제품 측정은 `/healthz`까지 45.075초이고 실행별 Docker 리소스가 모두 제거됐다. 이후 같은 구현 체크포인트의 새 Workspace Testing 분기도 검증 우회 없이 196.9초에 PASS했다. 이것은 단계 성공의 증거이나 환경 차이 때문에 전체 시간 절감률은 아직 주장하지 않는다.
- Trivy와 배포 package 경계 시간을 canonical Testing report에 남겼다. 집중 테스트 후 실제 계산기 Testing에서 각각 10.24초/69.64초가 저장되고 gate 3개·workflow 1개가 모두 통과함을 확인했다. 이는 관측성 개선과 단계 성공의 근거이며 계측 자체가 실행을 빠르게 만든 것은 아니다.
- Testing/Arazzo의 작은 OSS 호출에서 producer 후보 선택 또는 부분 graph 비용이 개선된 사례가 있으나, workflow 완성 및 HTTP 실행은 실패했다. 계획 성공률이나 전체 Testing 속도 향상으로 해석하지 않는다.

## 다음의 제한된 검증 순서

1. 같은 Testing checkpoint 또는 동등한 고정 입력에서 계획 생성, 앱 준비, 각 workflow 실행, 결과 검증, 자동 수리/재검증 경계를 기록한다. 성공·실패를 모두 보존하고, 실패가 나면 그 실패 단계만 재현한다.
2. 한 runner 연속 실행으로 줄어든 작업 간 공백을 더 복잡한 보호 로직 없이 유지한다. 새 계산기 구현 결과에서 Testing을 이어 실행하고, 이후 완료된 course 구현 체크포인트에서 Testing만 공식 분기로 검증한다. 전체 126분 course 구현을 계측 확인만 위해 반복하지 않는다.
3. 소규모 경계 검증이 통과하면 소형 앱의 단계 실행으로 합성 효과를 확인하고, 마지막에 no-demo-bypass 수강신청 앱 요구사항 16개 전체 Workspace 실행으로 완료 여부와 총 wall time을 기록한다.

현재까지 전체 파이프라인의 전후 성능 개선은 입증되지 않았다. 다음 실행의 우선 목적은 실패를 포함한 전체 단계별 시간을 하나의 명령·attempt 식별자로 연결하는 것이다. 그 자료와 실제 성공률을 기준으로 최적화 우선순위를 정한다.
