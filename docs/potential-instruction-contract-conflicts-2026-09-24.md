# Potential instruction and contract conflicts

**Status:** Investigation memo, 2026-09-24. The items below came from a read-only code-path audit. None has yet been confirmed by a live model call or end-to-end run; treat each as a hypothesis pending focused reproduction.

## Findings

1. **Arazzo input-value generation may use a different provider/model than workflow planning.** The shared client is constructed from `build_arazzo_llm_connection()` (`app/testing/nodes/dynamic_functional.py:704-714`), while `_propose_input` independently selects its model/profile from `build_llm_connection()` (`app/testing/nodes/dynamic_functional.py:1191-1197`). Input proposals are then made through that shared client (`app/testing/nodes/dynamic_functional.py:1785-1788`). If the configured Arazzo and default connections differ, the client endpoint and requested model may not agree. **Risk:** failed calls or validation against the wrong model profile. **Candidate fix:** pass the resolved Arazzo connection/profile through the proposal path, or construct a matching client from the same connection used to choose the model.

2. **Required cookie parameters may be offered as connectable workflow inputs although validation rejects them.** Candidate construction includes every required parameter without filtering its `in` location (`app/testing/utils/arazzo_planner.py:443-452`), but the OpenAPI execution profile accepts required parameter locations only in `path`, `query`, or `header` (`app/testing/schemas/arazzo.py:648-666`). **Risk:** the planner proposes an unusable cookie connection that fails later validation. **Candidate fix:** define supported parameter locations once and apply that rule while projecting candidate inputs, with a clear unsupported-input diagnostic.

3. **Partial request-body connections are candidates, but the compiler requires all projected body inputs.** The planner independently exposes connections for compatible prior outputs to each input slot (`app/testing/utils/arazzo_planner.py:475-490`). The compiler rejects a selected subset unless it covers every projected body slot (`app/testing/nodes/dynamic_functional.py:255-265`). **Risk:** a semantically sufficient partial mapping is presented as legal and then rejected during compilation. **Candidate fix:** align candidate generation and compilation: either expose only complete body-connection sets, or compile partial mappings by filling remaining fields through an explicit supported mechanism.

4. **The shared implementation prompt assumes backend completion markers for all owners.** The common owner prompt tells every implementation agent to start from a writable source containing an assigned completion marker and consult an operation contract (`app/implementation/agents/prompts/easydep_owner_system_prompt.j2:10`). This can conflict with frontend tasks whose assigned source and completion evidence follow a different convention. **Risk:** frontend agents may waste effort searching for inapplicable artifacts or report a false upstream gap. **Candidate fix:** make the shared prompt owner-neutral, then inject backend- or frontend-specific workflow instructions from the task type.

5. **Missing-use-case deduplication by display name may discard requirement traceability.** For each audited functional requirement, the code skips a missing-use-case candidate when its normalized name already exists (`app/requirements/modeling/use_cases.py:483-488`); newly added cases receive only the current requirement ID (`app/requirements/modeling/use_cases.py:489-500`). **Risk:** distinct functional requirements that share a display name may not both be represented in `requirement_ids`. **Candidate fix:** deduplicate by stable semantic/actor-goal identity while merging requirement IDs, and preserve requirement-to-use-case links explicitly.

## Validation follow-up

Reproduce each item with a small focused case before changing behavior. For the model-connection item, use distinct Arazzo and default model configurations and observe the endpoint/model pair. For the contract items, verify planner candidates against schema validation and compiler behavior. For prompt applicability and requirement traceability, use one frontend task and two distinct FRs proposing the same display name. Record outcomes here or in a follow-up issue memo, then run the relevant stage-level live-call check if a generation prompt or LLM-producing stage changes.
