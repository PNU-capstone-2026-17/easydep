# 구현 에이전트를 위한 클라우드 가드레일과 사례·평가 계획

> 작성일: 2026-08-10  
> 현재 지원 범위: AWS·Azure·GCP의 Docker-on-Linux-VM 애플리케이션  
> 주의: 이 문서는 실행 계획을 설명한다. `research.md`의 연구 목표를 변경하지 않으며,
> 아직 실행하지 않은 실험을 완료 결과로 표현하지 않는다.

## 1. 무엇을 만들려는가

EasyDep은 사용자의 업무 요구사항을 곧바로 특정 CSP의 리소스 목록으로 번역하지 않는다.
먼저 애플리케이션이 필요로 하는 기능과 배포 제약을 구조화하고, 구현 에이전트가 소스코드,
Dockerfile과 Terraform을 만들 때 다음 실패를 줄이는 가드레일을 제공한다.

- 필요한 클라우드 리소스나 연결 관계를 빠뜨리는 문제
- 애플리케이션의 포트·저장 경로·실행 의존성과 클라우드 구성이 맞지 않는 문제
- 데이터 보존이나 고가용성처럼 서로 충돌할 수 있는 요구를 임의로 해석하는 문제
- 용량 근거가 없는데도 특정 VM 제품을 그럴듯하게 추천하는 문제
- 생성에는 성공했지만 애플리케이션 업무 기능은 작동하지 않는 문제

현재 목표는 모든 클라우드 네이티브 애플리케이션을 지원하는 것이 아니다. Kubernetes,
서버리스, 관리형 데이터베이스 및 메시징 서비스는 현재 검증 범위 밖이다. 논문과 시연에서는
**세 CSP의 VM 위에서 Docker 애플리케이션을 배포하는 범위**라고 명시한다.

## 2. 에이전트가 받을 요구사항

사용자는 클라우드 제품명이나 NIC 개수 같은 구현 세부사항보다 자신이 알고 있는 업무 기능과
운영 목표를 입력한다. 시스템은 아래 항목을 자연어에서 구조화하되, 확인할 수 없는 값은
추측하지 않고 질문 또는 `unresolved` 상태로 남긴다.

### 2.1 애플리케이션 요구사항

| 입력 관심사 | 자연어 예시 | 구현·검증에 사용하는 값 |
|---|---|---|
| 업무 기능 | “상품 목록과 상세 정보를 조회한다” | API 동작, 입력·출력, 인수 테스트 |
| 실행 형태 | “Docker 컨테이너로 실행한다” | Linux VM, 이미지 빌드·기동 조건 |
| 서비스 포트 | “8080 포트에서 API를 제공한다” | 앱 설정, Docker 포트, 방화벽·LB 포트의 일치 |
| 상태와 데이터 | “등록한 메모는 재시작 후에도 남아야 한다” | 영속 저장 필요성, 앱 데이터 경로, 재시작 검사 |
| 상태 검사 | “서비스 상태를 확인할 수 있어야 한다” | health endpoint와 LB health check 연결 |
| 외부 연동 | “외부 결제 API에 접속한다” | 아웃바운드 네트워크와 비밀값 주입 요구 |
| 비밀정보 | “API 키는 코드에 넣지 않는다” | 런타임 주입 여부와 평문 포함 검사 |

### 2.2 클라우드·운영 요구사항

| 입력 관심사 | 자연어 예시 | 설계에 미치는 영향 |
|---|---|---|
| CSP와 지역 | “AWS 서울 리전에 배포한다” | 사용할 provider와 region 제한 |
| 외부 공개 | “인터넷에서 접근한다” | 공개 진입점, 라우팅, 보안 규칙 |
| 전송 암호화 | “HTTPS로 접속한다” | 인증서와 TLS 종단 구성 |
| 데이터 보존 | “VM을 재시작해도 데이터가 남아야 한다” | 별도 디스크, 연결, 포맷·마운트·앱 경로 |
| 가용성 | “한 VM이 중단돼도 조회가 계속되어야 한다” | 복수 VM, 장애 영역, LB와 health check |
| 최소 용량 | “최소 2 vCPU와 4 GiB 메모리” | VM 후보 필터의 하한 |
| 부하 목표 | “초당 200건, p95 300ms 이하” | 부하 시험 조건; VM 성능의 자동 보장은 아님 |
| 예산 | “월 compute 비용 10만 원 이하” | 목록가격 기준 후보 제한과 충돌 경고 |

사용자가 “빠른 서버”처럼 측정할 수 없는 표현만 제공하거나 최소 용량 없이 VM 추천을 요구하면,
시스템은 임의의 숫자를 만들지 않는다. 필요한 질문을 생성하고 답변된 하위 작업부터 재개한다.

## 3. 구현 에이전트에 제공할 가드레일

### 3.1 클라우드 리소스 의존성 가드레일

설계가 선택한 시작 리소스에서 DepKB의 `mandatoryForProvisioning` 관계를 따라가며 필요한
리소스와 참조를 보충한다. 예를 들어 VM을 배치하려면 CSP에 따라 Network, Subnet, NIC,
Security Group 또는 Firewall 같은 구성이 필요하다. 영속 저장, 로드밸런싱 및 TLS는 각각
여러 네이티브 리소스로 투영될 수 있다.

가드레일이 제공하는 것은 다음과 같다.

- CSP별 필요한 리소스 종류와 명시 참조 관계
- 의존 대상이 먼저 생성되도록 하는 순서
- 삭제할 때 역순으로 처리해야 하는 수명주기 관계
- 조건이 충족될 때만 필요한 리소스와 미해결 조건
- 같은 중립 기능이 CSP별로 여러 리소스에 대응하는 다대다 projection

관계가 있다는 이유만으로 cardinality나 기능 성공까지 통과했다고 판정하지 않는다. 예를 들어
로드밸런서와 서브넷의 참조가 존재하는 것과 실제로 두 장애 영역에 배치됐는지는 별도 검사다.

### 3.2 애플리케이션–클라우드 계약 가드레일

클라우드 리소스 생성 가능성과 애플리케이션 기능 성공은 분리해서 확인한다. 여기서
“계약”은 새로운 클라우드 제품이 아니라 서로 다른 단계가 약속한 값을 비교하는 구조다.

```text
사용자 요구사항
  → ApplicationRuntimeContract: 앱이 실제로 필요로 하는 것
  → CloudCapabilityContract: 클라우드가 제공하기로 결정한 것
  → DeploymentBindingContract: 두 값이 어디에서 연결되는가
  → 정적 validator
  → 빌드·컨테이너·업무 기능·클라우드 기능 시험
```

예를 들어 앱이 `/srv/state`에 데이터를 기록하고 클라우드 설계가 영속 디스크를 제공하더라도,
Docker가 디스크를 `/mnt/data`에만 연결하면 앱 데이터는 영속 디스크에 저장되지 않는다.
각 산출물은 따로 보면 합법이지만 두 값의 binding은 잘못됐다. 계약 가드레일은 이런 교차 단계
불일치를 실제 배포 전에 찾는 역할을 한다.

#### 현재 실제 구현·검증 상태

| 검사 대상 | 실제 판정 방식 | 구현 상태 | 지금까지 확인된 범위 | 아직 확인하지 못한 것 |
|---|---|---|---|---|
| 빌드·런타임 의존성 | 소스가 사용하는 API·통합 기능과 Gradle 선언을 대조해 `APP-DEP-*`, `APP-DB-*` 진단 생성 | 구현됨 | 고정 입력에서 불일치 탐지, 정상 입력 오탐 없음, `implementation.logic`으로 부분 복구 라우팅. 최신 스냅샷에서 진단 해소와 로컬 업무 테스트 통과 | 다양한 언어·빌드 시스템 일반화, 실제 VM에서의 런타임 통합 |
| 포트 연결 | 앱 listen port, Docker publish/target, Terraform의 backend·방화벽·LB port를 대조해 `BIND-PORT-001` 생성 | 구현됨 | 고정 입력 탐지 및 `implementation.vm_delivery` 부분 복구. 최신 스냅샷에서 진단 해소와 로컬 업무 테스트 통과 | 실제 세 CSP 공개 endpoint에서의 종단 연결 반복 |
| 저장 경로 | 앱 `accessPath`, guest mount source, Docker container target을 분리해 `BIND-STORAGE-001` 생성 | 구현됨, 복구는 불안정 | 고정 입력 탐지와 정상 binding 판별, VM delivery로 부분 복구 라우팅 | 최신 확인 실행에서는 한 번의 LLM 수리 후에도 경로 불일치가 남음. 실제 cloud 재시작 영속성은 미확인 |
| 상태와 가용성 | 노드 로컬 상태인데 여러 active replica·zone을 요구하고 공유·복제 전략이 없으면 `BIND-STATE-HA-001` 생성 | 판정 구현됨 | 구조화 계약과 오케스트레이션 시험에서 충돌을 사용자 질문 대상으로 라우팅 | 자연어 질문→사용자 답변→설계 갱신→실제 장애 허용 기능의 완전한 종단 실행 |
| health check | 앱 health path·port·protocol과 LB health-check 구성을 비교하는 계약 | 설계·진단 코드만 정의, 종단 validator는 미완성 | CSP별 health-check 리소스와 GCP의 일부 실제 기능 개입은 별도로 관측 | 일반 `BIND-HEALTH-001` 검출·부분 복구·세 CSP endpoint 시험 |
| 비밀값 | 앱이 요구하는 secret과 클라우드의 전달 위치를 binding하고 산출물의 평문 포함을 검사하는 계약 | 계약 필드 수준, 가드레일 미완성 | 요구사항·계약에서 비밀값을 코드에 넣지 않는 정책을 보존 | 일반 평문 검출, 런타임 주입, 실제 CSP secret 전달의 종단 검증 |

따라서 현재 “실제로 이뤄진다”고 말할 수 있는 핵심은 다음과 같다.

1. 앱과 배포 산출물에서 의존성·포트·저장 경로·상태 속성을 관측한다.
2. 서로 맞지 않으면 구조화 진단 코드를 생성한다.
3. 진단을 전체 실행이 아니라 소유 하위 작업으로 돌려보낸다.
4. 의존성·포트는 최신 고정 스냅샷에서 부분 수정과 로컬 업무 테스트까지 통과했다.

그러나 저장 경로의 자동 복구, health check, 비밀값 전달 및 실제 3사 클라우드 endpoint 기능은
아직 완성됐다고 표현하면 안 된다. 특히 정적 진단이 사라졌다는 사실은 실제 mount, 재시작 후
데이터 보존 또는 장애 허용 성공을 뜻하지 않는다.

#### 실행 중 개입 위치

| 시점 | 수행 내용 | 실패할 때 돌아갈 곳 |
|---|---|---|
| 애플리케이션 골격·로직 생성 후 | 소스 API, Gradle 의존성, DB/runtime 설정 검사 | `implementation.logic` 등 앱 소유 하위 작업 |
| VM 전달용 IaC 생성 후 | 앱 포트·데이터 경로와 Docker/Terraform binding 검사 | `implementation.vm_delivery` |
| 로컬 동적 검사 | 빌드, 컨테이너 시작, health, 업무 API 검사 | 실패를 소유한 구현 또는 VM 전달 작업 |
| 실제 cloud 배포 후 | 공개 endpoint, 영속성 재시작, 장애 허용 기능 검사 | 해당 기능을 소유한 하위 작업; 현재 일부만 구현·실측 |

특정 프레임워크나 SQLite 문자열에 맞춘 예외 패치를 가드레일로 만들지 않는다. 판정은 가능한 한
요구사항과 산출물에서 얻은 포트, 경로, 의존성 및 상태 속성을 사용한다. 현재 Java·Gradle 관측기는
지원 범위에 따른 구현체이며, 계약 모델 자체가 모든 언어를 지원한다는 뜻은 아니다.

### 3.3 용량·비용 추천 가드레일

최소 vCPU·메모리, CSP·지역 및 예산이 주어졌을 때만 검증된 카탈로그에서 후보 VM을 좁힌다.
현재 추천은 **명시된 하한과 compute 목록가격에 맞는 후보 안내**이지, 애플리케이션 코드를
보고 필요한 용량을 자동 예측하거나 전체 클라우드 비용을 최적화하는 기능이 아니다.

### 3.4 산출물과 실행 가드레일

- 요구사항 ID에서 설계 결정, 소스·IaC 요소와 테스트 결과까지 추적한다.
- OpenTofu/Terraform 구문·provider 검증과 리소스 의미 검사를 수행한다.
- Docker 이미지 빌드, 컨테이너 기동, health endpoint와 업무 API를 검사한다.
- 클라우드 실행은 apply, ready, 업무 기능, 필요한 장애·재시작 시험, destroy 순으로 기록한다.
- 성공·실패와 관계없이 생성 자원을 정리하고 잔존 자원 0건을 확인한다.
- 실패한 하위 작업의 체크포인트에서 재개하여 무관한 상류 단계를 반복하지 않는다.

## 4. 사례 선정

### 4.1 주 시연 도메인: 소형 상품 카탈로그 API

최종 시연은 사용자가 이해하기 쉽고 동일한 업무 맥락에서 클라우드 조건을 바꿀 수 있는
**소형 상품 카탈로그** 도메인을 우선한다. 이 도메인이 클라우드 애플리케이션의 대표 모집단을
뜻하지는 않는다. 현재 지원 기술의 차이를 통제된 방식으로 보여주기 위한 사례다.

| 변형 | 요구사항 | 드러나는 지원 기술 |
|---|---|---|
| 무상태 조회 | 이미지에 포함된 상품을 단일 VM에서 조회 | 기본 VM·Network·Subnet·보안·공개 진입 의존성, 불필요 디스크 억제 |
| 영속 관리 | 상품을 등록·수정하고 재시작 후 보존 | Disk–VM 연결, guest mount–앱 저장 경로 계약, 재시작 기능 검사 |
| 고가용 조회 | 복수 VM, HTTPS LB, 한 VM 장애 후 조회 지속 | CSP별 LB 다대다 projection, TLS, health check, 장애 영역과 기능 검사 |
| 충돌 요구 | 로컬 쓰기 상태와 다중 active VM을 동시에 요구 | 조용한 추측 대신 충돌 탐지와 사용자 질문 |

하나의 도메인을 사용하면 P1~P3처럼 업무 기능까지 함께 달라져 결과 원인이 섞이는 문제를
줄일 수 있다. 다만 기존 P1 단위 변환, P2 메모 CRUD, P3 상품 조회는 폐기하지 않고 종단
smoke 및 과거 결과 호환용 프로필로 남긴다.

### 4.2 단일 변수 의존성 사례

DepKB 효과는 큰 앱 하나의 성공 여부보다 동일 입력에서 클라우드 관심사 하나만 바꾼 쌍으로
평가한다.

- 저장 불필요 ↔ 재시작 후 저장 필요
- 단일 VM 직접 진입 ↔ 복수 VM과 load-balanced ingress
- HTTP 내부 진입 ↔ HTTPS 종단

이 사례는 실제 사용자 요구의 빈도를 주장하기 위한 표본이 아니라, 특정 의존성이 산출물에
반영됐는지 확인하는 controlled contrast다.

### 4.3 앱–클라우드 불일치 사례

특정 도메인 문자열이 아니라 다음 일반적인 연결 지점을 한 번씩 의도적으로 어긋나게 한다.

- 빌드와 런타임 의존성
- 애플리케이션 포트와 클라우드 진입 포트
- 애플리케이션 데이터 경로와 영속 볼륨 mount 경로
- 로컬 상태와 다중 active 배치

각 사례에서는 탐지 여부뿐 아니라 발견 단계, 수정한 하위 작업, 상류 단계 재실행 여부,
최종 업무 기능과 오수정 여부를 기록한다.

## 5. 평가 대상과 평가 범위

외부 시스템 비교와 EasyDep 내부 구성요소 제거 실험은 서로 다른 질문에 답하므로 분리한다.

### 5.1 전체 시스템 외부 비교

| 대상 | 역할 | 비교할 수 있는 것 | 비교하면 안 되는 것 |
|---|---|---|---|
| 동일 LLM의 표준 CoT | 단일 프롬프트 기반 생성 기준선 | 종단 산출물 완성도, 기능 성공, IaC 품질, 시간·호출 수 | DepKB만의 인과효과 |
| MetaGPT standard | 공개 멀티에이전트 개발 기준선 | 전체 개발 시스템의 실용 성능과 실패 양상 | 멀티에이전트 구조만의 인과효과 |
| EasyDep full | 제안 시스템 | 요구사항–설계–구현–검증–복구의 종단 결과 | 모든 차이가 특정 한 구성요소 때문이라는 주장 |

세 시스템에는 같은 자연어 요구사항과 실행 예산을 제공하고, 시스템 내부 계획이 아닌 최종
소스코드, Dockerfile, Terraform 및 실행 결과를 공통 외부 평가기로 검사한다.

Cloud-Barista는 현재 애플리케이션 생성 에이전트가 아니므로 직접 성능 기준선으로 두지 않는다.
공통 리소스 용어와 VM 사양·가격 측정 결과를 연결하는 호환 대상 및 참고 모델로 사용한다.
OpenHands 역시 EasyDep 구현 단계에서 사용하는 실행 도구이므로 독립 비교군으로 간주하지 않는다.

### 5.2 내부 절제실험

| 조건 | 차이 | 답하려는 질문 |
|---|---|---|
| `easydep-full` | DepKB와 검증 사용 | 전체 제안 경로의 결과는 어떠한가 |
| `easydep-no-depkb` | 같은 경로에서 DepKB 조회만 제거 | 의존성 지식이 노드·간선 누락을 줄이는가 |
| `easydep-no-consistency-validator` | 앱–클라우드 일관성 검사만 제거 | 조기 불일치 탐지가 복구와 기능 성공에 기여하는가 |

`no-depkb`는 개선할 대상이 아니라 의도적으로 지식을 제거한 대조 조건이다. 두 조건은 가능한
한 같은 요구사항, 같은 상류 산출물, 같은 LLM 설정과 같은 평가기를 사용해야 한다.

## 6. 무엇을 측정할 것인가

### 6.1 의존성 및 IaC

- 요구된 네이티브 리소스 유형의 존재율
- 독립 기준 관계 중 최종 IaC가 명시적으로 참조한 관계의 재현율
- 불필요 리소스 수
- Terraform/OpenTofu 구문 및 provider validate 통과 여부
- 실제 apply 성공 여부와 실패한 리소스·단계
- 삭제 성공 및 잔존 리소스 수

component 존재, 구조적 참조, cardinality, 배치 제약과 업무 기능을 하나의 “의존성 정확도”로
합산하지 않는다. 현재 구현되지 않은 제약 gate는 `not-measured`로 남긴다.

### 6.2 애플리케이션 기능

- Docker 이미지 빌드 및 컨테이너 기동
- health endpoint 응답
- 프로필별 업무 API 인수 테스트
- 영속 사례의 재시작 후 데이터 조회
- 고가용 사례의 한 VM 중단 후 서비스 지속
- HTTPS endpoint의 실제 연결

로컬 테스트 성공과 실제 CSP endpoint 성공을 별도 열로 보고한다. 리소스 생성 성공도 업무
기능 성공을 대신하지 않는다.

### 6.3 충돌 탐지와 부분 복구

- 실제 불일치 탐지율과 정상 사례 오탐률
- 올바른 실패 소유 하위 작업 식별률
- 무관한 상류 단계 재실행 회피율
- 질문이 필요한 사례에서의 질문 정확성과 불필요 질문 수
- 답변 또는 수정 후 최종 기능 성공률과 복구 시간

### 6.4 효율성과 비용

- 전체 및 단계·하위 작업별 경과 시간
- LLM 호출 수, 토큰 수, 429·timeout·재시도 횟수
- provider 초기화·검증 시간과 캐시 적중 여부
- 클라우드 실행 시간과 compute 목록가격 기준 추정 비용
- 예산 제한이나 CSP 작업 지연으로 결과가 검열됐는지 여부

## 7. 최소 실행 순서

1. 상품 카탈로그 무상태 사례 한 셀을 끝까지 실행해 앱, Docker, IaC 및 cloud cleanup 경계를 확인한다.
2. 저장·LB·TLS 단일 변수 쌍을 `full/no-depkb`로 한 번씩 실행해 처치가 실제로 달랐는지 확인한다.
3. 3개 CSP의 정적 생성·provider 검증을 수행하고, 실제 cloud apply는 파일럿 시간·비용을 보고 확대한다.
4. 앱–클라우드 불일치 네 종류를 `full/no-consistency-validator`로 비교한다.
5. EasyDep·CoT·MetaGPT를 각 1회 실행해 비용과 실패율을 확인한 뒤 감당 가능한 반복 수를 정한다.
6. 반복 수가 부족하면 과도한 통계적 일반화 대신 사례별 원시 결과와 제한을 함께 보고한다.

## 8. 최종적으로 주장할 수 있는 범위

실험이 완료되면 다음 수준을 목표로 한다.

> EasyDep이 AWS·Azure·GCP의 Docker-on-Linux-VM 사례에서 요구사항을 CSP별 리소스와
> 연결 관계로 투영하고, 앱–클라우드 불일치를 검사하며, 생성뿐 아니라 대표 업무 기능까지
> 검증하는 단계별 개발 지원 경로를 제공한다.

DepKB 절제 결과가 확보되면 의존성 지식이 해당 제한 범위에서 리소스와 구조적 참조 누락을
줄였는지 말할 수 있다. 그러나 다음은 별도 근거 없이는 주장하지 않는다.

- 모든 클라우드 네이티브 애플리케이션과 모든 CSP 리소스를 지원한다.
- 특정 VM 후보가 실제 부하에서 최적 성능 또는 최저 총비용을 보장한다.
- EasyDep과 MetaGPT의 차이가 멀티에이전트 구조 하나 때문에 발생한다.
- 정적 IaC 검사가 실제 가용성·영속성·업무 기능 성공을 보장한다.
