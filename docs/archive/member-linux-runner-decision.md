# 멤버 구현 구간의 고정 Linux 실행 경계

## 결정

전체 EasyDep 개발 시스템을 컨테이너로 옮기지 않는다. 오케스트레이터는 호스트에서 유지하고, 멤버 구현의 생성·OpenHands 수정·Gradle/npm 빌드·애플리케이션 테스트만 하나의 고정 Linux 실행 경계로 묶는다. 클라우드 CLI와 실제 배포는 별도 권한 경계로 유지한다.

이 문서는 `docs/research.md`의 연구 배경을 변경하지 않는다. P1~P3 사례를 근거 모델로 삼지 않으며, 실제 P1-AWS 연결 실행에서 확인한 실행환경 문제와 후속 구현 범위만 기록한다.

## 실제 실행에서 확인한 근거

- Windows 호스트 경로를 Linux 컨테이너 작업 경로로 그대로 전달해 Docker가 거부했다. 오케스트레이터 전용 경로 어댑터로 호스트 경로와 `/easydep-workspace`를 연결한 뒤 생성 명령이 통과했다.
- 멤버 생성기는 존재하지 않는 `gradle:21-jdk` 태그를 요구했다. 이번 개발 실행에서는 `gradle:8.14.2-jdk21` 이미지에 로컬 별칭을 부여했으며, 이는 재현 가능한 최종 해결이 아니다.
- 최초 Gradle 실행은 classpath snapshot에 약 140초, 전체 `compileJava`·`bootJar`에 약 272초가 걸렸다. 멤버 내부 300초 제한과 가까웠고, Docker CLI 제한 뒤 컨테이너가 남아 staging 승격을 막은 사례가 있었다.
- Docker bind mount가 만든 `application/infra`의 Windows ACL 때문에 호스트 artifact 복사가 실패했다. 동일 Linux 실행 경계 안에서 생성과 검증을 끝내고 결과를 명시적으로 반출하면 이 권한 왕복을 줄일 수 있다.
- 멤버 내부 검증에서는 통과했던 산출물이 호스트의 최종 testing에서 OpenAPI 모델용 build dependency 누락으로 컴파일에 실패했다. 생성과 최종 앱 테스트가 같은 고정 환경을 사용해야 하는 직접 근거다.

## P1-AWS 연결 실행의 현재 결과

- 같은 EasyDep run과 체크포인트를 유지했다. 요구사항과 설계를 처음부터 다시 실행하지 않았다.
- 멤버 생성 manifest는 `SUCCEEDED`에 도달했고 OpenHands 계획 작업 13개가 한 시점에 모두 `SUCCEEDED`였다.
- completion audit는 backlog 0, end-to-end 누락 0, 계약 위반 0을 기록했다.
- 실제 기능 검증은 별개로 유지했다. source-design conformance와 Gradle 테스트가 불일치를 발견해 부분 수리 루프를 수행했다.
- 동일 멤버 task가 반복되는 경우 task별 초기 1회와 위임된 수리 3회를 합친 4회에서 멤버 planner를 중단하고 임시 LLM 단계로 넘기도록 오케스트레이터 경계를 제한했다. 상한을 넘은 반복을 성공으로 간주하지 않는다.
- 임시 acceptance, logic, VM delivery는 완료됐지만 최종 builtin testing은 실패했다. 현재 직접 원인은 생성된 OpenAPI 모델이 요구하는 Swagger·nullable 등 build 계약과 `build.gradle`의 불일치다. 따라서 이 실행은 종단 성공 사례가 아니다.

## 실행 경계 계약의 최소 범위

고정 Linux runner는 다음 입력만 받는다.

- 멤버 job JSON과 설계 산출물
- 고정 이미지 또는 이미지 digest
- 승인된 LLM endpoint 설정
- 작업별 시간·호출·검증 로그 설정

다음 결과만 호스트로 반환한다.

- 최종 application workspace
- run manifest와 workflow state
- 작업별 agent execution 결과와 검증 보고서
- 빌드·단위·통합 테스트 결과
- 실패한 경우 마지막 성공 체크포인트와 구조화 진단

클라우드 자격증명은 기본 이미지에 넣지 않는다. 실제 apply가 필요한 단계에서만 별도 경계로 전달하며, 실행 후 생성 자원을 정리한다.

## 체크포인트 재개 원칙

실행환경만 바뀐 경우에는 전체 개발 과정을 새로 시작하지 않는다. 다음 순서로 기존 실행을 우선 재사용한다.

1. 마지막 성공 체크포인트의 입력·산출물이 남아 있는지 확인한다.
2. 새 실행환경에서 실패했던 검증 또는 실패 하위 작업만 먼저 실행한다.
3. 산출물 자체가 현재 계약과 맞지 않을 때만 그 산출물의 소유 하위 작업을 무효화한다.
4. 요구사항·설계 같은 상위 단계는 입력이나 시스템 로직이 바뀌었거나 체크포인트 무결성이 깨졌을 때만 다시 실행한다.
5. 비교실험에서 독립 반복이 필요한 경우에는 부분 재개 결과와 신규 run 결과를 구분해 기록한다.

환경 호환 문제를 앱 로직 실패로 오분류하지 않도록 실행환경 식별자, 사용한 체크포인트, 실제 재실행 단계와 하위 작업, 재사용한 상위 산출물 해시를 결과 manifest에 남긴다. 이 원칙은 특정 P1 사례의 예외 처리가 아니라 모든 단계형 실행에 적용한다.

## 다음 구현 순서

1. 현재 오케스트레이터–멤버 입출력 파일을 그대로 사용하는 Linux runner 명령 하나를 만든다.
2. Node, OpenAPI Generator, JDK, Gradle 버전을 고정하고 생성 직후 같은 환경에서 compile과 test를 수행한다.
3. 호스트 오케스트레이터는 runner exit code가 아니라 manifest의 생성·빌드·테스트 상태를 각각 읽는다.
4. 현재 Windows 경로 어댑터는 개발용 임시 호환층으로만 유지하고 Linux runner 경로가 검증된 뒤 제거 여부를 판단한다.
5. P1-AWS 한 건에서 종단 성공을 확인한 뒤에만 다른 CSP나 사례로 확대한다.

재현성 전체를 완성하거나 모든 도구를 컨테이너화하는 작업은 이 단계의 범위가 아니다.
