# 구현 단계 OpenHands 효율 보완 계획

- 작성일: 2026-09-09
- 상태: GLM 소형·유스케이스 탐색 결과를 반영한 구현 계획. 성능 개선 완료 보고가 아니다.
- 대상: 구현 단계의 OpenHands 실행, 검증, 수리, 체크포인트 재개
- 현재 실행 구조: [구현 단계 README](../app/implementation/README.md)
- 현재 제품 상태의 기준: [현재 시스템 구성](current-system-status.md)

## 1. 목표와 범위

검증을 통과한 애플리케이션을 만드는 데 필요한 시간과 LLM 사용량을 줄인다. 작업이 완료되었다고
표시되는 비율만 높이지 않고, Testing까지 통과하는 품질과 실패 후 재개 가능성을 함께 유지한다.

결정론적 scaffold, 공개 계약 보호, 후보 workspace와 독립 검증, 완료된 source와 checkpoint
재사용은 유지한다. 보완 대상은 반복 탐색, 작업 크기, 부정확한 종료 복구, 누적 실행 비용,
재개 호환성, 측정 방식이다. 이번 계획에 OpenHands 교체나 담당자 수 확대는 포함하지 않는다.

## 2. 분석 근거와 해석 한계

현재 코드에는 다음 장치가 이미 있다.

- 백엔드와 프론트엔드 담당 대화를 각각 하나씩 실행한다.
- owner별 대화 ID와 후보 소스를 보존하고 같은 작업을 재개한다.
- 메서드별 문맥과 소스 인덱스를 제공하고 원본 설계는 필요할 때 읽게 한다.
- Gradle/npm 캐시, 대화 요약, stuck 감지와 무동작 응답 감지를 사용한다.
- 종료 후 후보 소스를 독립 검증하고 허용된 변경만 승격한다.

저장된 실행 기록은 이 장치만으로 해결되지 않는 위험도 보여 준다.

| 기록 | 관찰 | 보완 방향 |
|---|---|---|
| `run_0b7e5a6306fe` 백엔드 attempt 1·2 | 약 312초·terminal 84회 후 실패하고, 같은 대화 재개 후 약 313초·terminal 92회로 다시 실패 | 대화 재사용과 별도로 실제 진전 감지 필요 |
| 위 attempt 2 이벤트 | 동일 소스 조회 명령이 최대 6회 반복되고, 초반 Gradle 실패 이후에도 조회가 이어짐 | 실패 증거를 수정 행동으로 연결하고 반복 읽기 축소 |
| `run_fa1721b147c5` 백엔드 attempt 1 | 약 22분·도구 174회, 에이전트 누적 입력 6,318,400토큰으로 성공 | 성공당 누적 사용량과 지연을 측정 |
| 위 대화 attempt 2 | `terminal` 제거에 따른 도구 구성 불일치로 재개 실패 | 저장 대화와 실행 환경의 호환성 사전 확인 |

위 기록은 이전 도구 구성과 실행 조건을 포함한다. 현재 코드의 성공률이나 평균 성능으로
합산하지 않는다. 누적 입력 토큰은 여러 요청에서 처리한 토큰의 합이며 단일 문맥 크기가 아니다.
6,318,400토큰 사례에는 캐시 읽기 2,241,024토큰이 별도로 기록되어 있다. 비용 필드의 `0.0`은
실제 무료 사용의 증거가 아니므로 과금 금액으로 사용하지 않는다.

### 2.1. GLM 탐색 뒤 바뀐 가정

2026년 9월 10일의 실제 `@cf/zai-org/glm-5.3-flash` 실행에서는 전체 backend owner뿐 아니라
UC10 전체와 application 단계도 source 변경 전에 탐색이 길어졌다. 반면 같은 모델이 짧은 행동
capsule을 받은 단일 domain marker는 38초와 7개 도구 행동으로 구현·compile을 마쳤다. 자세한
수치는 [하네스 구현 검증](openhands-agent-harness-validation.md)에 기록했다.

따라서 백엔드 전체를 한 대화에 맡긴다는 기존 가정은 유지하지 않는다. 유스케이스는 진행·재개를
위한 상위 checkpoint로 유지하고, 실제 LLM 대화는 operation marker 또는 서로 강하게 결합된
작은 marker 묶음으로 순차 실행한다. source 위치는 탐색 시작 힌트이고 주변 main source의 읽기와
필요한 보조 변경은 허용한다. 유스케이스별 병렬 구현은 이번 단계에서 제외한다.

첫 자동 capsule은 확장 시나리오 누락과 원본 설계 재탐색 때문에 편집 없이 끝났다. 생성기가
확장 step과 명시적인 구현 기본값을 넣은 뒤에는 같은 domain marker가 61초에 성공했고, 다음
`createTerm` marker도 이전 source를 이어받아 성공했다. 따라서 단순 분할만으로는 부족하며,
marker가 바로 코드로 옮길 수 있는 행동 사실과 이미 정한 구현 관례를 함께 전달해야 한다.
같은 성공 source를 checkpoint로 재사용한 뒤 8K·medium 조건에서
`updateRegistrationPeriod`(125초)와 HTTP adapter(183초)도 순서대로 compile을 통과했다. 두 실행은
각각 배정된 source 한 개만 바꿨고 endpoint retry나 finish-recovery는 없었다.

이후 8K/16K 상한 비교는 중단하고 adapter의 첫 편집 전 탐색을 직접 줄였다. raw API JSON을
endpoint·service 호출·인자·응답 상태 규칙으로 바꾸고 generated API/DTO/control의 정확한 경로를
제공한 같은 adapter 실행은 108초에 끝났다. 이전과 비교해 첫 편집 전 읽기·검색은 19회에서 8회,
전체 event는 46개에서 24개, prompt token은 220,687에서 68,695로 줄었다. 남은 두 grep이 찾은
반환 domain 경로와 Java getter 표현을 당시 실험 capsule 후보에 포함했으며, 이 마지막 보완을
위한 별도 성능 재측정은 하지 않았다.

후속 일반화 검토에서는 위 실험의 `create/update/set`, `*Id`, `*Start/*End`, 결과 label, 반환 타입
이름을 이용한 규칙이 UC10에 과적합된 것으로 판정했다. 이 규칙과 추정 Java getter·Repository·
Entity 경로는 제품 코드에서 제거했다. 현재 capsule은 canonical ID, 승인된 `sourceRef`, BCE
stereotype, HTTP status/schema처럼 명시된 계약만 사용한다. 성공 상태가 여러 개인데 selector가
없거나 오류 상태에 exception/result 연결이 없으면 이름으로 고르지 않고 설계 공백으로 남긴다.
따라서 108초 수치는 압축된 capsule의 탐색 감소를 보여 주는 과거 관측값이지, 제거된 이름
휴리스틱을 다시 도입할 근거가 아니다.

기록 위치는 다음과 같다. 로컬 실행 산출물이므로 다른 checkout에는 없을 수 있다.

- 반복 실행: `.easydep/implementation-runs/b86d418472ee454e85acc5d171c61431/generated/runs/run_0b7e5a6306fe/reports/agent-executions/`
- 성공 및 재개 실패: `.easydep/implementation-runs/169e8e9b46d743db97d839aedc4ef7ff/generated/runs/run_fa1721b147c5/reports/agent-executions/`
- adapter 병목 개선: `.easydep/experiments/glm-5.3-flash-adapter-bottleneck-002/`

| 순서 | 작업 | 주요 변경 대상 | 완료 기준 |
|---|---|---|---|

| P0-2 | 실행·수리 누적 예산 도입 | `agents/runtime.py`, `workflows/coordinator.py`, `config.py` | 재개와 수리에서도 누적 예산이 유지됨 |

| P1-2 | marker 행동 capsule과 순차 유스케이스 checkpoint | planner, `planning/design_context.py`, coordinator | 이름 추론 없이 명시된 계약으로 단일 marker 성공을 이어 붙이고 유스케이스 완료 상태를 보존 |
| P1-3 | 문맥·도구 출력 사용량 절감 | `planning/design_context.py`, `workflows/repair.py` | 품질 저하 없이 반복 읽기와 입력량 감소 |

위 경로는 `app/implementation/` 기준이다. 공통 설정 변경이 필요하면 `app/config.py`에도
연결한다. 책임이 다른 계층에 같은 재시도 정책을 중복 구현하지 않는다.

P1-2의 탐색 구현은 현재 opt-in이다. `IMPLEMENTATION_BACKEND_TASK_STRATEGY=marker`에서만
operation marker 계획을 만들고 기본 `owner` 경로는 유지한다. marker 작업은 테스트 source를
소유하지 않으며 `marker 제거 + compileJava`까지만 확인한다. GLM 조건과 작업 구조가 확정된 뒤
테스트 작성 checkpoint를 열어 확장 step 투영, 순차 계획, marker·검증 증거 계약의 최소 회귀
사례와 GLM 8K runtime profile 사례 네 개를 추가했고 모두 통과했다. 조건 하나를 바꿀 때마다
제품 테스트 코드를 새로 생성하거나 수정하는 방식은 계속 사용하지 않는다. 실제 생성
애플리케이션의 제품 테스트는 대표 유스케이스 실행을 더 확인한 뒤 별도 checkpoint에서 작성한다.

## 4. P0: 종료 처리와 실행 경계

### 4.1. 종료 복구 조건

현재 `_conversation_needs_finish_recovery()`는 `FINISHED`와 `STUCK` 이외의 typed 상태를
복구 대상으로 포함한다. 검증 성공을 확인하지 않은 채 검증을 이미 실행했다는 메시지를
보낼 수 있다. 뒤의 독립 검증은 유지되지만 불필요한 호출과 잘못된 수리 경로가 발생할 수 있다.

복구 정책은 다음과 같이 나눈다.

| 상태·증거 | 처리 |
|---|---|
| `FINISHED` | 독립 검증과 승격 경계 검사로 진행 |
| 종료 도구 누락, 현재 후보에 대한 신뢰 가능한 검증 성공 증거 있음 | 작은 별도 예산으로 종료 도구 호출만 요청 |
| 종료 도구 누락, 검증 성공 증거 없음 | 검증을 실행하거나 미완료로 기록. 성공을 전제한 메시지 금지 |
| `STUCK` | 최근 실패·진전 증거가 포함된 복구를 제한적으로 수행 |
| `ERROR`, iteration 초과, provider 오류 | 실제 원인별 처리. 종료 도구 누락 복구에서 제외 |

SDK 상태 목록과 원인 정보는 설치된 버전의 typed API로 확인한다. 자연어 오류 문자열만으로
새로운 상태 분류기를 만들지 않는다. 종료 전용 복구의 초기 실험값은 2 iteration으로 두되,
설치 SDK에서 호출별 예산을 바꾸는 지원 방식과 경계 동작을 먼저 검증한다.

검증 증거에는 후보 소스·build 설정·의존성 해시, 실행 명령, 종료 코드, 실행 시점을 연결한다.
검증 후 소스가 바뀌었으면 이전 성공 증거를 종료 판단에 사용하지 않는다. 에이전트가 출력한
성공 문장이나 수정 가능한 보고 파일만으로 검증 성공을 인정하지 않는다.

이 조건은 구현에 반영했다. 제한 도구의 `run_task_check`가 현재 source snapshot에서 성공한
기록이 있을 때만 종료 전용 복구를 허용한다. iteration 초과나 marker 잔존 상태에서는 같은
대화에 “검증이 끝났다”는 종료 메시지를 보내지 않는다.

### 4.2. 누적 예산과 중단 후 재개

현재 owner의 96 iteration은 `conversation.run()` 한 번의 제한이다. stuck·finish 복구에서
다시 `run()`을 호출하며, 일반 검증 실패 수리는 기본 횟수 상한이 없다. 작업 전체 예산을
추가하고 모든 재개·수리 경로에서 같은 누적 사용량을 참조한다.

다음 값은 새로 도입할 제안 필드이며 현재 저장 계약이 아니다.

- `budgetPolicyVersion`: 적용한 예산 정책 버전
- `usageScope`: job·run·task·conversation 식별자
- `activeDurationMs`: 실행 중 소비한 누적 시간. 사용자가 중단한 대기 시간은 제외
- `agentUsage`, `condenserUsage`: 에이전트와 요약 모델의 누적 사용량
- `repairCycleCount`, `recoveryCount`: 수리 및 실행 복구 누적 횟수
- `stopReason`, `remainingBudget`: 중단 사유와 남은 예산

기존 96 iteration을 최초 비교의 기준으로 유지한다. 총 시간·토큰·수리 횟수의 상한은 작업
규모별 기준선에서 결정하며, 임의의 단일 값을 모든 앱의 최적값으로 선언하지 않는다.
예산 정책과 구체적인 제한값은 실험 시작 전에 고정하고 결과 manifest에 남긴다.

예산은 LLM 호출·수리 시작 전에 확인하고 호출 완료 후 누적한다. 호출 중에는 별도의 요청
timeout이 필요하므로, 호출 사이의 예산 검사만으로 정확한 실시간 상한을 보장한다고 표현하지
않는다. provider 재시도는 SDK 경로에 맡기고 바깥에 동일한 재시도 루프를 추가하지 않는다.

예산 소진 시 후보·대화·마지막 검증 증거를 보존한다. 처음부터 다시 시작하거나 성공한 다른
담당자를 재생성하지 않는다. 기존 상태 모델에 중단 사유를 매핑하고 사용자 재개 경로를 연결한다.
예산을 연장할 때에도 누적 사용량은 초기화하지 않고 연장 이력을 남긴다.

### 4.3. 체크포인트 호환성

재개 manifest에 다음 정보를 추가한다.

- 앱 ID, job ID, run ID, task ID, conversation ID
- 완료 단계, 설계 snapshot 해시, accepted source와 후보 source 해시
- OpenHands SDK·tools 버전과 도구 스키마 해시
- runner 이미지 digest, workspace 경로 규칙 버전
- 모델·provider 식별자, prompt·예산 정책 버전. 비밀값은 기록하지 않음

ID와 산출물 대응을 확인한 뒤 도구 구성을 SDK의 복원 계약과 비교한다. 이미지나 버전이
바뀌었다는 이유만으로 무조건 거부하지 않고, 반드시 일치해야 하는 항목과 검증 가능한 변경을
구분한다. 모델 설정 변경은 도구 제거와 같은 오류로 취급하지 않는다.

기존 manifest에 필드가 없으면 확보 가능한 증거를 검사하고 확인 불가능한 항목을 명시한다.
호환성을 확인할 수 없는 대화를 새 대화로 조용히 대체하지 않는다. 먼저 원래 도구·환경을
복원할 수 있는지 확인하고, 실패하면 구체적인 불일치와 복구 경로를 보고한다.

## 5. P1: 탐색·문맥·검증 비용

### 5.1. 진전 관찰과 복구 메시지

SDK stuck 감지는 유지한다. 추가 관찰은 먼저 실행을 중단하지 않는 기록 모드로 적용한다.
LLM 감독자를 추가하지 않고 기존 이벤트와 검증 결과를 이용한다.

- 소스 내용 변경, 미구현 marker 감소, 검증 실패 지문 변화를 기록한다.
- 파일·조회 구간·내용 해시가 같은 반복 읽기를 집계한다.
- 같은 검증 입력에서 같은 실패가 반복되는지 확인한다.
- 테스트 삭제나 단순 변경 파일 수 증가를 진전으로 인정하지 않는다.

탐색 초반에 파일을 읽는 것은 정상이다. read-only 호출 횟수만으로 중단하지 않으며 진전 지표
하나만으로 완료를 판단하지 않는다. 터미널 명령의 읽기 범위를 정확히 해석할 수 없으면 반복
조회 여부를 미상으로 남긴다. 변경 없는 긴 조사 구간은 관찰 기록과 실제 결과를 대조한 뒤
개입 기준을 정한다.

재개 메시지는 현재 후보 해시, 마지막 검증 실패, 남은 구현 항목, 이미 시도한 수정과 결과,
다음 검증 명령을 짧게 전달한다. 원래 설계와 전체 실행 이력을 다시 붙이지 않는다. 동일 실패와
동일 소스가 반복되면 예산 안에서 원인 분류를 수행하고, 추가 시도가 유효하지 않으면 증거와
함께 중단한다.

### 5.2. 문맥과 도구 출력

현재 source-index와 method-context를 재사용한다. 긴 출력의 원문은 파일에 남기고 모델에는
관련 구간과 원문 위치를 제공한다. 편집 대상의 정확한 본문이나 오류 원인을 과도하게 축약하지
않으며, 필요한 원문은 다시 읽을 수 있어야 한다.

대화 요약에는 완료한 수정, 미해결 오류, 유지해야 할 계약, 현재 경로와 검증 명령을 보존한다.
요약 누락으로 이미 확인한 파일을 다시 읽는지도 측정한다. SDK 기본 condenser를 기준선으로
두고 임계치 변경을 비교한다. 더 저렴한 요약 모델로의 변경은 별도 실험으로 분리한다.

### 5.3. 검증 비용

작업 중에는 변경에 관련된 낮은 비용의 검증을 사용하고, 승격 전 독립 검증은 유지한다.
canonical 명령의 도구 버전·프로필·캐시 설정을 실제 검증기와 일치시킨다. 실패 로그를 더
자세히 보기 위한 동일 명령 재실행 대신 저장된 진단 파일을 읽게 한다.

검증 재사용은 첫 보완에서 필수로 도입하지 않는다. 반복 비용을 측정한 뒤 효과가 큰 경우에만
소스·설정·lockfile·도구 버전·검증 명령을 포함한 캐시 키를 설계한다. 동적 외부 상태에 의존하는
검사는 소스 해시만으로 재사용하지 않는다. 증거는 owner가 수정할 수 없는 위치에 저장한다.

22분 성공 사례의 독립 검증은 약 86초였다. 이 사례에서는 독립 검증 제거보다 반복 에이전트
호출 감소의 기대 효과가 크다. 구현 단계 빌드 성공을 Testing의 기능 검증 통과로 대체하지 않는다.

## 6. 구현 순서와 검증

| 단계 | 산출물 | 확인 항목 |
|---|---|---|
| 1 | 종료 정책과 회귀 테스트 | `ERROR` 제외, 성공 증거 없는 종료 복구 방지, 검증 후 변경 탐지 |
| 2 | 누적 예산 저장·중단·재개 | 재시작 후 사용량 유지, 요약 비용 포함, 예산 소진 후 무한 자동 재개 방지 |
| 3 | 재개 manifest와 사전 검사 | 도구 제거·스키마 변경·ID 불일치·구버전 manifest 처리 |
| 4 | 진전 관찰과 압축된 복구 증거 | 정상 조사 오탐, 반복 실패 식별, 불완전 이벤트 처리 |
| 5 | 문맥·검증 최적화 | 계약 보존, 요약 후 작업 연속성, 캐시 무효화 |
| 6 | 동일 조건 평가 보고 | 시간·비용 개선과 Testing 통과율을 함께 확인 |

상태·예산·호환성 테스트는 실제 LLM 없이 먼저 검증한다. 기존 테스트는 최소한 다음 파일에서
변경에 관련된 범위를 실행한다.

- `tests/test_implementation_engine.py`
- `tests/test_implementation_worker.py`
- `tests/test_linux_runner_transport.py`
- `tests/test_shared_toolchain_validation.py`

앞선 분석에서는 종료 복구·무동작 감지·provider 재시도 중복 방지·실패 저장 관련 기존 테스트
4개를 실행해 통과했다. 이는 새 정책의 검증 결과가 아니다. 특히 기존 종료 복구 테스트에는
`ERROR` 상태와 검증 증거 유무에 대한 회귀 사례를 추가해야 한다.

네트워크를 사용하는 검증은 처음부터 필요한 권한으로 실행한다. sandbox 차단, 429, 스트림
미종료, 실제 timeout을 별도 원인으로 기록한다. 실패한 하위 단계부터 재개하고 임시 프로필·캐시를
저장소에 만들지 않는다. Python 실행은 `-X utf8`을 사용한다.

## 7. 성능 평가와 적용 기준

현재 코드를 고정한 기준선과 보완 코드를 같은 입력으로 비교한다. 과거 결과는 사례 분석에만
사용한다. 설계 snapshot, source revision, SDK·tools, runner digest, 모델·provider, reasoning
설정, 예산 정책, 캐시 조건을 실행 manifest에 저장한다.

소형·중형·상대적으로 큰 앱을 선정하고 각 조건을 우선 3회씩 반복한다. 표본이 작을 때는
개별값·중앙값·범위를 보고하고 p95나 통계적 우월성을 확정하지 않는다. 캐시가 비어 있는 실행과
준비된 실행은 구분한다. 초기 생성과 Testing finding에 따른 수리도 별도 집계한다.

| 지표 | 집계 원칙 |
|---|---|
| 최종 성공률 | 고정된 필수 Testing gate까지 통과한 작업 비율 |
| 최초 시도 통과율 | 추가 수리 없이 필수 검증을 통과한 작업 비율 |
| 완료 시간 | 능동 실행 시간과 사용자 대기를 포함한 전체 경과 시간을 구분 |
| 토큰·비용 | agent·condenser, 캐시·비캐시 정보를 구분하고 실제 과금 자료가 있으면 대조 |
| 성공당 사용량 | 실패한 시도의 소비까지 포함한 전체 소비를 최종 성공 건수로 나눔 |
| 반복 탐색·수리 | 같은 파일 조회, 같은 실패 지문, 수리·복구 횟수 |
| 재개 신뢰성 | 호환되는 checkpoint의 재개 성공률과 사전 불일치 탐지 결과 |
| 검증 비용 | LLM 실행·내부 검증·독립 검증 시간을 중복 합산하지 않고 구분 |

대화별 통계는 누적값일 수 있으므로 시도별 누적 snapshot을 그대로 더하지 않는다. 동일 대화의
전후 차분을 구하고 reset·누락을 별도 표시한다. 금액을 알 수 없으면 0원이 아닌 미상으로 기록한다.
실행 중단으로 끝난 표본도 실패·중단과 사용량 집계에서 제외하지 않는다.

기본 적용 조건은 필수 계약·Testing 검사를 약화하지 않고, 기준선의 통과 사례에서 설명되지
않는 회귀가 없으며, 시간 또는 성공당 사용량이 줄어드는 것이다. 반대 지표가 악화되면 그 크기와
원인을 명시한다. 작은 표본의 성공률 동일만으로 품질 동등성을 입증했다고 보고하지 않는다.

백엔드·프론트엔드 병렬화는 P0·P1 이후 별도 비교한다. 같은 frozen API를 사용하는 두 후보의
격리, 승격 충돌, provider 요청 제한, 통합 수리 증가를 확인한 뒤 결정한다. 처음부터 유스케이스별
다중 작업자로 확대하지 않는다.

## 8. 적용과 되돌리기

종료 상태의 잘못된 분류는 회귀 검증 후 먼저 수정한다. 예산은 관찰값을 확인한 뒤 제한을
활성화하고, 진전 감지와 문맥 조정은 관찰 모드에서 효과를 확인한 뒤 적용한다. 각 실행에 정책
버전을 남겨 결과를 비교할 수 있게 한다.

성공률 하락이나 정상 조사 중단이 관찰되면 해당 정책의 개입만 끄고 이벤트와 사용량 기록은
유지한다. checkpoint와 후보 소스를 삭제하지 않는다. 신규 필드가 없는 기존 실행도 읽을 수
있도록 하고, 되돌리기가 필요한 경우 저장 상태와 도구 구성의 호환성부터 확인한다.

완료 보고에는 적용한 정책, 코드 revision, 실행 조건, 원시 결과 위치, 회귀 검증 결과와 남은
한계를 기록한다. 상세 계획은 완료 후 보관소로 옮기고 현재 동작은 구현 README와 상태 문서에
반영한다.
