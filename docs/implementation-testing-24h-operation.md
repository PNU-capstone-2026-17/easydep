# 구현·테스팅 작동 검증: 자율 작업 기준

## 목표와 완료 기준

- 최대 24시간 동안 EasyDep의 **실제 구현·테스팅 경로**를 작동 가능한 수준으로 개선한다. 목표가 먼저 달성되면 즉시 종료한다.
- `EASYDEP_DEMO_SKIP_VALIDATION` 같은 데모 우회 없이 Workspace API의 정상 경로에서 구현 소스가 생성되고 관련 검사가 실행되어야 한다.
- 테스팅 프로필과 실제 실행 결과가 생성·저장되고 단계가 정상 종료되어야 한다. 개별 테스트 실패는 정확히 실패로 기록할 수 있지만, 예외나 미실행을 PASS로 바꾸지 않는다.
- 작은 합성 앱으로 변경 지점을 확인한 뒤, 16개 요구사항 수강신청 앱에서 구현·테스팅 경로를 확인한다. 매번 새 종단 실행을 만들지 않고 일치하는 기존 체크포인트를 우선 재개한다.

## 자율 작업 규칙

1. 매 반복은 **관찰한 증거 → 하나의 원인 가설 → 최소 변경 → 그 가설만 검증**하는 단위로 제한한다. 실제 소스 변경, 진단 변화, 완료 단계의 진전으로 효과를 판단한다.
2. 같은 국소 실패로 수정·실행이 반복되면 방어 코드나 특수 분기를 계속 쌓지 않는다. 원인과 시도 결과를 기록하고, 더 넓은 구조 문제인지 재판단하거나 다른 진행 경로를 선택한다. 직접 막지 않는 결함은 기록만 한다.
3. 영향받는 작은 검사와 소규모 **실제 LLM 호출**을 먼저 수행하고, 통과한 변경을 모아 종단 실행은 필요한 횟수로만 한다. 합성 앱에 관한 저장소의 LLM 호출·컨텍스트 전송은 사용자가 일괄 승인했으므로 전송 허락을 반복해서 묻지 않는다. 실행 환경의 권한 차단은 승인 부재와 구분하여 처리한다.
4. Luna/Terra가 가능한 일상적인 조사·편집·실행을 맡고, root는 가설·범위·통합 판단에 집중한다. 무거운 JDK·컨테이너 실행을 불필요하게 겹치지 않는다.
5. DB 스키마나 생성 앱 산출물을 직접 수정하지 않는다. 기술적 재시도와 서버 재시작은 자율적으로 진행한다. 제품 의미를 바꾸는 실제 사용자 결정은 시스템의 근거 있는 질문·선택지 경로로 요청하며, 임의의 자유 피드백으로 대신하지 않는다.
6. 24시간이 끝나거나 목표가 달성되면 완료된 경로, 남은 차단 요인, 검증 증거를 보고한다. 세션 중단에 대비해 진행 상황과 체크포인트 식별자를 기록한다.

## 보류 중인 분석 결과

- 수강신청 앱 `cdf30533-63ad-4519-a774-5c49b54d120e`의 **구조화 명세**에서는 UC2 학생 등록의 신원 값·출처가 빠지고 UC7 대기열 등록의 필수 값 목록이 비었는데도 의미 검사 결과가 `ok`다. 이것만으로 원 요구사항에 결정이 없다고 단정하면 안 된다.
- 원문과 RR1에는 보호된 작업의 인증된 신원·역할이 전제된다는 근거가 있다. RR14는 역할 기반 인가를 요구한다. 그러나 현재 RTM에서 RR1·RR14의 `constrains_use_cases`가 비어 있고 UC2·UC7의 `nfr_ids`도 비어 있어, 해당 전역 근거가 개별 명세 생성·검토의 입력으로 전달되지 않는다. UC4·UC8 명세에는 동일 학생의 인증 컨텍스트 출처가 이미 표현돼 있다. 먼저 전체 근거를 대조해 구조화·연결 누락인지 실제 사용자 선택인지 판단한다.
- 현재 정적 검사는 이미 선언된 신원 의무와 필수 값의 연결을 검사하지만 둘 다 빠진 계약은 발견하지 못한다. 신원 출처 선택지 질문은 기존 `identify` 의무가 `unresolved`일 때만 열리고, 제안 스키마는 값 출처를 미리 세 가지 중 하나로 고르게 한다. 이는 질문 경로의 도달성 문제이지만, **근거 전달 누락을 해결하기 전에 질문을 늘리는 근거로 사용하지 않는다.**
- 이전의 근거 없는 질문을 막는 검사는 유지한다. 역할명·식별자 변수명만으로 신원 출처를 추측하지 않고, 구체적인 동작·필수 값·전역 제약·관련 RTM을 함께 검토한다. 직접 막는 범위에서만 고치고 요구사항 단계 전체를 다시 만들지 않는다.

### 2026-09-25 소규모 실모델 확인

- 현재 저장 명세에 RR1·RR14를 전역 문맥으로 추가하고 실제 OSS `openai/gpt-oss-120b`의 `spec.public-behavior-completeness` 검토를 유스케이스당 한 번씩 실행했다. UC2는 신원 의무 누락을 찾았지만, UC7은 누락을 찾지 못했고, UC1 검색에는 인증 역할 의무를 추가하라는 근거 부족 판단이 나왔다. DB나 산출물은 수정하지 않았다.
- 따라서 **전역 제약을 모든 UC에 단순 전달하는 수정만으로는 충분하지 않다.** 보호 여부와 해당 동작에 필요한 행위자 신원을 별도로 구분할 수 있는 일반적인 검토 지침이 필요하다. 이 판단을 여러 도메인의 작은 실호출로 확인하기 전에는 광역 문맥 전달을 적용하지 않는다.
- UC7은 UC2의 수강신청 거절 이후에 실행되는 `<<extend>>` 관계다. UC7에 새 사용자 입력을 무조건 추가해야 한다고 단정할 수 없으며, 거절된 신청의 과목 정보와 인증된 행위자 신원을 이어받는 흐름도 검토해야 한다. 현재 클래스 협력 모델은 UC7 Control의 두 인자를 아직 실행되지 않은 Boundary 결과 필드에 연결해 순환하므로, 실제 차단은 **문맥 전달을 표현하지 못한 설계 값 연결**에도 있다.
- RR1처럼 선언적 역할 설명과 실제 운영 전제조건이 섞인 NFR을 기존 추적성 프롬프트가 `null`(제약 아님)로 취급할 수 있었다. 이를 `[]`(명시적인 전역/미지정 제약)로 분류하도록 좁은 프롬프트 보완을 했고, 실제 OSS 호출 3개에서 혼합 제약 `[]`, 순수 선언문 `null`, 특정 작업 제약 `['UC2']`가 확인됐다.
- 전역 인증 문맥을 구분하라는 더 엄격한 일회성 OSS 검토에서는 UC1 검색에 대한 근거 부족 지적은 없어지고 UC2 누락은 검출됐지만 UC7은 여전히 검출되지 않았다. 생성기 소규모 호출에서도 UC2·UC7의 신원 값은 생성되지 않았다. 같은 검토 프롬프트를 계속 재시도하지 않고, UC2는 **신원 의무와 연결된 식별 값을 함께 요구하는 수리 지시**, UC7은 상위 유스케이스에서 이어지는 실행 문맥의 표현 여부로 나눠 처리한다.
- 변경된 전역 문맥 전달과 수리 지침을 합쳐 다시 호출했을 때는 UC2 누락을 놓치고 UC7에는 파생 필드 `identity_source_kind`를 직접 바꾸라는 잘못된 지시가 나왔다. 공개 계약만 Pydantic으로 받는 별도 소규모 호출은 UC2를 올바르게 연결하고 UC1을 보존했지만 UC7은 무효한 인증 출처 연결을 냈다. 같은 구조를 다른 도메인 둘에 적용하자 신원 의무의 대상·인덱스가 다시 어긋났다. **현재 OSS의 자유문장 검토와 `PublicBehaviorContract` 직접 생성 중 어느 것도 이 계약을 안정적으로 완성한다고 입증되지 않았다.** 더 많은 같은 프롬프트 재시도나 새 수리 엔진 추가는 보류하고 직접 차단 중인 설계 값 연결을 별도로 확인한다.

### 소형 앱 구현·테스팅 경로 확인

- 기존 단일 사용자 계산기 앱 `207f67d0-58ac-4983-85c0-d3854a3092a6`의 설계 완료 command `db5981e9-7838-439e-9645-385573912102`를 사용한다. 새 앱이나 설계 실행을 만들지 않는다.
- 이전 구현 command `c551ebc8-d82d-496a-b19b-ee91d5cc829b`는 중단 상태이고 저장된 소스·테스트 산출물 버전이 없다. 재개를 한 번 시도한 command `124c2436-e7fd-4b89-ac91-52ef086fc3e1`은 기존 job `26ee9afa028e489fa55386c38d5a54f7`의 저장된 OpenHands 하네스 계약이 현재 정책 v8/프롬프트 v9/도구 스키마와 달라 실패했다. 이 job은 더 재시도하지 않는다.
- 8100 EasyDep 서버를 현 코드로 재시작했으며 데모 검증 우회는 꺼져 있다. 같은 설계 완료 체크포인트에서 현 계약의 구현 job을 한 번 새로 시작해 소스 생성·검사 결과를 확인한다. 구현이 완료되면 해당 완료 command와 job ID로 `start_testing`을 호출하고, 생성된 Arazzo 계획뿐 아니라 워크플로별 실제 실행 결과가 저장됐는지 확인한다.
- 같은 앱의 `start_implementation`은 현재 체크포인트에서 액션이 제공되지 않아 409를 반환한다. 실패한 command의 `retry_implementation`은 이전 job·하네스 manifest를 재사용하므로 호환성 오류를 반복한다. 기존 정상 API인 `rerun_from_stage`에서 `restart_stage=implementation`으로 완료된 설계를 새 분기 앱에 복사하고 현 하네스로 새 구현 job을 한 번 시작한다. 이는 설계 재실행 없이 체크포인트를 재사용하는 경로다.
- 실제 분기 command `8983b728-4a3c-4043-b485-6ecd62873238`은 새 앱 `276745f6-55d9-4c60-b72f-61a60b5c02fb`와 설계 v1 및 완료된 설계 진입 command `681abf58-0022-45df-ba43-3660b2e5620f`를 만들었으나, 해당 진입 command가 `start_implementation` 대신 `Continue conversation`만 제공해 409로 중단됐다. 새 분기를 반복하지 않고, 완료된 설계 분기의 액션 노출 결함을 일반적으로 수정한 뒤 이 앱에서 재개한다.
- 원인은 분기 진입 기록에는 검증된 설계 산출물이 있지만 LangGraph 설계 실행 체크포인트가 복사되지 않아 `design_complete` 힌트가 계산되지 않는 점이다. 완료된 `branch_checkpoint`의 `checkpoint_stage=design`이면 구현 시작을 제공하도록 액션 레지스트리를 좁게 수정했고, 집중 회귀 테스트 1개가 통과했다. 이후 기존 분기 앱에서 실제 액션 노출과 구현 시작을 확인한다.
- 서버 재시작 후 기존 분기 앱에서 `start_implementation`이 노출돼 command `4c461c6b-54e1-40ed-a404-746db217a14b`, job `c984ecc7a0ec4c628ce3a366d9b1d14f`가 정상 생성됐다. 그러나 초기 구현 입력 검증이 다이어그램의 `participant_ref` 및 여러 메시지의 `call_ref`/`operation_ref` 누락으로 실패해 소스·테스트 산출물은 저장되지 않았다. 오래된 설계 체크포인트의 스키마와 현재 생성기의 결함을 구분한 뒤 진행하며, 같은 job을 반복하지 않는다.
- 기존 설계 스냅샷은 현재 참조 필드 스키마보다 오래됐고, 제한된 기존 앱 조사에서 현 스키마에 유효한 완료 설계를 찾지 못했다. 따라서 계산기 앱의 요구사항 완료 체크포인트에서 설계만 재실행해 새 분기 앱 `d2729fb8-59b4-4814-82c9-2830d962b883`을 생성했다. 설계 command `841283da-e218-4c03-8b0c-e777197d3320`은 현재 OSS 호출 후 최종 BCEModel 합성에서 미선언 타입 `CalculationResult`로 실패했다. 조각 단위 수리는 있지만 최종 합성 검증은 그 밖에서 실패하며, 원 LLM 후보는 command에 저장되지 않았다. 기존 `retry_design`이 실패한 클래스 노드만 다시 생성할 수 있어 한 번 재시도하고, 반복되면 이름별 예외 대신 합성 검증 경계의 일반 수리 문제로 다룬다.
- `retry_design` command `02064d56-72ea-491b-b199-6dfef9f7f0f7`은 BCE 오류를 지나 UC1 `operand1` 출처 질문을 생성했다. 원 요구사항·RR2·UC1 주 흐름에는 사용자가 두 숫자를 입력한다고 명시돼 있어 실제 사용자 결정이 아니다. 재사용한 오래된 요구사항 명세에는 현재 스키마의 `public_contract`/`required_values` 필드 자체가 없어 클래스 값 연결의 근거가 빠졌다. 이 앱에 호환성 보정을 덧붙이지 않고, 현재 요구사항 생성기부터 새 소형 앱을 한 번 실행해 필수 입력 계약이 구조화되는지 확인한다. 질문에 Codex가 답하지 않았다.
