# 상호작용 설계 개선과 LLM 호출 최적화

이 문서는 클래스·시퀀스 설계 수직 교체 이후 남은 개선 사항과 LLM 호출 운영 원칙을
기록한다. 현재 생성 계약은 [클래스·시퀀스 설계 생성 로직](class-design-pipeline.md)을
따르며, 여기서는 아직 해결하지 않은 문제와 다음 변경의 성공 조건만 다룬다.

## 현재 기준선

- 클래스 단계가 BCE 구조, 메서드 계약, 호출 트리와 값 출처를 소유한다.
- 시퀀스 단계는 저장된 `Collaborations`를 결정론적으로 투영한다.
- 모든 호출에는 대응하는 반환 메시지가 있다.
- 긴 요구사항·설계 LLM 호출의 기본 동시성은 2다.
- 호출 대상과 모호한 값 바인딩은 실제 후보로 구성한 유한 enum에서만 선택한다.
- 실패 시 전체 모델이 아니라 실패한 실행 슬라이스만 한 번 교체한다.

이 기준선은 E2E 사례의 클래스·시퀀스·API·ERD·배포 생성, CSP별 IaC 정적 검사를
통과했다. 다만 기계 검증 통과는 다이어그램의 가독성이나 도메인 설계의 유일한 정답을
뜻하지 않는다.

## 남은 개선 사항

### 우선순위 높음

1. **클래스 다이어그램 밀도**
   현재 BCE 클래스와 모든 DTO·enum을 한 화면에 펼치므로 타입이 많으면 가로 폭이 크게
   늘어난다. 구조화 모델이나 산출물 종류를 추가하지 않고, 같은 PlantUML에서 BCE 중심
   배치, 타입 접기 또는 패키지 배치를 적용한다. 성공 조건은 메서드 시그니처와 관계를
   잃지 않으면서 주요 BCE 흐름을 기본 화면에서 읽을 수 있는 것이다.
2. **ERD 외래키 중복 표현**
   Entity에 이미 존재하는 참조 필드와 관계 투영 과정에서 합성한 외래키가 같은 의미를
   다른 이름으로 중복 표시할 수 있다. 이름 문자열의 유사성으로 지우지 말고, 관계의
   source field와 target identifier를 정규화한 뒤 기존 필드를 재사용한다. 성공 조건은
   논리 속성을 보존하면서 관계당 하나의 명시적 외래키 경로만 남는 것이다.
3. **정성 평가의 반복 가능성**
   클래스 개수나 해시를 정답으로 고정하지 않는다. 대신 요구사항 충실성, 책임 응집도,
   값 출처 완결성, 호출·반환 가독성, 불필요한 타입과 관계의 비율을 동일한 검토표로
   기록한다. 사례 고유 이름을 검사 규칙에 넣지 않는다.

### 후속 개선

- 사용자 피드백이 전역 구조, 메서드 조각, 협업 중 어느 수정 대상을 바꿨는지 진행
  이벤트에서 더 명확히 표시한다.
- 체크포인트 재개 시 입력 digest뿐 아니라 사용한 prompt/schema 버전도 함께 비교하여
  생성 계약이 바뀐 결과를 오래된 캐시로 오인하지 않게 한다.
- API·ERD가 클래스 계약을 소비할 때 임의 `dict` 접근을 줄이고 경계에서 한 번 검증된
  모델을 사용한다.
- 유일한 골드셋은 회귀 기준으로 유지하되, 검증 규칙에는 이름을 하드코딩하지 않는다.
  일반성 확인은 작은 합성 입력의 참조 무결성·순서·타입 속성으로 수행한다.

## LLM 호출 최적화 원칙

호출 최적화의 우선순위는 동시 호출 수 증가가 아니라 선택 공간 축소, 재호출 범위 축소,
관찰 가능성 확보다.

### 이미 적용한 최적화

- 긴 호출의 전역 기본 병렬도를 2로 제한한다.
- 메서드 조각은 최대 두 실행 슬라이스씩 wave로 생성하고, 앞선 결과의 이름을 다음 wave의
  예약 목록으로 전달한다.
- 전역 인벤토리에는 원문 전체 대신 역할·목표·단계·관계의 압축 payload를 전달한다.
- LLM은 실제 operation ID와 타입 호환 provenance 후보만 선택할 수 있다.
- `stepRefs`, 유일 후보 binding, 반환 메시지와 표시용 의존선은 코드가 투영한다.
- 시퀀스 생성은 LLM을 호출하지 않는다.
- 수리는 실패한 수정 대상에만 적용하고 성공한 나머지 슬라이스는 보존한다.

### 다음 최적화 순서

1. **호출 전 결정론적 축소**: 타입, 실행 범위, 인과 순서와 BCE 호출 방향으로 불가능한
   후보를 먼저 제거한다. 의미 점수만으로 유효 후보를 잘라내지는 않는다.
2. **호출 단위 캐시**: 정규화한 입력, schema 버전, prompt 버전과 모델 설정의 digest가
   모두 같을 때만 인벤토리·메서드 조각·협업 결과를 재사용한다.
3. **적응형 호출 생략**: 후보가 0개면 즉시 구조 오류, 1개면 코드 선택, 2개 이상일 때만
   LLM을 호출한다. 결정론적 검사에 finding이 없으면 별도 의미 검토 호출을 만들지 않는다.
4. **작업별 출력 예산**: 공통 토큰 상한을 낮추지 않고 각 schema의 최대 항목 수로 필요한
   출력 예산을 산정한다. 구조화 JSON이 잘리는 경우는 품질 실패가 아니라 운영 실패로
   분류한다.
5. **관찰과 재개**: operation, 실행 슬라이스, 입력 digest, 후보 수, 응답 시간, 토큰,
   재시도 사유를 기록한다. 타임아웃이나 429는 완료된 형제 작업을 버리지 않고 해당
   호출만 재개한다.

병렬도 2는 기본 운영값이지 도메인 규칙이 아니다. 공급자와 모델을 바꾸더라도 먼저 단일
호출 지연, 429 비율, 미종료 스트림과 구조화 응답 완결성을 측정한 뒤 설정으로만 조정한다.

## 피해야 할 최적화

- 토큰 절약을 위해 필수 근거·후보를 프롬프트에서 임의로 누락하는 것
- 한 슬라이스 실패로 전역 클래스 모델을 다시 생성하는 것
- 자연어 응답을 받은 뒤 코드에서 문자열 보정 규칙을 계속 추가하는 것
- 특정 골드셋의 클래스·메서드·매개변수 이름을 고정하는 것
- prompt 문구 자체를 테스트하고 실제 입력·출력 계약은 검사하지 않는 것
- 서로 다른 수리 루프가 같은 모델을 번갈아 수정하게 하는 것

## 측정 항목

변경 전후에는 다음을 같은 체크포인트에서 비교한다.

- 단계별 LLM 호출 수, 최대 동시 호출 수와 재시도 수
- 호출별 입력·출력 토큰과 wall time
- 유한 후보의 평균·최대 개수와 LLM을 생략한 binding 비율
- 전체 재생성 없이 재개한 실행 슬라이스 비율
- 최종 참조 무결성, 값 출처, 호출·반환 검사 결과
- 사람 검토에서 발견된 거대 클래스, 중복 타입·필드와 읽기 어려운 다이어그램 수

최적화는 호출 수나 토큰만 줄이는 것이 아니라 동일하거나 더 나은 설계 품질을 유지해야
완료로 본다.
