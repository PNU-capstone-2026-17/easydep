## 남은 불확실성과 다음 검증 경계

- 원래 시퀀스·ERD 꼬리 지연은 현재 재현되지 않았다. 저장·체크포인터·서버 출력 중 하나를 원인으로 확정하거나 이를 겨냥한 최적화를 적용할 근거가 아직 없다.
- 당시 stderr에는 현재의 `stage_subgraph`·`persist`·`gate` 세부 타이머가 없었다. SQL echo에는 쿼리 소요·연결 대기 시간이 없고, stdout access log에는 시각이 없다. MySQL의 장기 statement history consumer도 비활성화되어 테이블이 비어 있다. 따라서 **옛 로그만 다시 읽는 조사로 끝내지 않고**, 보존된 단계 직전 체크포인트를 같은 입력으로 재생하면서 출력 후 처리·저장·체크포인트·게이트 경계에 계측을 적용한다. 재생 결과가 과거의 간헐적 지연까지 재현하는지는 별도로 판정한다.
- 원래 측정 앱은 내부 설계 체크포인트와 Workspace 명령 상태가 서로 다른 단계에 있다. 앱 분기 API는 산출물은 복사하지만 Design graph의 게이트·재개 체크포인트는 복사하지 않는다. 따라서 이를 과거와 같은 작업 단위의 전후 비교로 사용하지 않았다.
- 다음에 일치하는 Workspace 설계 작업이 자연스럽게 실행될 때 `design.stage_subgraph.completed`, `design.persist.save_stages.completed`, `graph_ms`, `payload_ms`, `db_ms`, `image_warm_ms`와 전체 명령 시간을 함께 수집한다. 체크포인터가 의심되는 경우에만 그 경계를 더 잘게 계측한다. 동일 작업의 수정 전후 시간이 있어야 새 최적화 효과를 주장한다. 현재 근거만으로 수강신청 앱 전체 종단검증을 다시 시작하지 않는다.

## 중첩 체크포인트 상속 최적화

설계 단계 생성 및 피드백 서브그래프를 `compile(checkpointer=False)`로 컴파일하도록 변경했다 (`app/design/graphs/subgraphs.py`). LangGraph 1.2.1에서는 기본 컴파일된 서브그래프가 부모 그래프의 checkpointer를 상속해 별도 namespace 체크포인트를 기록한다. 기존 분기의 읽기 전용 집계에서도 이를 확인했다. 중첩 namespace의 checkpoint/blob/write 행은 sequence 5/34/29, ERD 5/44/39, deployment 6/57/51이었다. 변경 전 같은 분기의 루트 namespace에는 16/207/204행이 있었다.

실제 ERD 스냅샷을 고정한 ABBA 측정은 비활성화 조건 0.457930초, 0.368409초와 상속 조건 0.720533초, 0.732470초였다. 대응 행 수는 비활성화 [3, 94, 91], 상속 [8, 153, 145]였다. 두 조건의 의미상 출력은 같았고 생성된 `episode_id`만 달랐다. 합성 thread는 모두 정리되어 잔여 행 0개를 확인했다. 표본은 조건별 2회뿐이며 기존의 약 54초 구간이 해결됐다는 주장은 하지 않는다.

이 변경은 단계 중간의 노드 단위 crash recovery를 없애므로 실패 시 해당 단계 작업을 다시 수행할 수 있다. 루트 feedback gate의 resume probe는 통과했다. Requirements도 같은 상속 구조지만, 중간 복구 손실의 trade-off를 검토하지 않았으므로 변경하지 않았다.

변경 후 실제 Workspace API로 요구사항 체크포인트에서 분기한 소형 앱 `ba63640b-be66-4911-b882-40fcf3177727`의 클래스 단계만 실행했다. `start_design` 명령 `901e9ecb-23ea-4234-8e8b-d3a2ab9f6d4e`는 약 21.086초의 설계 그래프 실행 뒤 클래스 검토 게이트에서 `AWAITING_INPUT`으로 멈췄고, `CLASS` 산출물이 `needs_review`로 저장됐다. 서브그래프 20.746초와 `save_stages` 0.278초가 기록됐다. 이 앱의 설계 체크포인트는 루트 namespace에 checkpoint/blob/write 4/40/37행이 있고, 중첩 namespace에는 세 표 모두 0행이다. 이는 실제 경로의 기능·기록 확인이지 변경 전후의 동일 입력 시간 비교는 아니다.

검증 클라이언트의 첫 `start_design` 요청은 필수 `action_id` 누락으로 409를 받았는데, 해당 스크립트의 이전 폴링 프로세스가 오류 뒤에도 조회를 계속했다. 클라이언트 포트 3902의 PID 21280을 확인해 그 프로세스만 종료했다. 이 추가 `get_tuple` 로그의 누적시간을 생성 단계의 자체 비용이나 과거 지연의 원인으로 계산하지 않는다.

### 저장된 모델 응답 재생으로 분리한 비-LLM 시간

현재 첫 PlantUML 문법 검사는 캐시 미스마다 별도 `java -jar … -syntax -pipe` 프로세스를 시작하고, 이미지 준비는 이미 실행 중인 PicoWeb 렌더러를 이용한다. 같은 원문을 두 번 처리하지만 렌더 결과를 문법 검사 성공으로 간주하면 오류 검출 계약이 달라질 수 있다. 유효·무효 원문 양쪽에서 동일한 판정과 첫 실행 시간을 비교하기 전에는 두 경로를 합치지 않는다.

## 요구사항 단계의 별도 집중 측정

기존 소형 앱 `3bae0dc2-ec5f-414c-8848-f3b7de9192d8`의 Requirements 체크포인트에는 완료된 `resource_constraint_extraction` 캐시가 있었다. 이를 고정해 LLM을 호출하지 않는 단일 노드 `structure_constraints`를 합성 thread 네 개에서 ABBA로 실행했다. 중첩 체크포인터 상속 조건은 0.522418초·0.414263초, 비활성화 조건은 0.272413초·0.284423초였다. 전자의 루트/중첩 checkpoint·blob·write 행은 각각 3/64/61 및 3/37/34였고, 후자는 루트 3/64/61만 남았다. 네 번의 의미상 결과가 같고 LLM 제안 함수는 호출되지 않았으며, 합성 thread의 세 표 잔여 행은 모두 0개임을 확인했다. 이 작은 단위의 차이로 과거 85초 지연을 설명할 수는 없다. 여러 LLM 노드가 있는 요구사항 단계의 중간 실패 복구를 잃지 않도록 Requirements 코드는 변경하지 않았다.

과거 Requirements 분석의 마지막 모델 응답은 01:11:59.614, 실행 종료 기록은 01:13:25.020으로 간격이 85.406초다. 당시 access log에는 앱 조회 요청이 전체 파일에 26건 있으나 각 줄의 시각이 없어 이 간격에 몇 건이 있었는지 알 수 없다. 이번 검증 클라이언트의 폴링 누수를 과거 지연 원인으로 소급하지 않는다.

## 동결 체크포인트로 긴 종료 구간 재생

오래된 로그의 빈 구간을 추측으로 채우지 않기 위해 원래 앱 `3bae0dc2-ec5f-414c-8848-f3b7de9192d8`의 단계 직전 체크포인트를 읽어 재생했다. 원본 앱의 산출물은 수정하지 않았다.

- 요구사항: 마지막 두 OSS 응답 뒤 부모 `analyze` 체크포인트가 기록되기까지의 약 85초가 대상이다. 보존된 병렬 분기 출력으로 부모 합류를 재구성하니 약 0.533초였고 의미상 결과가 같았다. `structure_constraints` 이후만 재생한 0.0205초는 **대상 85초보다 뒤의 경로**라 원인 근거로 사용하지 않는다. 원래 `analyze` 직전 체크포인트에서 해당 노드만 실모델로 두 번 실행한 전체 시간은 8.195초와 6.345초였다. 두 번째 실행에서는 마지막 모델 응답 뒤 분기 반환이 약 0.028ms, 노드 완료 뒤 부모 체크포인트·중단까지 약 0.42초였다. 과거 85초 대기는 재현되지 않았다. 모델 응답 문구는 실행마다 달라질 수 있으므로 과거 실행과 완전히 동일한 출력 비교로 해석하지 않는다.
- 설계: 원래 시퀀스 단계 입력을 두 번 재생하니 하위 그래프 4.117/4.228초, 전체 그래프 4.734/4.781초, 하위 그래프 종료 후 체크포인트·게이트 반환 0.617/0.553초였다. 원래 ERD 입력은 하위 그래프 6.1/10.0ms, 전체 0.901/1.200초, 이후 0.895/1.190초였다. 게이트 본문은 0.08–0.13ms였다. 현재 코드와 같은 동결 입력에서도 과거 32초·69초 꼬리는 재현되지 않았다.

## OpenTelemetry 전환과 동결 입력 계측

기존 시간 로그만으로 부모·자식 작업의 겹침과 모델 응답 이후 체크포인트 경계를 연결하기 어려워, 요구사항 그래프·병렬 분석 분기·모델 작업과 설계 그래프·하위 단계·저장·게이트, 공용 SQL 체크포인터의 `put`/`put_writes`에 OpenTelemetry span을 추가했다. span 속성에는 단계명, 작업 ID, 쓰기 건수 같은 식별·수치 정보만 넣고 프롬프트·응답·산출물·SQL 본문과 예외 메시지는 넣지 않는다. 평소에는 exporter가 꺼져 있으며, 로컬 서버/runner에 `EASYDEP_OTEL_CONSOLE=1`을 설정하면 배치형 콘솔 exporter가 켜진다. 이는 **계측 변경**이지 지연 최적화가 아니다.

설계 ERD의 동결 입력을 실제 SQL 체크포인트가 있는 일회용 thread로 한 번 더 재생했다. 모델 호출과 산출물 쓰기는 없었다. 한 trace ID 아래 그래프 루트는 **780.864ms**, 설계 하위 단계는 4.203ms, 저장 노드의 산출물 비작성 경로는 0.033ms, 게이트는 0.102ms였다. 체크포인터 `put_writes` 네 건은 각각 95.796·139.848·419.896·398.303ms, `put` 네 건은 188.542·254.882·142.466·22.648ms였다. 이 span들은 그래프 루트의 직접 자식이며 서로 겹쳐 실행되므로 합산해 루트 시간과 비교하지 않는다. 재생 후 일회용 checkpoint/blob/write 행은 모두 0건이다. 이 관찰에서 현재 ERD 재생의 눈에 띄는 비-모델 시간은 설계 노드 본문보다 체크포인트 경계에 있지만, 과거 54초의 직접 원인이라는 뜻은 아니다.

요구사항·설계의 SQL saver 양쪽에서 `put`/`put_writes` span의 trace 부모 관계를 격리된 합성 thread로 확인했다. 별도 로컬 smoke에서 콘솔 exporter가 trace ID를 실제 출력했다. 요구사항의 첫 동결 재생 probe는 진단용 함수가 context를 이중으로 바인딩해 부모 검사가 무효였으므로 결과로 쓰지 않았다. 한 번만 바인딩하도록 바로잡은 재생에서는 원래 `analyze` 직전 체크포인트와 보존된 분기 출력을 사용했으며 의미상 결과가 일치했다. 그래프 전체 **560.979ms**, `analyze` 노드 **1.431ms**, 두 분기 **0.539/0.296ms**, 노드 종료 → checkpoint `put` 시작 **0.180ms**였다. 모델 응답 자리의 0.060/0.040ms span은 **캐시 반환**이지 실모델 시간은 아니다. SQL 체크포인터 `put`/`put_writes`는 각각 **207.451/351.653ms**였고 그래프 루트에 연결됐다. 일회용 checkpoint/blob/write 및 App 행은 정리 후 모두 0건이다.

이 두 동결 재생에서 현재 관찰되는 비-모델 비용은 그래프의 분석·설계 노드 본문보다 공용 체크포인터 호출에 집중됐다. 그러나 과거 약 54초·85초 지연은 여전히 재현되지 않았다. 다음 정상 Workspace 실행에서 같은 trace ID로 모델 작업 종료 → 분기 반환 → 부모 그래프 종료 → 체크포인트 기록을 수집해야 간헐 지연의 위치를 확정할 수 있다. 이 계측 자체는 지연을 줄이지 않는다.

### 공용 체크포인터의 반복 조회 축소

동일한 동결 ERD 입력을 한 번씩 재생하며 SQLAlchemy cursor 이벤트로 saver 호출 안의 SQL 문장 수와 cursor 시간을 쟀다. 수정 전 `put`은 SELECT 100회·INSERT 8회, `put_writes`는 SELECT 93회·INSERT 4회였다. 코드상 blob마다 `merge`하고 일반 pending write마다 `get`하므로 행별 조회가 많다는 관찰과 일치한다. 먼저 의미 보존이 단순한 `put_writes`의 **일반(음수가 아닌) 인덱스 기존 행 조회만** 동일 task의 복합키 범위에서 한 번에 수행하도록 바꿨다. 음수 인덱스의 최신 값 덮어쓰기는 그대로 `merge`한다. DB 스키마와 `put` 경로는 바꾸지 않았다.

| 동일 동결 ERD 재생 | `put_writes` SELECT / INSERT | cursor 누계 | 호출별 최대 wall time | `put` SELECT / INSERT |
| --- | ---: | ---: | ---: | ---: |
| 수정 전 1회 | 93 / 4 | 873.205ms | 820.962ms | 100 / 8 |
| 수정 후 1회 | **4 / 4** | **71.897ms** | **237.339ms** | 100 / 8 |

SELECT 횟수 감소는 같은 입력에서 검증된 직접적인 효과다. cursor 누계와 호출 wall time은 한 번씩의 전후 표본이며 호출들이 서로 겹치므로 정밀한 개선율이나 그래프 전체 절감 시간으로 환산하지 않는다. `put`의 SELECT 100회는 이번 변경 범위 밖이다. 수정 후에도 원래의 수십 초 지연은 관찰되지 않았으므로 이 변경을 과거 지연의 해결로 주장하지 않는다. 임시 thread의 checkpoint/blob/write 잔여 행은 전후 모두 0건이고, 재시도 첫 값 보존·특수 인터럽트 최신 값·작업별 분리의 집중 테스트 3개가 통과했다.

실제 OSS 호출을 포함한 요구사항 trace 재생도 한 번 시도했으나, 실행 래퍼가 하위 명령의 `output`만 전달했고 빈 문자열만 반환했다. 종료 코드·실행 span·요청 성공 여부는 보존되지 않아 이 시도에서는 사용할 수 있는 시간 근거가 없다. 같은 호출을 재시도하지 않았으며, 후속 읽기 전용 조회에서 일회용 checkpoint/blob/write 및 App 행은 0건이었다. 이 실행을 실모델 검증 성공으로 계산하지 않는다. 다음 계측 명령은 반드시 하위 명령의 종료 코드와 제한된 trace 요약을 함께 보존해야 한다.

수강신청 앱 분기 `bec3aa53-ee83-4705-abc4-bdad2f994ad1`의 현재 상태를 읽기 전용으로 확인했다. 구현 job은 완료됐고 이후 `start_testing` 명령도 종료됐지만, 테스트 checkpoint는 `verification_complete`, `passed=false`, `gateStatus=FAIL`이다. 결과는 생성 앱 실패가 아니라 내부 test-plan authoring 결함을 platform diagnostic으로 기록한다. 활성 작업이나 재개 가능한 checkpoint가 없어 기존 명령의 나머지만 이어갈 수는 없고, 이 결함을 최소 범위로 해결한 뒤 새 시스템 명령으로 테스팅을 재검증해야 한다.

Requirements·Design·Implementation은 다시 만들지 않았다. 최종 검사 결과는 FAIL이고, 이전과 같은 workflow ID/order 오류가 발생했다. 그러나 진행 기록에는 11개 계획 중 8개 유효·3개 실패, 8개 workflow 중 3개 PASS·5개 FAIL이 남았다. 누락된 계획 ID는 UC3·UC5·UC8이다. 같은 명령의 technical retry 표식과 구현 경로를 대조하면, 첫 회차의 부분 `candidatePlan`을 재시도에서 전체 11개 후보와 비교해 ID/order 오류로 바꾼 경로가 확인된다. 중간 원문 문서는 종료 시 덮여 직접 복원할 수 없다는 한계가 있다.

이에 저장된 부분 계획의 ID가 고정 후보의 순서 있는 부분집합인지 검증한 뒤, 빠진 후보만 생성하고 유효한 기존 workflow와 다시 고정 순서로 조립하도록 수정했다. 8개 보존·3개 누락(그중 1개 생성 실패)의 집중 no-LLM 테스트와 완전 보존 계획의 무재생성 테스트가 통과했다. 실패 후보를 진행 카드의 계획 완료 상태로 덮지 않도록 했다. 이는 재시도 오류 수정이지 UC3·UC5·UC8의 원래 계획 생성 실패를 해결한 것은 아니다.
