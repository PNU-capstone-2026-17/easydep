# 구현 검증 시간 개선안

## 관찰 결과

2026-08-09~10의 PS-AWS 개발 실행에서 다음 현상을 확인했다.

- 구조화 설계 응답은 출력 상한을 명시한 뒤 정상 종료했다. 설계 단계는 약 217~222초였다.
- 멤버 구현 작업은 고정 Linux runner에서 순차 실행되며, 각 작업 뒤에 Gradle 검증을 수행한다.
- 첫 셀은 17개 구현 작업 중 14개를 통과한 뒤 `application-wiring`의 통합 검증·수정 반복 중 3,600초 측정 한계에 도달했다.
- 이 한계는 기능 실패가 아니라 `measurementWallClock` 검열로 기록했다. 완료된 상류 단계와 구현 작업은 체크포인트에 남았다.
- 실험 작업자 종료 뒤 Docker runner가 남는 문제가 한 번 관찰됐다. 실험 세션 label과 timeout 정리를 오케스트레이터 경계에 추가했다.

## 병목 해석

현재 병목은 하나의 단발성 LLM 호출이나 provider 다운로드가 아니다. 작은 하위 작업마다 전체 애플리케이션의 컴파일·패키징·테스트를 반복하고, wiring처럼 여러 계약이 합쳐지는 작업에서는 같은 전체 검증을 수정 피드백마다 다시 수행하는 구조가 지배적이다.

검증을 제거하면 생성 코드가 테스트 기대값을 약화하거나 Spring bean 계약을 깨뜨린 사례를 놓치므로 적절하지 않다. 개선 대상은 검증의 존재가 아니라 실행 범위와 시점이다.

## 제안하는 검증 계층

1. 하위 작업 검증
   - `compileJava`를 항상 수행한다.
   - 변경 파일과 소유 계약에 대응하는 테스트만 우선 실행한다.
   - 컴파일 오류가 다른 소유 작업의 파일을 가리키면 현재 작업 내부 재시도를 중단하고 오케스트레이터에 반환한다.
2. 단계 체크포인트 검증
   - controller, persistence, adapter처럼 작업군이 끝날 때 해당 작업군의 통합 테스트를 수행한다.
   - 같은 입력 hash와 Gradle cache를 재사용한다.
3. 구현 완료 검증
   - 전체 `test`, `bootJar`, source-design conformance를 한 번 수행한다.
   - 독립 평가기의 앱 기능 검사는 멤버 테스트와 별도로 유지한다.
4. 복구 검증
   - 실패 테스트와 그 테스트가 참조하는 소유 작업부터 재개한다.
   - 최종 전체 검증은 복구가 수렴한 뒤 다시 한 번 수행한다.

## 측정 항목

개선 전후에 다음 값을 분리해서 비교한다.

- LLM 생성·수정 시간
- Gradle 구성·컴파일·테스트 시간
- Spring context 시작 횟수
- 하위 작업별 검증 재시도 횟수
- 전체 테스트 실행 횟수
- 상류 단계 재실행 회피율
- 최종 독립 기능 검사 통과 여부

## 적용 경계

현재 저장소에서는 멤버 구현 코드 자체를 수정하지 않는다. 오케스트레이터가 전달하는 검증 정책 입력과 멤버 runner의 공개 실행 경계로 지원할 수 있을 때 적용한다. 그 전까지는 고정 Linux 환경, provider/Gradle cache, 실패 체크포인트 재개, 세션별 runner 정리로 실행 낭비를 제한한다.

이 개선안은 특정 P1·P2 앱이나 SQLite 경로를 전제하지 않는다. 파일 소유권, 변경 영향 범위, 단계 체크포인트라는 일반 실행 정보만 사용한다.
