# EasyDep 졸업과제 작업 기준

이 문서는 현재 작업의 범위와 우선순위만 정한다. 승인된 연구 배경은 [research.md](research.md), 구현 현황은 [current-system-status.md](current-system-status.md), 측정 결과는 [research-results-20260810.md](research-results-20260810.md)를 따른다.

## 확정 범위

- AWS·Azure·GCP의 Docker-on-Linux-VM 배포를 대상으로 한다.
- 벤더별 DepKB와 중립 capability는 완결된 범용 메타모델이 아니라, 앱 요구를 벤더 리소스군과 의존관계로 연결하는 제한된 지식 계층이다.
- 앱 생성 성공, IaC 생성·검증 성공, 실제 앱 기능 성공을 서로 다른 지표로 기록한다.
- P1~P3은 종단 통합 점검 사례이며 리소스 모델이나 전체 CNA 모집단의 근거로 사용하지 않는다.
- `no-depkb`는 개선 대상이 아니라 DepKB 효과를 비교하기 위한 대조 조건이다.

## 현재 해석

동일 입력 54셀 개발 측정에서는 DepKB 조건의 전달 완료율과 의존관계 완전성이 대조 조건보다 높았다. 그러나 반복 간 변동이 컸고 cloud apply와 앱 기능의 paired 성공이 확보되지 않았으므로, 이를 일반적인 기능 향상이나 인과효과로 확대하지 않는다. 정확한 수치와 실패 내역은 결과 보고서에만 둔다.

## 다음 작업 순서

1. 고정 Linux 멤버 실행 경계를 마련하되, 시스템 로직이 바뀌지 않은 검증은 기존 체크포인트에서 시작한다.
2. P1-AWS 한 셀로 구현·빌드·테스트 핵심 경로의 종단 성공을 먼저 확인한다.
3. 같은 실행환경에서 PS-AWS의 control/treatment × full/no-depkb 네 셀을 실행해 처치 충실도와 paired 집계를 확인한다.
4. 네 셀이 안정적으로 완료된 뒤에만 CSP와 capability 범위를 늘린다.
5. cloud apply는 사전 gate를 모두 통과한 최소 셀에만 수행하고, 종료 후 destroy와 잔여 리소스 0을 확인한다.

## 중단 기준

- 동일 실패를 사례별 문자열·경로·리소스명 패치로 우회해야 하는 경우
- 정적 projection 성공을 실제 생성 또는 앱 기능 성공으로 해석하게 되는 경우
- 기존 체크포인트로 재개할 수 있는데 전체 파이프라인을 다시 실행하는 경우
- 실패한 파일럿 상태에서 대규모 반복 실행으로 넘어가는 경우
- 졸업과제 범위를 넘어 범용 클라우드 메타모델이나 자동 용량 최적화 연구로 확장되는 경우

실패한 단계는 가능한 한 같은 run의 소유 하위 작업 체크포인트에서 수정·재개한다. 결과를 확정하기 전에는 입력 해시, 설정, 원시 결과와 정리 기록을 보존한다.
