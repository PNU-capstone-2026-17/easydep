# 임시 검토: 클라우드 리소스 의존성 분석의 부족한 점

> 상태: **임시 작업 문서**  
> 검토일: 2026-08-07  
> 목적: DepKB의 다음 작업 범위를 확정한 뒤 정식 문서에 반영하고 이 파일은 삭제한다.

## 결론

현재 DepKB는 검증 항목을 저장하고, 시작 리소스에서 연쇄적으로 필요한 자원과 생성 순서를
계산할 수 있다. 가장 부족한 것은 검증 항목의 수가 아니라 다음 두 경계다.

1. 요구사항을 DepKB가 사용할 시작 리소스로 정확히 변환하는 경계
2. DepKB가 요구한 자원·관계가 최종 Terraform에 반영됐는지 확인하는 경계

따라서 지금은 검증 항목을 더 추가하기보다 두 경계를 먼저 고쳐야 한다.

## 확인된 현재 데이터

`claims.json`을 직접 집계한 값이다.

| 항목 | 값 |
|---|---:|
| 전체 검증 항목 | 56 |
| AWS / Azure / GCP | 20 / 21 / 15 |
| 생성 가능 여부 / 수명주기 / 기능 | 33 / 11 / 12 |
| 필수 / 선택 / 성립 확인 | 10 / 23 / 23 |
| 별도 조건 설명이 있는 항목 | 25 |
| 기계 판독 가능한 `constraint`가 있는 항목 | 2 |
| 실제 제어면 적용 실험 / 사전 검증 | 50 / 6 |

근거 파일과 검증 항목의 연결은 갖춰져 있다. 그러나 같은 원실험을 공유하는 골드셋으로
평가했으므로 현재 F1 1.0은 독립 정확도보다 계산 경로가 연결됐다는 사실을 보여준다.

## 우선순위별 부족한 점

### P0. 요구사항에서 시작 리소스로 가는 규칙이 일관되지 않음

현재 설계 adapter는 영속 스토리지를 다음 두 방법으로 판단한다.

- `deployment_needs.persistent_storage.required`
- 설계 배포 모델에 `database` 노드가 있는지 여부

반면 VM Terraform 생성 adapter는 첫 번째 키만 읽는다. 실제 요구사항 산출물에는
`stateless_execution.metadata.persistent_storage`처럼 다른 이름이 나올 수 있다.

이로 인해 같은 실행에서도 설계는 디스크가 필요하다고 판단하고 구현은 필요 없다고 판단할
수 있다. 설계의 DB 노드가 단순 모델링 오류여도 디스크가 선택되는 문제도 있다.

필요한 조치:

```text
자유 형식 DeploymentNeeds
→ 고정된 배포 의사결정
→ DepKB 시작 리소스
```

고정할 최소 값:

- `externalIngressRequired`
- `persistentStorageRequired`
- `highAvailabilityRequired`
- `instanceCount`
- `networkMode`

자연어와 자유 형식 필드를 읽는 일은 LLM이 담당하되, DepKB 이후 단계는 이 고정 값만
사용해야 한다.

### P0. `multiZone`과 고가용성·로드밸런서가 같은 의미로 처리됨

현재 설계 adapter는 `resource_spec.multiZone=true`이면 바로 `loadBalancer`를 시작
리소스로 추가한다. 하지만 여러 가용영역 사용은 배치 조건이고, 로드밸런서는 외부 진입 및
장애 전환 구조다. 둘은 항상 같은 결정이 아니다.

필요한 조치:

- `multiZone`, `highAvailabilityRequired`, `externalIngressRequired`, `instanceCount` 분리
- LB 선택 조건을 명시적 규칙으로 고정
- P3 사례에서 VM 수와 LB 필요성을 각각 평가

### P0. 미결 질문이 있어도 구현이 진행됨

DepKB는 네트워크 방식처럼 정해지지 않은 조건을 `open_questions`로 반환한다. 하지만 batch
실행은 이 값을 차단 조건으로 사용하지 않고 Terraform 생성까지 진행한다. 결국 LLM이
미결정을 임의로 채울 수 있다.

필요한 조치:

- `blocking`: 구현 전에 반드시 결정
- `nonBlocking`: 안전한 기본값이 명시된 경우
- `deferred`: 현재 단계의 결정 대상이 아님

세 종류로 나누고 `blocking`이 남으면 구현을 중단해야 한다.

### P0. DepKB 계획과 최종 Terraform의 직접 대조가 없음

현재 DepKB 계획 검사기와 Terraform 의미 평가기는 별도로 존재한다. 다음 대조가 제품 흐름에
연결되지 않았다.

```text
DepKB가 요구한 자원·관계
↔ Terraform에서 추출한 실제 자원·관계
```

필요한 지표:

- 필수 자원 precision, recall, F1
- 필수 관계 precision, recall, F1
- 불필요·금지 자원 수
- 조건부 관계 만족률
- 생성 순서 위반 수
- 검사하지 못한 제약 수

### P1. 계획 검사기의 성공 의미가 문서와 다름

`check.py`의 설명은 검사할 수 없는 규칙을 `unchecked`로 보고하고 통과로 보지 않는다고
쓴다. 하지만 실제 `Report.ok`는 위반과 필수 자원 누락만 확인하며 `unchecked`가 있어도
`True`가 될 수 있다.

또한 `Constraint.machine`이 존재하지만 일부 검사기는 여전히 한국어 규칙 문장에서 숫자,
영역, 이름을 정규식으로 읽는다. 이는 “산문을 파싱하지 않는다”는 주석과 맞지 않는다.

필요한 조치:

- `ok`, `partiallyChecked`, `unchecked` 상태를 분리
- 검사는 `constraint` 구조만 사용
- 구조화되지 않은 규칙은 성공이 아니라 `unchecked`로 유지

### P1. 조건 25개 중 기계 판독 가능한 조건은 2개뿐임

조건 설명 자체는 25개에 존재하므로 “조건 지식이 없다”고 볼 수는 없다. 문제는 대부분
자연어라 자동 판정과 최종 IaC 검증에 사용하기 어렵다는 점이다.

전체 조건을 범용 규칙 언어로 만들 필요는 없다. 우선 P1~P3에서 사용하는 다음 조건만
구조화한다.

- 기본 네트워크와 사용자 정의 네트워크
- 영속 데이터 디스크 필요 여부
- 단일 VM과 복수 VM
- 고가용성과 LB
- 영역·리전 일치
- CSP 자동 생성 자원

### P1. 독립 골드셋이 없음

현재 구성요소 평가의 골드와 DepKB는 같은 실험 근거를 공유한다. 따라서 현재 결과는
배선 검사로는 유효하지만 정확도 증명으로는 부족하다.

필요한 조치:

- CSP별 대표 시나리오를 독립적으로 재검토
- 검토자가 공식 문서·Terraform schema·실험 결과를 다시 판정
- 검토 결과와 기존 검증 항목의 일치율 및 의견 차이 기록

큰 골드셋은 필요하지 않다. P1~P3와 직접 관련된 자원·관계부터 검토한다.

### P1. 시나리오 커버리지를 알 수 없음

56개라는 개수만으로 Docker-on-VM 범위가 충분히 덮였는지 판단할 수 없다. 다음 표를
CSP별로 작성해야 한다.

| 시나리오 | 생성 관계 | 조건 | 생성 순서 | 삭제 관계 | 기능 신호 |
|---|---|---|---|---|---|
| 단일 VM 외부 접속 | 미확인 | 미확인 | 미확인 | 미확인 | 미확인 |
| 사용자 정의 네트워크 | 미확인 | 미확인 | 미확인 | 미확인 | 미확인 |
| 영속 데이터 디스크 | 미확인 | 미확인 | 미확인 | 미확인 | 미확인 |
| 복수 VM과 LB | 미확인 | 미확인 | 미확인 | 미확인 | 미확인 |
| VM identity/role | 미확인 | 미확인 | 미확인 | 미확인 | 미확인 |

`미확인`은 지식이 없다는 뜻이 아니라 아직 이 표로 감사하지 않았다는 뜻이다.

### P2. 수명주기·기능 관계가 최종 평가에 충분히 연결되지 않음

수명주기 11개와 기능 관계 12개가 존재한다. 하지만 최종 평가는 주로 생성된 Terraform의
정적 구조, OpenTofu 검증, Docker 접근 성공을 본다. 각 실행 결과가 어떤 DepKB 검증 항목을
확인했는지 추적하지 않는다.

필요한 조치:

- 기능 관계와 health/API 관측 결과 연결
- 생성·삭제 관계와 `tofu apply/destroy` 결과 연결
- 남은 리소스가 없는지 확인

실제 CSP apply/destroy는 비용과 자격증명이 필요하므로 전체 비교실험이 아닌 소수 대표
사례에서만 수행한다.

### P2. 기존 리소스 재사용을 표현하지 못함

현재 계산은 필요한 자원은 알려주지만 사용자가 이미 가진 VPC·서브넷·인증서를 새로 만들지
재사용할지 알 수 없다. 지금의 동결 사례는 새 환경 생성을 전제로 하지만 실제 사용에서는
중요한 제한이다.

졸업과제 범위에서는 다음 중 하나를 명시해야 한다.

1. 모든 평가 사례는 새 격리 환경을 생성한다고 제한
2. `existingResourceIds`를 입력으로 받아 생성 대상에서 제외

현재 범위에는 1번이 더 단순하다.

### P2. 최신성 정책이 없음

각 항목에는 실험 날짜와 근거가 있지만 CSP API나 Terraform provider가 바뀌었을 때 무엇을
재검증할지 정한 정책은 없다.

필요한 최소 메타데이터:

- CSP API 및 Terraform provider 버전
- 관측 날짜와 리전
- 재현 명령
- 마지막 독립 검토 날짜
- 만료 또는 재검토 조건

## 수정 순서 제안

| 순서 | 작업 | 완료 기준 |
|---:|---|---|
| 1 | 배포 의사결정 5개 필드 정규화 | 설계·Terraform이 같은 값 사용 |
| 2 | 미결 질문의 차단 등급 추가 | blocking 결정이 남으면 구현 중단 |
| 3 | P1~P3 핵심 조건 구조화 | 산문 정규식 없이 판정 |
| 4 | DepKB 계획–Terraform 그래프 대조 | 자원·관계 P/R/F1 출력 |
| 5 | CSP별 시나리오 커버리지 감사 | 표의 미확인 칸 해소 |
| 6 | 소규모 독립 골드 검토 | 같은 원자료를 공유하지 않는 평가 확보 |
| 7 | full/no-DepKB 및 종단 비교 | DepKB 효과와 전체 시스템 효과 분리 보고 |

## 용어 원칙

- 사용자 문서에서는 설명 없는 그래프 이론 전문용어 대신 **연쇄 의존 자원 집합** 또는
  **연쇄 의존 자원 계산**을 쓴다.
- 사용자 문서에서는 의미가 불명확한 음역어 대신 **시작 리소스**를 쓴다.
- 코드의 `closure()`는 그래프 이론의 표준 transitive-closure 알고리즘과 기존 API를
  나타내므로 식별자만 유지한다.
- `claim`, `anchor`, `attachable` 같은 JSON·Python 필드명은 호환성을 위해 유지하되 문서에서
  각각 검증 항목, 시작 리소스, 선택 연결 가능 자원으로 설명한다.
- 새 용어를 만들기 전에 표준 용어인지 확인하고, 처음 사용할 때 한 문장으로 정의한다.
