# EasyDep의 클라우드 분석과 리소스 추천 안내

이 문서는 클라우드를 잘 모르는 사람도 EasyDep이 무엇을 판단하고, 어떤 근거를 사용하며,
어디까지 믿을 수 있는지 이해할 수 있도록 작성한 통합 안내서다. 대상 범위는 현재 연구가 실제로
다루는 **AWS·Azure·GCP의 Docker-on-Linux-VM 배포**다.

이 문서는 승인된 연구 배경인 [research.md](research.md)를 해석하거나 변경하는 문서가 아니다.
현재 코드와 개발 실험을 설명하며, 최신 측정값은
[2026-08-10 연구 결과](research-results-20260810.md)를 원문으로 삼는다.

## 1. 전체 그림

EasyDep의 판단은 다음 네 단계로 이어진다.

| 단계 | 답하는 질문 | 쉬운 비유 | 대표 출력 |
|---|---|---|---|
| 리소스 의존성 분석 | 무엇을 만들고 어떻게 연결해야 하는가? | 건물의 배관·전기 배선도 | CSP별 구성요소와 관계 |
| 앱 용량 측정 | 앱이 실제로 얼마나 많은 자원을 쓰는가? | 입주 인원과 전력 사용량 측정 | vCPU·메모리·디스크·대수 하한 |
| 앱–클라우드 충돌 검사 | 앱의 사용법과 배포 환경이 서로 맞는가? | 가전제품의 전압과 콘센트 확인 | 진단, 질문, 수정할 하위 작업 |
| 리소스 추천 | 위 조건을 만족하는 구매 후보는 무엇인가? | 규격과 예산에 맞는 제품 고르기 | CSP·리전별 VM 후보와 가격 근거 |

흐름을 한 줄로 쓰면 다음과 같다.

```text
사용자 요구
  → 필요한 기능과 연결 관계 결정
  → 앱을 부하 시험해 용량 하한 계산
  → 앱·컨테이너·VM·IaC 사이의 값 대조
  → 용량·리전·예산을 만족하는 VM 후보 선택
  → 생성·기능·재시작·정리 시험
```

어느 한 단계도 나머지를 대신하지 않는다. 예를 들어 Terraform 검증에 통과했다고 업무 API가
작동하는 것은 아니며, 앱이 로컬에서 잘 작동한다고 클라우드 리소스 관계가 올바른 것도 아니다.

## 2. 먼저 알아둘 용어

- **CSP**: AWS, Azure, GCP 같은 클라우드 제공자다.
- **리소스**: VM, 디스크, 서브넷, 방화벽, 로드밸런서처럼 클라우드에서 만드는 대상이다.
- **의존 관계**: 한 리소스가 다른 리소스를 참조하거나 먼저 필요로 하는 관계다.
- **IaC**: Terraform처럼 클라우드 구성을 코드로 표현하는 방식이다.
- **capability**: 사용자가 원하는 기능을 벤더 이름 없이 표현한 비교 좌표다. 예를 들어
  `persistent-block-storage`는 “재시작 뒤에도 남는 블록 저장소”라는 요구를 뜻한다.
- **SLO**: 목표 처리량, 최대 지연시간, 허용 오류율처럼 앱이 만족해야 할 성능 기준이다.
- **하한**: 이보다 작으면 요구를 만족한다고 말할 근거가 없다는 최소값이다. 최적값이나 보장값은 아니다.
- **보류**: 근거가 부족할 때 값을 추측하지 않고 질문하거나 측정을 요구하는 결과다.

## 3. 클라우드 리소스 의존성 분석

### 3.1 왜 필요한가

“VM 하나에 앱을 배포한다”는 요구도 실제로는 VM만 만들면 끝나지 않는다. 네트워크 인터페이스,
서브넷, 보안 규칙, 이미지, 권한 등이 연결돼야 한다. 영속 디스크나 HTTPS 로드밸런서를 추가하면
필요한 리소스와 관계는 CSP마다 더 크게 달라진다.

하나의 중립 리소스 표를 세 CSP에 억지로 적용하면 이 차이가 사라진다. 반대로 벤더별 이름만
사용하면 같은 사용자 요구를 비교하기 어렵다. EasyDep은 이를 세 층으로 나눈다.

| 층 | 내용 | 정답의 근거 |
|---|---|---|
| 벤더 사실 | AWS·Azure·GCP의 native 리소스와 관계 | 공식 문서, control-plane API, provider schema |
| 중립 capability | 사용자가 원하는 기능 | 요구사항과 검토된 capability 정의 |
| CSP 투영 | capability를 실현하는 리소스군 | 벤더 사실을 조합한 provider projection |

중립 capability는 완결된 “세계 공통 클라우드 모델”이 아니다. 벤더 사실을 지우지 않고 요구와
구현을 연결하기 위한 작은 좌표다. 실제 정본 데이터는
[DepKB](../app/core/cloudkb/depkb/)에 있고, 설계 원칙은
[리소스 의존성 분석 안내](../app/core/cloudkb/document/resource-dependency-analysis-guide.md)와
[구성요소 projection](../evaluation/research_protocol/reports/component-projections.md)에 정리돼 있다.

### 3.2 하나의 기능이 여러 리소스가 되는 이유

예를 들어 `load-balanced-ingress`라는 기능은 단일 리소스로 끝나지 않는다. 로드밸런서,
listener, backend 또는 target group, health check, 네트워크 연결이 필요할 수 있다. 어떤 CSP에서는
한 리소스의 내부 블록인 요소가 다른 CSP에서는 독립 리소스일 수도 있다.

따라서 EasyDep은 다음 두 방향을 모두 허용한다.

- 하나의 capability가 여러 native 리소스로 실현되는 1:N 관계
- 하나의 native 리소스가 여러 capability의 일부로 사용되는 N:M 관계

합법적인 토폴로지도 하나뿐이지 않다. EasyDep은 사용자 요구를 만족하는 **허용 가능한 리소스군
중 하나**를 선택하고, 그 선택이 근거와 제약을 만족하는지 검사한다. 특정 Terraform 모양 하나를
정답으로 외우게 하지 않는다.

### 3.3 분석 절차

1. 자연어 요구에서 저장, 부하분산, TLS처럼 배포 결과를 바꾸는 요구를 찾는다.
2. 근거가 확인된 capability에만 연결한다. 모호하면 새 capability를 즉석에서 만들지 않는다.
3. 선택한 CSP의 projection에서 필요한 native 구성요소와 관계를 얻는다.
4. 생성된 IaC에서 구성요소가 있는지 확인한다.
5. 리소스 사이에 명시적인 참조가 있는지 확인한다.
6. 다중 AZ, 동일 AZ, 인증서 수, 디스크 format/mount 같은 제약은 별도 gate로 검사한다.
7. 정적 검증 뒤 실제 생성과 앱 기능 시험을 분리해 수행한다.

### 3.4 무엇을 측정하는가

의존성 평가 결과를 하나의 모호한 점수로 합치지 않는다.

| 관측 항목 | 의미 | 주의점 |
|---|---|---|
| 구성요소 존재 | 필요한 종류가 선언됐는가 | 존재만으로 연결 성공은 아님 |
| 구조 참조 | 근거 관계의 양 끝과 명시 edge가 있는가 | 개수·배치 제약까지 증명하지 않음 |
| cardinality | 한 요소가 몇 요소와 연결될 수 있는가 | 현재 설명용 metadata이며 점수에서 제외 |
| 독립 제약 gate | 다중 AZ, 동일 AZ, 인증서, mount 등 | 구현된 gate만 측정했다고 표시 |
| provider 검증 | 문법과 provider schema가 유효한가 | 실제 생성 성공과 다름 |
| 실제 생성 | `plan/apply`가 성공하는가 | 앱 기능 성공과 다름 |
| 앱 기능 | 업무 요청·재시작·장애 조건을 만족하는가 | 해당 기능별 probe가 필요 |
| 정리 | `destroy` 뒤 잔여 리소스가 0인가 | 비용과 실험 위생을 위해 필수 |

`one-to-many`라는 관계 표기는 “최소 두 개가 필요하다”는 뜻이 아니다. 예를 들어 다중 AZ 최소
2개 조건은 관계 이름에서 추론하지 않고 `availabilityZones.min=2` 같은 별도 근거와 gate로
확인한다. 마찬가지로 설정 파일에 `mount` 문자열이 있다는 사실은 재시작 뒤 데이터가 남는다는
증거가 아니다.

### 3.5 현재 확인된 범위

현재 개발축은 다음 세 가지다.

- `persistent-block-storage`: VM 재시작과 분리해 유지되는 블록 저장소
- `load-balanced-ingress`: HTTP 부하분산 진입점
- `https-load-balanced-ingress`: TLS 인증서와 HTTPS listener를 포함한 부하분산 진입점

이 세 항목은 Docker-on-VM에서 앱 동작을 바꾸는 핵심 개발축이지, 전체 클라우드 사용 사례의
대표 표본은 아니다. 고정 fixture와 동일 입력 절제실험에서 projection과 구조 참조의 효용은
확인했지만, 모든 CSP·토폴로지에서 앱 기능 향상을 인과적으로 증명한 것은 아니다. 정확한 결과와
실패 사례는 [DepKB 효과 평가](depkb-effect-evaluation-20260810.md)를 따른다.

## 4. 앱 용량 측정

### 4.1 왜 앱 이름만 보고 VM을 고르면 안 되는가

“게시판 API”, “Spring 앱”, “SQLite 사용” 같은 이름만으로 필요한 vCPU와 메모리를 알 수 없다.
같은 코드도 데이터 크기, 요청 비율, JVM 설정, 외부 API, 목표 지연시간에 따라 사용량이 달라진다.
따라서 EasyDep은 LLM이 사양을 추측하게 하지 않고, 실행 가능한 앱을 실제로 부하 시험해 하한을
계산한다.

측정 코드는 [HTTP 용량 측정 명령](../evaluation/research_protocol/commands/measure_http_capacity.py),
하한 계산은 [capacity_estimation.py](../app/core/orchestration/capacity_estimation.py)에 있다.

### 4.2 측정 전에 고정해야 할 것

비교 가능한 측정을 위해 다음 조건을 기록한다.

- 앱 이미지와 런타임 버전
- 초기 데이터와 요청 payload
- 읽기·쓰기 요청 비율
- 동시 사용자 또는 동시 요청 수
- 시험 시간과 준비 구간
- 목표 RPS, 최대 p95 지연시간, 최대 오류율
- CPU 목표 사용률과 메모리 여유 계수
- 영속 저장소가 필요하다면 보존기간과 쓰기 증가량

이 조건이 바뀌면 이전 측정값을 그대로 재사용할 수 없다.

### 4.3 측정과 계산 방법

1. 동시성을 단계적으로 높이며 처리량, 지연시간, 오류율을 측정한다.
2. 같은 시간에 컨테이너의 CPU core 사용량과 RSS 메모리를 기록한다.
3. 목표 지연시간과 오류율을 통과한 관측점만 사용한다.
4. 인스턴스당 지속 가능 RPS로 필요한 최소 인스턴스 수를 계산한다.
5. p95 CPU 사용량과 목표 사용률로 vCPU 하한을 계산한다.
6. p99 RSS와 여유 계수로 메모리 하한을 계산한다.
7. 영속 데이터는 현재 크기, 쓰기당 증가량, 쓰기 RPS, 보존시간으로 디스크 하한을 계산한다.

현재 계산식은 다음과 같다.

```text
최소 인스턴스 수 = ceil(목표 RPS / 인스턴스당 지속 가능 RPS)
vCPU 하한       = ceil(p95 CPU core / 목표 CPU 사용률)
메모리 하한     = 0.25 GiB 단위 올림(p99 RSS × 여유 계수)
예상 데이터량   = 현재 데이터 + 쓰기당 증가량 × 쓰기 RPS × 보존 초
디스크 하한     = ceil(예상 데이터량 × 디스크 여유 계수)
```

목표 처리량이 단일 인스턴스 측정 범위를 넘는데 수평 확장 가능성이 확인되지 않았다면 인스턴스
수를 임의로 늘리지 않고 질문으로 보류한다. 영속 데이터 증가량이나 보존기간이 없으면 디스크
크기도 계산하지 않는다.

### 4.4 결과 해석

용량 측정의 출력은 “이 VM이면 반드시 된다”가 아니라 **측정 조건에서 얻은 개발 하한**이다.
로컬 Docker에서 얻은 CPU 값은 실제 AWS·Azure·GCP VM의 CPU 세대, 네트워크, noisy neighbor와
다르다. 따라서 추천 후보에 실제 배포한 뒤 같은 부하 시험을 반복해야 최종 조정할 수 있다.

현재 한 개발 측정에서는 200 RPS 목표에 8 vCPU·0.5 GiB·1대라는 하한이 나왔지만, 짧은 로컬
시험에서 CPU 값이 높게 관측됐다. 이 숫자를 다른 앱이나 일반 권장 사양으로 재사용하면 안 된다.
원시 값과 한계는 [연구 결과 5절](research-results-20260810.md#5-성능비용-기반-리소스-추천)에
기록돼 있다.

## 5. 앱–클라우드 충돌 탐지와 해소

### 5.1 무엇이 충돌하는가

각 산출물이 따로 보면 정상이어도 함께 연결하면 실패할 수 있다.

- 소스는 라이브러리를 사용하지만 빌드 파일에는 의존성이 없다.
- 앱은 8080에서 듣지만 컨테이너나 로드밸런서는 80으로 연결한다.
- 앱은 `/srv/state`에 저장하지만 VM은 `/mnt/data`를 컨테이너에 연결한다.
- 로컬 디스크에만 상태를 두면서 여러 AZ의 active 인스턴스를 요구한다.
- 부팅할 때마다 디스크를 강제로 format해 기존 데이터를 지운다.
- 순서가 바뀔 수 있는 첫 번째 블록 장치를 무조건 데이터 디스크로 선택한다.

EasyDep은 이를 특정 앱 이름의 예외 목록으로 처리하지 않고 세 종류의 사실로 나눈다.

1. **앱 계약**: 빌드 의존성, 런타임 설정, listen port, 상태 경로와 durability
2. **클라우드 capability 계약**: VM, 저장소, 부하분산, TLS 등 환경이 제공해야 할 능력
3. **배포 binding 계약**: 앱 포트·경로를 컨테이너·VM·클라우드 설정에 연결한 값

이 세 계약은 외부 표준을 그대로 구현한 것이 아니라 EasyDep의 내부 연구 모델이다. TOSCA,
OAM, Kubernetes, CUE의 요구–제공–연결 분리를 참고했다. 자세한 출처와 필드 설계는
[앱–클라우드 계약 설계](app-cloud-contract-design.md)에 있다.

### 5.2 판단 방법

1. 사용자 요구에서 명시된 사실을 `intent`로 보존한다.
2. 소스, 빌드 파일, 설정, Dockerfile, IaC에서 실제 값을 관측한다.
3. 앱의 요구값과 클라우드의 제공값을 binding으로 연결한다.
4. 두 값이 일치하면 통과하고, 충돌하면 구조화된 진단을 만든다.
5. 해결 방법이 여러 개거나 사용자 의도가 필요하면 질문한다.
6. 자동 수정 가능한 경우 실패를 소유한 하위 작업만 다시 실행한다.
7. 수정 뒤 계약 검사와 앱 기능 시험을 다시 수행한다.

대표 진단은 다음과 같다.

| 진단 | 뜻 | 기본 수정 소유 작업 |
|---|---|---|
| `APP-DEP-001` | 앱이 사용하는 빌드·런타임 의존성 누락 | `implementation.logic` |
| `APP-DB-*` | DB driver, dialect, ORM 모듈 조합 불일치 | `implementation.logic` |
| `BIND-PORT-001` | 앱·컨테이너·backend 포트 불일치 | `implementation.vm_delivery` |
| `BIND-STORAGE-001` | 앱 상태 경로와 mount target 불일치 | `implementation.vm_delivery` |
| `BIND-STORAGE-DESTRUCTIVE-INIT` | 기존 데이터를 지울 수 있는 초기화 | `implementation.vm_delivery` |
| `BIND-STATE-HA-001` | 노드 로컬 상태와 다중 영역 장애 허용 충돌 | 사용자 질문 |

진단 코드와 소유 작업 연결은
[repair_routing.py](../app/core/orchestration/repair_routing.py), IaC 관측은
[iac_binding_validation.py](../app/core/orchestration/iac_binding_validation.py)에 구현돼 있다.

### 5.3 왜 전체를 처음부터 다시 만들지 않는가

요구 분석이 맞고 VM 전달만 틀렸다면 요구 분석과 앱 로직을 다시 생성할 이유가 없다. EasyDep은
완료된 단계의 manifest와 앱 snapshot이 일치하는 체크포인트만 재사용하고, 진단을 소유한 하위
작업부터 재개한다. 수정 실패 시에는 검증되지 않은 파일을 승격하지 않고 이전 checkpoint를
복원한다.

다만 코드나 입력이 바뀌어 체크포인트의 hash가 달라졌다면 억지로 재사용하지 않는다. 환경만
바뀐 연결 점검과 논문용 완전 종단 실행도 구분한다.

### 5.4 자동 수정하지 말아야 하는 경우

다음은 기술적으로 여러 답이 있으므로 사용자 의도가 필요하다.

- 상태를 외부 저장소로 옮길지, 복제할지, HA 요구를 낮출지
- CSP나 리전이 빠졌을 때 어디를 선택할지
- 성능 목표는 있지만 비용 한도가 없거나 그 반대인 경우
- 수평 확장이 가능한지 확인되지 않은 상태에서 목표 처리량이 측정을 초과한 경우

이때 시스템은 `needsQuestion` 또는 `abstained`를 반환한다. 보류는 실패가 아니라 근거 없는
추측을 막는 정상 동작이다.

### 5.5 현재 검증 수준

고정된 네 구조 불일치에서 4/4 탐지, 정상 control 0/4 오탐, 수정 소유 작업 4/4 일치를 확인했다.
동일 앱 snapshot의 실제 LLM 부분 수리에서는 세 사례 중 두 사례가 앱 테스트까지 복구됐고 저장
경로 사례는 실패를 그대로 보존했다. 이는 개발 사례의 조기 탐지와 부분 재개의 증거이지, 모든
프레임워크와 DB의 충돌을 찾는다는 증거는 아니다. 상세 결과는
[앱–클라우드 절제 평가](../evaluation/research_protocol/reports/app-cloud-ablation-evaluation.md)에 있다.

## 6. 리소스 추천

### 6.1 추천기는 무엇을 입력받는가

추천은 의존성 모델만으로 할 수 없다. 최소한 다음 정보가 필요하다.

- CSP와 정확한 리전
- 앱 용량 측정에서 얻은 최소 vCPU와 메모리
- 필요한 최소 VM 대수
- 월 compute 예산이 있다면 그 값
- steady 또는 burst 같은 트래픽 특성
- 가격 카탈로그의 수집 시각과 경고 정보

provider나 리전이 없거나 vCPU와 메모리 하한이 모두 없으면 가장 작은 VM을 추천하지 않고
보류한다.

### 6.2 후보 선택 순서

1. CSP와 리전을 정확히 일치시킨다.
2. 최소 vCPU와 메모리를 만족하지 못하는 VM을 제외한다.
3. 명시된 대수만큼의 월 compute 목록가격을 계산한다.
4. compute 예산을 넘는 후보를 제외한다.
5. steady 트래픽이면 기록된 성능 경고가 없는 후보를 우선한다.
6. 조건을 만족한 후보와 선택 근거를 함께 반환한다.

현재 선택 로직은 [vm_selection.py](../app/core/orchestration/vm_selection.py), 가격·성능 지식의 범위는
[VM 리소스 선택 문서](../app/core/cloudkb/document/vm-resource-selection.md)에 있다.

결과 상태는 세 가지다.

| 상태 | 의미 |
|---|---|
| `selected` | 현재 필터와 가격 자료에서 조건을 만족하는 후보가 있음 |
| `deferred` | provider, 리전, 용량 측정 등 판단 근거가 부족함 |
| `infeasible` | 현재 카탈로그에서 용량과 compute 예산을 함께 만족하는 후보가 없음 |

### 6.3 가격의 정확한 의미

현재 월 비용은 `시간당 VM 목록가격 × 월 환산 시간 × VM 수`다. 포함하는 것은 on-demand VM
compute 목록가격뿐이다. 다음 비용은 포함하지 않는다.

- 디스크와 snapshot
- 네트워크 egress
- 로드밸런서와 공인 IP
- 관리형 DB와 관측 서비스
- 세금, 환율, 약정·spot·기업 할인

따라서 “월 예산 통과”는 전체 클라우드 청구액이 예산 안이라는 뜻이 아니다. 추천기도 세계에서
가장 싸거나 가장 빠른 최적 해를 증명하지 않는다. **측정된 하한과 현재 카탈로그 조건을 만족하는
배포 후보**를 좁혀 주는 기능이다. 자세한 보류 정책은
[모호성·사이징 평가](../evaluation/research_protocol/reports/ambiguity-and-sizing-evaluation.md)에 있다.

## 7. 처음부터 끝까지 보는 예시

다음 요구를 가정한다.

> 서울 리전에서 메모 API를 운영한다. 재시작 뒤에도 데이터가 남아야 한다. 목표는 200 RPS,
> p95 100ms 이하, 오류율 1% 이하다. 월 compute 예산은 300달러다.

EasyDep은 다음처럼 처리한다.

1. **요구 분석**: provider와 리전, 성능 목표, 영속성, 예산을 구조화한다.
2. **의존성 분석**: `persistent-block-storage`를 선택하고 해당 CSP의 VM, 디스크, attachment,
   네트워크 구성과 참조 관계를 얻는다.
3. **앱 측정**: 고정 이미지와 대표 요청으로 RPS, p95, 오류율, CPU, RSS를 측정한다.
4. **용량 계산**: SLO를 통과한 관측점으로 vCPU·메모리·대수 하한을 만든다. 디스크 증가량이나
   보존기간이 빠졌다면 디스크 크기는 질문으로 남긴다.
5. **계약 검사**: 앱이 쓰는 경로, Docker mount target, VM mount 위치가 같은 의도를 가리키는지
   확인한다. 부팅 때 기존 디스크를 지우는 명령도 차단한다.
6. **후보 추천**: 서울 리전에서 용량 하한과 300달러 compute 예산을 만족하는 VM 후보를 찾는다.
7. **정적 검증**: Terraform 구성요소와 명시 참조, provider schema를 검사한다.
8. **클라우드 검증**: 실제 생성, ready, POST/GET, 재시작 뒤 조회를 검사한다.
9. **정리**: 리소스를 destroy하고 잔여 리소스가 없는지 확인한다.

7단계까지만 성공했다면 “IaC 후보가 정적 검증을 통과했다”고만 말해야 한다. 8단계까지 성공해야
“해당 실행에서 앱의 영속 기능이 작동했다”고 말할 수 있다. 다른 부하나 다른 VM에서도 된다는
주장은 다시 측정해야 한다.

## 8. 현재 가능한 주장과 불가능한 주장

| 구분 | 현재 말할 수 있는 것 | 아직 말하면 안 되는 것 |
|---|---|---|
| 의존성 | 공식 근거 기반의 제한된 벤더 모델과 capability projection 경로를 구현했다 | 모든 클라우드 리소스를 포괄하는 완결 모델이다 |
| DepKB 효과 | 동일 입력 개발 절제에서 평균적인 양의 차이를 관찰했다 | DepKB가 항상 성공률을 높인다는 인과 법칙이다 |
| 앱 계약 | 일부 구조 충돌을 조기에 찾고 소유 하위 작업부터 재개했다 | 모든 언어·프레임워크의 충돌을 자동 해결한다 |
| 용량 | 고정된 부하 조건에서 개발 하한을 계산한다 | 자연어만으로 실제 운영 용량을 보장한다 |
| 추천 | 하한·리전·compute 예산을 만족하는 후보를 고른다 | 총비용 또는 성능의 전역 최적해다 |
| 기능 | 개별 기능 probe가 통과한 실행 결과를 기록한다 | IaC 생성 성공만으로 앱 기능을 보장한다 |

## 9. 실무 사용 체크리스트

실행 전에 다음 질문에 답할 수 있어야 한다.

- 어느 CSP와 리전인가?
- 앱은 어떤 포트에서 요청을 받는가?
- 어떤 데이터가 재시작 뒤에도 남아야 하는가?
- 목표 RPS, p95 지연시간, 오류율은 얼마인가?
- 대표 부하와 데이터가 준비됐는가?
- 최소 vCPU·메모리는 실측했는가?
- 영속 데이터의 증가량과 보존기간을 아는가?
- HA가 필요하다면 앱 상태를 여러 인스턴스가 어떻게 공유하는가?
- compute 예산과 전체 비용 예산을 구분했는가?
- 실험 종료 후 자동 정리와 잔여 리소스 검사를 준비했는가?

답이 없는 항목은 LLM이 채워 넣을 빈칸이 아니라 질문·측정·보류의 대상이다.
